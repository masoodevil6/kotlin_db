# Plan 12.3 — ممیزی معماری و رفتار CTE

## وضعیت

**فقط بررسی و ممیزی؛ مجوز پیاده‌سازی صادر نشده است.**

این Plan رفتار و معماری فعلی CTE را پس از Planهای 12.0 تا 12.2 بررسی می‌کند. Plan 12.0 بسته‌شده باقی می‌ماند و این بررسی مجوز بازکردن دامنه یا تغییر کارهای پذیرفته‌شدهٔ آن نیست.

## هدف

معماری فعلی CTE و مسیرهای استفاده از آن را بررسی کن؛ به‌ویژه این نگرانی را که استفاده از Declaration مربوط به CTE در `FROM` ممکن است به‌جای ساخت زیرکوئری درون‌خطی، یک ورودی سطح بالای `WITH` ایجاد کند.

از ابتدا فرض نکن که مسئله فقط یک ایراد Renderer است. وابستگی‌های میان API، Builder، AST، composition و رندر را بررسی کن و اثر تغییرات اخیر را با شواهد مخزن بسنج.

## اصل معماری الزام‌آور برای بررسی

انتخاب source در `FROM` و composition صریح SQL `WITH` دو مسئولیت مستقل‌اند. DSL عمومی `FROM` sourceهایی از این نوع دارد:

- `table`: جدول یا SELECT تو‌در‌تو؛
- `model`: source مبتنی بر Model؛
- `cte`: source ساخته‌شده از یک CTE declaration.

هر سه مورد sourceهایی برای `FROM` کوئری بیرونی هستند. انتخاب source به‌تنهایی نباید تصمیم بگیرد که همان source به ورودی سطح بالای `WITH` تبدیل شود. API صریح `with(...)` سازوکار اعلام CTE در SQL `WITH` است.

این اصل قرارداد هدف ممیزی است؛ رفتار فعلی باید جداگانه از source و تست‌ها استخراج شود. این اصل مجوز تغییر API یا پیاده‌سازی نیست. اگر شواهد قرارداد فعلی با آن ناسازگار بود، ناسازگاری و نیاز به تصمیم را گزارش کن و پیش از هر پیاده‌سازی متوقف شو.

## ۱. تثبیت وضعیت واقعی مخزن

پیش از نتیجه‌گیری، وضعیت فعلی working tree و کد مرتبط را بررسی کن. تمام تغییرات موجود را حفظ کن و منشأ تغییرات را بدون شواهد به Planهای اخیر نسبت نده.

قراردادها، پیاده‌سازی‌ها و مسیرهای مرتبط زیر را بررسی کن:

- `IQueryTableApi` و پیاده‌سازی‌های آن؛
- `IQueryWithsItemApi` و پیاده‌سازی‌های آن؛
- `Cte` و `ICteDeclaration<P>`؛
- APIهای ساخت و composition مربوط به CTE؛
- `QueryTableBuilder` و `QueryRenderSelectBuilder`؛
- ASTها و Builderهای مرتبط با `FROM`، زیرکوئری مشتق‌شده و `WITH`؛
- مدیریت و ترتیب dependencyها؛
- رندر SQL مربوط به `WITH ... AS (...)` و derived table؛
- resolve کردن metadata، نام runtime، alias، خروجی‌های typed و ارجاع‌های property؛
- انتقال و ترتیب پارامترها در رندر و اجرا.

تفاوت میان تغییرات قابل مشاهده در working tree، سابقهٔ مستندشدهٔ تست‌ها و فرضیه‌های مربوط به منشأ تغییر را صریح نگه دار.

## ۲. بازسازی جداگانهٔ قراردادهای مورد انتظار

رفتار مورد انتظار را از رفتار فعلی کد جدا کن و شواهد هر دو را ثبت کن.

### ۲.۱. استفاده از Declaration در `FROM`

نمونهٔ مورد بررسی:

```kotlin
from {
    cte(declaration)
}
```

رفتار هدف برای این مسیر، استفاده از Declaration به‌عنوان source کوئری بیرونی و استفاده از محتوای SELECT آن به‌صورت زیرکوئری درون‌خطی در `FROM` است:

```sql
SELECT ...
FROM (
    SELECT ...
) AS effective_alias
```

استفاده از abstraction مربوط به CTE به‌تنهایی نباید باعث ثبت خودکار خود source به‌عنوان ورودی سطح بالای `WITH` شود. در عین حال، dependencyهای واقعی خود Declaration را جداگانه بررسی کن: بدون شواهد فرض نکن که همهٔ آن‌ها باید حذف شوند یا inline شوند. تعیین کن کدام dependencyها برای معتبرماندن SELECT درون‌خطی لازم‌اند و آیا باید به شکل مناسب در composition باقی بمانند.

این قرارداد هدف را با APIهای پذیرفته‌شده، مستندات و تست‌های مخزن تطبیق بده؛ آن را با رفتار فعلی اشتباه نگیر. اگر تغییر قرارداد عمومی برای تحقق آن لازم است، تغییر و پیامد سازگاری را فقط پیشنهاد بده.

### ۲.۲. تعریف CTE نام‌دار در `WITH`

مسیرهای مورد بررسی:

```kotlin
with(cte)
with(withName, cte)
```

رفتار مورد انتظار این مسیر، تولید CTE نام‌دار در SQL است:

```sql
WITH effective_name AS (
    SELECT ...
)
SELECT ...
```

این مسیر باید مستقل از انتخاب source در `FROM` قابل استفاده باشد. ترتیب تقدم نام، استقلال نام runtime از alias، dependencyها، هویت composition و پارامترها باید مطابق قراردادهای موجود باقی بماند. رفتار `with(...)` را برای جبران رفتار نادرست `FROM` تغییر نده.

### ۲.۳. انواع دیگر منبع

رفتار جدول خام، Model، زیرکوئری‌های موجود و دیگر انواع source را جداگانه بررسی کن. مشخص کن تغییرات اخیر هر مسیر را چگونه تحت تأثیر قرار داده‌اند. فرض نکن که هر Declaration باید در تمام مسیرها رفتار یکسانی داشته باشد؛ معنای هر ورودی را از قرارداد عمومی و شواهد واقعی استخراج کن.

برای مسیرهای `table`، `model` و `cte`، چرخهٔ عمر source را جداگانه ثبت کن: ساخت source، resolve شدن alias، اتصال خروجی‌ها و metadata، انتقال پارامترها و ثبت آن در AST. سپس مشخص کن کدام مراحل باید مشترک بمانند و کدام مرحلهٔ فعلی ناخواسته انتخاب source را به ثبت `WITH` متصل می‌کند.

## ۳. ردیابی کامل مسیرها

برای هر مسیر مرتبط، زنجیرهٔ فراخوانی را از API عمومی تا SQL و پارامترهای نهایی دنبال کن:

1. فراخوانی DSL و انتخاب source؛
2. Builder و ثبت source یا CTE؛
3. ساخت و تغییر AST؛
4. composition و گردآوری dependencyها؛ در این مرحله میان source مصرف‌شده در `FROM` و CTEهایی که صریحاً در `WITH` تعریف شده‌اند تمایز بگذار؛
5. resolve کردن نام، alias و metadata خروجی؛
6. انتخاب مسیر رندر، شامل `WITH` یا derived table؛
7. ترتیب placeholderها و پارامترهای bindشده؛
8. در صورت نیاز، مرز اجرای Query و materialization نتیجه.

برای هر مرحله، فایل، symbol و انتقال دادهٔ مؤثر را مشخص کن. نقطه‌ای را که رفتار از مسیر مورد انتظار منحرف می‌شود، فقط در صورت اثبات با کد یا تست به‌عنوان علت اعلام کن.

## ۴. ممیزی رفتار و رگرسیون‌ها

تست‌های موجود و مثال‌های مرتبط را برای این موارد بررسی کن:

- CTE در `WITH` در برابر زیرکوئری درون‌خطی در `FROM`؛
- استقلال انتخاب `table`، `model` و `cte` به‌عنوان sourceهای `FROM` از ثبت صریح `with(...)`؛
- رفتار dependencyهای یک Declaration وقتی خود Declaration به شکل source درون‌خطی مصرف می‌شود؛
- sourceهای تو‌در‌تو و composition چندسطحی؛
- ترتیب dependencyها و parameterها؛
- نام‌های تکراری و تشخیص چرخه؛
- نام runtime و تقدم نام صریح؛
- alias پیش‌فرض و alias صریح occurrence؛
- نگاشت خروجی typed و ارجاع property؛
- هویت مرجعی composition؛
- رفتار مثال‌های V1، V2 و V3 و مسیرهای عملیاتی دیگر که از Builder مشترک استفاده می‌کنند.

هر مورد را در یکی از گروه‌های زیر طبقه‌بندی کن:

- رگرسیون تأییدشده با بازتولید و شواهد؛
- نقص موجود و نامرتبط با تغییرات مورد بررسی، در صورت وجود شواهد کافی؛
- برداشت نادرست از قرارداد یا رفتار هدف؛
- مورد حل‌نشده به‌دلیل ناکافی بودن شواهد.

رفتار فعلی را بدون شاهد به‌عنوان رفتار مورد انتظار معرفی نکن و رگرسیون را بدون baseline قابل اتکا به تغییر اخیر نسبت نده.

## ۵. روش اعتبارسنجی

این Plan برای بررسی خواندنی است. سورس، تست، مثال، مستندات، تنظیمات و وضعیت Git را تغییر نده.

در صورت امکان، تست‌های موجود و مرتبط را بدون تغییر فایل‌های پروژه اجرا کن و نتیجه را ثبت کن. شکست‌های baseline را از خطاهایی که مستقیماً مسیر مورد بررسی را بازتولید می‌کنند جدا نگه دار. اگر تست کافی وجود ندارد، مشخصات تست لازم را بنویس؛ در این مرحله تست جدید پیاده‌سازی نکن.

حداقل مشخصات آزمون‌های پذیرش پیشنهادی را به‌صورت جداگانه ثبت کن:

1. `from { table { ... } }` یک SELECT تو‌در‌تو را در `FROM` رندر کند.
2. `from { model(...) }` source مدل را در `FROM` رندر کند.
3. `from { cte(declaration) }` خود Declaration را به ورودی سطح بالای `WITH` تبدیل نکند و source مناسب `FROM`، مانند `FROM (SELECT ...) AS effective_alias`، تولید کند.
4. `with(cte)` و `with(withName, cte)` همچنان CTEهای صریح `WITH` را تولید کنند.
5. alias، خروجی typed، پارامترها و ترتیب آن‌ها برای source درون‌خطی حفظ شوند.
6. dependencyهای لازم Declaration در حالت inline طبق تصمیم مبتنی بر شواهد حفظ شوند؛ تست باید روشن کند کدام dependency در SQL نهایی باقی می‌ماند و چرا.
7. مصرف یک CTE در `FROM` و اعلام همان CTE در `WITH` دو رفتار مستقل داشته باشند و یکدیگر را ناخواسته فعال یا حذف نکنند.

## ۶. خروجی‌های الزامی

گزارش ممیزی باید شامل این موارد باشد:

1. نقشهٔ معماری مسیرهای CTE و source مرتبط، با مسیر فایل‌ها و نام دقیق symbolها؛
2. قرارداد مورد انتظار هر مسیر عمومی و شواهد آن؛
3. زنجیرهٔ فراخوانی واقعی از API تا AST، composition، رندر و پارامترها؛
4. رگرسیون‌های تأییدشده، نقص‌های نامرتبط، برداشت‌های نادرست و موارد حل‌نشده، به‌صورت جداگانه؛
5. بازتولید دقیق هر مشکل تأییدشده، شامل ورودی، SQL یا نتیجهٔ مشاهده‌شده و تست مرتبط؛
6. طرح حداقلی اصلاحات احتمالی، اولویت‌بندی‌شده و محدود به مسئلهٔ اثبات‌شده؛
7. تفکیک چرخهٔ عمر sourceهای `table`، `model` و `cte` و توضیح محل ثبت فعلی آن‌ها در AST؛
8. تحلیل رفتار dependencyهای CTE-derived source در حالت inline، بدون فرض حذف یا inline کردن خودکار؛
9. کمترین تغییرات احتمالی لازم در API، Builder و AST، با فایل‌ها و symbolهای دقیق و فقط در صورت اثبات ضرورت؛
10. تست‌های پذیرش لازم برای تفکیک sourceهای `FROM` از CTEهای صریح `WITH`؛
11. محدودیت شواهد، تست‌ها یا baseline که مانع نتیجه‌گیری قطعی شده‌اند.

## محدودیت‌های قطعی

- هیچ تغییر سورس، تست، مثال، مستندات یا تنظیماتی انجام نده.
- Plan 12.0 را بازنویسی یا دوباره باز نکن.
- APIهای legacy را حذف نکن و معماری عمومی را بازطراحی نکن.
- برای جبران رفتار نامناسب `FROM`، معنای `WITH` را تغییر نده.
- راهکار renderer-only پیشنهاد نکن، مگر آنکه ردیابی کامل ثابت کند مسئولیت انحراف صرفاً در Renderer است و AST و Builder مفهوم موردنیاز را از قبل حفظ می‌کنند.
- صرفاً برای یکسان‌کردن سه نوع source، abstraction عمومی تازه‌ای پیشنهاد نکن.
- هویت Declaration را با alias مربوط به source آن یکی نگیر.
- تغییرات موجود در working tree را حفظ کن.
- هیچ فایل یا تغییری را stage، commit، reset، clean، revert یا حذف نکن.
- ممیزی را تا زمانی که مسیرها، قراردادها و شواهد گزارش نشده‌اند، تکمیل‌شده اعلام نکن.
