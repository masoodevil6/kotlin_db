## Relation Identity Decision

```text
Relation Identity:
Chosen: Unresolved
Evidence: QueryDefinition و QueryRelation در source نیستند؛ ASTهای query فقط clause data حمل می‌کنند. `ICte` یک query-provider است و `IQueryWithsItemAst.withName` نام CTE را ذخیره می‌کند. `ModelTableAliasContext`، KClass را فقط برای alias lookup به‌کار می‌برد.
Rejected Alternatives: فعلاً هیچ‌کدام به‌عنوان قرارداد پذیرفته یا رد قطعی نمی‌شوند.
Reason: source هیچ identity precedentی ندارد که انتخاب instance، explicit relation object، Kotlin class یا SQL alias را الزام کند. SQL alias در Renderer صرفاً نام رندرشده است و هویت reusable query را اثبات نمی‌کند.
Contract Impact: قبل از implementation باید owner یک use case ارائه کند که نشان دهد یک definition چند بار با aliasهای متفاوت مصرف می‌شود یا identity باید میان instanceها پایدار باشد.
```

Candidate A (QueryDefinition instance)، B (explicit Relation object)، C (Kotlin output/model class) و D (SQL alias) همگی از نظر source قابل اثبات نیستند. D با معنای فعلی alias به‌عنوان String رندرشده پشتیبانی نمی‌شود؛ اما رد آن به‌عنوان identity نیازمند تصمیم semantic است، نه صرفاً مشاهدهٔ کد.

## Output Field Identity Decision

```text
Output Field Identity:
Chosen: Unresolved
Owner: Unresolved؛ owner باید شامل هویت Relation باشد، ولی شکل آن evidence ندارد.
Property Identity: KProperty1 یک راه candidate برای مشخص کردن property است؛ repository آن را فقط برای physical Model column استفاده کرده است.
Logical Name: Unresolved؛ naming/alias conversion برای Output property تعریف نشده است.
Physical SQL Name: فقط برای physical field از `QBColumn.name` resolve می‌شود؛ این قاعده Output field name را تعیین نمی‌کند.
Evidence: `IQueryColumnsAst.ColumnAlias` فقط String nullable است و `QueryColumnsBuilder.alias(String)` مقدار خالی را به null تبدیل می‌کند.
Rejected Alternatives: `SQL alias only` به‌عنوان معادل اثبات‌شدهٔ هویت رد می‌شود؛ source نشان نمی‌دهد نام alias به‌تنهایی Relation owner یا property identity را نگه دارد.
Reason: `UserOrderStats.Output::userId` و `ImportantUsers.Output::id` در source اصلاً قابل نمایش نیستند.
```

## Output Property Binding Decision

```text
Chosen: Unresolved
Evidence: SELECT API فعلی `addColumn { column(KClass, KProperty) ; alias(String) }` دارد؛ property-based output binding یا `.as(KProperty)` وجود ندارد. SELECT AST alias را به‌صورت String نگه می‌دارد.
Required closure: owner باید تعیین کند آیا public syntax expression-first است (`.as(Output::field)`)، output-first است (`output(field) { ... }`) یا شکل دیگری. همچنین باید بگوید آیا Output property همزمان منبع نام SQL alias هست یا فقط semantic identity.
```

شواهد فعلی اجازه نمی‌دهند A/B/C را انتخاب کنیم. هیچ‌یک نباید به‌عنوان implementation contract تحویل داده شود. آنچه قابل تثبیت است: اگر semantic binding لازم باشد، باید تا زمان اعتبارسنجی پیش از rendering قابل تشخیص بماند؛ Renderer فعلی Stringهای AST را مصرف می‌کند و نباید ناگهان KProperty یا annotation بخواند.

## Relation SQL Placement Decision

```text
Chosen: Unresolved; CTE-only equivalence rejected as an assumption.
Evidence: SELECT table API مدل typed، table string و `cte(name, alias)` دارد؛ CTE AST `withName/withBody` دارد. table/JOIN source shape برای Relation عمومی یا derived table در source فعلی یافت نشد.
Required closure: owner باید حداقل use-siteهای لازم را برای Relation در CTE/FROM/JOIN/derived source مشخص کند و تعیین کند آیا یک Relation در چند source position قابل مصرف است.
```

قرارداد معنایی Relation باید از SQL placement جدا بماند؛ اما انتخاب placementهای v3 از repository evidence به‌تنهایی ممکن نیست. CTE implementation، FROM Relation و derived table همگی خارج از implementation این مرحله‌اند.

## SELECT Expression Scope Decision

**تصمیم جزئی:** physical column و aggregateهای فعلی پشتیبانی می‌شوند. Aggregate در SELECT یک `ColumnMethod` روی column است، نه یک expression tree عمومی.

**باقی unresolved:** آیا v3 شامل CASE، arithmetic، function یا expression composition می‌شود. Source برای CASE/arithmetic/function SELECT AST/API evidence ندارد. برای بستن scope، owner باید اعلام کند کدام سناریوهای 3–8 واقعاً v3 deliverable هستند. تا آن زمان هیچ generic Expression یا Selectable framework تصویب نمی‌شود.

## SQL Scope Rules Decision

`Unresolved`. Clause APIs فعلی scopeهای SELECT, FROM, WHERE, GROUP و ORDER را جدا می‌کنند؛ HAVING API مستقل در SELECT surface شناسایی نشد. هیچ Relation Field وجود ندارد که رفتار قانونی‌اش میان این scopeها اثبات شود.

برای closure لازم است تعریف شود Relation Field در کدام use siteها باید قابل استفاده باشد، dialectهای هدف کدام‌اند، و برای هر scope یک query example/test contract ارائه شود. تا آن زمان از SQL alias به‌عنوان reference عمومی استفاده نمی‌کنیم و قواعدی دربارهٔ معتبر بودن alias در همهٔ clauseها استنتاج نمی‌کنیم.

## Output Type / Nullability Decision

**تصمیم جزئی:** در این Plan، Kotlin property type و nullability فقط می‌توانند metadata مربوط به property identity باشند؛ از آن‌ها SQL type، SQL nullability یا ResultSet mapping نتیجه نمی‌گیریم. Repository typed physical reference را generic می‌گیرد، ولی `QueryColumnsAst` type parameter ندارد و aggregate result typing را مدل نمی‌کند.

**Unresolved:** آیا v3 باید type compatibility compile-time را الزام کند، فقط property reference نگه دارد، یا Output type/nullability را به قرارداد دیگری بسپارد. برای تصمیم، owner باید requirement نمونهٔ compile-time و رفتار مورد انتظار برای nullable property و aggregate output را مشخص کند. Result Mapping همچنان out of scope است.

## Candidate A vs Candidate B

| Candidate | Source-backed evaluation | تصمیم |
| --- | --- | --- |
| **A.** QueryDefinition موجود و Relation semantics جدا از آن | نزدیک‌ترین گزینه به AST render-oriented فعلی است و query clauses را از Output schema جدا نگه می‌دارد؛ اما محل دقیق ownership/output binding را حل نمی‌کند. | برای ادامهٔ طراحی گزینهٔ کم‌تغییرتر است؛ implementation contract نیست. |
| **B.** QueryRelation شامل QueryDefinition + OutputSchema | تمایز schema و SQL clauses را روشن می‌کند، اما source فعلی precedent برای OutputSchema/Relation object ندارد و نحوهٔ اتصال به SELECT item باز است. | فعلاً پذیرفته نمی‌شود؛ نیاز به owner use case و binding decision دارد. |

**Closure:** بر اساس repository می‌توان گفت Query AST فعلی خودش QueryRelation نیست. نمی‌توان A یا B را به‌طور قطعی بست، چون identity و property binding unresolved هستند. اگر owner بخواهد یک design direction برای مرحلهٔ بعد ثبت کند، A نقطهٔ شروع کم‌تغییر است و schema باید بیرون AST فعلی بماند تا خلافش ثابت شود.

## Canonical Semantic Model

بخش‌های تثبیت‌شده:

```text
Physical Model Field = KClass + KProperty1 resolved through QBTable/QBColumn metadata
SQL SELECT alias = nullable String attached to current column AST
CTE = existing named query source with nested select body
Result Mapping = separate concern, out of scope
```

بخش‌های `Relation identity`, `Output Field identity`, `Output Schema`, و ارتباط آن‌ها unresolved هستند. بنابراین canonical model کامل برای implementation صادر نمی‌شود.

## DSL Contract

قراردادهای موجود را حفظ کن:

```kotlin
column(Model::class, Model::field)
alias("sql_alias")
table(Model::class)
```

این‌ها semantics فیزیکی/SQL موجودند. برای output binding، هیچ canonical API، DSL sugar یا underlying representation تعیین نمی‌شود تا owner تکلیف identity و alias mapping را مشخص کند. `.as(Output::field)` در source موجود نیست و از نظر قرارداد تصویب نشده است.

## AST Contract

AST فعلی را به‌عنوان render AST در نظر بگیر: `IQuerySelectAst.columns` مجموعه‌ای از `IQueryColumnsAst` است؛ هر column دارای base column، optional method و optional alias string است. این ساختار Relation identity یا Output Field را حفظ نمی‌کند.

قبل از implementation باید تصمیم گرفته شود semantic metadata در Relation wrapper/schema نگه داشته می‌شود یا AST تغییر می‌کند. بر اساس evidence فعلی generic hierarchy یا model-specific AST node لازم/موجه نیست. Lowering به SQL-ready string فقط پس از validationی انجام شود که semantic identity لازم را مصرف کرده باشد.

## Builder Boundary

| Responsibility | Builder | دلیل |
| --- | --- | --- |
| KClass/KProperty physical resolution | Yes | source فعلی همین‌جا reflection و metadata resolution انجام می‌دهد. |
| Annotation resolution | Yes | `findAnnotation<QBTable/QBColumn>` در Builder است. |
| Output Field resolution | Unresolved | Output contract تعریف نشده است. |
| Relation ownership validation | Unresolved | Relation identity تعریف نشده است. |
| Scope validation | Deferred / Unresolved | Relation Field و scope rules تعریف نشده‌اند. |
| Expression validation | Deferred | generic SELECT expression contract موجود نیست. |
| AST construction | Yes | Builderهای فعلی AST clauseها را می‌سازند. |
| SQL alias generation from Output property | Unresolved | naming rule و Output binding انتخاب نشده‌اند. |

## Renderer Boundary

```text
Renderer Input: موجود بودن dialect-specific AST و render dataهای فعلی؛ در آینده فقط دادهٔ resolveشده‌ای که قرارداد AST تعیین کند.
Renderer Responsibilities: تبدیل AST فعلی به SQL dialect-specific، از جمله alias rendering.
Renderer Must Not Know: KClass/KProperty/Model annotations؛ source فعلی چنین reflectionی ندارد و metadata را پیش از آن resolve می‌کند.
```

اینکه Renderer باید `Relation`, `OutputSchema` یا `OutputField` را ببیند، رد می‌شود به‌عنوان فرض پیش‌فرض؛ هیچ evidenceای ضرورتش را نشان نمی‌دهد. semantic resolution باید بیرون Renderer انجام شود، اما مالک دقیق resolution برای Relation unresolved باقی است.

## Dialect Boundary

**Dialect-neutral:** هویت معنایی Relation و Output Field، اتصال Output property به SELECT item و query composition.

**Dialect-specific:** identifier quoting، syntax رندر alias، CTE placement syntax، derived-table syntax، function/aggregate syntax و محدودیت‌های scope مربوط به dialect.

Source از MySQL capability registry برای render استفاده می‌کند. این Plan architecture جدید Dialect نمی‌سازد و پشتیبانی dialectهای دیگر برای Relation Vision را فرض نمی‌کند.

| V1 string APIs (`tableColumn(alias,name)`, `table(name,alias)`) | حفظ شوند؛ حذف یا تغییرشان evidence ندارد. |

هیچ API حذف یا تغییر نمی‌کند. اضافه شدن API آینده باید additive باشد و بعد از تعیین identity/binding/scope قرارداد شود.

| سناریو | وضعیت | دلیل |
| --- | --- | --- |
| Direct table output | `Supported partially` | typed physical column و SELECT موجود است؛ Relation output schema ندارد. |
| Renamed output | `Supported partially` | SQL alias موجود است؛ Output property binding/identity موجود نیست. |

## Deferred / Out of Scope

* ResultSet mapping، DTO auto-mapping، serialization و constructor mapping.
* CASE framework و generic arithmetic/function/expression framework تا زمانی که v3 use cases آن را الزام کنند.
* Derived table implementation، CTE redesign و Dialect redesign.
* Execution یا migration changes، database introspection، optimization/cache و raw SQL escape hatch.
* هرگونه source/test/documentation/configuration/dependency/refactor change در این مرحله.

## Unresolved Decisions

برای بستن closure به owner/use-case evidence زیر نیاز است:

1. Relation باید با چه identityای متمایز شود، به‌خصوص هنگام reuse یک definition با aliasهای مختلف؟
2. آیا هر Relation یک Output class/property دارد؟ اگر بله، property name چگونه به logical/output SQL name متصل می‌شود؟
3. API canonical output binding چیست و آیا explicit SQL alias می‌تواند آن را override کند؟
4. v3 دقیقاً کدام placementها را می‌خواهد: CTE، FROM، JOIN یا derived table؟
5. کدام expressionها جزو v3 هستند: فقط physical columns و aggregateهای موجود، یا CASE/arithmetic/functions؟
6. Relation field در SELECT/FROM/WHERE/GROUP/HAVING/ORDER/JOIN کجا باید مصرف شود و dialectهای هدف کدام‌اند؟
7. Kotlin output type و nullability فقط metadata هستند یا compile-time compatibility requirement دارند؟ SQL type inference و Result Mapping همچنان جدا بمانند.
8. پس از پاسخ موارد فوق، owner باید Candidate A/B را با یک use-site end-to-end انتخاب کند.

تا وقتی پاسخ این موارد ثبت نشده، API pseudo-code نباید به public contract تبدیل شود.

## Implementation Readiness

`Status: Ready for Traceability`

Closure جزئی انجام شد: physical model reference، metadata resolution، SQL alias، مرز renderer و سازگاری APIهای فعلی قابل تثبیت‌اند. اما Relation Identity، Output Field Identity، Binding، SQL Placement، scope rules و type/nullability behavior هنوز unresolved هستند. شواهد موجود برای `Implementation Ready` کافی نیستند؛ برای تصمیم‌گیری لازم است owner use caseها و قراردادهای فوق را مشخص کند. هیچ implementation انجام نشده است.
