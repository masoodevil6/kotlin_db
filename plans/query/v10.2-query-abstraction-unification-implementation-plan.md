# پلن 10.2 — اجرای یکپارچه‌سازی abstractionهای Relationمحور به Query

## وضعیت

**Blocked — پیش‌شرط معماری برقرار نیست**

Implementation آغاز نشده است. Plan 10.1 هنوز در وضعیت نیازمند ردیابی Repository و تصمیم‌گیری API قرار دارد و نگاشت دقیق و تأییدشده‌ای برای نمادهای مقصد ارائه نکرده است.

### اقدام لازم برای ادامه

1. ردیابی Repository در Plan 10.1 را کامل کن.
2. قرارداد canonical مربوط به declaration و نقش نهایی `QueryDeclaration` را تعیین کن.
3. نوع runtime مقصد را پس از بررسی مسئولیت‌ها و تداخل نام‌ها تعیین کن.
4. امضاهای دقیق declaration، ساخت runtime، source composition و output API را تثبیت کن.
5. شواهد، آثار سازگاری و تست‌های regression لازم را برای تصمیم‌ها ثبت کن.
6. نگاشت نهایی را پیش از آغاز implementation تأیید کن.

تا زمان بسته‌شدن تصمیم‌های فوق، هیچ source، test، Help یا documentationای برای این migration تغییر نکند.

**شرط ازسرگیری:** Plan 10.1 به وضعیت `Ready for Plan 10.2` برسد و نگاشت API تأیید شده باشد.

## Execution Gate — شرط اجباری شروع Implementation

وضعیت فعلی این Plan برابر `Blocked` است. وجود مراحل اجرایی در ادامهٔ سند به معنی مجوز اجرای آن‌ها نیست.

پیش از هرگونه تغییر در source، test، Help یا documentation:

1. خروجی نهایی Plan 10.1 را از Repository یا سند تأییدشدهٔ آن بازیابی و بررسی کن.
2. وجود جدول کامل نگاشت API، امضاهای دقیق مقصد، مالکیت moduleها، تصمیم canonical declaration، تصمیم runtime naming و آثار سازگاری را تأیید کن.
3. وضعیت Plan 10.1 را بررسی کن. فقط وضعیت صریح `Ready for Plan 10.2` مجوز عبور از این مرحله است.
4. اگر خروجی نهایی Plan 10.1 موجود نیست، ناقص است، هنوز تصمیم unresolved دارد یا وضعیت تأییدشدهٔ آن قابل اثبات نیست، هیچ تغییری انجام نده. فقط موارد مفقود، شواهد فعلی Repository و اقدام لازم برای رفع blocker را گزارش کن.
5. اگر پیش‌شرط‌ها برقرار هستند، نگاشت تأییدشده را با Repository فعلی تطبیق بده. هر تعارض جدیدی که تصمیم معماری یا امضای مصوب را تحت تأثیر قرار می‌دهد باید پیش از تغییر بخش وابسته گزارش و حل شود.

**ممنوعیت قطعی:** بر اساس نام‌های پیشنهادی، متن اولیهٔ Plan 10.1، حدس معماری یا برداشت شخصی از هدف پروژه، نگاشت جایگزین نساز. همچنین وضعیت Plan 10.1 را خودسرانه تأییدشده اعلام نکن.

پس از عبور از Execution Gate، مراحل implementation همین سند را به ترتیب اجرا کن. اگر Gate بسته نشد، خروجی این اجرا فقط گزارش blocker است و وضعیت نهایی باید `Implementation Status: BLOCKED` باشد.

## هدف

نگاشت تأییدشدهٔ Plan 10.1 را پیاده‌سازی کن تا declaration، runtime composition و APIهای source/output مربوط به abstraction فعلی `QueryRelation` یک مدل واحد و Queryمحور داشته باشند.

این پلن نباید نام یا امضای جدیدی اختراع کند. نام‌ها، نوع‌ها و امضاهای دقیق implementation باید عیناً از جدول نهایی Plan 10.1 گرفته شوند.

## منبع حقیقت برای Implementation

پیش از شروع:

1. وضعیت نهایی Plan 10.1 را بررسی کن.
2. نگاشت کامل symbolها، امضاهای عمومی، مالکیت module و تصمیم‌های سازگاری را از Plan 10.1 بردار.
3. اگر نماد، امضا یا تصمیمی unresolved است، اجرای بخش وابسته را متوقف کن و همان blocker را گزارش کن.
4. هیچ تصمیم بسته‌شدهٔ Plan 10.1 را با سلیقهٔ نام‌گذاری یا convenience تغییر نده.

## Scope

فقط تغییرهایی را انجام بده که مستقیماً در نگاشت تأییدشدهٔ Plan 10.1 آمده‌اند:

* یکپارچه‌سازی قرارداد declaration؛ حذف قرارداد عمومی موازی فقط مطابق تصمیم بسته‌شده.
* مهاجرت نوع runtime و factoryهای composition به نام‌ها و امضاهای Queryمحور تأییدشده.
* مهاجرت متدهای نام‌گذاری و ساخت Query که در نگاشت آمده‌اند.
* مهاجرت APIهای source composition و output-column که مستقیماً در نگاشت آمده‌اند.
* مهاجرت مستقیم V3 declarations و مصرف‌کننده‌هایشان.
* به‌روزرسانی تست‌ها، Help metadata و documentation فقط در نقاطی که migration تأییدشده لازم می‌کند.

هیچ قابلیت جدیدی برای composition اضافه نکن.

## محدودهٔ نام Relation

معیار حذف نام‌های Relation فقط به symbolهای مربوط به abstraction هدف محدود است؛ یعنی قرارداد declaration، runtime composition و APIهای source/output که Plan 10.1 در scope قرار داده است.

این پلن مجوز حذف یا rename موارد زیر نیست:

* کاربرد عمومی مفهوم relational database.
* APIها و annotationهای مستقل CTE.
* نام‌ها یا مفاهیم Relation که به abstraction مهاجرت‌شونده تعلق ندارند.

برای هر مورد مبهم، پیش از تغییر مشخص کن آیا در نگاشت Plan 10.1 هدف بوده است یا نه. موارد خارج از نگاشت را تغییر نده.

## مراحل اجرا

### مرحلهٔ 1 — ثبت baseline

* `git status` و diffهای موجود را ثبت کن و تغییرهای نامرتبط کاربر را حفظ کن.
* تست‌های contract و buildهای پایهٔ مربوط به moduleهای متأثر را اجرا کن، اگر محیط اجازه می‌دهد.
* SQL، parameter values/order، dependency order و رفتار مثال‌های V3 را به‌عنوان baseline ثبت کن.

### مرحلهٔ 2 — مهاجرت declaration canonical

* نوع و قرارداد canonical را دقیقاً مطابق Plan 10.1 اعمال کن.
* declarationهای مستقیم و مبتنی بر base class را به یک شیوهٔ عمومی واحد منتقل کن.
* حذف یا نگه‌داشتن هر interface/base class فقط مطابق نگاشت مصوب باشد.
* declaration owner و Typed Output validation را حفظ کن.

### مرحلهٔ 3 — مهاجرت runtime و composition

* نوع runtime، factoryها و extensionهای composition را مطابق نام‌ها و امضاهای مصوب مهاجرت بده.
* نام Query و متد declaration را در call siteهای هدف به‌روزرسانی کن.
* source composition و output-column API را فقط طبق نگاشت تغییر بده.
* identity، dependencies، cycle detection، source alias صریح و CTE lowering را حفظ کن.
* ترتیب و مقدار parameterها را حفظ کن.

### مرحلهٔ 4 — مهاجرت مصرف‌کننده‌ها و artifactها

* چهار declaration نمونهٔ V3 و تمام مصرف‌کننده‌های وابسته را طبق نگاشت مهاجرت بده.
* تست‌ها، Help metadata و documentation متأثر را به‌روزرسانی کن.
* APIها و annotationهای مستقل CTE و بخش‌های نامرتبط مثال‌ها را دست‌نخورده نگه دار.

### مرحلهٔ 5 — جست‌وجو و cleanup محدود

* جست‌وجوی repository را برای symbolهای قدیمی انجام بده.
* occurrenceهای باقی‌مانده را به موارد مجاز، مثل سند تاریخی یا CTE مستقل، نسبت بده.
* فقط occurrenceهای متعلق به abstraction هدف و در محدودهٔ مصوب را حذف یا مهاجرت بده.
* refactor و cleanup نامرتبط انجام نده.

## حفظ رفتار و سازگاری

در طول migration موارد زیر باید بدون تغییر بمانند:

* SQL رندرشده و رفتار Dialect.
* parameter values و ترتیب آن‌ها.
* validationها و error behavior.
* Typed Output owner resolution و alias semantics.
* composition تو‌در‌تو، dependency ordering و چرخه‌ها.

* execution ownership، executor boundary و result contracts.

اثر source compatibility باید دقیقاً مطابق Plan 10.1 باشد. اگر سازگاری API عمومی با نگاشت مصوب در تعارض است، خودسرانه compatibility layer اضافه نکن؛ implementation مربوط را متوقف و blocker را گزارش کن.

* تست dependency ordering، چرخه، CTE lowering و parameter ordering.
* تست‌های contract و builder متأثر.

* جست‌وجوی repository برای نمادهای قدیمی در محدودهٔ abstraction هدف.
* `git diff --check`.

گزارش باید command واقعی و نتیجهٔ هر verification را درج کند. تست یا build اجرا‌نشده را PASS اعلام نکن.
