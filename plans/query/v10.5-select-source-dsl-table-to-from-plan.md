# Plan 10.5 — اصلاح نام DSL منبع SELECT از `table` به `from`

## هدف

نام DSL سطح بالای تعیین‌کنندهٔ منبع اصلی در `QueryRenderSelectBuilder` از `.table { ... }` به `.from { ... }` تغییر کند تا نام API با معنای تعیین source در SELECT سازگار باشد.

```kotlin
// شکل فعلی
query.select { ... }
    .table { table(UserModel::class) }

// شکل هدف
query.select { ... }
    .from { table(UserModel::class) }
```

## شواهد فعلی Repository

- `IQueryRenderSelectApi` در `data_base/query/api/src/main/kotlin/interfaces/api/select_api/query_render_select/IQueryRenderSelectApi.kt` متد عمومی زیر را دارد:

  ```kotlin
  fun table(blockTable: IQueryTableApi.() -> Unit): IQueryRenderSelectApi
  ```

- همین interface از قبل `from(QueryRelation, alias)` را نیز دارد. این overload برای استفاده از Query به‌عنوان source/CTE است و بخشی از این rename نیست.
- `QueryRenderSelectBuilder.table(blockTable)` در `data_base/query/builder/src/main/kotlin/ast/select_builder/query_render_select/QueryRenderSelectBuilder.kt` با `QueryTableBuilder` همان source مربوط به `QueryTableAst` را می‌سازد.
- تابع درونی `IQueryTableApi.table(...)` منبع جدول یا Model را تعیین می‌کند؛ این نام با متد سطح بالای `QueryRenderSelectBuilder.table { ... }` یکی نیست و باید حفظ شود.
- call siteهای نمونهٔ SELECT در `data_base/query/example/src/main/kotlin/v1/queries/select` و `v2/queries/select` از متد سطح بالا استفاده می‌کنند.
- تست‌های Builder، به‌ویژه `QueryRelationContractTest`, `TypedModelReferenceTest` و `QueryMetadataResolutionTest`، مواردی از `.table { ... }` روی `QueryRenderSelectBuilder` دارند که باید به API هدف منتقل شوند.
- `.table { ... }` در INSERT، UPDATE، DELETE، JOIN itemها و بدنهٔ declarationهای Query قراردادهای جداگانه دارد و خارج از این تغییر است.

## قرارداد مقصد

1. API عمومی SELECT برای source جدولی این امضا را فراهم می‌کند:

   ```kotlin
   fun from(blockTable: IQueryTableApi.() -> Unit): IQueryRenderSelectApi
   ```

2. پیاده‌سازی آن همان رفتار متد فعلی `table(blockTable)` را حفظ می‌کند: همان guardها، `QueryTableBuilder`، mutation در AST و بازگرداندن Builder.
3. overload موجود زیر بدون تغییر باقی می‌ماند:

   ```kotlin
   fun from(relation: QueryRelation, alias: String? = null): IQueryRenderSelectApi
   ```

   بنابراین `from { ... }` source جدولی را تنظیم می‌کند و `from(queryRelation, alias)` همچنان Query/CTE را به‌عنوان source تنظیم می‌کند.
4. تابع داخلی `table(...)` در بلوک، `tableColumn(...)`، `tableAttribute(...)`، متدهای `table { ... }` برای عملیات CRUD و متدهای JOIN تغییر نام نمی‌دهند.
5. ساختار AST، SQL، پارامترها، ترتیب پارامترها، aliasها، join، where و رفتار rendering تغییر نمی‌کنند.
6. متد قدیمی `IQueryRenderSelectApi.table(blockTable)` صرفاً برای سازگاری نگه داشته نمی‌شود؛ حفظ آن تنها در صورت وجود سیاست صریح سازگاری عمومی قابل طرح است و به تصمیم جداگانه نیاز دارد.

### تمایز overloadهای `from`

```kotlin
from { table(UserModel::class) }       // source جدولی از طریق IQueryTableApi
from(queryRelation, "active_users")   // QueryRelation/CTE به‌عنوان source
```

در بررسی Kotlin overload resolution تأیید شود که هر دو شکل بدون cast و بدون ابهام قابل فراخوانی‌اند. امضای lambda باید همان receiver فعلی `IQueryTableApi.() -> Unit` را حفظ کند.

## محدودهٔ تغییر

- تغییر قرارداد عمومی `IQueryRenderSelectApi`.
- تغییر پیاده‌سازی `QueryRenderSelectBuilder` با reuse دقیق مسیر فعلی ساخت source جدولی.
- به‌روزرسانی تمام call siteهای داخل Repository که متد سطح بالای `QueryRenderSelectBuilder.table { ... }` را برای SELECT صدا می‌زنند.
- به‌روزرسانی تست‌های مستقیم Builder و هر fixtureای که همان API را مصرف می‌کند.

## خارج از محدوده

- تغییر overload `from(QueryRelation, alias)` یا رفتار QueryRelation/CTE.
- تغییر `IQueryTableApi.table(...)` یا محتوای بلوک `from { ... }`.
- تغییر DSLهای INSERT، UPDATE، DELETE، JOIN، CTEهای مستقل یا declarationهای Query.
- تغییر AST، renderer، executor، semantics پارامترها یا metadata.
- rename سراسری هر متد یا نمادی که نام `table` دارد.
- نگه‌داشتن overload قدیمی صرفاً با فرض سازگاری؛ سیاست سازگاری باید با شواهد Repository مشخص شود.

## سازگاری API

حذف `table(blockTable)` از interface عمومی، source compatibility مصرف‌کننده‌هایی را که این متد را فراخوانی می‌کنند می‌شکند و ممکن است binary compatibility را نیز تحت تأثیر قرار دهد. این Plan هیچ تضمین binary compatibility نمی‌دهد.

پیش از implementation باید سیاست صریح پروژه دربارهٔ سازگاری API عمومی بررسی شود. اگر الزام رسمی برای حفظ متد قدیمی وجود داشت، پیاده‌سازی متوقف و تعارض گزارش شود؛ بدون تصمیم جداگانه، alias/deprecated overload جدیدی برای `table { ... }` اضافه نشود.

## مراحل implementation پس از صدور مجوز

1. وضعیت Git را بررسی و تغییرهای موجود را حفظ کن.
2. قرارداد `IQueryRenderSelectApi`, `QueryRenderSelectBuilder` و تمام call siteها را پیش از تغییر دوباره جست‌وجو کن.
3. امضای `from(blockTable)` را کنار `from(QueryRelation, alias)` اضافه و behavior قبلی source جدولی را به آن منتقل کن.
4. متد عمومی `table(blockTable)` را مطابق قرارداد سازگاری تأییدشده حذف کن؛ متدهای `table` مستقل خارج از scope باقی بمانند.
5. فقط call siteهای source جدولی در SELECTها و تست‌های متناظر را به `.from { ... }` تغییر بده.
6. بررسی کن که نمونه‌های CRUD، JOIN و Query declaration تغییر ناخواسته نکرده باشند.

## Regression و Verification

- تست کن که `.from { table(Model::class) }` و `.from { table("users").alias("u") }` همان AST و SQL متناظر با baseline قبلی بسازند.
- تست کن مقدارها و ترتیب پارامترهای source و شرط‌ها تغییر نکنند.
- تست کن `.from { cte("...").alias("...") }` همان رفتار قبلی داشته باشد.
- تست کن `from(queryRelation, alias)` همچنان CTE، alias و dependencyهای قبلی را حفظ کند.
- تست compile-level برای overload resolution هر دو فرم `from` اضافه یا اصلاح شود.
- تمام call siteهای SELECT برای متد حذف‌شده را جست‌وجو کن؛ موارد `table` مربوط به CRUD، JOIN و داخل DSL باید جدا از این جست‌وجو باقی بمانند.
- تست‌های `:data_base:query:builder:test` و `:data_base:query:example:test` و buildهای `:data_base:query:api:build`, `:data_base:query:builder:build`, `:data_base:query:example:compileKotlin` را اجرا کن.
- `git diff --check` را اجرا کن. هیچ نتیجه‌ای را بدون اجرای command موفق اعلام نکن.

## معیار پذیرش

- برای تنظیم source جدولی SELECT، API سطح بالا `.from { ... }` باشد.
- overload موجود `from(QueryRelation, alias)` بدون تغییر semantics باقی بماند.
- هیچ call site اجرایی SELECT از `.table { ... }` سطح بالا استفاده نکند.
- `table(...)` داخل بلوک همچنان برای تعیین جدول، Model یا CTE در دسترس باشد.
- SQL، AST، aliasها، پارامترها و ترتیب آن‌ها نسبت به baseline رفتار یکسان داشته باشند.
- موارد `table { ... }` در CRUD، JOIN و declarationهای Query دست‌نخورده بمانند.
