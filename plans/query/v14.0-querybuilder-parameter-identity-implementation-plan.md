# Plan 14.0 — Implementation Plan: پارامترهای هویت‌محور

این سند اجرای مرحله‌ای [Plan 14.0](v14.0-querybuilder-parameter-identity-plan.md) را مشخص می‌کند. تصمیم‌های معماری در Plan اصلی مرجع‌اند؛ این سند API یا رفتار مستقل دیگری تعریف نمی‌کند.

**Status:** Implementation Not Authorized  
**محدوده:** QueryBuilder parameter identity، AST metadata، render occurrences، ordered JDBC execution و مهاجرت کنترل‌شده.  
**خارج از محدوده:** بازطراحی Migration، تغییر عمومی مدل `SqlParameter`، بازطراحی Model metadata، حذف فوری `BuiltQuery` یا تغییر SQLهای نامرتبط.

## قواعد اجرای مشترک

- پیش از هر مرحله `git status --short --branch` و diff همان لحظه ثبت شوند. Stage/commit/reset/checkout/clean/revert ممنوع است.
- تغییرات موجود Plan 13.1، چه tracked چه untracked، حذف یا بازنویسی خودکار نشوند. ابتدا هر تداخل با فایل‌های فاز تعیین و گزارش شود.
- هر مرحله: تغییر محدود، مرور diff، compile/test مرتبط، گزارش و توقف در صورت شکست خارج از دامنه.
- Build/Test فقط پس از مجوز implementation مرحلهٔ مربوط مجاز است؛ این سند به‌تنهایی مجوز نیست.
- برای مسیرهای خارج از DB لازم از PreparedStatement double استفاده شود. Integration test فقط با propertyهای دیتابیس معتبر اجرا شود.

## Phase 1 — قرارداد handle و API سازگاری

### فایل‌ها و نمادها

- `data_base/core/src/main/kotlin/query/reader/SqlParamData.kt` (`SqlParameter`؛ انتظار: بدون تغییر shape)
- `query:api`:
  - `interfaces/api/select_api/conditions_item/IQueryConditionsApi.kt`
  - `interfaces/api/select_api/conditions_item_collection/IQueryConditionsCollectionApi.kt`
  - `interfaces/api/insert_api/column_insert/IQueryColumnInsertApi.kt`
  - `interfaces/api/update_api/column_update/IQueryColumnUpdateApi.kt`
- implementerهای API در `query:builder`.

### کارها

1. Preserve: constructor, `of`, `nullOf`, `name`, `value`, `sqlType`, `bind`, data-class methods.
2. Add فقط entry pointهای reuse لازم برای گرفتن همان `SqlParameter` reference: scalar, collection, insert column و update column؛ call signatureهای فعلی دست‌نخورده بمانند.
3. هر اجرای `sideValue(name, value)` و هر collection item بدون handle مشترک، تعریف تازه بسازد؛ no canonicalization by name/value/type.
4. جست‌وجو و ثبت همهٔ implementerهای API قبل از تغییر. تست source-level caller و `SqlParameter.copy()`/equality semantics اضافه شود.

### معیار خروج

- Existing call sites همچنان compile می‌شوند.
- Same instance reuse فقط از API صریح ممکن است.
- دو object با فیلدهای برابر به دو identity map entry تبدیل می‌شوند.
- هیچ id یا public constructor parameter جدیدی به `SqlParameter` اضافه نشده است.
- اگر interface evolution با policy بیرونی نامعلوم ریسک دارد، بدون قرارداد approved ABI ادعای سازگاری نده و نتیجه را به reviewer گزارش کن.

## Phase 2 — AST و Builder references در تمام عملیات Query

### فایل‌های اصلی

- `query:ast/interfaces/select_interface/conditions_item/IQueryConditionsAst.kt` و schema متناظر فقط اگر نوع فیلد نیاز به تغییر ضروری داشته باشد.
- `query:ast/interfaces/select_interface/conditions_item_collection/IQueryConditionsCollectionAst.kt`
- `query:ast/schema/select_schema/conditions_item_collection/QueryConditionsCollectionAst.kt`
- `query:ast/interfaces/insert_interface/column_insert/IQueryColumnInsertAst.kt`
- `query:ast/schema/insert_schema/column_insert/QueryColumnInsertAst.kt`
- `query:ast/interfaces/update_interface/column_update/IQueryColumnUpdateAst.kt`
- `query:ast/schema/update_schema/column_update/QueryColumnUpdateAst.kt`
- Builderها:
  - `QueryConditionsBuilder.kt`
  - `QueryConditionsCollectionBuilder.kt`
  - `QueryConditionsGroupsBuilder.kt`, `QueryWhereBuilder.kt`
  - `QueryJoinsBuilder.kt`, `QueryJoinsItemBuilder.kt`
  - `QueryTableBuilder.kt`, `QueryRenderSelectBuilder.kt`
  - `QueryWithsBuilder.kt`, `QueryWithsItemBuilder.kt`
  - `QueryColumnInsertBuilder.kt`, `QueryColumnUpdateBuilder.kt`
  - `QueryRenderDeleteBuilder.kt` (برای تایید مسیریابی DELETE/WHERE)

### کارها

1. scalar/collection AST refs را typed یا به‌نحوی محدود نگه دار که exact `SqlParameter` instance حفظ شود؛ `conditionSideRight: Any?` فقط در صورت ضرورت و با حفظ valueهای غیرپارامتری باقی بماند.
2. collection list را به قرارداد type-safe پارامتر مهاجرت بده.
3. INSERT/UPDATE AST typed parameter reference اضافه کند و `columnTag` legacy حفظ شود.
4. تمامی nested builderها همان reference را حفظ کنند؛ nested list `addAll` نباید objectها را clone کند.
5. `IQueryApi.params` فعلاً حفظ شود؛ برای مسیر قدیم compatibility list باشد و برای مسیر جدید identity منبع آن نباشد.
6. `ParameterBindingScope` و scope injection را حذف/بی‌اثر کن فقط پس از آنکه builderها دیگر canonicalization مبتنی بر name/value نداشته باشند و تست reuse صریح جایگزین شده باشد. فایل untracked موجود را خودکار حذف نکن؛ مصرف‌ها را بررسی کن.

### تست خروج

- scalar، collection، JOIN، WHERE، nested table، inline CTE، explicit WITH، INSERT، UPDATE و DELETE AST را بررسی کن.
- هر AST reference با `assertSame` با handle اصلی یکسان باشد.
- مستقل‌های هم‌نام با `assertNotSame` باشند.
- SQL قدیمی در موارد بدون collision عیناً برابر بماند.

### فایل‌ها

- visitor و metadata model جدید زیر `data_base/query/meta_data/src/main/kotlin/`

## Phase 4 — Render result و occurrence order

### فایل‌ها

- `query:dialect`: `interfaces/IRenderContext.kt`, `interfaces/ISqlDialect.kt` فقط در صورت افزودن capability قرارداد، `manager/RenderContext.kt`, `manager/BaseSqlDialect.kt`, `manager/RenderSessionRegistry.kt`.
- `query:renderer`: `MySqlQueryConditionCapability.kt`, `MySqlQueryConditionCollectionCapability.kt`, `MySqlQueryRenderInsertCapability.kt`, `MySqlQueryRenderUpdateCapability.kt`, `MySqlQueryCapability.kt`, `MySqlQueryTableCapability.kt`, join/with renderers و tests.
- Built-in dialects: `MySqlDialect.kt`, `MariaDbDialect.kt` (MariaDB inheritance/registration verification).

### کارها

1. Replace untyped `Pair<String?, List<Any>>`/`MutableList<Any>` tracker with typed `RenderedQuery(sql, occurrences)`.
2. Thread the same render session through recursive registry dispatch.
3. Emit one occurrence per placeholder and only when final SQL contains that condition/node.
4. Record render order from actual SQL order (WITH/dependency order, nested sources, JOIN, WHERE, other parameter-bearing clauses), not Builder call order.
5. Keep named display SQL unchanged. Add lexical conversion/count validation for JDBC syntax; test colon-looking literals/comments or explicitly reject unsupported raw placeholder injection.
6. Built-in MySQL/MariaDB implement the occurrence capability. A custom `ISqlDialect` without it stays on legacy path where names are unambiguous; identity collisions fail clearly.

### تست خروج

- `where → from` vs `from → where`.
- Nested CTE order; shared reference multiple occurrences.
- Omitted/invalid condition produces no rendered occurrence; unmatched AST definition then follows explicit unused-definition rejection.
- exact legacy SQL comparisons; direct/custom dialect behavior.

## Phase 5 — Ordered execution transport و JDBC

### فایل‌ها

- `data_base/core/src/main/kotlin/query/reader/BoundQuery.kt` (یا هم‌مکان در `BuiltQuery.kt`؛ نام نهایی باید یکتا باشد)
- `data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt`
- `data_base/manager/execute/src/main/kotlin/manager/QueryExecute.kt`
- `data_base/manager/execute/src/test/kotlin/manager/QueryExecuteContractTest.kt`

### کارها

1. `BoundQuery` حامل non-null SQL و `List<SqlParameter<*>>` occurrence-ordered باشد؛ همان ref می‌تواند چند بار فهرست شود.
2. ordered execution overload برای SELECT/INSERT/UPDATE/DELETE اضافه شود؛ route فعلی `BuiltQuery` و `executeTable` legacy باقی بماند.
3. Bind بدون map بر اساس نام و مستقیم بر اساس occurrence index انجام شود.
4. count mismatch/missing value/type و Binding failure پیش از/در همان lifecycle فعلی resourceها مدیریت شود؛ connection/statement ownership semantics حفظ شود.
5. تست PreparedStatement proxy verifies `setObject(index, value, sqlType)` و `setNull(index, sqlType)` دقیقاً به ترتیب.

### معیار خروج

Legacy `BuiltQuery` testها بدون تغییر رفتار؛ Ordered path قابلیت same-name distinct-value را اثبات کند؛ هیچ وابستگی `manager:execute → query:*` اضافه نشود.

### کارها

1. `QueryBuilderExecutor` AST metadata استخراج کند، dialect render result بگیرد، identity membership/unused validation انجام دهد و `BoundQuery` بسازد.
2. QueryBuilder SELECT/CTE execution از ordered low-level path استفاده کند.
3. Queryهایی که عمداً legacy/manual AST هستند فقط با criteria روشن به BuiltQuery name path بروند؛ mixed AST silent fallback نداشته باشد.

### معیار خروج

## Phase 9 — حذف امن موقت‌ها و بستن Plan

### کارها

1. جست‌وجو و consumer map برای `ParameterBindingScope`, `RenderSessionRegistry`, occurrence `Any` list و name-based execution داخلی QueryBuilder.
2. فقط helperهایی که هیچ مصرف‌کنندهٔ لازم ندارند حذف شوند. Public `BuiltQuery`/`QueryConsumer.sql()`/Migration path طبق compatibility contract باقی می‌مانند.
3. آزمون‌های قدیمی حفظ یا به legacy contract محدود شوند؛ assertionها ضعیف نشوند.
4. Build/testهای module matrix دوباره اجرا، شکست baseline از regression جدا و نتیجه ثبت شود.

### معیار نهایی

`query:executor` برای QueryBuilderهای جدید از AST-derived identity و renderer occurrences استفاده کند؛ duplicate name binds درست؛ manual BuiltQuery/Migration legacy behavior پابرجا؛ custom dialect capability boundary مستند؛ هیچ tracked/untracked کار قبلی بدون شواهد حذف نشده؛ `git diff --check` پاک.

## توقف و محدودیت‌ها

- اگر API public reuse نیاز به breaking change برای implementerهای خارج مخزن داشته باشد، تغییر را اجرا نکن تا تصمیم نسخه‌بندی جدا صادر شود.
- اگر dialect custom قادر به occurrence tracking نباشد، همان dialect fail-fast شود؛ placeholder identity از SQL استخراج نشود.
- اگر AST node یا pathی از SQL نام‌دار بدون `SqlParameter` استفاده کند، آن مسیر legacy یا unsupported تلقی شود تا قرارداد جداگانه تعیین شود.
- اگر manager-level ordered execution بدون تغییر نامرتبط در `manager:execute` ممکن نباشد، مرحله متوقف و مرز API گزارش شود.
- تغییر Migration، public `BuiltQuery` یا خروجی‌های نامرتبط نیاز به مجوز مستقل دارد.
