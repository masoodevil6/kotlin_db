# Plan 14.0 — Implementation Plan: پارامترهای هویت‌محور

این سند اجرای مرحله‌ای [Plan 14.0](v14.0-querybuilder-parameter-identity-plan.md) را مشخص می‌کند. تصمیم‌های معماری در Plan اصلی مرجع‌اند؛ این سند API یا رفتار مستقل دیگری تعریف نمی‌کند.

**Status:** Implementation Not Authorized  
**Design status:** Implementation Ready; this label is not an authorization.
**محدوده:** QueryBuilder parameter identity، AST metadata، render occurrences، ordered JDBC execution و مهاجرت کنترل‌شده.  
**خارج از محدوده:** بازطراحی Migration، تغییر عمومی مدل `SqlParameter`، بازطراحی Model metadata، حذف فوری `BuiltQuery` یا تغییر SQLهای نامرتبط.

## قواعد اجرای مشترک

- پیش از هر مرحله `git status --short --branch` و diff همان لحظه ثبت شوند. Stage/commit/reset/checkout/clean/revert ممنوع است.
- هر تغییر ازقبل‌موجود حفظ شود. فایل‌های مرتبط تاریخی با Plan 13.1 ممکن است هم‌اکنون committed یا تغییرکرده باشند؛ status/diff همان زمان ملاک است و انتساب از حدس ممنوع.
- هر مرحله: تغییر محدود، مرور diff، compile/test مرتبط، گزارش و توقف در صورت شکست خارج از دامنه.
- Build/Test فقط پس از مجوز implementation مرحلهٔ مربوط مجاز است؛ این سند به‌تنهایی مجوز نیست.
- برای مسیرهای خارج از DB لازم از PreparedStatement double استفاده شود. Integration test فقط با propertyهای دیتابیس معتبر اجرا شود.

## Phase 1 — قرارداد handle و API سازگاری

### فایل‌ها و نمادها

- `data_base/core/src/main/kotlin/query/reader/SqlParamData.kt` (`SqlParameter`؛ انتظار: بدون تغییر shape)
- `query:api` extension files پیشنهادی:
  - `data_base/query/api/src/main/kotlin/interfaces/api/select_api/conditions_item/QueryParameterExtensions.kt`
  - `data_base/query/api/src/main/kotlin/interfaces/api/select_api/conditions_item_collection/QueryParameterExtensions.kt`
- API contracts موجود `IQueryConditionsApi` و `IQueryConditionsCollectionApi` فقط برای تایید extension receiver؛ interfaceها member جدید نمی‌گیرند.

### کارها

1. Preserve: constructor, `of`, `nullOf`, `name`, `value`, `sqlType`, `bind`, data-class methods.
2. دو extension محدود اضافه شود: `IQueryConditionsApi.sideValue(parameter)` و `IQueryConditionsCollectionApi.addParameter(parameter)`. هر دو handle را بدون copy/canonicalization مستقیماً به AST و compatibility `params` list اضافه کنند.
3. `addParameter(parameter)` دقیقاً یک collection element/placeholder می‌افزاید؛ برای افزودن value تازه، `addParam(value)` فعلی می‌ماند و same-scope canonicalization خود را حفظ می‌کند.
4. value-based Builder APIs و `ParameterBindingScope.canonical()` را در این فاز تغییر نده. INSERT/UPDATE handle API اضافه نکن.
5. `SqlParameter.copy()` از نظر `equals` برابر ولی از نظر `===` مستقل است؛ تست extensionها این تفاوت را نشان دهد. چون interface contract تغییر نمی‌کند، implementerهای بیرونی برای member جدید source recompilation لازم ندارند؛ public binary promises را همچنان ادعا نکن.

### معیار خروج

- Existing call sites همچنان compile می‌شوند.
- Same instance reuse از extension handleمحور ممکن است؛ value-based API قدیمی همچنان equivalent calls را در همان scope canonical می‌کند.
- دو handle object مستقل—even اگر فیلدها و data-class equality برابر باشند—در extension مسیر identity دو identity دارند.
- ترکیب یک handle extension با فراخوانی value-based هم‌نام، دو binding در IdentityAware مسیر می‌سازد؛ در صورت conflict، فراخوانی مستقیم/Legacy از طریق `BuiltQuery` conflict را هنگام validation گزارش می‌کند.
- هیچ id یا public constructor parameter جدیدی به `SqlParameter` اضافه نشده است.
- اگر interface evolution با policy بیرونی نامعلوم ریسک دارد، بدون قرارداد approved ABI ادعای سازگاری نده و نتیجه را به reviewer گزارش کن.

## Phase 2 — AST و Builder references در تمام عملیات Query

### فایل‌های اصلی

- `query:ast/interfaces/select_interface/conditions_item/IQueryConditionsAst.kt` و schema متناظر فقط اگر نوع فیلد نیاز به تغییر ضروری داشته باشد.
- `query:ast/interfaces/select_interface/conditions_item_collection/IQueryConditionsCollectionAst.kt`
- `query:ast/schema/select_schema/conditions_item_collection/QueryConditionsCollectionAst.kt`
- `query:ast/interfaces/insert_interface/column_insert/IQueryColumnInsertAst.kt`
- `query:ast/schema/insert_schema/column_insert/QueryColumnInsertAst.kt`
- `query:ast/interfaces/update_interface/column_update/IQueryColumnUpdateAst.kt`
- `query:ast/schema/update_schema/column_update/QueryColumnUpdateAst.kt`
- Builderها:
  - `QueryConditionsBuilder.kt`
  - `QueryConditionsCollectionBuilder.kt`
  - `QueryConditionsGroupsBuilder.kt`, `QueryWhereBuilder.kt`
  - `QueryJoinsBuilder.kt`, `QueryJoinsItemBuilder.kt`
  - `QueryTableBuilder.kt`, `QueryRenderSelectBuilder.kt`
  - `QueryWithsBuilder.kt`, `QueryWithsItemBuilder.kt`
  - `QueryColumnInsertBuilder.kt`, `QueryColumnUpdateBuilder.kt`
  - `QueryRenderDeleteBuilder.kt` (برای تایید مسیریابی DELETE/WHERE)

### کارها

1. Scalar `conditionSideRight: Any?` همان reference را می‌گیرد و انواع غیرپارامتری شناخته‌شده را نگه می‌دارد؛ identity path برای نوع ناشناخته fail-fast می‌کند.
2. `paramsCollection` به فهرست `SqlParameter<*>` یا قرارداد نوع‌دار هم‌ارز تغییر کند؛ raw `Any`/`toString()` فقط در Legacy representation باقی بماند.
3. INSERT/UPDATE column AST فیلد nullable typed `SqlParameter<*>` بگیرد و `columnTag` را برای SQL نام‌دار و Legacy حفظ کند؛ Builder همان object را هم در AST و هم compatibility list نگه دارد.
4. nested Builderها/Composition فقط references را منتقل کنند؛ `addAll` referenceها را clone نمی‌کند. scope injection موجود حفظ شود.
5. `IQueryApi.params` و ترتیب/محتوای فعلی projection را حذف یا بازتعریف نکن؛ identity execution آن را منبع binding نمی‌داند.
6. `ParameterBindingScope` را حذف نکن. `canonical()` برای `sideValue(name,value)` و `addParam(value)` همان same-scope equal reuse و same-name conflict timing را نگه می‌دارد. Extension handleمحور از آن bypass می‌کند.

### تست خروج

- scalar، collection، JOIN، WHERE، nested table، inline CTE، explicit WITH، INSERT، UPDATE و DELETE AST را بررسی کن.
- هر AST reference با `assertSame` با handle اصلی یکسان باشد.
- مستقل‌های هم‌نام با `assertNotSame` باشند.
- value-based same-scope reuse/conflict فعلی همان نتیجه و همان زمان خطا را حفظ کند.
- handle extension همان instance را در AST نگه دارد؛ equal-but-distinct و `copy()` distinct بمانند.
- SQL visible در موارد موجود بدون collision عیناً برابر بماند.

## Phase 3 — اسکلت ماژول و تثبیت مرز قرارداد `query:meta_data`

این فاز عمداً پیش از پیاده‌سازی traversal و پیش از هر اتصال به Renderer یا Executor انجام می‌شود. هدفش ایجاد ماژول و تثبیت سطح قرارداد/وابستگی است؛ هنوز مسئولیت‌های اجرایی metadata به مسیر Query وصل نمی‌شوند.

### فایل‌ها

- `settings.gradle.kts`
- `data_base/query/meta_data/build.gradle.kts`
- `data_base/query/meta_data/src/main/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadata.kt`
- `data_base/query/meta_data/src/main/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadataExtractor.kt`
- `data_base/query/meta_data/src/test/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadataTest.kt`
- task پیشنهادی `verifyQueryMetadataDependencyBoundary` در `data_base/query/meta_data/build.gradle.kts`

### قرارداد، پیش‌نیازها و کارها

1. `settings.gradle.kts` ماژول `:data_base:query:meta_data` را ثبت کند؛ build آن فقط project dependency به `:data_base:core` و `:data_base:query:ast` داشته باشد.
2. فقط قرارداد کوچک cross-module تعریف شود: `QueryParameterRepresentation`; `QueryParameterMetadata` با `containsDefinition(...)` و `validateOccurrences(...)`; و `QueryParameterMetadataExtractor.inspect(ast: IQueryAst)`. یک interface/plugin SPI یا model عمومی برای metadataهای دیگر نساز.
3. پیاده‌سازی `QueryParameterMetadata` backing identity membership را پنهان کند؛ collection معمولی مبتنی بر `equals` نباید هویت را collapse کند. امضای public فقط تا حد لازم برای دسترسی `query:executor` public باشد.
4. هیچ production source در `query:renderer`, `query:executor` یا `manager:execute` هنوز این contract را مصرف نکند و هیچ dependency از metadata به آن لایه‌ها اضافه نشود.
5. `verifyQueryMetadataDependencyBoundary` project dependencyهای production مستقیم را بررسی کند: در `implementation` فقط core و query:ast مجازند؛ resolved `compileClasspath` نیز نباید project component ممنوعی داشته باشد. وابستگی ناخواسته به Builder, Dialect, Renderer, Executor, Manager یا Migration باید verification را fail کند.

### معیار خروج

ماژول در Gradle قابل‌ساخت است؛ قراردادهای محدود cross-module تثبیت شده‌اند؛ verification مرز dependency فقط core و query:ast را می‌بیند؛ هنوز مصرف‌کنندهٔ Renderer/Executor ندارد؛ هیچ cycle یا edge معکوس ایجاد نشده است. تست traversal و رفتار در فاز بعد انجام می‌شود.

## Phase 4 — پیاده‌سازی استخراج و اعتبارسنجی metadata

### فایل‌ها

- `data_base/query/meta_data/src/main/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadata.kt`
- `data_base/query/meta_data/src/main/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadataExtractor.kt`
- `data_base/query/meta_data/src/test/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadataTest.kt`

### کارها

1. Visitor صریح تمام nodeهای واقعی جدول AST در Plan اصلی را طی کند: SELECT, WITH, derived query, JOIN, WHERE/group/condition/collection و leafهای فعلی، همچنین INSERT/UPDATE/DELETE و childهای واقعی آن‌ها.
2. `IQueryAst` sealed نیست؛ نوع/مسیر node ناشناخته باید خطای روشن دهد. `default no-op`, reflection و Legacy fallback در visitor مجاز نیست.
3. definitionهای AST بر مبنای `===` یکتا شوند؛ دو object مستقل حتی با `equals()` برابر، مستقل باقی بمانند؛ استفادهٔ چندباره از همان reference یک definition با occurrenceهای متعدد است.
4. طبقه‌بندی سه‌حالته طبق Plan اصلی انجام شود: `IdentityAware`, `LegacyOnly`, `MixedOrUnsupported`. در درخت INSERT/UPDATE، typed field همراه `columnTag` همان ستون فقط یک منبع است؛ legacy slot فقط وقتی typed field خالی است.
5. `validateOccurrences` membership هر occurrence را با identity در definitionهای AST بررسی کند؛ تکرار occurrence معتبر است؛ definition بی‌استفاده مجاز و بدون binding باقی می‌ماند؛ occurrence بیرون از AST خطاست.
6. برای APIهای جدید، `IQueryApi.params`, SQL text, name/value و reflection منبع استخراج identity نیستند.

### معیار خروج و تست

Node coverage matrix، duplicate reference، equal-but-distinct و `copy()`, classification هر سه mode, unused definition مجاز, invalid occurrence ردشده و unknown-node fail-fast آزموده شوند. تست‌ها فقط به core/ast و خود metadata وابسته باشند؛ Renderer/JDBC/Builder runtime هنوز درگیر نیست.

## Phase 5 — SELECT Renderer با occurrence و dual SQL output

### فایل‌ها

- `query:dialect`: `interfaces/IRenderContext.kt`, capability type کنار `ISqlDialect`, `manager/RenderContext.kt`, `manager/BaseSqlDialect.kt`, `manager/RenderSessionRegistry.kt`.
- `query:renderer`: `MySqlQueryConditionCapability.kt`, `MySqlQueryConditionCollectionCapability.kt`, `MySqlQueryCapability.kt`, `MySqlQueryTableCapability.kt`, JOIN/WITH/recursive rendererها و tests. Insert/update renderer در Phase 8 می‌آید.
- Built-in dialects: `MySqlDialect.kt`, `MariaDbDialect.kt` (MariaDB inheritance/registration verification).

### کارها

1. جایگزین قرارداد موقت `Pair<String?, List<Any>>`/collector untyped با `RenderedQuery(displaySql, jdbcSql, parameterOccurrences)` typed.
2. `IRenderContext` یک render mode می‌گیرد و helper اتمی `renderParameter(SqlParameter)` فراهم می‌کند: display mode `:name`; JDBC mode `?` و افزودن همان ref به occurrence list.
3. همان nested registry/session در recursive WITH/derived/table/JOIN rendererها منتقل شود. شرط scalar فقط پس از موفقیت کامل render placeholder/occurrence بدهد؛ collection برای هر پارامتر دقیقاً یک `?`/occurrence بسازد.
4. دو pass روی AST یکسان اجرا شوند: normal SQL نام‌دار و positional JDBC SQL. Source فعلی Rendererها AST را mutate نمی‌کند، اما آزمون determinism لازم است. ترتیب هر دو pass بر اساس clause render order است؛ Builder call order یا `params` list استفاده نمی‌شود.
5. هیچ SQL post-processing/regex/lexer برای جست‌وجو یا replace `:name` انجام نشود. تنها typed parameter node به `?` تبدیل می‌شود؛ colon داخل quote/comment/identifier و raw SQL دست‌نخورده می‌ماند. Parameterهای untyped در slot پارامتردار فقط Legacy هستند و در query mixed رد می‌شوند.
6. SQL نام‌دار خروجی `ISqlDialect.render(ast)` حفظ شود. Built-in MySQL و MariaDB capability dual-render را پیاده کنند. IdentityAware mode با custom dialect فاقد capability fail-fast دارد و به Legacy برنمی‌گردد.

### تست خروج

- `where → from` vs `from → where`: display SQL تاریخی برابر، JDBC SQL و occurrences مطابق placeholder-order.
- nested CTE/derived query order، JOIN، explicit WITH، collection IN و reference مشترک در چند occurrence.
- parameterless/omitted condition: نه `?` نه occurrence؛ AST definition باقی‌مانده خطا نیست.
- quoted single/double strings، backtick identifier و commentهای line/block که متن colon-like دارند، عیناً در هر دو خروجی بمانند.
- unknown/mixed parameter AST و custom dialect فاقد capability خطای مشخص دهد؛ مسیر Legacy فقط از classifier/entrypoint Legacy استفاده کند.
- SQL نام‌دار با `ISqlDialect.render` و render فعلی bit-for-bit مقایسه شود.

## Phase 6 — Ordered execution transport در مرز JDBC

### فایل‌ها

- `data_base/manager/execute/src/main/kotlin/query/BoundQuery.kt`
- `data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt`
- `data_base/manager/execute/src/main/kotlin/manager/QueryExecute.kt`
- `data_base/manager/execute/src/test/kotlin/manager/QueryExecuteContractTest.kt`

### کارها

1. `BoundQuery` حامل non-null positional `jdbcSql` و `List<SqlParameter<*>>` occurrence-ordered باشد؛ همان ref می‌تواند چندبار بیاید. این transport در `manager:execute` است تا `core` و Migration از آن مستقل بمانند.
2. ordered execution overload برای SELECT/INSERT/UPDATE/DELETE اضافه شود؛ route فعلی `BuiltQuery` و `executeTable` legacy باقی بماند.
3. Bind بدون map بر اساس نام و مستقیم بر اساس occurrence index انجام شود.
4. QueryBuilderExecutor پیش از ساختن/فرستادن `BoundQuery` موارد mixed/unknown و membership خطا را رد کند؛ ordered manager در lifecycle فعلی statement/resource هر occurrence را به index متناظر bind کند. Manager به AST یا SQL name parsing وابسته نشود.
5. تست PreparedStatement proxy verifies `setObject(index, value, sqlType)` و `setNull(index, sqlType)` دقیقاً به ترتیب.

### معیار خروج

`BuiltQuery` contract tests بدون تغییر؛ PreparedStatement proxy نشان دهد occurrenceهای 11/22/33 index/value/type درست دارند؛ هیچ dependency از `manager:execute` به `query:*` اضافه نشود. `BoundQuery` برای ورودی positional است؛ اعتبار SQL و تعداد emission را مسیر renderer/QueryBuilderExecutor تضمین می‌کند.

## Phase 7 — اتصال metadata، renderer و SELECT/CTE executor

### فایل‌ها

- `data_base/query/executor/src/main/kotlin/interfaces/IQueryBuilderExecutor.kt`
- `data_base/query/executor/src/main/kotlin/manager/QueryBuilderExecutor.kt`
- `data_base/query/executor/src/main/kotlin/result/QueryConsumer.kt`
- تست‌های `QueryConsumerTest.kt`, `SmartQueryResultTest.kt`, Builder CTE tests.

### کارها

1. Direct SELECT execution در `QueryBuilderExecutor` پیش از connection، `query:meta_data.inspect(ast)` را صدا بزند.
2. `IdentityAware` فقط capability renderer + `BoundQuery` positional را مصرف کند؛ `LegacyOnly` فقط از `BuiltQuery(sql, params)` استفاده کند؛ `MixedOrUnsupported` fail-fast شود. بعد از انتخاب mode، هیچ errorای به mode دیگر fallback نشود.
3. `IQueryBuilderExecutor.executeOut(...)` generic و `IQueryExecute.execute(BuiltQuery)` به‌عنوان entry pointهای صریح Legacy حفظ شوند. Direct Builder API route از AST classification می‌آید، نه از parameter names/values.
4. `QueryConsumer.sql()` همچنان `BuiltQuery` نام‌دار تولید می‌کند و duplicate conflict آن طبق Legacy contract می‌ماند.
5. `blockQueryInfo` همان projection فعلی `query.params.associate { name to value }` را حفظ کند (duplicate key: آخرین مقدار در ترتیب `params`); callback map در bind path مصرف نشود.
6. `sql(queryBuilder)` و خروجی نمایشی، display SQL فعلی را نگه دارند. Built-in `QueryBuilderExecutor` direct SELECT identity support می‌دهد؛ custom `IQueryBuilderExecutor` بیرونی خارج از کنترل مخزن است و binary/source policy آن نامعلوم باقی می‌ماند.

### معیار خروج

سه سطح values `11/22/33` در هر دو clause-call order به PreparedStatement درست Bind می‌شوند؛ metadata/occurrence identity از AST تا manager قابل‌ردیابی است. تست‌های LegacyOnly، MixedOrUnsupported و unknown node اثبات کنند fallback خاموش رخ نمی‌دهد.

## Phase 8 — Mutation QueryBuilder

### فایل‌ها

- Insert/Update Builder, AST و renderer files معرفی‌شده در Phase 2/5.
- `QueryBuilderExecutor`, `IQueryExecute`, `QueryExecute` ordered operation overloads.
- تست‌های query builder mutation و `manager:execute`.

### کارها

1. INSERT/UPDATE Builder هر parameter ساخته‌شده را در typed AST field و `columnTag` compatibility mirror نگه دارد. `columnTag` تنها source legacy است؛ اگر typed field در identity representation خالی باشد، representation mixed/invalid اعلام شود.
2. INSERT/UPDATE renderer از helper dual-mode استفاده کند؛ DELETE از condition/where occurrence path موجود بهره ببرد.
3. `QueryBuilderExecutor` برای INSERT/UPDATE/DELETE classification و `BoundQuery` را به‌ترتیب همین route SELECT استفاده کند؛ direct `executeOut` همچنان Legacy entry point باشد.
4. `executeTable` و تمام Migration flows legacy بمانند؛ هیچ dependency به `query:meta_data` نگیرد.

### معیار خروج

INSERT/UPDATE/DELETE same-name independent identity tests موفق؛ SQL نام‌دار قدیمی unchanged؛ unrendered definitions bind نشوند؛ Migration suite unchanged.

## الحاقیهٔ ممیزی نهایی Plan 14.0 — الزامات اجرایی تکمیل‌شده

این الحاقیه با بخش‌های متناظر Plan اصلی هماهنگ است و اگر توضیح قبلی ابهام داشت، معیار اجرا همین‌جاست. وضعیت **Implementation Ready / Not Authorized** باقی می‌ماند.

### A. API handle بدون تغییر interface

در Phase 1 extensionها در `query:api` و روی interfaceهای عمومی موجود تعریف می‌شوند؛ افزودن member جدید به `IQueryConditionsApi` یا `IQueryConditionsCollectionApi` مجاز/لازم نیست. دلیل قابلیت اجرا این است که `IQueryApi` propertyهای mutable عمومی `ast` و `params` را expose می‌کند و ASTهای متناظر slotهای mutable دارند: `IQueryConditionsAst.conditionSideRight: Any?` و `IQueryConditionsCollectionAst.paramsCollection: MutableList<Any>`.

- `sideValue(SqlParameter<*>)` همان reference را در scalar AST slot و compatibility `params` ثبت کند.
- `addParameter(SqlParameter<*>)` همان reference را در collection AST slot و compatibility `params` ثبت کند.
- از overload extension به نام `addParam(SqlParameter)` استفاده نشود: member عمومی generic `addParam(T)` بر extension هم‌نام اولویت دارد و می‌تواند پارامتر را دوباره wrap کند.
- call site باید extension را import کند. این extensionها API عمومی افزایشی‌اند، اما interface binary signatures را تغییر نمی‌دهند؛ تضمین ABI بیرونی همچنان خارج از شواهد مخزن است.

تست Phase 1 باید صرفاً reference equality در AST، یک‌بار اضافه‌شدن به `params` سازگاری، حفظ SQL موجود و عدم canonicalization handle مستقل را ثابت کند.

### B. قرارداد نهایی dual SQL rendering: دو pass

روش منتخب دو pass است. `IAstRenderer.render` و `IRendererRegistry.render` فقط یک `String?` می‌دهند؛ بنابراین dual output واقعی در یک traversal به تغییر قرارداد نتیجه و بازنویسی composition تمام rendererها نیاز دارد. در محدودهٔ فعلی، دو pass با mode/session مستقل، کم‌تغییرتر است و traversal clause موجود را حفظ می‌کند:

1. pass نمایشی با named placeholders موجود؛
2. pass اجرایی با `?` و occurrence collector typed؛
3. هر دو pass روی همان AST immutable-for-render اجرا و ساختار SQL آن‌ها با fixture/test مقایسه شود.

`MySqlQueryCapability.render` ترتیب traversal built-in را تثبیت می‌کند: WITH → SELECT → table/FROM → JOIN → WHERE → GROUP → ORDER → LIMIT → OFFSET. `RenderSessionRegistry` occurrence collector را از dispatcher به recursive renderها می‌رساند. تست determinism برای built-in MySQL و MariaDB شرط پذیرش است. Renderer سفارشی که stateful/non-deterministic باشد یا occurrence capability لازم را ارائه نکند در IdentityAware رد می‌شود؛ اجرای دو pass به‌تنهایی پشتیبانی آن را تضمین نمی‌کند. قرارداد تک‌خروجی `ISqlDialect.render(ast)` و نتیجهٔ نام‌دار موجود برای مسیر compatibility حفظ شوند.

### C. پوشش classifier و سه invariant مستقل

فاز metadata باید branch و تست پوشش برای همهٔ slotهای این ماتریس داشته باشد:

| Slot | Identity-aware source | Legacy source/قاعده |
|---|---|---|
| scalar condition `conditionSideRight` | `SqlParameter` reference | `String` خام candidate است؛ در کنار typed refs موجب `MixedOrUnsupported` می‌شود؛ هویت از متن استخراج نشود. column/expression AST خودش binding نیست؛ مقدار runtime ناشناخته unsupported است. |
| collection `paramsCollection` | همهٔ items از نوع `SqlParameter` | item غیرپارامتری که Renderer با `toString()` به placeholder نامی تبدیل می‌کند Legacy است؛ با typed item مخلوط نشود. |
| WHERE/JOIN/groups و nested/derived/CTE bodies | traversal بازگشتی به scalar/collection slots | هر node ناشناخته fail-fast. |
| INSERT/UPDATE | typed column parameter ref هدف؛ `columnTag` اختیاری و matching فقط mirror نام است؛ در نبود tag، نام نمایشی از handle گرفته می‌شود | `columnTag` بدون typed ref legacy است. tag و handle ناسازگار invalid/mixed است. |
| DELETE | WHERE scalar/collection slots | مانند شرط‌ها. |
| SELECT outputs و option leaves فعلی | slot پارامتری فعلی ندارند | leaf شناخته‌شده؛ extension AST ناشناخته fail-fast تا visitor/test افزوده شود. |

`IQueryApi.params`/flat builder params بخشی از AST نیست و extractor آن را identity definition فرض نمی‌کند. این فهرست compatibility projection و منبع Legacy است. سه validation جدا و اجباری‌اند:

1. **definition membership:** هر occurrence reference باید `===` در مجموعهٔ AST definitions باشد؛ unused AST definition مجاز و تکرار occurrence همان reference مجاز است.
2. **placeholder-emission count:** تنها helper typed هر بار دقیقاً یک `?` و یک occurrence بسازد؛ برابری تعداد emissionهای ثبت‌شده با occurrences اعتبارسنجی شود. SQL text scanning برای شمردن `?` ممنوع است؛ raw positional placeholder در IdentityAware unsupported است.
3. **JDBC occurrence order:** ترتیب فراخوانی helper باید با ترتیب placeholderهای پارامتری SQL نهایی یکی باشد و occurrence شمارهٔ `i` به JDBC index `i+1` برود. این با تست‌های independent از membership/count بررسی شود.

Definition membership در extractor، emission/count در typed render result یا validation نزدیک آن، و ترتیب در PreparedStatement/JDBC test هرکدام مالک و معیار جدا داشته باشند؛ هیچ‌یک به برابری تعداد definitions و occurrences فروکاسته نشود.

### D. مرز `.sql()` و `BuiltQuery` در مسیر Legacy

Phase route-selection باید تصریح کند:

- `QueryConsumer.sql()` و `InsertQueryConsumer.sql()`, `UpdateQueryConsumer.sql()`, `DeleteQueryConsumer.sql()` خروجی `BuiltQuery(namedSql, query.params)` می‌دهند؛ APIهایشان occurrence identity را حمل نمی‌کنند.
- `BuiltQuery(sql, params)` و `getListParamNames()` بر اساس regex/name-map هستند. برای دو binding مستقل هم‌نام با مقادیر یا sqlType متفاوت، ساخت container ممکن است ولی Legacy validation/اجرا conflict می‌دهد. Bindingهای هم‌نام برابر نیز به یک name-map entry collapse می‌شوند و استقلال identity حفظ نمی‌شود.
- بنابراین پشتیبانی binding مستقل هم‌نام فقط برای direct IdentityAware execution route معتبر است. `.sql()`، `BuiltQuery` دستی، `executeOut(...)` generic، `IQueryExecute` name route و Migration Legacy باقی می‌مانند؛ محدودیت این مسیرها باید در docs/API notes و acceptance test ثبت شود.
- `blockQueryInfo` از `Map<String, Any?>` است؛ نام‌های تکراری به یک entry تبدیل می‌شوند (در `associate` مقدار متأخر باقی می‌ماند). این callback صرفاً diagnostic است و نباید به‌عنوان binding representation یا اثبات مقادیر هر occurrence معرفی شود.

### E. تکمیل آزمون پذیرش این ممیزی

به تست ماتریس موجود اضافه شود:

1. API compilation/contract test که extensionها را از روی interface reference اجرا کند و نشان دهد همان reference در AST/compatibility list است، بدون member جدید.
2. metadata tests برای raw `String` در condition، item غیر SqlParameter در collection، `columnTag` تنها، typed column همراه tag سازگار/ناسازگار، ترکیب typed و legacy، تمام nested childها و unknown AST.
3. سه آزمون مجزا برای membership (unused definition مجاز، occurrence بیرونی رد)، emission count (یک placeholder به ازای emission و شرط حذف‌شده بدون occurrence) و JDBC order (SQL clause order مطابق indexهای bind).
4. determinism دو pass روی همان AST با MySQL/MariaDB: named SQL قدیمی حفظ شود؛ positional SQL تنها placeholderهای typed را تبدیل کند؛ order sidecar با SQL تطابق داشته باشد.
5. legacy test نشان دهد `QueryConsumer.sql()`/mutation `.sql()` و `BuiltQuery` دو مقدار مستقل هم‌نام را نمایش/اجراپذیر نمی‌کنند، duplicate متعارض طبق contract رد می‌شود و map diagnostic lossy می‌ماند؛ هم‌زمان direct IdentityAware path همان occurrences را درست bind می‌کند.

اجرای این آزمون‌ها و تمام پیاده‌سازی‌های مندرج در مراحل همچنان به authorization مرحله‌ای نیاز دارند. این الحاقیه صرفاً طرح را دقیق می‌کند.
