# Plan 5.1: API مصرف Query محور برای Smart Execute

## Status

```text
Ready for Traceability
```

این سند Plan و محدودهٔ کار را تعریف می‌کند؛ در این مرحله Contract نهایی یا Implementation تصویب نشده است. ابتدا باید Traceability و سپس Decision Closure انجام شود. تا زمان بسته‌شدن تصمیم مالکیت facade، هیچ source یا test تغییر نکند.

## هدف

Plan 5.0 قابلیت‌های Smart Result Consumption را پیاده‌سازی و contract آن‌ها را تثبیت کرده است. Plan 5.1 فقط فاصلهٔ API مصرف‌کننده را بررسی می‌کند:

```kotlin
queryManager.get(query)
```

به API مصرفی نزدیک‌تر به:

```kotlin
val query = /* query اجرایی */
query.get { result -> ... }
query.first { result -> ... }
query.sql()
```

این هدف نباید باعث شود Query Builder مسئول اجرای JDBC شود.

## Plan 5.0 Baseline

این contractها بسته هستند و Plan 5.1 نباید آن‌ها را تغییر دهد:

* `IQueryBuilderExecutor.first(...)` و `get(...)`، `QueryRow` و `sql(...)` در لایهٔ Executor قرار دارند.
* `QueryRow` غیر generic است و فقط با SQL output alias قابل دسترسی است.
* `first` ردیف اول را materialize می‌کند؛ نبود ردیف `Success(null)` است و limit یا ordering ضمنی اضافه نمی‌شود.
* `get` تمام ردیف‌ها را materialize می‌کند؛ نبود ردیف `Success(emptyList())` است.
* materialization در lifetime معتبر `ResultSet` انجام می‌شود.
* API قدیمی `IQueryBuilderExecutor.execute(...)`، `IQueryExecute.executeSelect(...)` و `ExecuteResult<ResultSet>` حفظ می‌شوند.
* `sql()` فقط SQL را render می‌کند؛ execution، connection و parameter interpolation ندارد.
* `execute(DataType)`، Query Result DataType و conversion در Plan 5.0 به Separate Contract موکول شده‌اند و خارج از scope این Plan هستند.

## Scope

فقط این موارد بررسی شوند:

1. مالکیت query construction و execution در source فعلی.
2. وجود یا نبود execution-facing facade/handle قابل استفادهٔ مجدد.
3. کوچک‌ترین bridge برای ارائهٔ API مصرفی `query.get()`, `query.first()` و `query.sql()` بدون انتقال execution به Builder.
4. نحوهٔ دسترسی V1.1 به facade و حفظ V1 به‌عنوان baseline.
5. source و binary compatibility و module dependencyهای لازم.
6. تست‌ها و buildهای لازم برای verification پس از Decision Closure.

## خارج از Scope

* تغییر semantics مربوط به Plan 4.0 یا QueryRelation.
* تغییر `QueryRow`، alias contract، `first/get` یا `sql()` در Plan 5.0.
* پیاده‌سازی `execute(DataType)` یا type conversion.
* حذف یا جایگزینی APIهای low-level فعلی.
* ORM، DTO mapping، result schema یا generic result type.
* raw SQL escape hatch، registry، global context، reflection dispatcher یا ThreadLocal executor.
* تغییر Help، مگر اینکه Traceability نشان دهد برای API نهایی واقعاً لازم است.
* refactor کردن مثال‌های V1.

## مسئلهٔ API فعلی

الگوی فعلی V1.1 برای هر SELECT هم query و هم Executor را به helper می‌دهد:

```kotlin
executeSmartSelectV1_1(queryManager, query(), title, aliases)
```

سپس helper عملیات `queryManager.get(queryBuilder = query, ...)` را فراخوانی می‌کند. در نتیجه consumer اجرای Smart را از طریق Executor می‌بیند.

هدف API consumer این است:

```kotlin
query.get { result -> ... }
```

اما query ساخته‌شده از `example.query()` در حال حاضر `IQueryRenderSelectApi` است و Executor در آن موجود نیست. روش اتصال execution ownership به query-facing facade هنوز باید از source evidence و تصمیم مالک مشخص شود.

## مالکیت فعلی

```text
QueryRenderSelectBuilder
    → ساخت AST و نگهداری parameters

IQueryBuilderExecutor / QueryBuilderExecutor
    → rendering و Smart Result Consumption و dispatch اجرای query

IQueryExecute / QueryExecute
    → low-level JDBC execution و lifecycle مربوطه
```

Plan 5.1 باید این جداسازی را حفظ کند. `QueryRenderSelectBuilder` نباید connection بسازد، JDBC اجرا کند یا `ResultSet` مصرف کند.

## Traceability موردنیاز

پیش از Decision Closure، source جاری را برای موارد زیر بررسی کن:

* تمام declarationها و implementationهای `IQueryRenderSelectApi` و `IQueryBuilderExecutor`.
* تمام call siteهای `first/get/sql/execute` و هر facade، adapter یا query handle احتمالی.
* همهٔ module dependencyها در API، Builder، Executor، Example و `manager:execute`.
* نحوهٔ ساخت و تزریق `QueryBuilderExecutor` در مثال‌ها، managerها و entry pointها.
* lifecycle query builder: آیا یک query قابل reuse است و آیا parameters یا AST پس از اجرا تغییر می‌کنند؟
* dependency direction؛ به‌ویژه ممنوعیت dependency معکوس Builder → Executor بدون تصمیم مالک.
* source/binary compatibility مصرف‌کنندگان فعلی و return typeهای `IExampleV1.query()` و نسخه‌های مرتبط.
* تمام APIهای `first/get/sql` در Plan 5.0 و callback/error behavior آن‌ها.
* wiring واقعی اجرای V1.1 و اینکه executor از کجا به query-facing object می‌رسد.
* Help و `Main(args)` فقط برای مشخص‌کردن اینکه انتخاب Example/parameterها به این bridge وابسته است یا نه.

برای هر نتیجهٔ معماری:

```text
Repository Evidence
↓
Interpretation
↓
Decision
```

## API هدف و مرز تصمیم

Target consumer syntax:

```kotlin
query.get { result -> ... }
query.first { result -> ... }
query.sql()
```

این syntax به‌تنهایی تعیین نمی‌کند که `query` چه concrete typeای دارد یا Executor چگونه به آن متصل می‌شود. این موارد باید در Decision Closure روشن شوند.

به‌خصوص این دو شرط را هم‌زمان بررسی کن:

1. Consumer نباید برای هر عملیات Smart، `queryManager.get(query)` یا `queryManager.first(query)` را صدا بزند.
2. Construction-facing Builder نباید execution owner شود.

اگر `val query = example.query(); query.get { ... }` با حفظ این دو شرط از wiring موجود قابل دسترسی نباشد، این تناقض را صریحاً برای تصمیم مالک ثبت کن؛ syntax هدف را با global state یا dependency معکوس به‌زور محقق نکن.

## Candidate Architectureها

این گزینه‌ها فقط برای ارزیابی هستند و تا زمان Decision Closure هیچ‌کدام Adopt نشده‌اند.

### Candidate A: متدهای execution روی `IQueryRenderSelectApi`

```kotlin
query.get { ... }
```

بررسی کن آیا این انتخاب execution ownership را به Builder/API construction منتقل می‌کند یا نه، چه dependency لازم دارد و آیا implementations جایگزین interface را می‌شکند. افزودن مستقیم این متدها بدون بررسی رد است.

### Candidate B: extension یا context سراسری

نمونه‌هایی مانند global executor، registry، ThreadLocal یا dispatcher مبتنی بر reflection را بررسی به‌عنوان راه‌حل نکن؛ این موارد خارج از constraints هستند. Extension بدون منبع قابل اتکای Executor نیز به‌خودی‌خود ownership را حل نمی‌کند.

### Candidate C: execution-facing facade/handle محدود

بررسی کن آیا یک facade کوچک در module دارای execution ownership می‌تواند query builder و `IQueryBuilderExecutor` را composition کند و همان `first/get/sql` موجود را delegate کند.

اگر چنین facadeای لازم است، Traceability/Decision Closure باید پیش از implementation مشخص کند:

* facade کجا ساخته می‌شود؛
* Executor چگونه به آن می‌رسد؛
* آیا یک bind/factory صریح لازم است؛
* آیا consumer API دقیقاً `query.get()` می‌ماند؛
* compatibility با return type فعلی `example.query()` چگونه حفظ می‌شود.

این Plan نوع، نام یا signature نهایی facade را از پیش تحمیل نمی‌کند.

### Candidate D: حفظ API فعلی

اگر source evidence نشان دهد facade کوچک بدون نقض constraints یا تغییرات گسترده ممکن نیست، API فعلی می‌تواند تا Decision جداگانه حفظ شود. صرفاً برای زیبایی syntax، execution ownership جابه‌جا نشود.

## Final Contract پس از Decision Closure

Final Contract باید بدون ابهام مشخص کند:

* آیا `query` همان `IQueryRenderSelectApi` است یا execution-facing wrapper/handle.
* دقیقاً کدام object متدهای `get()`, `first()` و `sql()` را expose می‌کند.
* Executor چگونه و در چه نقطه‌ای به این object bind یا تزریق می‌شود.
* `QueryRenderSelectBuilder` صرفاً construction owner باقی می‌ماند.
* `IQueryBuilderExecutor` همچنان execution و Smart Result Consumption را مالک است.
* `QueryExecute` همچنان low-level JDBC execution را مالک است.
* low-level `execute(...)`, `IQueryExecute.executeSelect(...)` و `ExecuteResult<ResultSet>` حفظ می‌شوند.
* semantics، alias validation، error behavior و lifecycle Plan 5.0 بدون تغییر باقی می‌مانند.
* هیچ تغییر معنایی در Plan 4.0 ایجاد نمی‌شود.
* `execute(DataType)` و conversion همچنان Separate Contract / Deferred هستند.

## Compatibility Impact

Traceability باید این موارد را جداگانه بررسی کند:

* source compatibility پیاده‌سازی‌های `IQueryRenderSelectApi`.
* source/binary compatibility مصرف‌کنندگان `IQueryBuilderExecutor`.
* نوع بازگشتی `IExampleV1.query()` و مثال‌های V1/V1.1/V2/V3.
* APIهای اجرای write query که در این scope تغییر نمی‌کنند.
* dependency graph میان `query:api`, `query:builder`, `query:executor` و `query:example`.
* رفتار Help Run action و `main(args)`؛ تغییر Help فقط با ضرورت evidenceشده مجاز است.

هیچ API قدیمی بدون evidence مستقیم حذف یا deprecate نشود.

## Implementation Boundary

پس از Decision Closure و فقط در صورت `Implementation Ready`:

1. facade/bridge حداقلی مطابق Contract بسته‌شده پیاده‌سازی شود.
2. facade فقط به Smart API و rendering موجود delegate کند؛ JDBC یا ResultSet جدیدی به Builder اضافه نشود.
3. V1.1 برای نمونه‌سازی API جدید migrate شود؛ V1 baseline باقی بماند.
4. هر migration دیگر فقط با شواهد مستقیم انجام شود.
5. Help فقط در صورت نیاز واقعی به تغییر contract جدید به‌روزرسانی شود.
6. Plan 4.0 و production behaviorهای نامرتبط دست‌نخورده بمانند.

این بخش ترتیب اجرای آینده را مشخص می‌کند و در مرحلهٔ نوشتن Plan هیچ تغییری را مجاز نمی‌کند.

## Verification Plan

پس از implementation اجرا و نتیجهٔ دقیق ثبت شود:

### Consumer API

* query-facing `get()`.
* query-facing `first()`.
* query-facing `sql()`.
* ایجاد/binding facade طبق Final Contract.

### Plan 5.0 regressions

* first: یک ردیف، صفر ردیف، چند ردیف و materialization failure.
* get: چند ردیف و صفر ردیف.
* alias access و رد alias خالی/تکراری/ناشناخته.
* parameter preservation و `sql()` بدون interpolation یا execution.
* low-level ResultSet consumption و lifecycle سازگار.

### Compatibility

* `IQueryBuilderExecutor.execute(...)` و `IQueryExecute.executeSelect(...)`.
* تست‌های Plan 4.0 و QueryRelation.
* Example V1 baseline و compile نمونه‌های V1.1/V2/V3.
* اجرای Help Run فقط اگر infrastructure/contract آن تغییر کرده باشد.

### Build و Integration

* تست‌های ماژول‌های واقعاً متأثر.
* build ماژول‌های متأثر و example compile.
* `git diff --check`.
* live integration فقط با configuration و database تستی تأییدشدهٔ موجود؛ بدون database introspection یا preflight جدید.

## Deferred

* `execute(DataType)`، Query Result DataType، conversion و null conversion policy.
* generic `Query<T>`, `QueryRow<T>`, Result Schema و DTO mapping.
* ORM و automatic property mapping.
* هر تغییر Plan 4.0 یا Relation semantics.
* تغییر Help workflow تا وقتی نیاز آن با evidence ثابت نشده است.

## Unresolved Decisions

1. آیا query-centric syntax دقیقاً روی همان `IQueryRenderSelectApi` الزام است یا روی execution-facing facadeای که query را نگه می‌دارد؟
2. اگر facade لازم است، Executor چگونه بدون global state یا dependency معکوس به آن متصل می‌شود؟
3. آیا API `example.query()` باید return type جدید بگیرد، یا wiring فقط در V1.1/example runner انجام شود؟
4. حداقل تغییر dependency/API لازم چیست و چه مصرف‌کننده‌هایی را source/binary ناسازگار می‌کند؟

این موارد باید با Repository Evidence و Decision Closure بسته شوند؛ اگر یکی از آن‌ها تصمیم معماری مالک می‌خواهد، آن را unresolved نگه دار و implementation نکن.
