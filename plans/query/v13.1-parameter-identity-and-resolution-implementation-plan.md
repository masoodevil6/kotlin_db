**Implementation Ready / Not Authorized**

## 1. هدف و اصل کمینه‌سازی

رفع مورد مشخص: سه Declaration تو‌در‌تو بتوانند هرکدام پارامتر منطقی هم‌نام shared_value را با مقادیر 11، 22 و 33 داشته باشند و هر placeholder مقدار scope درست را بگیرد، حتی وقتی ترتیب ساخت clauseهای Query بیرونی با ترتیب SQL فرق دارد.

اصل اجرا:

- سازوکار فعلی QueryBuilder، SqlParameter، BuiltQuery، placeholderهای قابل مشاهده و JDBC resolver حفظ شود.
- reference خود SqlParameter فقط برای تشخیص binding مستقل داخل درخت و sidecar محلی render استفاده شود.
- برای سازگاری با resolver name-based موجود، فقط BuiltQuery داخلی مسیر اجرای مستقیم SELECT با نام‌های موقت یکتا ساخته شود.
- نام‌های موقت هویت پارامتر نیستند، در API عمومی یا SQL معمولی دیده نمی‌شوند و در هر اجرای Query محلی و قطعی‌اند.
- هیچ ID عمومی، allocator سراسری/تصادفی، نوع عمومی جدید برای binding، مسیر موازی JDBC یا تغییر رفتار Migration اضافه نشود.

## 3. قرارداد داده و جریان اجرا

### 3.1 Scope و reuse

- Query ریشه‌ای و هر Declaration که جداگانه ساخته شده است scope مستقل دارند؛ scope را به‌صورت خودکار برای هر Builder داخلی SELECT نساز.
- `table { ... }` در SELECT FROM و `with(name, block)` زیرساخت همان Query هستند و باید scope والد را شریک شوند. منابع JOIN که API فعلی اجازه می‌دهد و شرط‌های JOIN نیز scope Query مالک را شریک‌اند؛ nested SELECT source در JOIN مجاز نیست. در مقابل، `cte(declaration)` و dependencyهای آن scope تعریف Declaration خود را نگه می‌دارند و با scope مصرف‌کننده ادغام نمی‌شوند.
- شرط‌ها، گروه‌های شرط، JOIN conditionها و سایر زیرسازنده‌های clause در یک Query، scope ریشه را شریک می‌شوند.
- در یک scope، نام، مقدار برابر با Kotlin equality و sqlType برابر، یک binding است و همان reference canonical SqlParameter reuse می‌شود.
- همان نام در همان scope با مقدار یا sqlType متفاوت رد می‌شود.
- در دو scope مستقل، حتی name/value/sqlType برابر به معنی binding مشترک نیست؛ referenceها جدا هستند.
- فهرست IQueryApi.params برای سازگاری حفظ می‌شود و هر استفادهٔ Builder همانند رفتار فعلی یک عضو به آن می‌افزاید؛ اعضای تکراریِ equivalent به reference canonical اشاره می‌کنند. این فهرست منبع ترتیب positional JDBC نیست.

### 3.2 AST و rendering

- scalar parameter node reference SqlParameter را در conditionSideRight نگه می‌دارد.
- collection parameter node reference هر SqlParameter را در paramsCollection نگه می‌دارد.
- مقادیر قدیمی String در این خانه‌ها همچنان پشتیبانی می‌شوند تا AST دستی/قدیمی به رفتار فعلی render شود.
- در **Phase 1**، Builder و Renderer با هم مهاجرت می‌کنند: Renderer با دیدن SqlParameter همان placeholder منطقی :name را تولید می‌کند و reference را در sidecar همان render session ثبت می‌کند؛ collection نیز همان placeholderهای منطقی پیشین را با همان ترتیب نگه می‌دارد.
- occurrence شرط فقط زمانی وارد sidecar می‌شود که شرط واقعاً fragment غیرتهی تولید کند و آن fragment در SQL والد باقی بماند. برای مسیر موجود شرط، Renderer باید پیش از render کردن سمت پارامتردار، قابل‌رندر بودن سمت چپ و باقی‌ماندن شرط را تعیین کند؛ اگر هر تصمیم حذف در سطح بالاتر انجام می‌شود، occurrenceها باید موقتاً نگه داشته و فقط پس از پذیرفته‌شدن fragment به sidecar اصلی commit شوند. occurrence یتیم مجاز نیست.
- sidecar فقط برای SELECT ساخته می‌شود. هیچ پارامترگذاری جدیدی برای ASTهای INSERT، UPDATE یا DELETE تعریف نمی‌شود.
- Phase 1 فقط مرجع‌دهی AST و رندر سازگار/sidecar را تثبیت می‌کند؛ تا تکمیل placeholder lowering و اتصال آن به اجرای SELECT در Phase 2، پشتیبانی اجرای bindingهای مستقل هم‌نام ادعا نمی‌شود.

### 3.3 سازگاری با resolver فعلی

در اجرای مستقیم SELECT ساخته‌شده توسط QueryBuilderExecutor:

1. built-in dialect، SQL و sidecar را render می‌کند.
2. helper داخلی QueryBuilderExecutor تعداد و ترتیب placeholderهای SQL را با sidecar مقایسه می‌کند، نام هر occurrence را با SqlParameter.name تطبیق می‌دهد و multiset هویت referenceها را با params همان Query اعتبارسنجی می‌کند.
3. اگر sidecar کامل و معتبر باشد، helper به هر occurrence نام فیزیکی موقت و یکتا می‌دهد، SQL داخلی اجرای SELECT را با همان نام‌ها می‌سازد و برای هر نام یک کپی SqlParameter با همان value و sqlType می‌سازد.
4. BuiltQuery(query, params) موجود ساخته و به همان executeSelect فعلی داده می‌شود. resolver name-based موجود هر placeholder را مستقل و به ترتیب SQL به JDBC bind می‌کند.
5. SQL عادی، QueryConsumer.sql(), IQueryBuilderExecutor.executeOut(...) و blockQueryInfo همچنان SQL و نام‌های منطقی را می‌بینند. blockQueryInfo همان map فعلی last-wins را حفظ می‌کند.
6. اگر dialect از sidecar پشتیبانی نکند یا SQL شامل placeholder ثبت‌نشده باشد، مسیر legacy با SQL و params اصلی استفاده می‌شود. در این fallback، تعارض هم‌نام همچنان پیش از JDBC رد می‌شود؛ سیستم نباید مقدار حدسی bind کند.

نام موقت برای هر occurrence جداست، حتی وقتی چند occurrence به یک reference canonical اشاره دارند. تولید نام باید فقط در اجرای همان Query انجام شود، candidate با grammar شناسهٔ `BuiltQuery` سازگار باشد، با تمام نام‌های placeholder استخراج‌شده از SQL اصلی و نام‌های `params` برخورد نکند، و پیش از تولید candidate بعدی به مجموعهٔ اشغال‌شده افزوده شود. بازنویسی occurrenceها با پیمایش ترتیبی tokenها انجام شود، نه جایگزینی متنی گسترده. نام موقت به SqlParameter اصلی یا API عمومی منتقل نمی‌شود.

### تست‌های مرزی اجباری

- تعارض هم‌نام در همان scope همچنان رد شود؛ test باید زمان رد شدن پیشنهادی (هنگام Builder construction) را صریحاً تثبیت کند. این زمان نسبت به validation legacy قابل‌مشاهده تغییر می‌کند؛ test نباید آن را حفظ زمان قبلی جلوه دهد.
- پارامتر همنام متعارض در `table { ... }` nested و در `with(name, block)` همچنان در scope والد قرار گیرد و مستقل‌بودن scope Declaration به این مسیرهای قدیمی سرایت نکند.
- رندر شرطی که به‌علت ناقص بودن node از SQL نهایی حذف می‌شود، نباید occurrence یتیم در sidecar باقی بگذارد. occurrence collection/scalar فقط اگر placeholder در fragment نهایی باقی است ثبت شود؛ در غیر این صورت fallback باید همان validation قدیمی missing/extra را اعمال کند.

### موارد آزمون تکمیلی

- Placeholderهای :name داخل AST دستی/legacy که SqlParameter reference ندارند، sidecar کامل محسوب نشوند و به fallback امن بروند.
- placeholder شمارشی، ترتیب نام‌ها و مقدارها با BuiltQuery.getListParamNames() برابر باشد.
- دو reference مستقل با یک نام به دو synthetic name متفاوت تبدیل شوند، حتی اگر مقدار برابر باشد.
- یک reference canonical که چند بار در SQL ظاهر شده، برای هر occurrence index مجزا با مقدار ثابت خودش bind شود.
- پارامتر اضافه، placeholder بدون پارامتر، occurrence جاافتاده، و sidecar با نام ناهماهنگ نباید باعث identity bind ناقص شود؛ fallback باید validation قدیمی را حفظ کند.
- دو ترتیب ساخت clause باید از نظر SQL و مقادیر index به index یکسان باشند.
- MySQL و MariaDB مبتنی بر MySqlDialect مسیر tracking را حفظ کنند؛ dialectی که BaseSqlDialect را به‌کار نمی‌برد، fallback legacy داشته باشد.

## 6. ترتیب اجرای implementation پس از مجوز

1. baseline Git و تست‌های مرتبط را ثبت کن؛ تغییرات موجود را جدا نگه دار.

### Phase 1 — Builder/AST و سازگاری حداقلی Renderer

این فاز شامل مراحل وابستهٔ قبلی 2 تا 5 است؛ این تجمیع فقط برای جلوگیری از شکستن rendering هنگام تغییر payload AST انجام می‌شود.

1. ParameterBindingScope را فقط در ریشهٔ Query و Declarationهای مستقل مالکیت بده؛ scope والد را از مسیرهای clause به WHERE، گروه‌ها، JOIN، collection، `table(blockQuery)` و `with(name, block)` انتقال بده. `cte(declaration)` scope خودش را حفظ کند. با تست unit هم reuse/conflict scope و هم این مرزها را ثابت کن.
2. فقط payload پارامترهای Builder-created را از رشته/نام به reference SqlParameter در خانه‌های Any موجود تغییر بده؛ امضا و schema AST را تغییر نده.
3. همان فاز، Renderer را به کمترین میزان لازم برای خواندن SqlParameter از AST تغییر می‌دهد: placeholderهای منطقی و SQL موجود برای scalar، collection و JOIN حفظ شوند و occurrence به‌ترتیب رندر در sidecar ثبت شود. رندر معمولی و AST دستیِ String همچنان همان رفتار را داشته باشند.
4. شرطی که به‌دلیل نامعتبر/ناقص بودن از خروجی حذف می‌شود نباید occurrence در sidecar باقی بگذارد. ثبت پارامتر پس از اثبات باقی‌ماندن fragment انجام شود؛ در صورت حذف در سطح والد، occurrenceهای محلی فقط هنگام commit fragment نهایی به sidecar اضافه شوند.
5. RenderContext، session registry و helper `renderWithBindings` در BaseSqlDialect را برای رساندن sidecar از renderهای recursive تکمیل کن. SQL قابل‌مشاهده باید با قبل یکسان بماند. در این فاز QueryBuilderExecutor و JDBC lowering تغییر نمی‌کنند.
6. تست‌های Phase 1 را اجرا کن. پایان این فاز، حفظ referenceهای AST و رندر/sidecar سازگار را ثابت می‌کند؛ اجرای مستقل پارامترهای هم‌نام در scopeهای مختلف هنوز پشتیبانی‌شده محسوب نمی‌شود.

### Phase 2 — اتصال sidecar به اجرای SELECT

8. فقط مسیر اجرای SELECT در QueryBuilderExecutor را به helper وصل کن؛ به IQueryBuilderExecutor، QueryExecute و CRUD دست نزن.
9. تست‌های placeholder lowering و JDBC binding را اجرا کن تا پشتیبانی independent same-name اثبات شود؛ اجرای موفق Phase 1 به‌تنهایی این قابلیت را اثبات نمی‌کند.

### Phase 3 — رگرسیون نهایی

## 7. ریسک‌ها، موارد باز و حدود پشتیبانی

- payload runtime خانه‌های Any در AST پارامتردار Builder از String/name به SqlParameter تغییر می‌کند، هرچند interface و نوع اعلام‌شدهٔ AST تغییر نمی‌کند. مصرف‌کنندهٔ خارجی که این Any را مستقیم inspect کند در Repository قابل شناسایی نیست.
- روش placeholder parsing باید دقیقاً با قرارداد regex فعلی BuiltQuery هماهنگ باشد. تغییر grammar در آینده باید هم parser BuiltQuery و هم lowering را هماهنگ کند. اگر raw SQL با colon در literal/comment وجود داشته باشد، رفتار فعلی regex نیز ممکن است آن را placeholder تلقی کند؛ این Plan grammar موجود را اصلاح نمی‌کند.
- نام‌های موقت صرفاً adapter به resolver legacy هستند. خطای نام‌گذاری یا sidecar ناقص باید به fallback امن برسد؛ مسیر identity-aware نباید حدس یا last-wins کند.
- تعارض نام در scope واحد زودتر از مسیر BuiltQuery فعلی گزارش می‌شود. قاعدهٔ reject و fail-fast پیش از JDBC حفظ می‌ماند، اما زمان دقیق exception تغییر می‌کند.
- dialect/renderer خارج از BaseSqlDialect یا renderer سفارشی‌ای که reference ثبت نکند، تا زمانی که tracking صریح را پیاده نکند، از مقادیر مستقل همنام پشتیبانی نمی‌کند.
- BaseSqlDialect یک helper عمومی افزایشی renderWithBindings می‌گیرد تا QueryExecutor بدون تغییر ISqlDialect بتواند قابلیت را تشخیص دهد. API/ABI مصرف‌کننده‌های بیرونی از اطلاعات Repository قابل تضمین نیست.
- blockQueryInfo map فعلی برای نام تکراری last-wins باقی می‌ماند؛ این Plan چند مقدار برای یک کلید را نمایش نمی‌دهد.
- اجرای موفق با fake JDBC مسیر bind را ثابت می‌کند؛ پیکربندی و رفتار واقعی هر database server خارج از این تست unit است.
- تغییر Migration production پیش‌بینی نمی‌شود؛ اگر تست موجود Migration شکست بخورد، علت باید جداگانه بررسی شود و رفع آن خودکار به این Plan افزوده نشود.

## 8. معیار اتمام و محدودیت مجوز

معیار پذیرش مستقل **Phase 1** این است که scalar، collection و JOIN پارامترهای AST را به placeholderهای منطقی قبلی رندر کنند؛ مقدار/referenceهای sidecar با هر placeholder واقعی و به همان ترتیب تطبیق داشته باشند؛ condition حذف‌شده occurrence یتیم نگذارد؛ و SQL قابل‌مشاهدهٔ این مسیرها تغییر نکند. این معیار شامل اجرای مقادیر مستقل هم‌نام نیست.

Plan فقط وقتی قابل بستن است که:

1. هر سه scope مستقل بتوانند shared_value را با مقادیر 11، 22، 33 به SQL نهایی بدهند و JDBC در ترتیب placeholderها دقیقاً همان مقادیر را bind کند.
2. هر دو ترتیب where → from و from → where نتیجهٔ binding هم‌معنا بدهند.
3. reuse پارامتر equivalent در یک scope باقی بماند و conflict همان scope رد شود.
4. BuiltQuery دستی، SqlParameter API، query SQL عمومی، blockQueryInfo، CRUD و Migration رفتار legacy خود را حفظ کنند.
5. sidecar ناقص، mismatch، پارامتر missing/extra و برخورد نام موقت هرگز موجب bind مقدار اشتباه نشوند.
6. nested render session ترتیب placeholderها را مطابق SQL واقعی حفظ کند.
7. تست‌های مربوط موفق شوند و git diff --check بدون خطا باشد؛ هر تست اجرا‌نشده یا محدودیت محیط گزارش شود.
