# Plan 3.0: QueryDefinition / QueryRelation Final Contract

## Status

`Implementation Ready` — revised by the owner’s final decision that SQL alias is the only SELECT output naming contract. This contract supersedes earlier Plan 3.0 wording about `OutputSchema`, `OutputField`, and Kotlin output-property identity.

## Objective

Allow a built SELECT query to be reused as a Relation and consumed by another query, lowering through the existing CTE AST and Renderer while preserving parameter order and legacy V1/V2 APIs.

## Canonical Contract

```text
SELECT item
    ↓ alias("sql_output_name")
SQL output name
    ├── ResultSet lookup name
    └── Relation consumption name
```

`alias(...)` is the only output naming mechanism. There is no Kotlin output-property identity, property-to-SQL-name mapping, `OutputSchema`, `OutputField`, or `output(...)` operation. `.as(...)` is not an API.

## Domain Model

| Concept | Contract |
|---|---|
| `QueryDefinition` | Built query payload containing the existing SELECT AST and its `SqlParameter` list. |
| `QueryRelation` | Reference-identity handle owning a SQL name, `QueryDefinition`, and ordered Relation dependencies. It has no generic Output type or output metadata map. |
| SQL output name | The non-empty `alias(...)` on a SELECT item. It is the name visible to SQL consumers and ResultSet label lookups. |
| Physical field | Existing `KClass + KProperty1` resolution through `QBTable`/`QBColumn`; database column name comes from `QBColumn.name`. |
| SELECT item | Existing column AST with optional aggregate modifier and alias. No new generic SelectItem/Expression AST is introduced. |

Relation SQL name is its CTE name, not its identity. Relation instances retain reference identity, even if their SQL names match.

## API Contract

```kotlin
fun queryRelation(
    name: String,
    block: IQueryRenderSelectApi.() -> Unit,
): QueryRelation

fun from(relation: QueryRelation, alias: String? = null)

fun relationColumn(
    relation: QueryRelation,
    sqlOutputName: String,
)
```

Every SELECT item published by a `QueryRelation` must have a non-empty, unique SQL alias. `relationColumn` resolves the exact SQL output name against the aliases in that Relation’s existing SELECT AST. Unknown or blank names are rejected by the Builder. Relation identity is checked separately: only the Relation configured as the active source may be referenced. No Kotlin reflection or property metadata participates in this resolution.

Example:

```kotlin
val orderStats = queryRelation("order_stats") {
    select {
        addColumn {
            column(OrderModel::class, OrderModel::id)
            count()
            alias("order_count")
        }
    }
    table { table(OrderModel::class) }
}

val consumer = QueryRenderSelectBuilder()
    .from(orderStats)
    .select {
        addColumn { relationColumn(orderStats, "order_count") }
    }
```

An explicit SQL alias is also the ResultSet lookup label, e.g. `alias("user_id")` is consumed with `ResultSet.getInt("user_id")`.

## Relation Identity and Composition

`from(relation)` supports one Relation source in a query and lowers it to the existing CTE `WITH` item and CTE table reference. Relation dependencies are emitted in dependency order. Cycles, duplicate CTE names, duplicate Relation output aliases, unknown output names, a second Relation source, or mixing a Relation source with a physical table source are rejected by the Builder.

Nested composition uses the same SQL output names at each boundary:

```text
Relation A: alias("base_id")
    ↓ relationColumn(A, "base_id")
Relation B: alias("selected_id")
    ↓ relationColumn(B, "selected_id")
Consumer
```

The effective `FROM` alias qualifies a consumed SQL output name. Relation identity and CTE name remain distinct from that placement alias.

## Alias Contract

- `alias("name")` sets the SQL output name for a SELECT item.
- Relation outputs require non-empty aliases; `alias("")` therefore cannot publish a Relation output.
- Relation consumers refer to exactly that name with `relationColumn(relation, "name")`.
- Query results use that SQL label for ResultSet access.
- `.as(...)` is not part of the public API.
- For ordinary legacy SELECT queries, existing alias behavior is preserved.

## AST, Builder, Renderer, and Executor Boundaries

- Builder owns Relation identity checks, SQL output alias validation, Relation dependency ordering, and lowering to existing CTE/table-column AST fields.
- No Relation-specific AST node or replacement metadata abstraction is added.
- Renderer receives only the existing AST and remains unaware of `QueryRelation`, Kotlin properties, and models.
- `manager:execute` and `QueryExecute` remain independent of QueryRelation, AST, Dialect, and Migration. Query execution receives rendered `BuiltQuery` as before.
- Aggregate rendering in the adopted scope uses SQL function-call form, e.g. `COUNT(column) AS total`, through the existing renderer capability.

## Parameter Contract

Relation-definition parameters retain dependency-first order, followed by parameters owned by that Relation. Consumer parameters follow Relation parameters. Existing positional JDBC binding semantics are unchanged.

## Compatibility

- V1 String-based `table`, `tableColumn`, and CTE APIs remain available.
- V2 typed Model table/column APIs remain available.
- Existing ordinary SELECT alias behavior remains unchanged.
- QueryRelation’s prior property-based API (`queryRelation(name, Output::class)`, `output(...)`, and `relationColumn(relation, property)`) is replaced by SQL-name-based Relation construction/consumption. This is the intentional contract adjustment requested by the owner.
- `QueryExecute`, ResultSet lifecycle, and execution behavior are unchanged.

## Adopted Scope

- Physical-column Relation outputs with explicit aliases.
- Existing aggregate outputs with explicit aliases.
- Relation pass-through projections using SQL output names.
- One Relation source in `FROM`, CTE lowering, dependency ordering, alias qualification, and parameter ordering.

## Deferred / Out of Scope

- ResultSet-to-object mapping, DTO construction, SQL type/nullability inference.
- CASE, arithmetic, generic functions, generic `Expression`/`Selectable`/`SelectItem` abstractions.
- Relation JOINs, multiple sources, self-joins, and Relation references in WHERE/GROUP/HAVING/ORDER.
- Derived tables, CTE redesign, Dialect redesign, execution or migration changes, database introspection, and raw SQL escape hatches.
- `.as(...)` syntax and any Kotlin output-property identity or mapping.

## Verification Contract

Tests cover explicit and duplicate aliases, unknown SQL output names, Relation identity, alias propagation, dependency ordering, nested composition, parameter ordering, cycle rejection, single-source rules, aggregate rendering, and V1/V2 API regression. Live MySQL verification is separate and uses the repository’s existing test configuration; it does not change production execution behavior.
