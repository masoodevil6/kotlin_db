# Plan 13.1 — هویت و حل‌وفصل پارامترها

## وضعیت

**تصمیم‌های طراحی در 2026-10-13 بسته شد؛ Plan اجرایی مستقل آمادهٔ بازبینی است. وضعیت: Implementation Ready / Not Authorized. این وضعیت صرفاً آمادگی طراحی را نشان می‌دهد و مجوز تغییر کد نیست.**

**یادداشت خواندن سند:** بخش‌های پیش از بخش 10، متن اولیه، شواهد و وضعیت تاریخی تصمیم‌ها را حفظ می‌کنند. پیشنهادهای اولیه دربارهٔ فیلد `id`، placeholder یکتا، location مدل، سازنده و موارد باز، تصمیم فعلی نیستند. بخش 10 تصمیم قبلی را ثبت می‌کند؛ بازبینی حداقل تغییر در بخش 11 دامنهٔ لازم را محدود و تصمیم جاری را مشخص می‌کند. در صورت تعارض، بخش 11 و Plan اجرایی مستقل بر بخش‌های قبلی مقدم‌اند.

## اصلاحیهٔ اولویت‌دار: تولید داخلی شناسه

این اصلاحیه بر هر بخش دیگری از Plan دربارهٔ تولید `id` و API مصرف‌کننده اولویت دارد.

- هویت فنی binding داخلی است و سیستم آن را می‌سازد؛ قرارداد نهایی این Plan آن را به‌صورت reference identity خود `SqlParameter` پیاده می‌کند، نه فیلد `id` رشته‌ای.
- مصرف‌کنندهٔ API نباید شناسه را تولید، انتخاب یا ارسال کند.
- API مصرف‌کننده از نظر مفهومی باید شبیه نمونهٔ زیر باشد؛ این نمونه قرارداد نهایی سازنده را تعیین نمی‌کند:

  ```kotlin
  SqlParameter(
      name = "shared_value",
      value = 11
  )
  ```

  این API هدف را نشان می‌دهد؛ در سورس فعلی چنین سازندهٔ دوآرگومانی وجود ندارد. factory موجود `SqlParameter.of(name, value)` نزدیک‌ترین مسیر فعلی برای مقدار غیر-null است و SQL type را resolve می‌کند.

- نمونهٔ سه‌فیلدی زیر فقط فرض اولیهٔ ممیزی بود و **تصمیم نهایی نیست**؛ `id` به primary constructor یا مدل `SqlParameter` اضافه نمی‌شود:

  ```kotlin
  data class SqlParameter<T>(
      val id: String,
      val name: String,
      val value: T
  )
  ```

- این شکل فقط یک مدل داخلی احتمالی است، نه امضای نهایی API عمومی. نمونه، `sqlType` موجود را نیز برای سادگی نشان نمی‌دهد؛ قرارداد هدف باید اطلاعات SQL type لازم برای bind و پارامترهای null را حفظ کند.
- نقطهٔ ساخت reference در `ParameterBindingScope` است که همان `SqlParameter` canonical را ایجاد یا reuse می‌کند. مصرف‌کننده نه reference را می‌فرستد و نه مدیریت می‌کند.
- تولید شناسه نباید semantics استفادهٔ مجدد را عوض کند: ارجاع‌هایی که عمداً یک binding را به اشتراک می‌گذارند باید به همان هویت فنی برسند. تولید یک شناسهٔ مستقل برای هر فراخوانی سازنده، بدون بررسی این semantics، قابل قبول نیست.

جریان فعلی پارامتر در QueryBuilder به‌صورت خلاصه چنین است:

1. Builder مقدار را دریافت می‌کند، placeholder متنی یا `columnTag` را در AST ثبت می‌کند و `SqlParameter` را به `params` می‌افزاید.
2. قرارداد `IQueryApi` در `data_base/query/api/src/main/kotlin/interfaces/api/IQueryApi.kt`، `params` را به‌شکل `MutableList<SqlParameter<*>>` جدا از AST نگه می‌دارد. `QueryRenderSelectBuilder` و Builderهای clause همین فهرست را به اشتراک می‌گذارند؛ nested query و Declarationها نیز هنگام اتصال، عناصر پارامتر را با `addAll` منتقل می‌کنند.
3. `IQueryBuilderExecutor.executeOut(...)` در `data_base/query/executor/src/main/kotlin/interfaces/IQueryBuilderExecutor.kt` ابتدا `queryBuilder.ast` را با Dialect رندر می‌کند و سپس همان SQL و فهرست params را در `BuiltQuery` قرار می‌دهد.
4. `BuiltQuery.getListParamNames()` occurrenceهای placeholder را از SQL به ترتیب متنی درمی‌آورد و وجود پارامترهای متناظر را بر اساس نام اعتبارسنجی می‌کند.
5. `IQueryExecute.execute(...)` SQL آماده و فهرست نام‌های placeholder را می‌سازد؛ `readyParamsInQuery(...)` برای هر occurrence به ترتیب نهایی SQL مقدار mapشده با نام را bind می‌کند.

### علت ریشه‌ای تعارض فعلی

AST، SQL و هر دو مرحلهٔ resolve، پارامتر را با رشتهٔ نام شناسایی می‌کنند. `BuiltQuery` و `readyParamsInQuery` برای هر نام فقط یک مقدار canonical نگه می‌دارند؛ اگر دو Declaration مستقل نام یکسان با مقدار یا SQL type متفاوت داشته باشند، خطای تعارض ایجاد می‌شود. افزودن `id` فقط به مدل `SqlParameter` این مشکل را حل نمی‌کند: تا وقتی placeholderهای AST و SQL همان نام منطقی را نگه می‌دارند، مراحل بعدی IDهای مختلف را نمی‌بینند. برای پشتیبانی هدف، شناسه یا reference متناظر باید از زمان ساخت placeholder تا resolve نهایی حفظ شود.

در نتیجه، راهکار تولید شناسه باید دو مسئولیت موجود را به هم متصل کند: محل ایجاد ارجاع placeholder در Builder و محل نگهداری/bind پارامتر در Core و Executor. تولید شناسه صرفاً هنگام JDBC bind دیر است، چون در آن مرحله AST و SQL قبلاً ارتباط پارامتر را فقط با نام ثبت کرده‌اند.

### پیشنهاد معماری اولیه بر پایهٔ شواهد (با تصمیم نهایی بخش 10 جایگزین شد)

در تصمیم نهایی، شناسهٔ جداگانه‌ای روی `SqlParameter` ذخیره نمی‌شود. Builder در `ParameterBindingScope` یک نمونهٔ canonical از همین نوع می‌سازد؛ AST آن reference را نگه می‌دارد و identity آن با `===`/`IdentityHashMap` شناخته می‌شود. این الگو شناسه را از API مصرف‌کننده پنهان می‌کند و نیازی به allocator عددی، تصادفی یا سراسری ندارد.

این پیشنهاد علتاً از سورس فعلی به دست می‌آید: `QueryConditionsBuilder.sideValue(...)` هم رشتهٔ `:name` را در AST می‌گذارد و هم بلافاصله `SqlParameter.of(...)` را می‌سازد؛ بنابراین شناسه باید در همین نقطه یا در factory سیستمی‌ای تولید شود که شناسهٔ تولیدشده را به Builder برمی‌گرداند تا AST همان شناسه را ثبت کند. تولید در `QueryExecute` یا فقط در `BuiltQuery` دیر است و نمی‌تواند مشخص کند دو occurrence هم‌نام به یک binding یا دو binding مستقل اشاره دارند.

سازوکار بر scope محلی Query/Declaration کار می‌کند. همان نام/مقدار/type در همان scope reference canonical را reuse می‌کند؛ همان نام با مقدار/type ناسازگار در همان scope رد می‌شود؛ scopeهای جدا نمونه‌های مستقل می‌سازند، حتی اگر مقدارها برابر باشند. ترکیب nested referenceها را حفظ می‌کند؛ یکتایی پس از ترکیب با identity مرجعی تضمین می‌شود.

مسیر نهایی چنین است: **Builder و scope → reference `SqlParameter` کنار occurrence در AST → SQL نمایشی با `:logical_name` و sidecar ordered occurrences از Renderer → `BoundBuiltQuery` → bind همان reference به index JDBC**. SQL placeholder فیزیکی جدیدی تولید نمی‌شود. مسیر قدیمی `BuiltQuery(sql, params)` همچنان name-based می‌ماند.

### گزینه‌های تولید و تضمین یکتایی

این گزینه‌ها در ممیزی ارزیابی شدند. تصمیم نهایی reference identity است؛ گزینه‌های دیگر برای traceability حفظ شده‌اند:

| گزینه | مزیت | هزینه یا ریسک |
|---|---|---|
| شناسهٔ تصادفی هنگام ساخت binding | از API مصرف‌کننده جدا می‌ماند و احتمال برخورد بسیار کم است. | یکتایی ریاضی را به‌تنهایی تضمین نمی‌کند؛ برای برخورد باید اعتبارسنجی در محدودهٔ Query وجود داشته باشد. خروجی و تست‌ها نیز nondeterministic می‌شوند. تولید شناسه در هر `SqlParameter.of` ممکن است استفادهٔ مجدد فعلی از نام یکسان را به چند هویت ناخواسته تبدیل کند. |
| شمارندهٔ قطعی در scope هر Query/Declaration | با شمارندهٔ کنترل‌شده، یکتایی در همان scope قابل تضمین و تست‌ها قابل‌تکرار می‌شوند. scope جدا برای Declarationهای تو‌در‌تو امکان جداسازی نام منطقی مشترک را می‌دهد. | allocator باید از Builderهایی که یک Query را می‌سازند عبور کند و در مرزهای nested/composition درست مدیریت شود. semantics استفادهٔ مجددِ یک نام در همان scope باید صریح بماند. |
| شناسهٔ قطعی مشتق از نام و scope | می‌تواند بدون state سراسری بازتولید شود. | نیازمند شناسهٔ پایدار scope و تعریف دقیق collision است؛ مشتق‌کردن صرف از نام، bindingهای مستقل هم‌نام در یک scope را ادغام می‌کند. |
| شناسهٔ سراسری افزایشی | پیاده‌سازی اولیه ساده و در یک فرایند یکتا است. | state مشترک، concurrency و چرخهٔ عمر سراسری ایجاد می‌کند؛ شناسه‌ها به ترتیب اجرای Queryها وابسته می‌شوند و نیاز پروژه به چنین stateای از سورس اثبات نشده است. |

هر راهکار منتخب باید برخورد را در محدودهٔ واقعی Query یا به‌طور قطعی ناممکن کند. صرف اتکا به احتمال برخورد پایین، بدون قرارداد و اعتبارسنجی، تضمین یکتایی محسوب نمی‌شود.

برای شمارندهٔ scopeدار نیز باید روشن شود ID در سطح یک Query نهایی یکتا است یا در scopeهای جداگانه تولید و هنگام composition بازنگاشت می‌شود. شمارنده‌های مستقل که از مقدار یکسان آغاز می‌شوند، به‌تنهایی برای Query نهایی composed یکتایی را تضمین نمی‌کنند. هر برخورد باید پیش از اجرای JDBC شناسایی شود، مگر آنکه راهکار انتخابی collision را با construction قطعی ناممکن کند.

### سازگاری API — متن ممیزی اولیه (تصمیم‌ها در بخش 10 بسته شده‌اند)

سازندهٔ فعلی `SqlParameter(name, value, sqlType)` عمومی است و کلاس data class نیز رفتارهای تولیدشده‌ای مانند `copy`، componentها، `equals` و `hashCode` دارد. تغییر primary constructor برای افزودن `id` می‌تواند امضای Kotlin/JVM و رفتار data class را تغییر دهد. وجود factoryهای عمومی `of` و `nullOf` مسیر مناسبی برای پنهان‌کردن تولید شناسه از مصرف‌کننده است، اما استفادهٔ مستقیم از constructor در تست‌های داخلی، به‌تنهایی سازگاری مصرف‌کنندگان بیرونی را اثبات یا رد نمی‌کند.

در ممیزی طراحی این گزینه‌ها مقایسه شوند:

1. حفظ شکل فراخوانی فعلی با constructor یا overload عمومی که شناسه را خودش تولید کند؛ بررسی شود چگونه `copy` و استفادهٔ مجدد از هویت را حفظ می‌کند.
2. انتقال تولید به factoryهای عمومی `of` و `nullOf` و محدودکردن/حفظ سازندهٔ مستقیم با overload خودکار؛ اثر آن بر source و binary compatibility جداگانه بررسی شود.
3. جداسازی ورودی عمومی بدون شناسه از مدل داخلی دارای شناسه؛ هزینهٔ مدل یا تبدیل اضافی، مرز Core و دسترسی Builder/Executor به شناسه بررسی شود.
4. افزودن شناسه به data class فعلی؛ اثر primary constructor، named/positional calls، `copy`, component functions، equality و ABI بررسی شود. این گزینه نباید باعث شود مصرف‌کننده شناسه را انتخاب یا ارسال کند.

در زمان ممیزی اولیه، امضای نهایی و scope هنوز باز بود. تصمیم جاری در بخش 10 این است که constructor و factories موجود حفظ شوند و binding identity همان reference `SqlParameter` باشد؛ بیرون از این Repository، policy نسخه‌بندی/مصرف‌کننده همچنان نامعلوم است.

در تصمیم نهایی، هیچ ID property در مدل مشترک اضافه نمی‌شود. carrierهای binding-aware از مرز subprojectها عبور می‌کنند؛ API دقیق آن‌ها در سند اجرایی مشخص شده است.

### حفظ استفادهٔ مجدد

رفتار فعلی قابل‌مشاهده این است که placeholder با نام یکسان به همان کلید resolve می‌شود؛ تکرار پارامترهای هم‌نام با `value` و `sqlType` برابر پذیرفته می‌شود، و مقادیر یا SQL typeهای متفاوت با همان نام رد می‌شوند. این رفتار در `BuiltQuery.getListParamNames()` و `IQueryExecute.readyParamsInQuery(...)` پیاده‌سازی شده و در `BuiltQueryTest.acceptsEqualDuplicateParametersAndRejectsConflicts` و تست‌های قرارداد Executor پوشش دارد.

طراحی جدید باید مشخص کند این اشتراک هویت چگونه حفظ می‌شود. allocator که برای هر بار ساخت `SqlParameter` بی‌قید یک ID تازه می‌دهد، بدون ثبت association در AST یا binding context، با این رفتار فعلی سازگار نیست. مصرف‌کننده نباید برای حل این مسئله `id` را دستی مدیریت کند.

### تست‌های افزودهٔ لازم برای اصلاحیه

- API مصرف‌کننده بتواند پارامتر را بدون آرگومان `id` بسازد؛ شناسه در مسیر داخلی ایجاد شود.
- دو Query مستقل و دو Declaration تو‌در‌تو بتوانند نام منطقی یکسان داشته باشند و شناسه‌های مؤثرشان طبق scope انتخاب‌شده متمایز باشد.
- چند occurrence که عمداً یک binding را به اشتراک می‌گذارند، پس از تولید شناسه همچنان به یک هویت resolve شوند و binding یکسان داشته باشند.
- برخورد شناسه در scope مربوط یا به‌طور قطعی ناممکن باشد یا با خطای مشخص پیش از bind شناسایی شود.
- مسیرهای `of`, `nullOf` و سازندهٔ عمومی/سازگاری آن‌ها behavior نوع SQL، مقدار null و bind را حفظ کنند.
- اگر constructor/data class تغییر می‌کند، تست‌های source/API قابل‌اعمال و رفتارهای `copy`, component و equality مطابق تصمیم سازگاری مشخص شوند؛ سازگاری باینری فقط با شواهد یا ابزار مناسب ادعا شود.
- AST، SQL رندرشده، تبدیل placeholder و `PreparedStatement` آزمایشی همگی association شناسه تا مقدار را در ترتیب occurrence نهایی اثبات کنند.

این تست‌ها پیشنهاد Plan هستند و در این مرحله اجرا یا اضافه نشده‌اند.

## هدف

طراحی مدلی سازگار با رفتارهای موجود برای هویت پارامتر که هویت فنی تولیدشده توسط سیستم را از نام منطقی و مقدار آن جدا کند؛ مصرف‌کنندهٔ API شناسه را مدیریت نمی‌کند.

مدل داخلی احتمالی — نه امضای نهایی API عمومی:

```kotlin
data class SqlParameter<T>(
    val id: String,
    val name: String,
    val value: T
)
```

هدف، پشتیبانی از پارامترهای مستقلی است که نام منطقی یکسان دارند؛ از جمله پارامترهایی که از Declarationهای تو‌در‌توی inline می‌آیند، بدون ایجاد ابهام هنگام resolve کردن پارامترها یا bind کردن آن‌ها به JDBC.

این مدل نقطهٔ شروع بررسی است، فیلدهای فعلی مانند `sqlType` را به‌تنهایی جایگزین نمی‌کند و پیش از ممیزی سازگاری نباید به‌عنوان طراحی نهایی API یا مجوز تغییر کد تلقی شود.

## شواهد فعلی

Plan 12.4 بسته شده است.

بر اساس گزارش تست‌های regression در `InlineCteParameterBindingTest.kt`:

1. پارامترهای Declarationهای تو‌در‌توی inline، مستقل از ترتیب ساخت clauseهای بیرونی، مطابق ترتیب placeholderهای SQL نهایی bind می‌شوند.
2. پیاده‌سازی فعلی نام پارامتر را به‌عنوان کلید سراسری برای resolve کردن مقدار به کار می‌گیرد.
3. مقادیر مستقل با نام یکسان به‌جای resolve مستقل، با خطای تعارض رد می‌شوند.
4. Executor فعلی مقادیر را با تطبیق نام placeholderها پیدا می‌کند و آن‌ها را بر اساس ترتیب occurrence در SQL رندرشده bind می‌کند.
5. در معماری فعلی، مقادیر پارامتر جدا از AST کوئری نگهداری می‌شوند.

این موارد شواهدی دربارهٔ پیاده‌سازی فعلی‌اند و مجوزی برای بازطراحی بخش‌های نامرتبط سیستم ساخت Query محسوب نمی‌شوند. جزئیات مسیرها و نمادهای سورس در جدول «شواهد Repository برای این اصلاحیه» ثبت شده‌اند. نتیجهٔ اجرای تست‌های Plan 12.4 گزارش تاریخی است؛ در این به‌روزرسانی تست یا Build اجرا نشده است.

## تصمیم‌های طراحی الزامی

### ۱. هویت پارامتر

معنای `id` را به‌عنوان هویت فنی پارامتر و معنای `name` را به‌عنوان نام منطقی آن مشخص کن.

پارامترهای مستقل می‌توانند `name` یکسان و `id` متفاوت داشته باشند، مشروط بر اینکه قرارداد هویت انتخاب‌شده این تمایز را در تمام مسیرها حفظ کند.

نمونهٔ مفهومی:

```kotlin
// در مدل داخلی، سیستم IDهای متفاوت را نگه می‌دارد؛ مصرف‌کننده آن‌ها را ارسال نمی‌کند.
listOf(
    internalParameter(id = generatedIdA, name = "shared_value", value = 11),
    internalParameter(id = generatedIdB, name = "shared_value", value = 22),
    internalParameter(id = generatedIdC, name = "shared_value", value = 33)
)
```

این pseudo-code فقط تفاوت مفهومی IDهای داخلی را نشان می‌دهد؛ `internalParameter` API موجود یا قرارداد پیشنهادی قطعی نیست. ID در تست‌ها باید از خود سیستم تولید شود، نه اینکه مصرف‌کننده آن را hard-code یا ارسال کند.

سیستم باید شناسه را تولید کند. محل مناسب تولید و تضمین یکتایی آن در محدودهٔ تعریف‌شدهٔ Query را با توجه به شواهد و گزینه‌های ثبت‌شده در اصلاحیه تعیین کن. تولید شناسه را به مصرف‌کننده واگذار نکن.

### ۲. ارجاع‌های AST

مشخص کن هر occurrence پارامتر در AST چگونه ارتباط خود را با `SqlParameter.id` حفظ می‌کند.

افزودن `id` فقط به فهرست داده‌های پارامتر کافی نیست، اگر nodeهای AST همچنان پارامترها را فقط با نام منطقی شناسایی کنند.

طراحی باید میان این دو حالت تمایز بگذارد:

- چند ارجاع به یک هویت پارامتر که باید عمداً یک مقدار را به اشتراک بگذارند؛
- پارامترهای مستقلی که صرفاً نام منطقی یکسان دارند.

فرض نکن که تکرار هر نام الزاماً یکی از این دو معنا را دارد. semantics موردنظر را از API و پیاده‌سازی فعلی استخراج کن.

### ۳. رندر و resolve کردن placeholder

مشخص کن هویت پارامترها چگونه به placeholderهای SQL رندرشده نگاشت می‌شود.

اگر Dialect یا مسیر اجرای JDBC فعلی به نام placeholder یکتا نیاز دارد، تعیین کن این نام‌ها چگونه تولید یا نمایش داده شوند، بدون آنکه `name` منطقی در `SqlParameter` بازنویسی شود.

SQL نهایی باید ارتباط درست هر پارامتر با مقدارش را حفظ کند؛ از جمله در Declarationهای inline تو‌در‌تو و پارامترهایی که در clauseهای متفاوت قرار دارند.

### ۴. سازگاری

رفتار فعلی Queryهایی که نام پارامترهای یکتا دارند حفظ شود.

پیش از پیشنهاد تغییر، APIهای عمومی موجود، سازنده‌های پارامتر، رفتار استفادهٔ مجدد از پارامتر، خطاهای تعارض و تست‌های فعلی را ممیزی کن.

اعتبارسنجی موجود را حذف یا تضعیف نکن، مگر آنکه ثابت شود مدل هویت جدید دقیقاً همان هدف را به شکل درست‌تری پوشش می‌دهد.

از refactor نامرتبط پرهیز کن.

## سناریوهای الزامی regression

Plan باید تست‌هایی را برای دست‌کم سناریوهای زیر تعریف کند:

1. **Declarationهای تو‌در‌توی inline:** سه پارامتر مستقل با نام `shared_value` و مقادیر `11`، `22` و `33` باید به placeholderهای متناظر خود resolve و bind شوند.
2. **ترتیب ساخت clauseها:** ابتدا `where` بیرونی پیش از `from` ساخته شود و سپس ترتیب معکوس نیز بررسی شود. نگاشت نهایی SQL به مقدار باید در هر دو حالت درست بماند.
3. **استفادهٔ مجدد از پارامتر:** چند ارجاع به یک هویت پارامتر باید مطابق semantics تثبیت‌شدهٔ استفادهٔ مجدد عمل کنند.
4. **پارامترهای مستقل با نام یکسان:** شناسه‌های متفاوت و نام منطقی یکسان نباید به‌اشتباه تعارض ایجاد کنند.
5. **برخورد شناسه‌ها:** شناسه‌های تکراری باید مطابق قرارداد انتخاب‌شده شناسایی یا از ابتدا جلوگیری شوند.
6. **سازگاری نام‌های یکتا:** رفتار Queryهای فعلی با نام‌های یکتای پارامتر حفظ شود.
7. **مدیریت تعارض:** ارتباط‌های واقعاً نامعتبر یا مبهم میان پارامترها همچنان باید صریحاً با خطا رد شوند.
8. **ترتیب bind:** indexهای JDBC باید مقادیر متناظر با placeholderهای SQL نهایی را دریافت کنند، نه صرفاً پارامترها را به ترتیب جمع‌آوری‌شدنشان.
9. **انتقال پارامترهای تو‌در‌تو:** مقادیر Queryهای تو‌در‌تو هنگام انتقال به Query بیرونی، ارتباط خود را با هویت پارامتر حفظ کنند.

از الگوهای تست موجود استفاده کن و در صورت تناسب، `PreparedStatement` آزمایشی یا dynamic proxy به کار ببر. اتصال واقعی به دیتابیس لازم نیست، مگر آنکه قراردادهای Repository ضرورت آن را نشان دهند.

| `data_base/query/builder/src/main/kotlin/ast/update_builder/column_update/QueryColumnUpdateBuilder.kt` | مسیرهای مقداردهی update، `columnTag` و پارامتر متناظر را ثبت می‌کنند. |
| `data_base/migration/executor/src/main/kotlin/manager/MigrationExecutor.kt` | در ساخت بعضی Queryهای داخلی migration نیز `SqlParameter.of(...)` استفاده می‌شود؛ پس `SqlParameter` فقط متعلق به DSL SELECT نیست. |

Builderهای clause در یک `QueryRenderSelectBuilder` معمولاً همان `params` mutable را دریافت می‌کنند؛ بنابراین خود فهرست، هنگام ساخت، با ترتیب فراخوانی Builderها تغییر می‌کند. `IQueryApi.params` در `data_base/query/api/src/main/kotlin/interfaces/api/IQueryApi.kt` فقط یک `MutableList<SqlParameter<*>>` عمومی تعریف می‌کند و قرارداد positional یا ترتیب SQL برای این property مستند نمی‌کند.

دو مسیر nested، فهرست‌ها را با `addAll` منتقل می‌کنند: `QueryTableBuilder.table(blockQuery)` در `data_base/query/builder/src/main/kotlin/ast/select_builder/table/QueryTableBuilder.kt` و `QueryRenderSelectBuilder.addInlineCteSource(...)` در `data_base/query/builder/src/main/kotlin/ast/select_builder/query_render_select/QueryRenderSelectBuilder.kt`. این کار فهرست مقصد را توسعه می‌دهد و همان referenceهای `SqlParameter` را نگه می‌دارد؛ ID یا مرجع placeholder جداگانه‌ای تولید یا منتقل نمی‌شود.

در `QueryTableBuilder.cte(declaration)` نیز `declaration.createCte(declaration.params)` فراخوانی می‌شود. این Builder نتیجهٔ قبلی را cache نمی‌کند. `CteDeclaration<P>` فقط پارامتر سازنده را نگه می‌دارد و `createCte` را abstract می‌گذارد؛ ساخت CTE در `CteBuilder.buildCteDefinition(...)` یک `QueryRenderSelectBuilder` و فهرست پارامتر جدید می‌سازد. بنابراین reuse همان شیء Declaration به‌تنهایی اثبات نمی‌کند که دو source به یک Cte یا یک binding runtime اشاره دارند.

### 2. AST، ترتیب رندر و مسیر نهایی JDBC

در AST فعلی، پارامتر با نام رشته‌ای نمایش داده می‌شود، نه با reference به شیء پارامتر:

- `IQueryConditionsAst.conditionSideRight` و `QueryConditionsAst.conditionSideRight` از نوع `Any?` هستند؛ مسیر scalar، رشتهٔ `:name` را در آن‌ها می‌گذارد.
- `IQueryConditionsCollectionAst.paramsCollection` و `QueryConditionsCollectionAst.paramsCollection` نام‌های پارامتر مجموعه را نگه می‌دارند.
- ASTهای INSERT و UPDATE، `columnTag` رشته‌ای دارند؛ Builder و Renderer همان tag را به‌صورت placeholder استفاده می‌کنند.
- در این nodeها `SqlParameter` یا هویت فنی binding نگهداری نمی‌شود.

در SELECT، ترتیب SQL از ترتیب ثابت `MySqlQueryCapability.render(...)` در `data_base/query/renderer/src/main/kotlin/nodes/select_nodes/query/MySqlQueryCapability.kt` حاصل می‌شود: WITH، SELECT، TABLE/FROM، JOIN، WHERE، GROUP، ORDER، LIMIT، OFFSET. این ترتیب مستقل از ترتیب فراخوانی clauseهای Builder است.

زنجیرهٔ اجرا چنین است:

```text
QueryConditionsBuilder / Collection / INSERT / UPDATE Builder
  → نام placeholder در AST + SqlParameter در params
  → MySql*Capability نام را به SQL رندر می‌کند
  → IQueryBuilderExecutor.executeOut(...) یک BuiltQuery(sql, params) می‌سازد
  → IQueryExecute.execute(...) query را به ? تبدیل و occurrenceهای :name را از متن SQL استخراج می‌کند
  → readyParamsInQuery(...) نام را به SqlParameter resolve و هر occurrence را به index JDBC bind می‌کند
```

شواهد مرزی:

- `data_base/query/dialect/src/main/kotlin/interfaces/ISqlDialect.kt`: `render(ast)` فقط `String?` برمی‌گرداند.
- `data_base/query/dialect/src/main/kotlin/interfaces/IRenderContext.kt`: context فقط `registry` و `dialect` دارد؛ فهرست occurrenceهای پارامتر ندارد.
- `data_base/query/dialect/src/main/kotlin/manager/RendererRegistry.kt`: هر `render(...)`، `RenderContext` جدید می‌سازد و رشتهٔ renderer را برمی‌گرداند.
- `data_base/core/src/main/kotlin/query/reader/BuiltQuery.kt`, `getListParamNames()`: regex، نام occurrenceهای placeholder را از چپ به راست از SQL استخراج می‌کند و فهرست نام‌های تکرارشونده برمی‌گرداند. پارامترهای ورودی را با `parameter.name` گروه‌بندی می‌کند؛ نام تکراری فقط وقتی پذیرفته می‌شود که `value` و `sqlType` یکسان باشند. placeholder بی‌پارامتر، پارامتر بی‌placeholder و مقدار/type متعارض رد می‌شوند.
- `data_base/core/src/main/kotlin/query/reader/BuiltQuery.kt`, `getReadyQuery()`: هر placeholder شناخته‌شده را در یک گذر به `?` تبدیل می‌کند.
- `data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt`, `execute(...)` و `readyParamsInQuery(...)`: پیش از گرفتن اتصال، occurrenceها را اعتبارسنجی می‌کند؛ سپس map را با نام می‌سازد و برای هر نام occurrence به ترتیب SQL مقدار را bind می‌کند.
- `data_base/query/executor/src/main/kotlin/interfaces/IQueryBuilderExecutor.kt`, `executeOut(...)`: SQL را از AST رندر و همان پارامترهای Builder را به `BuiltQuery` می‌دهد. `QueryConsumer.sql()` نیز `BuiltQuery` حاوی SQL و کپی فهرست پارامترها را به مصرف‌کننده برمی‌گرداند.

پس در مسیر فعلی ترتیب bind نهایی از occurrenceهای SQL می‌آید، اما *انتخاب مقدار برای هر occurrence* با نام منطقی انجام می‌شود. فهرست `query.params` به‌تنهایی ترتیب positional نهایی را تعریف نمی‌کند. در Repository قراردادی پیدا نشد که مصرف‌کنندهٔ بیرونی را از مصرف positional آن منع کند؛ نبود چنین مصرفی در کد مخزن، تضمین نبود مصرف بیرونی نیست.

### 3. رفتار واقعی reuse و برخورد نام‌ها

`SqlParameter` در `data_base/core/src/main/kotlin/query/reader/SqlParamData.kt` یک `data class` عمومی با constructor سه‌پارامتری `(name, value, sqlType)` است. `of(name, value)` SQL type را resolve و `nullOf(name, sqlType)` پارامتر null می‌سازد. `bind(...)` برای مقدار null از `setNull(index, sqlType)` و برای مقدار غیر-null از `setObject(index, value, sqlType)` استفاده می‌کند.

| حالت | رفتار فعلیِ قابل‌اثبات |
|---|---|
| چند placeholder با نام یکسان | هر occurrence به یک نام منطقی resolve می‌شود؛ JDBC همان مقدار canonical را در هر index bind می‌کند. |
| چند شیء `SqlParameter` با نام، مقدار و SQL type برابر | پذیرفته می‌شوند؛ `BuiltQueryTest.acceptsEqualDuplicateParametersAndRejectsConflicts` و `QueryExecuteContractTest.duplicateEquivalentParameterObjectsUseOneCanonicalValue` این رفتار را پوشش می‌دهند. Resolver بر اساس نام و برابری مقدار/type عمل می‌کند، نه `===` و نه `data class.equals`. |
| نام یکسان با مقدار یا SQL type متعارض | رد می‌شود، قبل از bind؛ در تست‌های `BuiltQueryTest`, `QueryExecuteContractTest` و `InlineCteParameterBindingTest` شواهد دارد. |
| نام یکسان در Declarationها/Builderهای جدا | پس از انتقال پارامترها، scope فعلی در resolver وجود ندارد؛ نام‌های مساوی با مقدار/type برابر canonical می‌شوند و مقدارهای/typeهای متفاوت تعارض می‌دهند. `InlineCteParameterBindingTest.same parameter name with independent nested values is rejected instead of being resolved per scope` مقدارهای 11، 22 و 33 را مستقل bind نمی‌کند و رد آن‌ها را می‌سنجد. |
| دو ارجاع به *همان* binding در سطح API | DSL عمومی `sideValue(name, value)` شیء یا handle پارامتر را از فراخواننده نمی‌گیرد و هویت مستقلی برای تشخیص reuse عمدی ندارد. آنچه فعلاً قابل‌مشاهده است، هم‌نامی همراه با مقدار/type برابر است؛ این را نباید با وجود یک API صریح برای ارجاع مجدد به binding اشتباه گرفت. |

`data class.equals/hashCode` از `name`, `value`, `sqlType` تبعیت می‌کنند، اما مسیرهای resolve بالا از map کلیددار با `String name` و مقایسهٔ صریح `value`/`sqlType` استفاده می‌کنند. جست‌وجوی Repository کاربردی از `SqlParameter.copy()`, destructuring یا serialization پیدا نکرد؛ این فقط دربارهٔ مصرف‌کنندگان داخل Repository است. سازگاری مصرف‌کنندگان بیرونی و قرارداد انتشار/نسخه‌بندی از مخزن قابل تعیین نیست.

### 4. قرارداد هدف پیشنهادی برای scope و reuse

برای دستیابی به سناریوی Plan، قرارداد پیشنهادی این است:

1. **Binding scope** یک Builder کامل SELECT/INSERT/UPDATE/DELETE یا یک Declaration داخلی مستقل است؛ sub-builderهای همان Query scope را شریک می‌شوند. یک Declaration تو‌در‌تو scope جدا دارد.
2. درون یک scope، یک نام منطقی به یک binding تعلق دارد. فراخوانی‌های تکراری با همان نام و همان مقدار/type reuse همان binding می‌شوند؛ همان نام با مقدار یا type متعارض در همان scope همچنان خطاست. چون API فعلی چنین دو حالت را با دو نام متفاوت مشخص نمی‌کند، پارامترهای هم‌نام و برابر در یک scope به‌عنوان reuse تفسیر می‌شوند.
3. دو scope مستقل می‌توانند همان نام منطقی را با مقدار/typeهای متفاوت داشته باشند و باید bindingهای جدا داشته باشند. در نتیجه سه Declaration مستقل در سناریوی پذیرش می‌توانند `shared_value` را با مقادیر 11، 22 و 33 حمل کنند.
4. در scopeهای مستقل، حتی نام/مقدار/type برابر به‌تنهایی اثبات reuse نیست؛ bindingها مستقل‌اند، مگر اینکه یک reference واقعی binding عمداً در هر دو ساختار استفاده شده باشد. برای حفظ reuse، همان token/reference باید در هر دو occurrence حمل شود. API جاری چنین referenceای را از `ICteDeclaration.createCte` یا `IQueryTableApi.cte(declaration)` به فراخواننده برنمی‌گرداند؛ این مرز باید در Plan اجرایی رعایت یا جداگانه حل شود.
5. ترکیب nested باید identity هر binding را حفظ کند؛ انتقال `params` یا AST نباید identity را از دست بدهد. دو binding مستقل نباید صرفاً به علت نام برابر یکی شوند.
6. برخورد هویت فقط در صورت یکی‌بودن token/object مجاز است. نام منطقی جداگانه برای SQL/logging باقی می‌ماند و برای resolve مقدار به‌تنهایی کافی نیست.

این قرارداد رفتار فعلی را برای پارامترهای هم‌نام و برابر در یک scope حفظ می‌کند و محدودیت فعلیِ رد نام یکسان میان scopeهای مستقل را برمی‌دارد. آن قسمت تغییر رفتار آگاهانهٔ هدف Plan است و باید به‌عنوان regression شکسته/جایگزین شود، نه اینکه تست conflict فعلی بی‌توضیح حذف شود.

### 5. گزینه‌های تولید شناسه و توصیه

| گزینه | مزیت | هزینه/ریسک واقعی |
|---|---|---|
| UUID یا رشتهٔ تصادفی | scopeهای جدا معمولاً نام برخوردی ندارند و انتقال ساده است. | یکتایی ریاضی تضمین نمی‌شود؛ collision detection همچنان لازم است. اگر ID در placeholder SQL قرار گیرد، SQL عمومی تغییر می‌کند یا باید شکل نمایشی جدا ساخته شود. |
| شمارندهٔ سراسری | تخصیص قطعی و ساده در یک process و thread-safe در صورت استفاده از atomic counter است. | state سراسری، وابستگی به lifecycle/process و احتمال overflow؛ API/تست نباید بر مقدار عددی خاص تکیه کند. |
| شمارندهٔ محلی به Builder یا Declaration | قطعی و مستقل در هر Builder. | ترکیب دو Builder می‌تواند ID مساوی بسازد؛ نیازمند namespace scope پایدار یا remap/collision handling در composition است. |
| مشتق‌سازی از نام | بدون allocator جداگانه قابل محاسبه است. | همان نام منطقیِ مستقل را ادغام می‌کند و نیاز اصلی را حل نمی‌کند؛ scope id جدا هم لازم می‌شود. |
| token ارجاعی opaque با reference identity | دو object زندهٔ متمایز با `===` برخورد ندارند؛ نیاز به رشتهٔ تصادفی/عددی یا counter سراسری نیست و انتقال reference nested می‌تواند identity را حفظ کند. | Renderer و BuiltQuery باید token را تا occurrence SQL حفظ کنند؛ map مبتنی بر `equals` کافی نیست. نوع/محل token باید با مرز Gradle modules سازگار باشد. |

**توصیهٔ معماری ثبت‌شده در ممیزی:** token همان reference `SqlParameter` است؛ consumer آن را مدیریت نمی‌کند و `data class.equals` مبنای resolve نیست. مرز moduleها با `RenderedSql` و `BoundBuiltQuery` پوشش داده می‌شود. جزئیات اجرایی نهایی در بخش 10 و Plan اجرایی آمده است.

بااین‌حال، source فعلی AST نام رشته‌ای را نگه می‌دارد و Renderer فقط `String` می‌دهد. برای اینکه SQL نمایشی همچنان `:shared_value` بماند و هم‌زمان هر occurrence به binding مستقل وصل شود، مسیر render باید occurrenceهای binding را به‌صورت sidecar و دقیقاً هم‌ردیف placeholderها تحویل دهد؛ مثلاً یک نتیجهٔ binding-aware شامل `sql` و فهرست occurrence identityها. `BuiltQuery` و `IQueryExecute` باید از این مسیر identity-aware استفاده کنند. مسیر قدیمی ساخت دستی `BuiltQuery(sql, params)` می‌تواند موقتاً name-based باقی بماند تا قرارداد فعلی آن حذف نشود.

گزینهٔ جایگزین، درج شناسهٔ یکتا در نام فیزیکی placeholder است. این کار می‌تواند از parser فعلی عبور کند، اما SQL خروجی، `QueryConsumer.sql()`, log/callback و هر مصرف‌کننده‌ای که `:logical_name` می‌بیند را تغییر می‌دهد. به‌دلیل سطح عمومی این خروجی‌ها و مجهول‌بودن مصرف‌کنندگان بیرونی، این گزینه توصیهٔ پیش‌فرض نیست.

### 6. حداقل محدودهٔ تغییر برای Plan اجرایی

در صورت تصویب قرارداد بالا، Plan اجرایی باید حداقل این زنجیره را پوشش دهد؛ این فهرست مجوز تغییر در این مرحله نیست:

1. در `query:builder`، context پارامتر به ازای Query scope، انتقال آن به sub-builderهای همان scope، و ایجاد/reuse binding در `QueryConditionsBuilder`, `QueryConditionsCollectionBuilder`, `QueryColumnInsertBuilder`, `QueryColumnUpdateBuilder` و محل‌های دیگری که جست‌وجوی `SqlParameter.of` نشان داد.
2. در `query:ast`، نگهداری reference binding کنار placeholderهای scalar، collection، INSERT و UPDATE؛ نام منطقی همچنان برای SQL باقی بماند. `query:ast` اکنون به `query:core` وابسته است، ولی اگر token نوع جدیدی در Core قرار گیرد باید وابستگی API دقیقاً بررسی شود.
3. در `query:dialect` و `query:renderer`، حفظ SQL متناظر و انتقال ordered binding occurrences از nested rendererها به render نهایی. قرارداد فعلی `ISqlDialect.render`, `IRendererRegistry.render` و `IRenderContext` رشته‌محور است؛ sidecar نیازمند یک مسیر render جدید یا تغییر مشخص در context/registry است.
4. در `query:executor` و `core`، حمل sidecar به مرز `BuiltQuery`, اعتبارسنجی placeholder-to-binding، و حفظ مسیر legacy name-based برای `BuiltQuery`هایی که دستی ساخته می‌شوند.
5. در `manager:execute`, resolve هر occurrence با binding identity و bind همان شیء در index نهایی؛ `readyParamsInQuery(..., List<String>)` به‌تنهایی برای دو مقدار با نام یکسان کافی نیست و باید حفظ یا با یک مسیر overloadشده تکمیل شود.
6. scope migration باید در Plan اجرایی صریح شود: `migration:builder` و `migration:executor` نیز `SqlParameter`/`BuiltQuery` مشترک را مصرف می‌کنند. اگر تغییرات identity فقط برای QueryBuilder است، migration باید با مسیر name-based فعلی سازگار بماند؛ اگر resolver مشترک تغییر کند، تست‌های migration و `IMigrationExecutor` نیز در scope قرار می‌گیرند.

مرز ماژولی از Gradle نیز تأیید می‌شود: `data_base/query/ast/build.gradle.kts`, `data_base/query/builder/build.gradle.kts`, `data_base/query/renderer/build.gradle.kts`, `data_base/query/executor/build.gradle.kts` و `data_base/manager/execute/build.gradle.kts` هرکدام subproject جدا هستند و dependencyهای Core را به‌صورت `implementation(project(...))` می‌گیرند. بنابراین Kotlin `internal` یک راه دسترسی مستقیم بین این moduleها نیست؛ type/reference موردنیاز برای AST-to-executor resolution باید از مرز moduleها عبور کند یا با یک carrier مشترک در ماژول مناسب جابه‌جا شود.

### 7. سازگاری API عمومی و آثار قابل‌اثبات

- حفظ primary constructor فعلی `SqlParameter(name, value, sqlType)` و factoryهای `of`/`nullOf`، safest baseline برای source compatibility است. قرار دادن `id` به‌عنوان پارامتر جدید primary constructor، امضای constructor و API تولیدشدهٔ data class (`copy`, componentهای جدید و destructuring) را تغییر می‌دهد؛ binary compatibility تضمین‌شده نیست.
- یک property غیر-constructor نیز به‌تنهایی حل نیست: اگر به‌صورت public باشد ID را در API قابل مشاهده می‌کند؛ اگر Kotlin `internal` باشد، دسترسی Builder/AST/Renderer در Gradle moduleهای جدا باید با visibility واقعی حل شود. `internal` Kotlin به‌طور عادی بین این subprojectها قابل دسترسی نیست.
- `IQueryApi.params` و `IMigrationApi.params` هر دو لیست `SqlParameter` عمومی‌اند؛ فهرست mutable باقی‌ماندنش می‌تواند direct mutation و `BuiltQuery` دستی را حفظ کند، اما identity-aware Builder به ارتباط AST-to-binding جداگانه نیاز دارد.
- `BuiltQuery` یک `data class` عمومی با constructor `(query, params)` است. تغییر پارامترهای primary constructor می‌تواند `copy`, `componentN`, `equals/hashCode` و امضای JVM را تغییر دهد. مصرف‌کنندگان مستقیم در تست‌های `BuiltQueryTest` و `QueryExecuteContractTest` ثابت‌اند؛ نبود مصرف بیرونی/باینری از Repository اثبات نمی‌شود.
- `IQueryExecute.readyParamsInQuery(...)`، `IQueryBuilderExecutor.executeOut(...)`، `QueryConsumer.sql()` و migration executor مرزهای دیگر مصرف عمومی‌اند. امکان نگه‌داشتن API قدیمی و افزودن مسیر identity-aware باید در Plan اجرایی دقیق شود؛ در این مرحله binary compatibility ادعا نمی‌شود.
- `blockQueryInfo` در `IQueryBuilderExecutor.executeOut(...)` و migration executor، `MutableMap<String, Any?>` می‌سازد. با duplicate logical name و مقادیر متفاوت، `associate { name to value }` آن‌ها را به یک ورودی map فرو می‌کاهد. این callback نمای occurrence-aware نیست. قرارداد مطلوب آن برای Queryهای دارای duplicate نام هنوز تعیین نشده است.
- جست‌وجوی source/test/documentation این Repository شواهدی از serialization روی `SqlParameter`, destructuring/copy call site, انتشار artifact, نسخه‌گذاری یا مصرف‌کنندهٔ بیرونی پیدا نکرد. این موارد نامشخص‌اند، نه اثباتِ نبود مصرف‌کننده.

### 9. وضعیت هنگام ممیزی اولیه (تاریخی؛ پیش از تصمیم‌های بخش 10)

**یافته‌های قطعی از سورس:** ID در هیچ لایه‌ای وجود ندارد؛ Builder placeholder و parameter را جدا و با name متصل می‌کند؛ nested `addAll` referenceهای پارامتر را حفظ می‌کند ولی هویت AST-placeholder ندارد؛ renderer رشته برمی‌گرداند؛ `BuiltQuery` و JDBC resolver name-based هستند؛ نام مساوی با مقدار/type برابر reuse مؤثر دارد و تعارض نام مساوی با مقدار/type متفاوت رد می‌شود؛ همان `SqlParameter` در Core بین Query و Migration مشترک است.

**توصیه‌های طراحی:** ID را consumer نفرستد؛ نام منطقی از هویت binding جدا بماند؛ scope منطقی هر Query/Declaration تعریف شود؛ repeated name/value/type در همان scope reuse شود؛ نام مساوی در scope مستقل ID جدا بگیرد؛ binding references تا رندر و bind حفظ شوند؛ API legacy دستی `BuiltQuery` تا تصمیم سازگاری name-based بماند؛ افزودن `id` به primary constructor عمومی `SqlParameter` مسیر پیش‌فرض نباشد.

**مواردی که هنگام ثبت ممیزی اولیه باز بودند:**

1. مالک باید بپذیرد که duplicate نام‌های دارای مقدار/type متفاوت *در scopeهای جدا* از conflict فعلی به bindingهای مستقل تغییر می‌کنند، درحالی‌که تعارض در یک scope باقی می‌ماند.
2. باید تأیید شود که reuse به همان binding reference محدود است و نام/مقدار/type برابر در Declarationهای مستقل به‌خودی‌خود reuse محسوب نمی‌شود. کد فعلی هر دو حالت را با نام یکسان canonical می‌کند؛ API فعلی reference پارامتر را از Declaration به caller بازنمی‌گرداند.
3. باید انتخاب شود که برای حفظ SQL نمایشی `:logical_name`، sidecar ordered occurrences به مسیر render/BuiltQuery اضافه شود، یا placeholderهای فیزیکی یکتا شوند و تغییر خروجی SQL/QueryInfo پذیرفته شود. شواهد فعلی ترجیح sidecar را نشان می‌دهد، اما امضای دقیق و compatibility آن تصمیم نهایی نشده است.
4. رفتار `blockQueryInfo` برای نام‌های منطقی تکراری مشخص شود؛ map فعلی نمی‌تواند چند مقدار برای یک کلید را نمایش دهد.
5. محدودهٔ migration مشخص شود: حفظ resolver legacy در `BuiltQuery` دستی، یا انتقال یکپارچهٔ resolver مشترک و تست‌های migration.
6. سیاست مصرف‌کنندهٔ بیرونی/source و binary compatibility از خود Repository قابل تعیین نیست. پیش از تغییر data classهای عمومی یا primary constructorهای `BuiltQuery` باید این ریسک را بپذیرند یا آن مسیرها حفظ شوند.

**وضعیت در زمان ثبت این ممیزی اولیه:** `Draft / Not Implementation Ready`. این وضعیت تاریخی بود و پس از ثبت تصمیم‌های نهایی بخش 10 به‌روزرسانی شد. در همان ممیزی هیچ production/test تغییر نکرد و هیچ Build یا Test اجرا نشد.

## 10. تصمیم نهایی معماری — اصلاح‌کنندهٔ موارد باز ممیزی

**وضعیت این بخش:** تصمیم قبلی و ثبت تاریخی است. بازبینی حداقل تغییر در بخش 11، دامنهٔ پیاده‌سازی آن را به SELECT و Declarationهای تو‌در‌تو محدود می‌کند و تغییرهای عمومی INSERT/UPDATE/DELETE را از کار جاری خارج می‌سازد.

**تاریخ بستن تصمیم‌ها:** 2026-10-13. این بخش تصمیم‌های طراحی را بر پایهٔ شواهد بخش‌های پیشین نهایی می‌کند و هر عبارت قبلی دربارهٔ «تصمیم باز» یا «نیاز به انتخاب مالک» را برای این موضوعات جایگزین می‌کند. هیچ source یا test در این مرحله تغییر نکرد و هیچ Build یا Test اجرا نشد.

### 10.1 هویت binding و scope

`ParameterBindingScope` جزئیات `internal` در `query:builder` است و در هیچ سازنده یا امضای عمومی Builder ظاهر نمی‌شود. امضاهای سازندهٔ عمومی موجود حفظ می‌شوند؛ Builderهای ریشه scope را می‌سازند و آن را از مسیر داخلی به sub-builderهای هم‌دامنه می‌رسانند.

1. **هویت داخلی binding همان هویت مرجعی شیء `SqlParameter` است.** `SqlParameter` به‌وسیلهٔ Builder ساخته می‌شود و API مقداردهی Builder شناسه‌ای از مصرف‌کننده نمی‌گیرد. در مسیر identity-aware، تمام مقایسه‌ها و resolveها باید بر پایهٔ reference identity (`===` یا `IdentityHashMap`) باشند؛ `SqlParameter.equals`, نام، مقدار و `sqlType` به‌تنهایی هویت binding نیستند.
2. **Scope** یک Query کامل یا یک Declaration کامل است. sub-builderهای همان Query یک scope را به اشتراک می‌گذارند. هر Query/Declaration تو‌در‌توی مستقلی که Builder جداگانه برای آن ساخته می‌شود scope تازه‌ای دارد.
3. داخل یک scope، پارامترهای تکراری با `name`, `value` برابر طبق برابری Kotlin (`==`) و `sqlType` برابر، یک binding هستند. `ParameterBindingScope` همان reference canonical را برمی‌گرداند؛ هر occurrence در AST به همان reference اشاره می‌کند. نام یکسان با مقدار یا `sqlType` متفاوت در یک scope همچنان خطاست.
4. بین دو scope مستقل، نام/مقدار/type برابر به معنی reuse نیست. هر scope reference مستقل تولید می‌کند. در نتیجه نام `shared_value` می‌تواند در سه سطح مستقل به مقادیر و SQL typeهای متفاوت متصل شود. انتقال یک CTE یا AST، referenceهای ساخته‌شده را عیناً حفظ می‌کند؛ API عمومی تازه‌ای برای اشتراک عمدی binding بین scopeها اضافه نمی‌شود.
5. چون هر reference تا زمان execution از AST/sidecar نگه داشته می‌شود، دو binding زنده با `===` یکسان‌اند یا مستقل؛ برخورد رشته‌ای، تصادفی، شمارنده‌ای یا global allocator وجود ندارد. `System.identityHashCode` به‌تنهایی برای تشخیص هویت مجاز نیست و فقط `IdentityHashMap`/مقایسهٔ مرجعی معتبر است.

این انتخاب از تولید UUID، شمارندهٔ سراسری، namespace و بازنام‌گذاری placeholderها کم‌تغییرتر است: `SqlParameter` از پیش در Core ساخته می‌شود و `query:ast`، `query:builder` و `query:renderer` همگی به Core وابستگی دارند. این شناسه runtime-only است؛ هویت binding پس از serialization، بازسازی پارامتر یا کپی با `SqlParameter.copy()` حفظ نمی‌شود و چنین انتقالی در قرارداد موجود پشتیبانی نشده است.

### 10.2 مسیر داده از Builder تا JDBC

1. `ParameterBindingScope` در ریشهٔ Builder ساخته می‌شود و پیش از اجرای block از مسیر داخلی به sub-builderهای همان Query متصل می‌شود؛ سازنده‌های عمومی فعلی تغییر نمی‌کنند. برای هر مقدار، scope یک `SqlParameter` می‌سازد یا reference canonical موجود را reuse می‌کند.
2. AST علاوه بر نام منطقی placeholder، reference پارامتر همان occurrence را نگه می‌دارد. برای collection، referenceها به ترتیب عضوها و هم‌تراز با نام‌های `paramsCollection` ثبت می‌شوند؛ برای scalar condition، INSERT و UPDATE هر node reference خود را دارد.
3. `IRenderContext` در یک render session توان ثبت occurrence دارد. Renderer هنگام درج placeholder، همان لحظه reference node را به collector مشترک اضافه می‌کند. Registryهای بازگشتی باید همان session را شریک شوند تا ترتیب collector با ترتیب واقعی SQL، از جمله subtreeهای nested، یکی بماند.
4. نتیجهٔ render شامل SQL نمایشی فعلی با placeholderهای `:logical_name` و sidecar مرتب `parameterOccurrences` است. `query:executor` این دو را همراه پارامترهای Query در `BoundBuiltQuery` می‌برد؛ `manager:execute` هر occurrence را با reference متناظر به ترتیب index JDBC bind می‌کند.
5. اعتبارسنجی مسیر binding-aware کنترل می‌کند تعداد و نام placeholderهای SQL با sidecar هماهنگ باشد، هر reference در فهرست params وجود داشته باشد و هیچ پارامتر بی‌مصرفی باقی نماند. تعارض درون یک scope هنگام ثبت binding رد می‌شود. یک Renderer که occurrence tracking را پشتیبانی نمی‌کند، مجاز نیست sidecar ناقص را به‌عنوان موفقیت identity-aware جا بزند؛ مسیر Builder باید به legacy mode برگردد و قواعد name-based آن در تعارض‌ها همچنان خطا بدهد.

### 10.3 دو مسیر اجرا و قراردادهای legacy

- **مسیر جدید QueryBuilder:** رندر binding-aware → `BoundBuiltQuery` → overloadهای identity-aware در `IQueryExecute`/`QueryExecute` → bind occurrence به occurrence. SQL عمومی همچنان از `:name` استفاده می‌کند.
- **مسیر legacy دستی:** `BuiltQuery(sql, params)` بدون sidecar باقی می‌ماند؛ `getListParamNames()`, `getReadyQuery()` و `readyParamsInQuery(..., List<String>)` همان رفتار name-based فعلی را حفظ می‌کنند. duplicate نام با مقدار/type برابر پذیرفته می‌شود؛ نام تکراری با مقدار/type متعارض همچنان پیش از اتصال JDBC رد می‌شود.
- `QueryConsumer.sql()` همچنان `BuiltQuery` برمی‌گرداند و در مسیر legacy است. این متد SQL و پارامترها را برای مصرف دستی/بازرسی ارائه می‌کند؛ برای اجرای identity-aware همان Query باید از مسیر اجرای مستقیم QueryBuilder استفاده شود. این Plan API جدیدی مانند `sqlWithBindings()` اضافه نمی‌کند.
- overloadهای تازهٔ `IQueryExecute` باید default implementation داشته باشند که به مسیر قدیمی delegate کند. `QueryExecute` استاندارد آن‌ها را برای binding-aware mode override می‌کند. پیاده‌سازی سفارشی `IQueryExecute` که override نمی‌کند، رفتار legacy امن را دارد و برای duplicate bindingهای هم‌نام و متعارض خطا می‌دهد؛ هیچ مقدار نادرستی bind نمی‌شود.
- سازندهٔ عمومی و factories `SqlParameter(name, value, sqlType)`, `of` و `nullOf` بدون تغییر می‌مانند. `BuiltQuery(query, params)` نیز یک data class با همان primary constructor باقی می‌ماند. `copy`, `componentN`, equality/hashCode و destructuring این دو نوع تغییر نمی‌کنند؛ هویت مرجعی جزو `data class` equality نیست.

### 10.4 قرارداد `query.params` و `blockQueryInfo`

- `IQueryApi.params` همچنان فهرست mutable پارامترهاست و **ترتیب positional نهایی SQL را تعریف نمی‌کند**. در مسیر Builder، این فهرست برای سازگاری، اعتبارسنجی عضویت bindingها و مشاهدهٔ پارامترهای ساخته‌شده باقی می‌ماند؛ ترتیب bind فقط از sidecar occurrenceهای Renderer به دست می‌آید. مصرف‌کنندهٔ `params` نباید ترتیب فهرست را به‌عنوان ترتیب placeholder/JDBC فرض کند.
- `blockQueryInfo(String?, MutableMap<String, Any?>)` قرارداد legacy نقشه‌ای خود را حفظ می‌کند: کلید، نام منطقی است و برای نام تکراری، همان `associate` موجود مقدار آخرِ فهرست `params` را نگه می‌دارد. این callback عمداً نمای کامل occurrenceها نیست و نمی‌تواند چند مقدار برای یک نام را نمایش دهد. این محدودیت اکنون صریح و قابل‌آزمون است؛ callback در bind یا انتخاب مقدار JDBC دخالت ندارد. API occurrence-aware جدید به این Plan افزوده نمی‌شود.

### 10.5 مرز ماژولی و سازگاری API

- `SqlParameter` و `BuiltQuery` در `data_base/core` می‌مانند. برای عبور اطلاعات از Gradle moduleها، carrierهای framework-level افزوده می‌شوند: نتیجهٔ render binding-aware در `query:dialect` و `BoundBuiltQuery` در Core. constructor یا field قابل‌تنظیم `id` به API مصرف‌کننده اضافه نمی‌شود.
- AST referenceها را در `query:ast` نگه می‌دارد؛ Builder scope و تولید reference در `query:builder` است؛ رندر و مرتب‌سازی occurrence در `query:dialect`/`query:renderer` انجام می‌شود؛ تبدیل به query قابل bind در `query:executor` و bind JDBC در `data_base/manager/execute` است. جهت dependencyهای فعلی حفظ می‌شود و هیچ وابستگی از Core به Query Builder/Renderer ایجاد نمی‌شود.
- Migration در `data_base/migration` از مسیر legacy `BuiltQuery`/`IQueryExecute` استفاده می‌کند و به binding identity مهاجرت داده نمی‌شود. resolver قدیمی دست‌نخورده می‌ماند؛ regression تست Migration لازم است تا ثابت کند overload قدیمی همچنان انتخاب می‌شود.
- امضاهای فعلی `SqlParameter`, factories و `BuiltQuery` حفظ می‌شوند و APIهای جدید additive هستند. این تصمیم source compatibility درون مخزن را تقویت می‌کند، اما **binary/ABI compatibility یا نبود مصرف‌کنندهٔ بیرونی را تضمین نمی‌کند**؛ Repository فاقد شواهد artifactهای منتشرشده، سیاست نسخه‌بندی و مصرف‌کننده‌های خارجی است. بررسی ABI بیرونی خارج از شواهد فعلی و به‌عنوان محدودیت گزارش می‌شود، نه یک تصمیم طراحی باز.

## 11. بازبینی حداقل تغییر — تصمیم جاری

**این بخش تصمیم جاری است و هر پیشنهاد گسترده‌تر در بخش 10 یا نسخهٔ اجرایی قبلی را جایگزین می‌کند.** شواهد اصلی از سورس و تست موجود **data_base/query/builder/src/test/kotlin/ast/select_builder/InlineCteParameterBindingTest.kt** گرفته شده‌اند. این بازبینی فقط اسناد را تغییر می‌دهد؛ هیچ source/test تغییر نکرده و Build یا Test اجرا نشده است.

### 11.1 مسئلهٔ تأییدشده

- **data_base/core/src/main/kotlin/query/reader/BuiltQuery.kt** و **BuiltQuery.getListParamNames()** پارامترها را بر مبنای **SqlParameter.name** resolve می‌کنند. **data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt** نیز در **readyParamsInQuery(...)** نام‌ها را به یک map تبدیل می‌کند؛ برای یک نام با مقدار یا SQL type متعارض، مسیر فعلی خطا می‌دهد. پس name-only resolution قادر به تفکیک چند مقدار مستقل با یک نام منطقی نیست.
- تست **InlineCteParameterBindingTest** نشان می‌دهد در ساخت بیرونی **where → from** فهرست params برابر **[33, 11, 22]** است، اما placeholderهای SQL به ترتیب **[11, 22, 33]** رندر می‌شوند. ترتیب Builder یا فهرست **params** را نمی‌توان به‌عنوان ترتیب bind استفاده کرد.
- **IQueryConditionsAst.conditionSideRight** از نوع **Any?** است و **IQueryConditionsCollectionAst.paramsCollection** از نوع **MutableList<Any>**. Builder اکنون در این خانه‌ها رشتهٔ **:name** یا نام پارامتر می‌گذارد؛ rendererهای **MySqlQueryConditionCapability** و **MySqlQueryConditionCollectionCapability** همان داده را به placeholder SQL تبدیل می‌کنند. این خانه‌ها می‌توانند reference شیء **SqlParameter** را نیز نگه دارند، بدون تغییر امضای عمومی AST.
- **RendererRegistry.render(...)** در **data_base/query/dialect/src/main/kotlin/manager/RendererRegistry.kt** برای هر رندر بازگشتی **RenderContext** جدید می‌سازد. بنابراین یک collector محلی باید از ریشه تا rendererهای فرزند منتقل شود تا occurrenceها را در ترتیب واقعی SQL ببیند.

### 11.2 گزینه‌ها و حداقل راهکار

| گزینه | ارزیابی |

| استفاده از ترتیب params برای انتساب occurrenceهای هم‌نام | کافی نیست؛ تست موجود اختلاف ترتیب Builder و SQL را اثبات می‌کند. |

نام‌های موقت placeholder فقط در BuiltQuery داخلی‌ای ساخته می‌شوند که **QueryBuilderExecutor** به **executeSelect** می‌دهد. آن‌ها هویت binding نیستند و به مصرف‌کننده نمایش داده نمی‌شوند. Query SQL عمومی، render معمولی، callback اطلاعات Query و **SqlParameter.name** همچنان از نام منطقی فعلی استفاده می‌کنند. تخصیص نام موقت باید محلی و قطعی برای همان اجرای Query باشد و با نام‌های موجود در SQL و params برخورد نکند.

### 11.3 تصمیم طراحی حداقلی

1. محدوده فقط SELECT و Declarationهای مستقل تو‌در‌تو در SELECT است. API عمومی Builder، امضای سازنده‌های فعلی، INSERT/UPDATE/DELETE و مسیر Migration تغییر نمی‌کنند.
2. Builder از یک **ParameterBindingScope** داخلی برای Query ریشه و هر Declaration که جداگانه ساخته شده استفاده می‌کند. این scope برای هر Builder فرزند به‌طور خودکار تازه نمی‌شود: `table { ... }` در SELECT FROM و `with(name, block)` و منابع/شرط‌های JOIN که API فعلی اجازه می‌دهد scope والد را شریک می‌کنند؛ API فعلی nested SELECT source در JOIN را مجاز نمی‌کند؛ `cte(declaration)` و dependencyهای آن scope تعریف Declaration خود را حفظ می‌کنند. در یک scope، سه‌تایی **(name, value ==, sqlType)** سازگار همان reference canonical را reuse می‌کند؛ نام یکسان با value یا type متعارض همچنان رد می‌شود. این اعتبارسنجی هنگام ثبت Builder انجام می‌شود؛ رد پیش از JDBC حفظ می‌شود، اما زمان مشاهدهٔ خطا از اعتبارسنجی نهایی BuiltQuery زودتر خواهد بود. این تفاوت بیرونی و قابل‌مشاهده است و Plan اجرایی باید آن را صریحاً با test ثبت کند؛ شواهد فعلی زمان دقیق را به‌عنوان قرارداد ممنوع نکرده‌اند.
3. به‌جای افزودن فیلد یا marker به AST، Builder reference خود **SqlParameter** را در خانه‌های Any موجود ذخیره می‌کند:
   - scalar: **IQueryConditionsAst.conditionSideRight**؛
   - collection: اعضای **IQueryConditionsCollectionAst.paramsCollection**.

   Renderer همچنان همان placeholder منطقی **:name** را تولید می‌کند و reference را در sidecar ثبت می‌کند. خانه‌های قدیمی String برای AST دستی یا قدیمی حفظ می‌شوند. امضای AST تغییر نمی‌کند؛ بااین‌حال مصرف‌کننده‌ای که مقدار runtime این خانه‌های Any را مستقیماً بررسی می‌کند ممکن است به‌جای String یک SqlParameter ببیند. جست‌وجوی فعلی Repository فقط Builder و rendererهای مربوط را به‌عنوان مصرف‌کنندهٔ این خانه‌ها نشان داده است؛ مصرف‌کنندهٔ بیرونی قابل احراز نیست.
4. sidecar فقط در render session نگهداری می‌شود. **IRenderContext** و **RenderContext** یک **MutableList<Any>?** اختیاری می‌گیرند؛ یک wrapper داخلی برای **IRendererRegistry** همان فهرست را در renderهای بازگشتی حفظ می‌کند، چون **RendererRegistry** عادی context تازه می‌سازد. **BaseSqlDialect** یک helper افزایشی **renderWithBindings(ast)** ارائه می‌دهد: SQL و sidecar را با **Pair** موجود Kotlin حمل می‌کند، بدون تغییر قرارداد **ISqlDialect**. **QueryBuilderExecutor** فقط برای dialect مبتنی بر **BaseSqlDialect** از این helper استفاده می‌کند؛ dialectهای دیگر در مسیر render معمولی و legacy می‌مانند. rendererهای شرط scalar و collection، reference را هم‌زمان با افزودن placeholder به خروجی ثبت می‌کنند. نوع عمومی جدید **RenderedSql** یا interface collector لازم نیست.
5. فقط **QueryBuilderExecutor** برای اجرای SELECT این sidecar را مصرف می‌کند. اگر تعداد و نام placeholderها با occurrenceها منطبق باشد و شمارش هویت referenceهای sidecar با فهرست params برابر باشد، برای هر occurrence یک نام فیزیکی موقت و یکتا ساخته می‌شود؛ candidate باید با grammar شناسهٔ **BuiltQuery** سازگار باشد، با placeholderهای SQL اصلی و نام‌های params برخورد نکند و پیش از candidate بعدی به مجموعهٔ اشغال‌شده افزوده شود. SQL اجرایی با پیمایش ترتیبی tokenها ساخته می‌شود، نه جایگزینی متنی گسترده؛ SQL اجرایی و کپی‌های **SqlParameter** با آن نام‌ها به **BuiltQuery** فعلی داده می‌شوند. سپس همان **executeSelect** و همان **IQueryExecute/QueryExecute** name-based مسیر JDBC را اجرا می‌کنند. اگر sidecar غایب یا ناقص باشد، مسیر legacy با SQL اصلی اجرا می‌شود؛ تعارض واقعی در آن مسیر همچنان رد می‌شود. منطق بازنویسی باید parser placeholder را با الگوی فعلی **BuiltQuery** هم‌تراز نگه دارد و با تست تطبیق SQL، sidecar و params اعتبارسنجی شود.
6. **SqlParameter**، factoryهای آن، data-class semantics، **BuiltQuery(query, params)**، **getListParamNames()**، **getReadyQuery()** و **readyParamsInQuery(...)** تغییر نمی‌کنند. BuiltQuery دستی همچنان name-based است و پارامترهای هم‌نام متعارض را رد می‌کند. **QueryConsumer.sql()**، **IQueryBuilderExecutor.executeOut(...)** و SQL معمولی، نام‌های منطقی را حفظ می‌کنند.
7. **blockQueryInfo** همان query SQL منطقی و map فعلی با رفتار last-wins را می‌گیرد؛ این map برای نام تکراری occurrence-aware نمی‌شود و مبنای bind نیست.
8. Migration تغییر نمی‌کند و از مسیر BuiltQuery و executeSelect/عملیات فعلی خود استفاده می‌کند. چون ماژول **manager:execute** و قرارداد **IQueryExecute** تغییر نمی‌کنند، تست Migration یک رگرسیون محافظتی است، نه نیاز به مهاجرت production.

### 11.4 تغییرهای گستردهٔ حذف‌شده از دامنه

- افزودن **BoundBuiltQuery** یا **RenderedSql**، overload جدید در **IQueryExecute/QueryExecute**، تغییر **BuiltQuery**، یا تغییر وابستگی Gradle لازم نیست؛ تبدیل نام فیزیکی موقت، resolver موجود را برای مسیر اجرای مستقیم SELECT قابل استفاده می‌کند.
- گسترش AST با interfaceهای marker، propertyهای binding-aware یا nodeهای جدید لازم نیست؛ فیلدهای Any فعلی جای ذخیرهٔ reference را دارند.
- تغییر rendererهای DML، API عمومی **IQueryBuilderExecutor**، **SqlParameter**، Migration، placeholderهای SQL قابل مشاهده یا map مربوط به **blockQueryInfo** لازم نیست.
- traversal موازی AST در Executor انتخاب نمی‌شود؛ sidecar ترتیب را از مسیر واقعی رندر می‌گیرد.

### 11.5 سازگاری و محدودیت‌های شواهد

- امضاها و constructorهای فعلی SqlParameter، BuiltQuery و Builderها دست‌نخورده می‌مانند؛ دو hook زیرساختی افزایشی در IRenderContext و BaseSqlDialect لازم‌اند. این تغییر افزایشی به‌تنهایی تضمین binary compatibility برای مصرف‌کنندگان بیرونی نیست. Repository اطلاعات artifactهای منتشرشده یا سیاست ABI را اثبات نمی‌کند.
- مسیر built-in انتخاب‌شده توسط `DialectSelector` فقط `MySqlDialect` و `MariaDbDialect` را دارد؛ `MariaDbDialect` از `MySqlDialect` ارث می‌برد و هر دو از `BaseSqlDialect` استفاده می‌کنند. بنابراین هر دو dialect داخلی در دامنهٔ tracking هستند. `QueryBuilderExecutor` در این Repository dialect تزریقی یا registry سفارشی نمی‌پذیرد. مصرف‌کننده‌ای که `IQueryBuilderExecutor` سفارشی بسازد، یا dialect/renderer بیرونی را خارج از مسیر فعلی انتخاب کند، از قابلیت identity-aware این Plan تضمین نمی‌گیرد؛ این محدودیت فعلیِ مسیرهای سفارشی و خارج از دامنه است، نه محدودیت یکی از dialectهای داخلی.
- اگر SQL خام یا AST دستی placeholderی بسازد که sidecar متناظر ندارد، مسیر identity-aware نباید آن را حدس بزند؛ باید legacy fallback اجرا شود و اعتبارسنجی موجود missing/extra/conflict را اعمال کند.
- پارامتر conflictدار در یک scope هنگام ثبت Builder رد می‌شود، زودتر از اعتبارسنجی legacy که پیش از اتصال JDBC انجام می‌شد. قاعدهٔ رد و fail-fast بودن حفظ می‌شود، اما زمان exception تغییر می‌کند. حفظ دقیق زمان قبلی بدون نگهداری اطلاعات scope در ساختار Query تغییر اضافی می‌خواهد و در این راهکار حداقلی هدف نیست.
- بازنویسی placeholder فقط برای BuiltQuery خصوصی اجرای SELECT انجام می‌شود. query قابل مشاهده و blockQueryInfo با placeholder منطقی باقی می‌مانند؛ نام داخلی نباید در API یا گزارش عمومی نشت کند.

### 11.6 اصلاحات حاصل از ممیزی نهایی source-level

این بخش، مرزهای scope و ثبت occurrence را دقیق می‌کند و بر عبارت کلی «هر SELECT» در بخش 11.3 اولویت دارد.

- **مرز scope:** scope مستقل متعلق به Query ریشه‌ای و هر Declaration که جداگانه ساخته شده است؛ نه هر نمونهٔ `QueryRenderSelectBuilder` که صرفاً برای ساخت clause فرزند ساخته می‌شود. `table { ... }` در SELECT FROM و `with(name, block)` باید scope مالک Query را به اشتراک بگذارند تا رفتار تعارض نام‌های فعلی در Queryهای تو‌در‌تو حفظ شود. منابع JOIN که API فعلی اجازه می‌دهد و شرط‌های JOIN نیز scope Query مالک را شریک‌اند؛ `table(blockQuery)` در JOIN مجاز نیست. `cte(declaration)` و dependencyهای آن scope تعریف Declaration خود را حفظ می‌کنند و با scope Query مصرف‌کننده ادغام نمی‌شوند. شواهد مسیرها: `QueryTableBuilder.table(blockQuery)` یک Builder nested می‌سازد؛ `QueryRenderSelectBuilder.from(...)` و `joins(...)` Builderهای منبع/شرط را می‌سازند؛ `QueryRenderSelectBuilder.withs(...)`، `QueryWithsBuilder.addWith(...)` و `QueryWithsItemBuilder.with(name, block)` برای بدنهٔ block از همان فهرست params استفاده می‌کنند. این مرزبندی نباید امضای عمومی Builderها را تغییر دهد.
- **حفظ reference در AST:** در مسیرهای Builder هدف، scalar reference در `IQueryConditionsAst.conditionSideRight` و هر occurrence collection در `IQueryConditionsCollectionAst.paramsCollection` قرار می‌گیرد. `QueryConditionsGroupsBuilder` و مسیر JOIN، nodeهای condition را به AST متصل می‌کنند؛ `QueryTableBuilder.table(blockQuery)` AST nested را به `derivedQuery` می‌سپارد و `params.addAll(nestedParams)` referenceهای `SqlParameter` را کپی نمی‌کند. `QueryRenderSelectBuilder.addInlineCteSource(...)` نیز بدنهٔ `cte.definition.ast` را به‌عنوان `derivedQuery` نگه می‌دارد و `params.addAll(...)` همان referenceها را منتقل می‌کند. مسیر composition CTE در `cteWithItem(...)` فرزندهای AST مانند `where`, `joins` و `table` را به‌صورت reference منتقل می‌کند. رشته‌های قدیمی/AST دستی reference ندارند و باید به‌عنوان مسیر untracked به fallback بروند.
- **ترتیب rendering:** `MySqlQueryCapability.render(...)` ترتیب `WITH → SELECT → FROM → JOIN → WHERE → GROUP → ORDER → LIMIT → OFFSET` را تولید می‌کند. رندرهای nested در `MySqlQueryTableCapability`، rendererهای JOIN، WHERE، گروه‌ها و WITH از `ctx.registry.render(...)` عبور می‌کنند؛ `RenderSessionRegistry` باید همان sidecar را در تمام این بازگشت‌ها نگه دارد. در نتیجه ترتیب sidecar از رندر واقعی می‌آید، نه ترتیب فراخوانی Builder. ثبت occurrence فقط وقتی مجاز است که placeholder متناظر در fragment نهایی SQL باقی بماند. Renderer شرط باید پیش از render کردن سمت راست پارامتر/collection، حالت حذف شرط را تشخیص دهد یا event fragment حذف‌شده را rollback کند؛ تطبیق count/name به‌تنهایی نباید occurrence یتیم را به placeholder خام دیگری نسبت دهد.
- **فقط مسیر پارامتردار SELECT:** در rendererهای داخلی SELECT، placeholderهای Builder از مسیر scalar و collection condition تولید می‌شوند؛ JOIN از renderer مشترک condition استفاده می‌کند. مسیر String در `MySqlQueryConditionCapability` و AST دستی reference ندارند؛ هر placeholder بدون binding متناظر باید render را به fallback legacy ببرد. اگر sidecar ناقص یا نامطمئن باشد، identity lowering نباید انجام شود.
- **Executor و dialect:** مسیر معمول `QueryConsumer.execute()` به `IQueryBuilderExecutor.get(...)` و `execute(...)` می‌رسد و `QueryBuilderExecutor.execute(IQueryRenderSelectApi, ...)` نقطهٔ lowering است. `QueryConsumer.sql()` و `IQueryBuilderExecutor.executeOut(...)` عمومی همچنان SQL منطقی و مسیر legacy را حفظ می‌کنند؛ بنابراین identity binding خارج از اجرای مستقیم SELECT با `QueryBuilderExecutor` تضمین نمی‌شود. `DialectSelector` فقط `MySqlDialect` و `MariaDbDialect` را انتخاب می‌کند و هر دو از `BaseSqlDialect`/rendererهای MySQL استفاده می‌کنند. dialect سفارشی در مسیر فعلی `QueryBuilderExecutor` قابل تزریق نیست؛ executor سفارشی بیرونی خارج از پوشش این Plan است، نه یک dialect داخلیِ جاافتاده.
- **زمان conflict همان scope:** تعارض در scope واحد هنگام Builder construction رد خواهد شد، زودتر از validation فعلی `BuiltQuery.getListParamNames()` در `IQueryExecute` که پیش از بازکردن اتصال اجرا می‌شود. این تغییر قابل‌مشاهده است. `BuiltQueryTest.acceptsEqualDuplicateParametersAndRejectsConflicts` قرارداد validation دستی را ثابت می‌کند، ولی تستی که زمان دقیق conflict در Builder را ممنوع کند در شواهد Repository نیست. Plan اجرایی باید زمان جدید را صریحاً تست کند؛ آن را حفظ کامل timing قبلی توصیف نکند.

### 11.7 مرز فازهای اجرا

مرز فازها برای جلوگیری از شکستن SQL موجود الزام‌آور است:

- **Phase 1** Builder/AST referenceها را همراه با حداقل پشتیبانی Renderer تغییر می‌دهد. scalar، collection و شرط‌های JOIN همچنان placeholderهای منطقی و SQL قبلی را تولید می‌کنند؛ sidecar فقط occurrenceهای باقی‌مانده در SQL را به‌ترتیب rendering نگه می‌دارد. condition حذف‌شده نباید occurrence یتیم ثبت کند. این فاز اجرای مستقل مقادیر هم‌نام در scopeهای جداگانه را پشتیبانی‌شده اعلام نمی‌کند، چون Executor هنوز نام‌های فیزیکی یکتا را اعمال نمی‌کند.
- **Phase 2** helper lowering را فقط به مسیر اجرای مستقیم SELECT در QueryBuilderExecutor وصل می‌کند؛ در این نقطه پشتیبانی binding مستقل همنام با تست JDBC قابل ارزیابی است.

این ترتیب فقط اجزای وابستهٔ Builder، AST، Renderer و sidecar را در یک فاز جمع می‌کند؛ ترتیب کارهای مستقل و مرز عدم تغییر CRUD، Migration و API عمومی باقی می‌ماند.

### 11.8 وضعیت

مسیر حداقلی، فایل‌های لازم و تست‌های پذیرش در Plan اجرایی مستقل مشخص شده‌اند. تصمیم طراحی برای این دامنه **Implementation Ready / Not Authorized** است. این وضعیت مجوز اجرا نیست؛ پیاده‌سازی همچنان به authorization جداگانه نیاز دارد.
