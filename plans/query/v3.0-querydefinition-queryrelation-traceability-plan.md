# 2. چشم‌انداز محوری

Vision مورد بررسی این است:

```text
Query Relation
      │
      ▼
Query Definition
      │
      ▼
SELECT Items
      │
      ├── Physical Field
      ├── Expression
      └── Relation Field
               │
               ▼
          .as(Output::field)
               │
               ▼
       Relation Output Field
               │
               ▼
          Output Model
               │
          ┌────┴─────┐
          ▼          ▼
       Execute    Compose
                    │
             ┌──────┼──────┐
             ▼      ▼      ▼
            CTE    FROM   JOIN
```

اصل مرکزی:

> هر چیزی که در `SELECT` قرار می‌گیرد باید بتواند با یک semantic مشترک به یک `Relation Output Field` تبدیل شود.

بنابراین این موارد باید از نظر semantic در یک مدل مشترک قابل بررسی باشند:

```kotlin
column(UserModelV2::id)
    .as(Output::id)

count(OrderModel::id)
    .as(Output::orderCount)

sum(OrderModel::amount)
    .as(Output::totalAmount)

case {
    ...
}.as(Output::ageGroup)

column(UserOrderStats.Output::orderCount)
    .multiply(10)
    .as(Output::score)
```

همه باید از نظر مفهومی در این مسیر قرار بگیرند:

```text
SELECT ITEM
    ↓
.as(Output::field)
    ↓
Relation Output Field
```

# 3. تمایزهای معنایی مهم

این سه مفهوم را از ابتدا جدا بررسی کن.

## 3.1 فیلد فیزیکی (Physical Field)

مثال:

```kotlin
UserModelV2::id
```

نمایندهٔ فیلدی است که در شِمای فیزیکی پایگاه داده وجود دارد.

مدل مفهومی:

```text
Table Model
    ↓
Physical Column
```

---

## 3.2 عبارت (Expression)

مثال:

```text
SUM(...)
COUNT(...)
CASE(...)
orderCount * 10
```

عبارت لزوماً فیلد فیزیکی پایگاه داده ندارد.

---

## 3.3 فیلد خروجی رابطه (Relation Output Field)

مثال:

```kotlin
UserOrderStats.Output::orderCount
```

نمایندهٔ فیلدی است که در شِمای منطقی خروجی یک Query Relation وجود دارد.

این field:

* ستون فیزیکی (Physical Column) نیست
* فقط یک رشته (String) نیست
* نگاشت ResultSet نیست
* باید بتوان در Query دیگری به آن ارجاع داد

---

# 4. اصل محوری

بررسی کن آیا معماری می‌تواند از این مدل پشتیبانی کند:

```text
Physical Field ─────┐
                    │
Expression ─────────┼──→ .as(Output::field)
                    │
Relation Field ─────┘
                         ↓
                 Relation Output Field
```

همچنین بررسی کن آیا `Relation Output Field` را می‌توان در Query دیگری به‌کار برد:

```text
Relation A.Output::field
        ↓
Query B
        ↓
WHERE / SELECT / JOIN / FROM
```

## سناریو ۱: خروجی مستقیم از جدول

مدل:

```kotlin
@QBTable(name = "user_users", alias = "uu")
class UserModelV2 : IModelBase {

    @QBColumn(name = "id", alias = "user_id")
    val id: Int = 0

    @QBColumn(name = "name", alias = "user_name")
    val name: String? = null

    @QBColumn(name = "age", alias = "user_age")
    val age: Int? = null
}
```

Query:

```kotlin
class ActiveUsers : IQueryRelation {

    data class Output(
        val id: Int,
        val name: String,
        val age: Int
    )

    override val query =
        query {
            select {
                column(UserModelV2::id)
                    .as(Output::id)

                column(UserModelV2::name)
                    .as(Output::name)

                column(UserModelV2::age)
                    .as(Output::age)
            }

            from(UserModelV2::class)

            where {
                column(UserModelV2::age) greaterThan 18
            }
        }
}
```

جریان معنایی مورد انتظار:

```text
UserModelV2::id
        ↓
Output::id

UserModelV2::name
        ↓
Output::name

UserModelV2::age
        ↓
Output::age
```

SQL مورد انتظار:

```sql
SELECT
    uu.id AS id,
    uu.name AS name,
    uu.age AS age
FROM user_users AS uu
WHERE uu.age > 18
```

ردیابی:

```text
Table Model
    ↓
Physical Column
    ↓
Output Field
    ↓
Output Model
```

# 7. سناریو ۳: عبارت تجمیعی

نمونه:

```kotlin
class UserOrderStats : IQueryRelation {

    data class Output(
        val userId: Int,
        val orderCount: Long,
        val totalAmount: Long
    )

    override val query =
        query {
            select {
                column(UserModelV2::id)
                    .as(Output::userId)

                count(OrderModel::id)
                    .as(Output::orderCount)

                sum(OrderModel::amount)
                    .as(Output::totalAmount)
            }

            from(OrderModel::class)

            groupBy {
                column(UserModelV2::id)
            }
        }
}
```

نگاشت معنایی مورد انتظار:

```text
COUNT(o.id)
    ↓
Output::orderCount

SUM(o.amount)
    ↓
Output::totalAmount
```

الزام اساسی:

`orderCount` و `totalAmount` ستون‌های فیزیکی پایگاه داده نیستند.

مشخص کن آیا معماری فعلی AST و عبارت‌ها می‌تواند این حالت را شفاف نمایش دهد.

# 8. سناریو ۴: CASE / فیلد مشتق‌شده

نمونه:

```kotlin
data class Output(
    val id: Int,
    val name: String,
    val ageGroup: String
)
```

Query:

```kotlin
select {
    column(UserModelV2::id)
        .as(Output::id)

    column(UserModelV2::name)
        .as(Output::name)

    case {
        whenCondition {
            column(UserModelV2::age) greaterThan 18
        }

        thenValue("adult")

        otherwiseValue("minor")
    }.as(Output::ageGroup)
}
```

SQL مورد انتظار:

```sql
SELECT
    uu.id AS id,
    uu.name AS name,
    CASE
        WHEN uu.age > 18 THEN 'adult'
        ELSE 'minor'
    END AS age_group
FROM user_users uu
```

مشخص کن آیا عبارت‌های دلخواه می‌توانند با همان معنای `.as(Output::field)` به Relation Output Field تبدیل شوند.

صرفاً برای CASE سامانهٔ نگاشت جداگانه‌ای معرفی نکن.

# 9. سناریو ۵: JOIN و مدل خروجی جدید

نمونه:

```kotlin
@QBTable(name = "user_phones", alias = "up")
class UserPhoneModelV2 : IModelBase {

    @QBColumn(name = "user_id")
    val userId: Int = 0

    @QBColumn(name = "phone")
    val phone: String? = null
}
```

مدل خروجی:

```kotlin
data class Output(
    val userId: Int,
    val name: String,
    val phone: String
)
```

Query:

```kotlin
class UsersWithPhone : IQueryRelation {

    data class Output(
        val userId: Int,
        val name: String,
        val phone: String
    )

    override val query =
        query {
            select {
                column(UserModelV2::id)
                    .as(Output::userId)

                column(UserModelV2::name)
                    .as(Output::name)

                column(UserPhoneModelV2::phone)
                    .as(Output::phone)
            }

            from(UserModelV2::class)

            join(UserPhoneModelV2::class) {
                UserModelV2::id eq UserPhoneModelV2::userId
            }
        }
}
```

مدل معنایی مورد انتظار:

```text
UserModelV2
      \
       \
        → UsersWithPhone.Output
       /
UserPhoneModelV2
```

مشخص کن آیا Output Model می‌تواند فیلدهای چند Database Model را از نظر معنایی ترکیب کند، بی‌آنکه به هیچ‌یک از مدل‌های فیزیکی وابسته شود.

# 10. سناریو ۶: استفادهٔ CTE از رابطه‌ای دیگر

رابطهٔ A:

```kotlin
class UserOrderStats : IQueryRelation {

    data class Output(
        val userId: Int,
        val orderCount: Long
    )

    override val query =
        query {
            select {
                column(UserModelV2::id)
                    .as(Output::userId)

                count(OrderModel::id)
                    .as(Output::orderCount)
            }

            from(OrderModel::class)

            join(UserModelV2::class) {
                OrderModel::userId eq UserModelV2::id
            }

            groupBy {
                column(UserModelV2::id)
            }
        }
}
```

رابطهٔ B:

```kotlin
class ImportantUsers : IQueryRelation {

    data class Output(
        val userId: Int,
        val orderCount: Long
    )

    override val query =
        query {
            with(UserOrderStats)

            select {
                column(UserOrderStats.Output::userId)
                    .as(Output::userId)

                column(UserOrderStats.Output::orderCount)
                    .as(Output::orderCount)
            }

            from(UserOrderStats)

            where {
                column(UserOrderStats.Output::orderCount) greaterThan 10
            }
        }
}
```

تمایز معنایی مورد انتظار:

```text
UserModelV2::id
        ↓
UserOrderStats.Output::userId
        ↓
ImportantUsers.Output::userId
```

الزام اساسی:

```kotlin
UserOrderStats.Output::userId
```

از نظر مفهومی باید چنین معنایی داشته باشد:

> فیلدی متعلق به رابطهٔ `UserOrderStats`

و نه:

* `UserModelV2::id`
* یک String خام
* فقط یک SQL alias
* نشانه‌ای برای نگاشت ResultSet

مشخص کن آیا معماری فعلی برای پشتیبانی از این حالت، هویت و context کافی دارد.

# 11. سناریو ۷: خروجی رابطه ← عبارت ← خروجی رابطهٔ جدید

نمونه:

```kotlin
class ImportantUsers : IQueryRelation {

    data class Output(
        val id: Int,
        val score: Long
    )

    override val query =
        query {
            with(UserOrderStats)

            select {
                column(UserOrderStats.Output::userId)
                    .as(Output::id)

                column(UserOrderStats.Output::orderCount)
                    .multiply(10)
                    .as(Output::score)
            }

            from(UserOrderStats)
        }
}
```

زنجیرهٔ معنایی مورد انتظار:

```text
UserModelV2::id
       ↓
UserOrderStats.Output::userId
       ↓
ImportantUsers.Output::id
```

و نیز:

```text
COUNT(order.id)
       ↓
UserOrderStats.Output::orderCount
       ↓
orderCount * 10
       ↓
ImportantUsers.Output::score
```

مشخص کن آیا عبارت‌ها می‌توانند Relation Output Fieldها را همان‌طور مصرف کنند که فیلدهای فیزیکی را مصرف می‌کنند.

# 12. سناریو ۸: ترکیب با جدول مشتق‌شده / زیرپرس‌وجو

معماری نباید این دو مفهوم را یکی بداند:

```text
Relation
```

یعنی Relation را هم‌معنای این مورد نگیرد:

```text

```

مدل مفهومی:

```text
UserOrderStats
      ↓
Query Relation
      ↓
┌───────────────┐
│ CTE           │
│ FROM          │
│ JOIN          │
│ Subquery      │
└───────────────┘
```

بنابراین مشخص کن آیا می‌توان از Query Relation به‌صورت مفهومی چنین استفاده کرد:

```text
FROM Relation
```

بدون آنکه Relation ناچار باشد همیشه به‌شکل CTE رندر شود.

تحلیل باید این دو را از هم جدا کند:

```text
Relation semantic identity
```

و آن را از روش جای‌گیری SQL متمایز کند، مانند:

```text
SQL placement strategy
```

برای نمونه:
برای نمونه:
* CTE
* جدول مشتق‌شده
* زیرپرس‌وجو
* منبع FROM
* منبع JOIN

هیچ‌یک از این موارد را پیاده‌سازی نکن.

# 18. هویت Relation

مشخص کن Relation به چه نوع هویتی نیاز دارد.

حداقل بررسی کن آیا معماری باید این دو را از هم تشخیص دهد:

```text
Relation A
Relation B
```

حتی اگر فیلدهای خروجی یکسانی داشته باشند.

برای نمونه:

```text
UserOrderStats.Output::userId
```

نباید به‌اشتباه معادل این مورد تلقی شود:

```text
SomeOtherRelation.Output::userId
```

فقط به این دلیل که نام هر دو property در Kotlin برابر `userId` است.

مشخص کن هویت Relation باید بر کدام مبنا باشد:

* هویت object
* هویت class
* هویت صریح query
* مفهوم دیگری که از قبل در repository وجود دارد

خودسرانه تصمیم نگیر.

به شواهد repository تکیه کن.
