# Plan 10.3 — یکپارچه‌سازی Metadata مدل و Query

## وضعیت

**آماده برای بازبینی پیاده‌سازی**

## ۱. هدف

پشتیبانی از metadata مدل و Query را تکمیل کن، در حالی که معماری فعلی QueryBuilder و رفتار خروجی‌های تایپ‌شده حفظ می‌شوند.

هدف‌های اولیهٔ تغییر نام Relation به Query و پشتیبانی از استفادهٔ Query به‌عنوان CTE برای این Plan انجام‌شده محسوب می‌شوند. APIهای فعلی `QueryRelation` برای سازگاری بدون تغییر می‌مانند.

این Plan فقط کار باقی‌ماندهٔ metadata را پوشش می‌دهد.

## ۲. تغییرات لازم

### ۲.۱. Annotationهای core

در ماژول `:data_base:core`:

- `QBQuery` را برای تعریف هویت Query و alias پیش‌فرض آن اضافه کن.
- `QBQuerySelect` را برای تعریف metadata خروجی Query اضافه کن.
- `QB_METADATA_UNSET` را برای فیلدهای String مربوط به `QBTable`، `QBColumn`، `QBQuery` و `QBQuerySelect` به‌عنوان مقدار پیش‌فرض annotation به‌کار ببر تا مقدار تنظیم‌نشده از رشتهٔ خالی صریح قابل تشخیص باشد.
- در فیلدهایی که Model یا Query هر دو منبع متناظر دارند، از اصل یکسان resolution استفاده کن: مقدار پیش‌فرض قراردادی → override در annotation → override صریح DSL یا occurrence. رفتار فعلی هر فیلد Model حفظ می‌شود، جز fallbackهای مقدار تنظیم‌نشده که صریحاً در بند ۲.۵.۱ تعریف شده‌اند. رشتهٔ خالی صریح و semantics فعلی هر مصرف‌کننده مطابق همان بند حفظ شود.

### ۲.۲. Resolution مربوط به metadata

در ماژول `:data_base:query:builder`:

- سازوکار داخلی مشترک resolution مربوط به metadata را در مصرف‌کننده‌های فعلی Model به‌کار ببر:
  - `QueryTableBuilder`
  - `QueryColumnsBuilder`
  - `QueryColumnsBaseBuilder`
  - `QueryColumnInsertBuilder`
  - `QueryColumnUpdateBuilder`
- resolution مربوط به Query را به مسیرهای فعلی `QueryDeclaration` و `QueryRelationBuilder` اعمال کن.
- تقدم‌های تعریف‌شده در قرارداد تأییدشدهٔ metadata را حفظ کن.
- overrideهای صریح DSL و الزامات سازگاری موجود را حفظ کن.

مگر اینکه API فعلی نتواند این الزامات را برآورده کند، abstraction عمومی تازه‌ای معرفی نکن.

### ۲.۳. Metadata خروجی Query

سازوکار فعلی خروجی تایپ‌شده را حفظ کن:

- `property.name` هویت Property در Kotlin باقی می‌ماند.
- `QBQuerySelect.name` نام منطقی خروجی را مشخص می‌کند.
- `QBQuerySelect.alias` alias خروجی منتشرشده در SQL را مشخص می‌کند.
- `alias(KProperty)` و `relationColumn(KProperty)` باید از مقادیر مؤثر metadata طبق این Plan استفاده کنند.
- `QueryRow.getValue(KProperty)` باید همچنان از سازوکار فعلی PropertyReference و SQL alias برای resolve کردن مقدار استفاده کند.

هنگام resolve کردن metadata، getter خروجی‌های Query را اجرا نکن.

### ۲.۴. اعتبارسنجی نام منطقی

اعتبارسنجی فعلی یکتایی SQL alias را حفظ کن.

یکتایی نام منطقی را فقط برای خروجی‌های تایپ‌شدهٔ Query جاری که به قرارداد خروجی همان Query تعلق دارند بررسی کن. از رابطهٔ فعلی Property تایپ‌شده با `declarationOwner` استفاده کن؛ عضویت را با بررسی مالک تعریف Property در JVM یا Kotlin تعیین نکن.

Propertyهای موروثی که به‌درستی از طریق نوع Query ارجاع داده شده‌اند، صرفاً به‌دلیل موروثی‌بودن نباید کنار گذاشته شوند.

Propertyهای Model که به‌عنوان ستون منبع انتخاب شده‌اند نباید با Propertyهای خروجی Query اشتباه گرفته شوند.

این اعتبارسنجی را پس از ساخته‌شدن declaration مربوط به SELECT و پیش از ایجاد `BuiltQueryDefinition` انجام بده.

### ۲.۵. تقدم یکپارچهٔ نام‌گذاری

قواعد تقدم این بخش مرجع نهایی resolution برای هر فیلد metadata هستند. هر قاعده فقط برای همان فیلد و همان سطح اعمال می‌شود. ترتیب تقدم میان نام کلاس، alias کلاس، نام Property، نام منطقی، نام ستون منبع و SQL alias قابل تعمیم نیست. رفتار فعلی Model و قرارداد جدید Query باید مستقل از یکدیگر و مطابق جدول‌های همین بخش پیاده‌سازی شوند. اگر توضیحات عمومی بخش‌های پیشین با این قواعد تعارض داشت، قواعد اختصاصی همین بخش ملاک هستند.

هر فیلد metadata را مستقل از فیلدهای دیگر resolve کن. نام، alias، نام ستون منبع و نوع استخراج مقادیر جداگانه‌اند؛ تنظیم یکی نباید به‌طور ضمنی مقدار دیگری را تغییر دهد. قواعد زیر رفتار فعلی Model را از قرارداد جدید Query جدا می‌کنند تا fallback آینده به‌عنوان رفتار موجود معرفی نشود.

#### Metadata سطح کلاس

| نقش | رفتار فعلی Model (`QBTable`) | قرارداد Query در این Plan | تقدم و fallback |
|---|---|---|---|
| نام فیزیکی Table در Model | `QueryTableBuilder.table(KClass)` در source فعلی وجود `@QBTable` و مقدار غیرخالی `QBTable.name` را لازم می‌داند. در حال حاضر fallback از نام کلاس وجود ندارد. `table(String)` مسیر صریح جداگانه‌ای است. | طبق بند ۲.۵.۱، مقدار پیش‌فرض از نام کلاس ساخته و سپس `QBTable.name` صریح اعمال می‌شود. | قرارداد هدف Model در بند ۲.۵.۱ مقدار تنظیم‌نشده را از نام کلاس می‌سازد و مقدار annotation را پس از آن اعمال می‌کند؛ این fallback نسبت به source فعلی تغییر رفتار است. رشتهٔ خالی صریح همچنان خطاست. |
| نام منطقی تعریف Query | در Query فعلی چنین metadataای وجود ندارد؛ `QBQuery` هنوز در source نیست. | قرارداد نام کلاس مقدار پیش‌فرض است؛ مقدار صریح `QBQuery.name` آن را override می‌کند. این مقدار metadata تعریف Query باقی می‌ماند و به‌تنهایی نام runtime Relation را تعیین نمی‌کند. | نام پیش‌فرض کلاس → `QBQuery.name`. این مقدار از `QueryRelation.name` و نام CTE/Relation در زمان استفاده مستقل است. |
| نام عملیاتی Relation مربوط به Query | `QueryDeclaration.relationName` در کلاس پایه abstract است؛ override زیرکلاس از طریق helper به factory می‌رسد. در دو factory عمومی، پارامتر `name` نام نهایی runtime `QueryRelation` است. | همان قرارداد و مسیر فعلی حفظ می‌شود. نام عملیاتی Relation از `QueryDeclaration.relationName` و مسیر ساخت Relation می‌آید؛ `QBQuery.name` خودکار جایگزین آن نمی‌شود. | override صریح `relationName` → ورودی factory بدون resolve مجدد. این ترتیب دربارهٔ metadata منطقی `QBQuery.name` نیست و آن را تغییر نمی‌دهد. |
| alias پیش‌فرض منبع یا qualifier مربوط به occurrence | برای `from(relation, alias)`, source فعلی از alias صریح استفاده می‌کند؛ در نبود آن `relation.name` را به‌کار می‌برد. | در Query دارای metadata، قرارداد نام کلاس alias پیش‌فرض است؛ `QBQuery.alias` آن را override می‌کند و `from(query, alias)` صریح برای همان occurrence بر هر دو تقدم دارد. اگر metadata مالک Query موجود نباشد، fallback فعلی `relation.name` حفظ می‌شود. | alias تعریف Query از نام Relation عملیاتی جداست. alias صریح occurrence فقط qualifier همان occurrence را تغییر می‌دهد و نام Relation یا `QBQuery.alias` را بازنویسی نمی‌کند. |

نام منطقی Query و نام عملیاتی Relation دو فیلد مستقل‌اند. نام منطقی Query از قرارداد نام کلاس آغاز می‌شود و `QBQuery.name` آن را override می‌کند؛ این مقدار در metadata تعریف Query حفظ می‌شود. قرارداد نام کلاس، نام سادهٔ کلاس را به `snake_case` تبدیل می‌کند و فقط یک پسوند پایانی دقیق `Query` را پیش از تبدیل حذف می‌کند. در مقابل، نام عملیاتی Relation از قرارداد فعلی `QueryDeclaration.relationName` و مسیر ساخت Relation به دست می‌آید. در هر دو factory عمومی `queryRelation(name, ...)`، مقدار `name` که فراخواننده می‌دهد نام نهایی runtime Relation است؛ factory آن را با `QBQuery.name` یا convention بازنویسی نمی‌کند. استفاده از Query به‌عنوان CTE نیز نام Relation عملیاتی را به‌کار می‌برد، نه نام منطقی annotation را. این Plan رفتار `QueryDeclaration.relationName`، APIهای `QueryRelation` و factoryهای موجود را تغییر نمی‌دهد.

#### مقدار تنظیم‌نشده و مقدار خالی صریح

Annotationهای فعلی Model مقدار پیش‌فرض `String = ""` دارند. بنابراین reflection در حال حاضر نمی‌تواند آرگومان حذف‌شدهٔ annotation را از مقدار خالیِ صریح تشخیص دهد. مصرف‌کننده‌های موجود بسته به هر فیلد این مقدار را چنین تفسیر می‌کنند:

| فیلد | رفتار فعلی Model | قرارداد این Plan برای مقدار تنظیم‌نشده و مقدار خالی صریح |
|---|---|---|
| `QBTable.name` | مقدار خالی در resolution جدول typed رد می‌شود. مقدار حذف‌شده و خالی صریح اکنون قابل تفکیک نیستند. | پس از تغییر پیش‌فرض annotation به sentinel، مقدار تنظیم‌نشده از قرارداد نام کلاس ساخته می‌شود؛ مقدار خالی صریح همچنان خطاست. الزام فعلی وجود خود `@QBTable` در این Plan حذف نمی‌شود. |
| `QBTable.alias` | مقدار خالی یعنی بدون alias؛ مقدار حذف‌شده و خالی صریح اکنون قابل تفکیک نیستند. alias تنظیم‌شده در DSL بر annotation تقدم دارد و `alias("")` یعنی بدون alias. | مقدار تنظیم‌نشده از قرارداد نام کلاس ساخته می‌شود؛ مقدار خالی صریح همچنان یعنی بدون alias. alias صریح DSL بر هر دو تقدم دارد. تفاوت این قرارداد با رفتار فعلیِ مقدار پیش‌فرض یک تغییر رفتاری مجازشده در این Plan است؛ تفاوت alias Query نیز در جدول بالا آمده است. |
| `QBColumn.name` | مقدار خالی در مسیرهای typed مربوط به SELECT/base-column/INSERT/UPDATE رد می‌شود. مقدار حذف‌شده و خالی صریح اکنون قابل تفکیک نیستند. | پس از تغییر پیش‌فرض annotation به sentinel، مقدار تنظیم‌نشده از `property.name` ساخته می‌شود؛ مقدار خالی صریح همچنان خطاست. الزام فعلی وجود خود `@QBColumn` در این Plan حذف نمی‌شود. این مقدار نام ستون منبع است، نه نام منطقی خروجی. |
| `QBColumn.alias` | در SELECT typed، مقدار خالی به `property.name` fallback می‌شود. مقدار حذف‌شده و خالی صریح اکنون قابل تفکیک نیستند. INSERT alias را نادیده می‌گیرد و UPDATE از این فیلد استفاده نمی‌کند. | مقدار تنظیم‌نشده و مقدار خالی صریح در SELECT هر دو به `property.name` resolve می‌شوند تا رفتار فعلی مقدار خالی حفظ شود. `alias("")` صریح DSL همچنان SQL alias را پاک می‌کند. این فیلد را به semantics مربوط به INSERT/UPDATE تعمیم نده. |
| `QBQuery.name` / `QBQuerySelect.name` | این annotationها هنوز در source وجود ندارند. | مقدار تنظیم‌نشده از قرارداد نام کلاس/Property استفاده کند؛ مقدار خالی صریح هنگام مصرف metadata خطای اعتبارسنجی باشد. برای `QBQuery.name` از قاعدهٔ نام کلاس و برای `QBQuerySelect.name` از `snake_case(property.name)` استفاده شود. |
| `QBQuery.alias` / `QBQuerySelect.alias` | این annotationها هنوز در source وجود ندارند. | مقدار تنظیم‌نشده از قرارداد نام کلاس/Property استفاده کند؛ مقدار خالی صریح هنگام انتخاب به‌عنوان alias occurrence یا alias خروجی منتشرشده نامعتبر باشد. مقدار تنظیم‌نشدهٔ `QBQuery.alias` از قرارداد نام کلاس و مقدار تنظیم‌نشدهٔ `QBQuerySelect.alias` از `snake_case(property.name)` استفاده می‌کند. `from(..., alias)` و `alias(String)` صریح DSL همچنان تقدم دارند؛ اگر `alias("")` یک alias خروجی الزامی را پاک کند، اعتبارسنجی SQL alias موجود نتیجه را تعیین می‌کند. |

#### ۲.۵.۱. Resolve مرحله‌ای Metadata در Model

Metadata در Model به‌ترتیب زیر ساخته و override می‌شود: ابتدا defaultهای قراردادی، سپس مقادیر صریح annotation، و در نهایت تنظیم صریح DSL در زمان ساخت Query. هر مرحله فقط فیلد متناظر خود را تغییر می‌دهد. defaultهای این بند، قرارداد هدف Plan هستند و از رفتار فعلی source متمایزند.

**سطح کلاس:**

برای `UserModel`, قرارداد نام پیش‌فرض کلاس پس از تبدیل `UserModel` به `user` چنین است:

~~~text
tableName  = user
tableAlias = user
~~~

سپس مقادیر تنظیم‌شدهٔ `QBTable` مستقل اعمال می‌شوند:

~~~kotlin
@QBTable(name = "user_users", alias = "uu")
class UserModel : IModelBase
~~~

نتیجه پس از annotation:

~~~text
tableName  = user_users
tableAlias = uu
~~~

در صورت تنظیم DSL:

~~~kotlin
table {
    table(UserModel::class)
    alias("uu1")
}
~~~

نتیجه نهایی:

~~~text
tableName  = user_users
tableAlias = uu1
~~~

`alias("uu1")` فقط alias جدول را تغییر می‌دهد و `tableName` را تغییر نمی‌دهد. API فعلی `table(KClass)` برای `tableName` override مستقیمی از DSL ندارد؛ مسیر `table(String)` یک API جدا برای منبع String است و override annotation در همان مسیر محسوب نمی‌شود.

| فیلد | ترتیب تقدم نهایی |
|---|---|
| `tableName` | قرارداد نام کلاس → `QBTable.name` |
| `tableAlias` | alias قراردادی کلاس → `QBTable.alias` → `alias(String)` صریح DSL |

برای حفظ سازگاری، خود annotation `QBTable` همچنان لازم است؛ این Plan الزام وجود annotation را حذف نمی‌کند. مقدارهای پیش‌فرض String در `QBTable` و `QBColumn` با sentinel مشخص می‌شوند تا فیلد تنظیم‌نشده از خالی صریح جدا باشد. نام کلاس `UserModel` به `user` تبدیل می‌شود؛ قاعدهٔ نام کلاس باید با قرارداد نام‌گذاری کلاس در بخش ۲.۵ سازگار باشد. `QBColumn` نیز در مسیرهای typed همچنان لازم است؛ این Plan فقط مقدار تنظیم‌نشدهٔ فیلدهای آن را resolve می‌کند.

**سطح Property:**

پس از resolve شدن Table، برای Property `id: Int` مقادیر اولیه چنین‌اند:

~~~text
tableName      = user_users
tableAlias     = uu1
-------------------------
columnName     = id
columnAlias    = id
columnDataType = INT
~~~

مقادیر پیش‌فرض Property عبارت‌اند از `property.name` برای نام ستون منبع و alias خروجی؛ نوع استخراج نیز از نوع Property استنتاج می‌شود. سپس annotation اعمال می‌شود:

~~~kotlin
@QBColumn(name = "user_id", alias = "user_id", primaryKey = true)
val id: Int = 0
~~~

پس از annotation:

~~~text
tableName      = user_users
tableAlias     = uu1
-------------------------
columnName     = user_id
columnAlias    = user_id
columnDataType = INT
primaryKey     = true
~~~

`QBColumn.name` فقط نام ستون منبع را override می‌کند؛ `QBColumn.alias` فقط alias پیش‌فرض خروجی را override می‌کند؛ `primaryKey` مستقل باقی می‌ماند.

در مرحلهٔ DSL:

~~~kotlin
addColumn {
    column(UserModel::class, UserModel::id)
    alias("user_id_out")
    execute(DataType.LONG)
}
~~~

مقادیر مؤثر برای همین SELECT item:

~~~text
tableName      = user_users
tableAlias     = uu1
-------------------------
columnName     = user_id
columnAlias    = user_id_out
columnDataType = LONG
~~~

`alias("user_id_out")` فقط SQL alias خروجی را تغییر می‌دهد؛ ستون منبع `user_id` باقی می‌ماند. `execute(DataType.LONG)` نوع استخراج همین خروجی Query را تعیین می‌کند و نوع Property یا Metadata تعریف Model را تغییر نمی‌دهد؛ Property همچنان `Int` است و metadata آن همچنان بر اساس نوع خود Property resolve می‌شود. `primaryKey = true` نیز با تغییر نام، alias یا نوع استخراج تغییر نمی‌کند.

| فیلد | ترتیب تقدم نهایی |
|---|---|
| `columnName` | `property.name` → `QBColumn.name` |
| `columnAlias` | alias پیش‌فرض Property (`property.name`) → `QBColumn.alias` → alias صریح DSL |
| `columnDataType` برای SELECT item | نوع استنتاج‌شده از Property → `execute(DataType)` صریح |
| `primaryKey` | مقدار پیش‌فرض annotation → `QBColumn.primaryKey`؛ بدون اثر از alias یا تنظیم نوع خروجی |

این قواعد مرحله‌ای برای Model هستند. آن‌ها تقدم Query یا metadata خروجی Query را تغییر نمی‌دهند؛ قواعد Query در جدول‌های همین بخش مستقل تعریف شده‌اند.

پیش‌فرض‌ها را برای هر فیلد جداگانه اعمال کن، نه برای کل annotation. alias تنظیم‌شده نباید name را پر یا تغییر دهد و name تنظیم‌شده نباید alias را پر یا تغییر دهد. مصرف‌کننده‌های فعلی Model نیز همهٔ فیلدهای یکسانی را نمی‌خوانند: به‌طور مشخص `QBColumn.alias` metadata خروجی SELECT است، در حالی که INSERT از `QBColumn.name` استفاده می‌کند و UPDATE در حال حاضر qualifier/tag را از `QBTable.alias` و `QBColumn.name` می‌سازد.

#### رفتار فعلی و رفتار برنامه‌ریزی‌شدهٔ Query

- `QBTable` و `QBColumn` در source فعلی sentinel ندارند؛ رشتهٔ خالی annotation حذف‌شده را از رشتهٔ خالی صریح متمایز نمی‌کند. در source فعلی فیلدهای نام فیزیکی اجباری‌اند و fallback قراردادی ندارند. بند ۲.۵.۱ fallback برای مقدار تنظیم‌نشده را به‌عنوان تغییر رفتار مجازشده تعریف می‌کند؛ مقدار خالی صریح برای name همچنان خطاست. مقدار خالی `QBTable.alias` یعنی بدون alias و مقدار خالی `QBColumn.alias` در SELECT به `property.name` fallback می‌شود.
- SELECT مدل در حال حاضر ابتدا از `QBColumn.alias` غیرخالی و سپس از `property.name` استفاده می‌کند؛ alias صریح DSL بالاترین تقدم را دارد. نام ستون منبع Model همچنان از `QBColumn.name` می‌آید و `tableColumn(...)` از alias جدولی می‌گیرد که caller صریحاً داده است.
- Annotationهای Query در این Plan جدیدند؛ بنابراین defaultها و تقدم‌های آن‌ها قرارداد افزوده‌شده‌اند، نه ادعایی دربارهٔ رفتار runtime فعلی. این قراردادها باید استقلال فیلدها را رعایت کنند و در عین حال رفتار نام/factory Query و alias مربوط به occurrence را حفظ کنند.
- هویت Property (`KProperty`)، نام منطقی، SQL alias منتشرشده، ستون فیزیکی منبع و `DataType` استخراج باید در مسیر Model و Query مستقل بمانند. برای lookup metadata، getter خروجی Query اجرا نشود.

#### شواهد Repository و مرز سازگاری

رفتار فعلی بالا بر اساس این پیاده‌سازی‌هاست:

- `data_base/core/src/main/kotlin/annotations/models/AnnotationModelTable.kt` و `AnnotationModelColumn.kt`: مقدار پیش‌فرض فعلی `QBTable.name/alias` و `QBColumn.name/alias` برابر `""` است؛ sentinel وجود ندارد.
- `data_base/query/builder/src/main/kotlin/ast/select_builder/table/QueryTableBuilder.kt`: جست‌وجوی جدول typed نام غیرخالی `QBTable.name` را لازم می‌داند؛ alias مؤثر برابر alias صریح `alias(...)` یا در غیر این صورت `QBTable.alias` است؛ رشتهٔ خالی نمایش فعلیِ بدون alias است.
- `data_base/query/builder/src/main/kotlin/ast/select_builder/column/QueryColumnsBuilder.kt`: SELECT typed مدل `QBColumn.name` غیرخالی را لازم می‌داند؛ ابتدا `QBColumn.alias` غیرخالی و سپس `property.name` را به‌کار می‌برد و alias DSL پس از آن اعمال می‌شود. `ExecutionType` جداگانه از نوع بازگشتی Property استنتاج می‌شود یا با `execute(DataType)` تعیین می‌شود.
- `data_base/query/builder/src/main/kotlin/ast/select_builder/column_base/QueryColumnsBaseBuilder.kt`، `data_base/query/builder/src/main/kotlin/ast/insert_builder/column_insert/QueryColumnInsertBuilder.kt` و `data_base/query/builder/src/main/kotlin/ast/update_builder/column_update/QueryColumnUpdateBuilder.kt`: نام ستون‌های typed منبع/INSERT/UPDATE از `QBColumn.name` می‌آید؛ qualifier مؤثر جدول در UPDATE از آرگومان صریح یا `QBTable.alias` می‌آید. این مسیرها semantics مربوط به alias خروجی SELECT را مشترک ندارند.
- `data_base/query/builder/src/main/kotlin/ast/select_builder/ModelTableAliasContext.kt`: alias مؤثر صریح Model به ستون‌های منبع typed آن SELECT منتقل می‌شود؛ این کار نام ستون فیزیکی، alias خروجی SELECT یا نوع استخراج را تغییر نمی‌دهد.
- `data_base/query/builder/src/main/kotlin/relations/QueryDeclaration.kt`، `data_base/query/builder/src/main/kotlin/relations/QueryRelationBuilder.kt` و `data_base/query/builder/src/main/kotlin/ast/select_builder/QuerySourceContext.kt`: `QueryDeclaration.relationName` اکنون abstract است؛ دو factory از نوع `queryRelation(name, ...)` نام ورودی را نهایی می‌گیرند؛ alias مربوط به occurrence Query در `from`/`QuerySourceContext` resolve می‌شود؛ runtime نام definition و declaration owner را نگه می‌دارد. `QBQuery` و `QBQuerySelect` در source فعلی وجود ندارند؛ قواعد آن‌ها در این سند قرارداد برنامه‌ریزی‌شده‌اند، نه رفتار فعلی پیاده‌سازی.

قاعدهٔ سازگاری: بند ۲.۵.۱ صریحاً مقدار پیش‌فرض قراردادی برای نام Table، alias جدول و نام ستون منبع Model تعریف می‌کند. این fallbackها برای مقادیر annotation تنظیم‌نشده، تغییر رفتار مجازشدهٔ این Plan نسبت به source فعلی هستند و باید با تست رگرسیون پوشش داده شوند. رفتار رشتهٔ خالی صریح و تفاوت semantics alias هر عملیات طبق جدول‌ها حفظ می‌شود. defaultها و sentinelهای Query نیز قابلیت‌های افزوده‌شدهٔ این Plan هستند. امضاهای API عمومی موجود تغییر نمی‌کنند.

نام منطقی Query در `QBQuery.name` جایگزین `QueryDeclaration.relationName` نیست؛ بنابراین این Plan نیازی به تغییر abstract بودن `relationName` یا رفتار زیرکلاس‌های آن ندارد. زیرکلاس همچنان نام عملیاتی Relation را طبق قرارداد فعلی فراهم می‌کند و factory همچنان نام ورودی خود را نهایی می‌گیرد. قرارداد مستقیم `IQueryRelation` و امضاهای هر دو factory بدون تغییر می‌مانند.

#### ۲.۵.۲. Resolve مرحله‌ای Metadata در Query

Metadata Query نیز به‌صورت مرحله‌ای resolve می‌شود، اما هر مقدار فقط در قرارداد خودش اثر دارد. `QBQuery.name` نام منطقی تعریف Query است؛ `QueryDeclaration.relationName` نام عملیاتی runtime Relation است؛ و alias occurrence نام منبع در همان استفاده از Query است. این سه مقدار قابل جایگزینی با یکدیگر نیستند.

**سطح کلاس Query:**

برای کلاس `UserDisplayQuery`، مقدار پیش‌فرض نام منطقی با حذف پسوند پایانی دقیق `Query` و تبدیل باقی‌مانده به `snake_case` ساخته می‌شود:

~~~text
class convention = user_display
logicalQueryName = user_display
defaultQueryAlias = user_display
~~~

Annotation می‌تواند نام منطقی و alias پیش‌فرض را مستقل از هم override کند:

~~~kotlin
@QBQuery(name = "v3_user_display", alias = "uud")
class UserDisplayQuery : QueryDeclaration<Params>()
~~~

پس از resolution:

~~~text
logicalQueryName = v3_user_display
defaultQueryAlias = uud
~~~

`logicalQueryName` در metadata تعریف Query باقی می‌ماند. این مقدار به‌تنهایی نام runtime `QueryRelation`، نام CTE یا `QueryDeclaration.relationName` را تغییر نمی‌دهد. اگر زیرکلاس `relationName` را override کند، مقدار آن طبق مسیر فعلی به factory داده می‌شود؛ اگر factory با نام صریح فراخوانی شود، همان نام صریح نام نهایی runtime Relation است و پس از ورود به factory دوباره از روی `QBQuery.name` یا convention resolve نمی‌شود.

هنگام استفاده از Query به‌عنوان source، `from(query, alias)` صریح فقط alias همان occurrence را تعیین می‌کند و از alias annotation تقدم دارد. در نبود alias صریح، از `QBQuery.alias` مؤثر به‌عنوان alias پیش‌فرض Query استفاده می‌شود، مشروط به اینکه metadata مالک Query در مسیر موجود قابل دسترسی باشد؛ اگر metadata قابل بازیابی نباشد، fallback فعلی `relation.name` حفظ می‌شود. alias occurrence نه `logicalQueryName` را تغییر می‌دهد و نه نام runtime Relation را بازنویسی می‌کند.

| فیلد Query | ترتیب resolution |
|---|---|
| نام منطقی تعریف Query | convention کلاس → `QBQuery.name` صریح |
| `QueryDeclaration.relationName` / نام عملیاتی Relation | override صریح زیرکلاس و مسیر فعلی declaration → مقدار صریح ورودی factory به‌عنوان نام نهایی runtime Relation؛ `QBQuery.name` در این resolution وارد نمی‌شود |
| alias پیش‌فرض Query | convention کلاس → `QBQuery.alias` صریح |
| alias یک occurrence در `from` | alias پیش‌فرض Query مؤثر → alias صریح `from(query, alias)`؛ بدون metadata مالک Query، fallback فعلی `relation.name` حفظ می‌شود |

**سطح Property خروجی Query:**

`property.name` هویت فنی عضو Kotlin است. `QBQuerySelect.name` نام منطقی خروجی است و در صورت تنظیم‌نشدن از `snake_case(property.name)` ساخته می‌شود. `QBQuerySelect.alias` نام پیش‌فرضی است که آن خروجی با آن در SELECT منتشر می‌شود؛ در صورت تنظیم‌نشدن، آن هم از `snake_case(property.name)` ساخته می‌شود. این metadata بدون اجرای getter از reference و annotation خوانده می‌شود.

~~~kotlin
@QBQuerySelect(name = "user_name", alias = "user_name")
val fullName: String?
    get() = error("Typed output property must not be read")
~~~

مقادیر پایه و مقادیر پس از annotation چنین‌اند:

~~~text
مرحلهٔ default:
propertyIdentity = fullName
logicalOutputName = full_name
publishedSqlAlias = full_name
inferredExecutionType = STRING

پس از QBQuerySelect:
propertyIdentity = fullName
logicalOutputName = user_name
publishedSqlAlias = user_name
inferredExecutionType = STRING
~~~

در این قرارداد، `logicalOutputName` همان مفهوم منطقی مستقل است؛ آن را با نام ستون فیزیکی منبع یا عبارت SELECT یکی نکن. مقدار `QBQuerySelect.name` به‌تنهایی عبارت/ستون منبع را بازنویسی نمی‌کند، SQL alias منتشرشده را تعیین نمی‌کند، کلید `QueryRow` نمی‌شود و مبنای `relationColumn(...)` نیست. بنابراین metadata منطقی می‌تواند برای اعتبارسنجی/هویت قراردادی خروجی استفاده شود، در حالی که SQL alias و PropertyReference مسیر فعلی دسترسی به خروجی را حفظ می‌کنند.

Overrideهای DSL فقط فیلد مربوط به خود را تغییر می‌دهند:

~~~kotlin
addColumn {
    // عبارت/ستون منبع را DSL به‌صورت مستقل تعیین می‌کند.
    alias("name")
    execute(DataType.LONG)
}
~~~

در این مثال `alias("name")` فقط `publishedSqlAlias` را برای همین SELECT item به `name` تغییر می‌دهد؛ `logicalOutputName` همچنان `user_name` می‌ماند. `execute(DataType.LONG)` فقط نوع استخراج همین خروجی را به `LONG` تغییر می‌دهد؛ نوع Kotlin Property همچنان `String?` و metadata annotation آن بدون تغییر است. سازگاری معنایی/نوعی میان نوع Property و نوع استخراج، تصمیم مستقلی است و این مثال به‌تنهایی الزام validation جدیدی ایجاد نمی‌کند.

مسیرهای Propertyمحور باید همین تفکیک را رعایت کنند:

- `alias(Query::property)` همان PropertyReference را حفظ می‌کند و alias مؤثر خروجی SQL را به‌کار می‌برد.
- `relationColumn(Query::property, qualifier?)` PropertyReference را به output متناظر resolve می‌کند و از SQL alias منتشرشده برای reference تایپ‌شده استفاده می‌کند؛ qualifier طبق قرارداد source/occurrence موجود resolve می‌شود.
- `relationColumn(QueryRelation, String)` ورودی String را به‌عنوان نام منتشرشدهٔ SQL output نگه می‌دارد و به `QBQuerySelect.name` تعبیر نمی‌کند.
- `QueryRow.getValue(KProperty)` همچنان از mapping موجود PropertyReference به SQL alias منتشرشده استفاده می‌کند؛ logical name کلید دسترسی QueryRow نیست.
- getter Property برای کشف نام، alias، نوع یا هویت اجرا نمی‌شود.

| فیلد خروجی Query | ترتیب resolution |
|---|---|
| هویت فنی Property | reference صریح `KProperty`; بدون rename metadata |
| نام منطقی خروجی | `snake_case(property.name)` → `QBQuerySelect.name` صریح؛ فقط قرارداد منطقی/اعتبارسنجی |
| SQL alias منتشرشده | `snake_case(property.name)` → `QBQuerySelect.alias` صریح → alias صریح DSL؛ این مقدار برای mapping فعلی QueryRow و reference خروجی به‌کار می‌رود |
| عبارت یا ستون منبع | فقط declaration صریح expression/column در DSL؛ از `QBQuerySelect.name` یا alias استنتاج نمی‌شود |
| نوع استخراج | نوع استنتاج‌شده از Property → `execute(DataType)` صریح؛ مستقل از نام و alias |

در نتیجه، نمونهٔ `name = "user_name"` و `alias = "user_name"` فقط یک انتخاب هم‌نام برای دو فیلد مستقل است. تغییر یکی نباید دیگری را تغییر دهد. اگر `QBQuerySelect.name` خالی صریح باشد، طبق جدول مقدارهای خالی خطای validation است؛ اگر تنظیم‌نشده باشد، fallback منطقی `snake_case(property.name)` اعمال می‌شود.

## ۳. سازگاری

رفتار موجود را حفظ کن، مگر اینکه قرارداد metadata صریحاً تغییر آن را لازم بداند.

اگر Query موجود به نام یا alias مشخص SQL وابسته است، در صورت نیاز metadata آن را طوری تنظیم کن که رفتار فعلی حفظ شود.

در چارچوب این Plan، AST، Executor، `QueryRow`، materialization یا امضاهای API عمومی را تغییر نده.

فرض نکن Executor باید تعریف Model یا Query را دوباره بخواند. ورودی فعلی آن همان Query ساخته‌شده و metadataای است که از قبل در pipeline اجرا حمل می‌شود.

## ۴. خارج از محدوده

این Plan شامل موارد زیر نیست:

- بازطراحی Executor یا AST.
- ایجاد مدل تازه برای خروجی Query یا سازوکار تازهٔ Property reference.
- بررسی reflection یا Kotlin metadata برای یافتن مالک declaration.
- semantics تازهٔ inheritance فراتر از قرارداد خروجی تایپ‌شدهٔ تصریح‌شده.
- API عمومی جدید و نامرتبط با نیازهای metadata.
- معماری عمومی ORM.
- بهینه‌سازی کارایی یا پاک‌سازی نامرتبط.

اگر یکی از الزام‌های فهرست‌شده در این مرزها قابل انجام نیست، پیش از پیشنهاد گسترش scope، blocker مشخص در سطح source را گزارش کن.

## ۵. معیارهای پذیرش

Plan زمانی کامل است که:

1. `QBQuery` و `QBQuerySelect` با defaultهای توافق‌شده در دسترس باشند.
2. metadata مدل و Query از قواعد تقدم مستندشده پیروی کند؛ تفاوت‌های ضروری و رفتار Model موجود حفظ یا صریحاً ثبت شده باشند.
3. خروجی‌های تایپ‌شدهٔ Query از مسیرهای `alias(KProperty)`، `relationColumn(KProperty)` و `QueryRow.getValue(KProperty)` همچنان کار کنند.
4. نام‌های منطقی از SQL aliasهای منتشرشده مستقل بمانند.
5. یکتایی نام منطقی برای قرارداد خروجی تایپ‌شدهٔ Query جاری، بدون اتکا به reflection مالک declaration، اعتبارسنجی شود.
6. اعتبارسنجی فعلی SQL alias و رفتار سازگاری لازم حفظ شوند.
7. نیازی به تغییر نامرتبط AST، Executor یا API عمومی نباشد.
8. تقدم جداگانهٔ سطح کلاس و Property برای Model و Query، شامل overrideهای DSL، fallback و رفتار مقدار خالی صریح، مستند باشد.
9. fallbackهای قراردادی Model در بند ۲.۵.۱ برای metadata تنظیم‌نشده اعمال شوند؛ رشتهٔ خالی صریح مطابق جدول‌ها اعتبارسنجی یا resolve شود و تفاوت رفتار با source فعلی با regression test پوشش داده شود.
10. نام منطقی خروجی Query، SQL alias منتشرشده، عبارت منبع و نوع استخراج مستقل resolve شوند؛ ارجاع‌های تایپ‌شدهٔ Query و `QueryRow.getValue(KProperty)` mapping فعلی PropertyReference به SQL alias را حفظ کنند.

## ۶. مرز پیاده‌سازی

فقط تغییرهای source لازم برای این Plan را همراه با regression testهای متمرکز بر قواعد metadata و رفتار فعلی خروجی تایپ‌شده انجام بده.

بدون مشخص‌کردن الزام برآورده‌نشدهٔ واقعی و گرفتن تأیید، scope را گسترش نده.

اصل راهنما این است که طراحی موجود metadata با کمترین تغییر لازم تکمیل شود.
