# Plan 4.0: قرارداد Typed Relation Output

## وضعیت

`Unresolved`

Traceability و Decision Closure قبلی ثبت شده‌اند. آخرین بررسی Concrete Relation Declaration همراه با Query Factory نشان می‌دهد repository برای انتخاب و نهایی‌کردن مدل ownership evidence کافی ندارد. این سند فقط blockerها را ثبت می‌کند؛ implementation، تست، build یا refactor انجام نمی‌شود.

## هدف

قرارداد Typed Relation Output را با معماری موجود هماهنگ کن و این مفاهیم را مستقل نگه دار:

```text
Relation Definition
Relation / CTE name
source occurrence / qualifier
Typed Output identity
SQL output name
outer SELECT output alias
```

## تصمیم‌های قطعی مالک

این تصمیم‌ها بسته‌اند و نباید دوباره به‌عنوان گزینه‌های unresolved مطرح شوند:

```text
QueryRelation<O>: Rejected
IQueryRelation: Rejected
.as(Output::property): Rejected
.<typed output declaration>(...): Rejected
alias(Output::property): Adopted
Nested Output semantic model: Adopted
Non-generic QueryRelation: Adopted
Typed Relation consumer semantic: Adopted
Canonical SQL output name: Output property name
Occurrence qualifier selection: Explicit
alias(String): Preserve
relationColumn(relation, String): Preserve only as Plan 3 compatibility API
OutputField / OutputSchema: Rejected
Output registry / Relation registry / global property mapping: Rejected
generic Expression abstraction: Out of scope
reflection registry: Rejected
```

Nested `Output` به‌عنوان semantic model پذیرفته شده است؛ این به معنی وجود concrete nested `Output` در source فعلی نیست. پیاده‌سازی concrete آن Target API است و هنوز انجام نشده است.

API typed هدف:

```kotlin
alias(Output::property)
relationColumn(Output::property)
relationColumn(Output::property, qualifier)
```

`relationColumn(relation, String)` فقط API سازگاری Plan 3.0 است و نباید با API Typed جدید اشتباه گرفته شود. هیچ Relation instance به consumer typed داده نمی‌شود.

## شواهد فعلی Repository

- `QueryRelation` یک interface غیر generic با `name`، `definition` و `dependencies` است: `data_base/query/api/src/main/kotlin/interfaces/relations/QueryRelation.kt`.
- `QueryDefinition`، AST و پارامترهای Definition را نگه می‌دارد: `data_base/query/api/src/main/kotlin/interfaces/relations/QueryDefinition.kt`.
- `queryRelation(name, block)` نام صریح و غیرخالی می‌گیرد، aliasهای SELECT را اعتبارسنجی می‌کند و `BuiltQueryRelation` خصوصی می‌سازد: `data_base/query/builder/src/main/kotlin/relations/QueryRelationBuilder.kt`.
- در source فعلی nested `Output` متعلق به Relation یا `IQueryRelation` وجود ندارد. معنای Nested Output پذیرفته‌شده، Target API است؛ نباید به‌عنوان implementation موجود گزارش شود.
- `IQueryColumnsApi` فعلی `alias(String)` و `relationColumn(relation, sqlOutputName)` دارد؛ overloadهای property-based در source نیستند.
- Model API از `KClass<T>` و `KProperty1<T, R>` برای خواندن `QBTable` و `QBColumn` استفاده می‌کند. این metadata در source فعلی Model property را به Relation Definition متصل نمی‌کند.
- `QueryColumnsBuilder` نام و annotation ستون Model را resolve می‌کند؛ این precedent به‌تنهایی مالکیت Relation برای یک Typed Output را ثابت نمی‌کند.
- `RelationSourceContext` یک Relation فعال و alias آن را نگه می‌دارد؛ resolver موجود Relation instance و SQL output name از نوع String می‌گیرد.
- `QueryRenderSelectBuilder.from(relation, alias)` مقدار `relation.name` را در CTE می‌گذارد و alias را جداگانه در `cteAlias` ثبت می‌کند. CTE ordering و dependency validation نیز از `relation.name` استفاده می‌کنند.
- AST فعلی `Column`، `ColumnAlias`، CTE table و join table را دارد؛ جزئیات sufficiency در بخش AST آمده است.
- naming utility یا repository-backed convention برای تبدیل class/type name به CTE name پیدا نشد. نام Relation در factoryها و تست‌ها صریح داده می‌شود.
- `IQueryRelation` در repository وجود ندارد.

این فهرست source evidence را از Target Contract جدا می‌کند. تصمیم semantic دربارهٔ Typed Output قابلیت پیاده‌سازی‌شده محسوب نمی‌شود.

## قرارداد نام Relation و CTE

هر Relation Definition یک نام canonical صریح دارد:

```text
Relation.name → canonical Relation / CTE name
```

نام باید پیش از dependency traversal، duplicate-name validation و rendering مشخص باشد. Renderer نام CTE را دوباره از نام class/type محاسبه نمی‌کند.

```text
Explicit Relation name: Adopted
Class-name-derived fallback: Deferred / Unresolved
```

تبدیل‌هایی مانند `UserStatsRelation → user_stats` بدون evidence موجود فرض نمی‌شوند. utility یا convention تازه‌ای برای class-name naming ایجاد نکن.

## Relation Definition و source occurrence

Definition و occurrence مستقل‌اند:

```text
Relation Definition
├── canonical name
├── query definition / AST
├── dependencies
└── Typed Output semantic

source occurrence
└── optional SQL source alias
```

رفتار فعلی `from(relation, alias)` حفظ می‌شود:

```kotlin
val effectiveAlias = alias ?: relation.name

QueryTableAst(
    cte = relation.name,
    cteAlias = effectiveAlias,
)
```

پس:

```text
relation.name → CTE name
alias         → source occurrence alias
alias == null → source alias برابر relation.name
```

`from(relation, alias)` نام Relation را جایگزین نمی‌کند و CTE name و source alias را یکی نمی‌کند.

## Typed Output declaration

API canonical declaration:

```kotlin
alias(Output::age)
```

معنا:

```text
Output::age
    → Typed Output identity
    → SQL output name = "age"
```

`alias(String)` همچنان برای alias خام SQL حفظ می‌شود. `alias(Output::property)` به `.as(...)` یا method دیگری تبدیل نمی‌شود. Nested `Output` و این overload تصمیم‌های Target Contract هستند؛ concrete declaration و overload فعلی در source وجود ندارند.

## Typed Relation consumer و occurrence qualifier

دو semantic form زیر canonical هستند.

### بدون source alias

```kotlin
from(userStats).select {
    addColumn {
        relationColumn(UserStatsRelation.Output::age)
    }
}
```

SQL مورد انتظار:

```sql
WITH user_stats AS (...)
SELECT user_stats.age
FROM user_stats
```

نبود qualifier یعنی qualifier برابر نام canonical Relation است. این مقدار از context حدس زده نمی‌شود.

### با source alias

```kotlin
from(userStats, "buyer").select {
    addColumn {
        relationColumn(UserStatsRelation.Output::age, "buyer")
        alias("buyer_age")
    }
}
```

SQL مورد انتظار:

```sql
WITH user_stats AS (...)
SELECT buyer.age AS buyer_age
FROM user_stats AS buyer
```

در این حالت caller qualifier را صریح به `relationColumn` می‌دهد. `from(relation, alias)` فقط occurrence را تعریف می‌کند و alias را به شکل ضمنی به Typed consumer منتقل نمی‌کند.

قرارداد خلاصه:

```text
relationColumn(Output::property)
    → qualifier = canonical Relation.name

relationColumn(Output::property, qualifier)
    → qualifier = همان مقدار صریح caller
```

Builder حق ندارد qualifier را از `RelationSourceContext`، اولین Relation، ترتیب declaration، alias پیش‌فرض، تنها occurrence قابل مشاهده یا heuristic دیگری حدس بزند. اگر qualifier صریح داده شود، همان qualifier به AST پایین آورده می‌شود.

`relationColumn(relation, String)` فقط compatibility API قدیمی Plan 3.0 است؛ قرارداد Typed جدید نیست.

## Typed Output → Relation Definition association

این تنها unresolved واقعی است:

```text
UserStatsRelation.Output::age
        ↓
Relation Definition ownership
```

Occurrence selection از این مسئله مستقل و بسته است:

```text
no qualifier       → canonical Relation.name
explicit qualifier → caller-provided value
```

### بررسی mechanismهای موجود

Traceability source فعلی mechanismی برای اتصال Typed Output property به Relation Definition مالک پیدا نکرده است:

- `data_base/query/api/src/main/kotlin/interfaces/relations/QueryRelation.kt`، نماد `QueryRelation`: metadata موجود شامل `name`، `definition` و `dependencies` است؛ owner type یا Output metadata ندارد.
- `data_base/query/api/src/main/kotlin/interfaces/relations/QueryDefinition.kt`، نماد `QueryDefinition`: Definition، AST و پارامترها را نگه می‌دارد؛ ارتباطی با nested Output type ندارد.
- `data_base/query/builder/src/main/kotlin/relations/QueryRelationBuilder.kt`، تابع `queryRelation(name, block)` و کلاس خصوصی `BuiltQueryRelation`: factory نام Relation و block را می‌گیرد و Definition/dependencies را می‌سازد؛ metadata مربوط به owner concrete Relation یا Output property در این مسیر ثبت نمی‌شود.
- `data_base/query/api/.../IQueryColumnsApi` و پیاده‌سازی‌های Builder: امضای موجود `relationColumn(relation, sqlOutputName)` است؛ شکل property-based یا owner resolution وجود ندارد.
- استفاده‌های موجود از `KClass` و `KProperty1` در Model API و `QueryColumnsBuilder` برای خواندن `QBTable`/`QBColumn` و resolve کردن نام جدول/ستون است. این مسیر مالکیت Relation Definition را برای Output property ثبت یا بازیابی نمی‌کند.
- `RelationSourceContext`: نماد موجود Relation occurrence فعال و qualifier را نگه می‌دارد؛ resolver فعلی Relation instance و نام خروجی String می‌گیرد. این فقط source/output-name resolution است و association بین Output type و Relation Definition را ثابت نمی‌کند.
- جست‌وجوی source برای nested `Output`، metadata مالک declaration، یا mechanism دیگری که `KProperty1<Output, R>` را به Relation Definition مشخص وصل کند، چنین مسیر فعالی نشان نداد. `KProperty1.name` فقط نام property را فراهم می‌کند و به‌تنهایی owner association نیست.

## Multi-occurrence

Multi-occurrence ambiguity دلیل الزام qualifier صریح است:

```text
UserStatsRelation
├── source alias: buyer
└── source alias: seller
```

در این حالت `Output::age` به‌تنهایی alias مقصد را مشخص نمی‌کند. Caller با `relationColumn(Output::age, "buyer")` یا `relationColumn(Output::age, "seller")` qualifier را انتخاب می‌کند. Builder نباید silently یکی را برگزیند.

Builder فعلی در هر `QueryRenderSelectBuilder` فقط یک Relation source اصلی ثبت می‌کند (`relationFromConfigured` و `RelationSourceContext`). AST یک `table` اصلی و فهرست `joins`/`joinTable` دارد، اما Join builder فعلی Relation Definition را در dependency، parameter و Relation context orchestration ثبت نمی‌کند. Simultaneous same-Definition multi-occurrence فعلاً `Deferred` است مگر اینکه جداگانه وارد scope شود. اگر آن scope Adopt شود، limitation موجود در source orchestration است؛ معنای `Relation.name` یا CTE naming را تغییر نده.

## ارزیابی AST

```text
No new generic AST abstraction is justified by current evidence.
```

برای single-source Contract، AST فعلی قابلیت نمایش SQL پایین‌آورده‌شده را دارد:

- `IQueryColumnsAst` دارای `Column` و `ColumnAlias` است.
- `IQueryColumnsBaseAst` دارای `cteAlias` و `select` است؛ qualifier و نام خروجی Relation را می‌تواند نگه دارد.
- `IQueryTableAst` دارای `cte` و `cteAlias` است؛ CTE name و source alias را جدا نگه می‌دارد.
- Join item دارای `joinTable` از نوع `IQueryTableAst` است.

بنابراین برای single-source، پس از resolution مالکیت Typed Output در Builder، nodeهای فعلی qualifier و نام SQL output را نمایش می‌دهند. این جمع‌بندی محدود به همین مسیر است و ادعای «هیچ AST تغییری در هیچ scope آینده‌ای لازم نیست» نیست. اگر Traceability مربوط به scope دیگری ثابت کند nodeهای فعلی کافی نیستند، فقط limitation را ثبت کن؛ در این مرحله AST node یا abstraction جدید نساز.

## اثر لایه‌ای

- **Builder:** باید Typed Output → Relation Definition association را resolve کند. qualifier را از canonical name یا صریحاً از caller می‌گیرد و از context occurrence حدس نمی‌زند.
- **AST:** برای SQL تک‌منبعی پس از resolution، nodeهای فعلی استفاده می‌شوند؛ generic AST abstraction جدید توجیه نشده است.
- **Renderer:** qualifier و output name resolveشده را render می‌کند؛ property یا ownership را resolve نمی‌کند.
- **Executor:** بدون تغییر می‌ماند.
- **Dependency graph:** بر اساس `QueryRelation.dependencies` و canonical `Relation.name` باقی می‌ماند.

## سازگاری Plan 3.0

- `alias(String)` حفظ می‌شود.
- `relationColumn(relation, String)` در صورت نیاز فقط برای compatibility حفظ می‌شود.
- `Relation.name` همچنان CTE name و `from(relation, alias)` همچنان source alias را مشخص می‌کند.
- Relation identity، خروجی‌های SQL، CTE lowering، dependency ordering، cycle detection، duplicate-name validation و parameter ordering بی‌دلیل بازطراحی نمی‌شوند.
- Renderer و Executor مسئول خواندن Model/Relation property metadata نمی‌شوند.

## Traceability: Concrete Relation Type و Typed Property

### Scope و candidate

این بررسی فقط candidate زیر را ارزیابی می‌کند؛ آن را implementation یا contract نهایی فرض نمی‌کند:

```kotlin
class UserStatsRelation(val minAge: Int) {
    val age: Int
    val name: String
    val query = query { /* ... */ }
}

relationColumn(UserStatsRelation::age, "adults")
```

### Repository Evidence

- `QueryRelation` فقط `name`، `definition` و `dependencies` دارد. `QueryDefinition`، AST و `params` را با هم در یک payload نگه می‌دارد.
- `queryRelation(name, block)` یک `BuiltQueryRelation` خصوصی ایجاد می‌کند. candidate class به‌شکل نشان‌داده‌شده `QueryRelation` نیست و بنابراین مستقیماً برای `from(relation)` قابل‌استفاده نیست؛ برای باقی‌ماندن روی API فعلی، concrete relation باید با قرارداد `QueryRelation` سازگار شود. این می‌تواند استفاده از interface موجود باشد، ولی شکل دقیق آن در repository precedent ندارد.
- اگر concrete instance در initializer خود `queryRelation(name) { ... minAge ... }` بسازد، factory می‌تواند مقدار `minAge` را در `SqlParameter`‌های همان Definition ثبت کند. در این حالت instanceهای هم‌نوع می‌توانند مقدارهای متفاوت بسازند، اما هر کدام `QueryRelation`/`QueryDefinition` ساخته‌شدهٔ خود را دارند؛ repository، یک AST/Definition مشترک با params جداگانه برای چند instance ارائه نمی‌کند.
- `QueryRenderSelectBuilder.from` نام CTE و source alias را جدا نگه می‌دارد. `syncRelationWithItems` و `orderedRelationClosure` dependencyها را بر اساس identity و `relation.name` مرتب می‌کنند؛ `ownRelationParams` پارامترهای dependency را از params خود relation جدا می‌کند؛ `relationWithItem` AST Definition را در CTE کپی می‌کند. این lowering قابل استفاده باقی می‌ماند اگر ورودی همچنان قرارداد `QueryRelation` و ترتیب `definition.params` را رعایت کند.
- `RelationSourceContext` در هر query فقط یک Relation source ثبت می‌کند. `relationColumn` با API فعلی `QueryRelation + String` resolve می‌شود. simultaneous چند source برای دو instance از یک concrete type، فعلاً پشتیبانی orchestration ندارد.
- repository در Model path از `KProperty1<T, R>`، `KClass<T>` و reflection برای metadata استفاده می‌کند؛ در این مسیر receiver type به‌عنوان Relation owner تطبیق داده نمی‌شود. در API Kotlin، `KProperty1<T, R>` پارامترهای نوع receiver و مقدار را دارد؛ این می‌تواند نوع receiver را برای candidate مشخص کند، ولی source فعلی از آن برای اتصال به `QueryRelation` استفاده نمی‌کند.

### Identity و Kotlin Property

```text
Relation Type:             UserStatsRelation
Typed property reference:  UserStatsRelation::age
Relation instance:         UserStatsRelation(18)
Query definition:          موجود در QueryRelation فعلی
Parameters:                بخشی از QueryDefinition فعلی
```

`UserStatsRelation::age` نسبت به `Output::age` receiver type را به خود Relation class وصل می‌کند؛ بنابراین candidate می‌تواند owner type را صریح‌تر کند. این به‌تنهایی instance یا `QueryRelation.definition` را ایجاد یا پیدا نمی‌کند. در source فعلی تطبیق receiver type با concrete Relation instance، یا تبدیل concrete class به Relation source، وجود ندارد.

استفاده از property به‌عنوان marker بدون خواندن getter از نظر API ممکن است، اما repository قراردادی دربارهٔ marker بودن، مقدار runtime، initializer، inherited property یا معنای type/nullability این properties تعیین نکرده است. type آن‌ها نباید به SQL type یا operator inference تبدیل شود مگر اینکه contract جداگانه‌ای تصویب شود.

### Constructor parameters و پارامترهای Query

- مقادیر constructor می‌توانند هنگام ساخت query به valueهای معمول Builder تبدیل شوند؛ پارامترها در `QueryDefinition.params` ذخیره می‌شوند.
- تست‌های موجود ترتیب پارامترهای relationهای تو‌در‌تو و query مصرف‌کننده را ثبت می‌کنند. `ownRelationParams` بر همین ترتیب و بر فرض وجود params در Definition تکیه دارد.
- اگر الزام این باشد که دو instance از یک type یک Definition واحد داشته باشند ولی params متفاوت حمل کنند، architecture فعلی این جداسازی را نشان نمی‌دهد؛ در وضع موجود، ساختن Definition برای هر instance به Definitionهای جداگانه منجر می‌شود.
- بنابراین constructor parameterization برای Definitionهای ساخته‌شده به‌ازای instance قابل تصور است، اما قرارداد «Same Definition + Different Instance Parameters» هنوز بسته نیست.

### Compatibility و Multi-occurrence

| API / behavior | تصمیم فعلی | دلیل |
|---|---|---|
| `queryRelation(name, block)` | Preserve | factory فعال و مسیر فعلی ساخت Definition است. |
| `QueryRelation`, `name`, `definition`, `dependencies` | Preserve | interface و metadata پایهٔ orchestration فعلی هستند. |
| `from(relation)` / `from(relation, alias)` | Preserve | ورودی `QueryRelation` می‌خواهد؛ alias occurrence را جدا از CTE name نگه می‌دارد. |
| `relationColumn(relation, String)` | Preserve به‌عنوان compatibility | API فعال Plan 3 است؛ Typed overload جدید در source نیست. |
| CTE lowering و dependency ordering | Preserve | با `QueryRelation` و `QueryDefinition` فعلی کار می‌کند. |
| parameter ordering | Preserve، با قید lifecycle فعلی | dependency و own params از `definition.params` خوانده می‌شوند؛ shared Definition با instance params جدا وجود ندارد. |
| هم‌زمانی `adults` و `seniors` به‌عنوان دو source | Defer | `relationFromConfigured` و `RelationSourceContext` در هر query یک source را می‌پذیرند. این محدودیت نباید با qualifier inference دور زده شود. |

اگر caller بنویسد `relationColumn(UserStatsRelation::age, "adults")`، target SQL qualifier باید دقیقاً `adults` باشد. این انتخاب همچنان explicit است؛ از active context یا ترتیب declaration استخراج نمی‌شود. بدون qualifier، قرارداد پیشین canonical Relation name را تعیین می‌کند، نه alias استنباط‌شده.

## Traceability نهایی: Concrete Relation Declaration + Query Factory

این بخش جدیدترین بررسی candidate زیر را ثبت می‌کند و وضعیت نهایی سند را تعیین می‌کند. مثال candidate به‌تنهایی API قطعی نیست.

### Repository Evidence و lifecycle

- `QueryRelation` engine-level interface موجود با `name`، `definition` و `dependencies` است. `IQueryRelation` در source پیدا نشد.
- `queryRelation(name, block)` نام صریح می‌گیرد و `QueryRelation` می‌سازد؛ `QueryRenderSelectBuilder.from` نیز همین نوع را می‌پذیرد. پس یک factory از نوع `query(args...): QueryRelation` از نظر خروجی می‌تواند وارد pipeline فعلی شود.
- `QueryRelation` تولیدشده owner concrete declaration را نگه نمی‌دارد. `RelationSourceContext` فقط QueryRelation فعال و alias را نگه می‌دارد؛ بنابراین با دریافت صرف `KProperty1<UserStatsRelation, R>` راهی برای ارتباط آن با Relation ساخته‌شده نشان داده نشده است.
- `QueryDefinition` هم AST و هم params را نگه می‌دارد. factory می‌تواند مقادیر args را هنگام ساخت query به `SqlParameter` تبدیل کند، اما source contract جداگانه‌ای برای shared Definition و params مخصوص هر invocation ندارد.
- `syncRelationWithItems`, `orderedRelationClosure`, `ownRelationParams` و `relationWithItem` بر همان QueryRelation و Definition/params موجود عمل می‌کنند. حفظ این مسیر مستلزم آن است که factory خروجی سازگار با QueryRelation و ordering فعلی بدهد.
- API فعلی `alias(String)` و `relationColumn(QueryRelation, String)` است. `alias(UserStatsRelation::age)` و `relationColumn(UserStatsRelation::age[, qualifier])` در source نیستند.
- در نمونه‌ی candidate، `val id: Int`, `val name: String` و `val age: Int` بدون initializer، `abstract` بودن یا custom getter برای concrete class تعریف کامل Kotlin نیستند. همچنین top-level `query {}` در مسیرهای جست‌وجوشده پیدا نشد؛ موجود در source factory، `queryRelation(name, block)` است.

### پاسخ به پرسش‌های ownership و API

- `UserStatsRelation::age` نوع receiver را در `KProperty1<UserStatsRelation, Int>` مشخص می‌کند و نام property را می‌دهد. این metadata به‌تنهایی QueryRelation ساخته‌شده را شناسایی نمی‌کند؛ owner type ↔ QueryRelation mapping در source موجود نیست.
- Typed properties می‌توانند از نظر semantic marker باشند، اما candidate مشخص نمی‌کند getter/value باید قابل اجرا باشد یا type/nullability چه معنایی دارد. repository هم قراردادی برای این موارد ندارد.
- Relation identity باید همچنان صریح باشد: candidate `relationName` باید به `QueryRelation.name` برسد تا نام CTE حفظ شود؛ class-name inference مجاز نیست.
- Typed alias نیازمند overload تازه‌ای است؛ property name به‌عنوان SQL output name قابل بررسی است، اما از source فعلی به‌تنهایی Adopt نمی‌شود. `alias(String)` حفظ می‌شود.
- Typed consumer نیازمند overload تازه‌ای است. qualifier همچنان explicit می‌ماند؛ بدون qualifier canonical Relation name استفاده می‌شود، و qualifier داده‌شده عیناً مصرف می‌شود. Builder نباید occurrence را infer کند.
- `class` و `object` هیچ‌کدام را source الزام نمی‌کند. `class` امکان instance state می‌دهد؛ ولی چون candidate متد `query(minAge)` را هم دارد، ضرورت instance-held parameters اثبات نشده است.
- `IQueryRelation` لازم‌بودنش از repository ثابت نمی‌شود: factory از قبل `QueryRelation` می‌دهد. در عین حال حذف نیاز به IQueryRelation، association Typed property به Relation را حل نمی‌کند. با محدودیت‌های فعلی interface جدید تصویب نمی‌شود.
