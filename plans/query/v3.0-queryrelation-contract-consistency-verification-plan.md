## 3. تصمیم قطعی API دربارهٔ Alias

در Plan 3.0 هیچ syntax یا API جدیدی به نام `.as(...)` ایجاد نمی‌شود.

مکانیزم موجود repository برای alias باید حفظ شود:

```kotlin
alias("userId")
```

این شکل جزو Contract واقعی نیست:

```kotlin
column(UserModelV2::id)
    .as(Output::id)
```

`.as(...)` صرفاً notation مفهومی در Vision یا exampleهای قدیمی است. API canonical باید بر اساس API موجود repository تعیین و verify شود؛ برای نمونه:

```kotlin
column(UserModelV2::id)
alias("userId")
```

هیچ API جدیدی برای alias پیشنهاد یا ایجاد نکن.

---

## 4. تمایز Alias و OutputField

این دو مفهوم را جدا نگه دار:

```text
alias(...)
    ↓
SQL output name

OutputField
    ↓
semantic identity of relation output
```

Contract مفهومی:

```text
Output Field Identity
    = Relation Identity + Output Property

Logical Output Name
    = Output Property Name

SQL Output Name
    = existing alias mechanism
```

اگر alias وجود نداشته باشد، نام SQL خروجی از نام property می‌آید. اگر alias وجود داشته باشد، فقط نام SQL را override می‌کند و نباید هویت semantic خروجی را تغییر دهد.

## 5. بررسی‌های الزامی

### 5.1 شواهد Alias در Repository

source جاری را بررسی و ثبت کن:

* alias در API موجود چگونه تعریف می‌شود
* Builder مقدار alias را چگونه دریافت و نگهداری می‌کند
* alias در AST چگونه نمایش داده می‌شود
* Renderer alias را چگونه در SQL رندر می‌کند
* آیا SELECT item از alias پشتیبانی می‌کند
* آیا پاک‌کردن alias در API فعلی ممکن است و معنای آن چیست
* syntax canonical فعلی alias چیست

هیچ API جدیدی پیشنهاد نده، مگر اینکه evidence واقعی repository آن را لازم کند.

### 5.2 سازگاری Contract

Plan 3.0 Final Contract و سندهای مرتبط را بررسی کن. هرجا `.as(...)` یا syntax جدیدی به‌عنوان API واقعی معرفی شده، آن را شناسایی کن و با تصمیم زیر مقایسه کن:

```text
.as(...) = conceptual notation only
alias(...) = canonical existing API
```

اگر Final Contract از قبل این تفکیک را رعایت می‌کند، Contract را تغییر نده.

### 5.3 معنای Output Field

تأیید کن حذف `.as(...)` از API واقعی هیچ تغییری در semantic model ایجاد نمی‌کند و همچنان می‌توان این مسیر را با abstractionهای موجود پیاده کرد:

```text
Physical Field
    ↓
SELECT item
    ↓
Output Field
    ↓
Relation Output Schema
```

Output Field نباید برای بیان binding مجبور به ایجاد syntax تازه شود.

### 5.4 مصرف Relation

بررسی کن مصرف Relation بر اساس Output Property یا property reference معنایی انجام می‌شود، نه بر اساس رشتهٔ SQL alias خام.

مفهوم مورد انتظار:

```text
Relation.Output::field
```

consumer نباید برای ارجاع معنایی مجبور به نوشتن نام SQL alias به شکل رشته باشد. Renderer باید SQL output name را از همان alias mechanism موجود دریافت کند.

### 5.5 مرز Scope نسخهٔ 3.0

بدون evidence روشن از repository، موارد زیر خارج از Scope باقی بمانند:

* CASE expression
* عبارت‌های arithmetic
* generic expression framework
* generic `Selectable`
* generic `Expression AST`
* Derived Table
* relation fields در JOIN
* relation fields در WHERE
* relation fields در GROUP BY
* relation fields در HAVING
* relation fields در ORDER BY
* Result Mapping
* API جدید `.as(...)`

### 5.6 Vision در برابر Plan 3.0

این تمایز را صریح نگه دار:

```text
Vision
    = architecture direction

Plan 3.0
    = adopted minimal subset
```

نبود `.as(...)` در Plan 3.0 به معنی نادرست‌بودن Vision نیست. در Vision، `.as(Output::field)` فقط notation مفهومی برای بیان binding بوده است. در implementation واقعی، همان semantic باید با abstractionهای موجود repository و `alias(...)` بیان شود.

### 5.7 راستی‌آزمایی Implementation

source code را فقط برای بررسی بخوان؛ آن را تغییر نده. مشخص کن implementation فعلی:

* alias mechanism موجود را حفظ کرده است یا نه
* API جدید `.as(...)` اضافه کرده است یا نه
* هویت semantic `OutputField` را از SQL alias جدا نگه داشته است یا نه
* مصرف Relation را با Output Property انجام می‌دهد یا با SQL alias خام
* SQL alias را فقط در مرز لازم برای تولید SQL اعمال می‌کند یا نه
* سازگاری V1/V2 را حفظ کرده است یا نه

برای هر تصمیم مهم این زنجیره را ثبت کن:

```text
Repository Evidence
        ↓
Interpretation
        ↓
Decision
```

شواهد source، Contract، example و notation مفهومی را با یکدیگر خلط نکن.


* عبارت یا بخش فعلی Contract

* عبارت صحیح پیشنهادی
* دلیل مبتنی بر evidence
* مواردی که نباید تغییر کنند

اگر source و Contract شواهد کافی برای تصمیم نهایی ندهند، مورد را unresolved ثبت کن و بدون evidence آن را قطعی اعلام نکن.
