# Plan 3.0: QueryDefinition / QueryRelation Traceability & Contract Analysis

## Status

`Ready for Traceability`

این گزارش بر پایهٔ source فعلی است. هیچ source، test یا configuration در این مرحله تغییر نکرده و هیچ build یا database operation اجرا نشده است. چند قرارداد محوری برای Composition هنوز از API و AST موجود قابل استخراج نیستند؛ در نتیجه وضعیت `Implementation Ready` موجه نیست.

## Objective

ردیابی کنیم که Query Builder V2 چگونه `KClass + KProperty1 + @QBTable/@QBColumn` را به SQL-ready AST تبدیل می‌کند و مشخص کنیم کوچک‌ترین قرارداد معنایی لازم برای تبدیل یک SELECT به خروجی قابل ترکیب چیست.

## Core Vision

هدف ارزیابی‌شده این زنجیره است:

```text
KClass + KProperty
        ↓
Physical Field
        ↓
SELECT item
        ↓
Relation Output Field
        ↓
Relation Output Schema
        ↓
Query Relation
        ↓
Another Query
```

Source فعلی دو گام نخست را تا resolved strings پوشش می‌دهد. `Relation Output Field`, `Output Schema` و `Query Relation` در source فعلی تعریف نشده‌اند. Vision هدف تحلیل است و به‌خودی‌خود evidence برای افزودن abstraction محسوب نمی‌شود.

## Existing Query Builder Architecture

`IQueryRenderSelectApi` surface شامل `withs`, `select`, `table`, `joins`, `where`, `limit`, `offset`, `group`, و `order` است. `QueryRenderSelectBuilder` برای هر clause AST مربوطه را می‌سازد و در root قرار می‌دهد. مسیر SELECT این است:

```text
IQueryRenderSelectApi.select { ... }
  → QueryRenderSelectBuilder.select
  → QuerySelectBuilder.addColumn
  → QueryColumnsBuilder
  → IQueryRenderSelectAst.select / IQuerySelectAst.columns
  → dialect registry
  → renderer capabilities
```

`QueryRenderSelectBuilder` یک `ModelTableAliasContext` داخلی را میان ساخت SELECT و table به‌اشتراک می‌گذارد. این context فقط map از `KClass` به alias مؤثر و فهرست nodeهای typed column قابل به‌روزرسانی است؛ schema یا relation identity نیست. ثبت table می‌تواند qualifierهای typed columnهای قبلی را نیز با alias مؤثر هم‌تراز کند.

رندر SQL در capabilityهای dialect انجام می‌شود. Query Builder V2 خود را جایگزین معماری فعلی نمی‌کند و APIهای legacy رشته‌ای در کنار typed API باقی‌اند.

## Existing QueryDefinition Evidence

`QueryDefinition`: **Not currently present** به‌عنوان domain/API مستقل در source جست‌وجوشده. نزدیک‌ترین ساختار، `IQueryRenderSelectAst` است؛ این ساختار AST یک query قابل render است، نه قرارداد مستقل query definition با هویت/خروجی schema.

## Existing QueryRelation Evidence

`IQueryRelation` / `QueryRelation`: **Not currently present** در source. `ICte` وجود دارد، اما یک CTE query provider است و به‌تنهایی معنای عمومی Relation یا output schema را اثبات نمی‌کند. `IQueryWithsItemAst` فقط `withName` و `withBody` را نگه می‌دارد.

## Model / KClass / KProperty Traceability

برای `column(UserModelV2::class, UserModelV2::id)`:

```text
IQueryColumnsApi.column(KClass<T>, KProperty1<T,R>)
  → QueryColumnsBuilder.column
  → table.findAnnotation<QBTable>()
  → property.findAnnotation<QBColumn>()
  → QueryColumnsBaseAst(tableAlias = QBTable.alias, column = QBColumn.name)
  → QueryColumnsAst.ColumnAlias = QBColumn.alias if non-empty
  → QuerySelectAst.columns
  → renderer emits qualified column and optional SQL alias
```

`KClass` generic type and `KProperty1<T,R>` constrain the Kotlin call statically to `T : IModelBase`. Runtime Builder resolves annotations with `kotlin.reflect.full.findAnnotation`. Missing annotations and empty table/column names fail with `IllegalArgumentException`/`require` before render. Physical SQL column comes from `QBColumn.name`, نه property name. Property ownership is not separately checked in the body against the passed class; generic typing constrains ordinary Kotlin use sites, while behavior for forged/unchecked reflection values is not contract-tested in the inspected test.

در مسیر `tableColumn(KClass, property, explicitTableAlias)`, Builder همچنان metadata ستون را resolve می‌کند ولی alias جدول را از argument می‌گیرد. مسیر `table(KClass, alias?)` از `QBTable.name` و alias صریح یا پیش‌فرض annotation استفاده می‌کند و alias context را ثبت می‌کند.

اطلاعات `KClass`, `KProperty1` و annotation پس از ساخت `QueryColumnsBaseAst` در آن AST نگهداری نمی‌شوند؛ در این مرز به SQL-ready strings فروکاسته شده‌اند. `ModelTableAliasContext` فقط برای resolve alias در زمان ساخت استفاده می‌شود.

## Physical Field Analysis

Repository یک **API operation** دارد که معنای Physical Field را موقتاً resolve می‌کند: model class + property + annotationها به table qualifier و database column name. اما یک Physical Field object/node با هویت یا metadata پایدار ندارد؛ بنابراین پاسخ دقیق: **معادل رفتاری در Builder هست، semantic node پایدار در AST وجود ندارد.**

## SELECT Item Analysis

`IQuerySelectAst.columns: MutableList<IQueryColumnsAst>` عملاً container آیتم‌های SELECT است. اما abstraction مستقل یا polymorphic `SelectItem` وجود ندارد. شکل فعلی هر آیتم دقیقاً یک `ColumnMethod? + ColumnBase? + ColumnAlias?` است. پس برای physical column و aggregate modifier کفایت دارد، ولی source evidenceای برای قرار دادن arbitrary expression یا Relation Field در همان جایگاه وجود ندارد.

`Column` و `Expression` parent semantic مشترک ندارند؛ مورد دوم به‌صورت SELECT expression در source فعلی **Not currently present** است. هیچ `Selectable`, `SelectItem`, `ExpressionOrField` یا hierarchy مشابهی در این مسیر وجود ندارد.

## `.as(...)` Analysis

هیچ extension/function به شکل `.as(...)` در Query Builder source فعلی پیدا نشد: **Not currently present**. API متناظر فعلی `alias(alias: String): IQueryColumnsApi` است.

`QueryColumnsBuilder` مقدار پیش‌فرض SELECT alias را از `QBColumn.alias` می‌گیرد؛ فراخوانی صریح `alias(String)` بر آن مقدم است، و رشتهٔ خالی به `null` در `ColumnAlias` تبدیل می‌شود. AST alias را فقط به‌صورت String nullable نگه می‌دارد. `MySqlQueryColumnCapability` alias را به `As <alias>` رندر می‌کند.

این alias در حال حاضر SQL SELECT output alias است؛ evidenceای وجود ندارد که alias هویت property، مالک Relation، schema output یا query-to-query reference باشد. CTE column reference از مسیر مجزای `cteColumn(cteAlias, selectName)` می‌گذرد و به Stringهای مستقل نیاز دارد. بنابراین SQL alias و Relation Output Field در مدل فعلی **یکی نیستند**.

## Output Field Analysis

`Relation Output Field`: **Not currently present**. `ColumnAlias` نزدیک‌ترین دادهٔ ظاهری است، اما فقط رشتهٔ رندر است؛ نه owner relation، نه source SELECT item، نه property identity و نه قابل ارجاع بودن در query دیگر را ثبت می‌کند.

## Output Model Analysis

`Output Model` / schema متناظر با `data class Output(...)`: **Not currently present** در Query Builder source. `KProperty1` در typed model API برای انتخاب ستون فیزیکی و `KClass` برای metadata table استفاده می‌شود؛ این به‌تنهایی contract برای Output DTO نیست.

اگر Output Field قرار باشد به property متصل شود، حداقل owner class و property identity باید در زمان ساخت/اعتبارسنجی قابل تشخیص باشند. نوع property و nullability از `KProperty1`/Kotlin reflection قابل مشاهده‌اند، ولی source فعلی آن‌ها را به SQL type، SQL nullability یا Result Mapping تبدیل نمی‌کند. Constructor metadata برای Query composition در source فعلی مصرف نمی‌شود و بر اساس شواهد فعلی برای فیلد معنایی خروجی لازم‌بودنش ثابت نشده است. این بحث نباید به mapper تبدیل شود.

## Relation Identity

Relation identity: **Not currently present**. Repository از `KClass` به‌عنوان schema model key در typed table/column و در `ModelTableAliasContext` استفاده می‌کند؛ از این usage نمی‌توان هویت Relation را به class identity تقلیل داد. CTE فعلی با `withName`/alias String شناخته می‌شود، اما این قرارداد Relation identity نیست. انتخاب object identity، class identity یا query identity بدون قرارداد/consumer evidence unresolved است.

## Field Identity

در AST فیزیکی، field مؤثر صرفاً از `tableAlias` + `column` (یا CTE alias + select name) ساخته می‌شود. property identity پاک شده است. از این رو AST نمی‌تواند تمایز معنایی بین این موارد را نگه دارد:

```text
UserModelV2::id
UserOrderStats.Output::userId
ImportantUsers.Output::id
```

حتی اگر SQL آخر به نام یکسان برسد. این تمایز در DSL/validation پیش از تبدیل به رشته‌ها باید قابل ردیابی باشد، اما مکان و شکل قرارداد در evidence فعلی تعیین نشده است.

## Query Scope

AST فعلی clauseهای SELECT، FROM/table، JOIN، WHERE، GROUP، ORDER و CTE را جداگانه نگه می‌دارد. SELECT alias فقط در SELECT item AST ذخیره می‌شود. Relation Field با scope identity در هیچ‌یک از clauseها حاضر نیست.

| Scope | وضعیت قابل استنتاج از source |
| --- | --- |
| SELECT | column/aggregate و SQL output alias رندر می‌شوند؛ Relation output semantics وجود ندارد. |
| FROM | table رشته‌ای یا مدل فیزیکی و CTE رشته‌ای قابل ثبت است؛ Relation به‌عنوان source عمومی وجود ندارد. |
| WHERE | selector ستون/raw column و value/parameter دارد؛ Relation field API ندارد. |
| GROUP BY | `IQueryOptionGroupApi.addColumn` از base-column builder استفاده می‌کند؛ Relation field typing ندارد. |
| HAVING | API مجزای HAVING در `IQueryRenderSelectApi` فعلی مشاهده نشد؛ **Not currently present**. |
| ORDER BY | order builder موجود است، اما property/reference معنایی Relation وجود ندارد. |
| JOIN | join table و condition group موجودند؛ join source فعلی table/مدل/CTE مسیرهای موجود است، Relation identity ندارد. |
| CTE | `withName + withBody` و raw CTE column names/aliases موجودند؛ Composition typed relation field نیست. |
| Derived table | source abstraction مستقل برای derived table/subquery به‌عنوان FROM/JOIN item پیدا نشد؛ **Not currently present**. |

پس معتبر بودن alias در هر SQL scope را نمی‌توان از `ColumnAlias` تعمیم داد. قرارداد scope-aware برای Relation Field unresolved است و نیازمند SQL dialect/use-site contract و API examples مشخص است.

## Composition Analysis

Composition از Relation A به Relation B در source فعلی پشتیبانی معنایی ندارد. V2 می‌تواند typed field فیزیکی را انتخاب کند؛ CTE renderer می‌تواند nested query را با نام CTE و CTE column را با رشته بسازد. بین این دو مسیر mapping معنایی بین output property و مصرف‌کننده وجود ندارد.

برای تشخیص «این فیلد متعلق به Relation است، نه Database Model» باید مالکیت و نوع منبع تا مرحلهٔ Builder/validation حفظ شود. Renderer فعلی فقط ASTهای رشته‌ای دریافت می‌کند و اطلاعی از model/field identity ندارد. تعیین اینکه این distinction در DSL یا AST نگهداری شود، با شواهد موجود قطعی نیست؛ اما تبدیل زودهنگام به `String` پیش از composition، distinction را از بین می‌برد.

## CTE Analysis

CTE بالفعل موجود است: `ICte` یک `cteQuery(params)` ارائه می‌کند؛ `IQueryWithsItemAst` دارای `withName` و `withBody` است؛ APIهای `withs` آن را در select root قرار می‌دهند. Base column builder یک `cteColumn(cteAlias, selectName)` رشته‌ای نیز دارد. این قابلیت CTE-specific است و evidence برای generic Relation source فراهم نمی‌کند.

در نتیجه Relation از نظر مفهومی نباید با CTE یکی فرض شود. امکان reuse یک Relation در CTE، FROM، JOIN یا derived table نیازمند source abstraction/placement contract جداگانه است؛ هیچ‌یک در v3 فعلی پیاده‌سازی یا تصمیم نهایی نمی‌شود.

## Derived Table Analysis

AST table node فعلی شامل table name/alias و CTE name/alias است؛ nested SELECT node در table/JOIN source shape مشاهده نشد. `Derived Table Source`: **Not currently present**. وجود nested query در CTE AST اثبات‌کنندهٔ FROM subquery نیست.

## Result Mapping Boundary

ResultSet → مدل‌سازی دستی در example code (مانند `rs.getInt("user_id")`) جدا از query AST است. در scope این trace، هیچ mapping خودکار Output DTO در Query Builder source یافت نشد. قرارداد مطلوب باید query composition/output schema را از ResultSet mapping جدا نگه دارد. هیچ mapper، constructor mapper، serialization یا code generation پیشنهاد یا ساخته نشده است.

## Candidate Architectures

| Candidate | ارزیابی بر اساس evidence فعلی | تصمیم traceability |
| --- | --- | --- |

| --- | --- | --- | --- | --- | --- |
| Physical Field | typed V2 API/metadata | رشته‌های qualifier و column در base AST | identity قابل حفظ تا composition | property/model metadata پس از Builder حذف می‌شود | Separate Contract |

| SELECT Item | `IQuerySelectAst.columns` | فهرست `IQueryColumnsAst` | physical/expression/relation output | shape فقط column + method + alias است | Separate Contract |
| `.as(...)` | در source نیست | API فعلی `alias(String)` | نام‌دهی output field و identity | alias فقط SQL string | Reject as semantic equivalence |
| Output Field | در source نیست | — | owner + source SELECT item + property | identity/schema absent | Unresolved |
| Output Model | در source نیست | — | property identity optional typed surface | Result Mapping نباید داخل شود | Defer |

| Query Relation | در source نیست | CTE فقط مورد نزدیک | output schema و composability | Relation semantic object absent | Unresolved |

Decision values طبق Plan تفسیر شده‌اند؛ `Adopt` برای abstraction یا implementationی که با evidence لازم توجیه نشده صادر نشده است.

## Builder Validation

Builder فعلی metadata ناقص/خالی برای `@QBTable` و `@QBColumn` را رد می‌کند. این validation metadata فیزیکی در source و tests پوشش دارد. مواردی مانند duplicate Output property، incompatible Output property type، invalid Relation reference، unresolved Relation field و invalid SQL scope فعلاً موضوعی برای اعتبارسنجی ندارند، چون آن domain model موجود نیست.

قرارداد آینده باید validation بر مبنای query/relation schema و قبل از rendering تعریف کند. AST تنها ساختار فعلی را حمل می‌کند؛ Renderer می‌تواند دفاعی render کند، اما مسئولیت Relation semantics با evidence فعلی به آن واگذار نمی‌شود. Database introspection/preflight برای QueryDefinition استفاده نشود.

## AST Contract

AST فعلی clauses را با interfaceهای مستقل نگه می‌دارد؛ SELECT column node دارای nullable string method, base column, alias است. `KClass`, `KProperty`, QB metadata، relation owner، output property و scope identity در AST فعلی وجود ندارند. `QueryDefinition`: **Not currently present** به‌عنوان domain contract؛ `IQueryRenderSelectAst` فقط نزدیک‌ترین render structure است.

برای composition، قرارداد آینده باید مانع از آن شود که Relation Field قبل از validation به یک SQL alias ساده فروکاسته شود. اینکه identity در Relation wrapper/schema قرار گیرد یا Select AST گسترش یابد، unresolved است؛ Candidate C فعلاً توجیه نشده.

## Renderer Contract

Renderer فعلی capability-driven و dialect registry-based است. SELECT renderer فهرست columns را render می‌کند؛ column renderer base column را render می‌کند و در صورت وجود `ColumnAlias`، `As ...` می‌افزاید. Base-column renderer table alias/column یا CTE alias/select strings می‌خواند. Renderer اطلاعات `KClass`, `KProperty`, metadata model، relation owner یا output schema نمی‌خواند.

پس semantic resolution و identity mapping نباید فرض شوند که در Renderer حاضرند. Renderer مسئولیت Relation Field resolution ندارد؛ این مسئولیت و زمان lower شدن به string باید در قرارداد آینده تعیین شود، بدون آنکه renderer به reflection متکی شود.

## Dialect Contract

`MySqlDialect` registry، `IQueryColumnsAst`, `IQueryColumnsBaseAst`, `IQuerySelectAst` و root SELECT AST را به capabilityهای مستقل متصل می‌کند. مفهوم model property و Relation identity به خودی خود dialect-neutral است؛ syntax alias، CTE، quoting و قانونی‌بودن reference در SQL scope dialect concerns هستند. این Plan معماری Dialect را بازطراحی نمی‌کند. Evidence حاضر فقط MySQL SELECT rendering paths را برای symbols یادشده بررسی کرده؛ پشتیبانی dialectهای دیگر از Vision جدید ثابت نشده است.

## Compatibility Impact

String APIهای موجود مانند `tableColumn(alias, name)`, `table(String, alias)` و CTE string reference در APIها باقی‌اند. Typed V2 SELECT API نیز public contract فعلی است. هر Relation API باید به‌صورت افزایشی coexist کند تا V1/V2 consumers شکسته نشوند. افزودن property-based output alias، تغییر semantics `alias(String)` یا بازتعریف CTE naming می‌تواند source/SQL compatibility risk داشته باشد؛ شواهد فعلی دلیلی برای breaking change نمی‌دهد.

## Final Contract

**قرارداد implementation-complete با evidence فعلی قابل صدور نیست.** آنچه منبع ثابت می‌کند:

1. Typed physical reference با `KClass + KProperty1` در Builder resolve می‌شود.
2. منبع database column name برابر `QBColumn.name` است؛ Kotlin property name جایگزین آن نمی‌شود.
3. table name از `QBTable.name` می‌آید؛ table alias و SELECT alias به‌ترتیب در table node و `ColumnAlias` نهایی می‌شوند.
4. AST فعلی SQL-ready strings را نگه می‌دارد، نه physical field identity یا relation output identity.
5. `alias(String)` فقط SQL alias contract موجود است؛ `.as(KProperty)` و Output Field mapping در source نیست.
6. CTE capability موجود است ولی generic QueryRelation، OutputSchema، Relation-as-FROM/JOIN/derived source در source نیست.
7. Relation composition باید ResultSet mapping و execution را بیرون نگه دارد؛ Renderer همچنان از Model reflection مستقل بماند.

قرارداد نهایی هنوز باید صریحاً تعیین کند: (a) identity و ownership مربوط به Relation و Output Field، (b) چگونگی bind شدن Output property به SELECT item، (c) آیا arbitrary SELECT expression جزو scope است، (d) مصرف Relation Field در هر SQL scope، و (e) Relation source با placementهای CTE/FROM/JOIN/derived table چگونه تفکیک می‌شود. این‌ها unresolved هستند؛ در این مرحله هیچ API یا abstractionی برایشان انتخاب نشده است.

## Deferred / Out of Scope

* ResultSet mapping، ساخت خودکار Output instance و serialization.
* CASE، arithmetic/function expression system و universal selectable abstraction، مگر آنکه scope بعدی evidence واقعی ارائه کند.
* پیاده‌سازی یا بازطراحی CTE، derived table، JOIN، Dialect یا Execution Core.
* database introspection، performance/caching و raw SQL escape hatch.
* تغییر source، tests، APIها، dependencies یا refactor.

## Implementation Readiness

`Ready for Traceability`

شواهد V2 یک baseline قوی برای **Physical Field resolution** می‌دهند، اما فلش‌های `SELECT → Output Field → Relation Output Schema → Query Relation → Another Query` هنوز در source پیاده‌سازی یا contract نشده‌اند. API نهایی و ownership relation/source unresolved است؛ بنابراین اجرای Implementation در این مرحله نباید آغاز شود. گزارش Traceability تکمیل‌شده است، اما لازم است این موارد در Decision Closure بعدی تعیین شوند.
