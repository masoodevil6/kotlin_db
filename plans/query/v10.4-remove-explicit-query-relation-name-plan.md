# Plan 10.4 — حذف کامل `relationName` صریح از Queryهای V3

## هدف

حذف کامل `relationName` از قرارداد Query. این سند قرارداد قطعی و محدودهٔ implementation را ثبت می‌کند؛ این نوبت فقط خود Plan را ویرایش می‌کند.

## تصمیم قطعی

- `relationName` از قرارداد Query حذف می‌شود.
- هیچ Query برای تعیین نام runtime خود نباید `override val relationName` تعریف کند.
- `QBQuery.name` نام canonical تعریف Query است و نام runtime پیش‌فرض آن، از جمله `QueryRelation.name` و نام CTE، را تعیین می‌کند.
- در مسیرهایی که caller واقعاً نام را صریحاً به factory می‌دهد، همان نام ورودی صریح runtime name نهایی است و بر `QBQuery.name` و convention مقدم می‌شود.
- در مسیر declaration که نام صریح مستقلی از caller ندارد، نام runtime به‌ترتیب از `QBQuery.name` و سپس convention مجاز resolve می‌شود؛ مقدار resolveشده، default نهایی آن مسیر است.
- `QBQuery.alias` فقط alias پیش‌فرض occurrence/source باقی می‌ماند و جایگزین نام runtime نیست.
- هر چهار Query V3، از جمله سه implementer مستقیم `IQueryRelation`، بدون تعریف یا override `relationName` کار می‌کنند.
- امضاهای factoryهای فعلی و قرارداد نام صریح آن‌ها حفظ می‌شوند. نامی که caller مستقیماً به factory می‌دهد runtime name صریح است و `QBQuery.name` آن را بازنویسی نمی‌کند. helperهای declaration در نبود نام صریح مستقل، نام پیش‌فرض را از `QBQuery.name` و سپس convention resolve می‌کنند.
- این تصمیم خاص Plan 10.4 است: نام runtime اکنون از `QBQuery.name` می‌آید. alias occurrence همچنان مستقل است و سایر بخش‌های Plan 10.3 بازطراحی نمی‌شوند.

## شواهد فعلی Repository

1. `IQueryRelation<P>` در `data_base/query/api/src/main/kotlin/interfaces/relations/IQueryRelation.kt` اکنون `relationName` را الزام می‌کند.
2. `QueryDeclaration<P>` در `data_base/query/builder/src/main/kotlin/relations/QueryDeclaration.kt` همین property را abstract می‌کند و helper پایه آن را به factory می‌دهد.
3. extension فعلی `IQueryRelation<*>.buildQueryRelation(...)` در `QueryRelationBuilder.kt` نیز نام را از `relationName` می‌گیرد.
4. factoryهای `queryRelation(name, block)` و `queryRelation(name, declarationOwner, block)` نام runtime را از ورودی صریح می‌گیرند.
5. `QueryRelation.name` در `QueryRenderSelectBuilder` برای نام CTE، dependency ordering، duplicate-name validation، cycle detection و تشخیص dependency استفاده می‌شود؛ occurrence alias در مسیر `from(...)` جداگانه تعیین می‌شود.
6. هر چهار Query V3 دارای `QBQuery(name, alias)` صریح‌اند. اکنون سه مورد `IQueryRelation` را مستقیم پیاده می‌کنند و `UserDisplayQueryV3` از `QueryDeclaration` ارث می‌برد. مقدارهای فعلی `relationName` با aliasهای V3 برابرند، اما نام‌های منطقی `QBQuery.name` مستقل‌اند.

## قرارداد نهایی نام Query

قاعدهٔ یکسان precedence در کل Plan چنین است:

```text
explicit declaration/factory name → QBQuery.name → class-name convention
```

«نام صریح factory» فقط نامی است که caller مستقیماً در فراخوانی factory موجود می‌دهد. نامی که helper از annotation یا convention resolve می‌کند، ورودی صریح caller محسوب نمی‌شود؛ helper آن را پیش از فراخوانی factory به‌عنوان نام نهایی پیش‌فرض مسیر declaration تعیین می‌کند. Factory پس از دریافت این مقدار، metadata را دوباره resolve نمی‌کند و آن را بازنویسی نمی‌کند.

### مسیر declaration

```text
QBQuery.name صریح
    → نام canonical Query
    → QueryRelation.name و نام CTE

QBQuery.name تنظیم‌نشده
    → class-name convention
    → نام canonical Query
    → QueryRelation.name و نام CTE
```

مقدار صریح خالی برای `QBQuery.name` مطابق قرارداد metadata خطای validation است و نباید به convention سقوط کند. این fallback فقط زمانی اعمال می‌شود که caller در آن مسیر نام صریح مستقلی نداده باشد. Resolution باید با `KClass` و annotation انجام شود و getter هیچ property خروجی اجرا نشود.

### Factoryها

```text
caller مستقیماً فراخوانی می‌کند:
queryRelation(name = explicitName, declarationOwner = QueryType::class, ...)
    → explicitName نام runtime نهایی است
    → QBQuery.name آن را بازنویسی نمی‌کند

helper declaration در نبود نام صریح مستقل:
resolve QBQuery.name → class-name convention مجاز
    → مقدار resolveشده را برای پارامتر اجباری name به factory موجود می‌دهد
    → این مقدار نام نهایی پیش‌فرض مسیر declaration است، نه نام صریحی که caller به factory داده باشد
    → factory آن را مصرف می‌کند و metadata را دوباره resolve یا بازنویسی نمی‌کند

queryRelation(name = explicitName, ...), بدون declarationOwner
    → explicitName نام runtime نهایی است، مطابق رفتار فعلی
```

هر دو overload موجود باقی می‌مانند و امضاهایشان تغییر نمی‌کند. چون factoryها پارامتر `name` را اجباری می‌گیرند، تفاوت در مرز فراخوانی روشن است: فراخوانی مستقیم caller، نام صریح دارد؛ helper declaration ابتدا metadata را resolve می‌کند و سپس نام نهایی پیش‌فرض را به همان factory می‌دهد. factory نباید provenance را حدس بزند، metadata را دوباره resolve کند یا نام صریح caller را با annotation جایگزین کند. overload بدون `declarationOwner` نیز نام صریح ورودی را حفظ می‌کند و annotation/convention را resolve نمی‌کند.

### Occurrence alias

`QBQuery.alias` برای alias پیش‌فرض منبع در occurrence باقی می‌ماند. `from(query, explicitAlias)` همچنان بر آن تقدم دارد. این alias نباید نام CTE یا `QueryRelation.name` را تعیین کند.

## تغییرات موردنیاز برای Plan 10.4

1. حذف `relationName` از `IQueryRelation<P>` و به‌روزرسانی مستندات همان قرارداد.
2. حذف abstract property از `QueryDeclaration<P>`.
3. تغییر helperهای declaration در Builder تا concrete owner را برای resolve کردن نام پیش‌فرض از `QBQuery.name` و سپس convention مجاز به‌کار ببرند و مقدار حاصل را به factory موجود بدهند.
4. تغییر extension فعلی `IQueryRelation<*>.buildQueryRelation(...)` تا نام پیش‌فرض را از owner concrete resolve کند؛ `relationName` نباید در مسیر باقی بماند. نامی که caller مستقیماً به factory می‌دهد همچنان صریح و مقدم است.
5. حذف overrideهای `relationName` از هر چهار Query V3؛ سه Query مستقیم باید بدون این property همچنان از مسیر فعلی declaration قابل ساخت باشند.
6. حفظ امضاهای factoryهای دارای `name` صریح. تست شود که نام caller در فراخوانی مستقیم overload دارای `declarationOwner` بر `QBQuery.name` مقدم است و پس از ورود به factory دوباره resolve نمی‌شود؛ همچنین helper declaration بدون نام صریح مستقل، ابتدا `QBQuery.name` یا convention مجاز را resolve کرده و نام نهایی پیش‌فرض را منتقل می‌کند. overload بدون owner نام صریح ورودی را حفظ می‌کند و metadata را resolve نمی‌کند.
7. حفظ `QueryRelation.name` و استفاده‌های داخلی آن؛ این Plan آن را rename یا حذف نمی‌کند.

هیچ annotation metadata جدیدی اضافه نشود. اگر resolution برای implementer مستقیم بدون تغییر امضای عمومی ممکن نبود، implementation باید در همان نقطه متوقف و مانع فنی مستند شود؛ `QBQuery.alias` نباید به‌عنوان workaround استفاده شود.

## سازگاری و آثار runtime

حذف property از `IQueryRelation` تغییر source و JVM contract عمومی است و implementerهای موجود باید از نظر compilation مهاجرت داده شوند. این Plan ادعای binary compatibility نمی‌کند.

برای V3، نام‌های runtime فعلی مانند `v3_user_display` با `QBQuery.name`های فعلی مانند `user_display_query_v3` متفاوت‌اند. پس از تغییر، `user_display_query_v3` canonical خواهد بود و نام `QueryRelation` و CTE جایگزین نام runtime قبلی می‌شود. همین اثر برای هر چهار Query V3 و هر dependency/nested Query مرتبط باید صریحاً ثبت و با regression test پوشش داده شود. `QBQuery.alias` و alias صریح `from(query, alias)` همچنان occurrence را تعیین می‌کنند و از تغییر نام CTE مستقل می‌مانند.

## آزمون‌های regression لازم

- حذف نیاز به `relationName` در هر چهار Query V3: سه implementer مستقیم و یک subclass از `QueryDeclaration`.
- resolution نام runtime از `QBQuery.name` صریح.
- fallback نام منطقی/runtime به convention برای annotation بدون name.
- خطا برای name خالی صریح.
- جدایی `QBQuery.name` از `QBQuery.alias` و alias صریح occurrence.
- تقدم نام caller در فراخوانی مستقیم factory owner-aware؛ تقدم `QBQuery.name` بر convention در helper declaration بدون نام صریح مستقل؛ حفظ نام صریح overload بدون owner.
- نام CTE، SQL rendering، dependency ordering، duplicate CTE detection و cycle detection.
- nested Query composition در `UserPageQueryV3`.
- Typed Output، declaration owner، SQL alias mapping و عدم اجرای getter.

## معیار پذیرش

- هیچ declaration یا قرارداد Query در scope به `relationName` وابسته نباشد.
- precedence در همهٔ مسیرها یکسان باشد: نام صریح caller در factory، سپس `QBQuery.name`، سپس convention مجاز. در مسیر helper declaration که نام صریح caller ندارد، resolver پیش از فراخوانی factory `QBQuery.name` و سپس convention را انتخاب می‌کند؛ factory آن مقدار نهایی را بدون resolution مجدد مصرف می‌کند.
- factoryهای بدون owner و owner-aware امضا و قرارداد نام صریح خود را حفظ کنند؛ helper declaration مقدار metadata-resolved را برای پارامتر factory فراهم کند.
- `QBQuery.alias` فقط occurrence/source alias را تعیین کند.
- CTE، dependency semantics، Typed Output و execution مطابق تغییر نام runtime تست شوند.
- تست‌ها و buildهای مرتبط واقعاً اجرا و نتیجه گزارش شوند؛ سازگاری binary بدون بررسی جداگانه ادعا نشود.
