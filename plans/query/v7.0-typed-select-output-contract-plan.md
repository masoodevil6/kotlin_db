# Plan 7.0 — Typed SELECT Output و Materialization

## وضعیت

**Decision Closure: بسته‌شده**  
**وضعیت: Implementation Ready**  
**Implementation: هنوز انجام نشده است**

ساختار، بخش‌ها و traceability فعلی Plan حفظ می‌شوند؛ تصمیم‌های معماری این مرحله فقط در بخش‌های مرتبط با SELECT Output Contract ادغام شده‌اند. Plan فقط Typed SELECT Output و materialization نتیجهٔ Smart SELECT را پوشش می‌دهد. این ویرایش source، test، build یا configuration را تغییر نمی‌دهد.

## اصل قطعی

```text
SELECT is the Single Source of Truth.

Alias defines result identity.
execute(DataType.X) defines typed extraction semantics.

If extraction type is not declared by SELECT,
the system must not infer it from outside SELECT.
```

هیچ نوع یا رفتار extraction از schema دیتابیس، metadata دیتابیس، Model/Entity، CTE declaration، نوع ستون جدول، reflection، naming convention، نام alias یا حدس از expression استخراج نمی‌شود.

## 1. Repository Evidence

### SELECT AST و Builder

هر SELECT item با `IQueryColumnsAst` مدل می‌شود. این AST در حال حاضر سه عضو اصلی دارد:

`ColumnMethod`، `Column` و `ColumnAlias`.

`Column` از نوع `IQueryColumnsBaseAst` است و expression/source را نگه می‌دارد. `QuerySelectAst.columns` ترتیب SELECT itemها را حفظ می‌کند. `QueryColumnsBuilder` AST مربوط به expression و alias را روی item جاری ثبت می‌کند.

شواهد source:

* `data_base/query/ast/src/main/kotlin/interfaces/select_interface/column/IQueryColumnsAst.kt`
* `data_base/query/ast/src/main/kotlin/schema/select_schema/column/QueryColumnsAst.kt`
* `data_base/query/ast/src/main/kotlin/interfaces/select_interface/select/IQuerySelectAst.kt`
* `data_base/query/ast/src/main/kotlin/schema/select_schema/select/QuerySelectAst.kt`
* `data_base/query/api/src/main/kotlin/interfaces/api/select_api/column/IQueryColumnsApi.kt`
* `data_base/query/builder/src/main/kotlin/ast/select_builder/column/QueryColumnsBuilder.kt`

در حال حاضر Query AST/API هیچ Query Result `DataType`، `IQueryColumnsApi.execute(DataType)`، یا extraction metadata ندارد. Renderer نیز فقط expression، method و alias را می‌خواند. قرارداد هدف این Plan تصریح می‌کند که `alias(...)` فقط result identity را تعیین می‌کند و `execute(DataType.X)` فقط extraction type صریح را؛ execution type نوع ستون دیتابیس نیست، بلکه قرارداد extraction انتخاب‌شده توسط نویسندهٔ SELECT است.

### مثال مرجع: `A6ExampleSelectV1`

`data_base/query/example/src/main/kotlin/v1/queries/select/A6ExampleSelectV1.kt` هر پنج SELECT item را در AST می‌سازد و برای هرکدام alias می‌گذارد. سپس `executeSmartSelectV1` همان `IQueryRenderSelectApi` را به `IQueryBuilderExecutor` می‌دهد.

مسیر واقعی:

```text
QueryRenderSelectBuilder
    ↓
QuerySelectAst.columns (expression + alias + order)
    ↓
executeSmartSelectV1(query)
    ↓
IQueryBuilderExecutor / QueryConsumer
    ↓
QueryBuilderExecutor
    ↓
IQueryExecute.executeSelect(...)
    ↓
ResultSet
```

فهرست aliasهایی که `executeSmartSelectV1` جداگانه می‌گیرد برای چاپ نمونه استفاده می‌شود؛ این فهرست execution input مستقلی به `IQueryBuilderExecutor` نیست. Executor خود `IQueryRenderSelectApi` و در نتیجه AST کامل SELECT را دریافت می‌کند. پس SELECT AST مسیر موجود و مستقیم انتقال قرارداد output به Smart executor است.

`IQueryBuilderExecutor.first/get` اکنون aliasها را با `requireResultOutputAliases()` اعتبارسنجی می‌کند، سپس فهرست `List<String>` را به materializer داخلی می‌دهد. Materializer metadata ResultSet را با ترتیب/label aliasها مقایسه می‌کند و مقدار را با `ResultSet.getObject(index)` می‌خواند. این `List<String>` فقط alias دارد و execution type ندارد.

### Renderer، BuiltQuery و JDBC boundary

* Renderer، `Column`، `ColumnMethod` و `ColumnAlias` را می‌خواند؛ extraction type نباید SQL را تغییر دهد.
* `BuiltQuery` در `data_base/core/src/main/kotlin/query/reader/BuiltQuery.kt` فقط SQL رندرشده و پارامترها را دارد.
* `QueryBuilderExecutor` پیش از فراخوانی `IQueryExecute`، خود builder/AST را در اختیار دارد.
* `IQueryExecute.executeSelect(...)` همچنان `ExecuteResult<ResultSet>` را در callback زنده تحویل می‌دهد؛ `QueryExecute` Statement و Connection را در scopeهای `use` نگه می‌دارد.
* `getDatabaseServerInfo` و migration consumers مستقیماً ResultSet را مصرف می‌کنند؛ این low-level قرارداد تغییر نمی‌کند.

بنابراین extraction metadata از AST به Smart materializer می‌رسد و نیازی به افزودن آن به `BuiltQuery` یا low-level `IQueryExecute` نیست.

### Existing DataType و Conversion

`MigrationColumnDataType` و subtypeهایش فقط قرارداد نوع ستون DDL/Migration هستند. آن‌ها Query Result type یا JDBC-to-Kotlin extraction contract نیستند و برای Plan 7.0 reuse نمی‌شوند.

در Query Result layer، converter مشترک یا getter strategy موجود نیست. getterهای JDBC پراکنده در testها و migration code precedent برای یک abstraction مشترک نیستند. Smart materializer فعلی از `getObject(index)` استفاده می‌کند.

## 2. Final SELECT Output Contract

هر SELECT item برای Smart materialization قرارداد واحد زیر را در خود SELECT AST نگه می‌دهد:

`source expression`، `result identity / SQL output alias` و `execution type`.

API هدف:

```kotlin
addColumn {
    column { tableColumn("uu", "id") }
    alias("user_id")
    execute(DataType.LONG)
}
```

معنای آن:

```text
source        = uu.id
resultKey     = user_id
executionType = LONG
```

### Alias

* `alias("user_id")` تنها result identity است.
* همان alias کلید `QueryRow` و مقدار مورد انتظار ResultSet column label است.
* alias خالی/مفقود و alias تکراری همچنان با validation موجود رد می‌شود.
* نام ستون، property name، source alias یا نام expression fallback نیست.

### Extraction type

* `execute(DataType.X)` extraction type را روی SELECT item جاری ثبت می‌کند؛ این نام در قرارداد یعنی تعیین روش استخراج برای آن output، نه اجرای مستقل Query.
* برای هر SELECT output که از Smart API و `QueryRow` materialize می‌شود، type الزامی است.
* در اولین مجموعهٔ پشتیبانی‌شدهٔ Plan 7.0، Query-scoped `DataType` شامل `LONG`, `INT`, `STRING` است. نوع‌های دیگر به قرارداد/تست صریح نیاز دارند و خودکار اضافه نمی‌شوند.
* نوع DDL یعنی `MigrationColumnDataType` جدا باقی می‌ماند.

## 3. محل API و Metadata

### DataType

Dependency graph واقعی بررسی شد: `settings.gradle.kts` ماژول‌های `:data_base:query:ast` و `:data_base:query:api` را مستقل include می‌کند؛ `data_base/query/api/build.gradle.kts` به `query:ast` با `implementation(project(...))` وابسته است و `data_base/query/ast/build.gradle.kts` فقط به `core` وابسته است. بنابراین جهت موجود `query:api → query:ast → core` است و dependency معکوس یا cycle بین `query:api` و `query:ast` وجود ندارد. بر اساس این جهت و اینکه metadata متعلق به SELECT AST است، محل قراردادی Query Result enum به نام `DataType`، ماژول `query:ast` است. چون dependency فعلی `query:api → query:ast` از نوع `implementation` است، در implementation باید visibility لازم برای مصرف‌کنندگان public API نیز compile-level بررسی شود؛ این Plan مجوز تغییر dependency configuration را صادر نمی‌کند.

این type **در source فعلی وجود ندارد**؛ این قراردادِ محل و نقش type جدید است، نه گزارش وجود implementation فعلی.

### SELECT item AST

execution type به خود `IQueryColumnsAst`/پیاده‌سازی `QueryColumnsAst` افزوده می‌شود. expression و alias موجود reuse می‌شوند؛ خروجی با یک DTO، registry، schema یا abstraction موازی مدل نمی‌شود. این type صرفاً روش استخراج مقدار ResultSet است؛ هیچ ادعایی دربارهٔ SQL/database column type یا کشف نوع واقعی ستون ایجاد نمی‌کند.

`IQueryColumnsApi` یک متد `execute(dataType: DataType)` عرضه می‌کند و `QueryColumnsBuilder` مقدار را روی SELECT item جاری می‌نویسد. `execute` نباید اجرای JDBC انجام دهد و نباید AST renderer را برای type extraction تغییر دهد.

### انتقال به Executor

Executor کل `IQueryRenderSelectApi` را پیش از dispatch به low-level می‌بیند؛ metadata از همان AST خوانده می‌شود. Materializer به‌جای اتکا به `List<String>` تنها، SELECT itemهای AST را به ترتیب مصرف می‌کند و از هر item alias/type را می‌خواند. برای جلوگیری از contract موازی، type جداگانه‌ای مثل `SelectOutput` لازم نیست؛ `IQueryColumnsAst` خودِ output item است.

`requireResultOutputAliases()` همچنان مسئول validation موجود aliasهاست. Smart materialization علاوه بر آن type هر item را از AST اعتبارسنجی می‌کند. مثال‌هایی که فقط alias list را برای نمایش نگه می‌دارند می‌توانند همان فهرست نمایش را حفظ کنند؛ این فهرست منبع extraction metadata نیست.

### BuiltQuery و low-level API

* `BuiltQuery` تغییر نمی‌کند؛ SQL و parameters مسئولیت آن هستند.
* `IQueryExecute.executeSelect(...)`، `QueryExecute` و `ExecuteResult<ResultSet>` تغییر نمی‌کنند.
* raw low-level مصرف ResultSet همچنان برای callerهای فعلی برقرار است و به Typed SELECT materialization نیاز ندارد.
* APIهای Smart یعنی `IQueryBuilderExecutor.first/get` و `QueryConsumer.first/execute` قرارداد type اجباری را اعمال می‌کنند.

## 4. JDBC Extraction Contract

Materialization در لایهٔ Smart فعلی، یعنی `IQueryBuilderExecutor`، داخل callback زندهٔ `executeSelect` انجام می‌شود. مقدار با index ترتیبی SELECT خوانده می‌شود؛ پیش از آن، metadata/label همان index با alias متناظر تطبیق داده می‌شود. Alias در این مسیر result key و validation label است؛ برای استخراج JDBC از overload نامی استفاده نمی‌شود.

| Query result type | JDBC getter | مقدار غیر NULL در `QueryRow` | SQL NULL |
|---|---|---|---|
| `DataType.LONG` | `ResultSet.getLong(index)` | boxed `Long` | پس از `wasNull()`، `null` |
| `DataType.INT` | `ResultSet.getInt(index)` | boxed `Int` | پس از `wasNull()`، `null` |
| `DataType.STRING` | `ResultSet.getString(index)` | `String` | `null` |

JDBC primitive getterهای long/int برای SQL NULL مقدار صفر می‌دهند؛ بنابراین بررسی `wasNull()` پس از getter الزامی است تا null فعلی `QueryRow` حفظ شود. خطای getter/materialization به‌صورت failure موجود Smart API برمی‌گردد.

این mapping قرارداد extraction است، نه type inference از ResultSet metadata. برای نمونه، SELECT item شمارهٔ ۰ با `alias = user_id` و `type = LONG` از `ResultSet.getLong(1)` خوانده و با کلید `QueryRow["user_id"]` ذخیره می‌شود. alias برای تطبیق label و ساخت result key است؛ getter بر اساس ترتیب SELECT و index یک‌مبنایی JDBC فراخوانی می‌شود، نه با overload نامی مانند `getLong("user_id")`. هیچ database introspection یا schema lookup انجام نمی‌شود.

## 5. Missing Type و Failure

برای Smart materialization، alias معتبر بدون extraction type کافی نیست:

```text
alias exists + execution type missing
= typed materialization unavailable
```

* فقدان alias و alias تکراری همچنان با `IllegalArgumentException` از validation موجود رد می‌شود.
* محل validation باید همان pre-execution boundary فعلی در `IQueryBuilderExecutor.first/get` باشد: هر دو متد ابتدا `queryBuilder.requireResultOutputAliases()` را در یک `try/catch` اجرا می‌کنند و فقط پس از موفقیت آن `execute(...)` را صدا می‌زنند. اعتبارسنجی execution type باید در همان بلوک و کنار alias validation افزوده شود؛ آن را به `materializeQueryRow` یا بعد از دریافت ResultSet منتقل نکنید.
* فقدان type با `IllegalArgumentException` پیش از dispatch به JDBC و پیش از بازشدن connection رد می‌شود؛ failure به callback موجود `ExecuteResult.Failure` تحویل داده می‌شود.
* پیام پایدار و قابل تشخیص:

```text
SELECT output at index <zero-based-index> ('<alias>') must declare an execution DataType
```

* چون validation در مسیر Smart `first/get` قبل از فراخوانی اجرای query است و همانند validationهای Smart به failure تبدیل می‌شود، نتیجه `ExecuteResult.Failure(IllegalArgumentException)` است.
* هیچ fallback ضمنی به `ResultSet.getObject(...)` وجود ندارد.
* هیچ type از alias، expression، schema، Model، CTE یا ResultSet metadata حدس زده نمی‌شود.
* low-level `IQueryExecute.executeSelect` و مصرف دستی ResultSet از این الزام مستثنا هستند؛ آن‌ها قرارداد Smart `QueryRow` نیستند.

---

## 6. QueryRow و Type Safety

`QueryRow` پس از materialization همچنان مقادیر را با alias و `Any?` نگه می‌دارد. کلید lookup فقط alias است و هیچ referenceای به ResultSet، Statement یا Connection نگه‌داری نمی‌شود.

این Plan **runtime typed materialization** را می‌بندد:

```text
DataType.LONG → JDBC long extraction → QueryRow["user_id"] contains Long?
```

این Plan **compile-time typed indexing** را فراهم نمی‌کند. چون `QueryRow.get(alias)` مقدار `Any?` می‌دهد، متغیر استنباط‌شده از `row["user_id"]` compile-time به `Long` تضمین نمی‌شود؛ DTO، property mapping، reflection یا typed key API خارج از scope است.

## 7. Resource Lifecycle و Compatibility

حفظ مسیر موجود:

```text
IQueryBuilderExecutor.first/get
    ↓ validate aliases and execution types before JDBC
IQueryBuilderExecutor.execute(queryBuilder)
    ↓
IQueryExecute.executeSelect(...)
    ↓ ResultSet is live in callback; Statement/Connection scopes remain open
Smart executor materializes each row
    ↓ ResultSet.use closes ResultSet
QueryRow / List<QueryRow> is delivered
    ↓ Statement/Connection use scopes close
```

* Smart consumer هیچ JDBC resourceای دریافت نمی‌کند.
* materialization پیش از بسته‌شدن ResultSet است؛ نتیجه پس از close قابل استفاده است.
* callback low-level داخل catch مربوط به SQLException قرار نمی‌گیرد؛ exception مصرف‌کننده به‌عنوان JDBC failure بازتفسیر نمی‌شود.
* low-level callback/live ResultSet semantics و APIهای `IQueryExecute` حفظ می‌شوند.
* پارامترها، ترتیب binding و rendered SQL تغییر نمی‌کنند؛ execution type وارد SQL یا interpolation پارامتر نمی‌شود.
* Renderer فقط expression و alias را رندر می‌کند.

### Migration اثرگذار

خروجی‌های SELECT که با Smart API materialize می‌شوند و فعلاً فقط alias دارند، باید در declaration خودشان `execute(DataType.X)` بگیرند. این تغییر عمداً مانع تکیهٔ خاموش بر `getObject` می‌شود. SELECTهایی که فقط از low-level API و ResultSet دستی استفاده می‌کنند تحت این migration نیستند.

نمونهٔ مرجع `A6ExampleSelectV1` فعلاً فقط alias می‌گذارد؛ در صورت استفاده از مسیر Smart، هر خروجی‌اش باید type صریح بگیرد. هنگام مهاجرت مثال، نویسنده باید برای هر خروجی type موردنظر را صریحاً در SELECT declaration انتخاب کند. حتی اگر `CteInfoUser` یا fixture/sample data نوعی مانند `Int` نشان دهد، این metadata یا نام‌هایی مثل `cte_user_id` و `cte_user_age` مبنای استنتاج خودکار نیستند؛ انتخاب باید با نوع نتیجه‌ای که نویسنده برای این SELECT قرارداد می‌کند سازگار باشد.

## 8. Scope و موارد خارج از محدوده

### داخل Scope اجرایی Plan 7.0

1. Query-scoped `DataType` با مقادیر اولیه `LONG`, `INT`, `STRING` در `query:ast`.
2. ثبت execution type روی همان SELECT item AST موجود.
3. متد `IQueryColumnsApi.execute(DataType)` و ثبت آن توسط `QueryColumnsBuilder`.
4. اعتبارسنجی type اجباری در Smart `first/get` پیش از JDBC.
5. نگاشت JDBC getter و حفظ SQL NULL با `wasNull()`.
6. materialization در `IQueryBuilderExecutor` و حفظ alias به‌عنوان تنها QueryRow key.
7. افزودن type صریح به Smart SELECT examples و tests وابسته.
8. regression tests برای getters، null، missing type، alias behavior، JDBC lifecycle و low-level compatibility.

### خارج از Scope

* Relations و Plan 4.0
* DTO/Entity mapping، reflection، code generation، ORM
* generic Result Framework، registry یا global mapping
* compile-time typed QueryRow indexing
* type inference از schema/metadata/model/CTE/alias/expression
* `DataType` migration/DDL
* تغییر گسترده INSERT/UPDATE/DELETE
* تغییر `BuiltQuery`، `IQueryExecute`، `QueryExecute` یا lifecycle قرارداد low-level
* GETTER typeهای دیگر غیر از `LONG`, `INT`, `STRING` تا وقتی قرارداد و تست مشخصی برایشان اضافه شود.
