# Plan 4.0: ردیابی قرارداد Expression و SELECT Item

## وضعیت

`Ready for Traceability`

---

## هدف

یک تحلیل کامل Traceability و Contract Analysis برای مرحلهٔ بعدی توسعهٔ Query Builder انجام بده.

پرسش اصلی:

> آیا معماری فعلی Query Builder می‌تواند انواع مختلف SELECT expression را با نام SQL خروجی مشخص‌شده توسط `alias(...)` render و در Relation مصرف کند؟ اگر نه، کوچک‌ترین تغییر مبتنی بر evidence چیست؟

این مرحله فقط برای بررسی repository، trace کردن مسیرها و طراحی Contract است. هیچ implementation انجام نده.

---

## Vision

Vision اصلی این مسیر را دنبال می‌کند:

```text
Physical Field
      │
      ▼
SELECT ITEM
      │
      ▼
SQL Output Name (`alias(...)`)
      │
      ▼
Query Relation
      │
      ▼
Query Relation
      │
      ▼
Consumer Query
```

اصل معماری:

> هر SELECT item در Relation باید یک SQL output name صریح و غیرخالی با `alias(...)` داشته باشد.

انواع بالقوهٔ SELECT item:

```text
Physical Column
Aggregate
Arithmetic Expression
CASE Expression
Function Expression
Relation Output by SQL name
```

این‌ها فقط candidateهای Vision هستند. فرض نکن که همه باید در Plan 4.0 Adopt شوند.

---

## وابستگی به Plan 3.0

قرارداد اصلاح‌شدهٔ Plan 3.0 مفاهیم `QueryRelation` و Relation identity را حفظ می‌کند، اما `OutputSchema`، `OutputField`، `output(...)` و Output property identity را حذف کرده است. `alias(...)` تنها نام خروجی SELECT است و Relation consumption با همان SQL output name انجام می‌شود. Plan 4.0 باید همین قرارداد را مبنا بگیرد:

```text
alias(...)
    ↓
SQL output name
    ├── ResultSet lookup
    └── Relation consumption
```

برای مصرف خروجی Relation از SQL output name استفاده می‌شود:

```text
relationColumn(relation, "sql_output_name")
```

هویت Relation مستقل از نام SQL خود Relation است؛ برای فیلد خروجی، identity جداگانه‌ای از SQL name وجود ندارد:

```text
Relation Identity = Relation handle identity
Relation Output   = SQL output name selected by alias(...)
```

`output(...)` و `.as(...)` API نیستند و نباید ایجاد یا بازگردانده شوند. `alias(...)` تنها قرارداد نام‌گذاری خروجی باقی می‌ماند.

## Physical Column Analysis

مسیر موجودی مانند زیر را بررسی کن:

```kotlin
column(UserModelV2::id)
```

API، AST، Builder، Renderer، type metadata و alias را از source واقعی trace کن. مشخص کن:

* physical column چگونه resolve می‌شود و نام database از کجا می‌آید
* در کدام AST field نگهداری می‌شود
* Renderer آن را چگونه render می‌کند
* type Kotlin در این مسیر چه نقشی دارد
* alias پیش‌فرض و alias صریح چگونه تعیین می‌شوند
* SQL output alias چگونه نام خروجی را تعیین می‌کند و در Relation مصرف می‌شود
* آیا مسیر فعلی باید بدون تغییر باقی بماند

---

## Aggregate Analysis

حداقل aggregateهای زیر را بررسی کن:

```text

SUM
AVG
MIN
MAX
```

برای هر مورد API، AST representation، Builder، Renderer، type، nullability و SQL alias را trace کن. مشخص کن:

* aggregate چگونه در API ساخته می‌شود
* آیا از همان SELECT item infrastructure مربوط به column استفاده می‌کند
* آیا واقعاً expression semantic مستقلی است یا modifier روی column AST
* type خروجی از کجا می‌آید و آیا در source تعیین شده است
* nullability چگونه مدل می‌شود
* aggregate خروجی با `alias(...)` چگونه نام‌گذاری و در Relation مصرف می‌شود

اگر implementation محدود یا ناقص است، دقیقاً evidence و محل آن را ثبت کن.

## Relation Output Name Analysis

این مسیر را بررسی کن:

```text
SELECT item
    ↓ alias("order_count")
SQL output name: order_count
    ↓ relationColumn(relation, "order_count")
Relation consumer
```

مشخص کن:

* alias خروجی در AST کجا ذخیره می‌شود
* آیا Relation consumer همان نام SQL را resolve می‌کند
* آیا alias صریح و غیرخالی برای هر خروجی Relation enforce می‌شود
* آیا alias تکراری و نام خروجی ناشناخته رد می‌شود

Use case مفهومی زیر را بررسی کن، بدون اینکه پشتیبانی آن را از قبل فرض کنی:

```text
UserOrderStats.Output::orderCount
            ↓
       orderCount * 10
            ↓
ImportantUsers.Output::score
```

## Arithmetic Expression Analysis

بررسی کن آیا source فعلی expressionهایی مانند موارد زیر را پشتیبانی می‌کند:

```text
orderCount * 10
amount + tax
price * quantity
```

API، AST، Builder، Renderer، type handling، nullability، parameter handling، operator precedence و parentheses را بررسی کن. اگر چنین infrastructureای وجود ندارد، فقط آن را با evidence ثبت کن؛ بدون evidence implementation یا abstraction پیشنهاد نده.

## CASE Expression Analysis

بررسی کن آیا CASE expression بالفعل وجود دارد، برای نمونه:

```sql
CASE
    WHEN age >= 18 THEN 'adult'
    ELSE 'minor'
END
```

condition AST، expression AST، THEN/ELSE value representation، type، nullability، renderer، parameter binding و SQL alias را trace کن. اگر CASE به Expression AST جدید وابسته است، این dependency و دلیل آن را ثبت کن.

## Function Expression Analysis

پشتیبانی فعلی از functionهای SQL در SELECT را برای نمونه‌های زیر بررسی کن:

```text
COALESCE(...)
CONCAT(...)
LOWER(...)
UPPER(...)
```

مشخص کن:

* function infrastructure فعلی وجود دارد یا نه
* function name و argumentها چگونه مدل می‌شوند
* type خروجی چگونه تعیین می‌شود
* dialect rendering چگونه انتخاب می‌شود
* آیا evidence از generic function framework پشتیبانی می‌کند یا capabilityهای مستقل کافی‌اند

این‌ها فعلاً فقط موضوع Traceability هستند. generic function framework را بدون evidence لازم پیشنهاد نده.

## SELECT Item Semantic Analysis

بررسی کن آیا repository فعلی عملاً semantic مشترکی برای SELECT item دارد. candidateها:

```text
Column
Aggregate
Relation output by SQL name
Arithmetic
CASE
Function
```

مشخص کن آیا همه از نظر معنایی SELECT item هستند و آیا این اشتراک در source به abstraction موجودی متکی است.

این رویکردها را مقایسه کن:

### Candidate A: ASTهای مستقل

Physical Column، Aggregate، CASE، Arithmetic و Function مستقل بمانند و `alias(...)` به‌عنوان نام خروجی بررسی شود؛ Output binding وجود ندارد.

### Candidate B: SelectItem مشترک

```text
SelectItem
├── PhysicalColumn
├── Aggregate
├── RelationOutput
├── Arithmetic
├── Case
└── Function
```

بررسی کن `SelectItem` abstraction semantic واقعی است یا فقط برای کاهش تعداد classها ساخته می‌شود.

### Candidate C: Expression AST مشترک

```text
Expression
├── Column
├── Aggregate
├── RelationField
├── Arithmetic
├── Case
└── Function
```

فقط با evidence واقعی آن را Adopt یا Reject کن. همچنین بررسی کن:

* آیا Predicate فعلی نیز Expression محسوب می‌شود
* SELECT expression و WHERE expression semantic مشترک دارند
* ترکیب آن‌ها coupling نامناسب ایجاد می‌کند یا نه
* generic بودن لازم است یا نه
* type system قابل نگهداری است یا نه
* dialect rendering ساده‌تر یا پیچیده‌تر می‌شود

صرفاً برای کاهش تعداد classها abstraction مشترک نساز؛ اگر abstraction مشترک justified نیست، ASTهای مستقل را ترجیح بده.

## Output Name Analysis

قرارداد اصلاح‌شدهٔ Plan 3.0 حفظ شود:

```text

    ↓ alias("sql_output_name")
SQL output name
    ├── ResultSet lookup
    └── Relation consumption
```

برای هر SELECT item بررسی کن آیا API و AST موجود alias را به‌عنوان SQL output name حفظ می‌کنند و همان نام را برای Relation consumption می‌توانند resolve کنند:

```text
Physical Column
Aggregate
Relation pass-through output
Arithmetic
CASE
Function
```

اگر نام‌گذاری/مصرف با alias موجود پوشش داده نمی‌شود، دلیل را با evidence توضیح بده. `OutputField`، mapping یا generic abstraction نساز. `.as(...)` API نساز.

## Alias Boundary

قرارداد alias اصلاح‌شدهٔ نسخهٔ 3.0 را حفظ کن:

```kotlin
alias("sql_name")
```

`alias(...)` نام SQL خروجی است و هم ResultSet lookup و هم Relation consumption از همین نام استفاده می‌کنند:

```text
COUNT(id)
    ↓ alias("order_count")
SQL output name: order_count
    ├── ResultSet lookup: "order_count"
    └── relationColumn(relation, "order_count")
```

در این نمونه هیچ Output property identity وجود ندارد. بررسی کن alias برای هر candidate چگونه تعیین و به SQL منتقل می‌شود. Relation output باید alias غیرخالی داشته باشد.

* آیا Builder اکنون type inference انجام می‌دهد
* آیا Output property type authoritative است یا صرفاً metadata
* آیا SQL type inference وجود دارد یا لازم فرض می‌شود

اصل Plan 3.0 را verify کن: Output type/nullability metadata است؛ SQL type inference و Result Mapping خارج از Contract است. اگر این اصل برای candidateها قابل حفظ است، حفظ شود؛ اگر نه، مرز اختلاف و evidence را ثبت کن.

## Parameter Handling

بررسی کن expressionهای دارای parameter چگونه می‌توانند پشتیبانی شوند، از جمله:

```text
price * :taxRate
```

و:

```sql
CASE
    WHEN age >= :adultAge THEN ...
END
```

در صورت وجود evidence، مالکیت parameter، ترتیب، parameterهای expression تو‌در‌تو، پارامترهای Relation dependency، رفتار duplicate parameter و سازگاری با `QueryExecute` را trace کن.

اگر Expression در Plan 4.0 Adopt نشود، parameter handling آن را Deferred ثبت کن و پشتیبانی فرضی نساز.

## SQL Rendering

مسیر Renderer فعلی برای SELECT itemها را بررسی کن:

* physical column
* aggregate
* alias
* relation column
* expressionهای احتمالی

مرز معماری را حفظ کن:

```text
Builder
    ↓

```

Renderer مسئول semantic resolution، Kotlin reflection، Model metadata یا Relation identity نباشد. اگر abstraction تازه‌ای لازم است، مشخص کن resolution و validation چگونه در Builder باقی می‌مانند.

## Dialect Contract

source مربوط به MySQL dialect، MariaDB dialect، capabilityهای موجود و rendering مربوط به function، aggregate، CASE و operator را بررسی کن. مشخص کن syntaxها کجا مشترک‌اند و کجا تفاوت دارند.

سازگاری database را از local DB استنتاج نکن. اگر minimum supported database version در repository صریحاً مشخص نشده، دقیقاً ثبت کن:

```text
Compatibility target: در repository مشخص نشده است
```

## Result Mapping Boundary

Result Mapping را با Expression architecture یکی نکن. این دو مسیر جدا هستند:

```text
Query Definition
      ↓
SELECT / Relation Output Schema
```

```text
ResultSet
      ↓
Result Mapper
      ↓
Output Model
```

بررسی کن Expression architecture واقعاً به Result Mapping dependency دارد یا نه. اگر evidence چنین dependencyای نشان نمی‌دهد، Result Mapping را خارج از Scope ثبت کن.

## Final Contract

Final Contract را فقط وقتی ارائه کن که تصمیم‌های لازم بسته شده باشند. Contract باید مشخص کند:

* کدام expressionها در Plan 4.0 Adopt می‌شوند و کدام Deferred هستند
* SELECT Item semantic model چیست
* آیا abstraction مشترک لازم است یا نه
* SQL output name چگونه با `alias(...)` تعیین و در Relation مصرف می‌شود
* alias چگونه عمل می‌کند
* type/nullability چگونه مدیریت می‌شود
* parameter handling چیست یا چرا Deferred است
* مرز Renderer و Dialect کجاست
* سازگاری با Plan 3.0 چگونه حفظ می‌شود
* test plan و implementation boundary چیست

اگر یک تصمیم معماری مهم unresolved است، Final Contract را `Implementation Ready` اعلام نکن.
