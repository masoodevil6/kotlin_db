# Plan 12.1 — بررسی Resolution مربوط به Qualifier خروجی CTE

## وضعیت

**فقط بررسی معماری؛ مجوز پیاده‌سازی صادر نشده است.**

Plan 12.0 بسته است. این Plan فقط رفتار qualifier در خروجی‌های typed CTE را بررسی می‌کند و کار پذیرفته‌شدهٔ Plan 12.0 را باز نمی‌کند.

## مسئله

نمونهٔ فعلی V3 می‌تواند SQL زیر را تولید کند:

```sql
WITH user_display_query_v3 AS (
    SELECT ...
)
SELECT
    user_display_query_v3.age AS age
FROM user_display_query_v3 AS v3_user_display
```

در این حالت، source در scope مصرف‌کننده با alias `v3_user_display` شناخته می‌شود؛ پس ارجاع به ستون باید از همان alias استفاده کند:

```sql
WITH user_display_query_v3 AS (
    SELECT ...
)
SELECT
    v3_user_display.age AS age
FROM user_display_query_v3 AS v3_user_display
```

عبارت `cteOutput(UserDisplayQueryV3::age)` باید CTE occurrence قابل‌مشاهده در scope کوئری مصرف‌کننده را qualifier قرار دهد؛ qualifier موردنظر، alias SQL resolveشدهٔ همان occurrence است، نه نام runtime تعریف CTE.

## اصول معماری

مفاهیم زیر مستقل از یکدیگرند و باید در بررسی از هم تفکیک شوند:

- **نام runtime مربوط به CTE:** شناسهٔ تعریف CTE در عبارت SQL `WITH`.
- **alias پیش‌فرض CTE:** alias حاصل از metadata برای occurrence مربوط به CTE.
- **alias صریح occurrence:** aliasی که DSL کوئری مصرف‌کننده برای همان source تعیین می‌کند، اگر API فعلی از آن پشتیبانی کند.
- **نام منطقی Property خروجی:** نام Property typed تعریف‌شده برای خروجی CTE.
- **SQL alias خروجی:** نامی که برای ستون خروجی در SQL منتشر می‌شود.

قاعدهٔ هدف برای resolve کردن qualifier یک CTE occurrence:

1. اگر DSL کوئری مصرف‌کننده برای همان occurrence alias صریح تعیین کرده باشد، از آن استفاده شود.
2. در غیر این صورت، از alias پیش‌فرض resolveشدهٔ همان occurrence استفاده شود.
3. اگر source در SQL alias دارد، صرفاً به این دلیل که نام runtime CTE در دسترس است، به آن نام برنگرد.

این قاعده موضوع بررسی است؛ مجوز افزودن API جدید یا تغییر metadataهای نامرتبط محسوب نمی‌شود.

## موارد بررسی

1. مسیر `cteOutput(property)` را از API عمومی تا resolution metadata، ساخت AST و SQL rendering دنبال کن.
2. مسیر `from { query(declaration) }` را ردیابی کن و مشخص کن `QBQuery.name`، `QBQuery.alias` و alias صریح DSL چگونه منتقل می‌شوند.
3. نقطهٔ دقیق دسترسی، از دست‌رفتن یا جایگزینی alias occurrence را پیدا کن.
4. تعیین کن منشأ رفتار در metadata resolution، نمایش AST، composition در Builder یا rendering است.
5. مسیر qualifier ستون‌های عادی Model را بررسی و با typed CTE output مقایسه کن.
6. تست‌های موجود، به‌ویژه `V3QueryRuntimeNameTest`، را بررسی و کوچک‌ترین regression test لازم برای بازتولید مشکل را مشخص کن.
7. رفتار موردانتظار را برای این حالت‌ها تعیین کن:
   - استفاده از alias پیش‌فرض CTE؛
   - override کردن alias occurrence از طریق DSL؛
   - تفاوت نام runtime CTE و alias پیش‌فرض آن؛
   - استفاده از یک تعریف CTE در بیش از یک occurrence با aliasهای متفاوت، اگر API فعلی چنین استفاده‌ای را پشتیبانی می‌کند.
8. بررسی کن این رفتار با قواعد metadata پذیرفته‌شده و تصمیم‌های Plan 10.4 و Plan 12.0 تعارض نداشته باشد.

## محدودیت‌ها

- بررسی فقط خواندنی است؛ کد، تست، مستندات یا وضعیت Git را تغییر نده.
- کار پذیرفته‌شدهٔ Plan 12.0 را باز نکن.
- API عمومی را rename نکن و abstraction عمومی metadata اضافه نکن.
- AST، Executor، `QueryRow` و Materializer را تغییر نده. اگر بررسی نشان داد تغییری در هرکدام ضرورت اجتناب‌ناپذیر دارد، آن را جداگانه با شواهد گزارش کن و برایش مجوز بگیر.
- تفاوت `cteOutput(...)` با `cteColumn(alias, selectName)`، یعنی API SQL-facing، حفظ شود.
- تست یکپارچه‌سازی نیازمند دیتابیس را بدون پیکربندی و مجوز اجرا نکن.
- پیاده‌سازی راه‌حل در این Plan مجاز نیست.

## خروجی‌های الزامی

1. تحلیل علت ریشه‌ای همراه مسیر دقیق فایل‌ها، symbolها و شواهد.
2. ردیابی مقدار metadata و alias در هر مرحلهٔ مسیر ساخت Query.
3. مشخصات کوچک‌ترین regression test و SQL مورد انتظار.
4. پیشنهاد محدود برای Plan 12.1، شامل فایل‌های احتمالی، معیارهای پذیرش، ریسک‌های سازگاری و اعتبارسنجی‌های به‌تعویق‌افتاده.
5. توصیهٔ روشن دربارهٔ اینکه مشکل با AST و معماری rendering فعلی قابل‌حل است یا به تصمیم طراحی جداگانه نیاز دارد.

پس از ارائهٔ بررسی و پیشنهاد متوقف شو؛ هیچ اصلاحی را اجرا نکن.
