## ۲. قرارداد هدف

### ۲.۱ تنها entry point در SELECT

`IQueryRenderSelectApi` باید تنها این overload عمومی `from` را داشته باشد:

```kotlin
fun from(
    blockTable: IQueryTableApi.() -> Unit
): IQueryRenderSelectApi
```

overload عمومی زیر حذف می‌شود و رفتار آن از راه `IQueryTableApi.query(...)` درون همان block قابل دسترسی خواهد بود:

```kotlin
fun from(
    relation: QueryRelation,
    alias: String? = null
): IQueryRenderSelectApi
```

حذف این overload، `QueryRelation` یا مسیر داخلی composition آن را حذف نمی‌کند؛ فقط انتخاب Query منبع را به DSL یکپارچهٔ `from { ... }` منتقل می‌کند.

### ۲.۲ شکل هدف `IQueryTableApi`

```kotlin
interface IQueryTableApi : IQueryApi<IQueryTableAst> {

    fun table(table: String): IQueryTableApi

    fun table(
        blockQuery: IQueryRenderSelectApi.() -> Unit
    ): IQueryTableApi

    fun <T : IModelBase> model(
        model: KClass<T>
    ): IQueryTableApi

    fun <P> query(
        declaration: IQueryRelation<P>
    ): IQueryTableApi

    fun cte(cte: String): IQueryTableApi

    fun alias(alias: String): IQueryTableApi
}
```

این امضا قرارداد هدف است، نه ادعای پشتیبانی فعلی. Declaration نمونه‌سازی‌شده و پارامترهای bound‌شده به آن را دریافت می‌کند؛ متد `query` پارامتر جداگانه نمی‌گیرد. قرارداد فعلی `IQueryRelation<P>` این اتصال را فراهم نمی‌کند و تغییر حداقلی پیشنهادی در بخش ۷ ثبت شده است. هیچ سازنده، مقدار پارامتر یا مسیر reflection ضمنی فرض نشده است.

### ۲.۳ چهار روش منبع

```kotlin
from {
    table("users")
    alias("u")
}
```

```kotlin
from {
    model(UserModel::class)
    alias("u")
}
```

```kotlin
from {
    table {
        select {
            // تعریف ستون‌های خروجی
        }
        from {
            table("users")
        }
        // سایر بخش‌های پشتیبانی‌شده SELECT
    }
    alias("q")
}
```

```kotlin
from {
    query(
        UserDisplayQueryV3(
            UserDisplayQueryV3.RelationFilters(
                userId = 10,
                minAge = 18,
            )
        )
    )
    alias("q")
}
```

تفاوت قراردادها:

- `table(String)` نام خام جدول را انتخاب می‌کند.
- `model(KClass<T>)` منبعی با metadata مربوط به Model انتخاب می‌کند؛ نام API از `table(KClass<T>)` به `model(KClass<T>)` تغییر می‌کند.
- `table(blockQuery)` یک SELECT داخلی را با API استاندارد SELECT تعریف می‌کند و آن را inline در FROM قرار می‌دهد.
- `query(declaration)` یک نمونهٔ ازپیش‌ساخته‌شدهٔ `IQueryRelation<P>` را می‌گیرد. پارامترهای `P` هنگام ساخت declaration به آن متصل‌اند؛ فراخواننده آن‌ها را دوباره به `query` نمی‌دهد.
- `cte(String)` و `alias(String)` باقی می‌مانند.
- `alias(String)` نام occurrence است. این مقدار نه نام تعریف Query است و نه نام CTE؛ برای `table(blockQuery)` alias پس از پرانتزبندی SELECT داخلی در منبع بیرونی اعمال می‌شود.

- renderer بررسی‌شدهٔ MySQL در `data_base/query/renderer/src/main/kotlin/nodes/select_nodes/table/MySqlQueryTableCapability.kt` فقط مقدار رشته‌ای table یا CTE و alias آن را رندر می‌کند.

نتیجه: inline SELECT در FROM با AST/renderer فعلی MySQL قابل نمایش نیست. برای تحقق قرارداد هدف باید AST منبع بتواند SELECT فرزند را نگه دارد و renderer آن را به صورت `(SELECT ...)` به‌همراه alias occurrence تولید کند. این نیاز مستقیم همین DSL است و در محدودهٔ Plan منظور می‌شود؛ نباید با CTE نام‌دار جایگزین شود.

### ۳.۳ WITH و ساخت SELECT تو‌در‌تو

API موجود در `data_base/query/api/src/main/kotlin/interfaces/api/select_api/withs_item/IQueryWithsItemApi.kt` این overload را ارائه می‌دهد:

```kotlin
fun with(
    withName: String,
    blockWith: IQueryRenderSelectApi.() -> Unit
): IQueryWithsItemApi
```

در `data_base/query/builder/src/main/kotlin/ast/select_builder/withs_item/QueryWithsItemBuilder.kt`، پیاده‌سازی:

1. `QueryRenderSelectAst` تازه می‌سازد؛
2. `QueryRenderSelectBuilder(params, ast)` را با همان فهرست mutable پارامترها اجرا می‌کند؛
3. AST نهایی را در `IQueryWithsItemAst.withBody` قرار می‌دهد.

این الگو برای ساخت Query داخلی، اجرای همان DSL SELECT و اشتراک فهرست پارامترها مبنای reuse است. اما `WITH` خودش منبع FROM نیست: نام CTE لازم دارد و بدنه در `withBody` ذخیره می‌شود.

Builder تو‌در‌توی `QueryRenderSelectBuilder` contextهای داخلی خودش را می‌سازد. در source فعلی، فراخوانی `from(QueryRelation, alias)` در همان builder relation dependencyها را مرتب و CTEهای لازم را در AST داخلی ثبت می‌کند. پس از حذف overload عمومی، این مسیر باید به helper داخلی composition منتقل شود تا `IQueryTableApi.query(...)` بتواند همان رفتار را مصرف کند.

### ۳.۴ Query declaration و runtime composition

- `data_base/query/api/src/main/kotlin/interfaces/relations/IQueryRelation.kt` قرارداد فعلی را تعریف می‌کند: `IQueryRelation<P>.queryRelation(params: P): QueryRelation`. در آن فعلاً پارامتر bound‌شده روی declaration ذخیره یا از آن قابل‌خواندن نیست.
- `data_base/query/builder/src/main/kotlin/relations/QueryDeclaration.kt` کلاس پایهٔ اختیاری `QueryDeclaration<P>` است که `IQueryRelation<P>` را پیاده می‌کند.
- `QueryDeclaration` در `query:builder` است، در حالی که `IQueryTableApi` در `query:api` است.
- `data_base/query/api/src/main/kotlin/interfaces/relations/QueryRelation.kt` runtime abstraction را با `name`, `definition` و `dependencies` نگه می‌دارد.
- factoryها و `BuiltQueryComposition` در `data_base/query/builder/src/main/kotlin/relations/QueryRelationBuilder.kt` قرار دارند. `queryRelation(name, block)` و overload دارای `declarationOwner` نام می‌گیرند؛ extension روی `IQueryRelation<*>` نیز با فراخوانی declaration به نام runtime می‌رسد.
- `QueryRenderSelectBuilder.from(QueryRelation, alias)` در `data_base/query/builder/src/main/kotlin/ast/select_builder/query_render_select/QueryRenderSelectBuilder.kt` relation را در `QuerySourceContext` ثبت می‌کند، dependency closure را مرتب می‌کند، duplicate CTE name و cycle را بررسی می‌کند، relation را به CTE AST تبدیل می‌کند و پارامترهای bound را به query والد اضافه می‌کند.

### ۳.۵ Declaration، پارامترها و فراخوانندگان

`UserDisplayQueryV3` در `data_base/query/example/src/main/kotlin/v3/queries/relations/UserDisplayQueryV3.kt` از `QueryDeclaration<UserDisplayQueryV3.RelationFilters>` مشتق می‌شود و این امضا را دارد:

```kotlin
override fun queryRelation(params: RelationFilters): QueryRelation
```

`RelationFilters` آن شامل `userId` و `minAge` است؛ مقادیر غیر null در `queryRelation(params)` به SQL parameter تبدیل می‌شوند. در وضعیت فعلی، فیلترها به متد داده می‌شوند و در نمونهٔ declaration نگهداری نمی‌شوند. برای syntax هدف، نمونه باید آن‌ها را هنگام ساخت دریافت و نگه دارد؛ وجود default value در فیلدهای data class به‌تنهایی سازوکار ذخیره‌سازی یا بازیابی از declaration ایجاد نمی‌کند.

سه Query نمونهٔ دیگر یعنی `UserStatsQueryV3`, `UserPhoneQueryV3` و `UserPageQueryV3` در فایل‌های هم‌نام زیر `data_base/query/example/src/main/kotlin/v3/queries/relations/` مستقیماً `IQueryRelation<P>` را پیاده می‌کنند، نه `QueryDeclaration<P>`. هر چهار declaration در وضعیت فعلی پارامتر را به `queryRelation(params)` می‌دهند؛ هیچ‌یک پارامترها را مطابق syntax هدف در خود instance نگه نمی‌دارد.

call siteهای V3 اکنون declaration را مستقیماً می‌سازند و پارامتر را ارسال می‌کنند؛ نمونه‌ها:

- `data_base/query/example/src/main/kotlin/v3/queries/select/A1ExampleSelectV3.kt`
- `A2ExampleSelectV3.kt` تا `A7ExampleSelectV3.kt` در همان پوشه
- nested dependency در `data_base/query/example/src/main/kotlin/v3/queries/relations/UserPageQueryV3.kt`

نمونهٔ A7 اکنون به‌صورت `UserDisplayQueryV3().queryRelation(UserDisplayQueryV3.RelationFilters())` عمل می‌کند. در قرارداد هدف، call site باید `RelationFilters` را هنگام ساخت declaration بدهد و سپس خود declaration را به `query(...)` ارسال کند؛ پارامتر نباید در هر دو مرحله جداگانه داده شود.

در source بررسی‌شده، generic factory برای instantiate کردن `KClass<T>` وجود ندارد. این مانع با قرارداد هدف instance-based رفع می‌شود، اما اتصال پارامتر به instance همچنان نیازمند تغییر declaration contract است؛ defaultهای `RelationFilters` به‌تنهایی جایگزین آن تغییر نیستند.

### ۳.۶ Dependency graph و محدودهٔ call siteها

`data_base/query/api/build.gradle.kts` به `core` و `query:ast` وابسته است. `data_base/query/builder/build.gradle.kts` به `core`, `query:ast` و `query:api` وابسته است؛ وابستگی معکوس `query:api → query:builder` وجود ندارد.

در نتیجه امضای هدف قبلی زیر، اگر `QueryDeclaration` در `query:builder` بماند، در `IQueryTableApi` متعلق به `query:api` قابل ارجاع نیست:

```kotlin
T : QueryDeclaration<*>
```

گزینهٔ `QueryDeclaration` برای API نهایی انتخاب نمی‌شود. استفاده از `IQueryRelation<P>` موجود در `query:api` وابستگی معکوس ایجاد نمی‌کند؛ بااین‌حال، دسترسی به پارامترهای متصل‌شده همچنان نیازمند تغییر قرارداد آن interface مطابق بخش ۷.۱ است.

call siteهای `table(KClass)` در v2، builder tests و nested queryها موجودند؛ در API هدف باید به `model(KClass)` مهاجرت کنند. call siteهای `from(QueryRelation, alias)` شامل A1 تا A7 نسخهٔ V3، declarationهای تو‌در‌تو و تست‌های `QueryRelationContractTest`, `TypedRelationPropertyTest` و تست‌های مرتبط هستند. این call siteها باید به `from { query(declarationWithBoundParams); alias(...) }` مهاجرت داده شوند.

## ۵. الزامات implementation بر حسب لایه

### ۵.۱ API

- `IQueryRenderSelectApi` فقط block-based `from(IQueryTableApi.() -> Unit)` را نگه دارد.
- از `IQueryTableApi` overloadهای هدف `table(String)`, `table(blockQuery)`, `model(KClass)`, `query(IQueryRelation<P>)`, `cte(String)`, `alias(String)` را ارائه کند.
- `IQueryTableApi` باید فقط به `IQueryRelation<P>` در `query:api` وابسته باشد، نه به `QueryDeclaration` در `query:builder`؛ دسترسی به پارامتر bound‌شده از طریق قرارداد مشترک `IQueryRelation<P>` انجام شود.

### ۵.۲ Builder و composition

- `QueryTableBuilder` همچنان مسیر مشترک raw/Model/CTE و alias باشد؛ API Model از `table(KClass)` به `model(KClass)` منتقل شود.
- `table(blockQuery)` یک `QueryRenderSelectBuilder` با AST فرزند بسازد، همان lambda استاندارد را اجرا کند و نتیجه را روی source AST ثبت کند.
- QueryRelation registration، dependency closure، CTE ordering و bound-param propagation باید از منطق فعلی `QueryRenderSelectBuilder.from(QueryRelation, alias)` reuse شود؛ دو مسیر مستقل composition ایجاد نشود. چون `QueryTableBuilder` اکنون `QuerySourceContext` والد را دریافت نمی‌کند، حداقل handoff لازم این است که منبع Query و alias نهایی را در طول block نگه دارد و `QueryRenderSelectBuilder.from(block)` پس از پایان block آن را به یک helper داخلی مشترک برای composition تحویل دهد.
- چون `QueryTableBuilder` در CRUD و JOIN نیز استفاده می‌شود، `query(...)` فقط در SELECT FROM باید قابل اجرا باشد. برای contextهای دیگر باید رفتار صریح (رد با پیام روشن یا API wiring محدود) تعیین شود؛ نباید SQL CRUD/JOIN تغییر کند.
- alias ممکن است پیش یا پس از انتخاب source بیاید؛ برای Query و inline source باید alias نهایی همان occurrence اعمال شود و هرگز به‌عنوان Query definition/CTE name مصرف نشود.

### ۵.۳ AST و renderer

- `IQueryTableAst` و `QueryTableAst` باید بتوانند nested SELECT AST را نگه دارند، بدون ادغام آن با فیلد `table` یا `cte` رشته‌ای.
- renderer MySQL باید nested SELECT را در FROM داخل پرانتز رندر و alias occurrence را روی source بیرونی قرار دهد.
- مسیرهای raw table و CTE rendering فعلی بدون تغییر بمانند.
- ادعای پشتیبانی dialectهای غیر از MySQL فقط پس از بررسی renderer همان dialect مجاز است؛ این Plan از source evidence فقط MySQL را تأیید می‌کند.

## ۶. پارامترها و dependencyها

- inline SELECT باید مانند `QueryWithsItemBuilder`، QueryRenderSelectBuilder استاندارد را با فهرست mutable parameterهای مشترک اجرا کند؛ AST فرزند باید داخل AST source والد نگهداری شود.
- regression باید ترتیب placeholderهای SQL نهایی را با ترتیب `SqlParameter`ها مقایسه کند؛ صرف اشتراک list اثبات ترتیب درست نیست.
- `query(declaration)` باید با استفاده از پارامتر ذخیره‌شده در declaration، `QueryRelation` را بسازد و به همان منطق composition فعلی بسپارد. این منطق dependencyها را با identity و ordering فعلی نگه می‌دارد، CTEها را می‌چیند و params bound relation/dependency را منتقل می‌کند.
- nested QueryRelationهای داخل inline SELECT باید توسط `QueryRenderSelectBuilder` داخلی resolve شوند و CTEهای مربوط در AST همان SELECT داخلی باقی بمانند؛ این metadata نباید با انتقال دستی AST ساده حذف شود.
- هیچ parameterless default برای declaration یا `RelationFilters` فرض نمی‌شود. فراخواننده `P` را هنگام ساخت declaration می‌دهد؛ `query(declaration)` آن را دوباره دریافت نمی‌کند و از reflection یا constructor selection استفاده نمی‌کند.

## ۷. قرارداد Declaration و سازگاری

### ۷.۱ قرارداد نهایی پارامترهای bound‌شده به declaration

قرارداد هدف `IQueryTableApi.query` بسته شده است:

```kotlin
fun <P> query(declaration: IQueryRelation<P>): IQueryTableApi
```

این متد فقط declaration را می‌گیرد؛ `P` باید هنگام ساخت همان instance تأمین و به آن متصل شده باشد. source فعلی نشان می‌دهد `IQueryRelation<P>` فقط `queryRelation(params: P)` دارد و هیچ property یا متد دسترسی به پارامترهای ذخیره‌شده ندارد. بنابراین API هدف با قرارداد فعلی مستقیماً قابل اجرا نیست و تغییر قرارداد declaration لازم است.

قرارداد نهایی Declaration برای اجرای این API:

```kotlin
interface IQueryRelation<P> {
    val params: P
    fun queryRelation(params: P): QueryRelation
}
```

`QueryDeclaration<P>` باید `params` را از سازنده دریافت و به‌صورت read-only نگه دارد؛ implementerهای مستقیم `IQueryRelation<P>` نیز باید همین پارامتر را در instance نگه دارند و `params` را ارائه کنند. قرارداد اجرایی موردنیاز برای `IQueryTableApi.query(declaration)` این است که دقیقاً یک بار `declaration.queryRelation(declaration.params)` را فراخوانی کند و همان نمونهٔ `QueryRelation` را به مسیر composition موجود SELECT تحویل دهد. این متد هنوز در source فعلی وجود ندارد؛ بنابراین این جمله قرارداد هدف و الزام implementation است، نه ادعای رفتار اجراشده. در مسیر هدف هیچ `P`ای استنتاج یا به‌طور ضمنی ساخته نمی‌شود.

شکل موردانتظار برای کلاس پایه و implementer مستقیم:

```kotlin
abstract class QueryDeclaration<P>(
    final override val params: P,
) : IQueryRelation<P>

class UserStatsQueryV3(
    override val params: RelationFilters,
) : IQueryRelation<UserStatsQueryV3.RelationFilters> {
    // queryRelation(params) همچنان QueryRelation را می‌سازد
}
```

در نمونهٔ `QueryDeclaration`، subclass پارامتر را به سازندهٔ پایه می‌دهد؛ در پیاده‌سازی مستقیم، کلاس خودش property را نگه می‌دارد. هنگام اجرای API هدف، هر دو مسیر باید همان مقدار ذخیره‌شده را به `queryRelation` بدهند. این برابری باید با regression test اثبات شود؛ صرف سازگاری نوعی امضاها اثبات رفتار runtime نیست.

این تغییر `IQueryRelation<P>` را در `query:api` نگه می‌دارد و به `QueryDeclaration` وابستگی نمی‌دهد؛ بنابراین جهت وابستگی ماژول‌ها حفظ می‌شود. افزودن property به interface عمومی مستلزم به‌روزرسانی implementerهای موجود است. جست‌وجوی source، سه implementer مستقیم V3 (`UserStatsQueryV3`, `UserPhoneQueryV3`, `UserPageQueryV3`)، implementerهای تست در `TypedRelationPropertyTest`, `QueryMetadataResolutionTest` و `SmartQueryResultTest`، و subclassهای `QueryDeclaration` در `QueryDeclarationTest` را نشان می‌دهد. این موارد قابل مهاجرت‌اند: پارامترهای typed از constructor به property منتقل می‌شوند و برای `Unit` مقدار `Unit` نگهداری می‌شود. `UserDisplayQueryV3`, `SampleQueryDeclaration` و subclassهای `QueryDeclaration<Unit>` فقط باید constructor/super-constructor لازم را برای نگهداری پارامتر بپذیرند؛ بازطراحی نامرتبط لازم نیست. امضای `queryRelation(params)` باقی می‌ماند، اما نمونه‌سازی‌های V3 از شکل بدون پارامتر به declarationهای constructor-bound مهاجرت می‌کنند. Source یا binary compatibility برای implementerهای بیرون Repository تضمین‌شده نیست و باید جداگانه ارزیابی شود.

قرارداد نهایی Plan این است: `IQueryRelation<P>` پارامترهای bound‌شده را با `val params: P` عرضه می‌کند، `QueryDeclaration<P>` آن را از constructor دریافت و نگه می‌دارد، و implementer مستقیم نیز همان property را فراهم می‌کند. `IQueryTableApi.query(declaration)` آن را به امضای فعلی `queryRelation(params)` می‌دهد. امضای هدف `query(declaration)` قطعی می‌ماند؛ نه `query(declaration, params)` و نه `query(KClass<T>)` مسیر جایگزین نیستند.

### ۷.۲ implementerهای مستقیم `IQueryRelation`

API هدف `IQueryRelation<P>` را می‌پذیرد؛ بنابراین implementer مستقیم پشتیبانی می‌شود و مهاجرت اجباری به `QueryDeclaration<P>` لازم نیست. implementer مستقیم و subclass کلاس پایه هر دو باید پارامترهای constructor-bound خود را نگه دارند و `params` را ارائه کنند. `QueryDeclaration<P>` محل اختیاری برای پیاده‌سازی مشترک همین نگهداری است.

## ۸. سازگاری و مهاجرت

- تمام `table(Model::class)`های داخل SELECT FROM به `model(Model::class)` تبدیل می‌شوند؛ `table(String)` تغییر نمی‌کند.
- تمام فراخوانی‌های عمومی `.from(queryRelation, alias)` به `.from { query(declarationWithBoundParams); alias(...) }` منتقل می‌شوند و از پارامتر ذخیره‌شده در همان declaration مطابق قرارداد بخش ۷.۱ استفاده می‌کنند.
- `UserPageQueryV3` و Queryهای دارای dependency داخلی باید هر declaration وابسته را جداگانه و با params خودش هنگام ساخت instance بسازند؛ params مربوط به declaration والد نباید به dependency نسبت داده یا جایگزین شود. رفتار nested composition و ordering حفظ شود.
- `cte(String)` و `alias(String)` در block باقی می‌مانند.
- `QueryRelation` و factoryهای عمومی فعلی حذف یا بازطراحی نمی‌شوند؛ فقط مسیر عمومی `from(QueryRelation, alias)` از `IQueryRenderSelectApi` حذف می‌شود و منطق composition داخلی reuse می‌گردد. قرارداد `IQueryRelation<P>` و سازندهٔ `QueryDeclaration<P>` فقط به‌اندازهٔ اتصال پارامتر به declaration، مطابق بخش ۷.۱، تغییر می‌کنند.
- `IQueryTableApi` در CRUD/JOIN مشترک است. تغییرهای این Plan نباید رفتار آن عملیات را تغییر دهد؛ Query selection در آن contextها باید محدود یا صریحاً رد شود.
- تغییر عمومی امضاها source compatibility را تغییر می‌دهد. سیاست binary compatibility در Repository تأیید نشده و نباید تضمین شود.

## ۱۰. تست‌های موردنیاز و معیارهای پذیرش

1. `IQueryRenderSelectApi` فقط overload block-based `from(IQueryTableApi.() -> Unit)` را در API عمومی داشته باشد؛ مسیر Query از table API قابل استفاده شود.

4. raw table syntax همان AST و SQL فعلی را بسازد.
5. inline nested SELECT در AST مستقل source نگهداری و در MySQL به `(SELECT ...) AS alias` رندر شود.

## ۱۲. نتیجهٔ implementation و وضعیت نهایی

Plan 10.6 در محدودهٔ مجاز پیاده‌سازی شد:

- IQueryRelation<P> اکنون val params: P دارد؛ QueryDeclaration<P> آن را از سازنده می‌گیرد. تمام implementerها و call siteهای داخل Repository مهاجرت داده شدند. این تغییر source/binary compatibility برای مصرف‌کننده‌های خارج Repository را تضمین نمی‌کند.

- AST جدول اکنون SELECT تو‌در‌تو را به‌عنوان derived source نگه می‌دارد. MySQL renderer آن را به‌صورت (SELECT ...) AS alias رندر می‌کند؛ MariaDB از renderer همین MySQL استفاده می‌کند. قابلیت‌های Query-specific در contextهای CRUD/JOIN رد می‌شوند و تست regression آن را پوشش می‌دهد.
