# Plan 8.0 — خروجی SELECT آگاه از Model و resolve کردن QueryRow

## 1. عنوان

**Plan 8.0 — استخراج خودکار DataType برای ستون‌های Model-backed و دسترسی QueryRow با property**

## 2. وضعیت

**وضعیت: Implementation Ready**

این Plan بر شواهد فعلی repository بنا شده است. Plan 7.0 مبنا باقی می‌ماند و فقط قابلیت‌های Model-backed SELECT و دسترسی تکمیلی به `QueryRow` به آن افزوده می‌شوند.

## 3. هدف

Plan 8.0 باید این سه قابلیت را فراهم کند:

1. استخراج یک `DataType` پیش‌فرض از نوع Kotlin property در مسیر `column(Model::class, property)`.
2. دسترسی به نتیجه با همان property از طریق `row.getValue(Model::property)` و در حالت تکرار با output-key hint.
3. حفظ دسترسی فعلی با SQL output alias برای V1 و مصرف‌کننده‌های موجود.

## 4. زمینه و اصول معماری

Plan 7.0 قرارداد زیر را بسته است و Plan 8.0 آن را تغییر نمی‌دهد:

```text
SELECT AST = Single Source of Truth
ColumnAlias = result identity / QueryRow key
ExecutionType = JDBC extraction contract
```

Plan 8.0 فقط در حالت ستون مستقیم Model-backed، یک مقدار پیش‌فرض برای `ExecutionType` از Kotlin property می‌سازد. این مقدار، قرارداد extraction انتخاب‌شده برای SELECT است؛ نوع واقعی ستون دیتابیس نیست.

این موارد همچنان ممنوع‌اند:

* حدس نوع از database schema، JDBC metadata، ResultSet metadata، نام ستون یا alias.
* حدس نوع از annotationهای مدل، entity/CTE، naming convention یا reflection غیرمرتبط با property انتخاب‌شده.
* fallback جدید به `ResultSet.getObject()`.
* DTO/Entity mapping، ORM، code generation یا result framework عمومی.
* تغییر قرارداد low-level JDBC یا تغییر semantics Plan 4.0.

## 5. شواهد Repository

### SELECT AST و Builder

هر output فعلی با `IQueryColumnsAst` و `QueryColumnsAst` نگهداری می‌شود. AST هم‌اکنون `ColumnMethod`، `Column`، `ColumnAlias` و `ExecutionType` دارد؛ ترتیب itemها در `QuerySelectAst.columns` حفظ می‌شود. این node صرفاً دادهٔ لازم برای SQL rendering نیست: alias و `ExecutionType` از همین SELECT item برای اعتبارسنجی و materialization استفاده می‌شوند. بنابراین property reference نیز می‌تواند metadata همان item باشد، نه تبدیل AST به مخزن عمومی Modelها. محل دقیق آن باید با شکل واقعی node در implementation تطبیق داده شود و abstraction موازی ساخته نشود.

منابع:

* `data_base/query/ast/src/main/kotlin/interfaces/select_interface/column/IQueryColumnsAst.kt`
* `data_base/query/ast/src/main/kotlin/schema/select_schema/column/QueryColumnsAst.kt`
* `data_base/query/ast/src/main/kotlin/interfaces/select_interface/select/IQuerySelectAst.kt`
* `data_base/query/ast/src/main/kotlin/schema/select_schema/select/QuerySelectAst.kt`
* `data_base/query/api/src/main/kotlin/interfaces/api/select_api/column/IQueryColumnsApi.kt`
* `data_base/query/builder/src/main/kotlin/ast/select_builder/column/QueryColumnsBuilder.kt`

`QueryColumnsBuilder.execute(DataType)` مقدار `ExecutionType` را روی AST item می‌نویسد. مسیر model-backed همین Builder، `column(KClass<T>, KProperty1<T,R>)`، annotationهای `QBTable` و `QBColumn` را می‌خواند و source column را روی همان `Column` AST ثبت می‌کند.

### Model metadata و Kotlin reflection

* `QBColumn` شامل نام ستون، alias مدل و primary-key flag است؛ DataType ندارد:
  `data_base/core/src/main/kotlin/annotations/models/AnnotationModelColumn.kt`
* `QBTable` شامل نام جدول و alias مدل است:
  `data_base/core/src/main/kotlin/annotations/models/AnnotationModelTable.kt`
* `QueryColumnsBuilder` از `KProperty1` و `kotlin.reflect.full.findAnnotation` استفاده می‌کند.
* `query:ast/build.gradle.kts` هم‌اکنون `kotlin-reflect` را دارد؛ نگهداری property reference در AST نیازمند dependency جدید نیست.

در وضعیت فعلی، `column(Model::class, property)` property type را برای execution استخراج نمی‌کند. `ColumnAlias` در صورت نبود alias صریح ممکن است با `QBColumn.alias` مقداردهی اولیه شود.

### QueryRow و materialization

`data_base/query/executor/src/main/kotlin/result/QueryRow.kt` مقادیر materialize‌شده را به صورت زوج‌های alias/value نگه می‌دارد و `operator get(alias)` فقط با SQL output alias lookup می‌کند. مقدارها `Any?` هستند و این Plan compile-time typed indexing اضافه نمی‌کند.

`data_base/query/executor/src/main/kotlin/interfaces/IQueryBuilderExecutor.kt` پیش از JDBC این موارد را بررسی می‌کند:

1. `requireResultOutputAliases()` برای وجود alias غیرخالی و یکتا.
2. وجود `ExecutionType` برای هر خروجی Smart.

سپس `materializeQueryRow` خروجی‌ها را بر اساس ترتیب SELECT/index استخراج می‌کند و `QueryRow` را می‌سازد. Lifecycle ResultSet و semantics `first()`/`get()` بخشی از baseline Plan 7.0 هستند و بدون تغییر می‌مانند.

`data_base/query/builder/src/main/kotlin/ast/select_builder/ResultOutputAliases.kt` فقط SQL output alias را validate می‌کند. این alias همان کلید نهایی ResultSet/QueryRow است.

* Model property references: `TypedModelReferenceTest.kt`

## 6. معماری فعلی

```text
column(Model::class, property)
        ↓
QueryColumnsBuilder
        ↓
IQueryColumnsAst / QueryColumnsAst
  ├── source column
  ├── ColumnAlias
  └── ExecutionType?
        ↓
IQueryBuilderExecutor first/get
        ↓
ResultSet getter بر اساس ExecutionType و index
        ↓
QueryRow با کلید SQL output alias
```

AST فعلی property مرجع را نگه نمی‌دارد؛ پس پس از ساخت SELECT، QueryRow نمی‌تواند تشخیص دهد کدام output با یک `KProperty1` مشخص شده است. در مقابل، مدل فعلی برای نگهداری metadata معنایی همان SELECT item و عبور آن به materializer ظرفیت دارد. افزودن property reference باید به همان metadata محدود بماند و AST را به repository عمومی Model تبدیل نکند.

## 7. مسئله

### استخراج نوع

Model-backed column اکنون باید `execute(DataType.X)` صریح بگیرد تا Smart materialization انجام شود، حتی وقتی نوع Kotlin property یکی از سه نوع اولیهٔ پشتیبانی‌شده است.

### دسترسی نتیجه

`QueryRow` فقط alias را می‌شناسد. برای یافتن خروجی متناظر با property، metadata declaration همان SELECT item باید تا QueryRow materialization حفظ شود. جست‌وجوی صرف بر اساس `property.name` یا alias مدل، قرارداد قابل قبول نیست.

### تکرار property

یک SELECT می‌تواند همان property مدل را بیش از یک بار با output aliasهای متفاوت انتخاب کند. property به‌تنهایی در این وضعیت یک خروجی یکتا تعیین نمی‌کند؛ output-key hint باید فقط برای انتخاب میان همان SELECT itemهای property یکسان به کار رود.

## 8. معماری پیشنهادی

از همان `IQueryColumnsAst`/`QueryColumnsAst` استفاده شود؛ abstraction موازی مانند `SelectOutput`, `OutputField`, `ResultSchema` یا registry ساخته نشود.

به metadata همان SELECT item یک فیلد nullable برای property مرجع Model-backed افزوده شود، برای نمونه:

```kotlin
var ModelProperty: KProperty1<*, *>?
```

فیلد صرفاً زمانی پر می‌شود که `column(Model::class, property)` یک ستون مستقیم مدل بسازد. `column { ... }`، raw SQL/table attribute، relation output و aggregate خروجی مستقیم Model property محسوب نمی‌شوند. `IQueryColumnsAst` از آنجا که همین حالا metadata موردنیاز validation و extraction را کنار SELECT item نگه می‌دارد، محل طبیعی و محدود این فیلد است؛ محل نهایی باید با ساختار واقعی node سازگار باشد و نباید برای آن abstraction موازی ساخته شود.

در زمان materialization، همان SELECT item AST مرجع این داده‌ها است:

```text
Column / expression
ModelProperty?       // فقط برای ستون مستقیم Model-backed
ColumnAlias          // کلید واقعی نتیجه
ExecutionType        // getter/materialization
SELECT index         // ترتیب استخراج
```

Executor metadata property/alias را به `QueryRow` داخلی منتقل می‌کند. QueryRow برای property access فقط از این metadata ثبت‌شده استفاده می‌کند و نتیجهٔ نهایی را با alias موجود lookup می‌کند.

## 9. تغییرات دقیق API

### Model-backed SELECT

امضای موجود `column(KClass, KProperty1)` حفظ می‌شود. فراخوانی زیر DataType پیش‌فرض را از نوع property می‌گیرد:

```kotlin
addColumn {
    column(UserModelV2::class, UserModelV2::id)
}
```

`execute(DataType)` موجود باقی می‌ماند و مقدار صریح آن بر مقدار استنتاج‌شده اولویت دارد.

### QueryRow

APIهای زیر افزوده می‌شوند:

```kotlin
fun getValue(outputKey: String): Any?

fun <T : IModelBase, R> getValue(
    property: KProperty1<T, R>,
    outputKeyHint: String? = null,
): Any?
```

همچنین API فعلی زیر برای source compatibility حفظ می‌شود:

```kotlin
operator fun get(alias: String): Any?
```

`getValue(outputKey)` و `getValue(property, hint)` مقدار `Any?` می‌دهند؛ این Plan compile-time typed index ایجاد نمی‌کند.

## 10. تغییرات دقیق AST و Model

1. metadata همان SELECT item در `IQueryColumnsAst` و `QueryColumnsAst` یک property reference nullable برای ستون Model-backed نگه می‌دارد؛ این فیلد به item محدود است و نقش Model registry ندارد.
2. `QueryColumnsBuilder.column(table, property)` همان `KProperty1` واقعی را در این فیلد قرار می‌دهد.
3. Builder برای columnهای raw و relation این فیلد را خالی نگه می‌دارد.
4. هیچ DataTypeای از `QBColumn`, `QBTable`, نوع ستون DDL، CTE یا ResultSet metadata استخراج نمی‌شود.
5. وابستگی موجود `query:ast → kotlin-reflect` حفظ می‌شود؛ dependency تازه لازم نیست.

یک `KProperty1` در زمان ساخت SELECT دو استفادهٔ مستقل دارد:

```text
KProperty1
  ├── خود property reference → ModelProperty metadata برای resolution بعدی در QueryRow
  └── property.returnType → DataType inference → ExecutionType برای JDBC extraction
```

نوع property به‌صورت metadata موازی در AST ذخیره نمی‌شود؛ Builder آن را هنگام declaration از `KProperty.returnType` می‌خواند و فقط نتیجهٔ قراردادی را در `ExecutionType` موجود ثبت می‌کند. `ModelProperty` برای lookup بعدی در QueryRow باقی می‌ماند. در نتیجه property identity و extraction type دو نقش جدا دارند.

## 11. قواعد resolve کردن DataType

فقط برای output مستقیم و بدون aggregate از `column(Model::class, property)`:

| Kotlin property type | Default execution DataType |
|---|---|
| `Int` یا `Int?` | `DataType.INT` |
| `Long` یا `Long?` | `DataType.LONG` |
| `String` یا `String?` | `DataType.STRING` |

قواعد تکمیلی:

* Nullable بودن mapping را تغییر نمی‌دهد؛ `Int?` همچنان `INT` است.
* نوع از classifier نوع property به دست می‌آید؛ نام property، `QBColumn`، database metadata و expression نقشی ندارند.
* `execute(DataType.X)` قرارداد صریح نویسنده SELECT است و حتی اگر با نوع Kotlin property فرق کند، بدون conflict-check مقدار default را جایگزین می‌کند. مثال: property از نوع `Int` با `execute(DataType.LONG)` خروجی را با semantics `LONG` استخراج می‌کند.
* inference فقط برای ستون مستقیم Model-backed مجاز است. اگر همان item به aggregate یا expression تبدیل شود، نوع property منبع نباید به نتیجهٔ expression سرایت کند؛ `COUNT(property)` از نوع `Int` بودن property، `INT` استنتاج نمی‌کند. Builder باید این مرز را در state/validation پیاده‌سازی enforce کند، نه اینکه صرفاً به مستندات تکیه کند. نوع aggregate فقط با `execute(DataType.X)` صریح تعیین می‌شود.
* اولویت صریح باید مستقل از ترتیب فراخوانی در block باشد: اگر `execute(...)` قبل از `column(...)` آمده باشد، inference بعدی نباید آن را overwrite کند.
* اگر نوع property پشتیبانی نشود، هیچ mapping جدیدی حدس زده نمی‌شود. مقدار inferred خالی می‌ماند؛ Smart `first()`/`execute()` پیش از JDBC همان validation Plan 7.0 را اجرا می‌کند. نویسنده می‌تواند با `execute(DataType.X)` نوع موردنظر را صریح تعیین کند.
* برای raw column/expression، aggregate (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) و relation output، نوع از property منبع استنتاج نمی‌شود؛ output همچنان باید DataType صریح داشته باشد، مگر اینکه یک قرارداد مستقل آینده نوع aggregate را تعیین کند.
* این `DataType` نوع ستون دیتابیس نیست؛ قرارداد استخراجی است که نویسندهٔ SELECT صریحاً انتخاب کرده یا برای ستون مستقیم مدل به‌عنوان default از نوع Kotlin property گرفته است.

## 12. قواعد دسترسی QueryRow

`getValue(property)` با فهرست SELECT item metadata در QueryRow مقایسه می‌کند. تطبیق باید با property reference ثبت‌شده در AST انجام شود، نه با `property.name` به‌تنهایی.

پس از یافتن SELECT item، alias نهایی همان `ColumnAlias` در AST است؛ مقدار از QueryRow با همان alias برداشته می‌شود. بنابراین alias هویت خروجی باقی می‌ماند و property فقط مسیر پیدا کردن output declaration است.

مقدار بازگشتی همچنان `Any?` است و materialization مطابق `ExecutionType` انجام شده است.

## 13. قواعد property تکراری و output-key hint

برای یک property مشخص:

| وضعیت | رفتار قطعی |
|---|---|
| هیچ SELECT item با همان property ثبت نشده | `IllegalArgumentException`؛ جست‌وجو با property name یا alias مدل fallback نمی‌کند |
| دقیقاً یک item ثبت شده و hint داده نشده | مقدار همان item برگردد |
| بیش از یک item ثبت شده و hint داده نشده | `IllegalArgumentException` مبنی بر ambiguous بودن property |
| چند item وجود دارد و hint برابر alias یکی از همان itemهاست | مقدار item متناظر برگردد |
| hint خالی/نامعتبر یا متعلق به هیچ‌یک از itemهای همان property است | `IllegalArgumentException`؛ بدون fallback |
| hint موجود در SELECT به property دیگری تعلق دارد | `IllegalArgumentException` مبنی بر عدم تطبیق hint با property |
| یک item برای property وجود دارد ولی hint alias متفاوتی می‌دهد | `IllegalArgumentException`؛ hint صریح نادیده گرفته نمی‌شود |

Aliasهای تکراری همچنان پیش از JDBC توسط `requireResultOutputAliases()` رد می‌شوند. Hint، alias جدید تعریف نمی‌کند و materialization/DataType را تغییر نمی‌دهد.

## 14. سازگاری V1

V1 از raw source column استفاده می‌کند و `KProperty` model ندارد:

```kotlin
addColumn {
    column { tableColumn("uu", "id") }
    alias("user_id")
    execute(DataType.LONG)
}

val userId = row.getValue("user_id")
// و همچنان:
val sameUserId = row["user_id"]
```

V1 نیازمند Model-backed API نیست. همه مسیرها در نهایت همان aliasهای یکتای SELECT و همان مقدارهای materialize‌شده را در QueryRow مصرف می‌کنند.

## 15. Alias و رفتار خطا

چهار مفهوم مستقل‌اند:

```text
ModelProperty                  → property declaration هویتی که برای resolve کردن SELECT item استفاده می‌شود
ExecutionType                  → قرارداد استخراج JDBC که از type property به‌عنوان default یا از execute(DataType) صریح می‌آید
SELECT Output Alias            → هویت خروجی و کلید نهایی QueryRow
Table Alias                    → qualifier مرجع SQL source؛ مستقل از هویت خروجی
```

`@QBColumn(alias = "user_id")` در Builder فعلی می‌تواند فقط default SELECT output alias سازگار با API موجود را فراهم کند، اگر alias صریحی تعیین نشده باشد. پس از ساخته‌شدن SELECT، resolution باید فقط از `ModelProperty` به SELECT item، و از آن item به alias نهایی AST برود؛ `QBColumn.alias` مستقیماً برای QueryRow lookup خوانده نمی‌شود. اگر `alias("userOutId")` صریح باشد، کلید QueryRow برابر `userOutId` است، نه `user_id`.

`ModelProperty`، `SELECT Output Alias`، `Table Alias` و `ExecutionType` نقش‌های متفاوت دارند و هیچ‌کدام fallback دیگری نیستند.

رفتارهای Plan 7.0 بدون تغییر باقی می‌مانند:

* alias گمشده، خالی یا تکراری در Smart path پیش از JDBC رد می‌شود.
* execution type گمشده نیز پیش از dispatch به JDBC رد و با `ExecuteResult.Failure` تحویل می‌شود.
* property انتخاب‌نشده، property مبهم یا hint ناسازگار در `QueryRow.getValue` با `IllegalArgumentException` شکست می‌خورد.
* خطای getter/materialization همچنان با semantics موجود `ExecuteResult.Failure` بازمی‌گردد.
* nullability با getter و `wasNull()` طبق Plan 7.0 حفظ می‌شود.

## 16. فایل‌ها، کلاس‌ها و interfaceهای متأثر

تغییرهای مورد انتظار، بر اساس symbolهای موجود:

* `query:ast`: `IQueryColumnsAst`, `QueryColumnsAst` — ذخیره property reference.
* `query:builder`: `QueryColumnsBuilder` — نگهداری property، استخراج سه default mapping، اولویت explicit type و جداکردن direct column از aggregate.
* `query:executor`: `QueryRow` — افزودن `getValue`های alias/property و metadata داخلی property-to-output-key؛ حفظ `operator get`.
* `query:executor`: `IQueryBuilderExecutor.materializeQueryRow` — پاس‌دادن mapping واقعی AST item به QueryRow بدون تغییر JDBC lifecycle.
* Tests: `TypedModelReferenceTest`, `TypedSelectOutputContractTest`, `SmartQueryResultTest` و در صورت نیاز تست‌های جدید نزدیک همین قراردادها.
* Exampleهای V2: نمونه‌سازی default mapping و صریح نگه‌داشتن مواردی که intentionally `execute(DataType.X)` را override می‌کنند.
* Exampleهای V1 و V3 فقط برای regression/backward compatibility بررسی می‌شوند؛ raw V1 باید explicit type داشته باشد و typed Relation معنای Model property پیدا نمی‌کند.

`BuiltQuery`, `IQueryExecute`, `QueryExecute`, renderer و dialect برای این قابلیت تغییر نمی‌کنند.

## 17. تست‌های لازم

### استخراج default و override

* `Int`, `Int?`, `Long`, `Long?`, `String`, `String?` به DataType درست نگاشت شوند.
* DataType inferred در AST همان item ذخیره شود.
* explicit `execute(...)` پس از inference مقدار را override کند.
* explicit `execute(...)` پیش از `column(...)` نیز محفوظ بماند.
* property type پشتیبانی‌نشده DataType تازه نسازد و Smart path را پیش از JDBC fail کند؛ explicit override آن را قابل materialize کند.
* raw column، table attribute، Relation output و aggregate از نوع source property inference نگیرند.

### QueryRow lookup

* یک property انتخاب‌شده با `getValue(property)` خوانده شود.
* همان مقدار با SQL alias از `getValue(alias)` و `row[alias]` خوانده شود.
* دو output برای یک property با aliasهای مختلف بدون hint ambiguous باشند.
* hint صحیح هر یک از دو output را انتخاب کند.
* unknown property، invalid hint، hint متعلق به property دیگر و hint نادرست برای تنها output خطا بدهند.
* propertyهای هم‌نام از دو Model متفاوت با هم اشتباه نشوند.
* `alias("userOutId")` بر `QBColumn.alias = "user_id"` مقدم باشد؛ property access مقدار را از کلید `userOutId` بخواند.

### Regression

* V1 raw `row[alias]` و `getValue(alias)` حفظ شوند.
* Plan 7.0 Smart `first()`/`execute()`، null handling، alias/type validation پیش از JDBC، parameter preservation و ResultSet lifecycle پاس شوند.
* low-level `IQueryExecute.executeSelect` و مصرف مستقیم ResultSet دست‌نخورده و سازگار بمانند.

## 18. اثر Migration

* Model-backed direct SELECTهایی که type property آنها یکی از سه نوع است، می‌توانند `execute(DataType)` را حذف و از default استفاده کنند.
* اگر نویسنده عمداً getter دیگری می‌خواهد، فراخوانی `execute(DataType.X)` باید باقی بماند؛ type property یک قید تبدیل نیست.
* خروجی‌های raw، computed، aggregate و relation همچنان type صریح نیاز دارند.
* V1 هیچ migration اجباری به مدل/property ندارد.
* alias صریح SELECT و key lookup فعلی تغییر نمی‌کنند.
* هیچ migration دیتابیس یا تغییر در schema/annotationهای model لازم نیست.

## 19. خارج از هدف

* DataTypeهای جدید غیر از `LONG`, `INT`, `STRING`.
* `getObject()` fallback یا type inference از JDBC/database.
* compile-time typed `QueryRow`, cast خودکار به generic R، DTO/entity mapping.
* generic `Query<T>`, generic result schema، registry، code generation یا ORM.
* type inference برای aggregate، raw expression، Relation یا SQL function.
* تغییر Plan 4.0 و Relation ownership/identity.
* تغییر `BuiltQuery`, parameter binding, Renderer, Dialect, Executor ownership یا low-level JDBC lifecycle.

## 20. مرزهای معنایی

```text
Model Property
    ├── identifies source declaration → ModelProperty برای resolve کردن SELECT item
    └── returnType → فقط default type input
                         ↓
                    ExecutionType
                         ↓
                 JDBC extraction
                         ↓
                   QueryRow value

SELECT Output Alias
    ├── identifies SELECT result output
    └── is the QueryRow key

Table Alias
    └── identifies SQL source reference / qualifier
```

قواعد قطعی:

* Model Property، `SELECT Output Alias` و Table Alias سه identity مستقل‌اند؛ `ExecutionType` نیز قرارداد extraction مستقل است.
* هیچ‌کدام از این مقادیر برای دیگری fallback نمی‌شود. property فقط SELECT item را resolve می‌کند؛ alias کلید نتیجه است؛ Table Alias فقط qualifier SQL است؛ `ExecutionType` فقط extraction را تعیین می‌کند.
* `getValue(property)` cast یا تبدیل Kotlin type انجام نمی‌دهد. property خروجی را از مسیر property metadata → SELECT item → SELECT Output Alias پیدا می‌کند و همان مقدار قبلاً materialize‌شده طبق `ExecutionType` را برمی‌گرداند. برای نمونه، اگر property نوع `Int` داشته باشد ولی item با `execute(DataType.LONG)` تعریف شده باشد، `getValue(property)` یک `Any?` حاوی `Long` برمی‌گرداند؛ آن را به `Int` تبدیل نمی‌کند.
* در نبود mapping برای property type پشتیبانی‌نشده، inference انجام نمی‌شود. `ExecutionType` خالی می‌ماند و Smart path پیش از JDBC رد می‌شود؛ نویسنده می‌تواند `execute(DataType.X)` را صریحاً تعیین کند.

## 21. ترتیب Implementation

1. AST فعلی و tests را برای property metadata بررسی و فیلد nullable `ModelProperty` را به همان SELECT item AST اضافه کن.
2. در `QueryColumnsBuilder.column(KClass, KProperty1)` property را ذخیره و DataType پیش‌فرض را فقط برای property typeهای سه‌گانه و خروجی مستقیم تعیین کن.
3. در همان Builder، state لازم برای حفظ اولویت explicit `execute(...)` مستقل از ترتیب DSL را اضافه کن؛ aggregate را از inference مستقیم خارج کن.
4. Smart materializer را از همان AST item metadata تغذیه کن و property-to-alias association داخلی را به QueryRow بده؛ مسیر JDBC و `ExecuteResult` را تغییر نده.
5. `QueryRow.getValue(String)` و `getValue(KProperty1, hint?)` را با جدول رفتار بخش 13 پیاده کن؛ `operator get` را حفظ کن.
6. تست‌های مثبت/منفی و تکرار property را اضافه یا به‌روزرسانی کن.
7. مثال‌های V2 را با default inference و explicit overrideهای عمدی بررسی کن؛ V1 raw path را حفظ کن.
8. اجرای تست‌های executor/builder و build ماژول‌های متأثر، example compile و `git diff --check` را ثبت کن.

## 23. معیارهای پذیرش

Plan 8.0 زمانی تکمیل است که:

1. سه Kotlin property type و nullable صورت‌هایشان مطابق جدول به default `DataType` برسند.
2. explicit type بدون توجه به ترتیب DSL بر inferred default مقدم باشد.
3. unsupported/raw/computed/aggregate/Relation outputها بدون type inference باقی بمانند و Smart execution پیش از JDBC رفتار Plan 7 را حفظ کند.
4. `QueryRow.getValue(property)` فقط از property metadata همان SELECT item resolve کند.
5. duplicate property بدون hint ambiguous باشد و hint تنها alias همان property را انتخاب کند؛ hint ناسازگار fail شود.
6. explicit SELECT alias کلید نهایی باشد و `QBColumn.alias` در resolution مستقل استفاده نشود.
7. `getValue(alias)` و `row[alias]` برای V1 و مصرف‌کننده‌های فعلی سازگار باشند.
8. `QueryRow` همچنان `Any?` برگرداند و هیچ JDBC resourceای نگه ندارد.
9. Plan 7.0، ResultSet lifecycle، parameter behavior و low-level APIs بدون تغییر بمانند.
10. تست‌ها، buildهای متأثر و `git diff --check` با نتیجهٔ ثبت‌شده تکمیل شوند.

**پایان Plan 8.0: مدل SELECT metadata موجود را گسترش می‌دهد؛ alias همچنان هویت خروجی است و property صرفاً مسیر resolve کردن همان output declaration را فراهم می‌کند.**
