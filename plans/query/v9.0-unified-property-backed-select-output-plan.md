# Plan 9.0 — یکپارچه‌سازی SELECT Outputهای مبتنی بر Property

## وضعیت

**Implementation Ready**

این Plan قابلیت‌های Model-backed SELECT در Plan 8.0 را به خروجی‌های SELECT مبتنی بر Relation نیز گسترش می‌دهد. Model و Relation از یک metadata مشترک در SELECT item و یک روش واحد برای resolve کردن مقدار در `QueryRow` استفاده می‌کنند؛ مسیر مجزای Relation یا framework عمومی نتیجه ساخته نمی‌شود.

## 1. هدف

برای هر SELECT output که به یک Kotlin property متصل شده است، property reference مبنای این موارد باشد:

* هویت property در SELECT و `QueryRow`
* نام پیش‌فرض خروجی SQL
* نوع پیش‌فرض استخراج نتیجه

منبع property می‌تواند Model، Relation یا نوع دیگری باشد که API آن را به‌عنوان typed output پشتیبانی می‌کند. تشخیص منبع برای خواندن metadata و annotationهای همان منبع به کار می‌رود؛ property identity همچنان خود `KProperty1` است.

Plan 9.0 نباید یک مسیر موازی مخصوص Relation ایجاد کند.

## 2. تصمیم‌های پایه

قرارداد Plan 7.0 حفظ می‌شود:

```text
SELECT AST = Single Source of Truth
alias       = result identity
ExecutionType = JDBC extraction contract
```

برای خروجی property-backed:

```text
KProperty1
  ├── Property identity
  ├── property.name
  ├── property.returnType
  └── source-appropriate annotation metadata
```

`ExecutionType` نوع ستون پایگاه داده نیست؛ قرارداد استخراجی‌ای است که نویسنده SELECT صریحاً انتخاب می‌کند یا برای property-backed output از نوع Kotlin property به‌عنوان پیش‌فرض به دست می‌آید.

## 3. هویت Property

هویت خروجی property-backed خود property reference است، نه `property.name` به‌تنهایی و نه alias آن.

برای نمونه، این دو property هویت‌های جدا دارند:

```kotlin
UserModelV3::name
OtherRelation::name
```

حتی اگر نام property یکسان باشد، تطبیق باید با خود property reference یا روش معادل سازگار با repository انجام شود. تطبیق صرفاً بر اساس نام property یا نام alias پذیرفته نیست.

## 4. قرارداد Alias خروجی

برای هر property-backed output، alias نهایی با این تقدم تعیین می‌شود:

```text
alias صریح DSL
        ↓ اگر وجود نداشت
alias annotation موجود مربوط به همان source
        ↓ اگر وجود نداشت
property.name
```

Plan 9.0 هیچ annotation جدیدی برای Relation تعریف نمی‌کند. قاعدهٔ source-aware در قرارداد کلی حفظ می‌شود: اگر یک source در repository metadata annotation دارای alias داشته باشد، همان metadata موجود استفاده می‌شود؛ در غیر این صورت `property.name` fallback است. این قاعدهٔ عمومی نیازمند افزودن annotation یا resolver تازه برای sourceهایی نیست که چنین metadataای ندارند.

نمونه Model:

```kotlin
@QBColumn(name = "name", alias = "user_name")
val name: String?
```

در نبود alias صریح DSL، alias خروجی `user_name` است. اگر annotation alias موجود نباشد، `property.name` استفاده می‌شود.

نمونه Relation:

```kotlin
val fullName: String?
    get() = error("Typed output property must not be read")
```

Relationهای فعلی هیچ metadata annotation برای alias ندارند. بنابراین برای Relation-backed output، alias پیش‌فرض فعلی همیشه `property.name` است، مگر اینکه alias صریح DSL تعیین شده باشد:

```text
alias صریح DSL
        ↓ اگر وجود نداشت
property.name
```

قاعدهٔ عمومی source-aware annotation فقط برای حفظ سازگاری با metadata موجود sourceهایی است که واقعاً چنین سازوکاری دارند؛ این قاعده در Plan 9.0 الزام ایجاد پشتیبانی annotation برای Relation نیست. Property getter نباید اجرا شود.

alias صریح DSL همیشه بر annotation alias و نام property اولویت دارد. alias annotation فقط default naming metadata است و هویت property را تعیین نمی‌کند.

قواعد Plan 7.0 درباره alias غیرخالی و یکتا حفظ می‌شوند و validation پیش از JDBC اجرا می‌شود. مسیر `relationColumn(property, qualifier)` نیز همین قرارداد را به کار می‌برد؛ Relation مسیر مستقل alias یا annotation ندارد.

## 5. قرارداد Execution DataType

برای property-backed output:

```text
execute(DataType.X) صریح
        ↓ در نبود آن
existing Plan 8 DataType inference روی property.returnType
```

نوع‌های پیش‌فرض این نسخه:

| Kotlin property type | Execution DataType پیش‌فرض |
|---|---|
| `Int` یا `Int?` | `DataType.INT` |
| `Long` یا `Long?` | `DataType.LONG` |
| `String` یا `String?` | `DataType.STRING` |

`execute(DataType.X)` صریح همیشه بر نوع استنتاج‌شده غالب است و این اولویت به ترتیب فراخوانی DSL وابسته نیست. برای نمونه، هر دو ترتیب زیر باید یک نتیجه داشته باشند:

```kotlin
execute(DataType.LONG)
column(Model::class, Model::id)
```

```kotlin
column(Model::class, Model::id)
execute(DataType.LONG)
```

در هر دو حالت، `ExecutionType = LONG` است. برای property از نوع `Int` نیز type صریح `LONG` بر default استنتاج‌شده `INT` غالب است.

Plan 9.0 باید همان utility/mapping موجود Plan 8 را برای تبدیل `KProperty.returnType` به `DataType` reuse کند؛ mapper جداگانه یا مسیر inference مخصوص Relation ایجاد نمی‌شود. Nullable بودن property، مانند `String?`، مطابق mapping موجود Plan 8 تفسیر می‌شود.

این استنتاج فقط برای property-backed output مجاز است. برای raw column، SQL expression، aggregate و سایر خروجی‌هایی که property reference ندارند، type از منبع دیگری حدس زده نمی‌شود و باید صریحاً با `execute(DataType.X)` تعیین شود.

هیچ typeای از schema دیتابیس، JDBC metadata، نام ستون یا alias، Model/CTE metadata، naming convention، expression یا reflection نامرتبط استنتاج نمی‌شود. `ResultSet.getObject()` fallback جدیدی نیست.

اگر property type پشتیبانی نشود و type صریح هم تعیین نشده باشد، خروجی Smart قابل materialize نیست و باید مطابق validation قرارداد Plan 7.0 پیش از dispatch به JDBC رد شود.

## 6. Metadata در SELECT AST

همان SELECT item فعلی metadata مربوط به property-backed output را نگه می‌دارد؛ abstraction موازی مانند `RelationOutput`، `SelectOutput`، `ResultSchema` یا registry ساخته نمی‌شود.

SELECT item باید بتواند این metadata را همراه هم نگه دارد:

```text
Column / expression
Property reference?  // فقط برای property-backed output
ColumnAlias          // هویت نهایی result
ExecutionType        // قرارداد استخراج
SELECT position      // ترتیب خواندن JDBC
```

Invariant مربوط به property reference:

```text
Property-backed SELECT item     → propertyReference != null
Non-property SELECT item        → propertyReference == null
```

`propertyReference` فقط توسط مسیر APIای مقداردهی می‌شود که واقعاً یک typed property reference دریافت می‌کند. هیچ Builder یا مرحله inference مجاز نیست property را از alias، نام ستون، expression، مدل/جدول یا هر منبع غیرمستقیم حدس بزند.

برای Model-backed و Relation-backed property output، همان reference واقعی `KProperty1` در SELECT item ثبت می‌شود. خروجی raw، expression و aggregate بدون property reference باقی می‌ماند.

جای دقیق فیلد باید با node واقعی AST سازگار باشد؛ AST نباید به مخزن Modelها یا Relationها تبدیل شود. `BuiltQuery`، renderer، JDBC lifecycle و قراردادهای Plan 4.0 تغییر نمی‌کنند.

## 7. Builder و Alias/Type Resolution

مسیرهای property-backed موجود و مسیر Relation باید property reference واقعی را در همان SELECT item ثبت کنند:

```text
column(Model, property)
relationColumn(property, qualifier)
        ↓
SELECT item metadata
```

Builder در زمان تعریف item:

1. property identity را ثبت می‌کند.
2. default alias را با تقدم DSL alias، annotation alias و `property.name` تعیین می‌کند.
3. default execution type را فقط برای property-backed item با همان mapper موجود Plan 8 و بر اساس `property.returnType` تعیین می‌کند.
4. مقدار صریح `execute(DataType.X)` را بر مقدار پیش‌فرض مقدم می‌داند؛ این اولویت مستقل از ترتیب فراخوانی DSL است و مقدار صریح نباید با inference بعدی overwrite شود.
5. برای raw expression، aggregate یا raw column هیچ type یا property identity جعلی ثبت نمی‌کند.

خواندن annotation به source وابسته است، اما precedence alias مشترک باقی می‌ماند. Plan 9.0 هیچ annotation جدیدی برای Relation تعریف نمی‌کند و Relation به `QBColumn` وابسته نمی‌شود. در repository فعلی، Relationها metadata annotation برای alias ندارند؛ پس alias پیش‌فرض Relation-backed output همان `property.name` است. استفاده از metadata annotation موجود در sourceهای دیگری که آن را دارند، قاعدهٔ عمومی است و پشتیبانی Relation-specific تازه‌ای ایجاد نمی‌کند.

## 8. QueryRow و دسترسی Property-based

`QueryRow` همچنان مقادیر materialize‌شده را با SQL output alias نگه می‌دارد و مقدارها همچنان `Any?` هستند؛ این Plan compile-time typed indexing ایجاد نمی‌کند.

دسترسی property-based با SELECT item metadata resolve می‌شود:

```text
KProperty1
    ↓ تطبیق با property reference ثبت‌شده در SELECT
SELECT item نهایی
    ↓
ColumnAlias نهایی
    ↓
QueryRow[alias]
```

نام property به‌تنهایی جایگزین lookup با identity نمی‌شود. اگر alias صریح `display_name` باشد، `row.getValue(UserModelV3::name)` باید همان خروجی را پیدا کند، نه اینکه به `name` fallback کند.

API property lookup عمومی است و به `IModelBase` محدود نمی‌ماند:

```kotlin
fun <T, R> getValue(
    property: KProperty1<T, R>,
    outputKeyHint: String? = null,
): Any?
```

APIهای alias-based موجود بدون تغییر حفظ می‌شوند:

```kotlin
row["user_name"]
row.getValue("user_name")
```

## 9. تکرار Property و outputKeyHint

قواعد resolve برای property تکراری:

| وضعیت | رفتار |
|---|---|
| Property در SELECT وجود ندارد | `IllegalArgumentException`؛ بدون fallback به نام یا alias |
| یک item متناظر و hint ندارد | مقدار همان item |
| چند item متناظر و hint ندارد | `IllegalArgumentException` به‌علت ambiguity |
| چند item متناظر و hint یکی از aliasهای همان property است | مقدار item متناظر با آن alias |
| hint خالی، نامعتبر یا متعلق به property دیگری است | `IllegalArgumentException`؛ بدون fallback |
| یک item وجود دارد ولی hint با alias نهایی آن مغایر است | `IllegalArgumentException` |

`outputKeyHint` فقط انتخاب بین itemهای هم‌هویت را رفع ابهام می‌کند؛ identity، alias، execution type یا مقدار materialize‌شده را تغییر نمی‌دهد. Aliasهای تکراری همچنان پیش از JDBC توسط validation موجود رد می‌شوند.

## 10. Property Metadata و getterها

برای typed outputهایی مانند:

```kotlin
val fullName: String?
    get() = error("Typed output property must not be read")
```

موتور فقط metadata مربوط به property reference، نام و return type را می‌خواند. ساختن instance برای خواندن مقدار، invoke کردن getter یا reflection روی instance برای استخراج type/value ممنوع است.

## 11. سازگاری با Plan 7.0 و Plan 8.0

Plan 7.0 همچنان مرجع قرارداد Single Source of Truth، alias و JDBC extraction است. Plan 8.0 قابلیت property-backed را برای Model اضافه کرده؛ Plan 9.0 همان الگو را به سایر property-backed outputهای پشتیبانی‌شده از جمله Relation گسترش می‌دهد.

رفتار raw V1 حفظ می‌شود:

```kotlin
addColumn {
    column { tableColumn("uu", "id") }
    alias("user_id")
    execute(DataType.LONG)
}

row.getValue("user_id")
row["user_id"]
```

رفتار Model property lookup نیز حفظ می‌شود و Relation property lookup به آن افزوده می‌شود:

```kotlin
row.getValue(UserModelV3::name)
row.getValue(UserDisplayRelationV3::fullName)
```

## 12. نمونهٔ مورد انتظار برای Relation

```kotlin
.select {
    addColumn {
        relationColumn(UserDisplayRelationV3::id, "details")
    }
    addColumn {
        relationColumn(UserDisplayRelationV3::fullName, "details")
    }
    addColumn {
        relationColumn(UserDisplayRelationV3::age, "details")
    }
}
```

در نبود alias یا DataType صریح، خروجی‌های property-backed بر اساس نام و نوع property پیش‌فرض می‌گیرند. سپس:

```kotlin
.success { rows ->
    rows.forEach { row ->
        val id = row.getValue(UserDisplayRelationV3::id)
        val fullName = row.getValue(UserDisplayRelationV3::fullName)
        val age = row.getValue(UserDisplayRelationV3::age)
        println("id=$id, fullName=$fullName, age=$age")
    }
    rows
}
```

برای هر property خروجی پیش‌فرض چنین است:

```text
id       → alias id,       DataType.INT
fullName → alias fullName, DataType.STRING
age      → alias age,      DataType.INT
```

اگر برای نمونه `age` صریحاً `execute(DataType.LONG)` تعیین شود، extraction type برابر `LONG` است و بر default غلبه می‌کند.

## 13. موارد خارج از Scope

Plan 9.0 این موارد را اضافه نمی‌کند:

* `RelationOutput`، `RelationQueryRow`، DTO، ORM یا framework عمومی result mapping
* registry یا mapping سراسری برای propertyها
* تبدیل `KProperty` به String به‌عنوان identity
* استفاده از annotation alias به‌عنوان identity property
* اجرای getter یا reflection روی instance
* type inference از JDBC/database metadata، expression، alias یا نام ستون
* fallback جدید `ResultSet.getObject()`
* تغییر Renderer، `BuiltQuery`، JDBC lifecycle یا Executor ownership
* تغییر semantics Plan 4.0 یا قرارداد low-level JDBC

## 14. ترتیب پیاده‌سازی

1. AST: بررسی `IQueryColumnsAst` و `QueryColumnsAst` و نگهداری property reference nullable در همان SELECT item.
2. Builder: ثبت property reference واقعی در مسیر Model و Relation؛ سایر مسیرها آن را خالی نگه می‌دارند.
3. Alias: اعمال قرارداد عمومی DSL alias، annotation alias موجود برای sourceهایی که آن را دارند، سپس نام property؛ برای Relation فعلی، چون annotation alias ندارد، DSL alias یا `property.name`؛ بدون تعریف annotation جدید برای Relation.
4. DataType: استفاده از mapper موجود Plan 8 برای نوع Kotlin property پشتیبانی‌شده و رعایت تقدم type صریح مستقل از ترتیب DSL؛ mapper موازی ساخته نمی‌شود.
5. Materialization: انتقال نگاشت property reference به alias نهایی همراه metadata همان SELECT item به `QueryRow`؛ lifecycle JDBC بدون تغییر.
6. QueryRow: lookup عمومی با `KProperty1<T, R>` و حفظ lookupهای alias-based.
7. Tests: پوشش موارد بخش بعدی و regression قراردادهای Plan 7.0/8.0.

## 15. آزمون‌های موردنیاز

حداقل موارد زیر باید verify شوند:

* Model property: `row.getValue(UserModelV3::id)`
* Relation property: `row.getValue(UserDisplayRelationV3::id)`
* property nullable، مانند `fullName: String?`
* annotation alias به‌عنوان default output alias
* نبود annotation alias و استفاده از `property.name`
* alias صریح DSL بر annotation alias و نام property اولویت دارد
* alias نهایی در property lookup به‌درستی resolve می‌شود
* `execute(DataType.LONG)` بر نوع استنتاج‌شده `INT` اولویت دارد
* type استنتاجی فقط برای `Int`، `Long` و `String` و nullableهای آن‌ها
* property type پشتیبانی‌نشده بدون type صریح پیش از JDBC رد می‌شود
* aggregate و expression بدون type صریح type از property مبنا به ارث نمی‌برند
* property غایب، property مبهم، hint معتبر و hint نامعتبر
* تکرار یک property با دو alias و انتخاب درست با hint
* aliasهای خالی/تکراری همچنان پیش از JDBC رد می‌شوند
* getter مربوط به Relation output اجرا نمی‌شود
* raw V1، `row[alias]` و `row.getValue(alias)` بدون تغییر کار می‌کنند
* Plan 7.0/8.0 regression و lifecycle فعلی ResultSet حفظ می‌شود

## 16. معیار تکمیل

Plan 9.0 کامل است وقتی Model-backed و Relation-backed SELECT outputها از یک mechanism مشترک استفاده کنند:

```text
Property reference
    ├── property identity
    ├── default output alias
    └── default extraction type (برای typeهای پشتیبانی‌شده)
             ↓
        SELECT item AST
             ↓
        Smart materializer
             ↓
        QueryRow با SQL output alias
```

هر دو API زیر باید بدون special-case معماری کار کنند:

```kotlin
row.getValue(UserModelV3::name)
row.getValue(UserDisplayRelationV3::fullName)
```

Plan 9.0 هیچ‌کدام از identity، alias و execution type را با یکدیگر یکی نمی‌کند و alias نهایی همچنان کلید واقعی `QueryRow` است.
