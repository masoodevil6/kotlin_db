# Plan 5.0: Smart Execute و Result Consumption Vision

## Status

`Ready for Traceability`

---

# 1. Objective

هدف Plan 5.0 طراحی کامل Vision و Contract برای نسل بعدی اجرای `SELECT` در `kotlin_db` است.

این Plan باید مشخص کند چگونه Query Builder از وضعیت فعلی:

```text
Query Builder
    ↓
SQL
    ↓
Executor
    ↓
ResultSet
    ↓
manual rs.next()
    ↓
manual rs.getInt(...)
    ↓
manual rs.getString(...)
```

به یک مدل ساده‌تر و semantic‌تر برسد:

```text
Query
├── sql()
├── first()
└── get()

first()
    ↓
Row?

get()
    ↓
Rows / Result

Row
    ↓
result["user_id"]
```

و هر SELECT output بتواند قرارداد extraction/conversion مشخصی داشته باشد:

```kotlin
addColumn {
    column {
        tableColumn("uu", "id")
    }
    alias("user_id")
    execute(DataType.INT)
}
```

که از نظر semantic یعنی:

```text
SELECT expression
        ↓
SQL output alias
        ↓
Result extraction contract
        ↓
Typed value
```

مثلاً:

```text
user_id   → INT
user_name → STRING
user_age  → INT
```

این Plan باید **کل Vision را در یک قرارداد واحد** مشخص کند.

تا زمانی که Contract نهایی نشده:

* implementation انجام نده
* source code تغییر نده
* test تغییر نده
* API جدید نساز
* abstraction جدید نساز
* Result hierarchy جدید اختراع نکن
* architecture را صرفاً برای زیبایی refactor نکن

# 7. SELECT Output as Source of Truth

اصل معماری Plan 5.0:

> Final SELECT output list is the source of truth for result identity.

مثال:

```kotlin
addColumn {
    column {
        tableColumn("uu", "id")
    }
    alias("user_id")
    execute(DataType.INT)
}
```

باید semanticاً چنین چیزی باشد:

```text
SELECT ITEM
├── expression = uu.id
├── alias = user_id
└── result extraction type = INT
```

و result key:

```text
user_id
```

باشد.

بنابراین:

```kotlin
result["user_id"]
```

صحیح است.

ولی:

```kotlin
result["id"]
```

نباید به صورت fallback کار کند.

# 12. `first()` Contract

Vision باید چنین رفتاری را بررسی کند:

```kotlin
val result = query.first()
```

Semantic:

```text
SQL execution
        ↓
first row
```

اگر query چند row داشته باشد:

```text
first()
→ first row
```

اگر هیچ row نداشته باشد:

```text
first()
→ no row
```

باید مشخص شود representation دقیق no-row چیست.

Candidate:

```kotlin
Row?
```

اما قبل از تصمیم نهایی بررسی کن:

* ExecuteResult فعلی
* Failure semantics
* null handling
* repository conventions

نباید صرفاً به خاطر سادگی `null` انتخاب شود اگر باعث مخلوط شدن:

```text
execution failure
```

با:

```text
no row
```

شود.

## Decision Closure (October 7, 2026)

### Repository Evidence

* `QueryRenderSelectBuilder` owns SELECT AST and `SqlParameter` values; it does not render or execute queries. The `query:builder` production dependencies include `core`, `query:ast`, and `query:api`, while Renderer and Executor are not production dependencies.
* `IQueryBuilderExecutor.execute(...)` accepts an `IQueryRenderSelectApi` and callback. `QueryBuilderExecutor` routes SELECT execution through `executeOut(...)` to `IQueryExecute.executeSelect(...)`.
* `executeOut(...)` selects a dialect, renders SQL, and constructs `BuiltQuery(query, params)`. The existing `blockQueryInfo` callback reports rendered SQL and parameters separately.
* `QueryExecute.executeSelect(...)` invokes its callback while the statement is in `use`; the connection is also scoped by `use` in `IQueryExecute`. A live `ResultSet` therefore must be consumed before the callback returns.
* `ExecuteResult.Success<T>(result: T?)` and `ExecuteResult.Failure(Throwable)` are already used by the public low-level API.
* `IQueryColumnsAst` stores `ColumnMethod`, `Column`, and `ColumnAlias`. The MySQL renderer emits `ColumnAlias` as SQL `AS`. `QueryRelationBuilder` requires non-empty unique output aliases. Existing SELECT example code reads `ResultSetMetaData.getColumnLabel(...)`; Executor tests also read values by alias.
* No Query Result `DataType`, result conversion utility, or Row abstraction was found. `MigrationColumnDataType` and its subtypes belong to Migration/DDL. `SqlTypeResolver` maps Kotlin input values to JDBC parameter types; it is not a JDBC-result converter.

### Final Decision Matrix

| Blocker | Evidence | Decision | Reason |
|---|---|---|---|
| Query Result DataType | Existing `MigrationColumnDataType` and subtypes are consumed by migration/DDL APIs; no query-result type exists. | Separate Contract | Migration data types do not establish a result extraction contract. |
| Result Conversion | `SqlTypeResolver` handles input parameter binding; SELECT consumers use JDBC getters directly. No result conversion utility was found. | Separate Contract | Input binding and JDBC-result conversion are distinct semantics. |
| `execute(DataType)` metadata | Select item AST retains only column method, column, and alias. Alias reaches SQL and JDBC column label; extraction-type metadata has no current carrier in AST or `BuiltQuery`. | Separate Contract | Core row materialization needs output labels only. Type conversion metadata belongs to the separate contract. |

### Final Contract

#### Low-Level API and Compatibility

Preserve the existing `IQueryBuilderExecutor.execute(...)`, `IQueryExecute.executeSelect(...)`, `ExecuteResult.Success` / `Failure`, and `ExecuteResult<ResultSet>` contract. Existing direct JDBC ResultSet consumption remains supported.

#### Smart Result API and Ownership

Query construction remains owned by `QueryRenderSelectBuilder`; rendering, execution, and Smart Result Consumption are owned by `IQueryBuilderExecutor`. Add callback-based convenience operations alongside the existing low-level API:

```kotlin
first(
    queryBuilder: IQueryRenderSelectApi,
    blockExecute: (ExecuteResult<QueryRow>) -> Unit,
    blockQueryInfo: ((query: String?, paramsMap: MutableMap<String, Any?>) -> Unit)? = null,
)

get(
    queryBuilder: IQueryRenderSelectApi,
    blockExecute: (ExecuteResult<List<QueryRow>>) -> Unit,
    blockQueryInfo: ((query: String?, paramsMap: MutableMap<String, Any?>) -> Unit)? = null,
)
```

These operations consume and materialize the ResultSet inside the low-level execution callback. They do not return a live ResultSet to the Smart API consumer.

* `first` materializes only the first row. No row is `ExecuteResult.Success(null)`; no implicit `LIMIT` or `ORDER BY` is added.
* `get` materializes all rows. Zero rows are `ExecuteResult.Success(emptyList())`.
* SQL execution, ResultSet access, and materialization failures are delivered as `ExecuteResult.Failure(Throwable)`.
* The final consumer callback remains outside JDBC error-catching so consumer exceptions are not reclassified as execution failures.

#### QueryRow and Output Identity

Declare a non-generic `QueryRow` in the `query:executor` result-consumption layer, with key access:

```kotlin
row["user_id"] // Any?
```

Materialize values using JDBC column labels and values while the ResultSet is live. The SELECT output alias is the sole row key. Smart result-consuming SELECTs require every output item to have a nonblank alias, with no duplicate aliases. Missing, blank, or duplicate aliases are rejected; source-column, Kotlin-property, and qualified-column fallback is forbidden.

An existing SQL NULL remains `null` in its row field. This is distinct from `first` returning no row (`Success(null)`), an unknown key, and an execution/materialization failure.

#### SQL Inspection

Do not add `sql()` to `QueryRenderSelectBuilder`. Add the standalone SQL convenience operation on the Executor boundary as `sql(queryBuilder): String`. It returns rendered SQL only; parameter values remain separate and are never interpolated. Actual execution continues to use `BuiltQuery(query, params)`.

#### Relation Compatibility

Preserve Plan 4.0 unchanged. Relation output aliases remain the SQL output names and can be consumed as `QueryRow` keys. Keep all existing low-level APIs and examples.

#### Separate Contract: `execute(DataType)`

Defer `execute(DataType)`, Query Result DataType definitions, conversion rules, and per-item conversion metadata to a separate contract. Do not reuse `MigrationColumnDataType` or `SqlTypeResolver` for query-result conversion. This deferred contract must specify supported types, JDBC-to-Kotlin conversion, null handling, and a metadata path before implementation.

### Implementation Readiness

```text
Plan 5.0 Core:
Query execution + QueryRow + first/get = Implementation Ready

Separate Contract:
Query Result DataType + Conversion + execute(DataType)
```

No Plan 4.0 decision is reopened by this closure.
