# پلن 10.1 — ردیابی Repository و تثبیت نگاشت API برای یکپارچه‌سازی Query

## وضعیت

**تصمیم معماری دربارهٔ جدایی قرارداد و کلاس پایه: تأیید و بسته شد**
**وضعیت کلی Plan 10.1: آمادهٔ Decision Closure (بخشی از نگاشت هنوز باز است)**

این پلن فقط برای بررسی معماری موجود، تکمیل شواهد و تثبیت نگاشت نمادهای مرتبط با abstraction فعلی Relation است. این سند مجوز تغییر source، test، Help یا documentation نیست. اجرای مهاجرت در Plan 10.2 و پس از بسته‌شدن نگاشت این پلن انجام می‌شود.

### اصلاحیهٔ معماری تأییدشده

`IQueryRelation<P>` و `QueryDeclaration<P>` دو لایهٔ مکمل‌اند و نباید یکی جایگزین دیگری شود:

* `IQueryRelation<P>` قرارداد عمومی declaration در `query:api` است.
* `QueryDeclaration<P>` کلاس پایهٔ abstract اختیاری در `query:builder` است که قرارداد را پیاده‌سازی و helper مشترک ساخت runtime composition را فراهم می‌کند.
* پیاده‌سازی مستقیم `IQueryRelation<P>` بدون ارث‌بری از `QueryDeclaration<P>` همچنان مجاز است.
* declarationهای کلاس‌محور می‌توانند از `QueryDeclaration<P>` استفاده کنند تا helper مشترک و انتقال `declarationOwner` را به‌کار بگیرند.

این تصمیم فقط رابطهٔ معماری این دو نوع را می‌بندد. نام‌گذاری Queryمحور، runtime type، امضاهای factory و سازگاری APIهای قدیمی همچنان باید در Symbol Mapping تعیین شوند. هیچ تغییر Repository در این اصلاحیه مجاز نیست؛ تنها همین سند Plan 10.1 به‌روزرسانی می‌شود.

## زمینه

Plan 10.0 نام کلاس پایهٔ اختیاری `QueryRelationDeclaration` را به `QueryDeclaration` تغییر داد. این rename محدود، مدل فعلی را یکپارچه نکرده است:

* `IQueryRelation` قرارداد عمومی declaration است.
* `QueryDeclaration` در Builder کلاس پایهٔ اختیاری است که `IQueryRelation` را پیاده‌سازی می‌کند.
* `QueryRelation` همچنان نوع runtime برای composition است.
* متدها و APIهای همین abstraction همچنان از نام Relation استفاده می‌کنند.
* مثال‌های V3 هم declaration مستقیم و هم ارث‌بری از base class را نشان می‌دهند.

هدف معماری مورد بررسی، یک مدل واحد Query برای همین قابلیت است؛ اما نگاشت دقیق باید از شواهد Repository استخراج و در این پلن بسته شود.

## هدف

پیش از هر implementation، مسئولیت‌ها و وابستگی‌های abstraction فعلی را ردیابی کن و نگاشت دقیق قدیم به جدید را برای یکپارچه‌سازی Query ثبت کن. تصمیم‌ها باید روشن کنند که قرارداد declaration، runtime composition و APIهای مصرف چگونه Queryمحور می‌شوند، بدون تغییر رفتار فعلی.

## محدودیت نام‌گذاری

این پلن فقط دربارهٔ نمادهای متعلق به abstraction فعلی QueryRelation است. عبارت «حذف APIهای Relationمحور» به معنی حذف واژه یا مفهوم Relation از کل کتابخانه نیست.

موارد خارج از هدف این مهاجرت:

* کاربردهای عمومی مفهوم relational database.
* APIها و annotationهای مستقل CTE.
* نام‌ها یا قابلیت‌های نامرتبط با declaration و composition فعلی QueryRelation.

## مرحلهٔ 1 — ردیابی کامل

در source، تست‌ها، مثال‌ها، Help metadata و documentation این موارد را بررسی و ثبت کن:

1. `IQueryRelation` و تمام پیاده‌سازی‌های مستقیم آن.
2. `QueryDeclaration`، helperها و زیرکلاس‌های آن.
3. `QueryRelation` شامل `name`، `definition`، `dependencies`، identity و declaration-owner metadata.
4. همهٔ declarationها، overrideها و call siteهای `relationName` و `queryRelation(...)`.
5. factoryها و extensionهای ساخت runtime.
6. APIهای `from(relation)` و `relationColumn(...)`، از جمله رفتار qualifier صریح.
7. مسیر SELECT، CTE lowering، dependency ordering، cycle detection و پارامترها.
8. Typed Output metadata، property referenceها، aliasها و owner resolution.
9. مرز Executor و materialization؛ مشخص کن کدام نوع‌ها و نام‌ها از آن عبور می‌کنند.
10. تمام moduleها، مثال‌ها، تست‌ها، Help و اسناد متأثر.

برای هر مورد مسیر، symbol، caller/implementer و رفتار قابل مشاهده را ذکر کن. نام‌ها را به‌تنهایی دلیل معماری تلقی نکن.

## مرحلهٔ 2 — تثبیت نگاشت API

برای هر نماد در scope، نگاشت قدیم به جدید را کامل کن:

| نماد فعلی | مسئولیت و مصرف‌کننده‌های فعلی | نام/نوع/امضای مقصد | اثر مهاجرت و سازگاری | شواهد و تست لازم |
| --- | --- | --- | --- | --- |
| `IQueryRelation<P>` | قرارداد عمومی declaration در `query:api`; پیاده‌سازی مستقیم دارد و توسط `QueryDeclaration<P>` نیز پیاده‌سازی می‌شود | حفظ یک قرارداد عمومی Queryمحور؛ نام و امضای Queryمحور باید در نگاشت نهایی ثبت شود | پیاده‌سازی مستقیم باقی می‌ماند؛ هر rename باید مصرف‌کننده‌های مستقیم را پوشش دهد | مسیر، direct implementerها، call siteها و تست‌های declaration |
| `QueryDeclaration<P>` | کلاس پایهٔ abstract اختیاری در `query:builder`; قرارداد `IQueryRelation<P>` را پیاده‌سازی می‌کند و helper ساخت runtime composition دارد | حفظ کلاس پایهٔ مکمل برای declarationهای کلاس‌محور؛ نام مقصد در نگاشت نهایی ثبت شود | اجباری‌کردن ارث‌بری یا تبدیل آن به تنها قرارداد ممنوع است | subclassها، owner metadata و تست helper/factory |
| `QueryRelation` | runtime composition و identity | نوع runtime Queryمحور با نام دقیق | باید تداخل نام و مسئولیت بررسی شود | sourceها، dependencyها و تست‌ها |
| `relationName` | نام فعلی declaration/runtime | نام Queryمحور دقیق | باید محل استفاده تعیین شود | declaration، CTE و rendering |
| `queryRelation(params)` | تولید runtime definition | متد Queryمحور دقیق | باید call siteها ثبت شوند | مثال‌ها و factoryها |
| `buildQueryRelation(...)` و factoryها | ساخت runtime object | نام‌های Queryمحور دقیق | حفظ owner metadata لازم است | تست factory و Typed Output |
| `from(relation, alias)` | افزودن composition source | API source با اصطلاح Query | حفظ alias و source semantics | تست source/CTE |
| `relationColumn(...)` | دسترسی به خروجی composition | API خروجی با اصطلاح Query | حفظ owner/property resolution | تست Typed Output |
| dependency/source internals | CTE closure و composition | نام‌های داخلی یا مقصد Queryمحور با دلیل | حفظ identity و ترتیب لازم است | تست composition و CTE |

تصمیم رابطهٔ این دو نوع بسته شده است: قرارداد عمومی در interface می‌ماند و کلاس پایهٔ Builder آن را پیاده‌سازی می‌کند و helper مشترک می‌دهد. این دو مسئولیت مکمل‌اند؛ interface حذف یا با کلاس پایه جایگزین نمی‌شود و ارث‌بری از کلاس پایه برای تمام declarationها اجباری نیست. ردیابی باقی‌مانده باید نام‌های Queryمحور و امضاهای مقصد را در هر دو لایه هماهنگ کند؛ اگر نام یا امضای نهایی هنوز evidence یا تأیید کافی ندارد، همان مورد unresolved می‌ماند.

نام runtime مقصد را بدون بررسی تداخل و مسئولیت این موارد نهایی نکن: `Query`، `QueryDefinition`، `BuiltQuery` و ASTهای موجود. امضای دقیق public API باید در خروجی نگاشت ثبت شود؛ اگر شواهد برای یک تصمیم کافی نیست، همان مورد را unresolved نگه دار و دلیل/evidence لازم را بنویس.

## تصمیم بسته‌شده: قرارداد عمومی و کلاس پایه

قرارداد فعلی عمومی:

```kotlin
interface IQueryRelation<P> {
    val relationName: String
    fun queryRelation(params: P): QueryRelation
}
```

کلاس پایهٔ اختیاری:

```kotlin
abstract class QueryDeclaration<P> : IQueryRelation<P> {
    abstract override val relationName: String
    abstract override fun queryRelation(params: P): QueryRelation

    protected final fun buildQueryRelation(
        block: IQueryRenderSelectApi.() -> Unit,
    ): QueryRelation = buildQueryRelationPrimitive(
        name = relationName,
        declarationOwner = this::class,
        block = block,
    )
}
```

این قراردادها نقش‌های مستقل و مکمل دارند. پیاده‌سازی interface بدون base class معتبر می‌ماند؛ base class مسیر استاندارد مشترک برای declarationهای کلاس‌محور است. هر تغییر نام‌گذاری در Plan 10.2 باید همین جدایی و رابطهٔ «کلاس پایه implements قرارداد عمومی» را حفظ کند. این بخش تصمیم معماری را می‌بندد، اما به‌تنهایی نام نهایی Queryمحور یا امضای runtime را تعیین نمی‌کند.

## اصول حفظ رفتار در نگاشت

نگاشت پیشنهادی باید حفظ این رفتارها را توضیح دهد، بی‌آنکه در این مرحله آن‌ها را پیاده‌سازی کند:

* SQL و رفتار Dialect.
* مقدار و ترتیب parameterها.
* Query filters و validation.
* alias خروجی، Typed Output و declaration owner validation.
* composition و source alias صریح.
* dependency ordering، identity، cycle detection و CTE lowering.
* execution boundary، result materialization و error handling.

هیچ قابلیت composition جدیدی وارد نگاشت نشود. APIها و annotationهای مستقل CTE خارج از scope هستند و نباید rename، حذف، ادغام یا بازطراحی شوند.

## خروجی الزامی Plan 10.1

گزارش نهایی این بخش‌ها را داشته باشد:

1. **Repository Evidence** — مسیر و symbol دقیق، call siteها و مسئولیت‌های تأییدشده.
2. **Lifecycle Trace** — مسیر declaration تا runtime object، source composition، CTE rendering و اجرای Query.
3. **Complete Symbol Mapping** — جدول کامل قدیم/جدید با امضا، مالکیت ماژول، مهاجرت، سازگاری و تست‌ها.
4. **Canonical Declaration Decision** — تصمیم بسته‌شدهٔ دو لایه: قرارداد عمومی `IQueryRelation<P>` و base class اختیاری `QueryDeclaration<P>` که آن قرارداد را پیاده‌سازی می‌کند؛ حذف هیچ‌یک یا اجباری‌کردن ارث‌بری مجاز نیست.
5. **Runtime/Composition Naming Decision** — نوع و API دقیق runtime/source/output، یا فهرست unresolvedهای مستند.
6. **Compatibility and Regression Plan** — رفتارهایی که باید حفظ شوند و تست‌های لازم برای Plan 10.2.
7. **Scope Exclusions** — مواردی که به اشتباه نباید با این migration حذف یا rename شوند.
8. **Decision Status** — موارد بسته و مواردی که هنوز به تصمیم مالک نیاز دارند.

## معیار بسته‌شدن Plan 10.1

Plan 10.1 فقط وقتی بسته است که:

* جست‌وجوی repository و lifecycle واقعی کامل شده باشد.
* برای تمام symbolهای هدف، نگاشت دقیق و مالکیت API ثبت شده باشد.
* هیچ نام یا امضای حیاتی صرفاً بر اساس حدس انتخاب نشده باشد.
* مرز نمادهای هدف از مفهوم relational database و APIهای مستقل CTE جدا شده باشد.
* تست‌های regression و اثر سازگاری برای مهاجرت بعدی مشخص باشند.
* جدایی نقش‌های `IQueryRelation` و `QueryDeclaration` به‌عنوان تصمیم بسته‌شده حفظ شود؛ unresolvedهای باقی‌مانده فقط به تصمیم‌های واقعاً باز دربارهٔ نام‌گذاری، runtime type، overloadها و سازگاری API محدود باشند و برای هرکدام تصمیم لازم مشخص شود.

Plan 10.1 مجوز تغییر source، test، Help یا documentation نمی‌دهد. اگر نگاشت کامل و تصمیم‌ها بسته شدند، Plan 10.2 می‌تواند برای اجرای آن نگاشت به‌صورت جداگانه آغاز شود.

## موارد خارج از Scope

* هرگونه تغییر source، test، Help یا documentation.
* implementation یا rename در هر ماژول.
* بازطراحی SELECT/INSERT/UPDATE/DELETE، execution یا result contract.

## وضعیت نهایی

تصمیم مربوط به interface/base-class separation بسته شده است؛ سایر تصمیم‌های لازم برای migration همچنان باید با evidence تکمیل شوند. پس از تکمیل traceability و نگاشت API، وضعیت را یکی از این موارد ثبت کن:

```text
Status: Ready for Decision Closure
```

اگر تصمیم‌های مالک دربارهٔ نگاشت و امضاها بسته شده‌اند:

```text
Status: Ready for Plan 10.2
```

در هیچ‌یک از حالت‌ها، Plan 10.1 اجازهٔ implementation نمی‌دهد.
