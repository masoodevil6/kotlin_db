# Plan 6.0: ردیابی قرارداد Fluent Query Builder و Query Consumption API

## وضعیت

```text
Ready for Traceability
```

این سند scope و پرسش‌های Traceability را مشخص می‌کند. در این مرحله API نهایی تصویب نشده و هیچ implementation یا تغییر repository مجاز نیست.

---

## هدف

بررسی شود آیا می‌توان ساخت Query و مصرف نتیجهٔ آن را در یک جریان fluent و query-centric ارائه کرد، بدون آنکه مالکیت فعلی construction، execution یا JDBC جابه‌جا شود.

نمونهٔ زیر فقط candidate است و تا زمان Traceability قرارداد نهایی محسوب نمی‌شود:

```kotlin
val user = queryManager
    .queryBuilder { query ->
        query
            .select { ... }
            .table { ... }
    }
    .first()
    .success { row -> row["user_id"] }
    .error { error -> logger.error(error) }
```

هدف Plan انتخاب کوچک‌ترین abstraction موجه بر اساس source evidence است؛ نه ساخت ORM یا framework عمومی نتیجه.

## Baselineهای قطعی

مالکیت‌های فعلی حفظ شوند:

```text
QueryRenderSelectBuilder
    = مالک ساخت Query

IQueryBuilderExecutor / QueryBuilderExecutor
    = مالک rendering، اجرا و Smart Result Consumption

IQueryExecute / QueryExecute
    = مالک اجرای سطح پایین JDBC
```

قرارداد Smart Result Consumption در Plan 5.0/5.1 بسته است. `first()`, `get()`, `sql()`, `QueryRow`, `ResultOutputAliases`، materialization، alias identity، callbackها و lifecycle آن‌ها در این Plan بازطراحی نمی‌شوند.

APIهای فعلی زیر حفظ می‌شوند، مگر آنکه source evidence مستقیم خلاف آن را ایجاب کند و جداگانه تصمیم‌گیری شود:

```text
IQueryBuilderExecutor.execute(...)
IQueryExecute.executeSelect(...)
ExecuteResult<ResultSet>
```

Plan 4.0 و QueryRelation خارج از scope هستند. `execute(DataType)` و conversion نیز همچنان قرارداد جداگانه/Deferred هستند.

## Scope

این Plan فقط Traceability و Contract Analysis برای موارد زیر است:

1. مالکیت فعلی ساخت Query و اجرای آن.
2. APIهای SELECT، INSERT، UPDATE و DELETE و نوع‌های بازگشتی آن‌ها.
3. امکان و پیامد API ورودی مانند `queryBuilder { ... }`.
4. نوع callback، مقدار بازگشتی آن و type inference در Kotlin.
5. نقش احتمالی Query Consumer برای fluent result consumption.
6. semantics موردنیاز `first()`, `get()`, `execute()` و `sql()`.
7. semantics موردنیاز `success {}` و `error {}`، فقط بر اساس evidence.
8. سازگاری با `ExecuteResult` و APIهای موجود.
9. module dependency، source/binary compatibility، Example و Help/Main، در حد اثر مستقیم.
10. Final Contract و آزمون‌های لازم برای مرحلهٔ بعد، اگر شواهد برای بستن تصمیم‌ها کافی باشد.

این مرحله implementation نیست.

## خارج از Scope صریح

موارد زیر ایجاد یا بازطراحی نشوند:

* Executor، JDBC abstraction، Connection Manager یا connection lifecycle جدید.
* تغییر `QueryExecute`، `IQueryExecute` یا semantics فعلی `ExecuteResult`.
* جایگزینی `IQueryBuilderExecutor` بدون evidence.
* ORM، generic `Query<T>`، generic `Result<T>`، `Row<T>` یا Result Mapping framework.
* `Selectable`، `Expression`، `SelectItem`، `OutputField` یا result schema.
* reflection-based mapping، code generation یا registry.
* global context، ThreadLocal، service locator یا `Map<String, Any>`.
* Raw SQL escape hatch، database introspection یا preflight.
* تغییر Plan 4.0، QueryRelation یا Smart Execute materialization.
* تغییر Help، مگر اینکه Traceability وجود نیاز مستقیم را ثابت کند.

اگر evidence dependency فنی مستقیمی به موردی خارج از فهرست نشان داد، فقط همان dependency و scope حداقلی آن گزارش شود؛ خودکار به دامنهٔ پیاده‌سازی افزوده نشود.

نمادها و قراردادهای اصلی:


Traceability باید implementation واقعی `queryManager`، call siteهای Exampleها و مسیر rendering تا JDBC را از source جاری تأیید کند. متن این Plan جایگزین بررسی source نیست.

## مالکیت فعلی اجرا

برای `queryManager.execute(...)` مشخص شود:

* چه objectی Query را می‌سازد.
* چه objectی AST را render می‌کند.
* چه objectی SQL را به execution پایین‌دستی dispatch می‌کند.
* connection را چه کسی می‌سازد و در چه lifetimeای می‌بندد.
* آیا `queryManager` connection زنده نگه می‌دارد یا فقط execution infrastructure را نگه می‌دارد.
* چه نقشی از `QueryExecute` در lifecycle وجود دارد.
* آیا API جدید می‌تواند روی execution manager موجود افزوده شود، بدون اینکه مالکیت آن تغییر کند.

از نام `queryManager` دربارهٔ ownership یا lifecycle نتیجه‌گیری نشود؛ نتیجه باید از implementation به دست آید.

## Smart Execute موجود

منبع semantics، implementation و tests فعلی Plan 5.0/5.1 هستند. Traceability فقط مشخص کند API جدید احتمالی چگونه می‌تواند آن‌ها را reuse کند، بدون بازنویسی.

حداقل ثبت شود:

* محل اجرای `first()` و `get()` و نوع دقیق نتیجهٔ آن‌ها.
* محل materialization و alias validation.
* نحوهٔ حفظ low-level `execute()` و `ExecuteResult<ResultSet>`.
* اینکه façade احتمالی فقط delegate است یا state/behavior تازه‌ای می‌آورد.

Smart Execute موجود صرفاً برای زیباترشدن syntax refactor نشود.

## Candidate API ورودی `queryBuilder`

شکل candidate:

```kotlin
queryManager.queryBuilder { query ->
    query.select { ... }
    query.table { ... }
}.first()
```

Traceability باید مشخص کند:

1. `queryBuilder` چه ورودی‌ای می‌گیرد.
2. نوع دقیق receiver یا پارامتر callback چیست.
3. callback چه چیزی برمی‌گرداند و آیا مقدار بازگشتی آن استفاده می‌شود.
4. نوع دقیق بازگشتی `queryBuilder` چیست.
5. نتیجهٔ callback چگونه به execution manager موجود دسترسی پیدا می‌کند.
6. آیا object برگشتی صرفاً façade است یا state تازه‌ای دارد.
7. آیا Kotlin type inference و overload resolution برای API انتخابی روشن است.

هیچ‌یک از callback shapeها بدون بررسی compiler/API contract قطعی فرض نشود.

## تحلیل نوع Operation

بررسی شود که آیا چهار operation واقعاً یک construction type مشترک دارند یا فقط از نظر شکل API مشابه‌اند:

```text
SELECT
INSERT
UPDATE
DELETE
```

Candidateها:

### Candidate A: callback با receiver استنتاج‌شده

```kotlin
queryBuilder {
    query.select { ... }
}
```

### Candidate B: callback با API پایه

```kotlin
queryBuilder { query: IQueryApi<*> ->
    ...
}
```

### Candidate C: overloadهای operation-specific

```kotlin
queryBuilder { query: IQueryRenderSelectApi -> ... }
queryBuilder { query: IQueryRenderInsertApi -> ... }
queryBuilder { query: IQueryRenderUpdateApi -> ... }
queryBuilder { query: IQueryRenderDeleteApi -> ... }
```

### Candidate D: entry pointهای operation-specific

```kotlin
select { ... }
insert { ... }
update { ... }
delete { ... }
```

برای هر Candidate type safety، overload resolution، discoverability، dependency direction، پیچیدگی API، extensibility، source compatibility و پیچیدگی پیاده‌سازی آینده بررسی شود.

generic abstraction فقط به‌دلیل شباهت ظاهری چهار API ساخته نشود.

## تحلیل Query Consumer

بررسی شود object برگشتی از `queryBuilder { ... }` یا API مشابه چه semanticای دارد:

```text
ساخت Query
    ↓
Query Consumer احتمالی
    ├── sql()
    ├── first()
    ├── get()
    └── execute()، فقط اگر برای آن operation evidence باشد
```

مشخص شود:

* آیا Query Consumer موجودی در repository هست.
* اگر نیست، آیا wrapper حداقلی واقعاً لازم است.
* آیا Consumer باید operation-specific باشد.
* آیا SELECT و mutation semantics مشترک دارند یا فقط syntax مشابهی دارند.
* آیا Consumer genericشدن را بدون نیاز واقعی تحمیل می‌کند.

Consumer عمومی برای همهٔ operationها صرفاً برای یکسان‌کردن شکل فراخوانی Adopt نشود.

## SELECT Consumption

برای candidateهای زیر نوع دقیق بازگشت و delegation ثبت شود:

```kotlin
queryManager.queryBuilder { ... }.first()
queryManager.queryBuilder { ... }.get()
```

مرجع semantics، API بستهٔ Smart Execute است:

```text
first() → ExecuteResult<QueryRow>
get()   → ExecuteResult<List<QueryRow>>
```

Traceability بررسی کند آیا همان semantics بدون wrapper نتیجهٔ تازه قابل expose است. `Success(null)`، `Success(emptyList())` و failure behavior نباید تغییر کند.

## Mutation Consumption

نوع نتیجهٔ operationهای فعلی بررسی شود:

```text
INSERT → Long
UPDATE → Int
DELETE → Int
```

مشخص شود آیا آن‌ها قرارداد مشترک واقعی برای fluent `execute()` دارند یا فقط callbackهای مشابه دارند. SELECT result و mutation result از نظر type/semantics یکی فرض نشوند. اگر برای mutation مصرف fluent لازم به Contract مستقلی نیاز باشد، آن را `Separate Contract` ثبت کن.

## قرارداد `sql()`

Traceability مشخص کند:

* آیا `sql()` فقط به `IQueryBuilderExecutor.sql()` delegate می‌کند.
* آیا rendering تکرار می‌شود.
* آیا SQL شامل placeholderها باقی می‌ماند و پارامترها تغییر نمی‌کنند.
* آیا execution یا connection رخ می‌دهد.
* آیا `sql()` برای mutation نیز معنی و evidence دارد یا باید operation-specific بماند.

Renderer جدید ایجاد نشود و contract Plan 5.0 تغییر نکند.

## قرارداد `success {}`

نمونه‌ها فقط برای طرح پرسش هستند:

```kotlin
query.first()
    .success { row -> row["user_id"] }
```

```kotlin
query.first()
    .success { row -> User(id = row["user_id"] as Int) }
```

```kotlin
query.first()
    .success { row -> println(row["user_id"]) }
```

Traceability فقط با بررسی `ExecuteResult` و use-siteهای موجود مشخص کند:

* `success` روی چه typeای قرار می‌گیرد و member است یا extension.
* رفتار آن side-effect است یا transformation.
* در transformation، type نتیجه چگونه حفظ/تغییر می‌کند.
* failure و `Success(null)` چه رفتاری دارند.
* lambda با نتیجهٔ `Unit` چگونه تفسیر می‌شود.
* چند بار زنجیره‌کردن `success` معنا دارد یا خیر.

رفتار implicit برای حدس intent lambda پیشنهاد نشود. اگر evidence کافی نیست، semantic unresolved بماند.

## قرارداد `error {}`

بررسی شود handler:

* روی کدام type قرار می‌گیرد.
* side-effect handler است یا transformation/fallback.
* چه typeای برمی‌گرداند.
* آیا `Failure` را بدون تغییر propagate می‌کند یا امکان تبدیل دارد.
* پس از handler چه valueای در chain باقی می‌ماند.
* آیا ترتیب `error` سپس `success` مجاز است.
* آیا handler terminal است یا chain را حفظ می‌کند.

بدون evidence برای return/fallback semantics، API آن تصویب نشود.

## سازگاری `ExecuteResult`

قرارداد موجود بررسی شود:

```kotlin
sealed class ExecuteResult<out T> {
    data class Success<out T>(val result: T?) : ExecuteResult<T>()
    data class Failure(val exception: Throwable) : ExecuteResult<Nothing>()
}
```

اولویت با reuse semantics موجود است. تغییر `ExecuteResult` فقط در صورت evidence الزام‌آور جداگانه تحلیل شود؛ این Plan مجوز تغییر آن نیست.

## Transformation در برابر Side Effect

این دو intent از هم تفکیک شوند:

```kotlin
.success { println(it) }       // side effect
.success { it["user_id"] }     // احتمالاً transformation
```

بررسی شود آیا API باید هر دو را بپذیرد، و آیا type inference بدون ambiguity ممکن است. هیچ signature فرضی بدون evidence یا بررسی Kotlin type system نهایی نشود.

## جهت وابستگی

dependency واقعی ثبت شود و اصل زیر حفظ گردد:

```text
query:builder → query:executor
ممنوع
```

`query:api` بدون evidence به Executor وابسته نشود. اگر API fluent نیازمند اجرای query است، محل facade/bridge باید در لایه‌ای بررسی شود که dependencyهای فعلی اجازه می‌دهند؛ انتخاب آن باید از evidence و Decision Closure حاصل شود، نه از نام‌گذاری.

## مالکیت Manager و Connection Lifecycle

بررسی شود آیا API زیر با execution manager موجود قابل ارائه است:

```kotlin
queryManager.queryBuilder { ... }
```

اگر object دیگری لازم است، state و مسئولیت واقعی آن مشخص شود؛ objectی که فقط برای زیبایی syntax یک reference به Executor نگه دارد، بدون توجیه ساخته نشود.

API جدید نباید فرض کند `queryManager` همان JDBC connection زنده است. اگر `QueryExecute` برای هر execution connection را acquire/use/close می‌کند، همان lifecycle حفظ شود. Connection دائمی به Query متصل نشود.

## سازگاری API موجود

بدون evidence مستقیم، حذف یا rename نشوند:

```kotlin
queryManager.execute(...)
queryManager.sql(...)
queryManager.first(...)
queryManager.get(...)
```

و APIهای ساخت:

```text
IQueryRenderSelectApi
IQueryRenderInsertApi
IQueryRenderUpdateApi
IQueryRenderDeleteApi
```

Traceability جداگانه بررسی کند:

* source compatibility implementerهای `IQueryRenderSelectApi` و `IQueryBuilderExecutor`.
* source/binary compatibility مصرف‌کنندگان `IExampleV1.query()`.
* اثر روی Exampleهای V1، V1.1، V2 و V3.
* اثر روی APIهای write که ممکن است خارج از scope مصرف fluent باشند.
* dependency graph بین API، Builder، Executor و Example.
* تغییر احتمالی `Main(args)` یا Help Run workflow؛ فقط در صورت نیاز اثبات‌شده.

## API callback و Naming

Kotlin type inference و overload resolution برای callbackها با typeهای واقعی API بررسی شود. syntax جدید صرفاً به‌دلیل زیبایی Adopt نشود.

نام‌های زیر در context repository بررسی شوند:

```text
queryBuilder
query
consumer
queryConsumer
queryHandle
result
execution
```

به‌ویژه روشن شود `queryBuilder` برای متدی که در نهایت consumer قابل اجرا برمی‌گرداند نام دقیقی است یا ممکن است با `QueryRenderSelectBuilder` اشتباه شود.

## مرز Implementation

تا پایان Traceability و Decision Closure:

* source code، tests، documentation، build و module structure تغییر نکنند.
* abstraction یا API جدید ساخته نشود.
* تست جدید اجرا یا اضافه نشود.
* هیچ Decision معماری بر اساس زیبایی syntax گرفته نشود.

فقط پس از بسته‌شدن تصمیم‌ها و اعلام `Implementation Ready` می‌توان Plan جداگانه‌ای برای implementation تصویب کرد.

## Test Plan آینده

این فهرست برای برنامه‌ریزی verification پس از implementation است؛ اجرای test در Traceability مجاز نیست.

### ساخت API

* اجرای callback ساخت query.
* callbackهای SELECT، INSERT، UPDATE و DELETE در صورت Adoptشدن.
* نوع برگشتی و semantics مقدار callback.

### SELECT

* `first()` با یک row، صفر row و چند row.
* `get()` با چند row و صفر row.
* `sql()` و عدم execution/interpolation.

### Mutation

* INSERT، UPDATE و DELETE فقط در صورت Adoptشدن fluent mutation contract.
* SQL rendering mutation بدون اجرا، اگر در Contract پذیرفته شود.

### Result Pipeline

* transformation و side effect در `success`.
* حفظ type در transformation و chaining.
* null result و failure propagation.
* رفتار و chaining مربوط به `error`.

### Compatibility و Lifecycle

* API فعلی `execute`, `sql`, `first`, `get`.
* callback سطح پایین ResultSet و lifecycle آن.
* type inference و overload resolution.
* connection lifecycle بدون نگهداری Connection دائمی در Query.

## Deferred / خارج از دامنه

تا زمان evidence و Contract مستقل:

* `execute(DataType)`، Query Result DataType و conversion.
* generic Query/Result، DTO mapping، ORM و result schema.
* تغییر Plan 4.0 و Relation semantics.
* APIهای async/reactive، transaction، retry، pool و batch.
* تغییر Help workflow بدون نیاز اثبات‌شده.

## تصمیم‌های حل‌نشده

Traceability باید هر مورد حل‌نشده را با شواهد و اثرش ثبت کند؛ از جمله:

1. نوع callback و نتیجهٔ آن.
2. مشترک یا operation-specific بودن entry pointها.
3. نوع و مالک Query Consumer.
4. semantics مربوط به transformation و side-effect در `success`.
5. semantics، بازگشت و chaining مربوط به `error`.
6. binding صریح Executor به مسیر fluent.
7. اثر روی return typeهای Example و compatibility.
8. mutation contract و حدود lifecycle/reuse.

نبود evidence باید `Unresolved` یا `Separate Contract` بماند؛ حدس معماری جایگزین source evidence نشود.
