# Vision: `data_base:query:meta_data`

## 1. Purpose

ماژول `meta_data` با هدف ایجاد یک محل مشخص و منسجم برای مدیریت metadata موردنیاز سیستم Query ساخته خواهد شد.

با گسترش قابلیت‌های Query Builder، اطلاعات مربوط به Modelها، Tableها، Columnها، Queryها، Relationها و propertyهای آن‌ها در بخش‌های مختلف سیستم اهمیت پیدا می‌کنند. این اطلاعات ممکن است از نام کلاس و property، annotationها، قراردادهای تعریف Query یا تنظیمات صریح API به دست بیایند.

هدف این ماژول، فراهم‌کردن زیرساختی برای شناخت، تفسیر و دسترسی یکپارچه به این اطلاعات است؛ به‌گونه‌ای که قابلیت‌های آینده بتوانند بر اساس metadata کار کنند، بدون اینکه هر قابلیت منطق شناسایی و تفسیر آن را به‌صورت مستقل پیاده‌سازی کند.

در این مرحله، این سند صرفاً نیازها و جهت کلی ماژول را مشخص می‌کند. معماری داخلی و جزئیات پیاده‌سازی هنوز موضوع این سند نیستند.

## 2. Problem Statement

در نبود یک محل مشخص برای مدیریت metadata، با افزایش قابلیت‌های سیستم ممکن است:

- منطق استخراج اطلاعات از کلاس‌ها و propertyها در بخش‌های مختلف تکرار شود.
- قواعد نام‌گذاری و تقدم مقادیر در قابلیت‌های مختلف ناسازگار شوند.
- هر قابلیت برای دسترسی به annotationها یا reflection، راهکار اختصاصی خودش را ایجاد کند.
- اطلاعات فنی property با مفاهیم منطقی و نام‌های منتشرشده در SQL اشتباه گرفته شوند.
- اضافه‌شدن قابلیت‌های جدید به تغییرات پراکنده در Builderها و بخش‌های دیگر منجر شود.
- حفظ سازگاری رفتار فعلی سیستم دشوارتر شود.

ماژول `meta_data` باید زمینهٔ کاهش این پراکندگی و فراهم‌کردن رفتار قابل پیش‌بینی در قابلیت‌های وابسته به metadata را ایجاد کند.

## 3. Scope of Metadata

ماژول باید در آینده ظرفیت مدیریت metadata مرتبط با مفاهیم اصلی سیستم Query را داشته باشد.

### 3.1. Model و Table

اطلاعات مربوط به ارتباط یک Model با Table، از جمله:

- نام منطقی و نام مورد استفاده در SQL
- alias
- قواعد نام‌گذاری پیش‌فرض
- تنظیمات و overrideهای تعریف‌شده با annotation یا قراردادهای موجود
- metadata مربوط به propertyهای نگاشت‌شده به Column

### 3.2. Column و Property

اطلاعات مرتبط با propertyهای Model و Columnهای متناظر، از جمله:

- هویت فنی property
- نام Column و alias آن
- metadata مربوط به کلید اصلی و سایر ویژگی‌های تعریف‌شده
- نوع داده و اطلاعات قابل استخراج از قراردادهای فعلی
- تفاوت میان مقدار پیش‌فرض، مقدار صریح و مقدار تنظیم‌نشده

### 3.3. Query و Relation

اطلاعات موردنیاز برای شناخت Queryها و خروجی‌های آن‌ها، از جمله:

- نام و alias تعریف Query
- metadata مربوط به خروجی‌های SELECT
- ارتباط خروجی با property تعریف‌کننده
- نام منطقی خروجی در مقابل نام منتشرشده در SQL
- اطلاعات لازم برای استفاده از خروجی Query در Relationها و Queryهای دیگر

### 3.4. توسعه‌پذیری

ساختار ماژول باید امکان اضافه‌شدن انواع metadata و قابلیت‌های وابسته به آن‌ها را در آینده فراهم کند، بدون اینکه برای هر نوع اطلاعات جدید ناچار به ایجاد منطق استخراج و تفسیر کاملاً مستقل در چند بخش سیستم باشیم.

این مورد به معنای الزام به ساخت یک framework عمومی یا سیستم plugin نیست. راهکار باید متناسب با نیازهای واقعی پروژه باقی بماند.

## 4. Core Responsibilities

در سطح نیازمندی، انتظار می‌رود ماژول در آینده مسئولیت‌های زیر را پوشش دهد:

1. **Metadata Discovery:** شناسایی metadata قابل دسترس از کلاس‌ها، propertyها، annotationها و قراردادهای موجود.
2. **Metadata Interpretation:** تفسیر اطلاعات خام و تبدیل آن‌ها به معنای مورد انتظار سیستم Query.
3. **Convention Handling:** فراهم‌کردن قواعد مشترک برای مقادیر پیش‌فرض و نام‌گذاری.
4. **Override Resolution:** مشخص‌کردن مقدار مؤثر هنگام وجود چند منبع تعریف، با رعایت تقدم و قواعد مشخص.
5. **Consistent Access:** فراهم‌کردن مسیر منسجم برای قابلیت‌های مختلفی که به metadata نیاز دارند.
6. **Validation Support:** فراهم‌کردن اطلاعات لازم برای اعتبارسنجی metadata و شناسایی تعارض‌ها، بدون ادغام قواعد اعتبارسنجی مستقل هر عملیات.
7. **Evolution:** امکان توسعهٔ تدریجی metadataها و قراردادهای آن‌ها، همراه با حفظ رفتارهای موجود.

این فهرست مسئولیت‌های مفهومی را مشخص می‌کند و هنوز به معنای تصمیم‌گیری دربارهٔ کلاس‌ها، interfaceها یا APIهای نهایی نیست.

## 5. Design Principles

### 5.1. Single Source of Metadata Rules

قواعد مشترک استخراج و تفسیر metadata نباید در چند Builder به شکل‌های متفاوت تکثیر شوند.

### 5.2. Explicit Semantics

مقادیر پیش‌فرض، مقادیر صریح، مقادیر تنظیم‌نشده و مقادیر نامعتبر باید از یکدیگر قابل تشخیص باشند.

خالی‌بودن یک رشته لزوماً به معنای تنظیم‌نشدن آن نیست؛ معنای هر مقدار باید مطابق قرارداد همان metadata تعیین شود.

### 5.3. Independent Identities

مفاهیم متفاوت نباید صرفاً به دلیل شباهت ظاهری در یک مقدار ادغام شوند.

برای نمونه، در خروجی Query ممکن است این سه مفهوم مستقل باشند:

- هویت فنی property
- نام منطقی خروجی
- نام منتشرشده در SQL

این اصل باید در توسعهٔ metadataهای آینده نیز حفظ شود.

### 5.4. Compatibility

ماژول باید با درنظرگرفتن APIها، رفتارهای فعلی و مصرف‌کنندگان موجود طراحی شود. ایجاد ماژول جدید به‌خودی‌خود مجوز بازنویسی معماری یا تغییر قراردادهای فعلی نیست.

### 5.5. Separation of Responsibilities

مدیریت metadata نباید مرز مسئولیت‌های موجود را از بین ببرد.

- Query Builder مسئول ساخت AST و پارامترهای Query است.
- Dialect و Renderer مسئولیت‌های مربوط به تفاوت‌های پایگاه داده و تولید SQL را حفظ می‌کنند.
- Executor مسئول اجرای Query و مصرف نتایج است.
- قواعد اعتبارسنجی اختصاصی هر عملیات باید در محل مناسب خود باقی بمانند.

ماژول metadata باید به این بخش‌ها کمک کند، نه اینکه جایگزین آن‌ها شود.

### 5.6. No Premature Generalization

نیازهای واقعی پروژه باید مبنای توسعه باشند. ساخت registry، cache، abstraction عمومی یا سازوکارهای پیچیده صرفاً برای پیش‌بینی نیازهای نامشخص آینده، بخشی از الزامات فعلی نیست.

## 6. Architectural Boundaries

محل موردنظر برای این ماژول:

`data_base:query:meta_data`

این ماژول بخشی از حوزهٔ Query است و نباید بدون نیاز مشخص به ماژولی عمومی در `core` تبدیل شود.

در عین حال، قرارگرفتن آن در `data_base:query` به این معنا نیست که تمام metadataها باید مستقیماً وارد AST شوند یا اطلاعاتی که صرفاً برای اعتبارسنجی لازم‌اند، الزاماً در زمان اجرا و هنگام مصرف نتیجه نگهداری شوند.

نحوهٔ ارتباط ماژول با AST، Builderها، annotationها و سایر بخش‌ها باید در مرحلهٔ طراحی معماری مشخص شود.

## 7. Non-Goals for the Current Stage

در این مرحله موارد زیر عمداً خارج از محدوده هستند:

- طراحی کلاس‌ها، interfaceها و APIهای عمومی یا داخلی
- تعیین ساختار دقیق فایل‌ها و packageها
- انتخاب میان reflection، metadataهای ازپیش‌ساخته‌شده یا راهکارهای دیگر
- تصمیم‌گیری دربارهٔ cache، lifecycle و performance strategy
- تعریف یک سیستم عمومی برای همهٔ انواع metadata ممکن
- انتقال فوری تمام منطق فعلی Query Builder به ماژول جدید
- تغییر AST صرفاً برای نگهداری metadata بیشتر
- بازنویسی APIهای فعلی
- پیاده‌سازی قابلیت‌های Plan 10.3 صرفاً با فرض وجود این ماژول
- تعیین جزئیات migration و انتشار نسخه

این تصمیم‌ها باید پس از روشن‌شدن نیازهای واقعی و بررسی ساختار فعلی repository اتخاذ شوند.

## 8. Expected Long-Term Outcome

در وضعیت مطلوب، قابلیت‌های سیستم Query برای دسترسی به metadata به منطق‌های پراکنده و تکراری متکی نخواهند بود.

قواعد مشترک استخراج، تفسیر و resolve کردن metadata در محل مشخصی مدیریت می‌شوند؛ Builderها و سایر مصرف‌کنندگان اطلاعات موردنیاز خود را با قراردادهای روشن دریافت می‌کنند؛ و اضافه‌شدن قابلیت‌های جدید بدون تکثیر بی‌رویهٔ منطق یا برهم‌زدن مرزهای معماری امکان‌پذیر می‌شود.

موفقیت ماژول با تعداد کلاس‌ها یا میزان abstraction آن سنجیده نمی‌شود؛ معیار اصلی، کاهش پراکندگی منطق metadata، افزایش سازگاری رفتارها و ساده‌ترشدن توسعهٔ قابلیت‌های آینده است.
