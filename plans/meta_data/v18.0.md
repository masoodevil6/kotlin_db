# طرح پیاده‌سازی 18.0 — دسترسی به نتایج Query بر اساس Namespace

**وضعیت:** طرح برای بررسی و پیاده‌سازی مرحله‌ای  
**دامنه:** افزودن راهی برای خواندن مقادیر خروجی Query بر اساس `namespace` ثبت‌شده در `EffectiveQueryMetadata`، بدون تغییر SQL یا رفتار اجرای Query.

## ۱. هدف

API دسترسی به نتیجه توسعه یابد تا مصرف‌کننده بتواند خروجی‌های Query را با استفاده از namespace منطقی آن‌ها پیدا کند.

نمونه‌های دسترسی موردنظر:

```kotlin
row.uu.user_id
row.method.user_full_name
row.v3_user_display.fullName
```

این نمونه‌ها هدف تجربهٔ کاربری‌اند و پیش از بررسی محدودیت‌های Kotlin/JVM نباید به‌عنوان syntax قطعی API تلقی شوند. هدف این طرح، تعریف قرارداد و پیاده‌سازی دسترسی namespace-based است. تغییر SQL تولیدشده یا رفتار اجرای Query خارج از محدوده است.

## ۲. مبنای فعلی مخزن

موارد زیر در ساختار فعلی مخزن مشاهده شده‌اند و باید در طول پیاده‌سازی حفظ یا با شواهد جدید بازنگری شوند:

- Gradle ماژول اجرا `:data_base:query:executor` است.
- `EffectiveOutputMetadata` فیلد `namespace` را دارد و مقدار آن در `EffectiveQueryMetadataAnalyzer` محاسبه می‌شود.
- `QueryRow` در حال حاضر خروجی‌ها را با کلید نام SQL منتشرشده نگه می‌دارد و دسترسی‌های `getValue(String)` و `getValue(KProperty1)` را فراهم می‌کند.
- `QueryConsumer.details()`، `EffectiveQueryMetadata` را از Provider یا Analyzer می‌گیرد؛ materialization ردیف در مسیر مجزایی انجام می‌شود.
- در زمان materialization، تعداد و برچسب خروجی‌های ResultSet با خروجی‌های SELECT بررسی می‌شود و نگاشت Property به alias نیز ساخته می‌شود.
- مسیر منبع فایل‌ها زیر `data_base/query/executor` است؛ نام‌گذاری packageهای Kotlin موجود ممکن است با نام Gradle ماژول یکسان نباشد و در این طرح موضوع بازنام‌گذاری package نیست.

مرحلهٔ بررسی باید مشخص کند metadata چگونه و در چه نقطه‌ای می‌تواند بدون محاسبهٔ مجدد namespace به materialization یا API نتیجه برسد. نباید فرض شود که `details()` به‌تنهایی metadata را به هر `QueryRow` منتقل می‌کند.

## ۳. مسئولیت ماژول‌ها

### `:data_base:query:meta_data`

مسئولیت این ماژول تحلیل AST و تولید `EffectiveQueryMetadata` باقی می‌ماند.

- قرارداد فعلی namespace برای خروجی‌ها حفظ شود.
- تشخیص نوع خروجی و namespace در Analyzer انجام شود.
- منطق تشخیص namespace در Executor یا `QueryRow` تکرار نشود.

### `:data_base:query:executor`

مسئولیت این ماژول materialization خروجی‌های اجراشده و فراهم‌کردن API دسترسی به مقادیر است.

- مقادیر همچنان از طریق نام SQL منتشرشده قابل خواندن باشند.
- metadata موجود برای تعیین مسیرهای namespace-based مصرف شود.
- دسترسی جدید بدون تغییر SQL، ترتیب مقادیر یا رفتار اجرای Query اضافه شود.

### API نتیجه

پیش از تعیین شکل نهایی API، پیاده‌سازی و مصرف‌کنندگان `QueryRow`، `rows`، `getValue(...)`، materialization و انتقال `EffectiveQueryMetadata` بررسی شوند. راهکار باید تا حد ممکن بر مسیرهای موجود تکیه کند و از ساخت مدل موازی برای نتیجه جلوگیری کند.

## ۴. قراردادهای دسترسی

طراحی باید میان این مفاهیم تفکیک روشن داشته باشد:

- **Published SQL alias:** نام واقعی ستون خروجی در ResultSet، مانند `fullName`.
- **Namespace:** مسیر منطقی خروجی از `EffectiveOutputMetadata`، مانند `v3_user_display.fullName`.
- **Typed output property:** پراپرتی مدل Query یا Relation که از طریق `KProperty1` ارجاع داده می‌شود.

مقدار خروجی باید با Published SQL alias خوانده شود؛ namespace مسیر یافتن خروجی است و جایگزین alias واقعی SQL نمی‌شود.

در مرحلهٔ طراحی باید بر اساس قابلیت‌های واقعی Kotlin/JVM انتخاب شود که API نهایی از چه صورتی استفاده کند. گزینه‌ها ممکن است شامل accessor مبتنی بر namespace، یک view محدود به namespace، یا دسترسی typed موجود باشند؛ انتخاب نهایی باید با معماری موجود و شواهد مرحلهٔ بررسی سازگار باشد و این گزینه‌ها الزام به افزودن چند API موازی نیستند.

نکتهٔ فنی: رشتهٔ namespace در metadata به‌تنهایی پراپرتی‌های Kotlin مانند `row.v3_user_display.fullName` را در زمان کامپایل ایجاد نمی‌کند. اگر syntax نمونه به نوع ایستا یا code generation نیاز داشته باشد، محدودیت و هزینهٔ آن باید پیش از انتخاب قرارداد ثبت شود. راهکار نباید دسترسی پویا را بدون بررسی معادل پراپرتی واقعی Kotlin فرض کند.

## ۵. مراحل پیاده‌سازی

### مرحلهٔ صفر: بررسی مسیر دادهٔ فعلی

پیش از تغییر کد موارد زیر مستند شوند:

1. نوع واقعی `row` و مجموعهٔ `rows` و مصرف‌کنندگان آن‌ها.
2. پیاده‌سازی و قرارداد `getValue(alias)` و `getValue(KProperty1)`.
3. محل تبدیل ResultSet به `QueryRow` و نگاشت خروجی‌ها به aliasها.
4. نحوهٔ ساخت `EffectiveOutputMetadata.namespace` و رفتار خروجی‌هایی که namespace ندارند.
5. مسیر دسترسی به خروجی‌های Relation و CTE و تفاوت آن‌ها با ستون‌های مستقیم یا عبارت‌های محاسباتی.
6. مسیر فعلی انتقال `EffectiveQueryMetadata` از Query به Executor و Result.
7. محدودیت‌های Kotlin/JVM برای syntax پویا یا typed موردنظر.
8. آزمون‌های موجود Result و Executor که رفتار سازگاری را مشخص می‌کنند.

در پایان این مرحله، نقاط لازم برای تغییر و محدودیت‌های فنی ثبت شوند. طراحی نباید بر فرضی دربارهٔ ساختار داخلی ResultSet یا `QueryRow` تکیه کند.

### مرحلهٔ یک: نهایی‌کردن قرارداد API

با تکیه بر یافته‌های مرحلهٔ صفر، قرارداد دسترسی مشخص شود:

1. syntax قابل پشتیبانی در Kotlin/JVM تعیین شود.
2. رابطهٔ namespace با Published SQL alias تعریف شود.
3. رفتار namespace ناشناخته، خروجی ناموجود، alias مبهم و مقدار `null` روشن شود.
4. رفتار namespaceهای چندبخشی، مانند `v3_user_display.fullName`، مشخص شود.
5. سازگاری با دسترسی typed مبتنی بر `KProperty1` تعریف شود.
6. مشخص شود metadata در چه نقطه‌ای به Result/`QueryRow` می‌رسد، بدون تکرار تحلیل AST یا محاسبهٔ namespace.

### مرحلهٔ دو: پیاده‌سازی حداقلی

پس از تثبیت قرارداد:

1. مسیر namespace-based به API نتیجه اضافه شود.
2. namespace از `EffectiveQueryMetadata` موجود مصرف شود.
3. مقدار نهایی از Published SQL alias متناظر خوانده شود.
4. اگر انتقال metadata به مسیر materialization لازم است، از همان مسیر موجود و با کمترین تغییر استفاده شود.
5. منطق تشخیص namespace در Executor یا `QueryRow` کپی نشود.
6. تغییرات به فایل‌ها و ماژول‌های ضروری محدود بمانند.

### مرحلهٔ سه: حفظ سازگاری

رفتارهای زیر باید حفظ شوند:

- `row.getValue("user_id")`
- `row.getValue(UserDisplayQueryV3::fullName)`
- اجرای Queryهای ساده و چندخروجی
- خروجی‌های محاسباتی مانند `CONCAT` و `MIN`
- خروجی‌های دارای `OVER`
- خروجی‌های مبتنی بر CTE و Relation
- مقادیر `null`، نوع مقادیر و ترتیب فعلی خروجی‌ها

API جدید نباید aliasهای SQL را تغییر دهد یا رفتار مدیریت خطا و materialization را بدون ضرورت قراردادی عوض کند.

### مرحلهٔ چهار: آزمون‌ها

آزمون‌های متمرکز زیر اضافه یا به‌روزرسانی شوند:

1. دسترسی به ستون مستقیم با namespace جدولی، مانند `uu.user_id`.
2. دسترسی به خروجی محاسباتی با namespace `method`، مانند `method.user_full_name`.
3. دسترسی به خروجی Relation یا CTE، مانند `v3_user_display.fullName`.
4. خواندن مقدار با Published SQL alias مربوط به namespace.
5. حفظ دسترسی typed از طریق `KProperty1` و دسترسی مستقیم alias.
6. رفتار namespace نامعتبر، alias ناموجود یا مبهم.
7. حفظ مقدارهای `null` و نوع واقعی دادهٔ خروجی.
8. استفاده از metadata بدون تغییر SQL رندرشده یا ترتیب ستون‌ها.
9. حفظ آزمون‌های موجود Result، Executor و materialization.

### مرحلهٔ پنج: اعتبارسنجی و تحویل

تست‌های ماژول‌های مرتبط، به‌ویژه `:data_base:query:meta_data` و `:data_base:query:executor`، اجرا شوند. در صورت تغییر قرارداد عمومی Result، تست‌های مصرف‌کنندهٔ `:data_base:query:example` نیز اجرا شوند. هر شکست قبلی یا نامرتبط جداگانه از شکست ناشی از تغییر تفکیک و با نام task و نتیجهٔ واقعی گزارش شود.

## ۶. محدودیت‌های صریح

- SQL تولیدشده، Renderer، Builder، AST و قرارداد پارامترها تغییر نکنند، مگر آن‌که مرحلهٔ بررسی مانع فنی مشخصی را ثابت کند.
- منطق تولید namespace در Executor یا `QueryRow` تکرار نشود.
- namespace جایگزین Published SQL alias نشود.
- APIهای موجود `getValue(...)` و رفتارهای معتبر `QueryRow` حفظ شوند.
- معماری Result یا Executor به‌صورت کلی بازطراحی نشود.
- نام Gradle ماژول‌ها یا packageهای فعلی صرفاً برای یکسان‌سازی ظاهری تغییر نکند.
- syntax مبتنی بر property پویا، بدون اثبات امکان آن در Kotlin/JVM، به‌عنوان قرارداد قطعی پذیرفته نشود.
- هیچ قابلیت تازه‌ای برای اجرای Query، نوع‌دهی نتیجه یا تبدیل داده خارج از هدف این طرح اضافه نشود.

## ۷. معیارهای پذیرش

کار زمانی پذیرفته است که:

- قرارداد API بر اساس محدودیت‌های واقعی Kotlin/JVM روشن و قابل استفاده باشد.
- `EffectiveOutputMetadata.namespace` منبع مسیر دسترسی باشد.
- مقدار خروجی با Published SQL alias صحیح خوانده شود.
- دسترسی‌های قبلی aliasمحور و typed بدون شکست باقی بمانند.
- خروجی‌های مستقیم، محاسباتی، Relation و CTE پوشش داده شوند.
- namespace نامعتبر یا مبهم رفتار مشخص و آزموده‌شده داشته باشد.
- SQL، ترتیب خروجی‌ها و رفتار اجرای Query تغییر نکند.
- تست‌های مرتبط موفق باشند و گزارش نهایی فایل‌های تغییرکرده، تصمیم API، اعتبارسنجی و نتیجهٔ واقعی تست‌ها را ثبت کند.

## ۸. ترتیب اجرا

کار از مرحلهٔ صفر، یعنی بررسی مسیر فعلی Result و Executor، آغاز شود. پس از ثبت محدودیت‌ها، قرارداد دسترسی نهایی گردد و سپس پیاده‌سازی حداقلی به‌صورت مرحله‌ای انجام شود. اجرای یک‌بارهٔ کل طرح یا انتخاب syntax نهایی پیش از اثبات امکان فنی آن مجاز نیست.
