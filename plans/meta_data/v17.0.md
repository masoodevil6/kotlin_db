# طرح پیاده‌سازی 17.0 — مالکیت Resolverها، انتخاب AST و گزارش خروجی‌های SELECT نهایی

**وضعیت:** فازهای ۰ تا ۶ تکمیل شده‌اند؛ اعتبارسنجی فاز ۷ انجام شده و دو شکست خارج از تغییرات این انتقال ثبت شده‌اند.  
**دامنه:** انتقال Resolverهای Declaration، طراحی AstSelector و انتقال تحلیل Final SELECT outputs به ماژول query:meta_data.

## ۱. مسئله و هدف

در ساختار فعلی، query:meta_data هم Resolverهایی دارد که Annotation و Declarationهای Kotlin را می‌خوانند و هم قرار است محل تحلیل AST باشد. Resolverها هنگام ساخت AST در Builder مصرف می‌شوند، در حالی که گزارش Metadata مؤثر نیز داخل QueryRenderSelectBuilder محاسبه می‌شود. این مرزها وابستگی Builder به Metadata را ایجاد کرده و Builder را هم‌زمان مسئول ساخت AST و تفسیر/گزارش آن کرده‌اند.

این Plan سه مسئولیت را از هم جدا می‌کند:

- Resolverهای Declaration در query:builder باقی می‌مانند و هنگام ساخت یا اعتبارسنجی AST مقدارهای لازم را در AST ثبت می‌کنند.
- AstSelector در query:meta_data رابطه‌های واقعی و typed بین گره‌های AST را دنبال می‌کند و Metadata همان گره‌ها را در اختیار مصرف‌کننده می‌گذارد.
- تحلیل‌گر مستقل در query:meta_data از selector و Metadata ثبت‌شده در AST برای ساخت EffectiveQueryMetadata استفاده می‌کند؛ Builder همچنان مالک ساختار و composition است.

تغییرات باید رفتار فعلی گزارش، ترتیب CTEها، تقدم aliasها، خروجی‌های SELECT نهایی و رفتار نامشخص/مبهم منبع را حفظ کنند. فرمت گزارش و مدل DTO فعلی در این Plan بازطراحی نمی‌شوند.

### ۲.۳. قرارداد فعلی AST

IQueryAst فقط metadata گره را در اختیار می‌گذارد و قرارداد عمومی برای پیمایش فرزندان ندارد. رابطه‌های هر نوع گره در interfaceهای typed تعریف شده‌اند، از جمله:

- IQueryRenderSelectAst: withs، select، table، joins و سایر اجزای Query.
- IQuerySelectAst: فهرست columns.
- IQueryTableAst: رابطهٔ nullable با derivedQuery.
- IQueryWithsAst و IQueryWithsItemAst: فهرست WITHها و بدنهٔ هر مورد.
- IQueryJoinsAst و IQueryJoinsItemAst: موارد JOIN و joinTable.

Metadata فعلی نیز در AST نگهداری می‌شود. برای نمونه، QueryTableAstMetadata نام و alias را از Model، Annotation و AST جدا می‌کند؛ QueryColumnsAstMetadata شامل ColumnAlias، ExecutionType، IsExecutionTypeExplicit و PropertyReference است؛ و QueryWithsItemAstMetadata در حال حاضر فقط withName دارد. هیچ‌یک از این interfaceها فرزندان را از یک فهرست عمومی و همگن ارائه نمی‌کنند.

### ۲.۴. گزارش فعلی و شکاف دادهٔ AST

مدل‌های گزارش در query:api/src/main/kotlin/metadata/EffectiveQueryMetadata.kt، EffectiveRelationMetadata.kt و EffectiveOutputMetadata.kt تعریف شده‌اند. EffectiveQueryMetadataProvider نیز در query:api/src/main/kotlin/metadata/EffectiveQueryMetadataProvider.kt قرار دارد.

QueryRenderSelectBuilder در query:builder/src/main/kotlin/ast/select_builder/query_render_select/QueryRenderSelectBuilder.kt پیاده‌سازی‌کنندهٔ Provider است. متد effectiveQueryMetadata() و توابع کمکی آن مسئول جمع‌آوری relationها، خروجی‌های SELECT، منبع خروجی و تفسیر metadata هستند. این Builder علاوه بر AST، contextهای ساخت را هم دارد: CteSourceContext، namedCteSourceConfigured، ریشه‌ها و overrideهای CTE. مسئولیت‌های composition مانند syncCteWithItems()، orderedCteClosure()، cteWithItem() و addCteSource() ساختاری‌اند و باید در Builder بمانند.

گزارش فعلی این قواعد را اعمال می‌کند و تحلیل‌گر جدید باید آن‌ها را حفظ کند:

- خروجی‌های outputs فقط از projection نهایی ast.select.columns گرفته می‌شوند؛ خروجی SELECTهای درونی به‌اشتباه خروجی نهایی محسوب نمی‌شوند.
- منبع خروجی با alias ستون در برابر FROM و JOINها پیدا می‌شود. تنها وقتی دقیقاً یک منبع match شود نام آن ثبت می‌شود؛ در حالت بدون match یا چند match، tableName برابر null است و alias مرجع فقط اگر غیرخالی باشد حفظ می‌شود.
- برای expression بدون alias منبع، منبع ساختگی تولید نمی‌شود.
- derived SELECT معمولی می‌تواند alias محل استفاده داشته باشد، ولی نام جدول داخلی آن به‌عنوان tableName گزارش نمی‌شود.
- CTE inline اطلاعات نام runtime و alias occurrence دارد؛ CTE نام‌دار رشته‌ای باید از جدول عادی با همان نام قابل تفکیک بماند.
- logicalQueryName، cteRuntimeName، withSqlName و occurrenceAlias معنای جدا دارند. نام effective در WITH، نام runtime اصلی را جایگزین نمی‌کند.
- logicalOutputName، aliasهای Model/Annotation و ColumnAlias نهایی SQL یکی نیستند. executionType از Metadata خروجی AST خوانده می‌شود.

**وابستگی relationها به context داخلی Builder:** گزارش فعلی فهرست relationها را فقط از ast.withs استخراج نمی‌کند. QueryRenderSelectBuilder ابتدا این مجموعه را می‌سازد:

    val knownRelations = orderedCteClosure(querySourceContext.dependencies() + explicitCteRoots)

در مسیر ساخت نیز syncCteWithItems() همین دو منبع ریشه را ترکیب می‌کند، orderedCteClosure را اجرا می‌کند و orderedRelations را پیش از explicitWithItems در ast.withs می‌نویسد. orderedCteClosure با هویت referenceای Cteها تکراری‌ها را حذف می‌کند، وابستگی‌ها را پیش از ریشه می‌چیند و چرخه/نام مؤثر تکراری را رد می‌کند. بنابراین ترتیب WITH فعلی یک نامزد جدی برای بازسازی ترتیب knownRelations است، اما به‌تنهایی اثبات نمی‌کند که تمام اطلاعات لازم برای relationMetadata از AST بازیابی می‌شود: cteWithItem فعلی در Metadata خود فقط withName و body را نگه می‌دارد و نام runtime/logical یا نشانگر Cte-object-backed بودن را ثبت نمی‌کند. این فاصله باید در فاز ۳ با مقایسهٔ دادهٔ context و AST برای سناریوهای واقعی حل شود؛ تا آن زمان هیچ نتیجه‌گیری دربارهٔ کافی بودن ast.withs یا شکل نهایی فیلدهای Metadata قطعی نیست.

در AST کنونی، PropertyReference وجود دارد اما logicalOutputName آمادهٔ تحلیل نیست و گزارش فعلی آن را با Resolver محاسبه می‌کند. namedCteSourceConfigured نیز در AST ثبت نشده و برای تشخیص CTE نام‌دار از جدول عادی لازم است. برای CTEها هم withName به‌تنهایی نام runtime و نام منطقی Declaration را نگه نمی‌دارد. پس صرف افزودن selector کافی نیست: اطلاعاتی که فقط در context/شیء CTE فعلی وجود دارد باید هنگام ساخت AST در Metadata موجود ثبت شود تا تحلیل‌گر AST-only بتواند گزارش را بدون ارجاع به Builder یا Resolver بازسازی کند.

## ۳. معماری هدف و مرز مسئولیت

### ۳.۱. Resolverها در Builder

هدف انتقال فایل‌ها به این بسته‌هاست:

- gog.my_project.data_base.query.builder.metadata.models.ModelMetadataResolver
- gog.my_project.data_base.query.builder.metadata.queries.QueryMetadataResolver

مسیر پیشنهادی متناظر:

- data_base/query/builder/src/main/kotlin/metadata/models/ModelMetadataResolver.kt
- data_base/query/builder/src/main/kotlin/metadata/queries/QueryMetadataResolver.kt

این Resolverها فقط دادهٔ Declaration و Annotation را می‌خوانند/اعتبارسنجی می‌کنند و Builder را برای نوشتن مقدار resolved در AST پشتیبانی می‌کنند. آن‌ها گره‌های AST را جست‌وجو نمی‌کنند. مدل‌ها و interfaceهای AST به Builder منتقل نمی‌شوند.

### ۳.۲. قرارداد AstSelector

AstSelector در ماژول query:meta_data و در بسته‌ای مانند gog.my_project.data_base.query.meta_data.ast یا gog.my_project.data_base.query.meta_data.selector قرار می‌گیرد. انتخاب دقیق نام بسته در implementation باید با ساختار نهایی این ماژول سازگار باشد؛ هر دو Resolver پس از انتقال از آن حذف می‌شوند.

Selector از یک گرهٔ مشخص و typed آغاز می‌کند و فقط relationshipهایی را دنبال می‌کند که caller به‌صراحت انتخاب کرده است. برای نمونه، مسیر خروجی نهایی چنین است: IQueryRenderSelectAst.select → IQuerySelectAst.columns. مسیرهای دیگر می‌توانند FROM، JOINها، WITH itemها و بدنهٔ هر WITH را دنبال کنند. Selector هیچ اسکن reflection-based یا پیمایش خودکار کل Query انجام نمی‌دهد.

API باید این semantics را فراهم کند، نه API تزئینی یا مخصوص یک گزارش:

1. گرهٔ انتخاب‌شده از نظر نوع AST قابل استفاده بماند.
2. caller بتواند از relationship nullable عبور کند؛ نبود رابطه به انتخاب خالی تبدیل شود.
3. برای relationship فهرستی، ترتیب AST حفظ و عناصر همان مسیر انتخاب شوند.
4. Metadata گرهٔ انتخاب‌شده از خود گره خوانده شود؛ selector annotation را دوباره resolve یا Metadata را حدس نمی‌زند.
5. مسیر نامعتبر/نوع ناسازگار به‌دلیل قرارداد typed در زمان compile محدود شود؛ خطای runtime فقط برای ورودی واقعاً ناسازگار و با پیام روشن باشد.
6. ambiguity معنایی منبع، کار analyzer است و نباید با خطای عمومی selector اشتباه شود.

شکل سطح API (نام دقیق متدها فقط پس از نمونهٔ compile در فاز طراحی تثبیت شود) می‌تواند انتخاب typed را با accessor صریح relationship ترکیب کند؛ قرارداد باید هم برای رابطهٔ تک‌گرهی nullable و هم فهرست فرزندان آزمون داشته باشد. اگر پیاده‌سازی بدون تغییر AST ممکن باشد، interfaceهای موجود کافی‌اند و AST دست‌نخورده می‌ماند. اگر چند مسیر مشترک به adapter نیاز داشتند، فقط adapterهای باریک و typed برای همان relationshipها اضافه شوند؛ از افزودن children-graph عمومی یا abstraction کامل traversal اجتناب شود.

### ۳.۳. تحلیل‌گر گزارش

در query:meta_data یک قابلیت جدا، مثلاً EffectiveQueryMetadataAnalyzer، اضافه می‌شود. این کلاس از AstSelector و DTOهای موجود در query:api استفاده می‌کند و aggregation را انجام می‌دهد. مسئولیت selector همچنان فقط انتخاب گره و دسترسی به Metadata است.

برای آنکه تحلیل‌گر به Builder یا Resolver وابسته نشود، Metadata موردنیاز باید در AST نهایی قابل دسترسی باشد. فیلدهای زیر نامزدهای اولیه‌اند، نه تصمیم قطعی دربارهٔ شکل نهایی Metadata؛ ضرورت و کفایت تک‌تک آن‌ها در فاز ۳ بررسی می‌شود. اگر لازم شوند، روی Metadata مدل‌های فعلی AST افزوده می‌شوند، نه با انتقال آن مدل‌ها به Builder یا جایگزینی ساختار AST:

- در QueryColumnsAstMetadata مقدار nullable logicalOutputName. Builder آن را هنگام پردازش property مرجع با همان semantics گزارش فعلی از QueryMetadataResolver.queryLogicalOutputName(property) می‌نویسد. alias SQL نهایی همچنان ColumnAlias است.
- در QueryTableAstMetadata یک تشخیص کوچک و صریح برای نوع source، حداقل با تمایز CTE نام‌دار، CTE inline و derived SELECT؛ مقدارهای دیگر از metadata فعلی Model/جدول قابل تشخیص‌اند. در همین metadata، در صورت نیاز cteRuntimeName و logicalQueryName nullable ثبت می‌شوند تا CTE identity و نام occurrence با نام FROM قاطی نشوند.
- در QueryWithsItemAstMetadata احتمالاً فیلدهای nullable برای نام runtime CTE و نام منطقی Query declaration و/یا نشانگر منشأ آیتم لازم می‌شود. withName فعلی همچنان نام SQL تعریف‌شده در WITH باقی می‌ماند. برای WITH خامی که CTE object-backed ندارد، مقادیر CTE باید مطابق قرارداد نهایی خالی بمانند.

**دروازهٔ اجباری knownRelations در فاز ۳:** برای هر سناریو، لیست مرجع knownRelations که از querySourceContext.dependencies() + explicitCteRoots و orderedCteClosure به دست می‌آید، با ترتیب و محتوای قابل‌مشاهده از AST نهایی مقایسه شود. ثابت شود هر relation مرجع دقیقاً یک نمایندهٔ قابل‌شناسایی در AST دارد، relationهای dependency-first و هویت‌محور deduplicate می‌شوند، explicit WITH خام به‌اشتباه known relation شناخته نمی‌شود، و runtime name، logicalQueryName، effective withName و occurrence source جدا می‌مانند. سناریوها حداقل زنجیرهٔ وابستگی، dependency مشترک، Cte تکراری با هویت یکسان، چند explicit Cte root، Cte ریشه‌شده از source، WITH خام، override نام WITH، source inline، Query بدون CTE و AST از پیش‌ساخته‌شده را پوشش دهند.

فقط اگر این مقایسه ثابت کند AST موجود به‌همراه Metadata حداقلی می‌تواند همان فهرست مرتب و همهٔ فیلدهای DTO را بازسازی کند، Analyzer مجاز است Builder context را کنار بگذارد. اگر داده‌ای مفقود بود، ابتدا کمترین ثبت پایدار در Metadata AST یا رابطهٔ موجود بررسی شود؛ افزودن فهرست موازی relations، شناسهٔ عمومی Cte یا تغییر AST ساختاری پیش‌فرض نیست و باید با شاهد مشخص توجیه شود. تا عبور از این gate، منطق فعلی effectiveQueryMetadata و contextهای Builder حذف یا جابه‌جا نمی‌شوند.

تحلیل‌گر باید aggregate فعلی را حفظ کند:

- relationهای WITH به همان ترتیب فعلی فهرست شوند؛ WITH خام Metadata تعریف را از body می‌گیرد، و نام runtime/logical فقط در صورت ثبت شدن گزارش می‌شود.
- occurrence منبع CTE، اگر قرارداد فعلی آن را جداگانه گزارش می‌کند، به‌عنوان relation جدا حفظ شود.
- projection نهایی فقط از SELECT مستقیم Query ریشه خوانده شود.
- برای هر خروجی، نام منطقی از فیلد جدید، alias SQL از ColumnAlias، نوع اجرا از ExecutionType و منبع از منبع یکتای alias-matched استخراج شود.
- sourceهای FROM و JOIN از مسیرهای AST انتخاب شوند؛ alias تکراری یا unresolved همان نتیجهٔ فعلی (نام null و حفظ alias غیرخالی) را بدهد.
- تحلیل CTE body از SELECTهای همان body استفاده کند؛ تحلیل خروجی نهایی نباید ناخواسته به SELECTهای nested در derivedQuery وارد شود.

### ۳.۴. دریافت Metadata در Executor و Provider

QueryRenderSelectBuilder دیگر EffectiveQueryMetadataProvider را پیاده‌سازی نمی‌کند و هیچ aggregation مربوط به گزارش را نگه نمی‌دارد. Builder به ساخت AST و نگهداری state موردنیاز composition ادامه می‌دهد و هنگام ساخت، دادهٔ گزارش لازم را در Metadata AST می‌نویسد.

QueryConsumer.details() ابتدا Provider اختیاری را برای سازگاری با پیاده‌سازی‌های سفارشی بررسی می‌کند؛ اگر Query از آن پشتیبانی نکند، EffectiveQueryMetadataAnalyzer را روی query.ast اجرا می‌کند. بدین ترتیب Query Builder پیش‌فرض از analyzer استفاده می‌کند و implementer سفارشی موجود می‌تواند قرارداد Provider را حفظ کند. چون Provider و DTO در query:api public هستند، در این Plan Provider از API حذف نمی‌شود؛ فقط رابطهٔ Builder با آن برداشته می‌شود. رفتار خطای نبود Provider در تست مصرف‌کننده باید متناسب با fallback AST بازنگری شود، نه اینکه بی‌دلیل باقی بماند یا برای AST قابل تحلیل گزارش خالی جعل شود.

### ۳.۵. وابستگی هدف

| ماژول | وابستگی production هدف پس از تغییر |
|---|---|
| query:api | بدون تغییر: core و AST |
| query:builder | core، AST و API؛ وابستگی مستقیم query:meta_data حذف شود |
| query:meta_data | AST و API برای انتخاب AST و تولید DTO؛ وابستگی core و kotlin-reflect فقط اگر source نهایی هنوز مستقیم به آن‌ها نیاز داشته باشد |
| query:executor | وابستگی فعلی حفظ شود و query:meta_data برای اجرای analyzer اضافه شود |
| query:renderer | بدون تغییر؛ تحلیل گزارش به Renderer منتقل نمی‌شود |
| query:example | بدون تغییر در formatter و فراخوانی گزارش |

نمودار جهت اصلی:

    query:builder → query:api → query:ast
    query:meta_data → query:api → query:ast
    query:executor → query:builder
    query:executor → query:meta_data

هیچ وابستگی از AST یا Metadata به Builder و هیچ وابستگی از API به Metadata ایجاد نمی‌شود. وابستگی test-only از تست Builder به analyzer فقط در صورت نیاز برای تست integration و با حفظ جهت acyclic مجاز است. وابستگی‌های مستقیم اضافی در پایان با source search و Gradle dependency report بازبینی شوند.

## ۴. فازهای اجرا

### فاز ۰ — تثبیت baseline و فهرست call siteها

**فایل‌ها:** بدون تغییر کد؛ مرور source و Gradle.  
**گام‌ها:** جست‌وجوی کل مخزن برای دو نام Resolver، Provider، متدهای گزارش و DTOها؛ ثبت وضعیت کاری Git قبل از شروع؛ بررسی همهٔ overloadهای with، cte، sourceهای derived و نحوهٔ ثبت metadata؛ ثبت جداگانهٔ دو ورودی knownRelations، ترتیب DFS dependency-first، deduplication بر اساس هویت و نحوهٔ همگام‌سازی آن با ast.withs.  
**تست/بررسی:** جست‌وجو با rg برای ModelMetadataResolver، QueryMetadataResolver، EffectiveQueryMetadataProvider و effectiveQueryMetadata؛ مرور فایل‌های test/Gradle؛ ثبت خروجی baseline تست‌های هدف گزارش و composition پیش از تغییر کد.  
**پایان فاز:** فهرست call siteها و semantics مورد انتظار با یافته‌های بخش ۲ تطبیق داشته باشد؛ موردی از بیرون دامنهٔ Builder/Metadata/Executor/Example بدون تصمیم باقی نماند؛ وضعیت dirty قبلی و فایل‌های خارج از scope مکتوب شده باشد.

**ثبت انجام فاز ۰ در 2026-10-20، فقط‌خواندنی:**

- شاخه در شروع main و هم‌تراز با origin/main بود، اما working tree از قبل به‌طور گسترده تغییرکرده بود: فایل‌های modified/deleted و untracked در API، AST، Builder، Metadata، Executor، Renderer، Example و اسناد وجود داشتند. این وضعیت به‌عنوان baseline موجود حفظ شد؛ هیچ‌یک از این تغییرات reset یا بازنویسی نشدند. فایل v17.0.md نیز از نوبت قبلی به‌صورت untracked موجود بود.
- جست‌وجوی کل مخزن، دو Resolver، دو تست Resolver، نه caller production در Builder، Provider در API و QueryConsumer در Executor را یافت. تست‌های report در Builder، API، Executor و Example نیز شناسایی شدند؛ مصرف‌کنندهٔ production دیگری برای Resolverها پیدا نشد.
- بازبینی سورس تأیید کرد که effectiveQueryMetadata()، knownRelations را از querySourceContext.dependencies() به‌علاوهٔ explicitCteRoots می‌سازد. syncCteWithItems() همین ریشه‌ها را می‌گیرد، closure را با DFS dependency-first و deduplication هویتی مرتب می‌کند و generated CTE items را پیش از explicitWithItems در AST می‌نویسد. cteWithItem() فعلی روی Metadata آیتم فقط withName را می‌نویسد و بدنهٔ AST را کپی می‌کند؛ بنابراین ترتیب لیست ممکن است ترتیب knownRelations را حفظ کند، اما اطلاعات runtime/logical و تشخیص قطعی relationهای object-backed باید جداگانه اثبات شوند.
- تست‌های موجود هم‌اکنون پوشش می‌دهند: ترتیب dependency-first در composition، حذف Cte root/source تکراری بر اساس identity، رد چرخه و نام مؤثر تکراری، جدایی نام runtime و WITH، جدایی WITH item از source occurrence، CTE inline و تفاوت projection ریشه با derived SELECT. پوشش مقایسهٔ کامل knownRelations با AST نهایی و parity همهٔ فیلدهای relation در ماتریس ریشه‌ها هنوز باید در فازهای ۳ و ۴ اضافه شود.
- baseline هدف در working tree فعلی با Gradle 8.14 اجرا شد: EffectiveQueryMetadataProviderTest برابر 21 passed، CteWithsIntegrationTest برابر 8 passed، و QueryConsumerTest برابر 18 passed؛ در هر سه، failure/error/skip صفر بود. اجرای اول با Gradle User Home پیش‌فرض به‌علت Access denied روی فایل wrapper lock شروع نشد؛ اجرای مجدد با Gradle User Home موجود در .gradle-user-home-test موفق شد. هشدار Kotlin دربارهٔ fallback هدف JVM 24 به JVM 22 هنگام Build ثبت شد. این نتایج baseline همین working tree هستند، نه ادعای موفقیت implementation آینده.

با ثبت این موارد، فاز ۰ ممیزی و baseline به پایان رسید. هنگام ثبت اولیهٔ این بخش، فازهای ۱ و ۲ انجام شده بودند و تحلیل/حذف گزارش Builder تا عبور از دروازهٔ knownRelations مجاز نبود؛ نتیجهٔ بررسی و عبور از آن دروازه در ثبت فازهای ۳ و ۴ آمده است.

### فاز ۱ — انتقال behavior-preserving Resolverها

**فایل‌ها:** دو فایل Resolver، ۹ caller ثبت‌شده در بخش ۲.۲، دو test Resolver و build.gradle.ktsهای Builder و Metadata.  
**گام‌ها:** انتقال package و مسیر Resolverها به builder.metadata.models و builder.metadata.queries؛ به‌روزرسانی importها بدون تغییر method body، ترتیب resolve، خطاها یا conventionها؛ انتقال تست‌های unit Resolver به Builder؛ حذف فایل/تست قدیمی از Metadata؛ حذف وابستگی Builder به Metadata پس از تأیید نبود مصرف دیگری.  
**تست:** تست‌های جدید Model/Query Resolver و :data_base:query:builder:compileKotlin.  
**پایان فاز:** تمام call siteها به package جدید اشاره کنند، تست Resolverها موفق باشد و query:builder برای Resolverها به query:meta_data وابسته نباشد.

**ثبت انجام فاز ۱ در 2026-10-20:**

- دو Resolver و تست‌هایشان به `query:builder` منتقل شدند؛ package declarationها و ۹ import production به‌روزرسانی شد. بدنه و رفتار Resolverها تغییر نکرد.
- وابستگی مستقیم Builder به `query:meta_data` حذف شد. با توجه به نبود مصرف core و kotlin-reflect در سورس باقی‌ماندهٔ Metadata، این دو dependency مستقیم نیز از آن ماژول حذف شدند؛ وابستگی AST حفظ شد.
- جست‌وجوی packageهای قدیمی در sourceهای فعال Builder/Metadata موردی نیافت.
- تست کامل Builder پس از انتقال: ۱۵۰ تست اجرا شد؛ ۱۴۸ موفق، ۱ ناموفق و ۱ skipped. شکست `TypedModelReferenceTest.renderer omits cleared table and select aliases()` در assertion خط ۵۶۴ است و در فایل‌های این انتقال تغییری ایجاد نشده؛ نتیجه به‌عنوان شکست موجود در working tree ثبت می‌شود و در این فاز اصلاح نشد.
- XML گزارش، تست‌های ModelMetadataResolver برابر ۶/۶ و QueryMetadataResolver برابر ۶/۶ را موفق ثبت کرد. Build با fallback Kotlin compiler به‌دلیل Access denied برای marker فایل daemon ادامه یافت و شکست compile نداشت.

### فاز ۲ — تثبیت قرارداد و آزمون AstSelector

**فایل‌ها:** فایل‌های جدید زیر query:meta_data/src/main/kotlin/.../ast یا .../selector و تست‌های متناظر؛ interfaceهای AST فقط اگر contract typed موجود برای یک relationship کافی نباشد.  
**گام‌ها:** API را بر مبنای relationshipهای واقعی بخش ۲.۳ تعریف کنید؛ یک مسیر nullable، یک رابطهٔ فهرستی و یک مسیر ترکیبی را در تست نشان دهید؛ Metadata selected node را بدون Resolver یا reflection annotation در دسترس قرار دهید؛ هیچ قابلیت SQL، report یا whole-query scanning وارد selector نشود.  
**تست‌ها:** انتخاب خود root، عبور از SELECT به ستون‌ها، عبور از joins به table، عبور از WITH به body، ترتیب list، رابطهٔ null و Metadata هر نوع selected node.  
**پایان فاز:** selector بدون import از Builder compile شود و رابطهٔ گم‌شده خروجی خالی/absence مستند داشته باشد.

**ثبت انجام فاز ۲ در 2026-10-20:**

- `AstSelector<T>` در بستهٔ `query.meta_data.ast` با `from`, `select` برای relationship nullable و `selectMany` برای relationshipهای مرتب پیاده شد؛ گره‌ها typed می‌مانند و metadata از همان گره‌ها خوانده می‌شود.
- تست‌ها root و Metadata آن، نبود رابطه، ترتیب SELECT columns، و مسیرهای JOIN→table و WITH→body را پوشش می‌دهند. نیازی به تغییر interfaceهای AST نبود.
- `:data_base:query:meta_data:test` موفق شد؛ ۴ تست selector موفق، بدون failure/error/skip. کامپایل Kotlin با fallback خارج از daemon انجام شد.

### فاز ۳ — ثبت دادهٔ لازم در AST موجود

**فایل‌ها:** Metadataهای AST در query:ast/src/main/kotlin/metadata/select/column/QueryColumnsAstMetadata.kt، .../table/QueryTableAstMetadata.kt، .../withs_item/QueryWithsItemAstMetadata.kt؛ سازنده‌های مرتبط در QueryColumnsBuilder، QueryTableBuilder، QueryWithsItemBuilder و QueryRenderSelectBuilder.  
**گام‌ها:** ابتدا به‌صورت صریح knownRelations را از دو ورودی فعلی querySourceContext.dependencies() و explicitCteRoots بسازید و خروجی orderedCteClosure را با AST نهایی مقایسه کنید؛ فقط بعد از ثبت نتیجه دربارهٔ کفایت ترتیب ast.withs تصمیم بگیرید. marker یا فیلد جدید را پیشاپیش قطعی نکنید. موارد هویت Cte، حذف تکرار، dependency order، چند root، explicit WITH خام/typed، source عادی/inline، override نام، و empty CTE list باید جدا بررسی شوند. پس از آن، برای هر دادهٔ گزارش که واقعاً از دست می‌رود کمترین Metadata لازم را روی AST موجود ثبت کنید؛ logicalOutputName را در نقطهٔ ساخت PropertyReference بنویسید؛ source kind و CTE facts را فقط در مسیرهایی که AST فعلی قادر به تمایز نیست پر کنید؛ نام runtime CTE، نام effective WITH و alias occurrence را جدا نگه دارید؛ در composition، override نام dependency و ترتیب closure را دست نزنید.  
**تست‌ها:** AST-builder assertions برای هر مسیر source؛ آزمون تفاوت جدول و CTE هم‌نام؛ آزمون تفاوت runtime name، withName override و occurrence alias؛ آزمون property بدون getter؛ آزمون خروجی DSL alias و logical output alias مستقل؛ تست differential که ترتیب و تعداد نماینده‌های knownRelations در AST را در برابر orderedCteClosure و context فعلی بسنجد.  
**پایان فاز:** برای تمام ماتریس فوق برابری ترتیب/تعداد relationهای مرجع و نمایش AST اثبات شده باشد یا شکاف با کوچک‌ترین فیلد/رابطهٔ Metadata مستند و پوشش داده شود؛ تا آن زمان انتقال گزارش به Analyzer و حذف contextهای لازم ممنوع است. Renderer/SQL تغییر نکند.

**ثبت انجام فاز ۳ در 2026-10-20:**

- ابتدا هر دو ریشهٔ `querySourceContext.dependencies() + explicitCteRoots` و خروجی closure مرتب‌شدهٔ فعلی بررسی شدند. در composition، generated `ast.withs` همان ترتیب DFS وابستگی‌پیش‌از‌مصرف‌کننده و حذف تکرار هویتی را نگه می‌دارد؛ موارد explicit WITH خام پس از generated CTEها می‌آیند. آزمون هدفمند چند dependency، dependency مشترک، تکرار یک Cte با همان هویت، چند ریشه، source ریشه و WITH خام را پوشش می‌دهد و لیست Metadata گره‌های WITH را با ترتیب مورد انتظار knownRelations می‌سنجد.
- AST پیش از تغییر، runtime identity مربوط به CTE و logical output name را برای تحلیل مستقل نگه نمی‌داشت. این مقادیر اکنون در Metadata گره‌های WITH و table و column ثبت می‌شوند. `isCteObjectSource` نیز فقط برای تفکیک مسیر Cte object از `cte(String)` افزوده شد: آزمون نشان داد نام یکسان به‌تنهایی برای بازسازی رفتار قبلی `namedCteSourceConfigured` کافی نیست. فیلدهای نام runtime، نام منطقی، نام مؤثر WITH و alias محل استفاده جدا باقی می‌مانند؛ WITH خام CTE identity دریافت نمی‌کند.
- مسیرهای model، table، named CTE، inline/composed CTE و derived SELECT در تست‌های AST بررسی شدند؛ property getter فراخوانی نمی‌شود. آزمون‌های `CteWithsIntegrationTest` و `EffectiveQueryMetadataProviderTest` پس از تغییر AST موفق شدند. در ماتریس closure ترتیب و تعداد رابطه‌های مرجع از AST نهایی قابل بازسازی است؛ شکاف‌های هویت/نام با Metadata حداقلی پوشش داده شدند، بنابراین gate فاز ۳ عبور کرد.

### فاز ۴ — پیاده‌سازی تحلیل‌گر گزارش با selector

**فایل‌ها:** کلاس جدید analyzer در query:meta_data/src/main/kotlin/.../analysis؛ تست‌های آن؛ تغییر query:meta_data/build.gradle.kts برای API dependency.  
**گام‌ها:** aggregation فعلی را در کنار Builder حفظ کنید و منطق متناظر را در effectiveQueryMetadata(), outputSource(), outputSourceCandidate() و relationMetadata() به Analyzer منتقل کنید؛ گره‌ها را فقط با AstSelector انتخاب کنید؛ هیچ annotation، property getter، Builder class یا Cte instance را resolve نکنید؛ DTOهای فعلی API را تولید کنید؛ قواعد یکتایی/ambiguity و nullهای فعلی را حفظ کنید. تا عبور از differential tests، نسخهٔ Builder همچنان oracle است و حذف آن به فاز ۵ موکول می‌شود.  
**تست‌ها:** test fixtureهای AST برای projection ساده، model/table، source unresolved/ambiguous، JOIN، WITH، CTE occurrence، derived SELECT، typed output، output alias و execution type. برای relationها، خروجی Analyzer را با فهرست/ترتیب baseline knownRelations و گزارش Builder مقایسه کنید؛ مقایسه باید موردبه‌مورد و شامل تمام فیلدهای EffectiveRelationMetadata باشد، نه فقط نام‌های فهرست.  
**پایان فاز:** analyzer مستقل از Builder باشد و برای ماتریس فاز ۳، EffectiveQueryMetadataAnalyzer(ast) با گزارش فعلی Builder دقیقاً برابر باشد؛ به‌ویژه relations از نظر تعداد، ترتیب و تمام فیلدها یکسان باشند. فقط پس از این پذیرش می‌توان وارد فاز ۵ شد.

**ثبت انجام فاز ۴ در 2026-10-20:**

- `EffectiveQueryMetadataAnalyzer` در query:meta_data با استفاده از AstSelector و Metadata AST پیاده شد؛ وابستگی به Builder، Cte instance، Resolver، reflection و getter ندارد. DTOهای API و رفتار null/ambiguity گزارش قبلی حفظ شدند. `query:meta_data` به API وابسته شد و تست Builder برای مقایسهٔ موقت با گزارش قدیمی، وابستگی test-only به Metadata دارد.
- پنج آزمون differential پیش از حذف گزارش Builder با `assertEquals` کل DTO را مقایسه کردند؛ در نتیجه تمام فیلدهای `EffectiveQueryMetadata`، شامل تمام relation/outputها و ترتیب، در این ماتریس برابر بودند: closure و override نام WITH، CTE inline و typed، تفاوت CTE نام‌دار و جدول هم‌نام، JOIN مبهم/unresolved، derived SELECT، مدل و raw expression. تست‌ها موفق شدند؛ ۵ اجرا، ۰ failure/error/skip. پس از ثبت برابری، تست‌ها به assertionهای قرارداد Analyzer تبدیل شدند تا بعد از حذف Provider نیز به‌عنوان regression باقی بمانند.
- Analyzer از AST نهایی، generated WITHها را به ترتیب ثبت‌شده می‌خواند و WITH خام را از روی خالی‌بودن هویت CTE تشخیص می‌دهد. نتیجه ثابت کرد `logicalQueryName` و `cteRuntimeName` به‌تنهایی برای منبع CTE کافی نبودند؛ `isCteObjectSource` که در فاز ۳ افزوده شد، تفاوت موردنیاز را نگه می‌دارد. با عبور از معیار differential وارد فاز ۵ شدیم.

### فاز ۵ — اتصال Executor و حذف گزارش از Builder

**فایل‌ها:** QueryConsumer.kt، query/executor/build.gradle.kts، QueryRenderSelectBuilder.kt، تست‌های Builder و Executor.  
**گام‌ها:** وابستگی production query:meta_data را به Executor اضافه کنید؛ QueryConsumer.details() را به Provider اختیاری و سپس analyzer AST وصل کنید؛ پیاده‌سازی Provider و DTO imports را از QueryRenderSelectBuilder حذف کنید؛ helperها و data classهای صرفاً گزارش را از Builder پاک کنید؛ composition/contextهای مورد استفاده در ساخت را نگه دارید؛ Provider API را برای implementerهای سفارشی حفظ کنید.  
**تست‌ها:** standard Builder با مسیر analyzer؛ Provider سفارشی همچنان honored شود؛ details() مستقل از .sql()؛ تغییر/عدم تغییر AST بین فراخوانی‌ها مطابق semantics جاری؛ .sql(), .execute() و parameter rendering بدون تغییر.  
**پایان فاز:** Builder هیچ aggregation گزارش نداشته باشد، QueryConsumer به گزارش استاندارد دسترسی داشته باشد و composition/SQL regression نداشته باشد.

**ثبت انجام فاز ۵ در 2026-10-20:**

- وابستگی production `query:meta_data` به Executor افزوده شد. `QueryConsumer.details()` ابتدا Provider اختیاری را honor می‌کند و در نبود آن Analyzer را روی AST اجرا می‌کند؛ API عمومی Provider حفظ شد.
- `QueryRenderSelectBuilder` دیگر Provider نیست و aggregation، helperها و DTO imports مربوط به گزارش از آن حذف شدند. state لازم برای composition، CTE closure و ساخت WITHها باقی ماند؛ `namedCteSourceConfigured` که فقط برای گزارش استفاده می‌شد، پس از ثبت هویت متناظر در AST حذف شد.
- تست‌ها مسیر استاندارد Builder→Analyzer، API سفارشی Provider، query سفارشی بدون Provider، `.details()` پیش/پس از SQL، `.execute()`، پارامترها و CTE را پوشش می‌دهند. تست‌های هدفمند Builder (Effective Metadata: ۲۲، CTE composition: ۱۲ و Analyzer: ۵) و QueryConsumer (۱۹) موفق شدند؛ composition و SQL به تغییر نیاز نداشتند.

### فاز ۶ — یکپارچه‌سازی تست‌ها و نمونه‌ها

**فایل‌ها:** EffectiveQueryMetadataProviderTest.kt یا نام تازهٔ متناسب با analyzer، EffectiveQueryMetadataContractTest.kt، QueryConsumerTest.kt، EffectiveQueryMetadataTableTest.kt و مثال‌های V1/V2/V3 فقط اگر call site واقعاً تغییر لازم دارد.  
**گام‌ها:** تست‌هایی که Builder را به Provider cast می‌کنند به analyzer یا QueryConsumer.details() تغییر کنند؛ تست DTO/Provider سفارشی و formatter حفظ شود؛ تست‌های موجود CTE و Query relation را به‌عنوان regression اجرا کنید؛ فرمت table و متن Final SELECT outputs را بدون نیاز واقعی تغییر ندهید.  
**تست‌های تکمیلی گزارش:** direct table و model، typed CTE، explicit WITH، dependency order، name override، JOIN alias یکتا/تکراری، expression فاقد منبع، nested derived SELECT، حفظ خروجی نهایی به‌جای خروجی nested و nullهای تعریف‌شده.  
**پایان فاز:** نمونهٔ فعلی همان مقادیر منطقی را نشان دهد و تمامی assertionهای قبلی با مسیر جدید پوشش داشته باشند.

**ثبت انجام فاز ۶ در 2026-10-20:**

- تست‌های Builder که Provider را cast می‌کردند به Analyzer تغییر کردند؛ تست composition نیز ترتیب relationها را از خروجی Analyzer می‌سنجد. تست‌های DTO و custom Provider در API و Executor باقی ماندند.
- نمونه‌های V1/V2/V3 هم‌اکنون از `QueryConsumer.details()` و formatter موجود استفاده می‌کنند؛ call site تغییر لازم نداشت، بنابراین formatter و مثال‌ها دست‌نخورده ماندند.
- تست ماژول Example یک شکست دارد: `V3QueryRuntimeNameTest.kt:87` مقدار typed output `fullName` را می‌خواند درحالی‌که projection متناظر در `UserDisplayQueryV3` کامنت شده است؛ خطا در `CteSourceContext.validateTypedOutput` رخ می‌دهد، پیش از هر تحلیل Metadata. این ناسازگاری خارج از انتقال گزارش است و در این مرحله تغییر نکرد.

## ۵. معیارهای پذیرش

### Resolverها
- تمام call siteهای فعال از packageهای Builder استفاده کنند.
- convention، اولویت Annotation، unset/خالی، validation و خطاهای قبلی حفظ شود.
- تست‌های Resolver پس از انتقال موفق باشند.
- query:meta_data دیگر Resolver declaration نداشته باشد و هیچ reference قدیمی باقی نماند.

### Selector
- از AST مشخص شروع کند و relationshipهای typed را به انتخاب تبدیل کند.
- ترتیب گره‌های چندتایی را حفظ کند و Metadata خود گره را بدهد.
- nullable relationship را با absence روشن نمایش دهد.
- به Builder، Resolver، Renderer یا گزارش خروجی وابسته نباشد.
- behavior را با تست‌های مستقل پوشش دهد.

### گزارش
- خروجی EffectiveQueryMetadata برای مثال فعلی برابر معنای قبلی باشد.
- tableName، tableAlias، logicalOutputName، publishedSqlAlias و executionType همچنان معانی و precedence قبلی را داشته باشند.
- نام runtime CTE، نام SQL در WITH و alias occurrence جدا بمانند.
- table، model، typed/inline/named CTE، WITH صریح، JOIN و derived SELECT به‌درستی پوشش داده شوند.
- ambiguity و source unresolved همان nullها/aliasهای فعلی را تولید کنند؛ fallback جدید ساخته نشود.
- فقط projection نهایی در outputs قرار گیرد و relation outputها در relations باقی بمانند.
- Builder فقط سازنده و مدیر composition باشد و تحلیل‌گر خروجی نداشته باشد.
- formatter و SQL render و پارامترها و execution بدون تغییر رفتار بمانند.

### وابستگی و یکپارچگی
- Builder برای ساخت AST به Metadata وابسته نباشد.
- Metadata فقط AST و API را برای تحلیل لازم داشته باشد؛ هر dependency دیگر با source usage توجیه شود.
- Executor analyzer را بدون dependency معکوس قابل فراخوانی کند.
- هیچ cycle بین API، AST، Builder، Metadata و Executor پدید نیاید.

## ۶. ریسک‌ها و کنترل

- **از دست رفتن اطلاعات در AST:** resolverها و contextهای Builder در چند مسیر source مقدار می‌سازند. جدول تست source pathها پیش از حذف Provider از Builder باید سبز باشد.
- **اشتباه گرفتن نام‌ها:** withName ممکن است با Cte.name فرق کند؛ فیلدهای نام‌دار باید جدا و تست شوند.
- **تغییر معنای property output:** الان گزارش از PropertyReference استفاده می‌کند؛ مقدار logical name باید همان resolver و همان لحظهٔ ساخت resolve شود، نه از alias SQL یا type property.
- **ترتیب closure و explicit WITH:** ترتیب فعلی حاصل الگوریتم Builder است؛ selector نباید ترتیب را sort کند و analyzer باید ترتیب AST را حفظ کند.
- **عبور ناخواسته به nested SELECT:** مسیر انتخاب خروجی نهایی باید صریحاً فقط SELECT ریشه را دنبال کند.
- **تغییر API ناخواسته:** DTO، formatter و Provider interface public حفظ شوند؛ فقط QueryRenderSelectBuilder دیگر Provider نباشد.
- **تغییر در working tree موجود:** در شروع و پایان وضعیت Git بررسی شود و تغییرات قبلی دست‌نخورده بمانند؛ هیچ stage یا commit انجام نشود.
