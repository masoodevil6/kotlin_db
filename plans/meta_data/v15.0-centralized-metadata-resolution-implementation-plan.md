# Plan 15.0 — برنامهٔ اجرایی متمرکزسازی حل Metadata

## وضعیت

**پیشنهاد اجرایی برای بازبینی — اجرای کد مجاز نیست.**

سند معماری [Plan 15.0](v15.0-centralized-metadata-resolution-plan.md) همچنان `Draft` است. این سند فقط ترتیب و معیارهای اجرای تصمیم‌های ثبت‌شده در آن را مشخص می‌کند؛ تغییر آن تصمیم‌ها یا شروع پیاده‌سازی را مجاز نمی‌کند.

## ۱. دامنه و قراردادهای ثابت

هدف، انتقال تفسیر annotationها، conventionها و اعتبارسنجی metadata اعلامی Model و Query از `query:builder` به `query:meta_data` است. Builder همچنان AST و DSL را می‌سازد و overrideهای همان محل استفاده را اعمال می‌کند.

در تمام مراحل الزامی است که:

- Model metadata و Query metadata دو قرارداد مجزا بمانند.
- هر resolver فقط فیلدی را که فراخواننده درخواست کرده resolve و validate کند. برای نمونه، `queryName(type)` نباید `queryAlias(type)` را زودتر اعتبارسنجی کند؛ همین استقلال برای نام/alias جدول، ستون و خروجی Query رعایت شود.
- تفاوت `QB_METADATA_UNSET` با رشتهٔ خالی عیناً حفظ شود. قواعد مشخص هر فیلد در بخش ۲ آمده است.
- metadata از همان `KClass` یا `KProperty1` ورودی خوانده شود؛ getter اجرا نشود و جست‌وجوی property هم‌نام یا پیمایش superclass اضافه نشود.
- convention یا annotation مقدار پایه را تعیین کند؛ overrideهای صریح DSL/API و تقدم آن‌ها در Builder باقی بماند.
- نام منطقی خروجی Query از alias منتشرشدهٔ SQL آن جدا بماند. نام تعریف، نام runtime در CTE و alias هر occurrence نیز یکی تلقی نشوند.
- `declarationOwner`، composition validation، هویت runtime، alias occurrence، ساخت AST، `PropertyReference`، `ExecutionType` و تعیین مالک property typed در Builder بمانند.
- قرارداد موجود `QueryParameterMetadata` و `QueryParameterMetadataExtractor` حفظ شود؛ این Plan آن‌ها، Renderer، Executor، Migration، `QBCte*` یا APIهای legacy را بازطراحی نمی‌کند.
- typeها و توابعی که Builder از ماژول جداگانه فراخوانی می‌کند Kotlin `public` باشند. `internal` فقط برای helperهایی مجاز است که از مرز ماژول عبور نمی‌کنند. این الزام دسترسی بین ماژول‌های همین Repository است و تضمین ABI یا انتشار بیرونی نیست.

## ۲. خط مبنای تأییدشده از سورس

در زمان این بازبینی، branch برابر `main...origin/main` بود. سند معماری `v15.0-centralized-metadata-resolution-plan.md` از قبل untracked بود؛ سند اجرایی هنوز وجود نداشت. تغییر tracked دیگری در `git status --short --branch` دیده نشد. فهرست call siteها در این سند از جست‌وجوی سورس فعال به‌دست آمده است و در مرحلهٔ ۰ باید پیش از هر تغییر دوباره استخراج شود.

پیاده‌سازی قواعد فعلی در `data_base/query/builder/src/main/kotlin/ast/select_builder/metadata/QueryBuilderMetadata.kt` قرار دارد. این `internal object` متدهای مستقل `requireTable`, `requireColumn`, `tableName`, `tableAlias`, `columnName`, `columnAlias`, `queryName`, `queryAlias`, `queryLogicalOutputName` و `queryPublishedAlias` دارد. `requireTable` وجود `QBTable` و نام جدول را بررسی می‌کند؛ `requireColumn` وجود `QBColumn` و نام ستون را بررسی می‌کند. این اعتبارسنجی‌های صریح و زمان آن‌ها باید حفظ شوند. درخواست نام Query نباید به‌تنهایی alias آن را بررسی کند.

Annotationهای در scope در `data_base/core/src/main/kotlin/annotations/models/AnnotationModelTable.kt`, `AnnotationModelColumn.kt`, `AnnotationQuery.kt`, `AnnotationQuerySelect.kt` و `AnnotationMetadataDefaults.kt` تعریف شده‌اند. Annotationها runtime-retained هستند. مقدار unset برابر sentinel `"\u0000"` است.

قواعد مقدار فعلی که migration باید حفظ کند:

| فیلد | Sentinel / مقدار پیش‌فرض فعلی | رشتهٔ خالی و validation |
|---|---|---|
| `QBTable.name` | convention از نام کلاس با حذف پسوند `Model` و تبدیل snake case | نام خالی نامعتبر است |
| `QBTable.alias` | همان convention جدول | alias صریح خالی به‌معنای نداشتن alias است |
| `QBColumn.name` | نام property | مقدار خالی نامعتبر است |
| `QBColumn.alias` | نام property | annotation خالی نیز به نام property برمی‌گردد؛ override خروجی صریح در Builder می‌ماند |
| `QBQuery.name` | convention از نام کلاس با حذف پسوند `Query` و تبدیل snake case | مقدار خالی نامعتبر است |
| `QBQuery.alias` | همان convention Query | مقدار خالی نامعتبر است؛ این field مستقل از نام است |
| `QBQuerySelect.name` | snake case نام property به‌عنوان نام منطقی | مقدار خالی نامعتبر است |
| `QBQuerySelect.alias` | snake case نام property به‌عنوان alias منتشرشدهٔ SQL | مقدار خالی نامعتبر است؛ مستقل از نام منطقی است |

### ۲.۲ وضعیت فعلی ماژول‌ها و تست‌ها

- `data_base/query/meta_data/build.gradle.kts` از `kotlin("jvm")` استفاده می‌کند، `tasks.test { useJUnitPlatform() }` دارد، و اکنون به `core` و `query:ast` وابسته است؛ dependency صریح `kotlin-reflect` ندارد. فایل‌های `parameters/QueryParameterMetadata.kt` و `QueryParameterMetadataExtractor.kt` و تست `parameters/QueryParameterMetadataTest.kt` موجودند و نباید بازطراحی شوند.
- `data_base/query/builder/build.gradle.kts` plugin مشابه دارد، JUnit Platform را برای `test` پیکربندی می‌کند و dependency فعلی `org.jetbrains.kotlin:kotlin-reflect:1.8.20` را دارد؛ این dependency در Plan حذف نمی‌شود. `query:meta_data` از قبل در `settings.gradle.kts` include شده است.
- APIهای `tableColumn` و `column(KClass, KProperty1)` در `query:api` دقیقاً `KProperty1<T, R>` می‌گیرند. پارامتر نوع `T` با Model مورد استفاده یکی است. `KProperty1` برای receiver کنتراواریانت است؛ بنابراین signature از نظر نوع اجازه می‌دهد reference property پایه به‌عنوان reference برای Model زیرکلاس فرستاده شود. نتیجهٔ واقعی `property.annotations` برای چنین referenceای هنوز باید با تست محدود پیاده‌سازی تأیید شود؛ این مجوز hierarchy traversal نیست.
- تست‌های موجودی که باید body و assertion آن‌ها حفظ و بازبینی شود:
  - `data_base/query/builder/src/test/kotlin/ast/select_builder/QueryMetadataResolutionTest.kt`، package `gog.my_project.data_base.query.builder.ast.select_builder`. assertionهای مستقیم `QueryBuilderMetadata` در حدود خطوط 157–158 و 290–298 باید به تست resolver منتقل شوند؛ assertionهای AST، runtime naming، typed output و composition در Builder بمانند.
  - `data_base/query/builder/src/test/kotlin/ast/select_builder/TypedModelReferenceTest.kt`، همان package؛ تست‌های Model، aliasها، annotationهای خالی/مفقود و AST/renderer را نگه دارد.
  - `data_base/query/builder/src/test/kotlin/ast/select_builder/QueryDeclarationTest.kt` و `data_base/query/builder/src/test/kotlin/ast/select_builder/CteWithsIntegrationTest.kt`، همان package؛ تست‌های declaration، composition و نام‌گذاری در Builder باقی بمانند.
  - `data_base/query/example/src/test/kotlin/v3/V3QueryRuntimeNameTest.kt`، package `gog.my_project.data_base.query.example.v3`; آزمون regression نام runtime و alias occurrence است.
  - `data_base/query/meta_data/src/test/kotlin/gog/my_project/data_base/query/meta_data/parameters/QueryParameterMetadataTest.kt`، package `gog.my_project.data_base.query.meta_data.parameters`; حفظ و اجرای آن بخشی از تست کامل metadata است.

در زمان این بررسی، تست‌های resolver مدل/Query در `query:meta_data` وجود نداشتند. نام فایل‌ها و packageهای آن‌ها در بخش ۴ proposal هستند، نه فایل‌های موجود یا نتایج اجراشده.

## ۳. قرارداد API هدف و وابستگی‌ها

API field-specific زیر نمونهٔ اجرایی پیشنهادی بر مبنای helperهای فعال فعلی است؛ نام‌ها final نمی‌شوند تا در بازبینی implementation با convention package هماهنگ شوند. Resolverهای Model و Query جدا می‌مانند. نوع‌های تجمیعی `ModelMetadata.kt` و `QueryMetadata.kt` فقط وقتی اضافه شوند که برای خروجی resolved واقعی لازم باشند؛ ساخت آن‌ها نباید فیلدهای مستقل را eager resolve/validate کند.

```kotlin
// Package پیشنهادی: gog.my_project.data_base.query.meta_data.models
object ModelMetadataResolver {
    fun requireTable(type: KClass<*>): Unit
    fun requireColumn(type: KClass<*>, property: KProperty1<*, *>): Unit
    fun tableName(type: KClass<*>): String
    fun tableAlias(type: KClass<*>): String
    fun columnName(type: KClass<*>, property: KProperty1<*, *>): String
    fun columnAlias(property: KProperty1<*, *>): String
}

// Package پیشنهادی: gog.my_project.data_base.query.meta_data.queries
object QueryMetadataResolver {
    fun queryName(type: KClass<*>): String
    fun queryAlias(type: KClass<*>): String
    fun queryLogicalOutputName(property: KProperty1<*, *>): String
    fun queryPublishedAlias(property: KProperty1<*, *>): String
}
```

امضاها نمونهٔ migration هستند. تفاوت مهم با helper قدیمی این است که resolver باید annotation را از class/property ورودی خودش بخواند، نه اینکه Builder یک annotation را resolve و به resolver دیگر پاس دهد. اگر برای حفظ دقیق زمان خطا، قرارداد `requireTable`/`requireColumn` به امضای دیگری نیاز داشت، آن تغییر باید با تست خط مبنا توجیه شود. هر نماد مورد استفادهٔ Builder `public` است؛ helperهای private/internal بیرون از API باقی می‌مانند. `QBColumn.primaryKey` در این Plan resolver ندارد، چون call site فعال هدفی برای آن یافت نشد.

وابستگی هدف:

```text
query:meta_data -> core
query:meta_data -> query:ast        (قرارداد parameter extractor فعلی؛ حفظ)
query:meta_data -> kotlin-reflect   (annotation lookup)
query:builder -> query:meta_data
query:builder -> kotlin-reflect     (dependency فعلی برای property.returnType/parameters)
```

`query:meta_data` نباید به Builder، Renderer، Executor، Manager، Migration یا نمونه‌های Model وابسته شود. تغییر `builder/build.gradle.kts` فقط dependency یک‌طرفهٔ بالا را اضافه می‌کند. `settings.gradle.kts` از قبل ماژول را include می‌کند و در نبود شواهد تازه تغییر نمی‌کند.

## ۴. فازهای اجرایی

هر فاز یک واحد مستقل و قابل بازبینی است. در صورت شکست assertion، تغییر خارج از inventory، نیاز به API جدید غیرضروری یا تغییر رفتار، همان فاز متوقف و گزارش شود؛ تغییر رفتار برای سبزکردن تست مجاز نیست.

### فاز ۰ — ثبت baseline و نهایی‌کردن inventory

**فایل‌های تغییر مورد انتظار:** هیچ فایلی.

**کارها:** وضعیت Git و فایل‌های untracked ثبت شوند؛ جست‌وجوی فعال `QueryBuilderMetadata`, `findAnnotation<QBQuery>`, `property.returnType` و `property.parameters` تکرار شود؛ body/assertion تست‌های بخش ۲.۲ بازبینی شود. هیچ تغییر قبلی بی‌مدرک به Plan 15 نسبت داده نشود.

**پذیرش:** inventory این سند با working tree لحظهٔ شروع تطبیق داده شود؛ برای هر assertion که منتقل یا حفظ می‌شود جایگاه آن مشخص باشد؛ تست‌ها یا source baseline موفق فرض نشوند مگر خروجی اجرای همان زمان موجود باشد.

**توقف:** اگر call site فعال تازه‌ای پیدا شد، پیش از migration دامنه‌اش در inventory ثبت شود. اگر تغییر dirty موجود نسبت‌دادنی نیست، حفظ و جدا گزارش شود.

### فاز ۱ — وابستگی Reflection ماژول Metadata

**فایل تغییر مورد انتظار:** `data_base/query/meta_data/build.gradle.kts`.

**کار مجاز:** افزودن `implementation("org.jetbrains.kotlin:kotlin-reflect:1.8.20")` برای annotation lookup، هم‌نسخه با dependency صریح موجود در Builder. dependency فعلی Builder حذف یا جابه‌جا نشود.

**پیش‌نیاز:** baseline فاز ۰؛ امضاهای public resolver برای استفاده از `KClass`/`KProperty1`.

**آزمون/پذیرش:** task کامپایل و تست metadata اجرا شود تا resolve شدن reflection در source و test source اثبات شود؛ فایل‌های parameter metadata و test آن بدون تغییر بمانند.

**توقف:** اگر dependency موجود از راه دیگری فراهم است یا نسخهٔ سازگار روشن نیست، dependency را حدس نزن؛ configuration فعلی و مانع را گزارش کن.

**دلیل تقدم:** در `meta_data/build.gradle.kts` اکنون dependency صریح reflection وجود ندارد، حال آنکه Builder آن را صریحاً با نسخهٔ `1.8.20` نیاز دارد. Resolverهای annotation از reflection استفاده می‌کنند؛ بنابراین compile dependency باید قبل از نوشتن resolver اثبات شود. این تغییر فقط setup مرحله‌ای است.

### فاز ۲ — Resolver و قرارداد Model

**فایل‌های مورد انتظار:**

- افزوده‌شونده: `data_base/query/meta_data/src/main/kotlin/models/ModelMetadataResolver.kt`.
- افزوده‌شونده فقط در صورت نیاز به type خروجی مستقل: `data_base/query/meta_data/src/main/kotlin/models/ModelMetadata.kt`.
- افزوده‌شونده: `data_base/query/meta_data/src/test/kotlin/gog/my_project/data_base/query/meta_data/models/ModelMetadataResolverTest.kt`.
- تغییر/حفظ: `data_base/query/meta_data/build.gradle.kts` فقط dependency فاز ۱.

**کار مجاز:** انتقال قواعد فعال `QBTable` و `QBColumn` به resolver field-specific. حفظ پیام/زمان validation مفقودی annotation و رشتهٔ خالی، convention و distinction alias خالی. هیچ AST یا Builder تغییر نکند.

## ۷. ریسک‌ها و موارد قابل‌تأیید

### موانع مسدودکنندهٔ اجرای هر فاز

- API resolver مورد نیاز Builder از module دیگر `public` نیست یا dependency جهت معکوس ایجاد می‌کند.

### موارد قابل‌تأیید حین implementation، نه مانع طراحی

- نتیجهٔ دقیق `KProperty1.annotations` برای inherited Model property reference، فقط در صورت استفادهٔ واقعی از همان reference و با یک تست محدود.

- task resolution در Gradle در صورت تفاوت محیط محلی؛ taskهای ثبت‌شده از Kotlin JVM plugin و build files استخراج شده‌اند، اما در این تدوین اجرا نشده‌اند.

### موارد خارج از scope

- external source/binary compatibility یا سیاست انتشار artifact که در Repository شواهدی برای آن پیدا نشده است.
- inheritance traversal، caching، generic metadata framework، `QBColumn.primaryKey`, APIهای legacy `QBCte*`, Migration، Renderer، Executor، SQL یا تغییر Query construction.
