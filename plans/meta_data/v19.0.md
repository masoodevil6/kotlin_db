# پلن 19.0: واشکافی سورس CTE و تدوین پلن انتقال به ماژول مستقل

**وضعیت:** گزارش بررسی و طرح پیشنهادی؛ اجرای انتقال نیازمند تأیید جداگانه است.  
**تاریخ بررسی سورس:** ۲۲ اکتبر ۲۰۲۶  
**دامنه:** تعیین مالکیت فعلی اجزای CTE و ارزیابی مسیر کم‌ریسک برای انتقال بخش‌های واقعاً مستقل به `:data_base:query:cte`.

## ۱. هدف و محدودیت

این سند مبنای بررسی مرحله‌ای CTE و تصمیم‌گیری دربارهٔ مرز ماژول آن است. هدف، انتقال همهٔ فایل‌هایی که نام CTE دارند نیست؛ هر جزء باید بر اساس مسئولیت و وابستگی واقعی‌اش ارزیابی شود.

این مرحله فقط شامل بررسی سورس، ثبت یافته‌ها و تدوین پلن است. هیچ فایل سورس، package، import یا فایل Gradle در این مرحله تغییر نمی‌کند و هیچ فایل یا تغییری stage یا commit نمی‌شود.

خارج از محدوده‌اند: بازطراحی Executor، پارامترهای خروجی و انتقال آن‌ها، دسترسی تایپ‌شده به نتیجه مانند `row.v3_user_display.fullName`، بازطراحی Query API یا سیستم `WITH` و افزودن قابلیت CTE جدید. اگر در این حوزه‌ها وابستگی‌ای مشاهده شود، فقط ثبت می‌شود.

## ۲. مبنای بررسی و وضعیت مخزن

بررسی بر اساس سورس موجود در checkout مورخ ۲۲ اکتبر ۲۰۲۶ انجام شد. `git status --short` تغییرات متعدد از قبل موجود در ماژول‌های Query و فایل‌های untracked را نشان می‌دهد. به‌طور مشخص، `data_base/query/builder/src/main/kotlin/ast/select_builder/cte/CteAstComposer.kt` در وضعیت فعلی untracked است. بنابراین این سند رفتار checkout فعلی را توصیف می‌کند، نه لزوماً رفتار آخرین commit؛ این وضعیت باید پیش از اجرای هر مرحلهٔ انتقال دوباره ثبت و با مالک تغییرات تطبیق داده شود.

در `settings.gradle.kts:44-52` ماژول‌های `:data_base:query:api`، `:ast`، `:builder`، `:meta_data`، `:dialect`، `:renderer`، `:executor` و `:example` تعریف شده‌اند؛ ماژول `:data_base:query:cte` در حال حاضر وجود ندارد.

## ۳. خلاصهٔ یافته‌های فعلی

### ۳.۱ قراردادهای API

- `api/interfaces/relations/Cte.kt:10-16` قرارداد عمومی `Cte` را تعریف می‌کند: `name`، `definition: IQueryApi<IQueryRenderSelectAst>` و `dependencies` که به‌صورت پیش‌فرض خالی است. این قرارداد هم به API Query و هم به AST وابسته است.
- `api/interfaces/relations/ICteDeclaration.kt:4-8` قرارداد ورودی declaration را تعریف می‌کند (`params` و `createCte`). این نوع در امضای عمومی `IQueryTableApi.cte(declaration)` استفاده می‌شود.
- `api/interfaces/cte/ICte.kt:5-7` قرارداد قدیمی `cteQuery()` را نگه می‌دارد. `IQueryWithsItemApi.with(name, ICte)` در `IQueryWithsItemApi.kt:14-18` هنوز آن را در API عمومی مصرف می‌کند و `QueryWithsItemBuilder.kt:33-50` مستقیماً `cteQuery().ast` را می‌گیرد. کامنت‌های `TODO/REMOVE` به‌تنهایی مجوز حذف آن در این انتقال نیستند.
- APIهای عمومی `IQueryTableApi` مسیرهای `table(String)`، `table(SELECT block)`، `cte(ICteDeclaration)`، `cte(Cte)` و `cte(String)` را از هم تفکیک می‌کنند. `IQueryWithsItemApi` نیز فرم CTE، فرم نام‌دار CTE و فرم ساخت مستقیم WITH از block را ارائه می‌دهد.

### ۳.۲ AST و سیستم WITH

- `ast/interfaces/select_interface/withs/IQueryWithsAst.kt:7-10` یک فهرست mutable از `IQueryWithsItemAst` نگه می‌دارد.
- `IQueryWithsItemAst.kt:7-11` بدنهٔ Query را نگه می‌دارد؛ `metadata/select/withs_item/QueryWithsItemAstMetadata.kt:5-11` نام WITH، نام runtime CTE و نام منطقی Query را از هم جدا می‌کند.
- `interfaces/select_interface/table/IQueryTableAst.kt:7-10` نیز `derivedQuery` دارد. در نتیجه AST بین منبع نام‌دار و derived SELECT تمایز ساختاری دارد.
- این ساختارها بخشی از AST عمومی Query هستند و Renderer آن‌ها را مصرف می‌کند. انتقال آن‌ها به ماژول CTE وابستگی AST به CTE یا جابه‌جایی مسئولیت AST را ایجاد می‌کند و از شواهد فعلی لازم نیست؛ مالکیت آن‌ها باید در `:ast` بماند.
- `QueryWithsBuilder` و `QueryWithsItemBuilder` در `:builder` مسیرهای `with(cte)`، `with(name, cte)` و `with(name, block)` را می‌سازند. دو فرم CTE ریشه و override نام را برای composition ثبت می‌کنند؛ فرم block بدنهٔ AST را مستقیم می‌سازد. این سازوکار، مالک ساخت `WITH` است و در این طرح بازطراحی نمی‌شود.

### ۳.۳ ساخت CTE و composition

- `builder/ast/select_builder/cte/CteBuilder.kt:15-96` دو factory عمومی `cte(...)` و extension عمومی `ICteDeclaration.buildCte(...)` دارد. factory یک `QueryRenderSelectBuilder` می‌سازد، block را اجرا می‌کند و SELECT، aliasهای خروجی و یکتایی aliasها را بررسی می‌کند. در حالت declaration، نام منطقی و مالک declaration را نیز ثبت می‌کند.
- همان فایل در `CteBuilder.kt:90-96` `BuiltCteComposition` را تعریف می‌کند. این شیء `Cte` را پیاده می‌کند و نام runtime، query definition، dependencyها، declaration owner و logical query name را با هویت شیء حفظ می‌کند. `CteSourceContext` و `CteAstComposer` با cast به همین پیاده‌سازی، داده‌های داخلی را می‌خوانند.
- `CteDeclaration.kt:10-22` یک helper عمومی برای declarationهای typed است و `buildCte` را با نام و مالک runtime خود فراخوانی می‌کند.
- `CteSourceContext.kt:10-140` context داخلی Builder برای منبع CTE فعال، alias مؤثر، منشأهای alias و dependencyهای CTE است. علاوه بر ثبت منبع، خروجی SQL و مالک typed output را با AST تعریف تطبیق می‌دهد. این context در Builderهای column، condition، joins و select استفاده می‌شود؛ بنابراین در سطح فعلی یک جزء یکپارچه‌سازی Builder است، نه یک مدل مستقل.
- `CteAstComposer.kt:16-224` نام مؤثر CTE را مدیریت می‌کند، dependency closure را با ترتیب dependency-first می‌سازد، ورودی‌های WITH صریح را با ریشه‌های CTE ترکیب می‌کند، برای CTEهای composable آیتم WITH تولید می‌کند و metadata منبع را در AST قرار می‌دهد. وابستگی مستقیم آن به `IQueryRenderSelectAst`، `QueryWithsBuilder`، `ModelTableAliasContext` و `CteSourceContext` نشان می‌دهد نقش فعلی‌اش orchestration بین Builder و AST است. این فایل در وضعیت فعلی untracked است و در `QueryRenderSelectBuilder.kt:56, 125-130` استفاده می‌شود؛ انتقال مستقیم آن به ماژول مستقل CTE، بدون انتقال مسئولیت Builder یا ایجاد وابستگی برگشتی، مناسب نیست.
- helper داخلی `selectAliases()` از ستون‌های SELECT در AST aliasهای SQL را استخراج می‌کند. در حال حاضر در جریان ساخت و اعتبارسنجی CTE استفاده می‌شود؛ فعلاً دلیلی برای انتقال آن به API/AST یا ساخت abstraction جدا وجود ندارد.

### ۳.۴ مسیرهای اتصال

- `QueryRenderSelectBuilder.withs()` و `from()` در `QueryRenderSelectBuilder.kt:72-80, 110-133`، و مسیرهای منبع در `QueryTableBuilder.kt:117-195` نقاط اتصال CTE با Query DSL هستند. Builderهای SELECT/column/condition/join نیز `CteSourceContext` را مصرف می‌کنند.
- در مسیر `from { cte(Cte) }`، Composer منبع را ثبت و dependencyها را برای WITH ترکیب می‌کند. مسیر `from { cte(declaration) }` از `selectedQueryRelation` استفاده می‌کند و به شکل inline/derived source ساخته می‌شود. `cte(String)` فقط منبع نام‌دار و metadata آن را در جدول ثبت می‌کند؛ lookup معنایی مستقل از SQL انجام نمی‌دهد.
- `ModelTableAliasContext` و `QueryMetadataResolver` در مدیریت alias و نام Query نقش دارند. تا وقتی مصرف‌کنندگان غیر CTE و مرز مالکیت آن‌ها بررسی نشده، نباید صرفاً به‌دلیل استفاده در CTE منتقل شوند.

## ۴. مانع اصلی در طراحی ماژول مستقل

وابستگی‌های Gradle فعلی این مسیر را نشان می‌دهند (`api/build.gradle.kts:12-15`، `ast/build.gradle.kts:12-16` و `builder/build.gradle.kts:12-16`):

```text
:data_base:query:ast  -> :data_base:core
:data_base:query:api  -> :data_base:core, :data_base:query:ast
:data_base:query:builder -> :data_base:core, :data_base:query:ast, :data_base:query:api
```

APIهای `table` و `with` در `:api` نوع `Cte` و `ICteDeclaration` را مصرف می‌کنند. از طرف دیگر قرارداد `Cte` در `:api` به `IQueryApi` و `IQueryRenderSelectAst` نیاز دارد. اگر همین قرارداد را به ماژول پایین‌دستی `:cte` منتقل کنیم، `:api` باید به `:cte` وابسته شود و `:cte` برای نوع `IQueryApi` به `:api` نیاز خواهد داشت؛ نتیجه چرخهٔ Gradle است.

انتقال `CteBuilder.kt` و `CteDeclaration.kt` به ماژولی بالادست که به Builder وابسته باشد، چرخهٔ main-module ایجاد نمی‌کند، اما این فایل‌ها به جزئیات `internal` در Builder، از جمله `requireCteOutputAliases` و `BuiltCteComposition`، متکی‌اند. انتقال آن‌ها یا نیازمند seam قابل دسترس بین دو ماژول است یا باعث باقی‌ماندن بخش مهمی از پیاده‌سازی در Builder می‌شود. اگر برای عبور از مرز، API عمومی تازه یا تغییر قرارداد لازم شود، این تصمیم باید صریح و جداگانه تأیید شود؛ در پلن حاضر چنین تغییری از پیش مجاز فرض نشده است.

پس صرف افزودن `include(":data_base:query:cte")` کافی نیست. جهت وابستگی و مرز دقیق ماژول، دروازهٔ معماری پیش از هر جابه‌جایی سورس است.

## ۶. دسته‌بندی اجزا

۱. **قراردادهای مفهومی CTE:** `Cte` و `ICteDeclaration` از نظر مفهوم CTE هستند، اما محل فعلی‌شان `:api` برای استفادهٔ APIهای Query است. قرارداد `Cte` به API و AST پیوند دارد؛ انتقال به‌تنهایی ممکن نیست.

۲. **ساخت و اعتبارسنجی CTE:** `cte(...)`، `buildCte(...)`، `CteDeclaration` و `BuiltCteComposition` نزدیک‌ترین بخش‌ها به ساخت CTE هستند. وابستگی مستقیم به Builder internals و مصرف `BuiltCteComposition` از داخل Builder مانع انتقال ساده است.

۳. **یکپارچه‌سازی Builder و AST:** `CteSourceContext`، `CteAstComposer`، `QueryTableBuilder` و `QueryRenderSelectBuilder` مسئول اتصال انتخاب منبع به AST/metadata و ساخت WITH هستند. مالک فعلی مناسب آن‌ها `:builder` است.

۴. **مصرف WITH:** `QueryWithsBuilder`، `QueryWithsItemBuilder`، APIهای `IQueryWiths*` و ASTهای WITH قابلیت عمومی WITH را می‌سازند/نمایندگی می‌کنند. طبق محدودیت کار، در همان ماژول‌های فعلی می‌مانند.

۵. **ابزارهای عمومی/مشترک:** `QueryMetadataResolver`، `ModelTableAliasContext` و `selectAliases()` را نباید بر اساس نام یا محل استفادهٔ فعلی منتقل کرد؛ ابتدا باید تمام مصرف‌کنندگانشان مشخص شوند. شواهد فعلی برای ایجاد abstraction یا ماژول utility جدید کافی نیست.

۶. **موارد مبهم:** محل نهایی factory عمومی CTE، دسترسی `CteBuilder` به internals، و سیاست سازگاری importهای فعلی هنوز تصمیم قطعی ندارند. این‌ها در بخش ۱۱ ثبت شده‌اند و باید قبل از جابه‌جایی فایل‌ها حل شوند.

## ۷. وابستگی‌های فعلی و گزینهٔ پیشنهادی

| وابستگی | وضعیت فعلی | اثر بر انتقال |
|---|---|---|
| `:api -> :ast` | مستقیم | قرارداد Cte به API و AST وابسته است |
| `:builder -> :api, :ast` | مستقیم | ساخت CTE و composition با هر دو لایه کار می‌کنند |
| `:renderer -> :api, :ast, :dialect` | مستقیم | AST WITH را می‌خواند؛ نباید به factory CTE وابسته شود |
| `:executor -> :builder, :api, :ast, :renderer, ...` | مستقیم | مصرف runtime؛ در این کار فقط مصرف‌کننده و regression target است |
| `:example -> :api, :ast, :builder, :renderer, :executor` | مستقیم | نمونه‌های CTE از factory و Builder استفاده می‌کنند |
| `:cte` | وجود ندارد | dependency direction هنوز باید انتخاب شود |

**گزینهٔ کم‌ریسک برای حفظ وضعیت فعلی:** قراردادها در `:api`، AST در `:ast`، composition و WITH integration در `:builder` بمانند. اگر الزام محصولی برای ماژول مجزا باقی است، ابتدا مشخص شود آیا `:cte` باید یک ماژول بالادستی authoring/factory وابسته به Builder باشد یا یک ماژول پایین‌دستی مستقل. گزینهٔ پایین‌دستی با قرارداد فعلی `Cte` سازگار نیست؛ گزینهٔ بالادستی به seam میان factory و internals Builder و همچنین سازگاری importها نیاز دارد. تا حل این تصمیم، انتقال فایل یا افزودن وابستگی Gradle توصیه نمی‌شود.

## ۸. ساختار پیشنهادی ماژول `cte`

ساختار هدف فعلاً **مشروط** است؛ شواهد موجود اجازه نمی‌دهند یک ماژول `cte` مستقل و پایین‌دستی را بدون تغییر قرارداد فرض کنیم.

اگر تصمیم معماری اجازه دهد یک ماژول بالادستی CTE authoring داشته باشیم، اسکلت نامزد آن می‌تواند این باشد:

```text
data_base/query/cte/
  build.gradle.kts
  src/main/kotlin/gog/my_project/data_base/query/cte/...
```

این ماژول در آن گزینه به `:data_base:query:builder` و به‌واسطهٔ آن به `:api`/`:ast` وابسته می‌شود؛ `:example` و مصرف‌کنندگان factory نیز ممکن است لازم باشد مستقیماً به آن وابسته شوند. `:builder` نباید به `:cte` وابسته شود. قرارداد `Cte`، ASTهای WITH، Composer و context در این گزینه منتقل نمی‌شوند.

این پیشنهاد هنوز مجوز انتقال `CteBuilder.kt` یا `CteDeclaration.kt` نیست: عبور آن‌ها از مرز ماژول، به دلیل `internal` بودن APIهای Builder و `BuiltCteComposition`، یک مانع فنی واقعی دارد. اگر seam قابل قبول بدون گسترش API عمومی پیدا نشد، تصمیم کم‌ریسک این است که این فایل‌ها در Builder بمانند و ماژول مستقل تا تصمیم معماری بعدی ساخته نشود؛ ماژول خالی یا facade صوری اضافه نشود.

## ۹. پلن اجرایی مرحله‌به‌مرحله

### فاز ۰ — تثبیت وضعیت و تکمیل inventory

- **هدف:** مشخص‌کردن دقیق baseline و تفکیک کار قبلی از انتقال.
- **فایل‌ها/ماژول‌ها:** `settings.gradle.kts`، Gradleهای Query و تمام مسیرهای ثبت‌شده در بخش ۵.
- **تغییرات:** هیچ تغییر سورس؛ ثبت `git status`، diffها، فایل‌های untracked، importها، سازندگان/مصرف‌کنندگان CTE و dependencyهای Gradle.
- **پیش‌نیاز:** دسترسی به checkout فعلی.
- **ریسک:** فایل‌های untracked یا تغییرات قبلی به انتقال نسبت داده شوند.
- **اعتبارسنجی:** inventory مسیرها با `rg` و dependencyها با فایل‌های واقعی Gradle تطبیق داده شود.
- **معیار اتمام:** فهرست کامل نمادها، مصرف‌کنندگان و وضعیت baseline ثبت شده باشد.
- **بازگشت:** چون فاز فقط‌خواندنی است، نیازی به بازگشت ندارد.

### فاز ۱ — تصمیم مرز و جهت وابستگی

- **هدف:** تعیین اینکه `:cte` پایین‌دستی است یا ماژول authoring بالادستی، و مشخص‌کردن اجزای واقعاً قابل انتقال.
- **فایل‌ها/ماژول‌ها:** قراردادهای `:api`، ASTهای `:ast`، factory و composition در `:builder`.
- **تغییرات:** تصمیم معماری مستند شود؛ هنوز سورس یا Gradle تغییر نکند.
- **پیش‌نیاز:** فاز ۰.
- **ریسک:** تلاش برای جابه‌جایی Cte contract چرخهٔ `api <-> cte` می‌سازد؛ انتقال factory بالادست نیز ممکن است به تغییر visibility/API نیاز داشته باشد.
- **اعتبارسنجی:** گراف جهت‌دار ماژول‌ها بدون چرخه باشد و هر API عمومی/import فعلی مالک و مقصد روشنی داشته باشد.
- **معیار اتمام:** فهرست فایل‌ها با یکی از تصمیم‌های «انتقال مستقیم»، «باقی‌ماندن» یا «نیازمند تصمیم بیشتر» نهایی شود.
- **بازگشت:** تصمیم را لغو یا به مرحلهٔ بررسی برگردان؛ هنوز فایل تغییر نکرده است.

### فاز ۲ — توصیف قراردادهای رفتار و characterization

- **هدف:** تثبیت رفتارهای فعلی پیش از جابه‌جایی، بدون تغییر قرارداد Query/CTE.
- **فایل‌ها/ماژول‌ها:** تست‌های Builder، Executor و Example مندرج در بخش ۱۰.
- **تغییرات:** ابتدا تست‌های موجود اجرا و نتایج ثبت شوند؛ تست جدید فقط برای رفتار واقعاً بدون پوشش اضافه شود.
- **پیش‌نیاز:** فاز ۱ و وضعیت قابل‌ساخت مخزن.
- **ریسک:** خطاهای قبلی/نامرتبط یا پیکربندی پایگاه داده با شکست انتقال اشتباه گرفته شوند.
- **اعتبارسنجی:** خروجی تست‌ها و علت شکست‌ها جداگانه ثبت شود؛ تست Integration دیتابیس تنها با تنظیمات لازم اجرا شود.
- **معیار اتمام:** رفتار baseline برای identity، dependency order، name override، occurrence alias، typed outputs و پارامترها ثبت باشد.
- **بازگشت:** تست تازهٔ نادرست حذف/اصلاح شود؛ رفتار تولیدی تغییر نمی‌کند.

### فاز ۳ — بررسی و طراحی seam برای مرز ماژول

- **هدف:** رفع مانع دسترسی `CteBuilder` به Builder internals، بدون گسترش بی‌دلیل API عمومی.
- **فایل‌ها/ماژول‌ها:** `CteBuilder.kt`، `CteDeclaration.kt`، `QueryRenderSelectBuilder.kt` و `BuiltCteComposition`.
- **تغییرات:** فقط طراحی گزینه‌ها و اثرشان؛ هیچ interface/class عمومی یا abstraction جدید تا تصویب اضافه نشود.
- **پیش‌نیاز:** تصمیم فاز ۱.
- **ریسک:** تغییر visibility یا انتقال `BuiltCteComposition` می‌تواند API را ناخواسته عمومی کند یا identity composition را بشکند.
- **اعتبارسنجی:** نمونهٔ dependency graph و compile boundary برای هر گزینه بررسی شود؛ identity و داده‌های declaration/dependency حفظ شوند.
- **معیار اتمام:** یک گزینهٔ مشخص انتخاب شود که بدون چرخه باشد و نیازمند تغییر API تأییدنشده نباشد؛ در غیر این صورت انتقال factory متوقف و فایل‌ها در Builder نگه داشته شوند.
- **بازگشت:** به نگه‌داشتن factory در Builder برگرد؛ تغییر production انجام نشده است.

### فاز ۴ — ایجاد اسکلت Gradle ماژول، فقط پس از عبور از دروازه‌ها

- **هدف:** افزودن کمینهٔ تنظیمات ماژول منتخب.
- **فایل‌ها/ماژول‌ها:** `settings.gradle.kts`، `data_base/query/cte/build.gradle.kts` و فقط build.gradle مصرف‌کنندگان لازم.
- **تغییرات:** افزودن include و dependencyهای ضروری مطابق گراف مصوب؛ بدون وابستگی به Renderer/Executor مگر با اثبات نیاز.
- **پیش‌نیاز:** فازهای ۱ تا ۳.
- **ریسک:** چرخهٔ ماژول، dependency زائد یا وابستگی test که ترتیب taskها را چرخه‌ای کند.
- **اعتبارسنجی:** Gradle project graph و taskهای compile برای `api`, `ast`, `builder`, `cte` و مصرف‌کنندگان بررسی شوند.
- **معیار اتمام:** ماژول با dependencyهای حداقلی پیکربندی و task graph بدون چرخه باشد.
- **بازگشت:** فقط include و dependencyهای افزوده‌شده در همین مرحله برگردانده شوند؛ تغییرات پیشین حفظ شوند.

### فاز ۵ — انتقال محدود فایل‌های مصوب

- **هدف:** انتقال فقط فایل‌هایی که فازهای ۱ و ۳ مستقلاً قابل انتقال تشخیص داده‌اند.
- **فایل‌ها/ماژول‌ها:** فقط فهرست مصوب؛ `CteSourceContext`، `CteAstComposer`، APIهای عمومی و ASTهای WITH پیش‌فرضاً خارج‌اند.
- **تغییرات:** جابه‌جایی/تغییر package و import فقط برای فایل‌های مصوب؛ حفظ نام و رفتار API تا حدی که تصمیم فاز ۱ الزام کرده است.
- **پیش‌نیاز:** اسکلت ماژول و seam تأییدشده.
- **ریسک:** شکست importهای مصرف‌کننده، visibility، ثبت dependencyها، name override، identity یا ترتیب bind parameterها.
- **اعتبارسنجی:** diff محدود به فایل‌های فهرست‌شده باشد؛ compile ماژول مبدأ/مقصد و تست‌های characterization اجرا شود.
- **معیار اتمام:** هیچ duplicate source باقی نماند و قرارداد رفتاری baseline حفظ شده باشد.
- **بازگشت:** تنها فایل‌های انتقال‌یافته و import/dependencyهای ناشی از آن مرحله برگردانده شوند.

### فاز ۶ — اتصال مصرف‌کنندگان و حفظ WITH/Query API

- **هدف:** به‌روزرسانی dependency/import مصرف‌کنندگان بدون تغییر قرارداد composition.
- **فایل‌ها/ماژول‌ها:** مصرف‌کنندگان واقعی در Example، تست‌ها و هر ماژول دیگری که فاز ۰ ثبت کرده است.
- **تغییرات:** فقط تغییرات لازم برای resolve شدن factory/contract؛ فرم‌های `with(...)`، `from { cte(...) }` و معنای `cte(String)` تغییر نکنند.
- **پیش‌نیاز:** فاز ۵.
- **ریسک:** تغییر ناخواسته نام runtime CTE، نام WITH، alias محل استفاده یا parameter order.
- **اعتبارسنجی:** تست‌های Builder/Renderer/Executor/Example و مقایسهٔ AST/SQL/پارامتر طبق تست‌های موجود.
- **معیار اتمام:** همهٔ مصرف‌کنندگان ثبت‌شده compile شوند و تست‌های CTE سبز باشند.
- **بازگشت:** تغییر import و dependency مصرف‌کنندگان به همراه انتقال همان مرحله rollback شود.

### فاز ۷ — ممیزی نهایی و حذف باقی‌ماندهٔ تکراری

- **هدف:** اطمینان از مالکیت یگانه و تکمیل migration.
- **فایل‌ها/ماژول‌ها:** کل `data_base/query` و مستندات تصمیم فاز ۱.
- **تغییرات:** حذف فقط فایل‌های قدیمی‌ای که انتقالشان تأیید شده، جایگزین‌شان compile می‌شود و مصرف‌کننده‌ای ندارند.
- **پیش‌نیاز:** فاز ۶ و قبولی تست‌ها.
- **ریسک:** حذف کد legacy دارای مصرف‌کنندهٔ خارج از inventory یا ازبین‌رفتن سازگاری source.
- **اعتبارسنجی:** جست‌وجوی نماد/import، diff/status، compile و suiteهای مرتبط.
- **معیار اتمام:** یک مالک برای هر نماد، dependency بدون چرخه و گزارش دقیق نتایج تست وجود داشته باشد.
- **بازگشت:** حذف‌ها با restore محدود همان فایل‌ها و وابستگی‌های مرحله انجام شود؛ از reset کلی استفاده نشود.

## ۱۲. موارد خارج از محدوده

این پلن شامل موارد زیر نیست:

- انتقال metadata به Executor یا تغییر materialization و `QueryRow`؛
- پارامترهای خروجی، دریافت یا انتقال آن‌ها؛
- API دسترسی نتیجه بر اساس namespace یا دسترسی تایپ‌شده مانند `row.v3_user_display.fullName`؛
- بازطراحی `WITH`، ترتیب‌دهی یا composition جدید CTE؛
- lookup معنایی CTE نام‌دار یا پیش‌بینی خطای SQL در Builder؛
- حذف `ICte` legacy، تغییر public Query API یا اضافه‌کردن قابلیت جدید CTE.

اگر وابستگی به موارد بالا در حین اجرا پیدا شد، به‌عنوان مانع/کار مستقل ثبت شود و دامنهٔ این پلن بی‌سروصدا گسترش نیابد.

## ۱۳. معیار پذیرش پلن 19.0

پلن اجرایی تنها زمانی آمادهٔ شروع است که:

1. inventory نمادها، فایل‌ها و مصرف‌کنندگان CTE با checkout زمان اجرا تطبیق داده شده باشد؛
2. مسئولیت API، AST، Builder و WITH برای هر جزء روشن باشد؛
3. جهت وابستگی ماژول جدید بدون چرخه و بدون تکیه بر فرض حل‌نشده تصویب شده باشد؛
4. فایل‌های قابل‌انتقال و فایل‌های ماندگار هرکدام صریحاً مشخص شده باشند؛
5. وضعیت untrackedها و تغییرات قبلی working tree از تغییرات انتقال تفکیک شده باشد؛
6. تست‌های baseline و معیار قبولی هر فاز مشخص باشند؛
7. انتقال نیازمند تغییر API یا visibility تأییدنشده نباشد؛
8. هیچ تصمیمی دربارهٔ Executor، پارامترهای خروجی یا دسترسی نتیجه وارد کار نشده باشد.

**تصمیم فعلی:** مرز ماژول مستقل با قراردادهای فعلی هنوز برای انتقال مستقیم آماده نیست. مالکیت فعلی `:api` / `:ast` / `:builder` باید حفظ شود تا تصمیم فاز ۱ دربارهٔ جهت `:cte` و seam مجاز اتخاذ شود. پس از آن می‌توان پلن انتقال را بدون تغییرات حدسی به فاز اجرایی برد.
