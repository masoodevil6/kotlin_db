# Plan 16.0 — نهایی‌سازی قرارداد مشاهدهٔ Metadata مؤثر Query

## وضعیت

**CLOSED — معیارهای پذیرش Plan 16 با شواهد اجرای 2026-10-15 تأیید شدند.**

## ۱. هدف

Metadata مؤثر Query را از مسیر واقعی ساخت Query به مصرف‌کنندهٔ Query منتقل کن تا توسعه‌دهنده بتواند آن را مستقل از مشاهدهٔ SQL بررسی کند.

هدف ارائهٔ اطلاعات ساختاریافته و قابل‌اعتماد دربارهٔ Query نهایی است؛ نه صرفاً نمایش Annotationها یا نام Propertyها.

نمونهٔ مفهومی استفاده:

~~~kotlin
queryManager
    .queryBuilder(query)
    .sql { (queryText, params) ->
        println("query: $queryText")
        println("params: $params")
    }
    .details { metadata ->
        println("metadata: $metadata")
    }
    .execute()
~~~

`.sql` قرارداد فعلی SQL و پارامترها را حفظ می‌کند. `.details` API مستقل مشاهدهٔ Metadata مؤثر است و قرارداد نهایی آن باید در مرحلهٔ پیاده‌سازی با سورس و تست‌های مربوط تأیید شود.

## ۲. تصمیم‌های تثبیت‌شدهٔ طراحی

- امضای فعلی `.sql()` و callback آن تغییر نمی‌کند.
- `BuiltQuery` تغییر نمی‌کند.
- API جدید با نام مستقل `.details { metadata -> ... }` بررسی و پیاده‌سازی خواهد شد؛ Metadata به callback فعلی `.sql` اضافه نمی‌شود.
- قرارداد عمومی (`public`) `EffectiveQueryMetadata` در `data_base:query:api` قرار می‌گیرد؛ `query:api` نباید به Builder یا Executor وابسته شود.
- قرارداد عمومی (`public`) `EffectiveQueryMetadataProvider` نیز در `query:api` قرار می‌گیرد؛ پیاده‌سازی داخلی Builder در صورت کفایت دسترسی می‌تواند `internal` بماند.
- این visibility تصمیم داخلی این Repository است و به‌تنهایی هیچ تضمینی دربارهٔ ABI، انتشار artifact یا سازگاری مصرف‌کنندگان بیرونی ایجاد نمی‌کند.
- انتقال Metadata از طریق یک provider مستقل در `query:api` انجام می‌شود؛ افزودن property اجباری به `IQueryRenderSelectApi` انتخاب پیش‌فرض نیست.
- Metadata هنگام فراخوانی `.details()` از وضعیت معتبر فعلی Builder خوانده می‌شود؛ برای استخراج آن SQL دوباره render نمی‌شود و cache یا state موازی بدون نیاز اثبات‌شده ایجاد نمی‌شود.
- دامنهٔ اولیه فقط SELECT است. Mutation consumerها در این Plan تغییر نمی‌کنند.
- Query سفارشی فاقد provider باید همچنان `.sql()` و `.execute()` فعلی را اجرا کند؛ `.details()` نباید Metadata حدسی یا ناقص تولید کند و باید با خطای روشن وضعیت پشتیبانی‌نشدن را اعلام کند.
- Executor فقط Metadata آماده‌شده را مصرف می‌کند و مسئول resolve کردن Declaration metadata یا بازسازی Query نیست.

### قواعدی که از این جدول نتیجه می‌شوند

- `logicalQueryName`، `cteRuntimeName`، `withSqlName` و `occurrenceAlias` چهار مفهوم عمومی متفاوت‌اند. `Cte.name` فقط نام runtime/SQL پیش‌فرض CTE است و به‌تنهایی owner یا هویت داخلی declaration را به Metadata عمومی تبدیل نمی‌کند.
- `logicalOutputName` هویت منطقی property در declaration است؛ `publishedSqlAlias` نام خروجی نهایی SQL است. `CteSourceContext.validateTypedOutput` در `builder/.../cte/CteSourceContext.kt:57-84` صرفاً مالکیت، وجود خروجی و alias SQL را اعتبارسنجی می‌کند و دلیل کافی برای افزودن فیلد عمومی مانند `relationOwnership` نیست.
- `executionType` از `IQueryColumnsAst.ExecutionType` می‌آید. `execute(DataType.LONG)` فقط قرارداد خواندن/Materialization خروجی را تعیین می‌کند و نباید به نوع property یا نوع ستون database تعبیر شود.
- `QB_METADATA_UNSET` با رشتهٔ صریح خالی یکی نیست: resolver در `QueryMetadataResolver.kt:12-40` unset را به convention می‌برد و empty string را برای فیلدهای annotation شده خطا می‌کند. این semantics باید در metadata مؤثر حفظ شود و با `null` یا فهرست خالی جایگزین نشود.

### وضعیت‌های فاقد مقدار

این وضعیت‌ها بخشی از قرارداد مدل‌اند و باید جداگانه تست شوند:

1. **Query بدون CTE:** `relations`/فهرست CTE خالی است؛ نباید یک relation ساختگی یا `cteRuntimeName = ""` تولید شود.
2. **خروجی بدون `PropertyReference`:** `logicalOutputName` و metadata declaration مربوط به property وجود ندارد؛ `publishedSqlAlias` فقط در صورتی وجود دارد که `ColumnAlias` نهایی AST مقدار داشته باشد.
3. **نبود `withSqlName`:** برای Query بدون WITH یا برای source inline رخ می‌دهد؛ فهرست WITH خالی می‌ماند و این وضعیت با رشتهٔ خالی نشان داده نمی‌شود.
4. **نبود typed output:** فهرست خروجی‌های typed خالی است؛ این حالت به `logicalOutputName = ""` یا alias حدسی تبدیل نمی‌شود.
5. **Query فاقد `EffectiveQueryMetadataProvider`:** `.sql()` و `.execute()` مسیر فعلی را حفظ می‌کنند، اما `.details()` باید خطای صریح پشتیبانی‌نشدن بدهد؛ metadata خالی به‌عنوان نتیجهٔ معتبر مجاز نیست.

در مواردی که ساختار فعلی برای relationهای عمومی یا خروجی‌های expression مقدار nullable مشخصی تعریف نکرده است، implementation باید type نهایی را با حداقل سطح nullable/collection لازم انتخاب کند و آن را با تست قرارداد تثبیت کند؛ از جعل sentinel یا `""` خودداری شود.

## ۴. مرز مسئولیت ماژول‌ها

### ۴.۱. ماژول data_base:query:meta_data

این ماژول منبع Metadata مربوط به Declaration است و مسئول موارد زیر می‌ماند:

- قواعد نام‌گذاری پیش‌فرض Model و Query.
- تفسیر Annotationهای QBTable، QBColumn، QBQuery و QBQuerySelect.
- استخراج نام منطقی خروجی و alias پیش‌فرض خروجی.
- حفظ قرارداد هر فیلد دربارهٔ QB_METADATA_UNSET و رشتهٔ خالی.
- حفظ نوع و معنای Metadata تعریف‌شده در Declaration.

این ماژول alias نهایی occurrence و overrideهای DSL را تعیین نمی‌کند.

### ۴.۲. ماژول Builder

Builder از Metadata Declaration به‌همراه وضعیت واقعی Query، Metadata مؤثر را می‌سازد. مسئولیت‌های آن شامل موارد زیر است:

- اعمال overrideهای صریح DSL.
- تعیین alias مؤثر برای هر occurrence.
- نگهداری جداگانهٔ نام CTE، نام SQL در WITH، هویت Query و alias occurrence.
- نگهداری جداگانهٔ نام منطقی خروجی و alias منتشرشده در SQL.
- اعمال قرارداد موجود execute(DataType) برای نوع مؤثر خروجی.
- فراهم‌کردن اطلاعات لازم برای مصرف‌کنندگان بعدی، بدون اجرای Getterهای Property.

اطلاعات مؤثر باید از همان داده‌ها و انتخاب‌هایی به دست آید که Query نهایی و SQL را شکل می‌دهند.

### ۴.۳. Executor

Executor فقط مسیر فعلی render و execute را حفظ می‌کند. `QueryConsumer` Metadata آماده‌شدهٔ Builder را از provider دریافت و از طریق `.details` منتشر می‌کند؛ Executor نباید Declaration metadata را دوباره resolve کند.

Executor نباید:

- Annotationهای Declaration را دوباره resolve کند.
- نام‌ها را با حدس از روی نام Property بسازد.
- نوع مؤثر خروجی را مستقل از قرارداد Builder تعیین کند.
- برای استخراج Metadata، Query را دوباره بسازد یا SQL را دوباره render کند.
- قرارداد JDBC، پارامترها یا QueryRow را بدون ضرورت اثبات‌شده تغییر دهد.

### ۴.۴. APIهای مشاهدهٔ Query

`.sql` فقط SQL و پارامترها را طبق قرارداد فعلی در اختیار توسعه‌دهنده می‌گذارد. `.details` فقط Metadata مؤثر را ارائه می‌کند و هر دو متد باید همان `QueryConsumer` را برای ادامهٔ زنجیره برگردانند.

کاربرد اولیه مشاهده، عیب‌یابی و ساخت ابزارهای توسعه است. ابزارهایی مانند Autocomplete می‌توانند بعداً از این Metadata استفاده کنند، اما پیاده‌سازی کامل Autocomplete جزو این Plan نیست.

## ۵. مدل مفهومی Metadata مؤثر

Query ممکن است چند relation و هر relation چند خروجی داشته باشد. بنابراین مدل باید relationها و خروجی‌ها را جدا نگه دارد و هویت‌های جدول بخش ۳ را در یک `name` یا `alias` عمومی ادغام نکند.

مدل مفهومی پیشنهادی، بدون تثبیت نام propertyهای نهایی:

~~~text
EffectiveQueryMetadata
└── relations: List<EffectiveRelationMetadata>
    ├── logicalQueryName: String?              // metadata declaration
    ├── cteRuntimeName: String?                // Cte.name / effective CTE name
    ├── withSqlName: String?                   // فقط برای WITH entry
    ├── occurrenceAlias: String?               // alias همان occurrence
    └── outputs: List<EffectiveOutputMetadata>
        ├── logicalOutputName: String?        // فقط property-backed typed output
        ├── publishedSqlAlias: String?         // مقدار نهایی ColumnAlias
        └── executionType: DataType?           // IQueryColumnsAst.ExecutionType
~~~

- `relations` و `outputs` مجموعه‌اند؛ نبود relation یا output با `null` داخل یک relation ساختگی نمایش داده نمی‌شود.
- `BuiltCteComposition.declarationOwner` و هویت referenceای خود `Cte` در Builder باقی می‌مانند و برای validation و composition استفاده می‌شوند؛ این تصمیم آن‌ها را حذف یا تغییر نمی‌دهد و فقط از expose کردنشان در Metadata عمومی جلوگیری می‌کند.
- `withSqlName` متعلق به یک WITH entry است، نه به CTE declaration یا occurrence inline. برای یک CTE که هم در WITH و هم به‌صورت occurrence دیگری مصرف می‌شود، این دو context باید جدا بمانند.
- `publishedSqlAlias` از AST نهایی خوانده می‌شود؛ resolver فقط مقدار پیش‌فرض declaration را فراهم می‌کند و DSL می‌تواند `ColumnAlias` را تغییر دهد.
- این مدل فقط داده‌هایی را عمومی می‌کند که منبعشان در Builder/AST/context موجود است. relation ownership، dependency graph و validation state فیلد عمومی Metadata نیستند؛ آن‌ها مسئولیت Builder و قواعد اعتبارسنجی باقی می‌مانند.

## ۶. قرارداد Provider و API مشاهده

قرارداد پیشنهادی provider در `query:api` باید عمومی (`public`) باشد تا Builder و Executor بتوانند از آن استفاده کنند، اما این تصمیم به‌تنهایی تضمین ABI یا انتشار برای مصرف‌کنندگان بیرونی نیست:

~~~kotlin
interface EffectiveQueryMetadataProvider {
    fun effectiveQueryMetadata(): EffectiveQueryMetadata
}
~~~

قرارداد عمومی مشاهده در SELECT از نظر مفهومی:

~~~kotlin
fun details(
    block: (EffectiveQueryMetadata) -> Unit
): QueryConsumer
~~~

`QueryRenderSelectBuilder` provider را پیاده می‌کند. `QueryConsumer` به قرارداد provider عمومی دسترسی دارد و نباید به implementation داخلی Builder cast کند.

Metadata در زمان فراخوانی `.details()` از وضعیت فعلی Query خوانده می‌شود. هر فراخوانی `.sql()` نیز SQL و پارامترها را از وضعیت همان لحظه می‌خواند. بنابراین:

- `.details()` قبل یا بعد از `.sql()`، تا زمانی که Query بین دو فراخوانی تغییر نکرده باشد، باید نتیجهٔ یکسان داشته باشد؛
- اگر Query بین دو فراخوانی تغییر کند، نتیجه‌ها لزوماً برابر نیستند؛
- بین callbackهای جداگانه تضمین snapshot اتمیک وجود ندارد؛
- `.execute()` قرارداد فعلی خود را حفظ می‌کند و وضعیت Query را مطابق مسیر موجود مصرف می‌کند؛
- استخراج Metadata نباید Query را mutate کند و نباید برای تهیهٔ Metadata دوباره SQL را render کند.

این قرارداد دربارهٔ زمان مشاهده است، نه دربارهٔ immutable کردن Builder. پیاده‌سازی باید از همان state مؤثر موجود بخواند و state موازی یا cache جدید ایجاد نکند مگر اینکه در مرحلهٔ implementation ضرورت آن اثبات شود.

اگر Query provider نداشته باشد:

- `.sql()` و `.execute()` باید رفتار فعلی خود را حفظ کنند؛
- `.details()` باید با خطای روشن و قابل‌تشخیص متوقف شود؛
- Metadata خالی یا حدسی نباید به‌عنوان Metadata معتبر منتشر شود.

تغییر callback فعلی `.sql`، تغییر `BuiltQuery` و افزودن property اجباری به `IQueryRenderSelectApi` در این طراحی مجاز نیست.

## ۷. محدوده

### داخل محدوده

- ردیابی مسیر انتقال Query از Builder تا Executor.
- تعیین محل ایجاد، تغییر، نگهداری و مصرف Metadata مؤثر.
- تعیین قرارداد قابل‌مصرف Metadata مؤثر.
- انتقال Metadata مؤثر از Builder تا `QueryConsumer` از طریق provider.
- افزودن API مستقل `.details` برای SELECT.
- افزودن تست‌های قرارداد و رگرسیون برای provider و `.details`.

## ۹. مراحل پیشنهادی

### فاز ۱ — بررسی قراردادهای موجود

مسیرها و APIهای زیر را بررسی کن:

- QueryRelation و قرارداد خروجی آن.
- QuerySourceContext و محل نگهداری alias مؤثر occurrence.
- QueryRenderSelectBuilder و مسیر ساخت خروجی SELECT.
- QueryColumnsBuilder و مسیر تعیین نام و نوع خروجی.
- CteDeclaration و CteBuilder.
- IQueryBuilderExecutor و QueryBuilderExecutor.
- callback فعلی .sql و نوع ورودی آن.
- BuiltQuery و قرارداد SQL و پارامترها.
- QueryConsumer و مسیر اجرای نهایی.

خروجی فاز، نقشه‌ای از محل تولید، تغییر، نگهداری و مصرف هر فیلد Metadata است. تا روشن‌شدن این مسیرها تغییری در کد لازم نیست.

### فاز ۲ — تعیین قرارداد Metadata مؤثر

با تکیه بر شواهد فاز ۱، قرارداد Metadata مؤثر را تعیین کن. این قرارداد باید:

- چند Relation را در یک Query پشتیبانی کند.
- چند خروجی را برای هر Relation پشتیبانی کند.
- نام CTE را از alias occurrence جدا نگه دارد.
- نام منطقی خروجی را از alias SQL جدا نگه دارد.
- نوع مؤثر خروجی را حفظ کند.
- هویت‌های عمومی بخش ۳ را بدون ادغام حفظ کند و owner/reference داخلی declaration را به API عمومی اضافه نکند.
- رفتار `QB_METADATA_UNSET`، رشتهٔ خالی، `null` و فهرست خالی را مطابق قرارداد موجود از هم جدا کند.

در این فاز تعیین شود که آیا type جدید لازم است یا ساختار موجود کفایت می‌کند.

### فاز ۳ — ساخت Metadata مؤثر در مسیر Builder

Resolverهای موجود منبع Metadata Declaration باقی بمانند. Builder، Metadata Declaration را با overrideهای معتبر DSL و context هر occurrence ترکیب کند و نتیجه را در ساختار مؤثر قرار دهد.

با شواهد یا تست مشخص شود که Metadata نهایی از همان اطلاعاتی به دست می‌آید که SQL نهایی را تعیین می‌کنند.

### فاز ۴ — تعریف قرارداد مشترک و Provider

**وضعیت ثبت‌شده: تکمیل‌شده به‌صورت retroactive**

معیارهای صریح این فاز با implementation موجود تأمین شده‌اند. قراردادهای عمومی
`EffectiveQueryMetadata` و `EffectiveQueryMetadataProvider` در `query:api` قرار دارند،
این ماژول به Builder، Executor یا `query:meta_data` وابستگی ندارد، resolverهای Declaration
و Annotation در `query:meta_data` باقی مانده‌اند و Builder منبع ساخت Metadata مؤثر است.

این implementation پیش از ثبت رسمی وضعیت فاز در سند وجود داشته است. نتیجه بر اساس شواهد
سورس و نتایج تست‌های قبلاً گزارش‌شده ثبت می‌شود؛ تست‌ها در آخرین ممیزی دوباره اجرا نشدند.
این ثبت هیچ ادعایی دربارهٔ سازگاری ABI یا مصرف‌کنندگان بیرونی ندارد. Plan 16 به‌صورت کلی
باز است و این یادداشت مجوز بستن کل Plan یا شروع فاز بعدی نیست.

در این فاز قراردادهای `EffectiveQueryMetadata` و `EffectiveQueryMetadataProvider` در
`query:api` بررسی و تعریف شدند، بدون وابستگی به Builder، Executor یا `query:meta_data`.

`query:meta_data` فقط resolverهای Declaration و Annotation را نگه می‌دارد و Builder تنها
منبع ساخت Metadata مؤثر باقی می‌ماند.

### فاز ۵ — انتقال Metadata به QueryConsumer

Provider را در `QueryRenderSelectBuilder` فراهم کن و آن را در مسیرهای `queryBuilderSelect`، `QueryBuilderSelection.querySelect` و `queryBuilder(existingQuery)` قابل‌دسترسی نگه دار، بدون اینکه:

- Declaration دوباره resolve شود؛
- SQL دوباره render شود؛
- پارامترها یا ترتیب آن‌ها تغییر کند؛
- رفتار اجرای Query تغییر کند؛
- اطلاعات occurrence یا هویت خروجی از دست برود؛
- به implementation داخلی Builder cast شود.

برای Query سفارشی فاقد provider، فقط `.details` باید با خطای روشن رد شود و `.sql` و `.execute` باید بدون تغییر کار کنند.

### فاز ۶ — توسعهٔ API `.details`

متد `details` را فقط برای `QueryConsumer` مربوط به SELECT اضافه کن. متد باید Metadata provider را مصرف کند، همان Consumer را برگرداند و اجرای Query را آغاز نکند.

قرارداد `.sql` و destructuring دو‌جزئی فعلی در تمام مصرف‌کنندگان حفظ شود.

## ۱۰. معیارهای پذیرش

Plan زمانی کامل است که:

- Metadata مؤثر از مسیر واقعی ساخت Query به `QueryConsumer` برسد.
- `.sql` قرارداد فعلی SQL و پارامترها را حفظ کند.
- `.details` Metadata مؤثر را مستقل از `.sql` ارائه کند.
- provider از مسیر واقعی Builder تا `QueryConsumer` قابل‌دسترسی باشد.
- مقادیر Metadata با DSL و Query نهایی منطبق باشند.
- هویت Declaration، نام CTE، alias occurrence، نام منطقی خروجی، alias SQL و نوع مؤثر مستقل بمانند.
- `QueryConsumer` برای ارائهٔ Metadata مجبور به تفسیر مجدد Declaration نباشد و Executor نیز منطق فعلی خود را حفظ کند.
- اجرای Query، binding پارامترها و رفتار QueryRow حفظ شوند.
- Query فاقد provider رفتار Legacy خود را حفظ کند و `.details` خطای روشن بدهد.
- تست‌های مرتبط موفق باشند و شواهد اجرای آن‌ها ثبت شوند.

## ۱۱. نتیجهٔ مورد انتظار

پس از تکمیل Plan، توسعه‌دهنده می‌تواند از `.sql` برای مشاهدهٔ SQL و پارامترها و از `.details` برای مشاهدهٔ Metadata مؤثر استفاده کند. این ساختار می‌تواند مبنای ابزارهای آتی مانند Autocomplete یا اعتبارسنجی آگاه از Relation باشد؛ پیاده‌سازی این قابلیت‌ها جزو Plan نیست.

## ۱۲. اصل معماری

query:meta_data قراردادهای Declaration را می‌شناسد؛ Builder آن اطلاعات را با تنظیمات واقعی Query ترکیب می‌کند؛ `QueryConsumer` Metadata مؤثر را از provider دریافت و منتشر می‌کند؛ Executor فقط مسیر فعلی render و execute را حفظ می‌کند. هیچ‌یک از این ماژول‌ها نباید مسئولیت دیگری را دوباره انجام دهد.

## ۱۳. Revision Audit

### اصلاحات انجام‌شده

1. مدل مفهومی از `cteName` و `columnDataType` به فیلدهای عمومی حداقلی `logicalQueryName`، `cteRuntimeName`، `withSqlName`، `occurrenceAlias`، `logicalOutputName`، `publishedSqlAlias` و `executionType` اصلاح شد.
2. نوع و منشأ هر فیلد، declaration/effective بودن، تقدم مقدار، دامنهٔ وجود و رفتار فقدان مقدار ثبت شد.
3. `executionType` صریحاً به `IQueryColumnsAst.ExecutionType` و `QueryColumnsBuilder.execute(DataType)` متصل شد و از نوع Property یا ستون database تفکیک شد.
4. تقدم alias occurrence و published SQL alias بر اساس مسیر واقعی Builder ثبت شد؛ مقدار نهایی `ColumnAlias` منبع حقیقت alias خروجی است.
5. `withSqlName` از CTE runtime name و occurrence alias جدا شد و رفتار `with(cte)`، `with(withName, cte)` و `effectiveCteName` مستند شد.
6. وضعیت‌های Query بدون CTE، خروجی بدون `PropertyReference`، نبود WITH، نبود typed output و Query بدون provider صریح شد.
7. رابطهٔ output با Relation به‌عنوان قاعدهٔ validation در `CteSourceContext.validateTypedOutput` ثبت شد؛ فیلد عمومی جدیدی مانند `relationOwnership` اضافه نشد.
8. semantics مربوط به snapshot زمانی `.sql()`، `.details()` و `.execute()` و نبود تضمین snapshot اتمیک بین callbackها ثبت شد.
9. visibility عمومی قراردادهای `EffectiveQueryMetadata` و `EffectiveQueryMetadataProvider` در `query:api` و نبود تضمین ABI بیرونی صریح شد.
10. `declarationIdentity` از مدل عمومی حذف شد، چون هدف فعلی debugging به identity یکتای CTE instance نیاز اثبات‌شده ندارد و `KClass` نیز identity یکتای instance نیست. `BuiltCteComposition.declarationOwner` و reference identity داخلی CTE در Builder حفظ می‌شوند.
11. Phase 4 به‌صورت retroactive تکمیل‌شده ثبت شد؛ معیارهای آن با شواهد سورس و نتایج تست‌های قبلاً گزارش‌شده تأمین شده‌اند، تست‌ها در آخرین ممیزی دوباره اجرا نشدند و این ثبت Plan 16 را به‌طور کلی نمی‌بندد.
