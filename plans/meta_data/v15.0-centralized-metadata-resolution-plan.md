# Plan 15 — متمرکزسازی حل Metadata برای Model و Query

## وضعیت

**Draft — طرح معماری برای بررسی؛ پیاده‌سازی مجاز نیست.**

تاریخ ثبت: 2026-10-13
آخرین بازبینی: 2026-10-14

این سند پیشنهاد می‌کند قواعد فعلی استخراج metadata مدل‌ها و Queryها در ماژول `data_base:query:meta_data` متمرکز شوند. این Plan به‌تنهایی مجوز تغییر سورس، API، Gradle، تست‌ها یا رفتار جاری نیست. تصمیم‌های باز و حدود شواهد در پایان مشخص شده‌اند.

## ۱. مسئله و هدف

قواعد مربوط به نام جدول، alias، نام ستون، نام Query و خروجی‌های typed اکنون در `query:builder` متمرکز شده‌اند؛ در حالی که ماژول `query:meta_data` برای استخراج metadata پارامترها وجود دارد و Renderer و Executor نیز به آن وابسته‌اند. این مرزبندی باعث می‌شود مسئولیت نام‌گذاری و تفسیر annotationها در Builder بماند و استفادهٔ سازگار از همان قواعد در سایر مسیرها دشوار شود.

هدف Plan، انتقال کنترل‌شدهٔ **حل metadata اعلام‌شده در مدل و تعریف Query** به `query:meta_data` است. Builder همچنان مسئول ساخت AST و اعمال تصمیم‌های مخصوص ساخت Query می‌ماند. این Plan قصد ندارد metadata را به مرکز وابستگی همهٔ ماژول‌ها تبدیل کند.

## ۲. اصول و مرزها

1. قواعد موجود و رفتار قابل مشاهده مبنای مهاجرت‌اند؛ انتقال مالکیت نباید به‌تنهایی رفتار را تغییر دهد.
2. `query:meta_data` مالک حل metadata اعلانی پشتیبانی‌شده است: تفسیر conventionها و annotationها، اعمال precedence تعریف‌شده، اعتبارسنجی و ارائهٔ مقدارهای حل‌شده.
3. Builder پس از centralization نباید conventionها و annotationها را مستقلاً دوباره تفسیر کند؛ اما همچنان مالک override صریح محل استفاده، ساخت source و AST، composition، alias occurrence در scope، و تصمیم‌های construction-time است.
4. مرز دقیق این مسئولیت‌ها چنین است:
   - **حل مقدار اعلانی/default:** استخراج مقدار convention یا annotation برای یک Model، property، Query یا Query output؛ مالک پیشنهادی `query:meta_data` است.
   - **override صریح محل استفاده:** مقداری که caller در DSL/API همان فراخوانی می‌دهد؛ آن را Builder اعمال می‌کند، مگر اینکه سورس نشان دهد override بخشی از metadata declarative است.
   - **ساخت AST و source:** تبدیل مقدارهای resolved و overrideها به nodeها و sourceها؛ مسئولیت Builder/AST است.
   - **alias occurrence:** alias مؤثر یک منبع در Query جاری و scope آن؛ مسئولیت Builder/context است و نباید metadata تعریف را mutate کند.
   - **execution type:** انتخاب نوع materialization طبق قرارداد فعلی `ExecutionType`/`execute(DataType)`؛ تصمیم construction-time در Builder/AST باقی می‌ماند.
5. precedence عمومی فقط برای فیلدهایی اعمال می‌شود که واقعاً هر منبع را پشتیبانی می‌کنند: `Convention default → Annotation override → Explicit DSL/API override`. منبعی که برای یک فیلد مسیر ورودی واقعی ندارد، در ماتریس `نامرتبط/پشتیبانی‌نشده` ثبت می‌شود؛ معنای API دیگری به آن تعمیم داده نمی‌شود.
5. سه مفهوم زیر جدا می‌مانند:
   - metadata مدل و propertyهای Model؛
   - metadata تعریف Query و خروجی typed؛
   - مفهوم legacy مربوط به `QBCte` و `QBCteSelect`.
6. قرارداد پارامترهای موجود در `query:meta_data` حفظ می‌شود و این Plan بازطراحی آن را در بر نمی‌گیرد.
7. هیچ تغییری در `IModelBase`، قراردادهای عمومی Query، SQL، Executor یا Migration صرفاً برای یکسان‌سازی نام‌ها مجاز نیست.

### ۳.۲ پیاده‌سازی فعلی metadata

فایل `data_base/query/builder/src/main/kotlin/ast/select_builder/metadata/QueryBuilderMetadata.kt` یک object داخلی با قواعد زیر است:

- `requireTable` و `requireColumn` وجود annotation مربوط را بررسی می‌کنند.
- `tableName`, `tableAlias`, `columnName`, `columnAlias` مقادیر `QBTable` و `QBColumn` را با conventionهای فعلی resolve می‌کنند.
- `queryName`, `queryAlias`, `queryLogicalOutputName`, `queryPublishedAlias` metadata مربوط به `QBQuery` و `QBQuerySelect` را resolve می‌کنند.
- convention نام‌گذاری شامل تبدیل به snake_case و حذف پسوند قراردادی `Model` یا `Query` از نام کلاس است.
- sentinel مشترک `QB_METADATA_UNSET` مقدار NUL است و omission را از رشتهٔ خالی صریح جدا می‌کند.

فهرست زیر از جست‌وجوی کل source فعال `query:builder` به دست آمده است و مبنای inventory این نسخه است:

## ۴. قراردادهای رفتاری فعلی و precedence به‌ازای هر فیلد

قاعدهٔ عمومی `Convention default → Annotation override → Explicit DSL/API override` فقط وقتی معنا دارد که هر سه منبع برای همان فیلد در API جاری وجود داشته باشند. مقدار resolved در `query:meta_data` باید convention و annotation را اعمال کند؛ Builder هر override صریح محل استفاده را جداگانه و مطابق قرارداد همان API اعمال می‌کند. در ستون «DSL/API» واژهٔ «ندارد» یعنی در مسیر typed همان فیلد، override مستقیمی در سورس مشاهده نشده است؛ API مشابهی که مسیر دیگری می‌سازد، override این فیلد محسوب نمی‌شود.

### قرارداد الزامی: resolution فیلدبه‌فیلد

Resolver فقط همان metadata fieldی را resolve و validate می‌کند که درخواست شده است. درخواست یک فیلد نباید فیلد نامرتبط را زودتر resolve یا validate کند. این قرارداد با API موجود `QueryBuilderMetadata` که متدهای مستقل دارد سازگار است و از تغییر زمان یا محل بروز خطا جلوگیری می‌کند. اگر یک value object چند field را حمل کند، ساخت آن نباید محاسبهٔ eager یا validation همهٔ fieldها را تحمیل کند. اعتبارسنجی‌های صریح موجود مانند `requireTable` و `requireColumn` نیز در callerهایی که اکنون آن‌ها را اجرا می‌کنند حفظ می‌شوند؛ این preconditionها مجوز resolve کردن alias یا field نامرتبط نیستند.

به‌طور مشخص:

- `queryName(type)` نباید `queryAlias(type)` را resolve کند؛ برای نمونه، `@QBQuery(alias = "")` نباید هنگام درخواست صرفاً نام Query خطا بدهد.
- `queryAlias(type)` نباید اعتبارسنجی نام Query را به‌طور ضمنی انجام دهد.
- `queryLogicalOutputName(property)` و `queryPublishedAlias(property)` مستقل‌اند؛ خالی‌بودن یکی فقط هنگام درخواست و اعتبارسنجی همان فیلد خطا می‌دهد.
- نام و alias جدول Model، و نام و alias ستون Model، مستقل resolve می‌شوند. اعتبارسنجی الزامی annotation/name همچنان در همان مسیرهایی انجام می‌شود که خط مبنا آن را انجام می‌دهد.
- override صریح Builder همچنان در Builder اعمال می‌شود. Metadata resolver نباید برای محاسبهٔ defaultهای استفاده‌نشده، خطای تازه یا زودهنگام ایجاد کند.

| فیلد | Convention/default | Annotation | Override صریح DSL/API | Unset و empty | اعتبارسنجی | مالک حل/اعمال |
|---|---|---|---|---|---|---|
| `QBTable.name` | نام کلاس با حذف پسوند `Model` و snake_case | `QBTable.name` مقدار صریح را جایگزین می‌کند | برای typed `model(KClass)` override نام شناسایی نشده؛ `table(String)` یک مسیر source جداست، نه override این metadata | sentinel یعنی convention؛ `""` نامعتبر | `@QBTable` لازم و نام غیرخالی | حل در metadata؛ انتخاب raw table در Builder |

ماتریس برای رفتارهای مستند در `QueryBuilderMetadata.kt`, `QueryTableBuilder.kt`, `QueryColumnsBuilder.kt`, `CteBuilder.kt` و `QueryRenderSelectBuilder.kt` تنظیم شده است. عبارت «شناسایی نشده» فقط به همان overload و مسیر typed اشاره دارد. تغییر validation، رفتار رشتهٔ خالی یا زمان اجرای validation در مهاجرت مجاز نیست.

### ۴.۱ تفکیک resolution از ساخت Query

- `QueryColumnsBuilder.inferExecutionType` هم‌اکنون نوع‌های `Int`, `Long` و `String` را نگاشت می‌کند. این inference مربوط به ساخت Query است و در این Plan به metadata resolver منتقل نمی‌شود.
- انتخاب صریح `execute(DataType)` و قرارداد AST مربوط به `PropertyReference` در Builder/AST باقی می‌مانند.
- AST مربوط به خروجی Query، `ColumnAlias`, `ExecutionType` و `PropertyReference` را نگه می‌دارد؛ metadata resolver نباید ساختار یا مالکیت آن را تکرار کند.
- metadata alias تعریف Query با alias مربوط به occurrence در scope مصرف‌کننده یک مفهوم نیست. `QueryRenderSelectBuilder.resolveCteOccurrenceAlias` alias صریح occurrence را بر default alias مقدم می‌کند و `CteSourceContext` همان alias مؤثر را نگه می‌دارد؛ resolver فقط default تعریف را می‌دهد.
- `QueryTableBuilder.model` ابتدا override از پیش تنظیم‌شده را بر alias metadata مقدم می‌کند؛ متد `alias(String)` نیز context و AST source را در زمان ساخت به‌روز می‌کند. این رفتار construction-time است و نباید به resolver منتقل شود.
- `QueryColumnsBuilder.alias(String)` alias SQL خروجی را در AST تنظیم می‌کند؛ `QueryBuilderMetadata.queryLogicalOutputName` نام logical property را جداگانه resolve می‌کند. دو فیلد نباید با هم تغییر کنند.
- `CteBuilder` نام runtime CTE را جدا از `logicalQueryName` نگه می‌دارد. `withName` در `QueryWithsItemBuilder` نام SQL entry را تعیین می‌کند و نباید identity یا metadata تعریف را تغییر دهد.
- `Cte` قابل composition، `ICteDeclaration<P>`، و APIهای legacy `ICte`/`with(...)` از هم جدا می‌مانند. `with(withName, cte)` نام SQL مربوط به entry را تعیین می‌کند و نباید به‌عنوان تغییر metadata تعریف Query تفسیر شود.
- `QBCte` و `QBCteSelect` legacy در این Plan به‌صورت خودکار به `QBQuery`/`QBQuerySelect` مهاجرت داده نمی‌شوند.

### ۴.۲ قرارداد استقلال فیلدها

تغییر یک فیلد metadata نباید به‌طور ضمنی فیلد مستقل دیگری را عوض کند، مگر آنکه قرارداد صریح موجود چنین رابطه‌ای را تعریف کرده باشد. این‌ها invariants رفتاری پذیرش‌اند؛ انتخاب representation داخلی آزاد است.

| invariant | مؤلفهٔ مرتبط | آزمون پذیرش قابل راستی‌آزمایی |
|---|---|---|
| تغییر `QBQuerySelect.alias`، `QBQuerySelect.name` را تغییر نمی‌دهد | `QueryMetadataResolver`; `QueryColumnsBuilder`; `CteBuilder` | annotation با logical name و SQL alias مستقل؛ assert کنید logical mapping ثابت و SQL output name فقط مطابق alias تغییر کند |
| `QBQuerySelect.name` هویت logical output است و `alias` نام SQL output | Query metadata، `CteBuilder`, `CteSourceContext` | خروجی‌ای با دو نام متفاوت؛ assert logical name مستقل بماند و typed output به SQL alias واقعی تعریف‌شده resolve شود؛ سازوکار lookup همان implementation جاری بماند |
| تغییر occurrence alias، metadata تعریف Query یا CTE را mutate نمی‌کند | `QueryTableBuilder`, `QueryRenderSelectBuilder`, `CteSourceContext` | همان definition دو بار با occurrence alias متفاوت استفاده شود؛ AST هر occurrence alias متفاوت داشته باشد و `Cte.name`/Query metadata ثابت بماند |
| تغییر CTE runtime/declaration name یا نام entry با `withName`، Query logical identity، declaration owner و occurrence alias را mutate نمی‌کند | `CteBuilder`, `QueryWithsItemBuilder`, `BuiltCteComposition` | دو حالت جدا: factory name صریح باید از `logicalQueryName` و occurrence alias جدا بماند؛ `withName` باید فقط SQL entry را تغییر دهد. object/declaration reference نیز ثابت assert شود |
| انتخاب `ExecutionType` مقدار نوع declared property را تغییر نمی‌دهد | `QueryColumnsBuilder`, `IQueryColumnsAst` | property reference و declared `KType` ثابت بمانند؛ فقط `ExecutionType` مطابق `execute(DataType)` تغییر کند |
| تغییر یک فیلد مستقل، فیلدهای دیگر را mutate نمی‌کند | Resolverهای Model/Query | دادهٔ metadata را با تغییر یک annotation field resolve کنید؛ assert فیلدهای نامرتبط byte-for-byte/value-equal بمانند |
| metadata مربوط به Model source property با Query output property اشتباه نمی‌شود | `ModelMetadataResolver` در برابر `QueryMetadataResolver`؛ Builder paths جدا | propertyهای هم‌نام در دو owner مختلف؛ assert Model column resolution و Query logical/SQL output resolution از قرارداد owner خود استفاده کنند |
| default alias، explicit alias، logical name، SQL name و declaration identity مجزا می‌مانند | resolverها و Builder source/CTE contexts | سناریوی همهٔ نام‌ها متفاوت؛ assert هر کدام در فیلد AST/CTE مورد انتظار ظاهر شود و دیگری را overwrite نکند |

این‌ها **تست‌های پیشنهادی Plan 15** هستند، نه ادعای پوشش در تست‌های موجود. فایل‌هایی مانند `QueryMetadataResolutionTest`, `TypedModelReferenceTest`, `QueryDeclarationTest`, `CteWithsIntegrationTest` و `V3QueryRuntimeNameTest` فقط candidate برای بازبینی‌اند؛ assertionهای واقعی باید پیش از استفاده به‌عنوان مدرک خوانده شوند. آزمون جدید باید برای هر invariant صریحاً assertion داشته باشد.

## ۵. Vision پیشنهادی برای `query:meta_data`

ماژول، مالک قواعد قابل استفادهٔ مجدد برای **استخراج و حل metadata اعلانی** باشد؛ نه مالک ساخت Query یا اجرای آن. Resolver مقدار default/annotation را resolve و validate می‌کند. سپس Builder مقدار resolveشده را با override صریح همان use-site ترکیب کرده، AST/source را می‌سازد و alias occurrence یا execution type را در چارچوب قرارداد فعلی اعمال می‌کند. Builder نباید قواعد annotation/convention را دوباره کپی کند.

### ۵.۱ مسئولیت‌ها

| مسئولیت | مالک پیشنهادی | دلیل و حد مسئولیت |
|---|---|---|
| تفسیر annotationهای `QBTable`, `QBColumn`, `QBQuery`, `QBQuerySelect` | `query:meta_data` | یک‌بار تعریف شدن sentinel، convention، annotation override و validation |
| استخراج metadata پارامترها از AST | قرارداد موجود در `query:meta_data/parameters` | مسئولیت فعلی ماژول؛ حفظ شود |
| انتخاب source و ساخت AST | `query:builder` | این کار ساخت Query است، نه introspection |
| اعمال override صریح DSL در محل استفاده | Builder | precedence به API همان use-site وابسته است؛ resolver convention/annotation را دوباره resolve نمی‌کند |
| ثبت alias occurrence فعال و lookup آن در composition | Builder/context مربوط به source | به scope نهایی Query وابسته است |
| تعیین `ExecutionType` و ساخت `ColumnAlias` در AST | Builder و `query:ast` | نوع اجرا و nodeهای Query جزو metadata reflection عمومی نیستند |
| SQL emission و dialect-specific syntax | `query:renderer` و `query:dialect` | metadata نباید به placeholder یا SQL نهایی وابسته باشد |
| JDBC binding و lifecycle منابع | `query:executor` و `manager:execute` | metadata فقط دادهٔ مورد نیاز را می‌دهد |
| مدل‌های نمونه مانند `Users` | `models:eloquent` | ماژول metadata نباید به نمونه‌های پروژه وابسته شود |

### ۵.۲ شکل خروجی resolverها

پیشنهاد حداقلی این است که خروجی‌های typed و immutable، مقدارهای resolveشده را حمل کنند، نه خود annotation را به‌عنوان تنها API مصرف‌کننده:

- metadata مدل: نام جدول و alias resolved/default (با حفظ امکان alias خالی)، و نام ستون و alias property. `QBColumn.primaryKey` در این Plan وارد قرارداد resolver نمی‌شود، چون مصرف‌کننده‌ای در call siteهای هدف Builder پیدا نشده است.
- metadata Query: نام و alias پیش‌فرض تعریف Query، logical output name هر property و SQL-published alias.
- خطاهای metadata: validation در مرز resolver با پیام‌های هم‌ارز خط مبنا.

Resolver خروجی declared/default metadata را ارائه می‌کند و DSL override را اعمال نمی‌کند. هر تابع و typeای که Builder مستقیماً مصرف می‌کند باید Kotlin `public` باشد، چون Builder ماژول جداگانه‌ای است؛ helperهایی که از مرز ماژول عبور نمی‌کنند باید `internal` بمانند. این الزام visibility بین ماژول‌های Repository به‌تنهایی به معنی API پایدار منتشرشده یا تضمین ABI بیرونی نیست. شواهد فعلی دربارهٔ انتشار artifact یا سیاست ABI وجود ندارد و Plan چنین تضمینی نمی‌دهد.

### ۶.۱ مسئولیت فایل‌ها

این ساختار و تمام نام‌های کلاس/فایل تازه **پیشنهادی و موقت** هستند؛ پیش از implementation باید نیاز هر type/file و انطباقش با convention واقعی Repository توجیه شود. فایل مستقل فقط در صورت وجود مسئولیت روشن ایجاد شود. اگر metadata model کوچک و محدود است، ادغامش در فایل resolver مرتبط ترجیح دارد تا وقتی رشد واقعی جداسازی را توجیه کند. هیچ‌یک از این مسیرها هم‌اکنون وجوددار یا پیاده‌سازی‌شده فرض نمی‌شوند.

### ۶.۲ شکل API پیشنهادی، نه امضای مصوب

نمونهٔ مفهومی برای بحث طراحی:

```kotlin
ModelMetadataResolver.tableName(type: KClass<*>)
ModelMetadataResolver.tableAlias(type: KClass<*>)
ModelMetadataResolver.columnName(type: KClass<*>, property: KProperty1<*, *>)
ModelMetadataResolver.columnAlias(property: KProperty1<*, *>)

QueryMetadataResolver.queryName(type: KClass<*>)
QueryMetadataResolver.queryAlias(type: KClass<*>)
QueryMetadataResolver.queryLogicalOutputName(property: KProperty1<*, *>)
QueryMetadataResolver.queryPublishedAlias(property: KProperty1<*, *>)
```

این امضاها **نمونهٔ پیشنهادی و field-specific** هستند و symbol موجود محسوب نمی‌شوند؛ نام دقیق و گروه‌بندی فایل‌ها هنگام implementation می‌تواند با convention Repository هماهنگ شود، اما قرارداد استقلال فیلدها الزامی است. هر درخواست فقط فیلد خودش را resolve و validate می‌کند. اگر نوع‌های immutable تجمیعی استفاده شوند، ساخت آن‌ها نباید فیلدهای نامرتبط را eager محاسبه کند. عمداً پارامتر explicit alias ندارند: resolver مقدار convention/annotation را برمی‌گرداند و Builder override صریح source/output را مطابق قرارداد همان API اعمال می‌کند. API مصرفی بین دو module باید Kotlin `public` باشد؛ helperهای داخلی باقی‌مانده `internal` می‌مانند. API جدیدی صرفاً برای شبیه‌شدن به این نمونه‌ها لازم نیست.

## ۷. قرارداد وابستگی‌ها

### ۷.۱ گراف هدف

```text
query:meta_data -> core
query:meta_data -> query:ast        (برای extractor فعلی پارامتر؛ فقط در صورت نیاز باقی بماند)
query:meta_data -> kotlin-reflect   (برای annotation lookup و KClass/KProperty reflection)

query:builder -> query:meta_data
query:builder -> kotlin-reflect     (وابستگی موجود و لازم برای returnType/parameters در Builder)
query:renderer -> query:meta_data   (وابستگی موجود برای پارامترها)
query:executor -> query:meta_data   (وابستگی موجود برای پارامترها)
```

ممنوع:

- `query:meta_data -> query:builder`
- `query:meta_data -> query:renderer`, `query:executor`, `manager:execute`, Migration یا `models:eloquent`
- وابستگی دوری یا تعریف مستقل و ناسازگار یک metadata model در چند ماژول.

### ۷.۲ Reflection و توسعه‌پذیری

اضافه‌شدن AST node جدید نباید خودبه‌خود ماژول metadata را تغییر دهد، مگر اینکه node جدید metadata اعلانی تازه‌ای مصرف کند. نوع Binding/Parameter جدید باید از قرارداد پارامترهای موجود پیروی کند یا یک نیاز جدید را جداگانه مطرح سازد. Dialect و روش اجرای جدید نباید به resolverهای مدل/Query وابسته شوند مگر اینکه واقعاً metadata اعلانی نیاز داشته باشند.

reflection مربوط به declaration metadata در `query:meta_data` به Kotlin `KClass` و `KProperty1` محدود می‌ماند؛ resolver باید annotationهای همان class یا property referenceای را بخواند که caller داده است و نباید model instance، getter، جست‌وجوی property هم‌نام یا پیمایش superclass لازم داشته باشد. Source فعلی همین الگو را نشان می‌دهد: `QueryBuilderMetadata` از `type.annotations` و `property.annotations` استفاده می‌کند. تست موجود `QueryMetadataResolutionTest` نیز یک inherited Query property reference (`DerivedInheritedQuery::inheritedCode`) را به API typed output می‌دهد؛ این شاهد رفتار عمومی همهٔ حالت‌های Model نیست. اگر مسیر Model در عمل یک inherited `KProperty1` می‌پذیرد، فقط همان reference ورودی باید بررسی شود؛ هیچ آزمونی برای traversal یا ارث‌بری خودکار annotation کلاس لازم نیست. Builder وابستگی reflection موجود را حفظ می‌کند، چون انتخاب `ExecutionType` از `property.returnType` و تعیین typed-property owner از `property.parameters` مسئولیت Builder است.

Caching بخشی از مرحلهٔ نخست نیست. تا وقتی شواهد کارایی یا قرارداد lifecycle وجود ندارد، resolver خالص و بدون cache نگه داشته شود تا رفتار و تست‌پذیری ساده بماند.

## ۱۰. تست‌های پذیرش

موارد زیر معیارهای آزمون آینده‌اند، نه ادعای پوشش فعلی. نام یک تست یا گزارش اجرای قبلی به‌تنهایی اثبات نمی‌کند invariant پوشش داده شده است؛ assertionهای واقعی باید خوانده شوند و اگر assertion مستقیم وجود ندارد، تست افزوده یا گسترش داده شود.

### ۱۰.۱ Resolution و precedence

- `QBTable.name`: sentinel/default، مقدار annotation صریح و empty نامعتبر.
- `QBTable.alias`: sentinel/default، مقدار annotation، empty annotation به‌معنای بدون alias و DSL alias صریح.
- `QBColumn.name`: default از property، مقدار annotation و empty نامعتبر.
- `QBColumn.alias`: default از property، annotation خالی/حذف‌شده و override خروجی SELECT صریح.
- `QBQuery.name` و `QBQuery.alias`: default، annotation صریح و empty نامعتبر.
- `QBQuerySelect.name` و `QBQuerySelect.alias`: default، annotation صریح و empty نامعتبر؛ تفاوت logical name و SQL name.
- خطای annotation مفقود برای Model/property و نام convention غیرقابل استنتاج.
- `QBCte` و `QBCteSelect`: مقدار پیش‌فرض annotation خالی است. قطعهٔ lookup مشاهده‌شده در `QueryColumnsBaseBuilder` کامنت است؛ این Plan فعال‌سازی یا بازطراحی مسیر legacy را مجاز نمی‌کند. اگر در inventory زمان اجرا call site فعال پیدا شد، آن را خارج از این resolver نگه دارید مگر با تصمیم جداگانه.
- override صریح فقط در APIهایی که در ماتریس بخش ۴ برای آن فیلد ثبت شده؛ سایر overloadها نباید به‌عنوان override تلقی شوند.
- resolution مستقل fieldها: درخواست `queryName` نباید `queryAlias` را resolve یا validate کند؛ همین معیار برای `queryLogicalOutputName`/`queryPublishedAlias` و فیلدهای Model اعمال شود.
- class/property ورودی: resolver باید فقط metadata همان `KClass` یا `KProperty1` داده‌شده را بخواند. Source فعلی `type.annotations` و `property.annotations` را مستقیماً می‌خواند و traversal سلسله‌مراتبی ندارد. اگر مسیر Model reference یک property ارث‌رسیده را می‌پذیرد، تست محدود همان reference را به resolver می‌دهد و نتیجهٔ metadata آن را بررسی می‌کند؛ هیچ `QBTable` از superclass برای subclass استنتاج نمی‌شود و property دیگری با جست‌وجوی نام کشف نمی‌شود. رفتار فنی Kotlin reflection برای چنین referenceای، اگر برای قرارداد call site لازم باشد، فقط به‌عنوان جزئیات مشخص و محدود baseline می‌شود.
- property Model دارای getter خطادار باید metadata را بدون اجرای getter resolve کند.

### ۱۰.۲ آزمون‌های field independence

| invariant | مسیر آزمون | assertion پذیرش |
|---|---|---|
| `QBQuerySelect.alias`، `QBQuerySelect.name` را تغییر نمی‌دهد | metadata resolver + typed CTE Builder | هر دو مقدار جداگانه assert شوند؛ SQL alias تغییر کند ولی logical name ثابت بماند |
| logical output name و SQL output alias دو مفهوم‌اند | typed output composition | مقدار logical مستقل و SQL alias واقعی خروجی assert شود؛ lookup/validation داخلی طبق implementation موجود بماند |
| occurrence alias metadata تعریف را mutate نمی‌کند | Model/CTE source Builder | یک definition در occurrenceهای متفاوت با aliasهای متفاوت استفاده شود؛ metadata و identity تعریف ثابت بمانند |
| نام SQL declaration/`withName`، Query identity یا occurrence alias را تغییر نمی‌دهد | `CteBuilder` و `QueryWithsItemBuilder` | فقط نام WITH entry تغییر کند؛ CTE runtime identity، `logicalQueryName`, declaration owner و source alias جداگانه assert شوند |

| درخواست یک field باعث eager validation فیلد نامرتبط نمی‌شود | Model/Query resolverهای field-specific | `queryName` برای Query دارای alias خالی موفق باشد و `queryAlias` همان Query هنگام درخواست خودش خطای فعلی را بدهد؛ زوج‌های name/alias دیگر نیز جدا resolve شوند |

| default alias، explicit alias، logical name، SQL output name و declaration identity مستقل‌اند | integration test typed CTE با نام‌های عمداً متفاوت | مقدار هر مفهوم در محل AST/API مورد انتظار جداگانه assert شود |

- Resolverها از مصرف‌کنندگان مجاز قابل دسترسی باشند؛ dependency graph Gradle چرخه نداشته باشد.
- تست‌های Model, Query, CTE/WITH و typed output که assertion مرتبط دارند اجرا شوند؛ coverage فقط بر اساس assertion ثبت شود.
- تست‌های `query:meta_data/parameters` رفتار قبلی پارامترها را حفظ کنند.
- در صورت تغییر compile dependencies، compile/test ماژول‌های Renderer و Executor اجرا شوند.
- آزمون metadata ورودی مستقیم، class/property دقیقِ داده‌شده را پوشش دهد. اگر مسیر Model inherited `KProperty1` می‌پذیرد، یک تست کوچک همان reference را بررسی کند؛ تست traversal، جست‌وجوی سلسله‌مراتب یا inherited class annotation اضافه نشود.
- getterهای Model property در resolution اجرا نشوند؛ این موضوع با getterی سنجیده شود که عمداً خطا می‌دهد. تست‌های موجود getterهای Query output را نیز حفظ کند.

- تست مرز ماژول تأیید کند Builder به resolverهای `public` دسترسی دارد؛ helperهای غیرعبوری `internal` می‌مانند.
- نام taskهای دقیق باید از Gradle واقعی تأیید شوند؛ این Plan هیچ فرمانی را اجراشده یا موفق اعلام نمی‌کند.

## ۱۱. ریسک‌ها و تصمیم‌های باز

1. **جزئیات Kotlin reflection برای inherited property reference:** قرارداد پایه، استفاده از همان class/property ورودی و نبود hierarchy traversal است. Source فعلی `type.annotations` و `property.annotations` را مستقیماً می‌خواند و تست موجود inherited Query property reference را پوشش می‌دهد؛ اینکه مسیر Model فعلی چنین referenceای را از call site می‌پذیرد و دقیقاً چه نتیجه‌ای از API reflection می‌گیرد، فقط اگر در پیاده‌سازی لازم شود با یک آزمون محدود baseline می‌شود. این ابهام مجوز طراحی inheritance behavior نیست.
2. **Visibility و ABI:** resolverهای مورد استفادهٔ Builder باید `public` باشند؛ آیا این module-facing Kotlin API بعداً منتشر یا ABI-stable خواهد شد نامشخص است و خارج از ادعای این Plan باقی می‌ماند.
3. **Getter Model:** source فعلی annotation property می‌خواند، نه getter، اما test مستقیم Model وجود ندارد؛ acceptance test باید این رفتار را تثبیت کند.
4. **وابستگی Kotlin reflection:** inventory فعلی نشان می‌دهد Builder همچنان به reflection برای `returnType` و `parameters` نیاز دارد؛ dependency آن در این Plan حفظ می‌شود.
5. **QBCte legacy:** default annotationها خالی‌اند، اما lookupهای پیدا‌شده در Builder کامنت هستند و reader فعال از این جست‌وجو تأیید نشد. فعال‌سازی یا مهاجرت احتمالی خارج از scope است.
6. **Caching:** ضرورت و scope cache شواهد ندارد؛ در این Plan اضافه نمی‌شود.
7. **مدل‌سازی property metadata:** `PropertyReference`, `ColumnAlias` و `ExecutionType` جزو AST/Builder فعلی‌اند. `QBColumn.primaryKey` نیز تا زمان یافتن مصرف‌کنندهٔ در scope بخشی از خروجی resolver نیست.
8. **Migration call sites:** Migration خارج از scope مستقیم Plan 15 است؛ صرفاً برای تکمیل metadata centralization نباید تغییر کند. اگر شواهد Repository یک dependency ضروری یا نگرانی سازگاری را ثابت کرد، آن مورد به‌عنوان تصمیم scope جداگانه مستند و تصویب می‌شود. این Plan هیچ تغییر سورسی در Migration را مجاز نمی‌کند.

## ۱۲. موارد خارج از محدوده

- تغییر SQL، AST، alias precedence، پارامترها یا ترتیب bind.
- طراحی generic metadata framework یا plugin registry.
- cache سراسری، reflection scanning گسترده یا annotation processor.
- تغییر APIهای عمومی Model/Query، CTE یا `WITH` بدون نیاز اثبات‌شده و تأیید جداگانه.
- حذف `QBCte`, `QBCteSelect`, `ICte` یا `with(...)` legacy.

آمادگی برای شروع کار و اثبات تکمیل کار دو gate مستقل‌اند؛ اصلاح این سند هیچ‌کدام را خودکار برآورده نمی‌کند.

### ۱۳.۱ آمادگی برای implementation

این نسخه قراردادهای لازم را برای آماده‌سازی Plan اجرایی مشخص می‌کند؛ بااین‌حال وضعیت سند تا بازبینی و تأیید صریح آن `Draft` می‌ماند و این بخش مجوز پیاده‌سازی نیست. معیارهای قبل از صدور مجوز عبارت‌اند از:

1. inventory کامل و قابل بازبینی از call siteهای `QueryBuilderMetadata`؛
2. inventory مستقیم Kotlin reflection در Builder بازبینی شده باشد؛ dependency آن در Builder حفظ شود و فقط lookupهای declaration metadata منتقل شوند؛
3. baseline رفتارها و تست‌های مرتبط، با بازبینی assertionهای واقعی؛
4. قرارداد visibility بین metadata و Builder ثبت شده باشد: API مصرفی Kotlin `public`، helperهای غیرعبوری `internal`، بدون ادعای ABI پایدار یا انتشار بیرونی؛
5. dependency graph هدف بدون چرخه و با وابستگی‌های ضروری؛
6. ماتریس precedence، unset/empty، validation و field independence برای همهٔ فیلدهای در scope؛
7. acceptance test مشخص برای هر invariant وجود داشته باشد؛ آزمون‌ها resolution از class/property ورودی، field independence و عدم اجرای getter را تثبیت کنند؛ فقط در صورت پشتیبانی call site از inherited Model property reference، جزئیات خواندن همان reference جداگانه baseline شود؛
8. legacy `QBCte*` و Migration در scope خود باقی بمانند، مگر اینکه تغییرشان جداگانه مستند و تصویب شود.

اگر یکی از تصمیم‌های مؤثر بر correctness، compatibility یا API design باز باشد، وضعیت **Draft / Not Implementation Ready** باقی می‌ماند و implementer نباید آن را با فرض شخصی حل کند.

### ۱۳.۲ تکمیل implementation و بستن Plan

پس از implementation جداگانه و مجاز، بستن Plan نیازمند شواهد واقعی برای تمام موارد زیر است:

1. همهٔ call siteهای هدف از قرارداد مرکزی resolution استفاده کنند؛
2. منطق convention/annotation تکراری از Builder حذف شده باشد یا باقی‌ماندن هر مورد با دلیل مشخص مستند شود؛
3. رفتار Model و Query، از جمله validation، empty/sentinel، error cases و metadataهای خروجی حفظ شده باشد؛
4. تمام invariants بخش ۴.۲/آزمون‌های بخش ۱۰ با assertion مستقیم پاس شوند؛
5. تست‌های مرتبط Builder، CTE/WITH، Renderer، Executor و parameter metadata موفق باشند؛
6. Gradle dependency graph بدون چرخه باشد و وابستگی reflection در محل لازم قرار گیرد؛
7. قرارداد parameter metadata موجود حفظ شده و regression testهای آن موفق باشند؛
8. هیچ تغییر ناخواسته در API، SQL، AST، execution behavior، legacy CTE یا Migration رخ نداده باشد؛
9. نتایج test/build از اجرای واقعی همان working tree ثبت شوند؛ تست اجرا‌نشده یا گزارش تاریخی موفق شمرده نشود؛
10. تغییرات خارج از scope و وضعیت working tree گزارش شده باشند.

وضعیت فعلی این سند **Draft — طرح معماری برای بررسی؛ پیاده‌سازی مجاز نیست** باقی می‌ماند. بازنگری مستندات نه پیاده‌سازی است و نه اعلام closure.
