# Test Plan v3.0: Migration Test Context, Workflow و Runtime Monitoring

## وضعیت

`Implementation Ready`

این سند فقط Plan است. در این مرحله هیچ source، test، Gradle، `help.json`، UI یا documentation اجرایی تغییر نمی‌کند.

## 1. هدف

برای Testهای Integration ماژول `:data_base:migration`، صفحهٔ نتیجهٔ Help باید علاوه بر وضعیت کلی Gradle/JUnit، دو نوع اطلاعات را از هم جدا کند:

1. **Test Context**: قرارداد ثابت و قابل‌فهم تست؛ هدف، پیش‌شرط‌ها، مراحل مورد انتظار، اثر refresh و آنچه تست بررسی می‌کند.
2. **Test Runtime**: دادهٔ واقعی همان اجرای مشخص؛ مرحله‌هایی که واقعاً شروع/تمام شده‌اند، Migrationهایی که واقعاً اجرا شده‌اند، state مشاهده‌شدهٔ schema و history، و محل توقف در صورت failure.

صفحه نباید از روی نام تست یا تعریف ثابت، اجرای واقعی را حدس بزند. اگر یک مرحله اجرا نشده، باید `Not executed` نمایش داده شود؛ این وضعیت با `Failed` فرق دارد.

## 2. Scope

### داخل Scope

* تعریف و نمایش Context ثابت برای Testهای موجود Migration.
* قرارداد جمع‌آوری و انتقال Runtime همان اجرای تست.
* workflow قابل‌نمایش برای `MigrationSystemIntegrationTest` و `MigrationSchemaIntegrationTest`.
* نمایش وضعیت مستقل از وضعیت Report HTML و نتیجهٔ کلی Gradle.
* نمایش snapshot/diffهای واقعی database فقط بر اساس داده‌ای که خود Test مشاهده و گزارش کرده است.
* امنیت داده‌های ورودی و Runtime payload.
* تست‌های Help و تست‌های مرتبط با Test instrumentation/reporting.

### خارج از Scope

* تغییر رفتار Migration API، AST، Builder، Renderer، Executor، Migrator یا State Store.
* تغییر معنای refresh یا ownership آن.
* transaction، rollback، retry، lock، runner جدید یا lifecycle جدید Migration.
* اجرای SQL از Help یا ایجاد تفسیر حدسی از SQL/JUnit output.
* تعریف workflow engine عمومی، plugin system، event bus یا framework عمومی برای همهٔ تست‌ها.
* تغییر قرارداد ورودی‌های دیتابیس یا انتخاب Database.
* تضمین compatibility برای MariaDB یا نسخه‌های MySQL که در Repository تعیین نشده‌اند.

## 4. تفکیک قرارداد Context و Runtime

### 4.1 Test Context — تعریف ثابت

Context از Test Definition ثابت خوانده می‌شود و قبل از اجرای Test نیز قابل نمایش است. حداقل باید شامل این مفاهیم باشد:

* هدف و دامنهٔ Test.
* شرایط لازم و پیش‌فرض‌های واقعی Test، از جمله MySQL و propertyهای اجباری.
* معنای refresh و مسیر collision برای `refresh=true` و `refresh=false`.
* workflow مورد انتظار با ترتیب declaration/test code.
* Migration IDهای مورد انتظار و grouping در صورت وجود.
* schema objectها و relationهایی که Test قرار است بررسی کند.
* assertionهای کلیدی: schema، foreign key/index/constraint، history، batch، rerun یا failure/resume.
* محدودیت‌ها: Test واقعی MySQL است و موفقیت آن اثبات پشتیبانی MariaDB یا همهٔ نسخه‌ها نیست.

Context **انتظار/توضیح** است؛ نمی‌تواند مدرک اجرای فاز یا وجود object در database همان اجرا تلقی شود.

### 4.2 Test Runtime — مشاهدهٔ همان اجرا

Runtime فقط از دادهٔ تولیدشده/مشاهده‌شده در اجرای جاری می‌آید و باید run-scoped باشد. مفاهیم موردنیاز:

* وضعیت آماده‌سازی و refresh: `not_started`, `in_progress`, `succeeded`, `failed`, `not_executed`.
* وضعیت collision guard و اینکه آیا Migrator شروع شد.
* مراحل/گام‌های ثبت‌شده در Test، با ترتیب واقعی، timestamp یا duration در صورت اندازه‌گیری معتبر.
* Migration ID، batch، نتیجهٔ واقعی execute و وضعیت ثبت history برای هر Migration که Test مشاهده کرده است.
* فاز توقف و علت قابل‌نمایش؛ گام‌های پس از آن `not_executed` باشند، نه `failed`.
* snapshotهای قبل/بعد که خود Test از database metadata/history گرفته است؛ نبود داده باید `unknown/not_collected` باشد، نه فهرست خالی فرضی.
* وضعیت نهایی objectهای تحت بررسی و history؛ failure نتیجهٔ واقعی تست نیز جدا باقی بماند.

Runtime نباید از عنوان Test، JUnit duration، exit code یا HTML report برای ساختن جزئیات فرضی workflow استفاده کند.

### 4.3 محورهای مستقل نتیجه

| محور | نمونهٔ مقادیر | منبع |
|---|---|---|
| Gradle/Test outcome | `Passed`, `Failed` | exit code و Gradle/JUnit نتیجهٔ همان اجرا |
| HTML report | available / unavailable | `index.html` تازهٔ همان اجرا |
| Runtime detail | available / unavailable / incomplete | Runtime payload تازه و معتبر همان اجرا |
| Workflow step | `succeeded`, `failed`, `not_executed`, `not_collected` | Test instrumentation/runtime evidence |

ناهم‌خوانی بین محورهای مستقل پنهان نشود. برای مثال، Gradle `Failed` می‌تواند Runtime artifact معتبر و گام‌های قبلی موفق داشته باشد؛ Report HTML ممکن است مستقل از هر دو موجود یا ناموجود باشد.

## 5. Workflow مورد انتظار هر Test

### 5.1 `migration-system-integration`

Context ثابت باید مراحل زیر را با ترتیب مطابق Test source نمایش دهد:

1. خواندن و validate کردن propertyها و تعیین MySQL `DatabaseConfig`.
2. نصب config تست و بازکردن connection؛ تأیید catalog انتخاب‌شده.
3. اگر refresh فعال است، refresh ابتدای تست روی database انتخاب‌شده؛ در غیر این صورت ارزیابی collision و توقف بدون mutation در صورت برخورد.
4. اجرای successful registration و Migrationها با ترتیب ثبت‌شده؛ بررسی table/column و history/batch.
5. اجرای دوبارهٔ همان Migrator و بررسی عدم تغییر history/schema.
6. اجرای سناریوی failure/resume و بررسی Migrationهای موفق پیش از failure، عدم اجرای موارد پس از failure و عدم ثبت ID ناموفق.
7. اجرای سناریوهای zero-operation و multiple-operation و بررسی عدم ثبت/ساخت موارد بعدی.
8. بررسی state نهایی قابل‌مشاهده؛ database پس از Test برای inspection باقی می‌ماند.
9. بستن connection و restore کردن config process؛ این lifecycle cleanup database نیست.

Runtime باید مسیر واقعی را نشان دهد. اگر collision guard در مرحلهٔ 3 تست را خاتمه دهد، مراحل 4 تا 8 `not_executed` هستند. اگر refresh یا آماده‌سازی پیش از Migrator fail کند، نباید مهاجرتی به‌عنوان شروع‌شده گزارش شود.

### 5.2 `migration-schema-integration`

Context ثابت باید workflow زیر را ثبت کند:

1. خواندن DB properties و نصب config MySQL.
2. اتصال و تأیید catalog انتخاب‌شده.
3. refresh ابتدای تست، در صورت فعال بودن property؛ در غیر این صورت collision check بدون تغییر database.
4. ثبت هفت Migration schema با ترتیب فعلی configuration.
5. اجرای pipeline واقعی `MigrationConfiguration → MigrationMigrator → MigrationExecutor → database`.
6. مشاهدهٔ schema از JDBC metadata: table/column/type/nullability/auto-increment/PK/index/FK بر اساس assertionهای خود Test.
7. مشاهدهٔ history: هفت ID دقیق و batchهای assertion‌شده در همین Test.
8. اجرای collision guard مجدد و اطمینان از عدم mutation و عدم شروع Migrator دوم.
9. نگه‌داشتن schema/history برای inspection؛ فقط restore config و بستن connection.

Runtime نباید نتیجهٔ metadata را فقط به‌صورت «schema درست است» خلاصه کند؛ باید جزئیات ثبت‌شده توسط خود Test یا Test report محدودشده را در اختیار UI بگذارد. قرارداد دقیق level جزئیات باید با توجه به حجم و اعتبار payload در Traceability نهایی شود.

## 6. Runtime Data Contract و Freshness

### Evidence

* API فعلی JSON outcome را از `/api/runs` می‌دهد.
* Gradle runner برای `testResults` از JUnit XML و برای HTML از report directory استفاده می‌کند.
* هیچ schema یا transport موجودی برای Test-generated runtime snapshot، event، DB diff یا phase report پیدا نشده است.

### Interpretation

Help نمی‌تواند واقعیت داخل Test JVM را از API فعلی بازیابی کند. تفسیر JUnit failure text یا اجرای query از Node راه معتبر برای پرکردن جزئیات Runtime نیست.

### نتیجهٔ Traceability

این موارد در این revision بررسی و تعیین تکلیف شده‌اند: Test JVM منبع تولید Runtime است؛ artifact ساخت‌یافته و run-scoped زیر build output استفاده می‌شود؛ UUID پیش از اجرای Gradle ساخته و به Test منتقل می‌شود؛ شکست/partial artifact status مستقل دارد؛ snapshot فقط به دادهٔ قابل‌مشاهدهٔ Test محدود است؛ و Context/Workflow با schema v2 و loader سخت‌گیرانه اعتبارسنجی می‌شود. جزئیات در بخش 17 آمده است.

### Freshness invariants

* قبل از شروع Gradle، artifact Runtime قبلی همان Test باید از مسیر validated پاک یا از طریق run identity قابل رد باشد.
* شکست preparation باید مانع شروع Gradle شود و Runtime قبلی را جاری جلوه ندهد.
* artifact فقط در صورت parse/validation موفق، containment تأییدشده و تعلق به run جاری `available` است.
* اگر تست شکست بخورد ولی Runtime artifact تازه و معتبر موجود باشد، آن artifact نمایش داده می‌شود.
* Runtime ناموجود/ناقص با موفقیت یا failure Test یکی نیست.
* HTML report freshness و Runtime freshness مستقل هستند.

## 7. Refresh و Collision: قرارداد نمایش

* تنها مقدار refresh همان `migration.test.db.refresh` فعلی است؛ Plan رفتار اجرایی آن را عوض نمی‌کند.
* Context مقدار پیش‌فرض تعریف‌شده در `help.json` را نمایش می‌دهد، اما Runtime مقدار effective property دریافتی Test را ثبت می‌کند.
* `refresh=true`: Test source پیش از Migration lifecycle، user tableهای catalog انتخاب‌شده را مشاهده و پاک می‌کند؛ `system_migration` نیز در محدودهٔ فعلی refresh است. هیچ database-level `DROP/CREATE` نداریم.
* `refresh=false`: Test چیزی را به‌خاطر refresh حذف نمی‌کند؛ collision guard ممکن است پیش از Migrator متوقف شود.
* refresh failure: setup شکست می‌خورد، Migrator شروع نمی‌شود و گام‌های بعدی `not_executed` می‌شوند.
* پس از Test cleanup دیتابیسی انجام نمی‌شود؛ state موفق یا نیمه‌تمام برای inspection باقی می‌ماند.
* UI نباید ادعا کند فقط fixture tableها حذف شده‌اند؛ آن توصیف با رفتار فعلی `refreshAllTables` سازگار نیست.
* Runtime باید distinction بین «refresh انتخاب شد»، «refresh واقعاً اجرا شد»، «refresh کامل شد» و «refresh اجرا نشد» را نگه دارد.

## 8. خطا و Failure Semantics

* Gradle/JUnit outcome از runtime step outcome جداست.
* Runtime stepهای قبل از نقطهٔ توقف می‌توانند `succeeded` باشند؛ مرحلهٔ واقعی شکست `failed` و مراحل بعد `not_executed` هستند.
* اگر Test قبل از تولید runtime artifact fail کند، Runtime status `unavailable` یا `incomplete` است و Help از متن failure workflow جعلی نمی‌سازد.
* خطای parse، schema mismatch یا run ID mismatch به `invalid/unavailable` منجر می‌شود؛ دادهٔ ناقص به‌صورت موفقیت تفسیر نمی‌شود.
* اگر Report HTML تازه وجود نداشته باشد، این موضوع Runtime availability را تعیین نمی‌کند.
* JUnit failures و stack/message فعلی حفظ شوند؛ Runtime summary جای گزارش Gradle را نمی‌گیرد.

## 9. امنیت و حریم داده

* فقط loopback Help API فعلی و مسیر containment موجود حفظ شود.
* Runtime payload از فایل/path خارج از Project root خوانده نشود؛ symlink containment باید بررسی شود.
* Password، database credential، connection string کامل و مقدار secret هرگز در Runtime report، result API، UI، HTML context یا AI Markdown handoff قرار نگیرد.
* برای عیب‌یابی فقط metadata صریحاً مجاز (مانند نام Test، شناسهٔ run، dialect اعلام‌شده، dbName در صورت تصمیم) ثبت شود؛ credentialها از environment/JVM property دوباره serialize نشوند.
* Context یک فایل declarative تحت کنترل repository است، نه executable code؛ schema آن باید strict validate شود.
* Failure message و stringهای database با `textContent`/encoding امن نمایش داده شوند؛ HTML runtime دلخواه اجرا یا embed نشود.

## 17. Traceability Revision و Final Contract

این بخش اصلاحیهٔ نهایی Plan است و تصمیم‌های قبلیِ «Candidate» یا «Unresolved» را در مواردی که اینجا تعیین تکلیف شده‌اند جایگزین می‌کند. Plan همچنان فقط contract است و هیچ implementation در این مرحله انجام نشده است.

### 17.1 Runtime Transport Decision

#### Evidence

* `/api/runs` در `help/src/server.mjs` پیش از اجرای Test، run identifier نمی‌سازد؛ `sessionKey` فقط ترکیب Project و Test است.
* `reportToken` در `help/src/gradle-test-runner.mjs` پس از پایان Gradle و فقط در صورت وجود report ساخته می‌شود؛ بنابراین Test JVM نمی‌تواند آن را به‌عنوان شناسهٔ artifact استفاده کند.
* Gradle runner فعلی `ORG_GRADLE_PROJECT_*` را برای propertyهای تعریف‌شده به child process می‌دهد.
* `data_base/migration/build.gradle.kts` propertyهای allow-listed را از Gradle project به JVM Test از طریق `tasks.test { systemProperty(...) }` منتقل می‌کند.
* stdout/stderr child Gradle در `runChild` نادیده گرفته می‌شود؛ structured stdout marker مستلزم تغییر process capture و Gradle/Test logging است.
* JUnit XML و Gradle HTML در حال حاضر آمار، failure و report را می‌دهند؛ phase، migration state یا schema diff قراردادی ندارند.
* Test source خودش با JDBC metadata و history را می‌خواند، پس Test JVM مرجع مشاهدهٔ state است.

#### Candidate comparison

| Candidate | Producer / Consumer | Freshness و run identity | Security / containment | سازگاری و تغییر لازم | تصمیم |
|---|---|---|---|---|---|
| A. #### Decision

کمینهٔ معتبر در معماری فعلی یک **Test-generated structured JSON artifact** در مسیر موقت زیر `Project root/build/reports/help/runtime/` است. Help آن را پیش از Gradle آماده و پس از اجرا parse می‌کند. API همان payload اعتبارسنجی‌شده را به Test View می‌دهد. Test JVM تنها producer واقعیت‌های Test است؛ Help runner مسئول اجرای فرایند، freshness، path validation و انتقال است.

Artifact در پایان read/validation مصرف می‌شود و فایل موقت پاک می‌شود. پاک‌سازی artifact اگر شکست بخورد نباید نتیجهٔ Migration Test یا Runtime payload parse‌شده را تغییر دهد؛ خطا فقط diagnostic محلی Help است. این cleanup مربوط به فایل report است و هیچ database cleanup انجام نمی‌دهد.

### 17.2 Run Identity و Path Ownership

#### Evidence

* Browser `startedAt` زمان است، run identity نیست و به Test JVM منتقل نمی‌شود.
* `sessionKey` فعلی Project/Test را گروه‌بندی می‌کند؛ برای اجرای منفرد یکتا نیست.
* `reportToken` بعد از Gradle ساخته می‌شود و برای Test JVM قابل استفاده نیست.

#### Decision

Help runner پیش از اجرای Gradle یک UUID می‌سازد. همان `runId` و یک `runtimePath` یکتا، فقط از طریق propertyهای داخلی Help به Test JVM می‌رسند. این propertyها UI input نیستند و از request کاربر پذیرفته نمی‌شوند.

Test-side writer باید پیش از بازکردن فایل:

1. `runId` را به‌عنوان UUID معتبر parse کند.
2. `runtimePath` را normalize و canonicalize کند.
3. بررسی کند مسیر فقط زیر runtime root مجاز همان Gradle Project قرار دارد، segment تست با Test ID ثابت همان integration test مطابق است و نام فایل با `runId` جاری منطبق است.
4. فقط به همان مقصدی بنویسد که Help برای همین execution داده است؛ path را از ورودی دیگری نسازد، به run دیگر تغییر ندهد و به مسیر خارج از root redirect نکند.

Help پس از اجرا نیز containment، Test ID و runId داخل artifact را با execution مورد انتظار تطبیق می‌دهد. هر mismatch به `runtimeStatus = invalid` و عدم نمایش payload منجر می‌شود.

`reportToken` همچنان فقط برای دسترسی به HTML report است؛ ownership و runtime artifact identity را بر عهده نمی‌گیرد.

### 17.3 Freshness Contract

```text
Create runId + unique runtimePath
    ↓
Validate/prepare exact destination under Project build output
    ↓
Pass runId + runtimePath to Test JVM
    ↓
Test publishes complete checkpoints
    ↓
Help validates path, schema and run ownership
    ↓
API response holds the parsed Runtime for this run
    ↓
Remove only the temporary artifact for this run
```

* مقصد برای هر run یکتا است؛ artifact اجرای قبلی با مسیر ثابت reuse نمی‌شود.
* **Preferred:** checkpoint با temporary sibling و atomic replacement به همان `runtimePath` منتشر شود.
* اگر atomic replacement در filesystem موجود پشتیبانی نشود، direct overwrite یا روش دیگری که فایل نیمه‌نوشته را قابل‌خواندن کند ممنوع است. fallback امن می‌تواند publication را متوقف کند؛ در این حالت Test outcome تغییر نمی‌کند و Runtime `unavailable/incomplete` می‌شود.
* فایل staging فقط در صورت containment و promotion امن پذیرفته می‌شود؛ Help هیچ‌وقت staging یا JSON ناقص را parse نمی‌کند.
* بعد از crash، آخرین checkpoint کامل و معتبر همان run قابل نمایش است و `runtimeStatus = incomplete` خواهد بود. گامی که صریحاً شروع شده ولی completion checkpoint ندارد `in_progress` می‌ماند.
* failure قبل از Gradle یا پیش از اولین checkpoint: Runtime `unavailable`؛ Gradle preparation failure طبق رفتار موجود process را شروع نمی‌کند.
* خطای runtime writer نباید failure اصلی Test را بپوشاند یا Migration/JUnit result را تغییر دهد. اگر checkpoint معتبر قبلی هست همان incomplete می‌ماند؛ در غیر این صورت Runtime unavailable است.
* Help پس از parse/validation، فقط artifact همان run را پاک می‌کند. این cleanup فایل report است و database state را تغییر نمی‌دهد.
* HTML report freshness و Runtime freshness مستقل‌اند.

### 17.4 Test Ordering Contract

#### Evidence

* `help.json` دو Test ID و دو JUnit filter جدا تعریف می‌کند؛ `/api/runs` در هر invocation فقط یک Test ID/filter را به Gradle می‌فرستد.
* `MigrationSystemIntegrationTest` و `MigrationSchemaIntegrationTest` از Help به‌صورت مستقل قابل اجرا هستند.
* هیچ JUnit method/class order، Gradle test ordering، parallel policy یا cross-Test fixture lifecycle در build/test config پیدا نشد.
* هر Integration Test خودش refresh/collision path دارد. Refresh defaultهای Help برای دو Test متفاوت‌اند؛ مقدار مؤثر از property همان execution می‌آید.

#### Decision

**Standalone execution supported; cross-Test sequential workflow is not part of v3.0.** هیچ‌کدام از Testها نباید به اجرای Test دیگر یا ترتیب تصادفی JUnit/Gradle اتکا کند. هر Test باید با Database state و refresh parameter خودش نتیجهٔ قابل‌تفسیر داشته باشد.

وقتی `refresh=false` و collision موجود است، Integration method ممکن است collision contract را assert کرده و بدون شروع `MigrationMigrator` برگردد؛ JUnit `Passed` در این branch به معنی اجرای schema/migration lifecycle نیست. Runtime View باید مسیر collision را موفق، و مراحل Migration را `not_executed` نشان دهد.

### 17.5 Standalone vs Sequential Execution

* هر دو Test **standalone** هستند؛ registration، expected history و schema assertions در خود Test تعریف می‌شوند.
* v3.0 هیچ حالت Sequential، chain بین دو Test، dependency ordering یا data handoff بین آن‌ها اضافه نمی‌کند.
* برای standalone run، مقدار refresh همان ورودی مؤثر Test است؛ اگر refresh خاموش و collision وجود داشته باشد، نتیجهٔ مورد انتظار ممکن است «collision guard verified; migration lifecycle not executed» باشد.
* اجرای چند Test متوالی از UI در این نسخه پشتیبانی نمی‌شود. اگر در آینده لازم شد، باید Plan جداگانه برای ordered test workflow تهیه شود.

### 17.6 Final Context Contract

هر Test دارای Runtime payload، در Test Definition نسخهٔ 2 descriptor زیر را دارد:

```json
"runtime": { "type": "test-runtime-json", "schemaVersion": 1 }
```

این descriptor نوع payload را اعلام می‌کند؛ `runtimePath` و `runId` را Help برای هر invocation می‌سازد و از `help.json` یا UI نمی‌گیرد.

`help.json` Test Definition به Context declarative با فیلدهای محدود زیر گسترش می‌یابد:

```json
{
  "purpose": "...",
  "scenario": "...",
  "preconditions": ["..."],
  "expectedWorkflow": [{ "id": "...", "label": "..." }],
  "expectedMigrations": [
    { "id": "...", "order": 1, "group": "...", "operationType": "...", "target": "..." }
  ],
  "verificationCategories": ["schema", "history"],
  "runtime": { "type": "test-runtime-json", "schemaVersion": 1 }
}
```

* `Context = Expected`; `Runtime = Observed`. Runtime **هرگز Context را mutate یا reinterpret نمی‌کند** و expected workflow را صرفاً به‌علت اجرای یک مسیر، به actual workflow تبدیل نمی‌کند.
* فیلدهای `expected*` در View با برچسب Expected نمایش داده می‌شوند؛ مشاهده‌ها جداگانه و با provenance می‌آیند.
* Context سناریو و مفاهیم قابل‌فهم Developer را پوشش می‌دهد؛ private helper، variable، خط assertion یا جزئیات JDBC را mirror نمی‌کند.
* Test System Context سناریوهای موفقیت، rerun، failure/resume، zero/multiple-operation و refresh/collision را در سطح مفهومی معرفی می‌کند.
* Test Schema Context schema رابطه‌ای، هفت migration و دسته‌های verification را معرفی می‌کند؛ ادعاهای جزئی‌تر فقط وقتی وارد Context می‌شوند که contract/test آن‌ها را تعریف کرده باشد.
* توضیح refresh باید با رفتار واقعی `refreshAllTables`: حذف user tableهای catalog انتخاب‌شده، از جمله `system_migration`، در ابتدای Test سازگار باشد؛ تعبیر «فقط fixtureها» ممنوع است.

#### Versioning

`help/src/help-file-loader.mjs` فیلد `schemaVersion` را در root definition و همراه `module` و `tests` می‌خواند؛ بنابراین این مقدار نسخهٔ کل Help Definition document است، نه version یک family از Testها. Loader فعلی فقط root `schemaVersion: 1` و فیلدهای allow-list همان سند را می‌پذیرد.

تصمیم: چون Context/Workflow/Runtime descriptor ساختار رسمی همان Help Definition document را گسترش می‌دهند، `data_base/migration/help.json` به schema version 2 می‌رود. Loader همچنان schema v1های موجود را بدون تغییر می‌پذیرد و برای v2 نیز فیلدهای مجاز را strict validate می‌کند. Version داخلی جدا برای Context ایجاد نمی‌شود؛ در حال حاضر هیچ family مستقل یا مصرف‌کننده‌ای که versioning جداگانه را توجیه کند در Repository وجود ندارد.

### 17.7 Final Workflow Contract

* Workflow ثابت هر Test از Context Definition می‌آید و order آن ترتیب مورد انتظار را بیان می‌کند.
* Runtime eventها همان step IDهای تعریف‌شده را ارجاع می‌دهند؛ ID ناشناخته معتبر نیست.
* Runtime step شامل `id`, `order`, `status`, زمان/duration فقط در صورت اندازه‌گیری معتبر، و `data` محدود به schema است. `label` از Context resolve می‌شود و Runtime نمی‌تواند آن را بازنویسی کند.
* statusهای مجاز و معنای قطعی:
  * `not_started`: آخرین checkpoint معتبر نشان می‌دهد اجرا هنوز به این مرحله نرسیده است؛ به‌تنهایی ثابت نمی‌کند مرحله در نهایت skip شده.
  * `in_progress`: Test صریحاً شروع مرحله را ثبت کرده ولی checkpoint تکمیل ندارد.
  * `succeeded`: Test تکمیل موفق مرحله را با evidence مرتبط ثبت کرده است.
  * `failed`: failure واقعی به همین مرحله نسبت داده شده است.
  * `not_executed`: branch یا termination point به‌طور قطعی ثابت می‌کند این مرحله اجرا نخواهد شد/نشده است.
  * `not_collected`: برای این مرحله evidence معتبر جمع‌آوری نشده؛ نبود event به‌تنهایی `not_executed` نیست.
* در crash میان checkpointها، مرحلهٔ بعدی `not_started` یا `not_collected` می‌ماند، نه `not_executed`؛ `not_executed` فقط با branch/termination اثبات‌شده صادر می‌شود.
* Help وضعیت را از ترتیب تعریف یا نبود event حدس نمی‌زند.
* `MigrationSchemaIntegrationTest` و `MigrationSystemIntegrationTest` workflow definition جدا دارند.

### 17.8 Final Runtime Contract

Runtime artifact نسخهٔ 1 شامل envelope زیر است:

```text
schemaVersion, projectPath, testId, runId,
startedAt, completedAt?, runtimeStatus,
steps[], migrations[], schemaVerification?, historyVerification?, finalState?
```

`runtimeStatus`: `complete`, `incomplete`, `unavailable` یا `invalid`.

هر Migration runtime item، در صورت جمع‌آوری، execution و persistence را مستقل نگه می‌دارد:

```json
{
  "migrationId": "create_users",
  "registrationOrder": 1,
  "operationType": { "value": "CREATE TABLE", "provenance": "declared" },
  "target": { "value": "users", "provenance": "declared" },
  "executionStatus": "succeeded",
  "historyStatus": "recorded",
  "batch": 1
}
```

* `executionStatus`: `succeeded`, `failed`, `not_executed` یا `unknown`.
* `historyStatus`: `recorded`, `not_recorded`, `recording_failed`, `not_applicable` یا `unknown`.
* داشتن history row معتبر اثبات می‌کند identity ثبت شده است؛ طبق v1.20 ordering که record پس از اجرای موفق انجام می‌شود، می‌تواند موفقیت operation را نیز پشتیبانی کند.
* نبود history row به‌تنهایی ثابت نمی‌کند operation شکست خورده است: اگر Test failure را به operation مشخص نسبت دهد، `executionStatus = failed`; اگر branch ثابت کند Migration شروع نشده، `not_executed`; در سایر حالت‌های مبهم `unknown` است. `historyStatus = not_recorded` فقط وقتی history همان اجرا واقعاً خوانده شده باشد ثبت می‌شود.
* `recording_failed` فقط با evidence مستقیم از failure مرحلهٔ ثبت ثبت می‌شود. اگر execution موفق و history ناموجود باشد ولی مرحلهٔ ثبت جداگانه قابل مشاهده نباشد، execution/history به‌صورت مستقل گزارش می‌شوند و علت recording به‌عنوان unknown باقی می‌ماند؛ کل Migration بی‌توضیح `succeeded` نمی‌شود.
* operation type و target با provenance `declared` از قرارداد Test/Context می‌آیند. فقط داده‌ای که از همان `MigrationDefinition` اجرای واقعی capture شده باشد می‌تواند `observed` شود؛ نام کلاس، حدس از SQL یا expected context به‌تنهایی observation نیست.
* `schemaVerification` فقط فیلدهایی را capture می‌کند که Test فعلی واقعاً مشاهده و assert می‌کند. برای Schema Test این شامل table/column و type mapping، nullability/auto-increment در موارد assertionشده، primary keyها، نام/ستون/uniqueness indexها، و endpoint/order مربوط به foreign keyها است.
* Test فعلی index method یا FULLTEXT type را به‌طور دقیق verify نمی‌کند؛ این موارد Runtime به‌عنوان verified report نمی‌شوند. Foreign key action نیز فقط طبق assertion فعلیِ پذیرش ruleهای `NO ACTION`/`RESTRICT` خلاصه می‌شود؛ Runtime ادعای verify یک action مشخص را نمی‌کند.
* `expected`, `actual`, `difference` فقط برای assertionهای واقعی نگهداری می‌شوند؛ `actual` از JDBC observation همان run و `expected` از Context/Test contract می‌آید.
* `historyVerification` شامل IDها، ترتیب و batchهای واقعاً خوانده/assertشده است؛ batch 1 به Test دیگری تعمیم داده نمی‌شود.
* `finalState` به objectهای موردنیاز سناریو و `system_migration` محدود است؛ هیچ dump کامل DB، `DatabaseMetaData`, `ResultSet`, SQL log یا نام جدول نامرتبط در payload پیش‌فرض قرار نمی‌گیرد.
* secret، credential، JDBC URL کامل، environment variable و raw JDBC property serialize نمی‌شوند.

### 17.9 Final Test View Contract

پاسخ `/api/runs` برای invocation جاری `runId`, `runtimeStatus`, `runtime` و وضعیت‌های مستقل `executionStatus`/`historyStatus` برای هر Migration را در کنار فیلدهای outcome فعلی برمی‌گرداند. Result View چهار بخش مستقل نشان می‌دهد:

1. **Context**: هدف، پیش‌شرط و مسیر مورد انتظار.
2. **Observed workflow**: timeline واقعی با وضعیت‌های بالا؛ failure مرحله و مراحل اجرا‌نشده قابل تشخیص‌اند.
3. **Expected vs Actual**: schema/history مواردی که Test مشاهده کرده، به همراه difference؛ دادهٔ ناموجود `not_collected` است.
4. **Gradle result & reports**: Passed/Failed، JUnit metrics/failures و HTML Report فعلی.

* Passed/Failed از Gradle/JUnit می‌آید و با Runtime status ادغام نمی‌شود.
* HTML Report availability مستقل از Runtime availability باقی می‌ماند.
* Test View renderer است و DB query، SQL parsing یا workflow inference نمی‌کند.
* حالت `refresh=false + collision` صریحاً می‌گوید guard با موفقیت بررسی شد ولی migration workflow اجرا نشد.
* AI Markdown handoff شامل Test identity، ورودی‌های غیرمحرمانه، Context، Gradle result، Runtime summary/diff و limitation است؛ secretها و credentialها حذف می‌شوند.

### 17.11 Acceptance Criteria

* Context static و Runtime observed با label و source مشخص از هم جدا باشند.
* runtime transport همان runId را از Help process تا Test artifact و API response حفظ کند.
* artifact run-scoped، atomic، path-contained و stale-proof باشد.
* Gradle result، HTML report freshness و Runtime status تماماً مستقل باشند.
* failure stage، موفقیت‌های قبل از آن و `not_executed`/`not_collected` بعدی بدون حدس نمایش داده شوند.
* expected/actual/difference فقط از Context و observations واقعی Test ساخته شوند.
* System و Schema Test standalone باشند؛ order یا state مشترک بینشان فرض نشود.
* refresh explanation با database-wide refresh واقعی هماهنگ باشد؛ refresh در این مرحله تغییر semantic نکند.
* دو Test فقط metadata و Runtime fieldهای لازم خودشان را گزارش کنند؛ هیچ full DB/JDBC dump نباشد.
* definitionهای Help schema v1 همچنان load شوند و v2 با allow-list strict اعتبارسنجی شود.
* AI handoff هیچ credential یا secret نداشته باشد.
* فقط test-side instrumentation افزوده شود؛ Migration production pipeline و API دست‌نخورده بماند.
