# Test Tool - Plan 1.1 (Superseded)

## Status

`Superseded by Help - Plan 2.0; do not use as the current implementation contract.`

This file is retained as the historical Plan 1.1 baseline. The active architecture and implementation contract is [Help - Plan 2.0](v2.0-help-test-module.md).

این سند Contract و plan نسخهٔ 1.1 ابزار گرافیکی داخلی اجرای Test است. Traceability مخزن انجام شده است. Implementation این ابزار در این مرحله انجام نمی‌شود.

## Objective

یک mini-project داخلی برای Developer Tooling بسازیم تا توسعه‌دهنده بتواند Integration Test موجود `MigrationSystemIntegrationTest` را با configuration گرافیکی اجرا کند و نتیجهٔ HTML خود Gradle را در همان صفحه ببیند.

اجرای Test و semantics آن همچنان متعلق به Gradle و Kotlin/JUnit است. Node فقط process را هماهنگ می‌کند، وضعیت اجرا را نگه می‌دارد و static files و report موجود را از HTTP ارائه می‌دهد.

### External Gradle Reference

Gradle User Manual دربارهٔ Build Environment توضیح می‌دهد که project property می‌تواند از `ORG_GRADLE_PROJECT_<name>` در environment دریافت شود و آن را برای secretهای buildهای unattended ترجیح می‌دهد؛ `providers.gradleProperty()` نیز این ورودی را resolve می‌کند. API مربوط به `Test.systemProperty(...)` مقدار را به process تست می‌فرستد. در implementation باید این مسیر با Wrapper همین repository (`Gradle 8.14`) و propertyهای دارای نقطه در نام، با یک JVM-level smoke test تأیید شود. این سند نسخهٔ مستندات عمومی را جایگزین verification روی Wrapper پروژه نمی‌کند.

## Existing Test Architecture

### Evidence

* `settings.gradle.kts`، `:data_base:migration` را در Gradle build ثبت می‌کند.
* `data_base/migration/build.gradle.kts` task تست را با JUnit Platform پیکربندی می‌کند.

* Gradle Wrapper در root قرار دارد و project-level test task، Test JVM را اجرا می‌کند.

### Interpretation

Test Tool باید Test task فعلی را invoke کند؛ Test logic، filtering semantics، assertions، database lifecycle و exit result همچنان در Gradle/JUnit/Test باقی می‌مانند.

### Decision

MVP فقط `MigrationSystemIntegrationTest.runsTheMigrationSubsystemLifecycleAgainstMySql` را اجرا می‌کند. هر توسعهٔ بعدی برای انتخاب چند Test باید configuration-driven باشد، اما در v1.1 test discovery عمومی ساخته نمی‌شود.

### Evidence

## Existing Integration Test Contract

### Configuration

| JVM property | UI control | Contract |
|---|---|---|
| `migration.test.db.domain` | Database Domain / JDBC Prefix | اجباری؛ باید با `jdbc:mysql://` شروع شود. |
| `migration.test.db.port` | Database Port | اجباری؛ عدد صحیح بین 1 و 65535. |
| `migration.test.db.name` | Database Name | اجباری و non-blank؛ تنها Database هدف Test است. |
| `migration.test.db.username` | Database Username | اجباری و non-blank. |
| `migration.test.db.password` | Database Password | property باید منتقل شود؛ مقدار خالی به‌عنوان password خالی مجاز است. UI مقدار را mask می‌کند. |
| `migration.test.db.refresh` | Refresh Database | `true` یا `false`؛ default `false`. |

### Refresh and Safety

`refresh=false` یعنی Test از database انتخاب‌شده استفاده می‌کند و collision با owned object باعث failure می‌شود. `refresh=true` به Test اجازه می‌دهد پیش از lifecycle، `ownedFixtureTables + system_migration` را با مسیر موجود حذف کند. این گزینه `DROP DATABASE`، `CREATE DATABASE` یا پاک‌کردن tableهای نامرتبط را انجام نمی‌دهد.

Tool database connection باز نمی‌کند، SQL اجرا نمی‌کند، migration object را نمی‌شناسد و هیچ database objectی را مستقیماً دست‌کاری نمی‌کند. Warning کنار checkbox باید دقیقاً محدود بودن refresh را توضیح دهد و اعلام کند که lifecycle در Test اجرا می‌شود.

## Proposed Tool Architecture

### Evidence

Repository دارای ماژول `tools` است، ولی در آن HTTP server، browser UI یا Node application وجود ندارد. `settings.gradle.kts` module دیگری برای developer tool ثبت نکرده است.

### Interpretation

برای یک UI تک‌صفحه‌ای و orchestration کوچک، framework، frontend bundler و Gradle plugin جدید لازم بودنشان از evidence فعلی ثابت نمی‌شود.

### Decision

MVP به‌صورت یک mini-project Node مستقل در `tools/test-tool/` ساخته می‌شود؛ این directory زیرمجموعهٔ `:tools` Gradle project path است ولی build/test target خودش ندارد و `settings.gradle.kts` تغییر نمی‌کند.

* Server: Node built-in HTTP و `child_process`.
* UI: static HTML/CSS/JavaScript، بدون frontend framework.
* State: فقط یک run فعال و metadata همان run در حافظه؛ بدون history یا persistence.
* Binding: فقط loopback (`127.0.0.1`).
* Server، DB credentials را در فایل، URL، browser storage یا log نگه نمی‌دارد.

مقدارها پس از refresh صفحه نگه‌داری نمی‌شوند. UI نام Test، Gradle task، working directory یا shell command آزاد از کاربر نمی‌گیرد.

## Node Orchestration Contract

### Run Request

`POST /api/test/run` configuration را دریافت و validate می‌کند. Server یک Run ID می‌سازد، process را asynchronous شروع می‌کند و فوراً Run ID و `running` را برمی‌گرداند. اگر run فعال دیگری وجود داشته باشد، درخواست دوم با پاسخ conflict رد می‌شود؛ queue و parallel Test نداریم.

### Status

`GET /api/test/status/:id` وضعیت `running | passed | failed`، exit code در صورت پایان، diagnostics محدودشده و وجود/عدم وجود report را می‌دهد. Run ID ناشناخته خطای Not Found می‌دهد. بعد از restart شدن Node، runهای قبلی بازیابی نمی‌شوند.

### Process

* process با `child_process.spawn` اجرا شود؛ از `execSync` و هر روش blocking استفاده نشود.
* working directory root repository است.
* Gradle Wrapper موجود اجرا شود و task/filter ثابت باشند؛ ورودی UI به command تبدیل نشود.
* Tool فقط یک test method مشخص را به task موجود می‌فرستد.
* stdout/stderr برای diagnostics خوانده می‌شود، اما secretها redact می‌شوند و diagnostics روی disk نوشته نمی‌شود.
* exit code صفر یعنی `Passed`؛ exit code غیرصفر، spawn error یا signal failure یعنی `Failed`.

### Gradle Property Transport

برای اینکه password در process command line ظاهر نشود، Plan مسیر environment-backed Gradle project properties را adopt می‌کند:

```text
Node child environment
  ORG_GRADLE_PROJECT_migration.test.db.domain
  ORG_GRADLE_PROJECT_migration.test.db.port
  ORG_GRADLE_PROJECT_migration.test.db.name
  ORG_GRADLE_PROJECT_migration.test.db.username
  ORG_GRADLE_PROJECT_migration.test.db.password
  ORG_GRADLE_PROJECT_migration.test.db.refresh
       ↓
Gradle providers.gradleProperty(...)
       ↓
Test.systemProperty(...)
       ↓
MigrationSystemIntegrationTest System.getProperty(...)
```

Tool باید `refresh` را همیشه به‌شکل `true` یا `false` منتقل کند تا default UI و Test همسان باشد. Propertyها یا password به `-P` command-line argument تبدیل نمی‌شوند. Verification روی Gradle 8.14 باید ثابت کند environment keyهای dotted-name به‌درستی resolve می‌شوند و property در Test JVM می‌رسد؛ اگر این smoke test شکست خورد، Implementation متوقف و Plan با evidence اصلاح شود، نه اینکه secret به argv یا فایل دائمی منتقل شود.

* Node آن directory را read-only از HTTP روی همان loopback server ارائه می‌دهد.

## iframe Contract

بعد از اتمام Gradle process، UI با `iframe.src` همان report از مسیر HTTP را بارگذاری می‌کند. صفحهٔ اصلی باقی می‌ماند و reload نمی‌شود. اگر Test شکست خورده ولی Gradle report موجود است، report failure همان‌طور نمایش داده می‌شود. اگر report موجود نیست، UI diagnostics را حفظ می‌کند و پیام نبود report می‌دهد.

## Async Execution

```text
POST /api/test/run
  ├── validate input
  ├── spawn fixed Gradle Wrapper task
  └── return runId

GET /api/test/status/:id
  └── running / passed / failed

GET /reports/...
  └── Gradle HTML report static files
```

MVP از polling استفاده می‌کند. WebSocket، queue، retry و execution concurrency اضافه نمی‌شوند. HTTP server در طول Gradle process پاسخ‌گو باقی می‌ماند.

## Error Handling

* ورودی نامعتبر: درخواست رد شود و Gradle شروع نشود.
* run فعال: run دوم رد شود؛ اولین process ادامه پیدا کند.
* spawn/Wrapper/JDK failure: وضعیت `Failed` و diagnostics قابل مشاهده.
* Gradle exit غیرصفر: وضعیت `Failed`؛ در صورت وجود report، نمایش داده شود.
* refresh failure یا DB error: failure همان Test Gradle است؛ Tool retry یا fallback نمی‌کند.
* report مفقود: execution status حفظ می‌شود و فقط نمایش report unavailable است.
* password نباید در response status، URL، stdout/stderr UI، log یا فایل ماندگار شود.

## Safety

* فقط یک endpoint محلی برای شروع Test وجود دارد؛ server روی `127.0.0.1` bind می‌شود.
* درخواست mutation از browser باید Origin/Host مجاز و JSON content type مورد انتظار را داشته باشد تا صفحهٔ دیگری نتواند بی‌صدا Test refreshدار را trigger کند. Authentication و user management ساخته نمی‌شود.
* فقط task و test filter ثابت مجاز است؛ arbitrary process execution وجود ندارد.
* Refresh یک opt-in روشن و default آن false است. UI پیش از اجرا می‌گوید Integration Test فقط owned fixture tables و `system_migration` را refresh می‌کند.
* Tool خودش به database وصل نمی‌شود و lifecycle را اجرا نمی‌کند؛ اجرای DB فقط از مسیر Test فعلی است.
* Database values در حافظهٔ process باقی می‌مانند و بعد از اتمام run قابل query مجدد نیستند؛ password persistent storage ندارد.

## Scope

* Node orchestration server محلی.
* یک صفحهٔ configuration برای `MigrationSystemIntegrationTest`.
* validation و انتقال propertyهای موجود.
* اجرای یک Gradle test filter ثابت و نمایش وضعیت.
* HTTP serving برای HTML Test Report موجود Gradle.

* تست‌های محدود خود orchestration و safety boundary.

* Test Framework یا Test Runner جدید.
* JUnit replacement یا تغییر Test semantics.
* Test discovery یا انتخاب arbitrary test/task.
* ساخت یا تغییر Gradle HTML Report.
* Database provisioning، Docker orchestration یا اجرای مستقیم SQL.
* Test history، persistence از runها یا analytics.
* WebSocket، queue، parallel run، retry و scheduling.
* Authentication، user management و distributed execution.
* CI/CD integration.
* تغییر Migration API، `DatabaseConfig`، Integration Test behavior یا production code.
* افزودن ماژول Node به `settings.gradle.kts`.
