# پلن نسخهٔ 5.0: API نتیجهٔ Typed CTE و استخراج Collection

## وضعیت سند و مرز این مرحله

- وضعیت: Phaseهای 1 تا 4 پیاده‌سازی و اعتبارسنجی شده‌اند؛ جزئیات و محدودیت‌های اعتبارسنجی در همین سند ثبت شده است.
- تاریخ تهیهٔ پلن: 2026-10-26؛ آخرین ثبت وضعیت Phase 4: 2026-10-27.
- دامنهٔ این سند: callbackهای `success` و `error` پیرامون اجرای typed CTE و استخراج مستقیم `ICollection<T>` از نتیجه.
- نسخهٔ 5.0 باید بر API فعلی typed CTE در V4.0 بنا شود؛ مسیر اجرای خام `QueryConsumer.execute()`، mapper، قراردادهای CTE، SQL، metadata و مدیریت منابع را بازطراحی نمی‌کند.

## وضعیت نهایی پیاده‌سازی و اعتبارسنجی

Phaseهای 1 تا 4 تکمیل شده‌اند. قراردادهای تثبیت‌شده عبارت‌اند از:

- `CteDeclaration.execute(queryManager, params)` اجرای typed را با خروجی `ExecuteResult<ICollection<Self>>` انجام می‌دهد. مسیر آن `queryReady → configureConsumer → executeAs(::fromQueryRow)` است و mapping هر ردیف از mapper موجود عبور می‌کند.
- `QueryConsumer.execute()` مسیر اجرای خام را با خروجی `ExecuteResult<List<QueryRow>>` حفظ می‌کند؛ این مسیر با materialization تایپ‌شدهٔ `executeAs()` متفاوت است. `CteDeclaration` متد `executeRows()` ندارد.
- mapper موجود در `data_base/query/cte/src/main/kotlin/mapper/CteQueryRowMapper.kt` metadata مربوط به `@QBQuerySelect` و alias منتشرشدهٔ SQL را برای mapping به‌کار می‌برد، descriptorها را برای کلاس cache می‌کند و برای هر ردیف نمونهٔ تازه‌ای با سازندهٔ بدون پارامتر می‌سازد. property مقصد باید setter قابل‌استفاده برای mapping داشته باشد. نوع‌های تبدیل‌شدهٔ فعلی `Int`, `Long` و `String` هستند؛ تبدیل ضمنی نوع انجام نمی‌شود و `NULL` فقط برای property nullable پذیرفته می‌شود. این محدودیت‌ها متعلق به mapper موجودند و در V5.0 گسترش نیافته‌اند.
- `success` و `error` همان قرارداد همگام موجود را دارند: callback موفقیت برای payload غیرnull اجرا می‌شود و نتیجهٔ آن را در `Success` می‌گذارد؛ callback خطا همان `Throwable` را می‌بیند و نتیجهٔ Failure را حفظ می‌کند. خطای پرتاب‌شده از خود callback به Failure تبدیل نمی‌شود.
- `ExecuteResult<ICollection<T>>.toCollection()` در `data_base/query/executor/src/main/kotlin/result/ExecuteResultCollectionExtensions.kt`، همان instance را برای Success غیرnull برمی‌گرداند؛ Failure همان `Throwable` را بدون wrapper پرتاب می‌کند؛ و `Success(null)` را با `IllegalStateException("Successful result contains no collection")` رد می‌کند. Collection خالی واقعی معتبر است و به Collection دیگری تبدیل نمی‌شود.

سه الگوی استفاده در مثال‌های V3.1 ثبت شده‌اند:

1. زنجیرهٔ callback داخل override در `data_base/query/example/src/main/kotlin/v3_1/queries/relations/UserDisplayQueryV31.kt`؛ callbackها روی نتیجهٔ یک `super.execute()` اجرا می‌شوند و تنظیم‌های SQL و metadata از `configureConsumer()` حفظ می‌شوند.
2. زنجیرهٔ callback در محل فراخوانی در `data_base/query/example/src/main/kotlin/v3_1/queries/execute/CteExecutionExampleV31.kt` که توسط `data_base/query/example/src/main/kotlin/managers/ManagerExampleV31.kt` اجرا می‌شود.
3. استخراج با `.toCollection()` و پیمایش Collection تایپ‌شده در `data_base/query/example/src/main/kotlin/managers/ManagerExampleV31.kt`.

## ۱. هدف و موارد خارج از محدوده

V5.0 سه شکل مصرف زیر را پیاده‌سازی و آزمود:

1. callbackهای `success` و `error` داخل override متد `execute()` در declaration فرزند؛
2. همان callbackها در محل فراخوانی `execute()`؛
3. استخراج Collection تایپ‌شده از `ExecuteResult` با `toCollection()` و پیمایش مستقیم آن.

در هر سه حالت، اجرای Query باید یک بار انجام شود و خروجی typed همان `ICollection<Self>` باقی بماند. نسخهٔ 5.0 نباید یک مسیر اجرای موازی، callback framework جدید، mapper دوم، DTO جداگانه یا تبدیل پنهان به `List<T>` بسازد.

موارد خارج از محدوده:

- تغییر امضای `CteDeclaration.execute(queryManager, params)` یا `ICteDeclaration`؛
- تغییر `QueryConsumer.executeAs()`, `QueryConsumer.execute()`, `ExecuteResult` یا الگوریتم `CteQueryRowMapper`؛
- تغییر رفتار `.sql {}` و `.details {}`، SQL، metadata، بستن منابع یا materialization؛
- تبدیل خودکار خطا به Collection خالی؛
- معرفی `firstAs` یا عملیات جدید در `ICollection`؛
- تغییر dependencyهای Gradle، مگر اینکه اعتبارسنجی مصرف‌کننده مشکل واقعی visibility را نشان دهد و تغییر جداگانه تصویب شود.

## ۲. وضعیت فعلی تأییدشده از سورس

### ۲.۱. `ExecuteResult`

در `data_base/manager/execute/src/main/kotlin/tools/ExecuteResult.kt` قرارداد فعلی چنین است:

```kotlin
sealed class ExecuteResult<out T> {
    data class Success<out T>(val result: T?) : ExecuteResult<T>()
    data class Failure(val exception: Throwable) : ExecuteResult<Nothing>()
}
```

دو نکتهٔ مهم برای طراحی V5.0:

- payload شاخهٔ `Success` حتی وقتی `T` غیرnullable است، از نظر قرارداد `ExecuteResult` می‌تواند `null` باشد.
- خطای `Failure` از نوع `Throwable` است و همان شیء exception را نگه می‌دارد.

در baseline پیش از Phase 1، متد member برای استخراج payload یا `toCollection()` وجود نداشت. اکنون extension عمومی `toCollection()` در ماژول executor پیاده‌سازی شده است؛ رفتار نهایی آن در بخش وضعیت نهایی و قرارداد استخراج آمده است.

### ۲.۲. extensionهای callback موجود

در `data_base/query/executor/src/main/kotlin/result/ExecuteResultFluentExtensions.kt` این APIهای عمومی وجود دارند:

```kotlin
fun <T, R> ExecuteResult<T>.success(
    transform: (T) -> R,
): ExecuteResult<R>

fun <T> ExecuteResult<T>.error(
    handler: (Throwable) -> Unit,
): ExecuteResult<T>
```

رفتار واقعی آن‌ها:

- `success`، فقط برای `Success` دارای payload غیرnull، `transform` را فوراً اجرا می‌کند و نتیجهٔ آن را در `Success` برمی‌گرداند. برای `Success(null)`، callback اجرا نمی‌شود و `Success(null)` با نوع خروجی جدید حفظ می‌شود. برای `Failure` همان failure عبور می‌کند.
- `error`، فقط برای `Failure`، `Throwable` اصلی را به handler می‌دهد و همان شیء `ExecuteResult` را برمی‌گرداند؛ خطا را recover یا حذف نمی‌کند.
- هر دو extension synchronous هستند و callback را هنگام فراخوانی extension اجرا می‌کنند، نه هنگام Query یا payload extraction بعدی.
- استثنایی که خود callback پرتاب کند به `ExecuteResult.Failure` تبدیل نمی‌شود؛ از زنجیره به caller پرتاب می‌شود. در صورت پرتاب استثنا، ادامهٔ زنجیره اجرا نمی‌شود.
- callbackها ثبت یا جایگزین نمی‌شوند. هر extension فراخوانی‌شده یک callback مستقل و فوری اجرا می‌کند. بنابراین callbackهای داخل override و callbackهای جداگانهٔ call site، اگر هر دو استفاده شوند، هر دو به ترتیب تو‌در‌تو اجرا می‌شوند؛ روی Failure نیز هر `error` صریح می‌تواند همان خطا را مشاهده کند.

### ۲.۳. مسیر typed execution و callbackهای SQL/metadata

در `data_base/query/cte/src/main/kotlin/declaration/CteDeclaration.kt`:

```kotlin
open fun execute(
    queryManager: IQueryBuilderExecutor,
    params: P,
): ExecuteResult<ICollection<Self>> =
    configureConsumer(queryReady(queryManager, params))
        .executeAs(::fromQueryRow)
```

`QueryConsumer.executeAs()` در `data_base/query/executor/src/main/kotlin/result/QueryConsumer.kt` یک بار `execute()` را صدا می‌زند، ردیف‌ها را به ترتیب با mapper می‌سازد و در `ICollection<T>` قرار می‌دهد. failure اجرای Query را حفظ می‌کند؛ Success بدون row list را به failure مشخص تبدیل می‌کند؛ نتیجهٔ صفر ردیف، Collection خالی موفق است. این مسیر نباید در V5.0 تکرار شود.

`configureConsumer()` مسیر callbackهای `.sql {}` و `.details {}` را پیش از اجرای Query تنظیم می‌کند. متدهای `sql()` و `details()` introspection همان consumer هستند؛ آن‌ها callbackهای `success/error` نیستند و API یا ترتیبشان در V5.0 تغییر نمی‌کند.

### ۲.۴. Collection تایپ‌شده

`collection/core/src/main/kotlin/collection/ICollection.kt` قرارداد عمومی Collection است. این interface `forEach`, `filter`, `map`, `firstOrNull`, `toList`, `get` و `size` دارد، اما `Iterable<T>` نیست. فراخوانی `rows.forEach { ... }` از member خود `ICollection` استفاده می‌کند.

`QueryConsumer.executeAs()` مستقیماً `ICollection<T>` می‌سازد. `CteDeclaration.execute()` آن را به‌صورت `ExecuteResult<ICollection<Self>>` برمی‌گرداند. بنابراین استخراج برای پیمایش باید همان instance از `ICollection<T>` را برگرداند؛ ساخت wrapper یا `List<T>` غیرضروری است.

### ۲.۵. مصرف‌کنندگان و تست‌های موجود

- `data_base/query/example/src/main/kotlin/v3_1/queries/execute/CteExecutionExampleV31.kt` نتیجهٔ typed را در محل فراخوانی با `.success {}` و `.error {}` زنجیر می‌کند.
- `data_base/query/example/src/main/kotlin/managers/ManagerExampleV31.kt` مثال call-site را با declarationهای واقعی اجرا می‌کند و استخراج `.toCollection()` را نیز نشان می‌دهد.
- `UserDisplayQueryV31.execute()` در `data_base/query/example/src/main/kotlin/v3_1/queries/relations/UserDisplayQueryV31.kt` نتیجهٔ `super.execute()` را با `.success {}` و `.error {}` زنجیر می‌کند؛ تنظیم SQL و metadata از `configureConsumer()` می‌گذرد.
- `data_base/query/cte/src/test/kotlin/declaration/CteDeclarationExecutionTest.kt` تست‌های typed success/error chaining با `ParameterizedDeclaration` دارای mapping واقعی دارد. تست موفقیت نوع `ICollection<ParameterizedDeclaration>`، ترتیب ردیف، instanceهای تازه، callbackها و یک‌بار اجرا را بررسی می‌کند؛ تست خطا حفظ identity خطا و اجرا نشدن callback موفقیت را بررسی می‌کند.
- `data_base/query/executor/src/test/kotlin/manager/QueryConsumerTest.kt` semantics عمومی extensionها را برای payloadهای خام، failure و استثنای callback می‌آزماید.
- فهرست بالا مصرف‌کنندگان و تست‌های مرجع V5.0 را مشخص می‌کند؛ نتیجهٔ Phaseها و وضعیت نهایی اعتبارسنجی در بخش‌های مربوط ثبت شده است.

## ۳. قرارداد نهایی سه شکل استفاده

### ۳.۱. callback در override فرزند

نمونهٔ هدف:

```kotlin
override fun execute(
    queryManager: IQueryBuilderExecutor,
    params: RelationFilters,
): ExecuteResult<ICollection<UserDisplayQueryV31>> =
    super.execute(queryManager, params)
        .success { rows ->
            rows.forEach { row -> println("row: ${row.id}, ${row.fullName}") }
            rows
        }
        .error { failure -> println("error: $failure") }
```

Callback موفقیت باید `ICollection<UserDisplayQueryV31>` ببیند و برای حفظ امضای override همان `rows` را بازگرداند. `super.execute()` فقط یک بار فراخوانی می‌شود. از آنجا که callback در extension بعد از برگشت نتیجهٔ `super.execute()` اجرا می‌شود، خطای callback جزئی از `ExecuteResult` نیست و طبق قرارداد فعلی به caller پرتاب می‌شود.

این mode در `CteDeclarationExecutionTest.kt` با fixture دارای output mapping معتبر آزموده شده و در `UserDisplayQueryV31.kt` نیز به‌عنوان مثال production نشان داده می‌شود. چون extensionها فوری و همگام‌اند، اگر یک نتیجه هم درون override و هم در call site callback داشته باشد، هر دو callback اجرا می‌شوند؛ استفادهٔ هم‌زمان باید عمدی باشد.

### ۳.۲. callback در محل فراخوانی

نمونهٔ هدف:

```kotlin
val result: ExecuteResult<ICollection<UserDisplayQueryV31>> =
    UserDisplayQueryV31()
        .execute(queryManager, params)
        .success { rows ->
            rows.forEach { row -> println("row: ${row.id}, ${row.fullName}") }
            rows
        }
        .error { failure -> println("error: $failure") }
```

این مسیر با extensionهای موجود سازگار است و به تغییر production API نیاز ندارد. importهای `success` و `error` باید در فایل مصرف‌کننده باشند. callback success نوع را فقط تا وقتی `rows` یا مقداری سازگار با نوع مورد انتظار برمی‌گرداند، به `ICollection<UserDisplayQueryV31>` حفظ می‌کند؛ اگر نوع دیگری برگرداند، نوع `ExecuteResult` نیز طبق generic extension تغییر می‌کند.

### ۳.۳. استخراج و پیمایش با `toCollection()`

نمونهٔ هدف:

```kotlin
val rows: ICollection<UserDisplayQueryV31> =
    UserDisplayQueryV31()
        .execute(queryManager, params)
        .toCollection()

rows.forEach { row -> println("row: ${row.id}, ${row.fullName}") }
```

`toCollection()` فقط payload را از نتیجهٔ قبلاً اجراشده استخراج می‌کند. در Success غیرnull، همان reference از `ICollection<T>` را برمی‌گرداند؛ query اجرا نمی‌کند، mapper را دوباره صدا نمی‌زند، Collection را کپی نمی‌کند و آن را به `List<T>` تبدیل نمی‌کند.

## ۴. قرارداد نهایی خطا در `toCollection()`

برای آنکه نتیجهٔ متد مستقیماً قابل `forEach` باشد، نوع خروجی `ICollection<T>` است. در نتیجه، Failure از مسیر مقدار خروجی خارج و به‌صورت exception پرتاب می‌شود. قرارداد `ExecuteResult` نیز `Success(null)` را ممکن می‌داند. extension عمومی در ماژول executor این قرارداد را پیاده می‌کند:

```kotlin
fun <T> ExecuteResult<ICollection<T>>.toCollection(): ICollection<T> =
    when (this) {
        is ExecuteResult.Success -> result
            ?: throw IllegalStateException("Successful result contains no collection")
        is ExecuteResult.Failure -> throw exception
    }
```

پیاده‌سازی بدون تغییر hierarchy یا فایل `ExecuteResult.kt` انجام شده است. `Failure` همان `Throwable` را بدون wrapper یا جایگزینی پرتاب می‌کند. `Success(null)` با `IllegalStateException("Successful result contains no collection")` شکست می‌خورد و هرگز به Collection خالی تبدیل نمی‌شود. Success غیرnull، از جمله Collection خالی، همان object را برمی‌گرداند.

حفظ Failure به‌صورت value در خروجی مستقیم `ICollection<T>` ممکن نیست؛ برای پیمایش بدون شاخه‌بندی قرارداد تثبیت‌شده این است که همان خطا پرتاب شود. تغییر این قرارداد به wrapper یا نوع خروجی دیگری خارج از محدودهٔ تأییدشدهٔ V5.0 است.

چینش زیر ابتدا خطا را از طریق `error` مشاهده می‌کند و همان نتیجه را حفظ می‌کند؛ سپس `toCollection()` همان Failure را به‌صورت exception پرتاب می‌کند. Caller نباید انتظار داشته باشد `toCollection()` خطا را recover کند:

```kotlin
val rows = query.execute(queryManager, params)
    .error { log(it) }
    .toCollection() // Failure را همان‌طور که هست پرتاب می‌کند.
```

## ۶. وضعیت فازهای اجرایی

### Phase 0 — تأیید قرارداد و baseline: تکمیل شد

**فایل‌ها:** فقط بررسی source و تست‌های فهرست‌شده در بخش ۲؛ بدون تغییر.

**کار انجام‌شده:** semantics `success/error`, `Success(null)`, خطاهای callback و typed `execute()` بررسی شد. قرارداد extraction تثبیت شد: Failure همان Throwable را پرتاب می‌کند و Success(null) به `IllegalStateException` منتهی می‌شود.

**نتیجه:** تصمیم extraction صریح و پیاده‌سازی شد؛ Failure به‌صورت value از `toCollection()` برگردانده نمی‌شود.

### Phase 1 — افزودن extraction extension: تکمیل و اعتبارسنجی شد

**فایل‌های اصلی:** `ExecuteResultCollectionExtensions.kt` و `ExecuteResultCollectionExtensionsTest.kt`.

**رفتار اجراشده:** `toCollection()` روی `ExecuteResult<ICollection<T>>` تعریف شد؛ Success غیرnull را عیناً برمی‌گرداند، Failure را با همان Throwable پرتاب می‌کند، و Success(null) را به Collection خالی تبدیل نمی‌کند. dependency یا قرارداد sealed result تغییر نکرد.

**نتیجه:** compile-time type و identity، Collection خالی واقعی، Failure و Success(null) در تست واحد بررسی شدند؛ تست هدفمند موفق شد.

### Phase 2 — تثبیت callback chaining در CTE: تکمیل و اعتبارسنجی شد

**فایل تست اصلی:** `CteDeclarationExecutionTest.kt`؛ production در این Phase تغییر نکرد.

**رفتار اجراشده:** تست‌های جداگانه برای callbackهای داخل override و callbackهای call-site؛ نوع callback موفقیت `ICollection<ConcreteDeclaration>`، دریافت Throwable اصلی در callback خطا، و تعداد دفعات صریح اجرای callback بررسی شد.

**نتیجه:** تست‌های CTE و executor، نوع typed، ترتیب callbackها، حفظ Throwable، یک‌بار اجرا و mapping، callbackهای SQL/metadata و نبود اجرای مجدد پس از extraction را پوشش دادند و موفق شدند.

### Phase 3 — تکمیل مثال‌های V3.1 و compile fixture: تکمیل شد

**فایل‌های مرتبط:** `UserDisplayQueryV31.kt`, `CteExecutionExampleV31.kt` و `ManagerExampleV31.kt`. `TypedQueryConsumerApiCompileFixture.kt` در compile sources باقی ماند.

**رفتار اجراشده:** مثال call-site حفظ شد؛ `ManagerExampleV31` نتیجهٔ `toCollection()` را مستقیماً به‌عنوان Collection typed پیمایش می‌کند؛ `UserDisplayQueryV31` callbackها را داخل override روی نتیجهٔ یک اجرای `super.execute()` زنجیر می‌کند.

**نتیجه:** مثال‌ها سه الگو را نشان می‌دهند و compile-time typed usage در example تأیید شد. Consumer compile مستقل با تنها dependency مستقیم CTE در Phase 4 دوباره اجرا نشد؛ اجرای مستقل موفق قبلی در محدودیت‌های بخش وضعیت نهایی ذکر شده است.

### Phase 4 — اعتبارسنجی و release review: تکمیل شد

**دامنهٔ اجراشده:** 7 تست CTE، 55 تست executor، 13 تست example و کامپایل production مثال؛ جزئیات و محدودیت‌های اجرا در بخش وضعیت نهایی آمده‌اند.

**نتیجه:** مجموعه‌های هدفمند با موفقیت اجرا شدند و وضعیت `UP-TO-DATE` از taskهای اجراشده تفکیک شد. محدودیت تکرار نشدن consumer compile مستقل در این مرحله باقی است؛ این نتیجه به معنی اجرای همهٔ تست‌ها یا مثال‌های دیتابیس‌محور نیست.

## ۷. ماتریس تست و معیارهای قابل بررسی

| سناریو | انتظار |
|---|---|
| chaining موفق در override فرزند | `rows` از نوع `ICollection<Concrete>`؛ همان نتیجهٔ typed از `super.execute()` حفظ شود |
| chaining موفق در call site | callbackها فوراً و به ترتیب زنجیره اجرا شوند؛ Query دوباره اجرا نشود |
| چند `success` | هر callback موفقیت روی payload غیرnull فعلی اجرا شود؛ نوع generic طبق مقدار برگشتی هر callback تغییر کند |
| Success(null) در `success` | callback اجرا نشود و null success حفظ شود |
| chaining خطا | success اجرا نشود؛ هر `error` صریح، همان `Throwable` را ببیند و result را حفظ کند |
| callback success/error exception | طبق قرارداد موجود به caller پرتاب شود؛ به Failure تبدیل نشود و callbackهای بعدی اجرا نشوند |
| `toCollection()` روی Success غیرnull | همان instance از `ICollection<T>` برگردد؛ نه کپی، نه List و نه mapping مجدد |
| `toCollection()` روی Failure | همان `Throwable` بدون wrapper پرتاب شود؛ در تست identity بررسی شده است |
| `toCollection()` روی Success(null) | `IllegalStateException("Successful result contains no collection")`؛ Collection خالی ساختگی تولید نشود |
| Collection خالی واقعی | همان Success خالی قابل استخراج و پیمایش باشد؛ با خطا اشتباه نشود |
| typed CTE end-to-end | `createCte`/execution یک بار، mapper یک بار برای هر ردیف، ترتیب ردیف‌ها حفظ شود |
| SQL و metadata callbacks | `configureConsumer`, `.sql {}` و `.details {}` همچنان یک بار و روی consumer آماده‌شده اجرا شوند |
| compose callback و extraction | پس از مشاهدهٔ خطا، extraction همچنان failure را طبق قرارداد خودش مدیریت کند؛ failure خاموش نشود |
| API visibility | consumer compile مستقل قبلی موفق گزارش شد؛ در Phase 4 دوباره اجرا نشد. compile fixture داخل example، consumer مستقل CTE-only محسوب نمی‌شود |

## ۸. محدودیت‌ها و موارد خارج از محدوده

1. **اجرای دیتابیس:** مثال‌های وابسته به دیتابیس در این اعتبارسنجی اجرا نشدند؛ compile و تست‌های گزارش‌شده جای اجرای end-to-end با دیتابیس را نمی‌گیرند.
2. **Consumer compile مستقل:** اجرای مستقل قبلی با dependency مستقیم CTE موفق گزارش شد، اما در Phase 4 تکرار نشد؛ جزئیات fixture تاریخی محدود است. fixture موجود زیر example dependencyهای مستقیم بیشتری دارد و جایگزین آن بررسی مستقل نیست.
3. **هشدار Kotlin daemon:** در یکی از کامپایل‌ها دسترسی به فایل موقت daemon رد شد؛ Gradle به fallback بدون daemon رفت و کامپایل موفق شد.
4. **هشدار JVM target:** با JDK 24، Kotlin compiler به JVM target 22 fallback کرد و هشدار ناسازگاری target گزارش شد. این هشدار در این کار رفع یا با اجرای مجدد جداگانه بررسی نشد.
5. **Callbackهای تودرتو:** اگر declaration override و caller هر دو callback زنجیر کنند، هر دو callback صریحاً فراخوانی‌شده اجرا می‌شوند. خطای callback به Failure تبدیل نمی‌شود و اجرای ادامهٔ زنجیره را متوقف می‌کند. این رفتار قرارداد موجود است.
6. **موارد خارج از scope:** تغییر `ExecuteResult` یا `ICteDeclaration`, تغییر رفتار callbackها، recovery خودکار خطا، تبدیل خطا به Collection خالی، اجرای `firstAs`, عملیات جدید Collection، mapper یا تبدیل‌های ضمنی نوع، و تغییر مدیریت منابع/SQL/metadata تأیید نشده‌اند و در V5.0 انجام نشده‌اند.

## ۹. جمع‌بندی نهایی V5.0

- Phaseهای 1 تا 4 تکمیل شده‌اند: extension `toCollection()` افزوده شد، رفتار callbackهای typed CTE با تست تثبیت شد، سه الگوی استفاده در مثال‌های V3.1 ثبت شدند و مجموعه‌های هدفمند CTE، executor و example موفق شدند.
- قرارداد نهایی `toCollection()` در بخش 4 آمده است. مسیر typed CTE و اجرای خام `QueryConsumer` جدا باقی مانده‌اند و mapper موجود تنها مسیر materialization ردیف‌های typed است.
- شمار 75 فقط جمع تست‌های هدفمند گزارش‌شده است (7 CTE + 55 executor + 13 example) و نباید به‌عنوان پوشش کامل پروژه تعبیر شود. محدودیت‌های اجرای دیتابیس، consumer compile مستقل، Kotlin daemon و JVM target در بخش 8 ثبت شده‌اند.
- قابلیت یا رفتاری فراتر از قراردادهای ثبت‌شده در این سند، بدون تصمیم و مجوز جداگانه خارج از محدوده است.
