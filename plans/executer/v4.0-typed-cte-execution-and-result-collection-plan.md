# پلن نسخهٔ 4.0: اجرای متمرکز و خروجی Collection برای Typed CTE

## وضعیت سند و مرز این مرحله

این سند ادامهٔ معماری نسخهٔ 3.0 و مرجع تصمیم‌ها و فازهای اجرای V4.0 است. مفاد آن مجوز ضمنی برای فاز یا validation نیست؛ build/test و تغییرات هر فاز نیازمند محدوده و مجوز جداگانه‌اند.

تصمیم‌های معماری v4.0 در این سند نهایی شده‌اند: `CteDeclaration` اجرای typed را متمرکز می‌کند، هر ردیف را به نمونه‌ای مستقل از Query class تبدیل می‌کند و `ExecuteResult<ICollection<Self>>` برمی‌گرداند؛ اجرای خام فقط در سطح `QueryConsumer.execute()` و `QueryConsumer.first()` باقی می‌ماند؛ و تنظیم callbackهای Query از hook محافظت‌شدهٔ `configureConsumer` عبور می‌کند. الگوی generic از CRTP استفاده می‌کند، با این محدودیت که Kotlin برابر بودن `Self` با کلاس concrete را تضمین نمی‌کند. تغییر نوع بازگشتی `execute` یک ناسازگاری منبعی تأییدشده است و باید با مهاجرت call-siteها مدیریت شود.

مبنای پیشین، `plans/executer/v3.0-typed-query-result-mapping-plan.md` است. قواعد v3.0 دربارهٔ declaration بدون پارامتر، ورود صریح params هنگام ساخت CTE یا اجرا، استفاده از همان Query class به‌عنوان مدل خروجی، alias منتشرشده، mapping صریح و حفظ composition در v4.0 همچنان معتبرند. v4.0 نباید `ICteDeclaration.params`، سازندهٔ پارامترپذیر یا overload قدیمی `cte(declaration)` را بازگرداند.

## ۱. مسئله و هدف نسخهٔ 4.0

در سورس کنونی، `CteDeclaration<P, Self>.execute(queryManager, params)` از `configureConsumer(queryReady(...)).executeAs(::fromQueryRow)` استفاده می‌کند و نتیجهٔ typed می‌دهد. اجرای خام ردیف‌ها از APIهای موجود `QueryConsumer.execute()` و `QueryConsumer.first()` در سطح consumer انجام می‌شود؛ `CteDeclaration` API اجرای خام جداگانه ارائه نمی‌کند. این نسخه قرارداد typed declaration را حفظ می‌کند:

1. declaration concrete نوع خروجی دقیق خود را به base class اعلام کند.
2. اجرای direct declaration از `QueryConsumer.executeAs` عبور کند.
3. هر `QueryRow` به یک نمونهٔ تازه از همان Query class تبدیل شود.
4. نتیجهٔ typed به‌صورت `ExecuteResult<ICollection<Self>>` منتشر شود.
5. SQL، materialization، binding، metadata و مدیریت منابع در مسیرهای موجود بمانند.
6. propertyهای خروجی با `@QBQuerySelect` قرارداد mapping را اعلام می‌کنند؛ mapper پیش‌فرض base آن‌ها را می‌خواند و فرزند برای mapping عادی به override یا companion factory نیاز ندارد. اجرای SQL در فرزند بازنویسی نمی‌شود.
7. قابلیت خام `QueryRow` برای مصرف‌کننده‌ای که واقعاً به آن نیاز دارد، از APIهای `QueryConsumer.execute()` و `QueryConsumer.first()` در سطح consumer استفاده می‌کند؛ `CteDeclaration` فقط مسیر typed مستقیم را ارائه می‌دهد.

این نسخه قابلیت typed موجود در `QueryConsumer.executeAs` و `collection:core` را در اجرای مستقیم declaration به کار می‌گیرد. Mapper metadata-based با reflection روی propertyهای `@QBQuerySelect`، سازندهٔ بدون پارامتر و setterها بخشی از قرارداد typed CTE است. عملیات جدید Collection و API `firstAs` در scope نیستند.

## ۳. قرارداد generic منتخب: CRTP

الگوی منتخب v4.0:

```kotlin
abstract class CteDeclaration<
    P,
    Self : CteDeclaration<P, Self>,
> : ICteDeclaration<P> {
    // ...
}
```

نمونهٔ concrete:

```kotlin
class UserDisplayQueryV31 :
    CteDeclaration<UserDisplayQueryV31.RelationFilters, UserDisplayQueryV31>() {
    // declaration و row properties
}
```

`P` ورودی یک invocation از CTE یا execute است؛ `Self` نوعی است که به‌عنوان خروجی typed استفاده می‌شود. پارامترها در constructor یا state declaration ذخیره نمی‌شوند. generic arity و `createCte(params)` در `ICteDeclaration<P>` حفظ شده‌اند؛ نسبت به `HEAD`، `val params: P` حذف و `operator fun invoke(params)` اضافه شده است (جزئیات در §۲). Self type فقط برای اجرای typed base لازم است و تعمیم interface با Self انجام نشده است.

**محدودیت CRTP:** bound بازگشتی `Self : CteDeclaration<P, Self>` رابطهٔ ارث‌بری را محدود می‌کند، اما Kotlin تضمین نمی‌کند `Self` دقیقاً همان concrete class جاری باشد. یک subclass می‌تواند Self نامناسبی اعلام کند یا subtype دیگری برگرداند. هر declaration باید با compile fixture و تست نوع خروجی بررسی شود؛ پلن ادعای self type کاملاً اثبات‌شده ندارد.

تغییر generic arity از `CteDeclaration<P>` به `CteDeclaration<P, Self>` برای هر subclass فعلی source-breaking است. هیچ سازگاری خودکاری برای نوشتار قدیمی وجود ندارد. CTEهای صرفاً test/helper که مدل خروجی ندارند نباید mapping ساختگی تعریف کنند؛ اگر فقط declaration را می‌آزمایند مستقیماً `ICteDeclaration<P>` را پیاده می‌کنند، و اگر هدف typed execution است باید output model و mapping واقعی داشته باشند یا تست در مسیر شکست پیش از mapping متوقف شود. base class دوم برای raw CTE در scope نیست.

## ۴. قرارداد mapping هر ردیف

Mapper مشترک در `CteQueryRowMapper` از metadata runtime مربوط به `@QBQuerySelect` استفاده می‌کند. پیاده‌سازی فعلی `CteDeclaration.fromQueryRow(row)` را به‌صورت پیش‌فرض فراهم می‌کند؛ subclass برای satisfy کردن قرارداد والد به factory یا override تکراری نیاز ندارد:

```kotlin
open fun fromQueryRow(row: QueryRow): Self = CteQueryRowMapper.map(this, row)
```

برای هر نوع declaration، mapper یک‌بار metadata کلاس را cache می‌کند و برای هر ردیف یک نمونهٔ مستقل با سازندهٔ بدون پارامتر می‌سازد. propertyهای خروجیِ دارای `@QBQuerySelect` به‌وسیلهٔ setter مقدار می‌گیرند؛ نمونهٔ اصلی، params، AST یا execution state را به نمونهٔ خروجی منتقل نمی‌کند. مسیر mapping نباید `createCte`, `queryReady`, executor یا ساخت AST را فراخوانی کند.

Reflection در این قرارداد محدود به کشف metadata و سازنده، ساخت نمونه و دسترسی به setterهای mapping است؛ از آن برای بازسازی query یا اثبات `Self` در CRTP استفاده نمی‌شود. CRTP به‌تنهایی تضمین نمی‌کند `Self` دقیقاً کلاس runtime باشد؛ mapper نیز فقط تضمین می‌کند نمونهٔ تازهٔ ساخته‌شده از همان runtime class declaration باشد.

### قواعد mapping

- فقط propertyهای runtime-annotated با `@QBQuerySelect` وارد mapping می‌شوند؛ annotation در `data_base/core` برای runtime retention تعریف شده است. هر مدل باید دست‌کم یک property نگاشت‌پذیر داشته باشد. property باید mutable (`var`) با getter واقعی و setter عمومی باشد؛ setter برای reflection قابل‌دسترسی می‌شود؛ `val` و setter غیرعمومی قرارداد mapping نیستند.
- alias lookup از published SQL alias انجام می‌شود: `@QBQuerySelect.alias` مبناست و اگر unset باشد resolver نام convention-based property را به کار می‌برد. `@QBQuerySelect.name` نام منطقی است و جای alias منتشرشده را نمی‌گیرد. alias خالی یا aliasهای تکراری روی propertyهای خروجی خطای mapping می‌دهند.
- تنها classifierهای `Int`, `Long` و `String` پشتیبانی می‌شوند؛ مقدار materialized باید دقیقاً همان نوع باشد. تبدیل ضمنی، widening عددی، parse رشته یا coercion دیگری انجام نمی‌شود.
- `NULL` فقط برای property nullable پذیرفته و به `null` map می‌شود؛ `NULL` برای property non-null، alias مفقود، نوع پشتیبانی‌نشده یا مقدار runtime با نوع ناسازگار خطای قابل‌تشخیص ایجاد می‌کند. مقدار پیش‌فرض ساختگی و `!!` پنهان‌کننده مجاز نیست.
- هر نوع خروجی باید سازندهٔ بدون پارامتر قابل‌دسترسی برای mapper داشته باشد. نبودن یا غیرقابل‌دسترسی بودن سازنده، خطای سازنده و شکست setter با خطای mapping و cause قابل‌ردیابی گزارش می‌شوند.
- lookup فقط از همان `QueryRow` است؛ هر ردیف identity مستقل دارد و property state بین ردیف‌ها share نمی‌شود. خطای mapper هنگام `executeAs` به Failure با شمارهٔ ردیف 1-based و exception اصلی به‌عنوان cause تبدیل می‌شود؛ فراخوانی مستقیم `fromQueryRow` خطای mapping را مستقیماً پرتاب می‌کند.
- ساخت خروجی نباید query، CTE یا AST را مجدداً بسازد. mapping روی ردیف materialize‌شده انجام می‌شود و به ResultSet وابسته نیست.

## ۵. قرارداد اجرای typed در base

قرارداد هدف از نظر مفهومی:

```kotlin
protected open fun configureConsumer(consumer: QueryConsumer): QueryConsumer = consumer

open fun execute(
    queryManager: IQueryBuilderExecutor,
    params: P,
): ExecuteResult<ICollection<Self>> =
    configureConsumer(queryReady(queryManager, params)).executeAs(::fromQueryRow)

```

این قرارداد typed تصمیم معماری v4.0 است، نه گزینهٔ باز. هر اجرای مستقیم از یک `queryReady` و همان hook استفاده می‌کند؛ هر فراخوانی `createCte(params)` را یک بار می‌سازد و سپس `executeAs` را روی همان `QueryConsumer` صدا می‌زند. ساخت Consumer به‌تنهایی SQL را اجرا نمی‌کند. تغییر return type متد موجود `execute` منبع‌شکن است؛ callerهایی که ردیف خام می‌خواهند باید از مسیرهای خام `QueryConsumer` استفاده کنند، نه از یک API خام declaration-level.

### ترتیب و مرز خطا

1. `queryReady(queryManager, params)` یک بار `createCte(params)` را صدا می‌زند و QueryConsumer موجود را می‌سازد؛ ساخت consumer به‌تنهایی SQL اجرا نمی‌کند.
2. `executeAs` دقیقاً یک بار `QueryConsumer.execute()` را صدا می‌زند. مسیر executor, ResultSet materialization, resource closing و ترتیب binding همان مسیر فعلی می‌ماند.
3. SQL/JDBC Failure از `executeAs` به همان Failure عبور می‌کند و mapper اجرا نمی‌شود.
4. `ExecuteResult.Success<T>` واقعاً payload از نوع `T?` دارد. در typed path، Success با payload تهی به Failure با `IllegalStateException("SELECT completed without a materialized row list")` تبدیل می‌شود؛ Success با صفر ردیف، `ICollection` خالی برمی‌گرداند. raw path همان قرارداد فعلی `QueryConsumer.execute()` را حفظ می‌کند.
5. Rowها به ترتیب materialization map می‌شوند. اولین `Exception` در mapper نگاشت را متوقف می‌کند و Failure با شمارهٔ ردیف 1-based و cause اصلی برمی‌گرداند؛ collection ناقص Success نمی‌شود. رفتار `Error`/`Throwable` همان قرارداد فعلی `QueryConsumer` است و نباید ضمن این کار عوض شود.
6. خطای synchronous در `createCte`/آماده‌سازی، پیش از ورود به `QueryConsumer.executeAs` رخ می‌دهد و طبق تست فعلی `CteDeclarationExecutionTest` از مرز result خارج می‌ماند؛ v4 نباید این مرز را تصادفاً تغییر دهد.
7. SQL و metadata callbackهای `.sql {}` و `.details {}` از طریق `configureConsumer` روی همان Query آماده‌شده اعمال می‌شوند. `sql()` و `details()` بدون callback به‌ترتیب `BuiltQuery` و `EffectiveQueryMetadata` برمی‌گردانند و hook نیستند؛ overloadهای callback همان `QueryConsumer` را برمی‌گردانند. اگر callback یا آماده‌سازی پیش از اجرای Consumer به‌صورت synchronous خطا دهد، خطا مانند رفتار فعلی بیرون از `ExecuteResult` پرتاب می‌شود؛ خطای SQL/JDBC از مسیر executor و خطای mapper از `executeAs` عبور می‌کند.

`queryReady(queryManager, params)` مسئول آماده‌سازی باقی می‌ماند و Collection نمی‌سازد. `QueryConsumer.executeAs` مسئول mapping و ساخت Collection باقی می‌ماند؛ `QueryConsumer.execute()` materialization خام را در سطح consumer فراهم می‌کند. `IQueryBuilderExecutor`, `QueryRow` و materializer در طرح پایه تغییر نمی‌کنند مگر اینکه مانع واقعی در پیاده‌سازی مستند و جداگانه تأیید شود.

| `CteDeclaration<P>` | `CteDeclaration<P, Self>` | همهٔ subclassها باید arity و Self را مشخص کنند؛ mapping پیش‌فرض از `@QBQuerySelect` metadata استفاده می‌کند و override تکراری لازم نیست. |
| `execute(queryManager, params): ExecuteResult<List<QueryRow>>` | `execute(queryManager, params): ExecuteResult<ICollection<Self>>` | return type با overload حل نمی‌شود؛ overrideهای خام و callerهای وابسته به List باید مهاجرت کنند. |
| mapping typed در Queryهای V3/V3.1 | default `fromQueryRow(row)` در base به metadata mapper reflection-based واگذار می‌شود | concrete declaration به override یا companion factory تکراری نیاز ندارد؛ نگاشت بر اساس annotation، alias منتشرشده و setter انجام می‌شود. |
| `CteExecutionExampleV31` و formatterهای وابسته به ردیف | مثال اصلی V3.1 typed باقی می‌ماند؛ مصرف‌کننده‌های نیازمند دادهٔ خام از `QueryConsumer.execute()` یا `first()` استفاده می‌کنند. |

`ICteDeclaration<P>.createCte(params)`، operator `invoke(params)`, ورودی‌های صریح params، inline `cte(relation)`, named `cte("name")`, `with(Cte)`, `with(name, Cte)`, `queryReady`, `QueryConsumer.execute()`, `QueryConsumer.first()`, `IQueryBuilderExecutor`، SQL، metadata، aliasها، parameter ordering و DML در این طرح حفظ می‌شوند.

### حفظ مسیر خام

تصمیم تأییدشده، typed `execute(queryManager, params)` است. تغییر نام/return type از نظر source compatibility ناسازگار است: هر assignment قدیمی به `ExecuteResult<List<QueryRow>>`، هر زنجیره‌ای که `List` انتظار دارد و هر override خامِ `execute` باید مهاجرت کند؛ Kotlin برای تفاوت صرفاً در return type overload نمی‌سازد و override قدیمی نیز با امضای جدید سازگار نیست. مصرف‌کنندگان خام باید به `QueryConsumer.execute()` یا `QueryConsumer.first()` در سطح consumer متکی باشند، نه به مسیر خام declaration-level.

`QueryConsumer.execute()` و `first()` همچنان خام و بدون تغییر می‌مانند. نمونهٔ A1 همچنان از `QueryConsumer.execute()` برای `QueryRow` استفاده می‌کند؛ مثال `CteExecutionExampleV31` typed است و از `execute` استفاده می‌کند. هیچ API خام declaration-level در v4.0 ارائه نمی‌شود و هیچ deprecation لایه‌ای لازم نیست.

## ۸. semanticsهایی که نباید تغییر کنند

- Params ورودی هر execute/createCte فقط همان invocation را تعیین می‌کنند؛ روی Query declaration یا نمونهٔ خروجی ذخیره نمی‌شوند.
- CTE inline و composition با `WITH` دو مسیر مجزا می‌مانند؛ در migration هیچ‌کدام برای سهولت compile جایگزین دیگری نمی‌شود.
- direct declaration execution با `queryReady` از AST relation ساخته‌شده با `createCte(params)` استفاده می‌کند؛ inline source با `from { cte(relation) }` است؛ در WITH composition relation به `withs` افزوده می‌شود و source با `cte("name")` ارجاع داده می‌شود. SQL، alias، dependency و ترتیب binding این مسیرها ممکن است متفاوت باشند و جداگانه سنجیده می‌شوند.
- `createCte(params)` برای direct execute یک بار فراخوانی می‌شود. row mapping نه CTE می‌سازد نه AST را دوباره تولید می‌کند.
- SQL aliases منتشرشده، ترتیب binding، dependencyها، runtime query names و aliasهای هر occurrence ثابت می‌مانند.
- materialization تا زمانی که ResultSet باز است در executor فعلی انجام می‌شود؛ mapping روی `QueryRow` materialize‌شده است و به ResultSet وابسته نیست.
- Query failure و مدیریت منابع مطابق مسیر executor باقی می‌مانند؛ mapping failure به query failure نسبت داده نمی‌شود و cause/context آن قابل مشاهده می‌ماند.
- `.sql {}` و `.details {}` در direct typed و raw execution از `configureConsumer` روی همان Query invocation اعمال می‌شوند؛ no-arg `sql()` و `details()` صرفاً مقدار برمی‌گردانند.
- `QueryConsumer.execute()`, `first()`, `QueryRow`, `IQueryBuilderExecutor` و INSERT/UPDATE/DELETE contracts تغییر معنا نمی‌دهند.

### معیار تکمیل نسخه

1. Typed `execute` در base فقط `queryReady(...).executeAs(...)` را برای اجرای SQL مصرف کند؛ منطق موازی JDBC یا materializer اضافه نشده باشد.
2. هر Query row نمونهٔ مستقل concrete دارد؛ factory فقط مقدارهای row را map می‌کند.
3. mapping، خطا، ترتیب و empty semantics جدول بالا با تست اثبات شوند.
4. dependencyهای لازم برای انتشار عمومی `ICollection<Self>` و انواع executor/result اکنون از CTE با پیکربندی `api` منتشر می‌شوند؛ consumer check مستقل با تنها dependency مستقیم روی CTE موفق گزارش شده است.
5. همهٔ direct execute callers، overrideها، subclass fixtures و مثال‌های V3/V3.1 inventory شده و آگاهانه مهاجرت شده باشند.
6. callbackها، SQL، metadata، composition، aliasها، dependencies و binding order بدون regression باشند.
7. خطاهای build/test به‌جای تضعیف assertion یا حذف تست با اصلاح علت ریشه‌ای حل شوند.
8. هیچ تغییر نامرتبط، dependency تازه، stage یا commit وارد کار نشود.

## ۱۰. فازهای پیشنهادی اجرا

### فاز ۰ — بازبینی امکان‌پذیری و تثبیت تصمیم‌ها — تکمیل‌شده

**دامنه و شواهد:** بازبینی read-only قراردادهای `CteDeclaration.kt`, `ICteDeclaration.kt`, `QueryConsumer.kt`, `IQueryBuilderExecutor.kt`, `QueryRow.kt`, `ExecuteResult.kt`، Gradle ماژول‌های executor/CTE و call-siteهای repository. نتیجه: overloadهای no-arg و callback در `sql/details` نوع و رفتار متفاوت دارند؛ `executeAs` روی `execute()` یک‌بار map می‌کند؛ CTE مسیر declaration-level typed دارد و raw execution در `QueryConsumer` باقی می‌ماند؛ CTE اکنون dependencyهای لازم را با `api` و `java-library` منتشر می‌کند و compile موفق consumer مستقل با تنها dependency مستقیم CTE گزارش شده، اما شواهد کامل آن در دسترس نیست؛ CRTP Self type را به‌طور مطلق تضمین نمی‌کند.

**تصمیم‌های تثبیت‌شده:** `execute` typed، نبود API خام declaration-level، hook محافظت‌شدهٔ `configureConsumer`، انتقال handlerهای UserDisplay به caller، حفظ A1 روی مسیر خام `QueryConsumer`, ممنوعیت mapping ساختگی در fixtures، و انتشار dependencyهای عمومی لازم از CTE که compile موفق آن گزارش شده است. `ICteDeclaration<P>` بدون Self باقی می‌ماند؛ حذف `val params` و افزودن `invoke(params)` نسبت به `HEAD` در §۲ ثبت شده و interface نباید بدون تغییر خوانده شود.

**بررسی:** build و test در این فاز اجرا نمی‌شوند.

**معیار پذیرش:** همهٔ قراردادهای باز در این بخش تصمیم‌گیری شده‌اند و inventory بخش ۷ مرجع مهاجرت است. این فاز از نظر تصمیم معماری تکمیل است؛ consumer compile مستقل با موفقیت گزارش شده، اما ثبت فرمان و خروجی کامل برای شواهد بازتولیدپذیر validation باقی می‌ماند.

**تأیید لازم:** تصمیم معماری جدیدی باز نیست؛ شروع هر فاز پیاده‌سازی و اجرای اعتبارسنجی همچنان باید جداگانه مجاز شود.

### فاز ۱ — قرارداد CRTP و row factory

**فایل‌ها/ماژول‌ها:** `data_base/query/cte/src/main/kotlin/declaration/CteDeclaration.kt`; `data_base/query/cte/src/main/kotlin/mapper/CteQueryRowMapper.kt`; چهار declaration در `data_base/query/example/src/main/kotlin/v3/queries/relations/`; چهار declaration در `.../v3_1/queries/relations/`; تست‌های mapper در `data_base/query/example/src/test/kotlin/v3/TypedQueryOutputFactoryTest.kt`; fixtures ارث‌برنده در CTE/executor که برای قرارداد base لازم‌اند. در این فاز تغییر دیگری در قرارداد `ICteDeclaration.kt` پیش‌بینی نمی‌شود؛ وضعیت تفاوت فعلی آن با `HEAD` در §۲ ثبت شده است.

**دامنه و رفتار:** افزودن `Self` به base و پیاده‌سازی پیش‌فرض instance-level `fromQueryRow(row): Self` با mapper metadata-based. Mapper propertyهای `@QBQuerySelect` را inspect می‌کند، metadata کلاس را cache می‌کند و برای هر row نمونهٔ تازه‌ای با no-arg constructor می‌سازد؛ setterهای public مقدار می‌گیرند. پشتیبانی به `Int`, `Long`, `String` و nullability واقعی Kotlin محدود است و conversion ضمنی ندارد. fixture بدون output معتبر مستقیماً `ICteDeclaration` می‌شود یا فقط در تستی استفاده می‌شود که پیش از mapping شکست می‌خورد؛ مقدار جعلی ساخته نمی‌شود.

**بررسی بعدی:** compile production و test ماژول‌های CTE/example و تست factoryهای alias/type/null/identity؛ تست‌ها هنوز اجرا نشوند تا مجوز مرحلهٔ اعتبارسنجی داده شود.

**معیار پذیرش:** concrete `Self` در مثال‌ها به نوع مورد انتظار assign می‌شود؛ mapper alias منتشرشده و نوع دقیق را می‌سنجد، propertyهای nullable را طبق قرارداد map می‌کند و خطاهای alias/type/constructor/setter را آشکار می‌کند؛ metadata هر کلاس cache و هر row مستقل ساخته می‌شود. Reflection فقط برای کشف metadata، constructor و setter در مسیر mapping است و هیچ query، CTE یا ASTی ساخته یا اجرا نمی‌کند؛ CRTP به‌تنهایی exact runtime class را تضمین نمی‌کند.

**تأیید لازم:** مجوز شروع فاز و سپس مجوز جداگانهٔ build/test.

### فاز ۲ — اجرای typed متمرکز و تنظیم Consumer

**فایل‌ها/ماژول‌ها:** `data_base/query/cte/src/main/kotlin/declaration/CteDeclaration.kt`; تست‌های `data_base/query/cte/src/test/kotlin/declaration/CteDeclarationExecutionTest.kt` و تست متمرکز executor در `data_base/query/executor/src/test/kotlin/manager/QueryConsumerExecuteAsTest.kt`. پیکربندی Gradle CTE فعلی از قبل `java-library` و dependencyهای عمومی `api` دارد؛ تغییر Gradle در scope این فاز نیست.

**دامنه و رفتار:** `execute(queryManager, params): ExecuteResult<ICollection<Self>>` از `configureConsumer(queryReady(...)).executeAs(::fromQueryRow)` استفاده می‌کند. `queryReady` یک بار `createCte(params)` را صدا می‌زند. Hook پیش‌فرض همان Consumer را برمی‌گرداند و امکان حفظ `.sql {}` و `.details {}` روی همان invocation را می‌دهد. ساخت Consumer SQL را اجرا نمی‌کند؛ مسیر executor، binding، materialization و بستن منابع دست‌نخورده می‌ماند.

**بررسی بعدی:** بلافاصله پس از این فاز فقط compile source ماژول CTE/executor اجرا می‌شود؛ compile/test کامل تست‌ها تا فاز ۳ به تعویق می‌افتد چون call-siteهای خام و overrideهای قدیمی هنوز مهاجرت نشده‌اند. در فاز ۳، تست‌های create/execute counter، failure پیش از اجرا، Query failure، mapping failure، row order، empty، Success(null)، callbackها و مدیریت منابع اجرا می‌شوند.

**معیار پذیرش:** دقیقاً یک create و یک execution برای هر invocation؛ Query failure بدون remap عبور می‌کند؛ mapper در اولین `Exception` متوقف می‌شود و cause/ردیف 1-based حفظ می‌شود؛ collection ناقص موفق نمی‌شود؛ خطای synchronous ساخت/hook مرز فعلی خود را حفظ می‌کند.

**تأیید لازم:** مجوز شروع فاز و مجوز جداگانهٔ اجرای build/test.

### فاز ۳ — مسیر خام و مرز سازگاری

A1 از قبل `QueryConsumer.execute()` دارد و در این فاز typed نمی‌شود. مثال `CteExecutionExampleV31` و `ManagerExampleV31` typed باقی می‌مانند.

**بررسی بعدی:** compile/test هدفمند CTE و تست‌های executor مربوط به raw row؛ مقایسهٔ aliasها، ترتیب، dependencyها و binding order؛ هیچ assertion خام حذف نمی‌شود.

**معیار پذیرش:** `CteDeclaration.execute(queryManager, params)` فقط `ExecuteResult<ICollection<Self>>` برمی‌گرداند و از mapper typed استفاده می‌کند؛ `QueryConsumer.execute/first` خام باقی می‌مانند؛ callbackها روی همان Consumer هستند و QueryRow تغییر نمی‌کند.

**تأیید لازم:** مجوز شروع فاز و مجوز جداگانهٔ build/test.

**معیار پذیرش:** هیچ declaration پارامتر را در state نگه نمی‌دارد؛ هر typed row مستقل است؛ نتیجه/خطا در لایهٔ caller نمایش داده می‌شود؛ aliases و رفتار هر مثال بدون تغییر ناخواسته‌اند؛ raw callers صریح‌اند.

### فاز ۵ — regression integration، API visibility و اسناد

**فایل‌ها/ماژول‌ها:** تست‌های CTE، builder، renderer، executor و example؛ consumer compile fixture ایزوله با تنها dependency مستقیم `:data_base:query:cte` برای gate انتشار. پیکربندی فعلی `data_base/query/cte/build.gradle.kts` از `java-library` و dependencyهای عمومی `api` استفاده می‌کند؛ consumer compile طبق گزارش موجود موفق بوده، اما فرمان و لاگ کامل برای بازبینی مستقل در دسترس نیست. `TypedQueryConsumerApiCompileFixture.kt` در example به‌تنهایی gate نیست، چون example خودش executor را مستقیم وابسته دارد. اسناد `plans/executer/exist.md` و `plans/executer/visision.md` فقط در صورتی تغییر می‌کنند که مهاجرت اسناد در محدودهٔ release جداگانه مجاز شود.

**دامنه و رفتار:** regression مسیر inline در برابر WITH، metadata، aliasها، binding order، typed/raw results و قراردادهای قدیمی. consumer fixture باید یک declaration کوچک با mapping واقعی بسازد و امضاهای عمومی typed را با `IQueryBuilderExecutor`, `ExecuteResult`, `ICollection` و `QueryRow` مصرف کند؛ executor، collection، manager execute و query API dependency مستقیم consumer نیستند. consumer compile با این شرط طبق گزارش موجود موفق شده است. چون لاگ کامل و تعریف دقیق اجرای fixture در دسترس نیست، پیش از اعلام نهایی release باید شواهد اجرای مستقل قابل‌بازتولید ثبت شود؛ این کار به‌معنای بازگشایی تصمیم dependency یا اقدام Gradle آینده نیست.

**بررسی بعدی:** compile consumer check، تست‌های module-level و integration متناسب با موارد تغییرکرده؛ هیچ تستی برای عبور صرفاً تضعیف نمی‌شود.

**معیار پذیرش:** consumer compile با تنها dependency مستقیم CTE موفق باشد و فرمان/خروجی آن در گزارش validation ثبت شود؛ نتیجهٔ موفق فعلی گزارش شده، اما شواهد کامل آن در سابقهٔ قابل‌دسترسی این سند موجود نیست. تمام semantics جدول بخش ۹ باید پوشش داشته باشند و اسناد تغییرکرده با API نهایی هم‌خوان باشند.

**تأیید لازم:** تغییر dependencyهای فعلی اعمال شده‌اند و این پلن آن‌ها را به‌عنوان کار آینده یا تغییری مشروط به شکست gate معرفی نمی‌کند. هر تغییر تازه در build پس از مشاهدهٔ شکست مشخص، با شواهد و دامنهٔ دقیق بررسی می‌شود؛ ویرایش اسناد موجود خارج از این پلن همچنان مجوز جداگانه می‌خواهد.

## ۱۱. فایل‌ها/قراردادهایی که خارج از scope باقی می‌مانند

- `QueryRow`, `IQueryBuilderExecutor` و JDBC/materializer: بدون تغییر مگر مانع اثبات‌شده.
- `QueryConsumer.execute()`, `first()`, `executeAs`, `sql()` و `details()`: قراردادشان حفظ می‌شود. `sql()` و `details()` no-arg همچنان مقدار برمی‌گردانند؛ فقط callback overloadها همان Consumer را برمی‌گردانند.
- `ICteDeclaration<P>`: generic arity و امضای `createCte(params)` حفظ شده‌اند؛ نسبت به `HEAD`، `val params: P` حذف و `operator fun invoke(params)` اضافه شده است، پس interface بدون تغییر نمانده است. Self فقط در `CteDeclaration` است.
- Collection API: عملیات تازه یا تغییر semantics ندارد. `ICollection` از API عمومی CTE با `api(project(":collection:core"))` منتشر می‌شود؛ این dependency بخشی از پیکربندی فعلی است و دیگر اقدام مشروط آینده نیست.
- DML INSERT/UPDATE/DELETE و mutation consumers: خارج از دامنه.
- CTE parameter storage، API قدیمی `cte(declaration)` و constructor پارامترپذیر: بازگردانده نمی‌شوند.
- Reflection/annotation mapping، constructor discovery و setter mapping فقط برای CTE row mapper توصیف‌شده در §۴ داخل scope هستند؛ reflection برای بازسازی/اجرای Query یا اثبات رابطهٔ CRTP استفاده نمی‌شود. `firstAs` و گسترش mapping خودکار به `QueryConsumer`/`QueryRow` خارج از محدوده‌اند.

## ۱۲. تصمیم‌های قطعی و تأییدهای باقی‌مانده

تصمیم‌های معماری زیر تأیید شده‌اند و هنگام اجرا دوباره به‌عنوان گزینهٔ باز مطرح نمی‌شوند:

1. `CteDeclaration.execute(queryManager, params)` typed است و `ExecuteResult<ICollection<Self>>` برمی‌گرداند. اجرای خام فقط از `QueryConsumer.execute()` و `QueryConsumer.first()` در سطح consumer در دسترس است؛ ناسازگاری منبعیِ تغییر return type پذیرفته شده و call-siteهای خام باید به مسیر consumer مهاجرت کنند.
2. Base از `protected open fun configureConsumer(consumer: QueryConsumer): QueryConsumer` برای حفظ `.sql {}` و `.details {}` روی همان Consumer استفاده می‌کند. `UserDisplayQueryV31` دیگر execution را override نمی‌کند؛ success/error handling به caller یا wrapper منتقل می‌شود.
3. `ICteDeclaration<P>` پارامتر را به‌عنوان state نگه نمی‌دارد؛ `createCte(params): Cte` باقی است. نسبت به `HEAD`، `val params: P` حذف و `operator fun invoke(params)` اضافه شده است. این تغییر باید در بررسی سازگاری API ثبت شود و نباید interface را بدون تغییر معرفی کرد؛ Self فقط generic دوم base است.
4. fixture بدون output model mapping ساختگی نمی‌گیرد؛ fixture declaration-only از `ICteDeclaration` استفاده می‌کند و typed fixture باید mapping واقعی داشته باشد یا تست آن پیش از mapping متوقف شود.
5. A1 روی مسیر خام `QueryConsumer.execute()` می‌ماند چون aliasهای SQL آن با `UserPhoneQueryV3.fromQueryRow` یکی نیستند. alias یا mapping برای عبور از کامپایل تغییر نمی‌کند.
6. محدودیت CRTP پذیرفته‌شده است: bound به‌تنهایی exact runtime class را تضمین نمی‌کند. reflection موجود فقط برای کشف metadata و constructor/setter mapping در `CteQueryRowMapper` است و برای اثبات `Self` یا ساخت/اجرای Query استفاده نمی‌شود؛ compile/type tests نیز قرارداد generic را بررسی می‌کنند.
7. visibility انواع عمومی از CTE با `java-library` و dependencyهای `api` در `data_base/query/cte/build.gradle.kts` پیکربندی شده است؛ builder و `kotlin-reflect` همچنان `implementation` هستند. consumer مستقل با تنها dependency مستقیم CTE طبق گزارش موجود کامپایل موفق داشته است، اما لاگ و فرمان کامل در دسترس نیستند و برای اثبات قابل‌بازتولید باید ثبت شوند. این وضعیت تصمیم dependency را به اقدام آینده یا شکست احتمالی مشروط نمی‌کند.

**تأییدهای باقی‌مانده:** تصمیم معماریِ باز وجود ندارد. برای شروع هر فاز اجرایی و برای اجرای build/test مجوز جداگانه لازم است. dependencyهای فعلی CTE از قبل به‌روزرسانی شده‌اند؛ ثبت فرمان و خروجی کامل consumer compile در شواهد نهایی باقی است. هر تغییر جدید در Gradle باید بر اساس شواهد مشخص بررسی شود.

## ۱۳. ریسک‌ها و محدودیت‌ها

- افزایش arity generic و تغییر خروجی `execute` source compatibility را می‌شکند: call-siteهای `List<QueryRow>` و overrideهای خام باید مهاجرت کنند؛ جست‌وجوی فعلی inventory در بخش ۷ ثبت شده و ابتدای پیاده‌سازی دوباره اجرا می‌شود.
- `ExecuteResult.Success` payload nullable است؛ typed `Success(null)` باید از empty Collection متمایز و با پیام Failure فعلی مدیریت شود.
- شکست mapper پس از materialization رخ می‌دهد؛ ResultSet باید پیش‌تر بسته شده باشد و مدل نباید resource زنده نگه دارد.
- mapper فعلی تنها `Int`, `Long`, `String` را با نوع دقیق runtime می‌پذیرد؛ property باید `var` دارای setter عمومی و نوع خروجی سازندهٔ بدون پارامتر داشته باشد. افزودن نوع‌ها یا coercion جدید نیازمند تصمیم و تست مستقل است.
- `executeAs` فقط mapper `Exception` را می‌گیرد؛ mapper `Error` در Failure row-context wrap نمی‌شود. این قرارداد فعلی است و گسترش catch به `Throwable` تصمیم جداگانه می‌خواهد.
- CRTP رابطهٔ generic را محدود می‌کند، ولی `Self` دقیقاً همان concrete runtime class را تضمین نمی‌کند؛ هر concrete declaration باید در compile/type test پوشش داده شود.
- callbackهای UserDisplay باید از hook به همان Consumer منتقل شوند؛ handlerهای success/error بخشی از result API base نمی‌شوند و در caller باقی می‌مانند.
- A1 خروجی‌هایی با alias متفاوت از `UserPhoneQueryV3.fromQueryRow` دارد؛ این ناسازگاری عامدانه با حفظ raw route مدیریت می‌شود.
- CTE با `java-library` تنظیم شده و dependencyهای عمومی لازم را با `api` منتشر می‌کند؛ `:data_base:query:builder` و `kotlin-reflect` در `implementation` هستند. consumer compile مستقل با تنها dependency مستقیم CTE موفق گزارش شده، اما چون فرمان و لاگ کامل در دسترس نیست، این بازبینی جزئیات آن را مستقلاً تأیید نمی‌کند.
- اسناد موجود V3 ممکن است نمونه‌های تاریخی با constructor پارامترپذیر یا `cte(declaration)` داشته باشند؛ آن‌ها منبع حقیقت برای پیاده‌سازی جدید نیستند و باید پس از تصمیم نهایی sync شوند.

## ۱۴. جمع‌بندی وضعیت

مسیر typed در `QueryConsumer` و `ICollection` موجود است و mapper metadata-based در CTE از annotationها، reflection محدود و `QueryRow` materialize‌شده استفاده می‌کند. API v4 در این پلن مشخص شده: base هر invocation را با params صریح آماده می‌کند، hook را روی Consumer واحد اعمال می‌کند، و همان Consumer را یک‌بار در مسیر typed اجرا می‌کند؛ اجرای خام در سطح `QueryConsumer` می‌ماند. هیچ mapping موازی JDBC یا تغییر ذاتی materializer لازم نیست. مهاجرت شامل ۸ declaration تولیدی، callers و fixtures فهرست‌شده، مسیرهای خام QueryConsumer، callbackهای UserDisplay و consumer visibility gate است.

پس از Phase 0، مانع معماریِ نیازمند تصمیم باقی نمانده است. محدودیت CRTP و breaking change ثبت شده و پذیرفته‌اند. consumer compile مستقل با تنها dependency مستقیم CTE موفق گزارش شده است؛ برای پروندهٔ قابل‌بازتولید validation باید فرمان، پیکربندی fixture و خروجی کامل ثبت شود. این نسخهٔ سند طرح اجرا را مشخص می‌کند و مجوز شروع هیچ فاز یا اجرای build/test نیست.
