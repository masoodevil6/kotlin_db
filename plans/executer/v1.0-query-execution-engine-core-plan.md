# Executor Plan 1.0: Query Execution Core

## Status

**Implementation Ready** — معماری و قرارداد رفتاری این scope در سند بسته شده‌اند. این status به معنی اجرای implementation یا پاس‌شدن تست‌ها نیست؛ آن دو در مرحلهٔ بعد انجام می‌شوند.

## Objective

Execution Core واقعی repository را حفظ کنیم و با کمترین اصلاح رفتاری، پارامترها، callbackها، منابع JDBC، INSERT و DDL را قطعی کنیم. این Plan مجوز implementation نیست؛ در این مرحله فقط خود Plan به‌روزرسانی شده است.

اصل تصمیم:

```text
Repository Evidence
        ↓
Interpretation
        ↓
Contract Decision
        ↓
Minimal Implementation Scope
```

قراردادهای پایین که مستقیماً از source یا callsite ثابت نمی‌شوند، تصمیم‌های هنجاری و حداقلی این Plan هستند؛ با evidence تجربی اشتباه گرفته نشده‌اند.

## Repository Evidence

- مسیر اصلی فعال: Query API → `IQueryBuilderExecutor.executeOut` → Dialect render → `BuiltQuery` → `IQueryExecute` / `QueryExecute` → `DatabaseConnection` / JDBC → `ExecuteResult` callback.
- `IQueryExecute` در `data_base/manager/execute/.../IQueryExecute.kt` مسئول آماده‌سازی نام پارامترها، ایجاد connection و bind helper است. `QueryExecute.kt` پیاده‌سازی select/update/insert/delete/DDL است.
- `BuiltQuery.kt` در `data_base/core/.../query/reader` SQL nullable، فهرست mutable از `SqlParameter`، regex فعلی `:([a-zA-Z_][a-zA-Z0-9_]*)` و جایگزینی named tokenها را دارد.
- پارامترهای DSL در `QueryConditionsBuilder`, `QueryConditionsCollectionBuilder`, `QueryColumnUpdateBuilder`, و `QueryColumnInsertBuilder` ساخته می‌شوند. `sideValue(paramName, value)` از نام صریح استفاده می‌کند، بنابراین DSL می‌تواند یک نام را بیش از یک بار تولید کند؛ collection نام‌های suffixدار می‌سازد.
- `MigrationExecutor` نیز یک BuiltQuery مستقیم با دو نام متفاوت و هر نام یک‌بار می‌سازد. نمونه‌های بررسی‌شده نام‌های مجزا دارند؛ تست مستقیم binding برای mismatch/تکرار پیدا نشد.
- `SqlParameter.bind` در `SqlParamData.kt` فعالانه فراخوانی نمی‌شود. آن متد null را با `setNull(index, sqlType)` و مقدار غیر null را با `setObject(index, value, sqlType)` bind می‌کند. `readyParamsInQuery` binder فعال فعلی است.
- `SqlTypeResolver` مقادیر `Int`, `Long`, `Double`, `Float`, `Boolean`, `String`, `LocalDate`, `LocalTime`, `LocalDateTime`, `Instant`, null و سایر انواع را به JDBC Types نگاشت می‌کند. binder فعال Long را به `Int` cast می‌کند و برای java.time به کلاس‌های `java.sql` cast می‌کند.
- `manager:connection` از `mysql:mysql-connector-java:8.0.33` استفاده می‌کند. منبع این dependency وجود دارد؛ رفتار همهٔ نوع‌ها در driver با تست binding اختصاصی فعلی verify نشده است.
- SELECT callback درون scopeهای `PreparedStatement.use` و `Connection.use` اجرا می‌شود. مصرف‌کننده‌های مستقیم مشاهده‌شده (`getDatabaseServerInfo`, مثال‌های query, `SystemMigrationReader`, `MigrationExecutor`) ResultSet را داخل callback می‌خوانند و می‌بندند. Fake ResultSetهای migration نیز به شکل synchronous به callback تحویل می‌شوند.
- INSERT موفق، generated key را به صورت Long تحویل می‌دهد. صفر affected rows callback ندارد؛ شاخهٔ generated key خالی Failure می‌سازد اما آن را callback نمی‌کند.
- `executeTable` مقدار `Statement.execute()` را نادیده می‌گیرد و در نبود exception `Success(true)` می‌دهد. شواهد `Success(false)` در migration مربوط به نتیجهٔ سطح بالاتر operation هستند، نه producer مستقیم `IQueryExecute.executeTable`.
- Gradle/import: `query:executor → manager:execute → manager:connection/core`. وابستگی معکوس `manager:execute → query:executor` وجود ندارد.

## Existing Execution Architecture

Execution Core در `data_base/manager/execute` مستقر است. API و implementation موجود responsibility لازم برای prepare/bind/execute/result callback را دارند. تفاوت میان type binding و placeholder mapping با توابع همین ماژول قابل نگه‌داری است؛ شواهدی برای Engine موازی یا abstraction جدید وجود ندارد.

## IQueryExecute Analysis

`IQueryExecute` operation API عمومی را نگه می‌دارد: `executeSelect`, `executeUpdate`, `executeInsert`, `executeDelete`, `executeTable`. متد `execute` connection و خطای operation را هماهنگ می‌کند؛ `readyParamsInQuery` اکنون بر اساس نام distinct، index تعیین می‌کند.

**Interpretation:** interface و helper فعلی کافی‌اند، اما catch فعلی SQL exception را دور callback گرفته و می‌تواند callback را دوباره invoke کند. Validation و occurrence mapping را می‌توان در همین مسیر موجود اصلاح کرد.

**Decision:** signature متدهای عمومی حفظ شود. `readyParamsInQuery` نقش mapping نام/occurrence به JDBC index را نگه دارد؛ primitive نوشتن یک مقدار به index از `SqlParameter.bind` استفاده کند.

## QueryExecute Analysis

`QueryExecute` عملیات JDBC را در statement scope اجرا و result را به callback می‌دهد. INSERT دارای terminal branch ناقص است. Callback داخل try/catch بیرونی SQLException است و callback-thrown SQLException با JDBC exception اشتباه گرفته می‌شود.

**Decision:** اصلاحات محدود در همین implementation انجام شود. Renderer، Dialect و AST وارد JDBC layer نشوند.

## BuiltQuery Analysis

Regex فعلی برای تشخیص token نام‌دار، occurrenceها را به ترتیب متن پیدا می‌کند؛ اما `getListParamNames()` با set نام‌ها را deduplicate می‌کند و جایگزینی تکراری/نام‌های پیشوندی را با چند `String.replace` انجام می‌دهد.

**Decision:** قرارداد placeholder فقط برای tokenهای مطابق regex فعلی است؛ SQL parse/classify نمی‌شود. جایگزینی باید یک‌بار و occurrence به occurrence، از چپ به راست، انجام شود تا `:id` به اشتباه بخشی از `:id2` را تغییر ندهد. تفسیر placeholder داخل literal/comment خارج از scope است و رفتار regex فعلی تا تغییر جداگانه حفظ می‌شود.

## Parameter Binding Analysis

### Repository Evidence

- `SqlParameter.bind` no-callsite دارد ولی type-binding لازم را در یک index انجام می‌دهد.
- `readyParamsInQuery` هم mapping name/index و هم setter switch را انجام می‌دهد؛ این دو مسئولیت مستقل‌اند.
- Resolver نگاشت‌های مورد انتظار را مشخص کرده است: Int→INTEGER, Long→BIGINT, Double→DOUBLE, Float→FLOAT, Boolean→BOOLEAN, String→VARCHAR, LocalDate→DATE, LocalTime→TIME, LocalDateTime/Instant→TIMESTAMP, null→NULL, سایر→OTHER.
- setterهای فعال با Long/BIGINT و java.time ناسازگارند. `SqlParameter.bind` از `setObject(value, sqlType)` استفاده می‌کند و برای null، همان `sqlType` پارامتر را حفظ می‌کند.

### Interpretation

API عمومی `SqlParameter.of` و resolver، نوع‌های بالا را به عنوان نوع‌های قابل‌ارسال معرفی می‌کنند؛ این‌ها صرفاً mapping مرده نیستند، هرچند callsite جاری برای همهٔ آن‌ها یافت نشد. JDBC driver رفتار اجرایی را باید با تست contract پوشش دهد؛ source به تنهایی اثبات runtime نیست.

### Decision

`SqlParameter.bind` primitive canonical برای نوشتن یک parameter در یک 1-based JDBC index است. `readyParamsInQuery` فقط occurrence و index را resolve می‌کند و برای هر occurrence، parameter متناظر را با `bind` می‌نویسد. `setObject(index, value, sqlType)` برای مقادیر non-null و `setNull(index, sqlType)` برای null contract است. `Types.OTHER` نیز از همین مسیر استفاده می‌کند.

مقادیر supported همان انواع صریح `SqlTypeResolver` هستند. `Long` باید BIGINT باقی بماند و هیچ cast به Int مجاز نیست. java.time مستقیم با SQL type متناظر bind می‌شود؛ تبدیل به کلاس java.sql در Execution Core contract نیست. اگر MySQL driver برای یکی از این مقادیر آن binding را نپذیرد، تست باید شکست را آشکار کند و اصلاح در همین primitive/type mapping انجام شود، نه با binder abstraction تازه.

## ExecuteResult Analysis

`ExecuteResult.Failure(Throwable)` و `Success<T>` result channel عمومی موجودند. API امضای INSERT را `ExecuteResult<Long>` تعریف می‌کند؛ بنابراین generated key با Long حفظ می‌شود. APIهای update/delete نتیجهٔ affected rows را به صورت Int حفظ می‌کنند. DDL Boolean معنای مستقل خود را در قرارداد پایین می‌گیرد.

## Parameter Binding Contract

- هر execution برای هر JDBC placeholder occurrence حداکثر یک بار bind انجام می‌دهد.
- bind خطای SQLException را به execution failure بدل می‌کند؛ callback مصرف‌کننده دوباره اجرا نمی‌شود.
- null با sqlType ثبت‌شدهٔ `SqlParameter` bind می‌شود. برای null بدون type، `SqlTypeResolver` فعلی `Types.NULL` می‌دهد.
- نوع‌های پشتیبانی‌شده و JDBC type آن‌ها مطابق `SqlTypeResolver` است. `Types.OTHER` با `setObject(index, value, Types.OTHER)` bind می‌شود.

## Parameter Occurrence Contract

Binding بر اساس **placeholder occurrence** است، نه distinct parameter name.

- tokenها با grammar فعلی `:name` تشخیص داده می‌شوند و occurrence order از چپ به راست است.
- هر occurrence یک JDBC `?` و یک index متوالی از 1 دارد.
- `:id ... :id` با یک parameter object به نام `id` دو بار و به indexهای 1 و 2 bind می‌شود.
- چند parameter object با یک name تنها وقتی معتبرند که همگی `value` و `sqlType` برابر داشته باشند؛ یک مقدار canonical برای تمام occurrenceهای آن name استفاده می‌شود. هم‌نام با value یا sqlType متفاوت invalid است.
- parameter name بدون placeholder، placeholder بدون parameter، duplicate name متناقض، یا extra/unused parameter، mismatch است.
- empty parameter list معتبر است اگر و تنها اگر query هیچ placeholder مطابق grammar نداشته باشد.
- هر mismatch، `IllegalArgumentException` همزمان و پیش از connection acquisition می‌دهد؛ database callback اجرا نمی‌شود. این انتخاب به‌جای وابستگی به رفتار driver تعیین شده تا failure قطعی و بدون query side effect باشد.
- Regex-based token grammar retained است؛ SQL string/comment lexical parsing و SQL classification اضافه نمی‌شوند.

## Null/Blank Query Contract

- `BuiltQuery(null, params)`: رفتار فعلی حفظ می‌شود؛ connection acquisition ابتدا رخ می‌دهد، سپس query operation callback یک بار با `ExecuteResult.Failure(IllegalArgumentException)` دریافت می‌کند؛ statement ساخته نمی‌شود. Connection acquisition exception خودش synchronous propagate می‌شود و callback ندارد.
- `BuiltQuery("", params)` و whitespace-only query: trim/prevalidation اضافه نمی‌شود؛ query به JDBC prepare می‌رسد. SQLException از prepare به یک Failure callback تبدیل می‌شود. نتیجهٔ دقیق متن SQLException به driver وابسته است.
- render-null در `IQueryBuilderExecutor.executeOut` همچنان پیش از JDBC به صورت `IllegalStateException` synchronous رد می‌شود. این با direct `IQueryExecute` برابر نیست چون اولی خطای rendering است و دومی BuiltQuery input است.
- هیچ‌یک از مسیرها یک callback را بیش از یک بار invoke نمی‌کند. Query-info callback پیش از اجرا باقی می‌ماند و exception آن synchronous propagate می‌شود؛ database result callback اجرا نمی‌شود.

## ResultSet Ownership Contract

ResultSet به callback داده می‌شود و فقط تا پایان همان callback معتبر است. Caller موظف است درون callback آن را consume و close کند؛ Executor ResultSet را مستقلاً close نمی‌کند، اما Statement و Connection را در scope خود می‌بندد. نگه‌داری ResultSet پس از callback پشتیبانی نمی‌شود.

اگر callback هنگام `ResultSet.close()` یا هر عملیات مصرفی SQLException/non-SQL exception پرتاب کند، آن exception متعلق به caller callback است: به caller propagate می‌شود و execution callback دوباره invoke نمی‌شود. Statement و Connection همچنان طبق `use` بسته می‌شوند؛ close exceptionهای بعدی به قواعد Resource Lifecycle رجوع می‌کنند.

## INSERT Result Contract

- `affectedRows > 0` و یک generated key قابل خواندن: یک `Success<Long>` با مقدار key؛ affected rows هرگز به جای key برگردانده نمی‌شود.
- `affectedRows == 0`: یک `Failure(IllegalStateException)` callback؛ callback حذف نمی‌شود.
- `affectedRows > 0` و generated key خالی: یک `Failure(IllegalStateException)` callback؛ ساختن Failure بدون تحویل ممنوع است.
- affected rows null: در صورت رخ‌دادن، یک Failure callback؛ این حالت در concrete مسیر فعلی قابل‌دستیابی نیست، اما terminal behavior تعریف شده است.
- generated key retrieval SQLException: یک Failure callback.
- generated-key ResultSet close failure پیش از terminal callback: یک Failure callback، بدون Success قبلی.
- برای هر INSERT یک terminal callback حداکثر یک‌بار invoke می‌شود. Callback-thrown exception propagate می‌شود و callback retry نمی‌شود.

## DDL Result Contract

`ExecuteResult.Success(true)` معنی دقیق «DDL اجرا بدون exception گزارش‌شده تکمیل شد» را دارد. Boolean برگشتی از `Statement.execute()` وارد API نمی‌شود. Producer مستقیم `Success(false)` در Execution Core contract نیست؛ booleanهای MigrationExecutor operation-level باقی می‌مانند و مستقل‌اند. DDL failure یک `ExecuteResult.Failure` است.

## Exception and Callback Contract

اصل عمومی: هر execution callback حداکثر یک بار invoke می‌شود. خطای consumer هرگز به execution Failure callback تبدیل و همان callback دوباره invoke نمی‌شود. exception بلعیده نمی‌شود.

| Boundary | Current behavior | Desired contract |
| --- | --- | --- |
| connection acquisition | `DatabaseConnection.build()` exception را پیش از operation callback propagate می‌کند، معمولاً به صورت RuntimeException. | synchronous propagation؛ callback صفر بار چون connection و execution وجود ندارد. |
| `prepareStatement` | SQLException به outer helper catch می‌رسد و operation block دوباره اجرا می‌شود. | یک Failure callback؛ هیچ operation retryای رخ نمی‌دهد. |
| parameter binding | SQLException catch می‌شود؛ type cast exception ممکن است runtime propagate کند. | SQLException یک Failure callback؛ invalid parameter contract پیش از connection، sync `IllegalArgumentException`. |
| `executeQuery` | SQLException به همان callback-capable block catch می‌رسد. | یک Failure callback. |
| `executeUpdate` | SQLException به همان مسیر می‌رسد. | یک Failure callback. |
| generatedKeys retrieval | SQLException به outer helper می‌رسد؛ no-key اکنون callback ندارد. | retrieval/empty result یک Failure callback، یک terminal invocation. |
| callback body | SQLException می‌تواند همان execution block را دوباره وارد کند؛ runtime exception propagate می‌شود. | هر throwable از consumer synchronous propagate؛ callback retry یا Failure callback دوم ندارد. |
| `ResultSet.close` | consumer-side SQLException داخل callback و outer SQL catch قرار می‌گیرد. | consumer exception propagate، بدون re-entry؛ ownership caller است. |
| `Statement.close` | `use` close exception ممکن است پس از callback success، outer catch را وارد و callback را تکرار کند. | close exception propagate می‌شود؛ قبلی callback دوباره invoke نمی‌شود. |
| `Connection.close` | close exception خارج از inner SQLException catch propagate می‌شود. | synchronous propagation، callback retry ندارد. |

برای INSERT خطای generated-key close پیش از terminal callback، پس از شناسایی نتیجه و قبل از تحویل callback مدیریت می‌شود. در SELECT callback برای زنده‌بودن ResultSet ناگزیر در resource scope اجرا می‌شود؛ بنابراین close شکست‌خورده پس از callback از همان call stack propagate می‌شود و callback دوم نمی‌گیرد.

## Resource Lifecycle Contract

- Executor connection را برای هر operation می‌گیرد و با `use` می‌بندد.
- Executor statement را پس از operation و با `use` می‌بندد.
- SELECT ResultSet در اختیار caller است و درون callback بسته می‌شود.
- generated-key ResultSet در Execution Core بسته می‌شود.
- close exception هیچ‌گاه swallow نمی‌شود. اگر پیش از terminal callback رخ دهد، Failure تحویل می‌شود؛ اگر پس از callback رخ دهد، synchronous propagate می‌شود و callback دوباره فراخوانی نمی‌شود.
- Pool، transaction، retry، cache، batch و async lifecycle وارد scope نیستند.

## Query Type Dispatch

Typed query/executor API از قبل operation مشخص را dispatch می‌کند. SQL دوباره parse/classify نمی‌شود؛ CRUD و DDL methodهای موجود حفظ می‌شوند.

## Dependency Direction

Dependency واقعی Gradle/import:

```text
query:executor → manager:execute → manager:connection + core
```

`manager:execute` به executor، AST، Dialect، Model یا Migration وابسته نمی‌شود. این جهت حفظ می‌شود؛ Query Builder همچنان بدون تغییر API عمومی از `IQueryExecute` قابل استفاده است.

## Architecture Candidates

| Candidate | Repository Evidence → Interpretation | Decision |
| --- | --- | --- |
| A. Existing `IQueryExecute`, `QueryExecute`, `DatabaseConnection`, `BuiltQuery`, `ExecuteResult` | این‌ها هم‌اکنون path فعال و owner واقعی JDBC هستند؛ نقص‌ها در همین binding/terminal/error branches قابل اصلاح‌اند. | **Adopt**؛ انتخاب نهایی. |
| B. Existing core + small internal abstraction | هیچ responsibility اثبات‌شده‌ای وجود ندارد که در A قابل بیان نباشد. | **Reject for this scope**؛ abstraction جدید لازم نیست. |
| C. Move core to `query:executor` | executor هم‌اکنون به manager وابسته است؛ انتقال مالکیت dependency معکوس می‌سازد. | **Reject**؛ شواهد معماری مؤیدش نیست. |

## Decision Matrix

| موضوع | Evidence | Contract decision |
| --- | --- | --- |
| Core owner | `QueryExecute` implementation فعال در `manager:execute` | همان core حفظ شود. |
| Parameter positions | set فعلی occurrence را collapse می‌کند؛ DSL تکرار صریح نام را ممکن می‌کند | occurrence order، هر occurrence یک index. |
| Duplicate parameter objects | mutable list امکان چند object هم‌نام را می‌دهد | هم‌نام هم‌ارزش collapse مفهومی می‌شوند؛ تعارض sync reject می‌شود. |
| Mismatch | validation فعلی نیست | sync `IllegalArgumentException` پیش از اتصال. |
| Binder | `SqlParameter.bind` unused ولی type-aware است | canonical primitive؛ occurrence mapping جدا بماند. |
| Supported types | Resolver mapping صریح است؛ binder فعال با Long/java.time ناسازگار | Resolver type set normative؛ test driver-backed لازم است. |
| Null/blank | null و blank مسیر جاری متفاوت دارند | null Failure بعد از connection؛ blank JDBC prepare Failure؛ render-null sync exception. |
| ResultSet | consumerها داخل callback می‌خوانند/می‌بندند | caller-owned و callback-scoped. |
| INSERT | generated key Long؛ no-key branches ناقص | Long success؛ هر terminal failure callback دقیقاً یک بار. |
| Callback exceptions | SQLException مصرف‌کننده ممکن است re-entry دهد | exception consumer propagate؛ هیچ re-entry. |
| Close exceptions | بعضی closeها پس از callback رخ می‌دهند | propagate؛ callback دوباره invoke نشود. |
| DDL Boolean | execute return نادیده گرفته می‌شود؛ `Success(true)` صادر می‌شود | true=completed without reported error؛ JDBC boolean expose نشود. |
| Architecture | Gradle dependency direction یک‌طرفه است | Candidate A؛ B/C رد. |

## Final Contract

Execution Core همان `IQueryExecute` / `QueryExecute` در `data_base/manager/execute` است. `BuiltQuery` occurrence tokenهای مطابق grammar را به ترتیب متنی نگه می‌دارد؛ هر occurrence یک JDBC index می‌گیرد. Parameter mapping mismatch پیش از connection به synchronous `IllegalArgumentException` منتهی می‌شود. `SqlParameter.bind` تنها primitive type-binding است؛ `readyParamsInQuery` فقط name/value-to-occurrence mapping انجام می‌دهد.

Connection acquisition exception همزمان propagate می‌شود. بعد از acquisition، JDBC operation failure یک Failure callback می‌دهد؛ callback consumer exception propagate می‌شود و هیچ callback دوباره اجرا نمی‌شود. SELECT ResultSet caller-owned و callback-scoped است. INSERT success فقط generated key از نوع Long است؛ صفر row/empty key/retrieval failure به Failure می‌انجامد. DDL `Success(true)` یعنی completion بدون exception گزارش‌شده، نه مقدار JDBC `execute()`.

هیچ Engine، interface، mapper، execution context یا module جدید ایجاد نمی‌شود.

## Compatibility Contract

- امضاهای public موجود و `ExecuteResult` حفظ می‌شوند؛ dependency direction و `manager:execute` ownership تغییر نمی‌کند.
- String-based Query API، SQL rendering، dialect، AST و query type dispatch تغییر نمی‌کنند.
- SQLهای بدون mismatch و با انواع فعلی همان query و نتیجه را تولید می‌کنند؛ Long و java.time به جای cast نامعتبر با JDBC type متناظر bind می‌شوند.
- رفتارهای intentional جدید: parameter mismatch پیش از اتصال به‌صورت sync reject می‌شود؛ تکرار placeholder bind به ازای occurrence است؛ INSERT no-row/no-key به Failure callback ختم می‌شود؛ callback exception و post-callback close exception موجب callback re-entry نمی‌شوند.
- Null/blank behavior، generated-key Success<Long>، DDL Success(true) و migration operation Boolean مستقل حفظ می‌شوند.

## Compatibility

هیچ overload یا public API جدیدی لازم نیست. رفتار malformed/repeated SQL و INSERT terminal branches اصلاح می‌شود؛ این موارد قبلاً contract/test تثبیت‌شده نداشتند. مصرف‌کننده‌ای که callback را بیش از یک بار می‌دید به رفتار مشخص‌شده مهاجرت می‌کند؛ رفتار دوباره‌فراخوانی دیگر پشتیبانی نمی‌شود.

## Minimal Implementation Scope

### فایل‌هایی که احتمالاً تغییر می‌کنند

- `data_base/core/src/main/kotlin/query/reader/BuiltQuery.kt`: استخراج occurrenceها، replacement تک‌گذر و بررسی تناقض parameter names.
- `data_base/core/src/main/kotlin/query/reader/SqlParamData.kt`: در صورت نیاز فقط برای تضمین canonical type-binding contract موجود؛ API `SqlParameter` حفظ شود.
- `data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt`: occurrence-index mapping با فراخوانی `SqlParameter.bind` و جداسازی catch عملیات از callback.
- `data_base/manager/execute/src/main/kotlin/manager/QueryExecute.kt`: terminal callback کامل INSERT، خطای no-key/zero-row و callback/resource error boundaries.
- تست‌های unit/integration متمرکز در moduleهای `core` و `manager:execute`، با MySQL driver فعلی برای type-binding.

### فایل‌هایی که نباید تغییر کنند

- Query API، query AST، Renderer، Dialect، `query:executor` public API، `DatabaseConnection`، Migration API/Executor، Model، Example sourceها و Gradle dependency graph.
- `ExecuteResult` و signatureهای operation عمومی مگر اینکه implementation اثبات کند signature فعلی قابل تحقق نیست؛ این Plan چنین evidenceای ندارد.

### Preserve

`IQueryExecute` public operations، `ExecuteResult` shape، SQL rendering و named-token syntax موجود، generated-key `Long`, update/delete affected-row result، DDL `Success(true)`, callback-scoped SELECT access و dependency direction.

### اصلاح شود

Occurrence binding، mismatch detection، Long/java.time binding، INSERT terminal callbacks، callback exactly-once/re-entry و خطای resource close بدون swallow.

### تغییر نکند

Connection pooling، transaction management، retries، SQL classification/parsing، Renderer/Dialect ownership، DDL JDBC Boolean exposure، migration semantics، query DSL و module layout.

## Test Contract

تست‌ها را در implementation مرحله ایجاد/اجرا کن؛ در Traceability جاری هیچ تستی تغییر یا اجرا نشده است.

1. `BuiltQuery`: یکتا، تکراری، occurrence order، prefix-name collision (`:id` و `:id2`)، no placeholders, empty params، exact parameter mapping.
2. Mismatch: missing, extra/unused, duplicate identical, duplicate conflicting value, duplicate conflicting sqlType. Assert sync `IllegalArgumentException` و صفر connection acquisition/callback.
3. Binder: PreparedStatement test double بررسی `setObject(index,value,sqlType)` و `setNull(index,sqlType)` برای Int, Long, Double, Float, Boolean, String, LocalDate, LocalTime, LocalDateTime, Instant, OTHER, typed/untyped null.
4. Driver-backed MySQL integration: همین type matrix با `mysql-connector-java:8.0.33`; ثبت نتیجهٔ واقعی DATE/TIME/TIMESTAMP/Instant و BIGINT round-trip.
5. Null/blank: null BuiltQuery, empty, whitespace, render-null؛ تعداد callback و connection/prepare invocationها و thrown-vs-Failure دقیقاً مطابق contract.
6. ResultSet: callback درون statement lifetime، caller close، retention ممنوع قراردادی، consumer SQLException/RuntimeException بدون callback re-entry، close state.
7. INSERT: affectedRows 0, >0/key, >0/no key, generatedKeys retrieval/close error, statement/connection close error; assert Long key, Failure branches, max one callback, no swallowed exception.
8. Error boundary: connection acquisition, prepare, bind, query/update, callback body SQLException و RuntimeException، ResultSet/Statement/Connection close. Assert callback count/order و propagation.
9. DDL: `Statement.execute()` true/false هر دو به `Success(true)` در absence of exception؛ SQLException به Failure؛ Migration-level false behavior unchanged.
10. Regression: existing QueryExecutor/Migration tests و focused module builds پس از implementation.

## Implementation Sequence
