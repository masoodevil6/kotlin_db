# پلن نسخهٔ 3.0: خروجی typed برای Query Executor

## وضعیت سند

**وضعیت:** تصمیم معماری مربوط به ساخت Query بدون پارامتر، ورود صریح params و مدل‌بودن همان کلاس برای هر ردیف قطعی است و در این نسخه ثبت شده است. این سند برای بازبینی نهایی پلن ارائه می‌شود؛ شروع پیاده‌سازی همچنان به تأیید جداگانهٔ کاربر نیاز دارد.

این سند از سورس فعلی مخزن تهیه شده است. در این مرحله فقط اسناد معماری مرتبط به‌روزرسانی می‌شوند؛ هیچ source، تست، تنظیم Gradle یا فایل اجرایی پروژه تغییر نمی‌کند. هیچ build یا تستی نیز در زمان تدوین این پلن اجرا نشده است.

برای روشن‌بودن مرز شواهد، **وضعیت تأییدشده** به چیزی اشاره دارد که در سورس دیده شده است؛ تصمیم معماری بدون‌پارامتر بودن Query و ورودی صریح params قطعی است. موارد اجرایی مانند کامل‌بودن call-site inventory و انتشار Gradle باید در فاز پیاده‌سازی با آزمون مشخص شوند و اصل تصمیم را باز نمی‌کنند.

## ۱. خلاصهٔ اجرایی

هدف نسخهٔ 3.0 افزودن مسیر افزایشی SELECT typed با خروجی `ExecuteResult<ICollection<T>>` است. APIهای جاری `QueryRow`، `QueryConsumer.execute()/first()`، `IQueryBuilderExecutor`، callbackها، metadata، SQL و رفتار `INSERT/UPDATE/DELETE` حفظ می‌شوند. یک استثنای سازگاری‌شکنِ عمدی برای حذف state پارامتر از Query و CTE در بخش ۱۶ ثبت شده است؛ دامنه و مهاجرت آن محدود به قراردادهای CTE است.

تصمیم معماری قطعی: همان کلاس Query هم تعریف‌کنندهٔ Query و هم مدل هر ردیف خروجی است؛ DTO جداگانه وجود ندارد. نمونهٔ declaration بدون پارامتر ساخته می‌شود، مانند `val cte = UserStatsQueryV3()`. هیچ پارامتری در constructor یا state نمونهٔ Query ذخیره نمی‌شود. پارامتر فقط هنگام ساخت CTE به `createCte(params)` یا هنگام اجرای مستقیم به `execute(queryManager, params)` داده می‌شود.

برای هر ردیف خروجی، factory/mapper یک نمونهٔ تازه از همان Query class را با constructor بدون آرگومان می‌سازد و فقط propertyهای خروجی را مقدار می‌دهد. ساخت نمونه نباید query را اجرا کند، `createCte()` را فراخوانی کند یا AST اجرای query را بسازد. propertyهای خروجی getter واقعی و setter قابل‌استفاده دارند.

API typed همچنان `executeAs(mapper: (QueryRow) -> T): ExecuteResult<ICollection<T>>` است. نام‌گذاری CTE با `with(withName, cte(cteParams))` پشتیبانی می‌شود: `cte(cteParams)` از operator factory روی declaration استفاده می‌کند و یک `Cte` می‌سازد؛ پارامتر روی Query object ذخیره نمی‌شود.

## ۲. هدف‌ها و موارد خارج از محدوده

### هدف‌ها

- افزودن مسیر typed برای SELECT معمولی و CTE در کنار مسیر `QueryRow`.
- استفاده از همان Query class برای declaration و مدل هر ردیف؛ بدون DTO جداگانه.
- ساخت declaration بدون آرگومان و نگه‌نداشتن پارامترهای Query در state نمونه.
- دریافت پارامتر صریح در `createCte(params)`، `execute(queryManager, params)` و ساخت CTE در FROM/WITH.
- فراهم‌کردن شکل `with(withName, cte(cteParams))` با factory پارامتردار declaration.
- ساخت نمونهٔ مستقل و بدون پارامتر برای هر ردیف و مقداردهی صریح propertyهای خروجی.
- حفظ ترتیب ردیف، نتیجهٔ خالی، lifecycle منابع، SQL و رفتار materialization فعلی.
- حفظ APIهای قدیمی نامرتبط با مهاجرت CTE و مستندسازی دقیق ناسازگاری‌های اجتناب‌ناپذیر این مهاجرت.

### خارج از محدوده

- DTO مستقل از Query class به‌عنوان طراحی اصلی.
- حذف یا تغییر معنای `QueryRow`، `getValue(String)`، `getValue(KProperty1)`، APIهای عمومی `QueryConsumer` و `IQueryBuilderExecutor` نامرتبط با پارامترهای CTE.
- تغییر قراردادهای `INSERT/UPDATE/DELETE`، `ExecuteResult`، rendering، SQL یا composition CTE فراتر از تغییر ورودی صریح پارامترهای declaration.
- auto-mapping مبتنی بر reflection، constructor discovery یا setter discovery.
- نگهداری یا کپی پارامترها در Query instance؛ default یا پارامتر ساختگی.
- بازگرداندن `ICteDeclaration.params`، سازندهٔ `CteDeclaration(params)` یا `execute(queryManager)` بدون پارامتر؛ این شکل‌ها با تصمیم قطعی ناسازگارند و مهاجرتشان صریحاً در scope است.
- وابسته‌کردن `collection:core` به database/query/executor.
- افزودن `firstAs` یا Collection operation جدید.
- اجرای getterهای metadata-only برای resolve metadata؛ propertyهای typed output باید getter واقعی داشته باشند.

## ۳. وضعیت فعلی تأییدشده

### ۳.۱. ماژول‌ها و نسخه‌های ساخت

- `settings.gradle.kts` ماژول‌های `:data_base:query:executor`، `:data_base:query:cte`، `:data_base:query:example` و `:collection:core` را ثبت کرده است.
- Gradle Wrapper در `gradle/wrapper/gradle-wrapper.properties` روی Gradle `8.14` است.
- Version catalog در `gradle/libs.versions.toml` نسخهٔ Kotlin Gradle Plugin را `2.2.0` تعیین می‌کند.
- convention موجود `buildSrc/src/main/kotlin/kotlin-jvm.gradle.kts` و بسیاری از ماژول‌های query، `jvmToolchain(24)` را تنظیم می‌کنند. در اجرای قبلی خارج از این مأموریت، پیام fallback از Kotlin JVM target 24 به 22 دیده شده است؛ این سند آن را نتیجهٔ build فعلی تلقی نمی‌کند و اصلاح آن را هم به scope typed mapping اضافه نمی‌کند.

### ۳.۲. API فعلی SELECT و materialization

- `data_base/query/executor/src/main/kotlin/interfaces/IQueryBuilderExecutor.kt` مسیرهای `first(...)`، `get(...)` و `execute(...)` را دارد. `first` خروجی `ExecuteResult<QueryRow>` و `get` خروجی `ExecuteResult<List<QueryRow>>` را callback می‌کند.
- پیش از dispatch، `first` و `get` aliasهای خروجی را اعتبارسنجی می‌کنند و برای هر ستون SELECT وجود `ExecutionType` را لازم می‌دانند.
- در همین فایل، `materializeQueryRow(...)` ResultSet label را با `ColumnAlias` مقایسه می‌کند و مقدار را با `DataType.LONG`، `INT` یا `STRING` استخراج می‌کند. برای `INT` و `LONG` مقدار `wasNull()` نیز بررسی می‌شود.
- `get(...)` همهٔ ردیف‌ها را با ترتیب ResultSet به `List<QueryRow>` تبدیل می‌کند؛ نتیجهٔ بدون ردیف، فهرست خالی موفق است. `first(...)` در نبود ردیف، `Success(null)` می‌دهد.
- materialization در محدوده‌ای انجام می‌شود که ResultSet هنوز باز است؛ خود مسیر `first/get` ResultSet را با `use` می‌بندد. callback نهایی پس از materialization فراخوانی می‌شود.
- `data_base/query/executor/src/main/kotlin/result/QueryRow.kt` مقادیر را در `LinkedHashMap<String, Any?>` بر اساس SQL alias نگه می‌دارد. `getValue(String)` بر اساس alias می‌خواند. `getValue(KProperty1, outputKeyHint)` از mapping property-to-alias استفاده می‌کند، property انتخاب‌نشده را رد می‌کند و برای property تکرارشده hint می‌خواهد.
- `materializeQueryRow(...)`، `PropertyReference` ستون را با `ColumnAlias` به `QueryRow` می‌دهد. برای خروجی محاسباتی نیز `QueryColumnsBuilder.alias(property)` در سورس فعلی property reference و logical output name را ثبت می‌کند؛ استخراج نوع محاسباتی می‌تواند با `execute(DataType)` صریح شود.
- `data_base/query/executor/src/main/kotlin/result/QueryConsumer.kt`، `first()` و `execute()` را به executor متصل می‌کند؛ `sql()` و `details()` را مستقل در دسترس می‌گذارد. metadata از `EffectiveQueryMetadataProvider` استفاده می‌کند و در نبود آن از `EffectiveQueryMetadataAnalyzer` کمک می‌گیرد.
- `success` و `error` در `ExecuteResultFluentExtensions.kt` افزونه‌های روی `ExecuteResult` هستند. `success` نتیجهٔ غیر null را تبدیل می‌کند و Failure/null را حفظ می‌کند؛ استثنای transform را خودش به Failure تبدیل نمی‌کند.
- `QueryBuilderSelection` مسیرهای SELECT/INSERT/UPDATE/DELETE را انتخاب می‌کند. consumerهای mutation جدا از SELECT هستند و در این طرح هدف typed نیستند.

### ۳.۳. مسیر واقعی JDBC

- `data_base/query/executor/src/main/kotlin/manager/QueryBuilderExecutor.kt` SQL و پارامترها را رندر می‌کند؛ خروجی‌های legacy را به `BuiltQuery` و خروجی‌های identity-aware را به `BoundQuery` می‌فرستد.
- `data_base/manager/execute/src/main/kotlin/manager/QueryExecute.kt` و `interfaces/IQueryExecute.kt` مسئول connection، statement، bind و اجرای JDBC هستند. این لایه ResultSet را از طریق callback به لایهٔ بالاتر می‌دهد.
- SELECT ResultSet را در محدودهٔ statement/connection به consumer تحویل می‌دهد. مالکیت materialization typed باید در query executor باقی بماند تا هیچ مدل به ResultSet بسته‌شده وابسته نشود.
- `ExecuteResult` در `data_base/manager/execute/src/main/kotlin/tools/ExecuteResult.kt` یک `Success<T>(result: T?)` یا `Failure(Throwable)` است؛ nullable بودن payload بخشی از قرارداد فعلی است.

### ۳.۴. مدل‌ها و metadata

- `data_base/core/src/main/kotlin/managers/models/IModelBase.kt` یک interface خالی است و قرارداد constructor، getter یا setter تعریف نمی‌کند.
- annotationهای فعلی در `data_base/core/src/main/kotlin/annotations/models/` قرار دارند: `QBTable` و `QBQuery` برای کلاس، `QBColumn` و `QBQuerySelect` برای property؛ retention آن‌ها runtime است.
- `QBTable` فیلدهای `name` و `alias` دارد. `QBColumn` فیلدهای `name`، `alias` و `primaryKey` دارد. `QBQuery` و `QBQuerySelect` به‌ترتیب نام/alias تعریف query و نام منطقی/SQL alias خروجی را نگه می‌دارند.
- `ModelMetadataResolver` در `data_base/query/builder/src/main/kotlin/metadata/models/ModelMetadataResolver.kt` و `QueryMetadataResolver` در `.../metadata/queries/QueryMetadataResolver.kt` annotationها و conventionها را resolve می‌کنند. آن‌ها از annotation و metadata reflection استفاده می‌کنند و getter مقدار مدل را برای resolve کردن metadata فراخوانی نمی‌کنند.
- `QueryColumnsAstMetadata` در AST فیلدهای `PropertyReference`، `logicalOutputName`، `ColumnAlias` و `ExecutionType` را نگه می‌دارد. `ExecutionType` فعلی فقط `LONG`، `INT` و `STRING` را شامل می‌شود.
- `EffectiveQueryMetadata.outputs` فیلدهای logical name، SQL alias، execution type، table name و table alias را نگه می‌دارد؛ reference قابل نوشتن یا constructor metadata ندارد. این metadata برای گزارش‌دهی طراحی شده و نباید بدون نیاز به قرارداد عمومی mapper تبدیل شود.
- نسخهٔ Kotlin در version catalog `2.2.0` است، ولی `data_base:query:ast` و `builder` در حال حاضر `kotlin-reflect:1.8.20` را مستقیم اعلام می‌کنند. هماهنگی این dependency برای هر mapper مبتنی بر reflection باید پیش از افزودن dependency جدید ارزیابی و تست شود.

### ۳.۵. دو خانوادهٔ مدل و نمونه‌های فعلی

- `UserModelV31` مدل منبع جدول است و در نقش model با قرارداد Query declaration یکی نمی‌شود.
- Queryهای V3 و V3.1 در سورس فعلی constructorهای پارامترپذیر دارند؛ `UserStatsQueryV3` و `UserPageQueryV3` مستقیماً `ICteDeclaration<P>` را پیاده می‌کنند و برخی Queryها از `CteDeclaration<P>(params)` ارث می‌برند. این فقط وضعیت فعلی سورس است و با معماری مقصد قطعی سازگار نیست.
- در مقصد، همهٔ Query declarationها بدون پارامتر ساخته می‌شوند. برای Queryای که اجرای مستقیم لازم دارد، مانند `UserStatsQueryV3`، کلاس از `CteDeclaration<RelationFilters>()` ارث می‌برد؛ هیچ property پارامتری ندارد.
- `RelationFilters` فقط ورودی مستقل فراخوانی است. هر اجرای CTE یا Query، پارامتر خودش را به `createCte(params)` یا `execute(queryManager, params)` می‌دهد. پارامتر در declaration ذخیره نمی‌شود.
- خروجی‌های فعلی Query دارای `val` با getterهای `error(...)` هستند؛ خروجی typed باید propertyهایی با getter واقعی و امکان مقداردهی داشته باشد؛ در setter-based mapping از `var` با مقدار آغازین مناسب استفاده می‌شود.
- `QueryColumnsBuilder.alias(property)` همچنان مالکیت property را با همان Query class تطبیق می‌دهد؛ metadata و alias خروجی از قرارداد فعلی پیروی می‌کنند.
- `QBCte` و `QBCteSelect` از قرارداد `QBQuery` متمایزند و این تصمیم آن‌ها را یکی نمی‌کند.

### ۳.۶. CTE و Composition

- سورس فعلی `ICteDeclaration<P>` دارای `val params: P` و `createCte(params)` است. `CteDeclaration<P>(params)` مقدار params را در property نهایی نگه می‌دارد؛ تصمیم قطعی نسخهٔ 3.0 حذف این state است.
- قرارداد مقصد `ICteDeclaration<P>`، `createCte(params: P): Cte` را نگه می‌دارد، property پارامتر را حذف می‌کند و برای syntax پارامتردار declaration، `operator fun invoke(params: P): Cte = createCte(params)` را به‌صورت convenience فراهم می‌کند.
- `CteDeclaration<P>` constructor بدون آرگومان دارد. `queryReady(queryManager, params)` تعریف را با ورودی همان فراخوانی آماده می‌کند؛ `execute(queryManager, params)` از همین مسیر استفاده می‌کند و نتیجهٔ فعلی `ExecuteResult<List<QueryRow>>` را حفظ می‌کند.
- `IQueryTableApi.cte(declaration)` و پیاده‌سازی `QueryTableBuilder.cte(declaration)` در سورس فعلی از `declaration.params` استفاده می‌کنند. این overload بدون پارامتر حذف می‌شود؛ caller از `cte(declaration(params))` استفاده می‌کند که `Cte` می‌سازد و به overload موجود `cte(Cte)` می‌رسد. `cte(String)` نیز حفظ می‌شود؛ overload جدید `cte(declaration, params)` لازم نیست.
- `IQueryWithsItemApi.with(withName, cte: Cte)` از قبل موجود است. operator factory شکل قطعی `with(withName, declaration(params))` را ممکن می‌کند و composition فعلی CTE را حفظ می‌کند.
- برای اجرای مستقیم، `CteDeclaration.execute(queryManager)` بدون پارامتر قابل حفظ نیست؛ امضای مقصد `execute(queryManager, params)` است. `ICteDeclaration` به Executor وابسته نمی‌شود؛ Queryای که execution مستقیم می‌خواهد از base class مناسب استفاده می‌کند.
- ساخت `Cte` می‌تواند params را به‌عنوان دادهٔ binding در AST/تعریف همان CTE ثبت کند؛ این دادهٔ execution متعلق به CTE ساخته‌شده است، نه state پارامتری Query declaration. استفادهٔ مجدد از یک declaration با پارامترهای متفاوت نباید بین اجراها نشت state ایجاد کند.
- در composition چندلایه، هر declaration وابسته با پارامتر همان فراخوانی ساخته می‌شود؛ dependencyها از state پنهان Query instance گرفته نمی‌شوند. row factory هرگز `createCte()` یا composition را صدا نمی‌زند.

### ۳.۷. مسیرهای واقعی فراخوانی و معیار پذیرش

این مسیرها از سورس فعلی ردیابی شده‌اند. قرارداد مقصد، که در این جدول آمده، تصمیم معماری قطعی این پلن است؛ وجود امضای مقصد در سورس فعلی ادعا نمی‌شود.

| حوزه | مسیر فعلی و شواهد سورس | قرارداد مقصد و معیار قابل‌آزمون |
|---|---|---|
| ساخت و composition CTE | `ICteDeclaration.createCte(params)` در `data_base/query/api/src/main/kotlin/interfaces/relations/ICteDeclaration.kt`؛ `CteDeclaration.buildCte()` و `queryReady()` در `data_base/query/cte/src/main/kotlin/declaration/CteDeclaration.kt`؛ `CteBuilder.buildCteDefinition()` یک `QueryRenderSelectBuilder` تازه می‌سازد، DSL را اعمال می‌کند و یک `BuiltCteComposition` با AST و dependencies برمی‌گرداند (`data_base/query/builder/src/main/kotlin/ast/select_builder/cte/CteBuilder.kt`). `IQueryTableApi` هم‌اکنون `cte(ICteDeclaration)`, `cte(Cte)` و `cte(String)` دارد؛ overload declaration در `QueryTableBuilder` یک بار `createCte(declaration.params)` را صدا می‌زند. `QueryWithsItemBuilder.with(String, Cte)` خود Cte را نگه می‌دارد و `QueryWithsBuilder.addWith()` آن را به‌عنوان root composition ثبت می‌کند؛ `QueryRenderSelectBuilder.from()` نیز Cte object را به `CteAstComposer.addInlineCteSource()` می‌دهد. | `declaration(params)` با `operator invoke` فقط یک بار `createCte(params)` را صدا می‌زند و Cte می‌دهد. این مقدار مستقیماً به overloadهای موجود `with(String, Cte)` یا `cte(Cte)` می‌رسد؛ overload تازه‌ای برای آن‌ها لازم نیست. آزمون باید یک Cte و AST مستقل با binding همان ورودی بسازد، شمارندهٔ `createCte` را یک نشان دهد، executor را در مرحلهٔ ساخت صفر بار صدا بزند، و در composition نام تعریف/نام runtime، alias occurrence، dependencyها و ترتیب binding را حفظ کند. composition می‌تواند AST بیرونی را از Cte objectها بسازد؛ نباید declaration را دوباره فراخوانی یا Query را اجرا کند. |

#### حدودی که سورس به‌تنهایی تضمین نمی‌کند

- `ICteDeclaration` یک interface عمومی است؛ پیاده‌سازی سفارشی می‌تواند `Cte` یا AST را cache کند، state نگه دارد یا side effect داشته باشد. مسیر `CteBuilder.buildCteDefinition()` در هر فراخوانی builder/AST تازه می‌سازد، اما این ویژگی از type contract همهٔ implementerها قابل اثبات نیست. قرارداد پیاده‌سازی و تست باید fresh بودن Cte/AST و binding مستقل برای هر `createCte(params)` را بررسی کند.
- امضای `executeAs(mapper: (QueryRow) -> T)` نمی‌تواند مانع آن شود که caller یک object مشترک را از چند نوبت mapper برگرداند. استقلال نمونه‌ها مسئولیت mapper است؛ executor فقط تعداد و ترتیب فراخوانی را کنترل می‌کند. تست نمونهٔ مرجع باید factory تازه‌ساز را بررسی کند.
- `params` در خود declaration ذخیره نمی‌شود، اما مقدارهای مصرف‌شده می‌توانند در AST/Cte ساخته‌شده به‌عنوان binding بمانند. سورس فعلی قرارداد deep-copy برای ورودی‌های پارامتری دلخواه تعریف نمی‌کند؛ این نسخه نباید کپی عمومی یا ساختگی اضافه کند. آزمون‌ها باید دست‌کم استقلال bindingهای scalar و مقدار واقعی هر فراخوانی را ثابت کنند؛ رفتار انواع mutable دلخواه تا زمان تعریف قرارداد اختصاصی تضمین نمی‌شود.

### ۳.۸. Collection و تست‌های موجود

- `collection/core/src/main/kotlin/collection/ICollection.kt` و `Collection.kt` در package واقعی `gog.my_project.collection` هستند؛ package از مسیر فیزیکی استنتاج نشده است.
- `ICollection<T>` و `Collection<T>` عملیات فعلی `add`، `forEach`، `size`، `get`، `filter`، `map`، `firstOrNull` و `toList` را دارند. implementation از فهرست mutable خصوصی استفاده می‌کند و عملیات map/filter collection جدید می‌سازند.
- `collection:core` به query، executor یا database وابسته نیست. `collection:examples` به core وابستگی دارد و نمونه‌ها را با Helper انتخاب می‌کند.
- تست‌های Collection در `collection/core/src/test/kotlin/gog/my_project/collection/CollectionTest.kt` قرار دارند. این مأموریت آن‌ها را اجرا نکرده است.
- جست‌وجوی source در `data_base/query/executor`، `cte` و `example` استفادهٔ فعلی production از `ICollection` را نشان نداد؛ یکپارچه‌سازی نتیجهٔ typed هنوز انجام نشده است.

## ۴. معماری فعلی و جریان اجرای Query

مسیر رایج اجرای SELECT به‌صورت زیر است:

1. مصرف‌کننده با `IQueryBuilderExecutor.queryBuilderSelect` یا `queryBuilder(...)`، `QueryConsumer` می‌سازد؛ APIهای `QueryBuilderSelection` نیز مسیرهای operation-specific را فراهم می‌کنند.
2. `QueryColumnsBuilder`، `QueryTableBuilder` و builderهای دیگر AST را تکمیل می‌کنند. alias، `PropertyReference` و `ExecutionType` در AST قرار می‌گیرند.
3. `QueryConsumer.sql()` در صورت درخواست SQL و bindingها را می‌سازد؛ `details()` metadata را از provider یا analyzer می‌گیرد. این دو مرحله مستقل از اجرای Query هستند.
4. `QueryConsumer.execute()` به `IQueryBuilderExecutor.get(...)` می‌رسد. `first()` به `first(...)` می‌رسد.
5. `QueryBuilderExecutor` SQL و bindingها را رندر و به `QueryExecute` می‌فرستد.
6. `QueryExecute` اتصال و statement را مدیریت و ResultSet را فقط در callback زنده نگه می‌دارد.
7. `IQueryBuilderExecutor.get/first` alias و `ExecutionType` را اعتبارسنجی، ResultSet را در همان scope consume و `QueryRow` تولید می‌کند؛ ResultSet پیش از خروج از materialization بسته می‌شود.
8. `QueryConsumer` نتیجهٔ synchronous را در `ExecuteResult` می‌گیرد. `success` و `error` extensionها امکان زنجیرهٔ موجود را می‌دهند.

برای typed path، نقطهٔ کم‌ریسک تبدیل پس از materialization ردیف است: `QueryRow` همان منبع واحد مقادیر aliasدار باقی می‌ماند و mapper از آن نمونهٔ typed می‌سازد. نگاشت مستقیم ResultSet می‌تواند حافظهٔ میانی را کم کند، اما path جدیدی برای extraction، null handling، alias checking و resource management ایجاد می‌کند و خطر اختلاف با مسیر فعلی را دارد.

## ۵. قراردادهای معماری و API تأییدشده

### ۵.۱. حفظ API قبلی و محل mapper

**قرارداد:** `QueryConsumer.execute()` و `first()`، `IQueryBuilderExecutor.get/first/execute` و نوع‌های فعلی‌شان حفظ می‌شوند. typed result به‌صورت API افزایشی عرضه می‌شود؛ caller قدیمی برای استفاده از APIهای فعلی مجبور به migration نیست.

Mapper باید در لایهٔ query executor یا در فایل داخلی نزدیک به آن قرار بگیرد؛ نه در `data_base:manager:execute`، چون آن لایه از `QueryRow`، AST و مدل‌های query اطلاعی ندارد. در فاز اولیه mapper باید از materialization موجود استفاده کند و SQL یا JDBC binding را تغییر ندهد.

### ۵.۲. Query class به‌عنوان declaration و مدل ردیف

تصمیم قطعی این است که همان کلاس Query هم declaration و هم type مدل خروجی هر ردیف باشد؛ DTO جداگانه ساخته نمی‌شود. declaration بدون آرگومان ساخته می‌شود، برای نمونه `val cte = UserStatsQueryV3()`. constructor و state نمونهٔ Query هیچ پارامتر اجرایی ندارد.

پارامترها فقط به فراخوانی‌ای داده می‌شوند که واقعاً Query را می‌سازد یا اجرا می‌کند: `createCte(params)`، `with(withName, declaration(params))`، `from { cte(declaration(params)) }` یا `execute(queryManager, params)`. در قرارداد `ICteDeclaration<P>`، عملگر `invoke` به `createCte(params)` delegate می‌کند و یک `Cte` مستقل می‌سازد.

برای هر row، factory/mapper صریح caller یا concrete Query یک نمونهٔ تازه از همان Query class را با constructor بدون آرگومان می‌سازد و فقط propertyهای خروجی را مقدار می‌دهد. نمونهٔ row نه params دارد و نه AST/تعریف اجرای Query را از نمونهٔ declaration به اشتراک می‌گذارد. ساخت آن query را اجرا نمی‌کند، `createCte()` را فراخوانی نمی‌کند و AST اجرای query را بازسازی نمی‌کند.

پارامترهای `RelationFilters` و دیگر Pها متعلق به caller و همان فراخوانی‌اند. Query instance آن‌ها را نگه نمی‌دارد، mutate نمی‌کند یا بین اجراها share نمی‌کند؛ نیازی به کپی پارامتر برای row factory نیست، چون پارامتر اصلاً به row factory داده نمی‌شود. دادهٔ binding در CTE/AST ساخته‌شده مجاز است و از state declaration مستقل است.

propertyهای خروجی `@QBQuerySelect` getter واقعی دارند و برای setter-based mapping قابل مقداردهی‌اند؛ الگوی `var` با مقدار اولیهٔ مناسب مجاز است. mapper alias منتشرشده را از `QueryRow` می‌خواند و setter همان property را صریح صدا می‌زند. resolver metadata همچنان getter را برای استخراج metadata اجرا نمی‌کند.

حذف `ICteDeclaration.params`، تغییر constructor `CteDeclaration(params)` به constructor بدون پارامتر، تغییر `execute(queryManager)` به `execute(queryManager, params)` و حذف `IQueryTableApi.cte(declaration)` تغییرهای سازگاری‌شکنِ عمدی و قطعی‌اند؛ جزئیات migration در بخش ۱۶ آمده است.

### ۵.۳. API typed تأییدشده برای QueryConsumer

امضای API اصلی نسخهٔ 3.0:

    fun <T> executeAs(mapper: (QueryRow) -> T): ExecuteResult<ICollection<T>>

این متد به‌صورت additive روی `QueryConsumer` قرار می‌گیرد. ترتیب اجرا چنین است:

1. caller در صورت نیاز callbackهای فعلی `.sql {}` و `.details {}` را روی همان consumer ثبت/اجرا می‌کند؛ `executeAs` هیچ‌کدام را خودکار فراخوانی نمی‌کند.
2. `executeAs`، `execute()` فعلی را دقیقاً یک بار صدا می‌زند. همان مسیر، SQL، پارامترها، validation، JDBC و materialization موجود را اجرا می‌کند.
3. نتیجهٔ `Failure` اجرای query بدون اجرای mapper با همان exception عبور می‌کند. `Success` با لیست خالی به `Success(Collection<T>())` تبدیل می‌شود و mapper صفر بار فراخوانی می‌شود.
4. در نتیجهٔ موفق غیرخالی، ردیف‌ها به ترتیب موجود پیمایش می‌شوند و mapper برای هر ردیف دقیقاً یک بار فراخوانی می‌شود. mapper باید در هر فراخوانی یک Query class instance مستقل بسازد؛ API نمی‌تواند reuse یک reference را برای همهٔ ردیف‌ها به‌طور عمومی تشخیص دهد.
5. عناصر در یک `Collection<T>` محلی با `add` قرار می‌گیرند. فقط پس از پایان موفق همهٔ ردیف‌ها `Success(ICollection<T>)` تحویل داده می‌شود؛ هیچ نتیجهٔ نیمه‌کاره‌ای منتشر نمی‌شود.
6. اگر mapper برای ردیف N exception بدهد، پیمایش متوقف می‌شود و `Failure` با cause اصلی و شمارهٔ ردیف ۱-based در context خطا برمی‌گردد. retry انجام نمی‌شود. `Success(null)` برای payload چندردیفی، با توجه به قرارداد فعلی `get()`، نتیجهٔ نامعتبر است و به `Failure` روشن تبدیل می‌شود؛ آن را به Collection خالی تعبیر نمی‌کنیم.

پس از بازگشت `executeAs`، extensionهای موجود `.success {}` و `.error {}` روی `ExecuteResult<ICollection<T>>` قابل استفاده‌اند. رفتار آن extensionها تغییر نمی‌کند. `details()` مستقل و اختیاری باقی می‌ماند؛ mapper از metadata استفاده نمی‌کند و provider/analyzer را برای mapping صدا نمی‌زند.

هیچ متد typed به `IQueryBuilderExecutor` اضافه نمی‌شود. فراخوانی مستقیم همچنان از `queryManager.queryBuilder(query).executeAs(mapper)` به `QueryConsumer` می‌رسد. `IQueryBuilderExecutor`، `QueryRow`، `ExecuteResult` و امضاهای قدیمی تغییر نمی‌کنند.

`firstAs` در V3.0 وجود ندارد. `first()` با نوع و رفتار فعلی، از جمله `Success(null)` در نبود ردیف، حفظ می‌شود.

### ۵.۴. خطاهای mapper

- خطای SQL، bind یا JDBC از `execute()` بدون اجرای mapper و بدون تغییر علت عبور می‌کند.
- خطای mapper، cast، constructor، factory یا setter caller اجرای ردیف‌های بعد را متوقف می‌کند و به `ExecuteResult.Failure` با exception اصلی به‌عنوان cause و شمارهٔ ردیف ۱-based در context تبدیل می‌شود.
- alias انتخاب‌شده توسط mapper با `QueryRow.getValue(publishedSqlAlias)` خوانده می‌شود. alias ناموجود همان خطای lookup را می‌دهد؛ typed path آن را با context ردیف حفظ می‌کند. مقصدهایی که mapper آن‌ها را نخوانده، نیازی به validation ندارند.
- nullability و type conversion propertyهای خروجی Query class به عهدهٔ mapper caller است؛ framework annotation یا reflection برای استنتاج/تبدیل نوع به‌کار نمی‌برد.
- هیچ getter در query declaration یا model metadata برای resolve یا materialization فراخوانی نمی‌شود.
- در هیچ خطایی Collection نیمه‌ساخته تحویل داده نمی‌شود و query یا mapper به‌طور خودکار retry نمی‌شود.

## ۶. قرارداد مدل‌ها و annotationها

### ۶.۱. مدل جدول: `@QBTable` و `@QBColumn`

مدل جدول تعریف schema/identity منبع است. `QBTable.name/alias` و `QBColumn.name/alias/primaryKey` ورودی metadata هستند. از این annotationها نباید نتیجه گرفت که کلاس constructor قابل استفاده، property قابل نوشتن یا type conversion آماده دارد. `IModelBase` فعلاً marker خالی است.

در proposal فعلی، مدل `@QBTable` قرارداد schema/query source باقی می‌ماند و لزوماً target نتیجه نیست. اگر caller بخواهد همان نوع را خروجی کند، mapper صریح باید نمونهٔ معتبر آن را بسازد؛ framework آن را با reflection پر نمی‌کند. نمونه‌های فعلی `val`های initialized دارند و setter قابل استفاده ندارند، پس تغییرشان به `var` صرفاً برای feature جدید مجاز نیست.

### ۶.۲. مدل query: `@QBQuery` و `@QBQuerySelect`

`QBQuery.name/alias` برای declaration و `QBQuerySelect.name/alias` برای نام منطقی خروجی و SQL alias منتشرشده‌اند؛ این معانی از پارامترهای runtime مستقل‌اند. Query class با constructor بدون آرگومان ساخته می‌شود و هیچ `params` propertyای برای نگهداری ورودی ندارد.

propertyهای خروجی typed دادهٔ واقعی را نگه می‌دارند و getter واقعی دارند. در mapping با setter صریح، propertyها `var` هستند و برای instance تازه مقدار آغازین معتبر دارند. annotation و DSL نام منطقی و alias را حفظ می‌کنند؛ auto-mapping با reflection یا setter discovery افزوده نمی‌شود.

نمونه‌های فعلی V3.1 که getterهای `error(...)` دارند، برای typed output آماده نیستند و باید به getter/setter واقعی تبدیل شوند. `RelationFilters` همچنان یک type برای ورودی `createCte(params)` است، اما نه constructor Query را تغذیه می‌کند و نه به‌عنوان state نمونه نگهداری می‌شود.

### ۶.۳. قواعد metadata و مالکیت property

- `QueryColumnsAstMetadata.PropertyReference`، `ColumnAlias`، `logicalOutputName` و `ExecutionType` در AST اطلاعات انتخاب ستون را نگه می‌دارند؛ annotation metadata جایگزین مقدار runtime ردیف نیست.
- `EffectiveQueryMetadata.outputs` برای گزارش‌دهی است و constructor یا setter mapping ندارد. افزودن سازوکار construction به این metadata برای نسخهٔ 3.0 پیشنهاد نمی‌شود.
- `alias(property)` property متعلق به Query declaration را بررسی می‌کند. چون declaration و مدل خروجی همان کلاس‌اند، مالکیت property با همان کلاس حفظ می‌شود.
- `QueryRow` مقادیر را با published SQL alias نگه می‌دارد. mapper باید alias منتشرشده را دقیقاً بخواند؛ `logicalOutputName`، نام Kotlin property و نام فیزیکی ستون fallback یکدیگر نیستند.
- mapping از Row به property، setter با نام annotation را خودکار resolve نمی‌کند؛ mapper باید هم alias و هم مقصد property را صریح بنویسد.
- `DataType` فعلی `LONG`، `INT` و `STRING` را دارد. تبدیل‌های نوع هدف توسط mapper و با قرارداد صریح انجام می‌شود؛ cast اشتباه باید به‌عنوان mapping failure آشکار شود.
- resolverها باید همچنان فقط annotation/property reference را بررسی کنند و getter را برای metadata فراخوانی نکنند؛ getter واقعی صرفاً هنگام خواندن نمونهٔ خروجی به کار می‌رود.

## ۷. طراحی Mapper

### ۷.۱. ورودی و خروجی

امضای typed تأییدشده روی `QueryConsumer` چنین است:

```kotlin
fun <T> executeAs(mapper: (QueryRow) -> T): ExecuteResult<ICollection<T>>
```

در Queryهای موردنظر، `T` خود نوع Query class است؛ برای نمونه `UserDisplayQuery`. در هر فراخوانی mapper، factory صریح یک instance تازه از همان کلاس می‌سازد و mapper مقدارهای لازم را از `QueryRow` می‌خواند:

```kotlin
val rows = consumer.executeAs { row ->
    rowFactory().also { output ->
        output.id = row.getValue("id") as Int
        output.fullName = row.getValue("fullName") as String
    }
}
```

`rowFactory` در نمونه صرفاً نام توضیحی برای factory متعلق به caller است، نه API تازهٔ framework. `id` و `fullName` نشان‌دهندهٔ published SQL aliasهای این query هستند؛ مقدار دقیق باید با SELECT واقعی برابر باشد.

### ۷.۲. factory و constructor بدون پارامتر

- factory صریح در concrete Query یا mapper caller، برای هر row نمونهٔ تازه‌ای از همان Query class را با constructor بدون آرگومان می‌سازد.
- نمونهٔ مفهومی row factory برای `UserStatsQueryV3` برابر `{ UserStatsQueryV3() }` است؛ params به factory row داده نمی‌شود.
- هیچ `params` property در `ICteDeclaration` یا `CteDeclaration` وجود ندارد. پارامتر فقط به `createCte(params)` یا `execute(queryManager, params)` می‌رسد.
- ساخت row instance فقط constructor بی‌پارامتر و مقداردهی خروجی را انجام می‌دهد؛ نباید `createCte()`، `queryReady()`، query execution یا ساخت AST را اجرا کند.
- row factory برای هر ردیف object تازه می‌دهد. همان Query instance برای تعریف و آغاز اجرای query استفاده می‌شود؛ params و AST اجرای هر فراخوانی به row instances منتقل یا با آن‌ها share نمی‌شوند.
- reflection، constructor discovery، مقدار پیش‌فرض ساختگی یا object reuse فرض نمی‌شوند.

### ۷.۳. Alias، type و NULL

- ورودی نگاشت، `QueryRow` materialize‌شده است. مقدار با published SQL alias exact خوانده می‌شود؛ logical name و نام Kotlin property به‌صورت implicit alias محسوب نمی‌شوند.
- برای `@QBQuerySelect(name = "full_name", alias = "fullName")`، mapper باید alias خروجی `fullName` را بخواند، اما property مقصد `fullName` را مقدار دهد. `logicalOutputName` برابر `full_name` باقی می‌ماند.
- mapper نوع مقدار را به property مقصد تبدیل می‌کند. conversion عمومی یا truncate/cast ضمنی جدید به executor اضافه نمی‌شود. type mismatch، alias ناموجود یا setter exception خطای mapping است.
- برای SQL NULL، property مقصد nullable باید مقدار null بپذیرد؛ مقصد non-null باید یا با default معتبر و سیاست صریح مدیریت شود یا mapping را با خطای روشن متوقف کند. null نباید بی‌صدا به رشته یا مقدار عددی ساختگی تبدیل شود.
- ستون‌های اضافی که mapper استفاده نمی‌کند مجازند؛ alias انتخاب‌نشده‌ای که mapper درخواست کند، خطای فعلی `QueryRow` را ایجاد می‌کند و در context ردیف گزارش می‌شود.

### ۷.۴. Getter، setter و استقلال instance

- propertyهای خروجی Query class باید getter واقعی داشته باشند؛ getter پس از map مقدار setشده را برگرداند.
- در الگوی mutable هدف، propertyها `var` هستند تا mapper بتواند setter را صریحاً صدا بزند. اگر بعدها constructor mapping استفاده شود، API بازطراحی نمی‌شود مگر تصمیم جدا؛ این پلن بر setter صریح در mapper تمرکز دارد.
- هر ردیف یک بار factory می‌گیرد؛ identity دو خروجی متفاوت باید متفاوت باشد و مقداردهی یک ردیف مقدار ردیف دیگر را overwrite نکند.
- factory باید Query class را بسازد، ولی propertyهای خروجی را از `QueryRow` جدا و صریح مقدار دهد. `params`، AST و metadata query مقدار output property نیستند.
- تست metadata با getter خطادار می‌تواند به‌عنوان sentinel در fixtureهای صرفاً metadata باقی بماند؛ fixture typed باید getter واقعی و setter واقعی را اعتبارسنجی کند.

### ۷.۵. مسیر materialization

| مسیر | مزیت | ریسک | تصمیم پیشنهادی |
|---|---|---|---|
| `ResultSet → QueryRow → همان Query class` | reuse کردن alias/type/null handling و lifecycle فعلی؛ سازگار با API قدیمی | یک لیست میانی و نیاز به factory نمونهٔ Query class | مسیر V3.0 |
| `ResultSet → Query class` مستقیم | allocation میانی کمتر | تکرار JDBC، alias، null و resource logic؛ خطر واگرایی از `QueryRow` | خارج از V3.0 |

mapper پس از materialization اجرا می‌شود؛ ResultSet/statement/connection طبق مسیر فعلی پیش از تحویل نهایی بسته می‌شوند. در صورت شکست map، ICollection ناقص به caller تحویل نمی‌شود.

## ۸. طراحی API typed

### ۸.۱. API افزایشی روی QueryConsumer

API تأییدشدهٔ typed result روی `QueryConsumer` قرار می‌گیرد و نوع خروجی `T` می‌تواند خود Query class باشد:

```kotlin
queryManager.queryBuilderSelect { /* SELECT DSL */ }
    .sql { /* BuiltQuery */ }
    .details { /* EffectiveQueryMetadata */ }
    .executeAs { row ->
        rowFactory().also { output ->
            output.id = row.getValue("user_id") as Int
            output.fullName = row.getValue("fullName") as String?
        }
    }
    .success { rows -> /* ICollection<UserDisplayQuery> */ rows }
    .error { failure -> /* failure */ }
```

`rowFactory` باید در هر ردیف یک Query object تازه بسازد. این API در سورس فعلی وجود ندارد و به‌عنوان design پیشنهاد شده است. `.sql {}` و `.details {}` همان رفتار مستقل فعلی را دارند و `executeAs` آن‌ها را دوباره صدا نمی‌زند. `QueryRow` با alias SQL exact lookup می‌کند؛ mapper مسئول cast/null handling و تعیین مقصد property است.

### ۸.۲. Direct executor callها و custom implementationها

`IQueryBuilderExecutor` عمومی است و ممکن است مستقیم یا با implementation سفارشی مصرف شود. در V3.0 typed method به این interface اضافه نمی‌شود؛ caller از `queryBuilder(...)` به `QueryConsumer` می‌رسد و `executeAs(mapper)` را صدا می‌زند. implementation سفارشی که فقط متدهای فعلی executor را دارد نباید برای استفاده از typed API مجبور به تغییر شود. این موضوع با compile compatibility fixture آزموده شود.

### ۸.۳. CTE و چرخهٔ پارامتر

- `ICteDeclaration<P>` پارامتر نگه نمی‌دارد؛ `createCte(params: P): Cte` حفظ می‌شود و `operator fun invoke(params: P): Cte = createCte(params)` شکل فراخوانی نمونهٔ declaration را فراهم می‌کند.
- `CteDeclaration<P>()` بدون پارامتر ساخته می‌شود. `queryReady(queryManager, params)` و `execute(queryManager, params)` همان پارامتر صریح را مصرف می‌کنند؛ نوع نتیجهٔ اجرای فعلی `ExecuteResult<List<QueryRow>>` باقی می‌ماند.
- `UserStatsQueryV3` که باید مستقلاً اجرا شود، از `CteDeclaration<UserStatsQueryV3.RelationFilters>()` ارث می‌برد. Queryهایی که فقط برای ساخت relation لازم‌اند، می‌توانند `ICteDeclaration` را پیاده کنند؛ هیچ‌یک پارامتر را در constructor/state نگه نمی‌دارند.
- DSL مرجع برای WITH برابر `val cte = UserStatsQueryV3(); with(withName, cte(cteParams))` است. `cte(cteParams)` یک `Cte` می‌سازد و overload موجود `with(String, Cte)` آن را می‌پذیرد؛ semantics نام و composition تغییر نمی‌کند.
- در FROM از `cte(declaration(cteParams))` استفاده می‌شود؛ این expression هم به overload موجود `cte(Cte)` می‌رسد. overload قدیمی `cte(declaration)` که به params ذخیره‌شده متکی است حذف می‌شود؛ `cte(String)` و `cte(Cte)` باقی می‌مانند.
- در اجرای مستقیم، همان نمونهٔ بدون state با پارامترهای مستقل قابل استفادهٔ مجدد است: `cte.execute(queryManager, paramsA)` و سپس `cte.execute(queryManager, paramsB)`. پارامتر هر بار در ساخت binding/CTE مصرف می‌شود.
- ساخت نمونهٔ typed هر row فقط constructor بدون پارامتر و مقداردهی propertyها را انجام می‌دهد؛ هیچ اجرای دوم، `createCte()`، composition یا ساخت AST رخ نمی‌دهد.
- خروجی Collection فقط projection نهایی SELECT را شامل می‌شود؛ outputهای داخلی CTE dependencyها خروجی نهایی نیستند.



#### نمونه‌های مرجع: `UserStatsQueryV3` و `A2ExampleSelectV3`

`UserStatsQueryV3` نمونهٔ Query declaration بی‌پارامتر است؛ در صورت نیاز به اجرای مستقیم، از `CteDeclaration<UserStatsQueryV3.RelationFilters>()` ارث می‌برد و `createCte(params)` را با ورودی هر فراخوانی می‌سازد. خود Query property پارامتر ندارد.

نمونهٔ استفادهٔ مرجع برای CTE نام‌دار در `A2ExampleSelectV3` پس از migration:

~~~kotlin
val cte = UserStatsQueryV3()
val cteParams = UserStatsQueryV3.RelationFilters(userId = 5)
val withName = "active_user_stats_v3"

val query = QueryRenderSelectBuilder().withs {
    addWith { with(withName, cte(cteParams)) }
}

val directResult = cte.execute(queryManager, cteParams)
~~~

در نمونهٔ A2، `cte(cteParams)` نتیجهٔ `Cte` را برای overload موجود `with(String, Cte)` فراهم می‌کند. اجرای مستقیم همان declaration نیز پارامتر را جداگانه می‌گیرد و نتیجهٔ legacy `ExecuteResult<List<QueryRow>>` را برمی‌گرداند. این snippets قرارداد مقصد هستند؛ source فعلی تا اجرای migration همچنان constructor/state قدیمی دارد.

### ۸.۴. `firstAs` خارج از scope

`firstAs` صریحاً خارج از V3.0 است. typed API فقط چندردیفی `executeAs` است. `first()` فعلی، `ExecuteResult<QueryRow>` و معنای `Success(null)` برای نبود ردیف را حفظ می‌کند؛ overload تازه‌ای اضافه نمی‌شود.

### ۸.۵. مرز API قدیمی و جدید

| مسیر | قرارداد مقصد | مهاجرت/اثر سازگاری |
|---|---|---|
| `QueryConsumer.execute()` و `first()` | امضا و رفتار `QueryRow` فعلی | بدون تغییر |
| `QueryRow` access | `getValue(String)`، `getValue(KProperty1)` و `outputKeyHint` | بدون تغییر |
| typed multi-row | `executeAs((QueryRow) -> T): ExecuteResult<ICollection<T>>` افزایشی | اجرای legacy یک بار انجام و سپس eager map می‌شود |
| `ICteDeclaration<P>` | `createCte(params)` و operator factory پارامتردار؛ بدون `params` property | حذف property عمداً source/ABI را می‌شکند |
| `CteDeclaration<P>` | constructor بدون پارامتر؛ `queryReady(queryManager, params)` و `execute(queryManager, params)` | constructor و execute قدیمی عمداً ناسازگارند |
| CTE در FROM | `cte(declaration(params))` از overload موجود `cte(Cte)` | overload `cte(declaration)` حذف می‌شود؛ مهاجرت call-site لازم است |
| CTE در WITH | `with(cte)` و `with(withName, cte)` | overloadهای موجود حفظ می‌شوند؛ declaration با invoke به `Cte` تبدیل می‌شود |
| direct executor و DML | امضاها، callbacks، metadata و payload فعلی | بدون تغییر |
| `firstAs` | خارج از V3.0 | `first()` فعلی تغییر نمی‌کند |

`executeAs` مسیر typed جدیدی روی اجرای legacy می‌سازد؛ APIهای قدیمی نامرتبط با انتقال پارامتر CTE را به مسیر جدید تبدیل نمی‌کند. تنها ناسازگاری‌های مورد تأیید این نسخه همان حذف state پارامتر و تغییر call-siteهای مستقیم CTE است؛ فهرست migration در بخش ۱۶ آمده است.

## ۹. یکپارچه‌سازی Collection

- جهت dependency تولیدی فقط از `:data_base:query:executor` به `:collection:core` است؛ Collection مستقل باقی می‌ماند.
- سورس واقعی `data_base/query/executor/build.gradle.kts` فقط `kotlin("jvm")` را اعمال می‌کند و dependencyهای production را با `implementation(...)` می‌آورد. convention مشترک `buildSrc/src/main/kotlin/kotlin-jvm.gradle.kts` نیز فقط Kotlin/JVM و toolchain را اعمال می‌کند؛ در build scriptهای بررسی‌شده `java-library` یا `api(...)` وجود ندارد. بنابراین وجود `api` را در configuration فعلی مفروض نمی‌گیریم.
- چون `ICollection<T>` در public return signature متد جدید دیده می‌شود، راهکار پیشنهادی برای فاز پیاده‌سازی این است که فقط ماژول executor، علاوه بر Kotlin/JVM، `java-library` را اعمال کند و `api(project(":collection:core"))` را اعلام کند. این محل از تغییر convention مشترک و اثرگذاری بر همهٔ ماژول‌های آن جلوگیری می‌کند. طبق راهنمای Gradle Java Library Plugin، configuration `api` برای dependencyهای حاضر در public API است و `java-library` آن را فراهم می‌کند؛ این dependency در compile مصرف‌کنندگان نیز در دسترس است. اجرای یک compile fixture از ماژول مصرف‌کننده و بررسی نبود چرخه، پیش‌شرط فاز یکپارچه‌سازی است. اگر plugin configuration واقعی با این پیشنهاد سازگار نبود، پیش از تغییر مسیر جایگزین گزارش شود؛ consumer نباید مجبور به dependency پنهان یا تصادفی شود.
- هیچ فایل Gradle در این مرحله تغییر نمی‌کند و configuration resolution/build اجرا نشده است؛ پیشنهاد بالا طراحی بر پایهٔ build scriptهای خوانده‌شده است، نه نتیجهٔ آزمایش build.
- `Collection<T>` با `add` قابل پرشدن است و برای query نیاز به تغییر API فعلی ندارد.
- بدون ردیف، نتیجه `Success` با Collection خالی است، نه null Collection؛ ترتیب ردیف‌ها عین ترتیب List materialize‌شده حفظ می‌شود.
- Collection از AST و metadata مستقل است. `List<QueryRow>` می‌تواند میانی بماند تا مسیر materialization تکرار نشود؛ بهینه‌سازی حافظه فقط با profiling جدا بررسی می‌شود.

## ۱۰. سازگاری با قابلیت‌های قدیمی

نسخهٔ 3.0 در بخش typed result افزایشی است: `QueryRow`، `QueryConsumer.execute()/first()`، `IQueryBuilderExecutor`، callbackها، metadata، SQL، execution parameters مربوط به Queryها و رفتار `INSERT/UPDATE/DELETE` حفظ می‌شوند.

یک تغییر سازگاری‌شکنِ مشخص و مورد تأیید معماری، حذف پارامتر از state Query/`CteDeclaration` است. به همین دلیل `ICteDeclaration.params`، سازندهٔ `CteDeclaration(params)`، `execute(queryManager)` و `IQueryTableApi.cte(declaration)` بدون پارامتر حفظ نمی‌شوند. جایگزین‌ها و تمام call-siteهای لازم در بخش ۱۶ آمده‌اند؛ این تفاوت نباید به‌عنوان سازگاری کامل CTE گزارش شود.

این موارد عدم رگرسیون هستند:

- `QueryConsumer.execute()` همچنان `ExecuteResult<List<QueryRow>>` می‌دهد و `first()` همان نوع و معنای `Success(null)` را حفظ می‌کند.
- `QueryRow` access، aliasها، outputKeyHint و materialization موجود بدون تغییر می‌مانند.
- SQL، parameter binding، alias، ترتیب ردیف‌ها، callbackها و metadata report در مسیرهای قدیمی ثابت می‌مانند.
- typed mapper از همان `QueryRow` می‌خواند و هیچ SQL یا execution دوم تولید نمی‌کند.
- `createCte(params)` و composition CTE باقی می‌مانند؛ فقط محل دریافت پارامتر از Query state به آرگومان صریح منتقل می‌شود.
- `INSERT/UPDATE/DELETE` و consumerهایشان خارج از مهاجرت declaration CTE باقی می‌مانند.
- custom `EffectiveQueryMetadataProvider` و fallback analyzer در `details()` مستقل از materialization typed هستند.

## ۱۱. مدیریت منابع و خطا

1. `executeAs` ابتدا `QueryConsumer.execute()` قدیمی را یک بار اجرا می‌کند. اجرای SELECT، consume کردن ResultSet و بستن ResultSet/statement/connection در همان مسیر فعلی انجام می‌شود.
2. Mapper پس از بازگشت موفق `execute()` و پس از پایان عمر JDBC resources روی `List<QueryRow>` اجرا می‌شود؛ Collection هیچ ResultSet، Statement، اتصال، lazy iterator یا accessor وابسته به منبع نگه نمی‌دارد.
3. Failure مربوط به SQL/bind/JDBC بدون اجرای mapper با همان exception عبور می‌کند. خطای mapper در مرز `executeAs` به `ExecuteResult.Failure` تبدیل می‌شود؛ cause اصلی نگه داشته و شمارهٔ ردیف ۱-based در context خطا ثبت می‌شود.
4. اگر هر row شکست بخورد، پیمایش متوقف می‌شود؛ Collection محلی دور انداخته می‌شود و هیچ نتیجهٔ نیمه‌کاره تحویل داده نمی‌شود. retry خودکار انجام نمی‌شود.
5. callbackهای `.sql {}` و `.details {}` فقط طبق زمان‌بندی API فعلی و به‌صورت صریح caller اجرا می‌شوند؛ `executeAs` آن‌ها را تکرار نمی‌کند. metadata provider برای mapping فراخوانی نمی‌شود.
6. پس از دریافت نتیجه، `.success {}` و `.error {}` همان extensionهای فعلی‌اند و رفتارشان تغییر نمی‌کند. خطای blockهای آن‌ها طبق semantics موجود باقی می‌ماند؛ مرز تبدیل exception به Failure مخصوص mapper در `executeAs` است.
7. precedence خطای close منابع همان رفتار `use` و مسیر قدیمی است. تغییر resource handling خارج از scope است.
8. در `CteDeclaration.execute` فعلی، ساخت CTE و آماده‌سازی query پیش از ورود به `QueryConsumer.execute()` انجام می‌شود؛ بنابراین exception از `createCte`/آماده‌سازی propagate می‌شود، درحالی‌که SQL/JDBC failure طبق مسیر Executor در `ExecuteResult.Failure` قرار می‌گیرد. این تفکیک باید هنگام افزودن params حفظ و با تست تثبیت شود.

### ۱۱.۱. قرارداد دقیق خطا و مقدارها

| حالت | قرارداد `executeAs` | مسیر قدیمی |
|---|---|---|
| SELECT بدون ردیف | `Success` با Collection خالی؛ mapper صفر بار اجرا می‌شود | `execute()` لیست خالی و `first()` مقدار `Success(null)` فعلی را حفظ می‌کنند |
| executor برای payload چندردیفی `Success(null)` بدهد | `Failure(IllegalStateException)`؛ null با empty اشتباه گرفته نمی‌شود | `execute()` بدون تغییر |
| خطای SQL/bind/JDBC | همان Failure/exception عبور می‌کند؛ mapper اجرا نمی‌شود | semantics موجود |
| mapper alias ناموجود را می‌خواند | خطای `QueryRow.getValue` با شمارهٔ ردیف و cause در Failure | همان lookup error |
| alias خالی/تکراری یا execution type ناموجود | validation فعلی Failure می‌دهد؛ typed همان را عبور می‌دهد | validation فعلی |
| نوع مقدار یا null با constructor/setter مقصد ناسازگار است | خطای mapper در Failure؛ conversion ضمنی یا default خاموش نداریم | `QueryRow` مقدار فعلی را نگه می‌دارد |
| mapper برای row N exception بدهد | پیمایش متوقف، Failure با cause اصلی و ردیف ۱-based؛ Collection نیمه‌کاره منتشر نمی‌شود | construction مدل ندارد |
| `firstAs` | در نسخهٔ 3.0 وجود ندارد؛ `first()` unchanged | `first()` unchanged |

نگاشت property مقصد از reflection کشف نمی‌شود. `DataType` فعلی نوع استخراج را تعیین می‌کند؛ هر conversion به عهدهٔ lambda caller است. `logicalOutputName` یا نام فیزیکی ستون جای published SQL alias را نمی‌گیرد.

## ۱۲. فازهای اجرایی

هیچ فازی با ثبت این سند آغاز نمی‌شود. اجرای هر فاز پس از تأیید جداگانهٔ کاربر برای شروع پیاده‌سازی انجام می‌شود.

### فاز صفر: baseline و call-site inventory

- وضعیت Git، source/API واقعی، همهٔ مصرف‌کنندگان `ICteDeclaration.params`، constructorهای پارامترپذیر، `createCte`، `queryReady`، `execute` و `cte(declaration)` ثبت شود.
- رفتار موجود CTE binding، execution، callbackها، metadata و CTE composition به‌عنوان baseline آزموده شود.
- تست‌ها و کامپایل baseline پیش از تغییر اجرا و ثبت شوند.

### فاز یک: انتقال پارامتر از Query state به ورودی صریح

- `ICteDeclaration<P>` بدون `params` property شود؛ `createCte(params)` حفظ و operator `invoke(params)` برای DSL هدف اضافه شود.
- `CteDeclaration<P>` بدون constructor params باشد و `queryReady(queryManager, params)` و `execute(queryManager, params)` را پیاده کند.
- تمامی Query declarationها parameterless شوند؛ `UserStatsQueryV3` برای direct execution از `CteDeclaration<RelationFilters>()` استفاده کند.
- پارامترهای runtime به همان نقاط ساخت CTE/Binding وارد شوند؛ به Query instance افزوده نشوند.

### فاز دو: migration مسیرهای WITH و FROM

- در Builder، هر دسترسی به `declaration.params` حذف شود.
- overload `cte(declaration)` که به state ذخیره‌شده وابسته است حذف و مصرف‌کننده به `cte(declaration(params))` یا `Cte` ساخته‌شدهٔ صریح منتقل شود.
- overloadهای `with(Cte)` و `with(withName, Cte)`، ترتیب composition، نام CTE و alias occurrence حفظ شوند.
- نمونهٔ مرجع DSL در `A2ExampleSelectV3` با declaration بی‌پارامتر و params محلی مهاجرت کند.

### فاز سه: Query class به‌عنوان row model و mapper

- خروجی‌های typed همان Query class با getter واقعی و setter قابل‌استفاده تعریف شوند.
- mapper/factory صریح برای هر row یک نمونهٔ بی‌پارامتر و مستقل از همان کلاس بسازد و فقط خروجی‌ها را مقدار دهد.
- ساخت row هیچ Query execution، `createCte`، composition یا بازسازی AST اجرای Query ایجاد نکند.

### فاز چهار: typed execution و dependency عمومی Collection

- `executeAs(mapper: (QueryRow) -> T): ExecuteResult<ICollection<T>>` به‌صورت additive روی مسیر مناسب `QueryConsumer` پیاده شود.
- ترتیب، نتیجهٔ خالی، callbackها، failure cause و lifecycle منابع مطابق قرارداد پلن حفظ شود.
- انتشار عمومی `ICollection<T>` با توجه به Gradle graph واقعی بررسی شود؛ compile fixture مصرف‌کننده و نبود cycle لازم است.

### فاز پنج: تست‌های رگرسیون و مثال‌ها

- تست‌های API مهاجرت، استقلال پارامترها، CTE/WITH، property mapper، SQL/metadata و رفتار قدیمی اجرا شوند.
- مثال‌های V3 و V3.1، به‌ویژه `UserStatsQueryV3` و `A2ExampleSelectV3`، به شکل نهایی مهاجرت کنند.
- تمام گزینه‌های Helper موجود حفظ و مسیر جدید با loader واقعی اجرا شود.

### فاز شش: release review

- ماتریس عدم رگرسیون، API breakها، Gradle publication، مستندات و خروجی تست‌ها بررسی شود.
- هیچ release یا سازگاری کامل CTE ادعا نشود تا migrationها و consumer compileها تأیید شده باشند.

| ۲ | Query constructor/state | constructor Query بدون پارامتر است؛ params در هیچ property اجرایی Query نگهداری نمی‌شود | حذف constructorهای paramsدار و propertyهای `params` |
| ۳ | ساخت CTE | `createCte(params)` ورودی پارامتر را صریح می‌گیرد | هر Cte از params همان فراخوانی ساخته می‌شود |
| ۴ | DSL پارامتردار WITH | `declaration(params)` یک Cte می‌سازد و `with(withName, declaration(params))` به overload موجود `with(String, Cte)` می‌رسد | operator `invoke(params)` روی `ICteDeclaration` لازم است |
| ۵ | FROM | از `cte(declaration(params))` استفاده می‌شود | overload قدیمی `cte(declaration)` که state مخفی می‌خواند حذف می‌شود؛ Cte/String overload حفظ می‌شوند |
| ۶ | direct execute | `CteDeclaration.execute(queryManager, params)` params همان اجرا را می‌گیرد و نوع legacy result را نگه می‌دارد | Queryهای نیازمند direct execution مانند `UserStatsQueryV3` از base class ارث می‌برند |
| ۷ | row factory | برای هر ردیف یک نمونهٔ نو و بی‌پارامتر از همان Query class ساخته می‌شود | فقط خروجی‌ها map می‌شوند؛ نه query execution، نه createCte و نه AST rebuild |
| ۸ | خروجی propertyها | getter واقعی و setter قابل‌استفاده لازم است؛ setter-based mapping صریح است | alias/type/null/error policy در بخش ۷.۳ و ۱۴ اعمال می‌شود |
| ۹ | Query parameters و row data | params فقط ورودی ساخت CTE یا اجرا هستند و بخشی از Query instance یا row model state نیستند | deep/shallow copy params در row factory موضوعیت ندارد |
| ۱۰ | legacy و DML | QueryRow، QueryConsumer و IQueryBuilderExecutor نامرتبط، callbacks، metadata، SQL و DML حفظ می‌شوند | ناسازگاری‌های مصرح CTE تنها استثنای این پلن هستند |
| ۱۱ | Collection API visibility | executor باید `ICollection<T>` را در public return type منتشر کند | روش Gradle با compile fixture و گراف واقعی تأیید می‌شود؛ source/build اکنون تغییر نمی‌کند |
| ۱۲ | `firstAs` | خارج از محدوده است | `first()` legacy ثابت می‌ماند |

### ناسازگاری‌های API و مسیر migration

| قرارداد فعلی | قرارداد مقصد | مصرف‌کنندگان نیازمند اصلاح |
|---|---|---|
| `ICteDeclaration<P>.params` | حذف کامل property | همهٔ declarationها و هر کدی که `declaration.params` می‌خواند |
| `CteDeclaration<P>(params)` | `CteDeclaration<P>()` | سازنده‌های همهٔ subclassها و فراخوانی‌های آن‌ها |
| `execute(queryManager)` | `execute(queryManager, params)` | فراخوانی‌ها و overrideهای execute؛ حفظ API قدیمیِ بدون منبع params ممکن نیست |
| `queryReady(queryManager)` | `queryReady(queryManager, params)` | subclassها/کدهای داخلی که helper protected را فراخوانی می‌کنند |
| `IQueryTableApi.cte(declaration)` | حذف؛ استفاده از `cte(declaration(params))` | تمام from-source call siteها و تست‌های Builder |
| پیاده‌سازی مستقیم interface همراه constructor پارامترپذیر | no-arg declaration؛ برای direct execute، subclass شدن از CteDeclaration | Queryهای V3/V3.1 همگی no-arg می‌شوند؛ `UserStatsQueryV3` برای direct execute به base class می‌رود و نیاز direct execution در `UserPageQueryV3` فقط برای انتخاب inheritance بررسی می‌شود |
| `A2ExampleSelectV3` constructor + خواندن `.params` | `val stats = UserStatsQueryV3()`، params محلی، `with(withName, stats(params))` | مثال و Helper مرتبط |

`createCte(params)` به‌عنوان متد موجود حفظ می‌شود، ولی هر implementer باید حذف params property و constructor state را انجام دهد. overloadهای `with(Cte)` و `with(String, Cte)`، APIهای legacy query execution و signatureهای DML تغییر نمی‌کنند.

### موارد اجرایی که هنوز باید راستی‌آزمایی شوند

این موارد تصمیم معماری را باز نمی‌کنند؛ فقط معیارهای اعتبارسنجی مرحلهٔ پیاده‌سازی‌اند:

- consumer compile با public type `ICollection<T>` و تعیین Gradle exposure درست.
- کامل‌بودن فهرست call-siteها، به‌ویژه تست‌های قدیمی و تمام مثال‌های V3/V3.1.
- binding params مستقل پس از build دو Cte با یک declaration و ورودی‌های متفاوت.
- صحت mapping alias/type/NULL و failure handling در Query classهای دارای getter/setter واقعی.

**وضعیت:** تصمیم معماری params و Query model قطعی است. پلن پس از این همگام‌سازی آمادهٔ بازبینی نهایی است؛ شروع implementation منوط به تأیید جداگانهٔ کاربر باقی می‌ماند.

## ۱۷. ترتیب اجرا و وابستگی فازها

`فاز ۰: baseline و inventory قراردادها/call-siteها
    ↓
فاز ۱: no-arg Query declaration و params صریح در ICteDeclaration/CteDeclaration
    ↓
فاز ۲: migration ساخت CTE در FROM/WITH و composition
    ↓
فاز ۳: Query class output properties و row factory مستقل
    ↓
فاز ۴: QueryConsumer.executeAs و Collection API visibility
    ↓
فاز ۵: تست‌های regression، مثال‌ها و Helper
    ↓
فاز ۶: release review و بررسی ناسازگاری‌ها

در مرحلهٔ row factory، constructor همان Query class بدون ورودی params اجرا می‌شود. این مسیر هیچ query execution، `createCte()`، CTE composition یا بازسازی AST اجرای Query ندارد. params هنگام اجرای واقعی به declaration داده می‌شود و دادهٔ binding در Cte/AST ساخته‌شده باقی می‌ماند؛ Query instance آن را نگه نمی‌دارد. `firstAs` خارج از scope می‌ماند.

## ۱۸. معیارهای نهایی تکمیل نسخهٔ 3.0

- همان Query class هم declaration و هم type مدل نتیجه است؛ DTO جداگانه استفاده نشده است.
- تمام Query declarationها constructor بدون پارامتر دارند و هیچ Query params state ندارد.
- `ICteDeclaration.createCte(params)`، `CteDeclaration.execute(queryManager, params)`، `with(withName, declaration(params))` و `from { cte(declaration(params)) }` با ورودی explicit کار می‌کنند.
- استفادهٔ دوباره از یک Query instance با params متفاوت، Cte/bindings و نتایج مستقل می‌دهد و هیچ state اجرای پیشین را نشت نمی‌دهد.
- برای هر row، factory concrete/caller یک نمونهٔ مستقل و بی‌پارامتر از همان کلاس می‌سازد و query را اجرا نمی‌کند، `createCte()` را فراخوانی نمی‌کند یا AST اجرای اصلی را بازسازی نمی‌کند.
- propertyهای خروجی getter واقعی و setter قابل‌استفاده دارند؛ mapper setter را صریحاً فراخوانی می‌کند و resolver metadata getter را اجرا نمی‌کند.
- `executeAs(mapper: (QueryRow) -> T): ExecuteResult<ICollection<T>>` additive است؛ rowها مرتب و یک‌بار map می‌شوند؛ نتیجهٔ خالی Collection خالی موفق می‌دهد و Failure علت را حفظ می‌کند بدون انتشار Collection ناقص.
- alias از published SQL alias exact خوانده می‌شود؛ logical name، Kotlin property و physical column name جایگزین آن نیستند.
- conversion، NULL، factory failure و setter/mapping failure مشخص و آزموده شده‌اند.
- QueryRow، QueryConsumer/IQueryBuilderExecutor قدیمی، callbacks، details/metadata، SQL، CTE composition و عملیات INSERT/UPDATE/DELETE بدون regression هستند؛ ناسازگاری‌های CTE جدول ۱۶ صریحاً migrate شده‌اند.
- `ICollection<T>` در public API مصرف‌کننده resolve می‌شود؛ Gradle graph چرخه ندارد و Collection مستقل است.
- `firstAs` اضافه نشده و تست/buildهای واقعی پیاده‌سازی گزارش شده‌اند.

## ۱۹. گزارش baseline و محدودیت‌های همین بررسی

- در این بازبینی، مسیر ساخت CTE و composition در `ICteDeclaration.kt`، `CteDeclaration.kt`، `Cte.kt`، `CteBuilder.kt`، `QueryTableBuilder.kt`، `IQueryTableApi.kt`، `IQueryWithsItemApi.kt`، `QueryWithsItemBuilder.kt`، `QueryWithsBuilder.kt`، `QueryRenderSelectBuilder.kt` و `CteAstComposer.kt` read-only بررسی شد.
- مسیر اجرا تا materialization نیز از `CteDeclaration.execute/queryReady`، `QueryConsumer.execute`، `IQueryBuilderExecutor.get/materializeQueryRow`، `QueryBuilderExecutor.execute` و `QueryExecute.executeSelect` دنبال شد؛ `QueryRow.getValue` و مسیر ثبت `PropertyReference` در `QueryColumnsBuilder.alias(property)` هم بررسی شدند.
- `UserStatsQueryV3`، `A2ExampleSelectV3`، `UserDisplayQueryV31.execute`، `CteExecutionExampleV31` و ثبت‌های آن در `ManagerExampleV31` بررسی شدند. wrapper فعلی `CteExecutionExampleV31(CteDeclaration<*>)` با حذف params state نمی‌تواند type ورودی را بازیابی کند؛ پلن اکنون generic شدن wrapper و دریافت params مستقل را صریح ثبت می‌کند.
- جست‌وجوی read-only برای `ICteDeclaration`, `CteDeclaration`, `.params` و `cte(declaration)` در `data_base/query`، فایل‌های تست و مثال‌های درگیر را مشخص کرد؛ فاز صفر باید inventory را دوباره روی کل repository اجرا کند. رفتار custom implementerها از سورس عمومی قابل تضمین نیست و محدودیت‌های mapper/factory و params mutable در بخش ۳.۷ ثبت شده‌اند.
- سورس فعلی `ICteDeclaration<P>` هنوز `val params: P` دارد؛ `CteDeclaration<P>(params)` آن را نگه می‌دارد و `execute(queryManager)`/`queryReady(queryManager)` از آن استفاده می‌کنند. این‌ها وضعیت فعلی‌اند؛ بخش‌های ۳.۶، ۸.۳ و ۱۶ قرارداد مقصد و مهاجرت تأییدشده را مشخص می‌کنند.
- `IQueryTableApi` هم‌اکنون overloadهای `cte(declaration)`، `cte(Cte)` و `cte(String)` دارد؛ Builder در overload declaration از `declaration.params` می‌خواند. قرارداد مقصد overload stateful اول را حذف و مصرف را به `cte(declaration(params))` منتقل می‌کند.
- `IQueryWithsItemApi` از قبل `with(Cte)` و `with(withName, Cte)` دارد؛ DSL مقصد از `operator invoke(params)` روی declaration برای ساخت Cte استفاده می‌کند.
- `A2ExampleSelectV3.kt` فعلاً declaration پارامترپذیر می‌سازد و `declaration.params` را به `createCte` می‌دهد. نمونهٔ مرجع مقصد در بخش ۸.۳ و فاز migration، declaration بی‌پارامتر، params محلی و `with(withName, declaration(params))` است.
- `UserStatsQueryV3` در حال حاضر مستقیم `ICteDeclaration` را پیاده می‌کند؛ برای مسیر اجرای مستقیمِ مصوب باید از `CteDeclaration<RelationFilters>()` ارث ببرد. Queryهای دیگر طبق نیاز direct execute یا صرفاً CTE composition انتخاب می‌شوند، اما هیچ‌یک params را ذخیره نمی‌کنند.
- Query result properties فعلی در مثال‌ها ممکن است getterهای خطادار داشته باشند؛ migration باید getter واقعی و setter قابل استفاده فراهم کند. `QueryConsumer.executeAs` در سورس فعلی وجود ندارد و همچنان API افزایشی پیشنهادشدهٔ این پلن است.
- `plans/executer/exist.md` و `plans/executer/visision.md` نیز با تصمیم قطعی و نمونه‌های مقصد مقایسه شدند؛ در این بازبینی ناسازگاری تازه‌ای نیازمند اصلاح در آن دو سند پیدا نشد.
- در این بازبینی هیچ سورس، build file یا تستی تغییر نکرد و هیچ build یا تستی اجرا نشد. فقط همین پلن تکمیل شد؛ هیچ staging یا commit انجام نشد.
