# پلن اجرای‌کننده ۲.۰: راستی‌آزمایی یکپارچه‌سازی و نهایی‌سازی قرارداد

## وضعیت

**پلن برای راستی‌آزمایی آماده است؛ راستی‌آزمایی زمان اجرا فعلاً مسدود است.** آزمون اختیاری MySQL به متغیرهای محیطی نیاز دارد که در این محیط تنظیم نشده‌اند و در حال حاضر فقط یک `SELECT` پارامتری و فقط‌خواندنی را پوشش می‌دهد. این پلن ادعای موفقیت آزمون یکپارچه‌سازی MySQL را مطرح نمی‌کند.

## هدف

شکاف شواهد پس از اجرای پلن ۱.۰ را با راستی‌آزمایی Execution Core موجود در برابر MySQL Connector/J پیکربندی‌شده و یک سرور واقعی MySQL ببندید. اتصال پارامترها، عملیات CRUD، کلیدهای تولیدشده، callbackها، مالکیت منابع، DDL و مرزهای فعلی خطا را بررسی کنید.

این سند فقط پلن راستی‌آزمایی و قرارداد است و مجوز پیاده‌سازی نمی‌دهد. اگر خطای مشخصی رخ داد، پیش از پیشنهاد اصلاح محدود، نمونهٔ بازتولید حداقلی و شواهد source/test را ثبت کنید.

## ردیابی پیاده‌سازی فعلی

آزمون اختیاری MySQL فقط‌خواندنی است: پس از probe مستقیم اتصال، `QueryExecute.executeSelect` را با عبارت‌های پارامتری فراخوانی می‌کند و نتیجه را می‌خواند. جدول ایجاد نمی‌کند، ردیفی نمی‌نویسد، CRUD، کلید تولیدشده یا DDL را نمی‌آزماید. موفقیت probe به‌تنهایی به معنی موفقیت Execution Core نیست.

`QueryExecuteContractTest` از JDBC Driver ثبت‌شده درون‌فرایندی و proxyها استفاده می‌کند. این آزمون bindهای تکراری، اعتبارسنجی ناسازگاری، SQL تهی/خالی، خطاهای اتصال/آماده‌سازی/bind/اجرا/callback، عمر ResultSet، شاخه‌های INSERT، خطاهای بستن منابع و رفتار Boolean مربوط به DDL را پوشش می‌دهد. این‌ها تست‌های قراردادی JDBC شبیه‌سازی‌شده‌اند، نه شواهد یکپارچه‌سازی MySQL.

`BuiltQueryTest` ترتیب رخدادها، برخورد پیشوندی، پارامترهای خالی، ناسازگاری‌ها و فراخوانی binder را پوشش می‌دهد. تست‌های migration executor که از بدل‌های `IQueryExecute` استفاده می‌کنند، فقط سازگاری migration را ثابت می‌کنند. در مسیرهای بررسی‌شده، منبع تست اختصاصی برای query executor پیدا نشد.

## دامنهٔ یکپارچه‌سازی MySQL

از یک پایگاه‌داده/schema صریحاً دورریختنی در MySQL استفاده کنید. نام جدول اختصاصی و یکتا یا پسوند یکتای اجرای تست به کار ببرید و فقط اشیایی را پاک کنید که همان اجرا ساخته است. اگر مالکیت امن schema و پاک‌سازی قابل تضمین نیست، راستی‌آزمایی زنده را **مسدود** اعلام کنید.

سناریوهای لازم روی server واقعی:

1. از مسیر `DatabaseConnection` پیکربندی‌شده متصل شوید. probe مستقیم اتصال را فقط شاهد آماده‌سازی بدانید.
2. همهٔ نوع‌های پشتیبانی‌شدهٔ resolver و null نوع‌دار را bind و مقدارشان را بخوانید.
3. جدولی مجزا با نوع‌های صریح MySQL برای ماتریس پارامتر و CRUD بسازید.
4. یک ردیف با کلید صحیح auto-generated درج کنید؛ یک callback، `Success<Long>`، مقدار کلید و ذخیره‌شدن ردیف را بررسی کنید.
5. ردیف را با کلید bindشده بخوانید؛ ResultSet را در callback مصرف و ببندید؛ یک callback را بررسی کنید.
6. ردیف را به‌روزرسانی کنید؛ تعداد ردیف‌های تغییرکرده و مقدار جدید را با خواندن مجدد بررسی کنید.
7. ردیف را حذف کنید؛ تعداد ردیف‌های حذف‌شده و نبود آن در خواندن بعدی را بررسی کنید.
8. DDL بی‌خطر را از مسیر `executeTable` اجرا کنید؛ `Success(true)` را بررسی کنید. خطای امن DDL را فقط در صورتی بیازمایید که تغییر داده ایجاد نکند.
9. اشیای متعلق به تست را در `finally` پاک کنید؛ خطای پاک‌سازی را گزارش کنید، بدون آنکه خطای اصلی پنهان شود.

تضمین rollback تراکنش را استنباط نکنید: مسیر آزموده‌شده wrapper تراکنش ندارد. تست باید آثار خودش را صریحاً پاک کند.

## مبنای Connector/J

**شواهد:** `data_base/manager/connection/build.gradle.kts` وابستگی `mysql:mysql-connector-java:8.0.33` را اعلام می‌کند؛ `DatabaseConnection` با `DriverManager` اتصال می‌گیرد.

**تفسیر:** این نسخه مبنای اعلام‌شدهٔ مخزن است، نه اثبات سازگاری با همهٔ نسخه‌های MySQL Server.

**تصمیم:** artifact نسخهٔ 8.0.33 را resolve و استفاده کنید؛ نسخهٔ واقعی driver و نسخهٔ server را از `SELECT VERSION()` ثبت کنید. وابستگی اضافه یا به‌روز نکنید. بدون قرارداد مالک مخزن، بازهٔ نسخهٔ پشتیبانی‌شده اعلام نکنید.

## قرارداد محیط MySQL

| متغیر | لازم؟ | رفتار فعلی |
|---|---:|---|
| `KOTLIN_DB_EXECUTE_TEST_HOST` | بله | میزبان مورد استفاده در `jdbc:mysql://<host>`. |
| `KOTLIN_DB_EXECUTE_TEST_DATABASE` | بله | نام پایگاه‌داده/schema؛ آزمون فعلی `?serverTimezone=UTC` را به آن اضافه می‌کند. |
| `KOTLIN_DB_EXECUTE_TEST_USERNAME` | بله | نام کاربری MySQL. |
| `KOTLIN_DB_EXECUTE_TEST_PASSWORD` | خیر | در نبود مقدار، رشتهٔ خالی استفاده می‌شود. هرگز آن را چاپ نکنید. |
| `KOTLIN_DB_EXECUTE_TEST_PORT` | خیر | پورت عددی؛ در نبود یا نامعتبر بودن مقدار، 3306 استفاده می‌شود. پورت مؤثر را ثبت کنید. |

آزمون فعلی `DefaultDatabaseConfig.config` را ذخیره و در `finally` بازیابی می‌کند. آن را از تست‌های موازی که این متغیر سراسری را تغییر می‌دهند جدا نگه دارید. ساخت URL فعلی نام پایگاه‌داده و پارامتر timezone را در `dbName` قرار می‌دهد؛ تا وقتی خطای مشاهده‌شده بازبینی آن را ایجاب نکرده، همین قرارداد را حفظ کنید. متغیر جداگانه‌ای برای schema وجود ندارد.

پیش از اجرا، دورریختنی‌بودن پایگاه‌داده را بررسی کنید و مطمئن شوید دسترسی‌های اعتبارنامه فقط برای عملیات لازم create/insert/select/update/delete/drop است. گذرواژه، URL کامل حاوی اطلاعات محرمانه یا dump متغیرهای محیطی را ثبت نکنید.

هنگام تدوین این پلن، هر پنج متغیر `KOTLIN_DB_EXECUTE_TEST_*` در این محیط تنظیم نشده‌اند. آزمون یکپارچه‌سازی فعلی skip می‌شود؛ بنابراین نتیجه‌ای دربارهٔ MySQL زنده در دست نیست.

## ماتریس راستی‌آزمایی پارامترها

index/value/type مربوط به bind را ثبت کنید، از Connector/J اجرا بگیرید و مقدار بازخوانی‌شده را صریحاً بررسی کنید. هم SELECT عبارتی و هم نمونه‌ای از مقدار ذخیره‌شده در ستون را بیازمایید، چون ممکن است MySQL تبدیل نوع انجام دهد.

| سناریو | ورودی Kotlin / JDBC type | bind مورد انتظار | assertion لازم در MySQL |
|---|---|---|---|
| عدد صحیح | Int / INTEGER | `setObject(index, value, Types.INTEGER)` | مقدار دقیق و نوع مشاهده‌شدهٔ نتیجه/ستون. |
| عدد صحیح بزرگ | Long / BIGINT | `setObject(index, value, Types.BIGINT)` | مقدار دقیق بزرگ‌تر از ۳۲ بیت، بدون کوچک‌سازی یا از دست‌رفتن دقت. |
| اعشاری Double | Double / DOUBLE | `setObject` نوع‌دار با DOUBLE | مقدار دقیق و قابل‌نمایش انتخاب‌شده. |
| اعشاری Float | Float / FLOAT | `setObject` نوع‌دار با FLOAT | مقدار مورد انتظار؛ اگر تبدیل server نمایش دودویی را عوض کرد، تلورانس را ثبت کنید. |
| Boolean | Boolean / BOOLEAN | `setObject` نوع‌دار با BOOLEAN | Boolean JDBC را بررسی و معنای نوع نتیجه/ستون در MySQL را ثبت کنید. |
| متن | String / VARCHAR | `setObject` نوع‌دار با VARCHAR | متن دقیق؛ در صورت پشتیبانی charset، نمونهٔ امن غیر ASCII نیز اختیاری است. |
| تاریخ | LocalDate / DATE | `setObject` نوع‌دار با DATE | تاریخ دقیق با `getDate().toLocalDate()`. |
| زمان | LocalTime / TIME | `setObject` نوع‌دار با TIME | مقدار دقیق در دقت آزموده‌شده با `getTime().toLocalTime()`. |
| timestamp محلی | LocalDateTime / TIMESTAMP | `setObject` نوع‌دار با TIMESTAMP | timestamp دقیق در دقت آزموده‌شده با `getTimestamp().toLocalDateTime()`. |
| لحظهٔ زمانی | Instant / TIMESTAMP | `setObject` نوع‌دار با TIMESTAMP | لحظهٔ مورد انتظار با تنظیم UTC در URL؛ کاهش دقت را ثبت کنید. |
| null نوع‌دار | null / نوع صریح، دست‌کم VARCHAR | `setNull(index, declaredSqlType)` | SQL NULL با `getObject`؛ هنگام getter اولیه، `wasNull()` را به کار ببرید. |
| نوع جایگزین | مقدار مشخص JVM پشتیبانی‌نشده / OTHER | `setObject(..., Types.OTHER)` نوع‌دار | رفتار واقعی driver را تعیین کنید؛ فرض نکنید هر object دلخواهی پشتیبانی می‌شود. محدودیت را صریحاً تعیین تکلیف کنید. |

آزمون فعلی بیشتر این مقدارها را در SELECT عبارتی دارد، اما ستون ذخیره‌شده، مقدار جایگزین، CRUD و assertion مربوط به `wasNull()` پس از getter اولیه را پوشش نمی‌دهد.

## راستی‌آزمایی CRUD

| عملیات | سناریوی زنده | assertionها |
|---|---|---|
| INSERT | درج یک ردیف با مقدارهای bindشده در جدول متعلق به تست و دارای کلید صحیح auto-generated. | یک callback؛ `Success<Long>` برابر کلید باشد؛ بازخوانی با دادهٔ ذخیره‌شده مطابقت کند. تست fake قراردادی بسته‌شدن ResultSet کلیدها پیش از callback را بررسی می‌کند. |
| SELECT | خواندن ردیف درج‌شده با کلید اصلی bindشده. | یک callback؛ مقدارها و SQL NULL بررسی شوند؛ caller در callback ResultSet را ببندد. |
| UPDATE | تغییر یک مقدار با پارامترهای bindشده. | یک callback؛ تعداد ردیف مورد انتظار؛ SELECT بعدی تغییر مقدار را تأیید کند. |
| DELETE | حذف ردیف با کلید bindشده. | یک callback؛ تعداد ردیف مورد انتظار؛ SELECT بعدی نبود ردیف را تأیید کند. |

از مقدارهای قطعی استفاده کنید و فقط داده‌های متعلق به تست را پاک کنید. می‌توان placeholder تکراری را در query معتبر گنجاند؛ fakeها همچنان شاهد قطعی برخورد پیشوند و نگاشت نامعتبر هستند.

## INSERT و کلیدهای تولیدشده

**شواهد فعلی:** API مقدار `ExecuteResult<Long>` را برمی‌گرداند. پیاده‌سازی `executeUpdate` را فراخوانی می‌کند، تعداد ردیف مثبت می‌خواهد، ستون اول کلید تولیدشده را به‌صورت Long می‌خواند، پیش از callback ResultSet کلیدها را می‌بندد و یک callback پایانی می‌فرستد. تست‌های fake موفقیت کلید، صفر ردیف، نبود ردیف کلید، خطای بازیابی/بستن و تعداد callback را پوشش می‌دهند. شاخهٔ affected rows تهی در source آمده، ولی `executeUpdate()` در JDBC مقدار اولیهٔ `Int` برمی‌گرداند و فراخوانی فعلی نمی‌تواند null تولید کند.

**راستی‌آزمایی زنده:** از کلید صحیح auto-increment استفاده کنید؛ کلید دقیق را بررسی و با SELECT درج‌شدن ردیف را تأیید کنید. از INSERT بدون کلید auto-generated انتظار کلید نداشته باشید.

**حل‌نشده:** `getLong(1)` برای SQL NULL مقدار `0L` می‌دهد؛ source فعلی `wasNull()` را فراخوانی نمی‌کند. ResultSet کلیدِ خالی تشخیص داده می‌شود، اما ردیفی که خانهٔ کلید آن SQL NULL باشد تشخیص داده نمی‌شود. امکان وقوع و رفتار مطلوب معلوم نیست. فرض نکنید صفر یعنی کلید مفقود. برای بستن این مورد، نمونهٔ JDBC/server قابل‌بازتولید یا مدرک ناممکن‌بودن این حالت برای INSERTهای پشتیبانی‌شده و نیز تصمیم مالک لازم است. این ابهام مانع بررسی کلیدهای عادی auto-increment نیست.

## SELECT و مالکیت ResultSet

executor یک ResultSet زنده را در callback موفق تحویل می‌دهد. caller آن را در همان callback مصرف و می‌بندد. statement و connection متعلق به executor هستند و با پایان عملیات بسته می‌شوند. استفادهٔ امن از ResultSet پس از بازگشت callback تضمین نشده است.

مصرف و بستن را در MySQL زنده بررسی کنید. برای ترتیب دقیق خطاهای تزریق‌شدهٔ close از تست fake JDBC استفاده کنید، چون بازتولید خطای شبکه/server قابل اتکا نیست. وضعیت بسته‌شدن را فقط در صورت قطعی‌بودن ثبت کنید؛ رفتار getter پس از بسته‌شدن را به قرارداد تبدیل نکنید.

## قرارداد callback

هر فراخوانی عملیات حداکثر یک callback پایانی دارد. موفقیت و خطای سطح عملیات JDBC پس از گرفتن اتصال یک callback می‌دهند. خطای گرفتن اتصال و ناسازگاری همزمان پارامتر هیچ callback عملیاتی نمی‌دهند. exception مصرف‌کننده از callback propagate می‌شود و موجب ورود مجدد نمی‌شود.

تعداد callbackهای SELECT/INSERT/UPDATE/DELETE/DDL زنده و هر خطای امنِ القاشده را بشمارید. رفتار SQLException/runtime پرتاب‌شده از مصرف‌کننده را در تست fake نگه دارید. شکست assertion درون callback تست را به‌عنوان نتیجهٔ Failure اجرایی نشمارید.

## چرخهٔ عمر منابع

| منبع | مالک و طول عمر | راستی‌آزمایی |
|---|---|---|
| Connection | توسط `DatabaseConnection` گرفته و پس از بازگشت callback با `use` توسط executor بسته می‌شود. | fakeها close و خطای آن را بررسی می‌کنند؛ اجرای زنده عملیات عادی و بازیابی config را بررسی می‌کند. |
| PreparedStatement | برای هر عملیات ساخته و با `use` توسط executor بسته می‌شود. | fakeها بستن عادی و ناموفق را بررسی می‌کنند. |
| ResultSet مربوط به SELECT | به caller تحویل می‌شود؛ caller در callback می‌بندد. | SELECT زنده داخل callback مصرف/بسته می‌شود؛ fakeها وضعیت را بررسی می‌کنند. |
| ResultSet کلید تولیدشده | executor آن را می‌خواند و پیش از callback INSERT می‌بندد. | fakeها بستن پیش از callback را بررسی می‌کنند؛ تست زنده مسیر موفق کلید را تأیید می‌کند. |

خطای close پس از callback همزمان propagate می‌شود و callback را تکرار نمی‌کند. طبق قرارداد فعلی، خطای بستن کلیدهای تولیدشده پیش از callback پایانی یک Failure می‌دهد. این دو ترتیب را از هم جدا نگه دارید.

## قرارداد DDL

`executeTable`، متد JDBC یعنی `execute()` را صدا می‌زند اما Boolean آن را دور می‌اندازد. اگر SQLException گرفته‌شده رخ ندهد، `Success(true)` برمی‌گرداند: تکمیل موفق بدون خطای گزارش‌شده، نه نشانگر ResultSet در JDBC. تست‌های fake مقدارهای true/false و SQLException را پوشش می‌دهند.

فقط در schema دورریختنی، CREATE/DROP بی‌خطر را اجرا کنید؛ `Success(true)` و یک callback را بررسی کنید. اگر حالت DDL نامعتبر را می‌آزمایید، مطمئن شوید schema را تغییر نمی‌دهد و Failure را بررسی کنید. معنای Boolean در سطح migration جدا می‌ماند.

## راستی‌آزمایی BuiltQuery

رفتار فعلی را بدون تغییر parser/classifier بررسی کنید:

- فقط نام‌های مطابق regex فعلی token محسوب می‌شوند؛
- ترتیب متنی رخدادها، نام تکراری و جفت پیشوندی مانند `:id` و `:id2` به جایگاه‌های یک‌مبنایی نگاشت می‌شوند؛
- پارامتر مفقود، اضافی/استفاده‌نشده و تکرار متعارض، پیش از اتصال و به‌صورت همزمان رد می‌شوند؛
- objectهای پارامتر تکراری و هم‌ارزش پذیرفته می‌شوند؛
- SQL بدون placeholder با فهرست پارامتر خالی معتبر می‌ماند؛
- ترتیب جایگزینی و bind یکسان است؛
- ادعا نمی‌شود متن شبیه placeholder در literal/comment parse یا پشتیبانی می‌شود.

آزمون زنده می‌تواند نام تکراری را در عبارت معتبر بیازماید. تست‌های unit/fake مدرک برخورد پیشوند و نگاشت نامعتبر باقی می‌مانند.

## قرارداد query تهی یا خالی

تست‌های قراردادی فعلی این موارد را ثابت می‌کنند:

- `BuiltQuery(null, ...)` به query آمادهٔ null تبدیل می‌شود، اعتبارسنجی پارامتر را رد می‌کند، اتصال می‌گیرد، یک callback از نوع Failure می‌دهد و statement آماده نمی‌کند.
- SQL فقط شامل فاصله به `prepareStatement` فرستاده می‌شود؛ خطای آن در یک callback از نوع Failure تحویل می‌شود. executor آن را trim یا طبقه‌بندی نمی‌کند.
- رفتار render-null در مرز caller/rendering است و به یکپارچه‌سازی JDBC با MySQL مربوط نیست.

رفتار دقیق را حفظ کنید. null و خالی را یکی نکنید و normalization اضافه نکنید.

## مرز خطا

| مرز | رفتار فعلی | شواهد / راستی‌آزمایی مورد انتظار |
|---|---|---|
| ناسازگاری پارامتر | اعتبارسنجی پیش از `DatabaseConnection.build()` انجام می‌شود. | unit/contract: `IllegalArgumentException` همزمان، بدون اتصال و callback. |
| گرفتن اتصال | `DatabaseConnection.build()`، SQLException را در RuntimeException می‌پیچد؛ callback عملیاتی اجرا نمی‌شود. | تست fake Driver؛ probe زنده فقط محیط را عیب‌یابی می‌کند. |
| SQLException در prepare | یک callback از نوع Failure. | تست fake JDBC؛ لازم نیست آن را در server زنده القا کنید. |
| SQLException در bind | خطای `SqlParameter.bind` به یک Failure تبدیل می‌شود. | تست fake JDBC؛ اجرای زنده bind عادی را بررسی می‌کند. |
| SQLException در query/update/execute | یک callback از نوع Failure. | fake JDBC؛ خطای زندهٔ امن فقط در صورت قطعی و بدون تغییر داده. |
| بازیابی/بستن کلید تولیدشده | Failure پیش از یک callback پایانی. | fake JDBC؛ مسیر auto-increment زنده فقط موفقیت را ثابت می‌کند. |
| SQLException/runtime از callback مصرف‌کننده | propagate می‌شود؛ callback ورود مجدد ندارد. | تست قراردادی fake JDBC. |
| بستن ResultSet در callback | خطای مصرف‌کننده propagate می‌شود؛ ورود مجدد رخ نمی‌دهد. | تست قراردادی fake JDBC. |
| بستن statement/connection پس از callback | خطا propagate می‌شود و callback تکرار نمی‌شود. | تست قراردادی fake JDBC. |
| Boolean مربوط به DDL در JDBC | نادیده گرفته می‌شود؛ موفقیت `Success(true)` است. | fake مقدار true/false را پوشش می‌دهد؛ DDL بی‌خطر زنده موفقیت را تأیید می‌کند. |

برای هر Throwable یک قاعدهٔ تبدیل به Failure فرض نکنید. source، SQLException را در عملیات JDBC می‌گیرد، اما خطاهای callback مصرف‌کننده و close منبع ممکن است propagate شوند. نوع exception و تعداد callback را برای هر مرز ثبت کنید.

## پوشش تست موجود

- `data_base/core/.../BuiltQueryTest.kt`: رخداد placeholder، اعتبارسنجی، تکرار و قرارداد فراخوانی binder.
- `data_base/manager/execute/.../QueryExecuteContractTest.kt`: Driver/proxy جعلی برای شاخه‌های شبیه‌سازی‌شدهٔ عملیات، callback و منابع.
- `data_base/manager/execute/.../QueryExecuteMySqlIntegrationTest.kt`: SELECT پارامتری زنده و اختیاری؛ اگر متغیرهای لازم نباشند skip می‌شود.
- تست‌های `data_base/migration/executor`: رفتار migration با بدل‌ها؛ شواهد JDBC زنده نیست.
- `data_base/query/executor`: source اجرایی و وابستگی به `manager:execute`؛ در مسیرهای بررسی‌شده منبع تست اختصاصی پیدا نشد.

تعداد موفق، ناموفق و skipشده را جداگانه گزارش کنید. تست یکپارچه‌سازی skipشده، پوشش محسوب نمی‌شود.

## طبقه‌بندی لایه‌های تست

| لایه | نوع شاهد | ادعایی که پشتیبانی می‌کند |
|---|---|---|
| Unit | تست‌های BuiltQuery/resolver/binder | ترتیب tokenها، اعتبارسنجی، JDBC type map و شکل فراخوانی binder. |
| قرارداد اجرا | تست قراردادی fake JDBC | تعداد callback، خطاهای شبیه‌سازی‌شده، بستن منابع و شاخه‌های INSERT/DDL. |
| یکپارچه‌سازی MySQL | Connector/J 8.0.33 و server واقعی | تبدیل و بازخوانی وابسته به driver و فقط سناریوهای CRUD/DDL که واقعاً اجرا شده‌اند. |
| Regression | مجموعه‌های migration/query-executor و buildها | سازگاری dispatch پایین‌دستی و کامپایل. |

شواهد fake JDBC را یکپارچه‌سازی زنده توصیف نکنید و کامپایل را راستی‌آزمایی رفتاری ندانید.

## راستی‌آزمایی regression

پس از آماده‌شدن محیط MySQL دورریختنی، مجموعه‌های متمرکز موجود را اجرا کنید:

1. تست‌های `data_base:core`.
2. تست‌های قراردادی و یکپارچه‌سازی `data_base:manager:execute`، بدون skip شدن آزمون یکپارچه‌سازی.
3. تست‌های `data_base:migration:executor` برای حفظ رفتار migration.
4. تست‌های `data_base:query:executor` در صورت وجود؛ وگرنه source اجرایی را کامپایل و نبود منبع تست را گزارش کنید.
5. کامپایل مثال query فقط اگر پیاده‌سازی مجازشده‌ای بعداً source را تغییر دهد.

این پلن اکنون درخواست اجرای build یا تست نمی‌دهد. در گزارش راستی‌آزمایی بعدی، نام دقیق taskهای Gradle، نتیجه و skipها را بنویسید. اگر اصلاحی جداگانه مجاز شد، `git diff --check`، امضاها و گراف وابستگی را بررسی کنید.

## تغییرات مجاز

هنگام اجرای این پلن، فعالیت به این موارد محدود است: بررسی فقط‌خواندنی مخزن؛ تنظیم متغیرهای opt-in بیرون از فایل‌های مخزن؛ اجرای تست/build موجود پس از آماده‌سازی محیط؛ ساخت و پاک‌کردن اشیای متعلق به تست در schema صریحاً دورریختنی؛ و تولید گزارش شواهد جداگانه با اطلاعات محرمانهٔ حذف‌شده.

اگر نقصی مانع سناریو شد، آن را متوقف کنید، شواهد را ثبت و کوچک‌ترین اصلاح لازم را برای مجوز جداگانه پیشنهاد دهید. خود این پلن مجوز تغییر source/test/documentation نمی‌دهد.

## تغییرات ممنوع

- Execution Engine، dispatcher، abstraction برای binder، mapper، لایهٔ transaction، pool، retry، cache، batch یا API ناهمگام جدید نسازید.
- `manager:execute` را به `query:executor` منتقل نکنید و جهت وابستگی/مالکیت ماژول را تغییر ندهید.
- برای پاک‌سازی، API عمومی، `ExecuteResult`، SQL rendering، دستور زبان placeholder یا قرارداد callback را تغییر ندهید.
- هنگام اجرای پلن، source تولیدی، تست، مستندات، Gradle یا ساختار مخزن را تغییر ندهید.
- Connector/J اضافه یا به‌روز نکنید.
- SQL مخرب را روی پایگاه‌دادهٔ مشترک/غیردورریختنی اجرا نکنید؛ schemaهای نامرتبط را introspect نکنید.
- مقدار پارامتر را به SQL الحاق نکنید یا URL/محیط حاوی اطلاعات محرمانه را log نکنید.
- تست skipشده، fake JDBC یا کامپایل را به‌عنوان PASS یکپارچه‌سازی واقعی حساب نکنید.

## معیارهای PASS

فقط در صورت وجود شواهد همهٔ موارد زیر، نتیجه را **PASS** اعلام کنید:

1. Connector/J نسخهٔ 8.0.33 resolve شده و نسخهٔ واقعی MySQL Server ثبت شده باشد؛ بازهٔ پشتیبانی اثبات‌نشده اعلام نشود.
2. متغیرهای لازم به‌صورت امن تنظیم شده و آزمون یکپارچه‌سازی skip نشده باشد.
3. برای تمام نوع‌های پشتیبانی‌شدهٔ resolver، از جمله Long بزرگ و null نوع‌دار، bind و بازخوانی زنده با assertion صریح موجود باشد. هر محدودیت `Types.OTHER` و تصمیم قرارداد آن ثبت شده باشد.
4. INSERT/SELECT/UPDATE/DELETE زنده روی جدول دورریختنی، مقدارها، تعداد ردیف‌ها و کلید Long تولیدشدهٔ مورد انتظار را تأیید کنند.
5. DDL موفق `Success(true)` بدهد؛ رفتار خطای امن نیز اگر آزموده شده، تأیید شود.
6. شمار callbackهای زنده و مالکیت ResultSet درست باشد؛ شاخه‌های شبیه‌سازی‌شدهٔ exception/close همچنان در تست قراردادی پاس شوند.
7. تست‌های BuiltQuery، manager execute و regression پایین‌دستی پاس شوند و skip بی‌توضیح در مجموعه‌های لازم وجود نداشته باشد.
8. برای سناریوهای ادعاشده تصمیم قراردادی بحرانی حل‌نشده نمانده باشد؛ داده/schema تست پاک‌سازی شده باشد.

شواهد زنده را از شواهد fake JDBC و بررسی ایستای source جدا گزارش کنید.

## معیارهای BLOCKED

در هرکدام از حالت‌های زیر نتیجه را **BLOCKED** گزارش کنید، نه PASS: نبود متغیرهای اتصال یا دسترسی امن لازم؛ شکست اتصال؛ skip شدن تست یا موفقیت صرفاً در probe؛ ناتوانی در بررسی رفتار نوع/null/key لازم؛ نامطمئن بودن مالکیت/پاک‌سازی schema دورریختنی؛ شکست یا نامشخص‌بودن سناریوی بحرانی CRUD/DDL/callback/چرخهٔ عمر؛ تفاوت نسخهٔ resolveشدهٔ Connector/J از baseline بدون توضیح؛ جایگزین‌شدن fakeها به‌جای شواهد زنده؛ یا شکست/skip در regressionهایی که پوشش لازم را ناقص می‌کند.

پرسش دربارهٔ بازهٔ نسخه‌های server می‌تواند خارج از scope بماند، به شرط اینکه گزارش ادعا را به همان نسخهٔ دقیق مشاهده‌شده محدود کند. ابهام SQL NULL در کلید تولیدشده را جداگانه نگه دارید، مگر شواهد یا قرارداد مالک آن را ببندد.

## قرارداد نهایی

Execution Core همان `IQueryExecute` / `QueryExecute` در `data_base/manager/execute` باقی می‌ماند و از `DatabaseConnection`، `BuiltQuery`، `SqlParameter.bind` و callbackهای فعلی `ExecuteResult` استفاده می‌کند. Connector/J نسخهٔ 8.0.33 baseline مخزن است. راستی‌آزمایی زنده با MySQL دورریختنی و متغیرهای opt-in موجود انجام می‌شود. پارامترهای نام‌دار به ترتیب رخداد متنی bind می‌شوند؛ ناسازگاری پیش از اتصال اعتبارسنجی می‌شود. ResultSet مربوط به SELECT محدود به callback است و caller آن را می‌بندد. ResultSet کلیدهای تولیدشده، statement و connection تحت مدیریت executor هستند. CRUD، کلید تولیدشده، ماتریس نوع‌های اعلام‌شده و DDL فقط با سناریوهایی اثبات می‌شوند که واقعاً روی MySQL اجرا شده باشند؛ شاخه‌های خطای تزریق‌شده شواهد قرارداد اجرا باقی می‌مانند.

## خارج از دامنه

پیاده‌سازی/بازآرایی؛ abstraction اجرایی یا تغییر وابستگی؛ ادعای کلی سازگاری MySQL؛ اعتبارسنجی/introspection schema تولیدی؛ تغییر یکپارچه‌سازی migration؛ semantics تراکنش، pool، retry، batch، cache یا اجرای ناهمگام؛ نگاشت مدل/ORM/repository؛ parse کامل SQL یا parse placeholder داخل literal/comment؛ بازطراحی رفتار null/blank، Boolean مربوط به DDL یا نوع نتیجه؛ و سیاست SQL NULL برای کلید تولیدشده بدون شاهد/قرارداد مالک.

## آمادگی پیاده‌سازی / راستی‌آزمایی

**پلن راستی‌آزمایی: آماده. راستی‌آزمایی زندهٔ فعلی: مسدود.** قراردادهای مبتنی بر source و سناریوهای لازم مشخص شده‌اند. تا زمانی که محیط و schema دورریختنی فراهم نشوند، نمی‌توان دربارهٔ رفتار MySQL ادعایی کرد. این پلن آمادگی پیاده‌سازی را تغییر نمی‌دهد؛ هر اصلاح source به شواهد و مجوز جداگانه نیاز دارد.
