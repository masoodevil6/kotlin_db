# Migration v1.5: MODIFY COLUMN Contract

وضعیت: `implemented`

## پیش‌شرط و هدف

این operation پس از تکمیل `v1.4 RENAME COLUMN` طراحی و اجرا شود. در تاریخچه فعلی repository، `v1.3` مربوط به `DROP COLUMN` است؛ این plan شماره‌ها را با تاریخچه واقعی ادامه می‌دهد، نه با مثال نسخه‌بندی متفاوت موجود در پیشنهاد اولیه.

هدف، تعریف operation مستقل `MODIFY COLUMN` برای جایگزینی تعریف یک ستون موجود است. عملیات باید از pipeline فعلی API → AST → Builder → Dialect/Renderer → Executor عبور کند و اجرای DDL را به `data_base:manager` موجود بسپارد.

## مبنا و traceability

- قبل از implementation، قراردادهای جاری `ADD COLUMN`، `CREATE TABLE` و `RENAME COLUMN v1.4` از API تا renderer و executor بررسی شوند.
- `IMigrationColumnAst` موجود در `data_base/migration/ast/.../interfaces/create_table/column/` و `MigrationColumnAst` موجود در schema فعلی نامزد reuse برای تعریف ستون‌اند. در مرحله traceability هر property و رفتار renderer بررسی شود؛ reuse تنها وقتی انجام شود که semantics یکسان بماند.
- در traceability، مجموعهٔ دقیق typeهای قابل قبول برای v1.5 باید از API/type model و renderer موجود استخراج و در همین plan ثبت شود: typeهای پشتیبانی‌شده به‌صورت فهرست بسته مشخص شوند و typeهای دیگر صریحاً رد شوند. «هر چیزی که renderer فعلی اتفاقاً می‌تواند چاپ کند» به‌تنهایی معیار پذیرش یا مجوز گسترش scope نیست.
- نتیجهٔ traceability انجام‌شده: فهرست بستهٔ v1.5 شامل `VarcharType`, `TextType`, `IntType`, `BooleanType`, `DecimalType`, و `JsonType` است. هیچ type دیگری وجود ندارد یا پذیرفته نمی‌شود؛ افزودن type جدید نیازمند تغییر contract است.
- ترتیب traceability پیش از implementation: تعیین فهرست نهایی typeها؛ بررسی `MigrationColumnAst`؛ بررسی `MigrationColumnBuilder`؛ بررسی column renderer؛ و سپس ثبت تصمیم reuse یا no-reuse. پس از آن کوچک‌ترین تغییر سازگار با این contract پیاده‌سازی شود.
- API/AST سطح operation مستقل `ModifyColumn` باشد؛ AST مربوط به `ADD COLUMN` یا `CREATE TABLE` به‌عنوان AST عملیات استفاده نشود.
- `MigrationColumnBuilder` و renderer تعریف ستون نیز فقط در صورت سازگاری واقعی reuse شوند. `AUTO_INCREMENT` باید به‌درستی برای `MODIFY` مدل شود؛ اگر renderer فعلی `PRIMARY KEY` را وارد column definition می‌کند، reuse مستقیم آن رد شود. grammar نامعتبر یا semantics ناخواسته پذیرفته نیست.
- نتیجهٔ traceability: `MigrationColumnAst` برای CREATE TABLE دارای `columnPrimary` است، stateهای nullability و auto increment را به‌صورت Boolean با default false نگه می‌دارد و default را با `hasColumnDefault` از مقدار null جدا می‌کند. renderer مشترک `MySqlMigrationColumnCapability`، `PRIMARY KEY` را نیز رندر می‌کند؛ بنابراین AST، Builder و renderer مشترک مستقیماً reuse نمی‌شوند. v1.5 از operation AST/Builder/renderer مستقل استفاده می‌کند تا invariantهای replacement و عدم نشت PK حفظ شوند.
- اصل تصمیم reuse در v1.5 چنین است: **correctness > reuse > DRY**. `MigrationColumnAst` یا renderer آن صرفاً برای کاهش تکرار وارد این operation نشود. اگر reuse، `PRIMARY KEY` یا metadata خارج از scope را وارد خروجی کند، یا abstraction مشترک scope را بی‌دلیل گسترش دهد، reuse کنار گذاشته شود.
- وابستگی واقعی v1.5 به contract مشترک `v1.2` در traceability بررسی شود. اگر v1.5 به آن وابسته است و هنوز `planned` مانده، ابتدا آن contract تعیین تکلیف شود؛ اگر وابستگی‌ای وجود ندارد، استقلال v1.5 از آن مستند شود و صرفاً به‌خاطر شماره نسخه implementation متوقف نشود.

## محدوده

در این نسخه:

- تغییر تعریف یک ستون موجود در هر operation، با حفظ نام ستون.
- شروع با MySQL dialect.
- پشتیبانی فقط از typeهایی که پس از traceability به‌صورت فهرست دقیق و بسته در همین plan ثبت می‌شوند؛ typeهای پشتیبانی‌نشده رد می‌شوند.
- «تعریف کامل» در این plan یعنی **full supported column definition**: نام ستون، type و attributeهای پشتیبانی‌شدهٔ v1.5؛ نه همهٔ metadata یا schema objectهایی که ممکن است در دیتابیس وجود داشته باشند.
- attributeهای column-definition پشتیبانی‌شده در v1.5: type، nullability صریح، default state صریح و `AUTO_INCREMENT`.
- اجرای DDL با executor و manager فعلی.
- مثال نسخه‌بندی‌شده و unit testهای بدون دیتابیس.

خارج از محدودهٔ قطعی v1.5؛ افزودن هر موردی از این فهرست نیازمند به‌روزرسانی plan پیش از implementation است:

- تغییر نام ستون (`RENAME COLUMN` یا `CHANGE COLUMN`).
- تغییر چند ستون در یک statement.
- `FIRST` / `AFTER` و جابه‌جایی ترتیب ستون‌ها.
- افزودن یا حذف `PRIMARY KEY`، unique/index، foreign-key constraint و cascade.
- attributeهای خارج از فهرست پشتیبانی v1.5 مانند comment، generated expression، column visibility و سایر metadataهای اختصاصی دیتابیس.
- behavior شبیه `IF EXISTS`، rollback، migration history و runner.
- dialectهای غیر از MySQL.

## تصمیم قراردادی blocker: full supported definition، نه patch ضمنی

`MODIFY COLUMN` تعریف موردنظر را به‌عنوان replacement ارائه می‌کند؛ API مبهمی که فقط چند تغییر دلخواه بگیرد می‌تواند ناخواسته ویژگی‌های فعلی ستون را از بین ببرد. به همین دلیل DSL باید یک **full supported column definition** نهایی و صریح بسازد، نه patch با semantics ضمنی. «کامل» فقط attributeهای پشتیبانی‌شدهٔ همین نسخه را شامل می‌شود و به معنی بازسازی تمام metadata یا schema objectهای MySQL نیست.

پیش از implementation باید برای هر property تصمیم قطعی ثبت شود:

- type الزامی است.
- nullability فقط دو state معتبر دارد: `NULL` و `NOT_NULL` (در SQL: `NULL` و `NOT NULL`). stateای مانند `UNSPECIFIED` تعریف نشود. `isNullable(true)` به `NULL` و `isNullable(false)` به `NOT NULL` نگاشت می‌شود؛ فراخوانی‌نشدن setter خطای validation در Builder است.
- default دقیقاً سه state دارد: `NO_DEFAULT_CLAUSE`، `DEFAULT_NULL` و `DEFAULT_VALUE(value)`. فراخوانی‌نشدن setter یعنی `NO_DEFAULT_CLAUSE`؛ `default(null)` یعنی `DEFAULT_NULL`، نه حذف clause.
- `AUTO_INCREMENT` باید state صریح `true` یا `false` داشته باشد؛ مدل nullable/سه‌حالته مجاز نیست. setter مفهومی `autoIncrement(true/false)` است و نبود آن خطای validation است.
- مقدار default فقط از ورودی literal پشتیبانی‌شده‌ای serialize شود که traceability renderer فعلی تأیید می‌کند. رشته‌ای مثل `"Unknown"` باید به literal رشته‌ای SQL تبدیل شود و هرگز به‌عنوان SQL خام/expression تفسیر نشود. Expression default مانند `CURRENT_TIMESTAMP` در v1.5 پشتیبانی نمی‌شود، مگر اینکه traceability وجود یک مدل expression صریح و سازگار در repository را اثبات کند؛ در غیر این صورت باید رد شود. فهرست نوع‌های literal پذیرفته‌شده در traceability ثبت شود.
- `PRIMARY KEY` صریحاً خارج از contract v1.5 است: `MODIFY COLUMN` نباید آن را اضافه کند، حذف کند یا از metadata موجود استنباط کند. همین قاعده برای `UNIQUE`، index، foreign key و constraintهای دیگر برقرار است؛ operationهای جداگانه برای آن‌ها لازم است.
- `AUTO_INCREMENT` ممکن است به نوع ستون و وجود key/index مناسب وابسته باشد. v1.5 نباید برای معتبرکردن آن `PRIMARY KEY` یا index بسازد؛ اگر ترکیب موردنظر را دیتابیس نپذیرفت، خطای اصلی manager/database حفظ شود و primary key نیز استنباط نشود.
- renderer فقط full supported definition را می‌سازد. attribute پشتیبانی‌نشده نباید نادیده گرفته یا از schema introspection تکمیل شود؛ ورودی رد و محدودیت مستند شود.
- هیچ attributeای معنای ضمنی «حفظ مقدار فعلی دیتابیس» ندارد و برای ساخت definition از schema introspection استفاده نمی‌شود.
- `ModifyColumn` باید هر attribute پشتیبانی‌شدهٔ الزامیِ تنظیم‌نشده را رد کند. semantics دیتابیس هنگام اجرای attributeهایی که صریحاً رندر شده‌اند را می‌توان در تست integration مستند کرد. نبود clause پیش‌فرض فقط از state صریح `NO_DEFAULT_CLAUSE` می‌آید و با omitted required state یکی نیست.

## Contract invariants

یک `ModifyColumn` AST معتبر است فقط اگر برای همهٔ attributeهای پشتیبانی‌شده state مطلوب صریح داشته باشد. invariant تعریف عبارت است از:

```text
ModifyColumn definition
├── columnName       required, non-blank
├── columnDataType   required, belongs to the explicit v1.5 supported-type list
├── nullability      exactly one of { NULL, NOT_NULL }
├── default          exactly NO_DEFAULT_CLAUSE, DEFAULT_NULL, or DEFAULT_VALUE(value)
└── autoIncrement    exactly true or false
```

- هیچ state ضمنی برای «حفظ وضعیت فعلی دیتابیس» وجود ندارد.
- `ModifyColumn` metadata ستون را با introspection واکشی یا تکمیل نمی‌کند.
- `ModifyColumn` فقط desired definition را حمل می‌کند؛ renderer به existing column definition یا وضعیت قبلی ستون دسترسی ندارد.
- `PRIMARY KEY`، index، `UNIQUE`، foreign key، comment، generated expression، visibility و metadataهای پشتیبانی‌نشده وارد definition تولیدشده نمی‌شوند.
- `NO_DEFAULT_CLAUSE` یعنی renderer عبارت `DEFAULT` تولید نمی‌کند؛ `DEFAULT_NULL` یعنی `DEFAULT NULL` تولید می‌کند.
- representation داخلی nullability (برای نمونه Boolean یا enum) جزئیات implementation است و در contract تثبیت نمی‌شود؛ invariant قراردادی فقط `nullability ∈ { NULL, NOT_NULL }` است. هیچ representation داخلی نباید state سومی مانند unspecified بسازد. اگر مدل فعلی repository این دو state را بدون ابهام نمایش نمی‌دهد، reuse مستقیم آن مجاز نیست.

شکل مفهومی DSL باید همهٔ stateهای الزامی را نشان دهد؛ نام setterها در implementation با convention واقعی `ADD COLUMN` هماهنگ می‌شود:

```kotlin
modifyColumn {
    tableName("users")
    name("name")
    dataType(VarcharType(255))
    isNullable(true)
    default("Unknown")
    autoIncrement(false)
}
```

خروجی مفهومی MySQL:

```sql
ALTER TABLE `users`
MODIFY COLUMN `name` VARCHAR(255) NULL DEFAULT 'Unknown'
```

Identifierها bind parameter نیستند و باید با convention فعلی quoting/escaping dialect وارد SQL شوند؛ v1.5 سازوکار quote تازه‌ای اختراع نمی‌کند. مقادیر literal default مطابق رفتار فعلی renderer تعریف ستون serialize/escape شوند؛ اگر reuse ایمن renderer ممکن نیست، منطق با تست دقیق پوشش داده شود.

## مدل AST و API

مدل مفهومی مورد انتظار:

```text
ModifyColumn
├── tableName
└── columnDefinition
    ├── columnName
    ├── columnDataType: one of the explicitly listed v1.5 supported types
    ├── nullability: exactly one of { NULL, NOT_NULL }
    ├── defaultDefinition
    │   ├── NO_DEFAULT_CLAUSE
    │   ├── DEFAULT_NULL
    │   └── DEFAULT_VALUE(value)
    └── autoIncrement: Boolean صریح
```

- `IMigrationModifyColumnAst` و `MigrationModifyColumnAst` مستقل باشند.
- AST یک desired definition کامل را نگه دارد؛ reuse از `IMigrationColumnAst` برای child definition فقط پس از traceability و حفظ invariantها مجاز است، اما AST operation مستقل می‌ماند.
- API در namespace مستقل `modify_column` قرار گیرد و با API `ADD COLUMN` تا جایی که semantics یکسان است هم‌نام بماند.
- Builder نام جدول و ستون را trim کند و مقدار normalized را در AST بگذارد. ورودی‌های خالی/whitespace-only رد شوند.
- Builder type و propertyهای اجباری/صریح را validate کند؛ Renderer هم AST را دفاعی پیش از quote کردن یا SQL composition validate کند.
- نبود setterهای اجباری برای type، nullability، default state یا `autoIncrement` باید در Builder رد شود؛ این کمبودها نباید با nullable field در AST به renderer منتقل شوند.
- Builder مسئول رد نام خالی جدول/ستون، type یا state اجباریِ تعیین‌نشده و ورودی API پشتیبانی‌نشده است. Renderer به‌صورت دفاعی AST مستقیم/بدساخت را بررسی می‌کند: identifier نامعتبر، type malformed یا پشتیبانی‌نشده، state نامعتبر و ناسازگاری AST باید پیش از quote یا composition SQL رد شوند.
- `default(null)` باید از setter فراخوانی‌نشده قابل تفکیک بماند و دقیقاً `DEFAULT_NULL` بسازد.
- `PRIMARY KEY` و schema-level constraintها نباید در child definition وارد شوند؛ reuse از `IMigrationColumnAst` فقط در صورت امکان حذف قطعی این semantics مجاز است.

## Renderer و SQL

- capability مستقل `MODIFY COLUMN` در dialect contract تعریف و در MySQL registry ثبت شود.
- شکل خروجی:

```sql
ALTER TABLE <quoted-table> MODIFY COLUMN <full-supported-column-definition>
```

- ستون موجود با نام تازه معرفی نشود؛ این operation حق rename ندارد.
- identifier quoting و escaping dialect-specific باشد.
- SQL در renderer ساخته شود؛ renderer database connection، executor یا JDBC را نشناسد.
- تست دقیق برای SQL نمونه و تمام type/propertyهای پذیرفته‌شده اضافه شود.
- renderer فقط desired definition موجود در AST را مصرف کند؛ هیچ existing column definition یا metadata قبلی به renderer داده نشود.
- ترتیب attributeهای SQL مستقل از ترتیب فراخوانی DSL باشد و از convention renderer فعلی column پیروی کند؛ ترتیب callهای Builder نباید به SQL نشت کند.
- constraints/indexes نباید به‌صورت ناخواسته ساخته یا حذف شوند. اگر shared column renderer باعث این رفتار می‌شود، reuse مستقیم آن رد شود.
- `AUTO_INCREMENT` فقط از desired AST رندر شود؛ renderer وضعیت فعلی دیتابیس را introspect یا ضمنی حفظ نکند.
- نبود default در desired AST یعنی clause `DEFAULT` تولید نشود، حتی اگر ستون موجود default داشته باشد؛ این operation patch نیست.
- primary key در definition خروجی قرار نگیرد و این operation هیچ primary-key DDL تولید نکند.
- تست صریح باید ثابت کند SQL تولیدشده برای این operation، حتی وقتی ستون فعلی در دیتابیس primary key است، شامل `PRIMARY KEY` نیست. این تست فقط SQL تولیدشده را بررسی می‌کند و دربارهٔ باقی‌ماندن یا حذف‌شدن PK پس از اجرای دیتابیس ادعایی ندارد.

## Executor، خطا و dependency direction

- overload لازم به `IMigrationExecutor` افزوده شود و از `IQueryExecute.executeTable` موجود عبور کند.
- `ifExists` یا suppression خطای implicit افزوده نشود؛ missing table/column و خطاهای type conversion/incompatible data با cause اصلی failure بمانند.
- تست fake باید `IQueryExecute` واقعی موجود را در مرز executor هدف بگیرد؛ abstraction تولیدی جدید فقط برای تست ساخته نشود.
- API/AST/Builder/Dialect/Renderer مستقل از اتصال و JDBC بمانند.
- executor migration عملیات را مصرف کند و اجرای SQL را به manager abstraction موجود واگذار کند؛ dependency direction فعلی عوض نشود.

## مثال و تست

- مثال نسخه‌بندی‌شده در مسیر واقعی convention `v1/migrations/modify_column/` اضافه شود. اجرا پیش‌فرض render-only باشد و DDL با opt-in صریح اجرا شود.
- تست‌ها بدون database اجرا شوند و موارد زیر را پوشش دهند:
  - AST مستقل و هر سه حالت default: setter فراخوانی‌نشده → `NO_DEFAULT_CLAUSE`، `default(null)` → `DEFAULT_NULL`، `default("Unknown")` → `DEFAULT_VALUE("Unknown")`.
  - trim و رد نام‌های خالی.
  - رد type یا propertyهای مورد نیاز ناقص.
  - serialization مقادیر default، از جمله quote، null و مقادیر پشتیبانی‌نشده.
  - replacement matrix که فقط AST مطلوب را به renderer می‌دهد و state ستون موجود را ورودی renderer نمی‌کند:

    | Existing state (سناریوی توضیحی، خارج از ورودی renderer) | Desired state | Expected SQL attribute |
    |---|---|---|
    | `NULL` | `NOT_NULL` | `NOT NULL` |
    | `NOT NULL` | `NULL` | `NULL` |
    | `DEFAULT 'A'` | `NO_DEFAULT_CLAUSE` | بدون `DEFAULT` |
    | بدون default | `DEFAULT_VALUE('B')` | `DEFAULT 'B'` |
    | `DEFAULT 'A'` | `DEFAULT_NULL` | `DEFAULT NULL` |
    | `AUTO_INCREMENT` | `false` | بدون `AUTO_INCREMENT` |
    | بدون `AUTO_INCREMENT` | `true` | `AUTO_INCREMENT` |
    | `AUTO_INCREMENT` | `true` | `AUTO_INCREMENT` |
  - semantics replacement: `NO_DEFAULT_CLAUSE` نباید clause موجود را در SQL حفظ کند؛ state صریح `DEFAULT_VALUE` یا `DEFAULT_NULL` باید دقیقاً رندر شود.
  - semantics replacement برای `AUTO_INCREMENT`: false باید attribute را حذف و true باید آن را اضافه کند؛ هر دو مقدار صریح‌اند.
  - آزمون عدم نشت `PRIMARY KEY`: سناریوی توضیحی ستون موجود با `PRIMARY KEY + AUTO_INCREMENT` و desired definition شامل type جدید، `NOT NULL`، `NO_DEFAULT_CLAUSE` و `autoIncrement(false)` باشد؛ assertion فقط بررسی کند SQL تولیدشده `PRIMARY KEY` ندارد. دربارهٔ باقی‌ماندن PK پس از اجرای دیتابیس assertion نشود.
  - identifier escaping برای نام عادی، دارای underscore، دارای backtick مثل `user``data` و reserved wordهایی مثل `order`، `group` و `select`، در حدی که با convention فعلی renderer سازگار است.
  - خروجی دقیق برای nullable/non-nullable و typeهای پشتیبانی‌شده.
  - ترتیب فراخوانی DSL بر AST معنایی یا SQL اثر نگذارد: برای نمونه، فراخوانی `default(...)` پیش از `dataType(...)` باید همان desired definition را بسازد و همان SQL را تولید کند که فراخوانی همان setterها به ترتیب معمول؛ دو ترتیب فراخوانی با stateهای مطلوب یکسان باید SQL یکسان بدهند. ترتیب attributeهای SQL تابع convention renderer موجود باشد.
  - identifier escaping و validation دفاعی AST در renderer.
  - executor: ارسال BuiltQuery، callback موفقیت و حفظ خطا.
- integration test فقط در MySQL اختصاصی و با داده آزمایشی قابل cleanup؛ تبدیل type ممکن است داده را نامعتبر یا truncate کند، بنابراین مثال عادی نباید آن را خودکار اجرا کند.
- تست regression operationهای پیشین در اجرای نهایی اجرا شود.

- نمونه SQL، semantics full supported definition، handling `DEFAULT NULL` در مقابل نبود clause، `AUTO_INCREMENT` صریح، خارج‌بودن `PRIMARY KEY`/constraintها و نسخه MySQL هدف مستند شوند.
- انواع literal default پشتیبانی‌شده و ردشدن expression defaultها (از جمله تصمیم صریح دربارهٔ `CURRENT_TIMESTAMP`) در مستندات ثبت شوند.
- هر تصمیمی که هنگام traceability از این contract خارج می‌شود، ابتدا در همین plan ثبت شود.
- فهرست بستهٔ typeهای پشتیبانی‌شده و typeهای ردشدهٔ v1.5 پیش از implementation در بخش traceability همین plan ثبت شود؛ هر گسترش بعدی نیازمند به‌روزرسانی contract است.

## معیار پذیرش

1. operation مستقل `MODIFY COLUMN` در API/AST/Builder/Renderer/Executor قابل ردیابی است.
2. full supported column definition semantics روشن و صریح برای type، nullability، default state و `AUTO_INCREMENT` دارد و فهرست بستهٔ typeهای پذیرفته/ردشده در plan ثبت شده است.
3. SQL معتبر MySQL با quoting/escaping صحیح render می‌شود.
4. propertyهای پشتیبانی‌نشده یا AST ناقص پیش از تولید SQL رد می‌شوند.
5. constraints/indexes به‌صورت ضمنی اضافه یا حذف نمی‌شوند.
6. execution از manager فعلی استفاده می‌کند و خطاها را حفظ می‌کند.
7. مثال render-only و unit test بدون DB وجود دارند و regressionهای قبلی pass هستند.
8. docs و dependency direction به‌روز می‌شوند؛ plan پس از Definition of Done به `implemented` می‌رود.

## نقشهٔ راه اطلاع‌رسانی پس از v1.5

پس از تکمیل operationهای پایه تغییر schema، ترتیب پیشنهادی برای scopeهای بعدی چنین است:

```text
v1.4 RENAME COLUMN
    ↓
v1.5 MODIFY COLUMN
    ↓
INDEX operations (CREATE / DROP / UNIQUE)
    ↓
CONSTRAINT operations (PRIMARY KEY / UNIQUE)
    ↓
FOREIGN KEY
    ↓
Migration History → Runner → Version Tracking → Rollback
```

این roadmap اطلاع‌رسانی است و تعهد ترتیب یا طراحی برای implementationهای بعدی ایجاد نمی‌کند. هر مرحله باید plan مستقل و traceability خودش را داشته باشد؛ افزودن موارد این roadmap به scope همین `MODIFY COLUMN` مجاز نیست.
