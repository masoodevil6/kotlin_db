# Migration v1.4: RENAME COLUMN Contract

وضعیت: `implemented` — مسیر native و سازگاری MariaDB قدیمی پیاده‌سازی و بررسی شده است. compatibility target کلی repository اعلام نشده و به‌عنوان finding ثبت می‌ماند.

## هدف

تعریف operation مستقل `RENAME COLUMN` در `data_base:migration` و ثبت آن در نوبت بعدی توالی عملیاتی واقعی repository. این operation نام یک ستون را در یک جدول عوض می‌کند، بدون آنکه تعریف ستون را تغییر دهد. پیاده‌سازی باید از مسیر فعلی API → AST → Builder → Dialect/Renderer → Executor → `data_base:manager` پیروی کند.

این plan ترتیب اعلام‌شده برای evolution ستون‌ها را رعایت می‌کند: `RENAME COLUMN` پیش از `MODIFY COLUMN` تکمیل می‌شود. بنابراین قرارداد مستقل `MODIFY COLUMN` در `v1.5` قرار می‌گیرد.

## مبنا و traceability

- آخرین operation ثبت‌شده در تاریخچه فعلی `v1.3 DROP COLUMN` است؛ شماره‌گذاری این plan از همین تاریخچه ادامه پیدا می‌کند.
- قراردادهای `RENAME TABLE` و `DROP COLUMN` الگوی مسیر و تست هستند، اما AST و API آنها reuse نمی‌شوند.
- پیش از implementation، وضعیت plan مشترک `v1.2` و کد واقعی `RENAME TABLE` از API تا executor بررسی شود. هر تغییر پذیرفته‌شده در آن قرارداد رعایت شود؛ بازطراحی pipeline خارج از scope است.
- مسیر packageها و نام فایل‌ها از ساختار واقعی operationهای موجود پیروی کند؛ صرفاً برای تطبیق با این plan hierarchy جدید ساخته نشود.

## محدوده

در این نسخه:

- rename کردن یک ستون در هر operation.
- dialect/renderer مربوط به MySQL.
- DSL با سه ورودی: جدول، نام فعلی ستون و نام جدید ستون.
- validation زودهنگام در Builder و validation دفاعی AST در Renderer.
- اجرای DDL از مسیر migration execution موجود و `IQueryExecute.executeTable`.
- مثال نسخه‌بندی‌شده و unit testهای مستقل از database.

خارج از محدوده:

- تغییر type، nullability، default، auto increment یا primary key.
- syntax مربوط به `CHANGE COLUMN` که هم‌زمان نام و تعریف ستون را تغییر می‌دهد.
- rename چند ستون در یک statement، `IF EXISTS`، انتقال جدول، index/constraint و foreign key.
- migration history، runner و rollback.
- dialectهای غیر از MySQL.

## Contract

```text
RenameColumn
├── Input
│   ├── tableName: String
│   ├── name: String       # نام فعلی ستون
│   └── to: String         # نام جدید ستون
├── AST
│   ├── tableName: String
│   ├── name: String
│   └── to: String
│
│   Constraint: هیچ attribute مربوط به column definition ندارد
│   (data type, nullable, default, autoIncrement, primaryKey, ...)
├── Validation
│   ├── هر سه نام پس از trim خالی نباشند
│   └── ستون مبدأ و مقصد پس از trim یکسان نباشند
├── Rendering
│   └── ALTER TABLE <quoted-table> RENAME COLUMN <quoted-old> TO <quoted-new>
└── Execution
    └── delegation به manager موجود؛ خطای دیتابیس بدون پنهان‌سازی حفظ شود
```

نمونه DSL مفهومی:

```kotlin
renameColumn {
    tableName("users")
    name("display_name")
    to("full_name")
}
```

SQL مرجع:

```sql
ALTER TABLE `users` RENAME COLUMN `display_name` TO `full_name`
```

Builder باید ابتدا هر ورودی را trim کند، سپس blank بودن و برابری source و target را روی مقادیر trim‌شده بررسی کند و فقط پس از موفقیت validation همان مقادیر normalized را در AST ذخیره کند. بنابراین `name(" display_name ")` و `to(" display_name ")` به `display_name == display_name` تبدیل و رد می‌شوند. Renderer نیز باید AST را مستقل validate کند: مقادیر null/blank رد شوند و source برابر target رد شود، آن هم پیش از quoting یا ترکیب SQL. Identifierها با quoting و escaping مخصوص dialect وارد SQL می‌شوند و bind parameter نیستند.

## معماری و dependency direction

- API و AST operation مستقل در namespace منطبق با convention واقعی `rename_table` تعریف شوند.
- AST فقط identifier جدول، identifier ستون مبدأ و identifier ستون مقصد را نگه دارد؛ API/AST مربوط به `RENAME TABLE` یا `DROP COLUMN` reuse نشوند.
- AST مربوط به `RENAME COLUMN` نباید هیچ attribute یا semantic از تعریف ستون داشته باشد یا به ارث ببرد؛ از جمله data type، nullable، default، primary key و auto increment. این AST فقط هویت سه identifier را مدل می‌کند.
- Renderer به manager، executor یا اتصال دیتابیس وابسته نشود.
- Executor به API/AST operation مصرف‌کننده بماند و اجرا را به abstraction موجود manager واگذار کند.
- فرض JDBC وارد API، AST، Builder، dialect یا Renderer نشود.
- abstraction production جدید صرفاً برای ساده‌کردن تست ساخته نشود.

## MySQL و سازگاری

Renderer برای سرورهای دارای syntax بومی از `ALTER TABLE ... RENAME COLUMN ... TO ...` استفاده می‌کند. طبق مستندات رسمی، این syntax در MySQL از 8.0 و در MariaDB از 10.5.3 در دسترس است. نسخه سرور واقعی محیط توسعه با `SELECT VERSION()` برابر `10.4.28-MariaDB` است و syntax بومی را ندارد.

برای MySQL قدیمی‌تر از 8.0 و MariaDB قدیمی‌تر از 10.5.3، executor پس از تشخیص version، `SHOW CREATE TABLE` می‌خواند، تعریف کامل و اصلی ستون را استخراج می‌کند و فقط نام ستون را در `CHANGE COLUMN` جایگزین می‌کند. این مسیر باید type، nullability، default، comment، generated expression و سایر بخش‌های تعریف خوانده‌شده از سرور را حفظ کند. اگر استخراج کامل و بدون ابهام ممکن نباشد، باید پیش از اجرای DDL failure بدهد؛ تعریف ناقص یا metadata حدس‌زده‌شده مجاز نیست. queryهای version و SHOW CREATE از `blockQueryInfo` گزارش می‌شوند. مسیر legacy برای خواندن تعریف جدول به مجوز `SHOW CREATE TABLE` نیاز دارد؛ در صورت نبود مجوز یا metadata قابل‌خواندن، عملیات پیش از DDL با خطا متوقف می‌شود.

compatibility target کلی repository و حداقل نسخه grammar دو مورد جدا هستند. اگر repository target اعلام‌شده ندارد، آن را به‌عنوان finding ثبت کن و نسخه‌ای بر اساس نصب محلی به کل library نسبت نده.

### یافته سازگاری در اجرای plan

در فایل‌های پروژه نسخه حداقلی **سرور** MySQL تعیین نشده است؛ `data_base/manager/connection/build.gradle.kts` فقط dependency درایور `mysql-connector-java:8.0.33` را مشخص می‌کند. این عدد نسخه سرور پشتیبانی‌شده را تعیین نمی‌کند. تطبیق نسخه سرور هدف با حداقل نسخه grammar هنوز باید پیش از ادعای سازگاری با نسخه‌های قدیمی سرور انجام شود.

Renderer نباید برای مقصد موجود یا مبدأ غایب SQL شرطی اختراع کند؛ رفتار خطا از دیتابیس عبور می‌کند. هیچ `IF EXISTS` ضمنی اضافه نشود.

## تست‌های مورد انتظار

- SQL مرجع با تطبیق دقیق.
- trim شدن table/source/target و ذخیره مقادیر نرمال‌شده در AST.
- Builder ورودی‌های خالی و whitespace-only را رد کند و پس از trim، source برابر target را رد کند.
- Renderer با AST مستقیم نیز null/blank و source برابر target را پیش از quoting رد کند.
- escaping backtick در هر سه identifier.
- رد AST ناقص در Renderer پیش از ساخت SQL.
- تست executor با fake روی `IQueryExecute`: ارسال BuiltQuery، callback موفقیت، حفظ علت خطا و عبور خطاهای دیتابیس.
- تست‌های Renderer/Builder بدون اتصال به دیتابیس.
- executor برای سرورهای قدیمی version را تشخیص می‌دهد و فقط با definition کامل استخراج‌شده از `SHOW CREATE TABLE` به مسیر legacy `CHANGE COLUMN` می‌رود.
- تست fake برای شاخه‌های native و legacy؛ شاخه legacy باید definition کامل را حفظ کند.
- integration test اختیاری فقط در MySQL/MariaDB اختصاصی و با نام جدول/ستون آزمایشی؛ علاوه بر موفقیت rename، باید با fixture مثلاً `display_name VARCHAR(120) NOT NULL DEFAULT 'New user'` تأیید کند ستون بعد از rename به `full_name` همان type، nullability و default را دارد و مقدارهای موجود آن بدون تغییر باقی مانده‌اند.

## مثال و مستندات

- مثال در نسخه و پوشه مستقل `v1` و `rename_column`، مطابق ساختار واقعی مثال‌های migration.
- اجرای دیتابیس واقعی پیش‌فرض نباشد؛ rendering و تست مستقل از connection اجرا شوند.
- در manager مثال، flag مستقل برای render/execute operation جدید اضافه شود و اجرای DDL تنها با opt-in روشن شود.
- structure docs مربوط به API، AST، Builder، dialect، renderer، executor و example به‌روز شوند.

## معیار پذیرش

1. `RENAME COLUMN` API، AST، Builder و Renderer مستقل و قابل ردیابی دارد؛ entry point/overload executor فقط در صورت نیاز convention فعلی افزوده می‌شود.
2. MySQL SQL دقیق مرجع را تولید می‌کند و identifierها را quote/escape می‌کند.
3. Builder و Renderer ورودی ناقص را در مرز خود رد می‌کنند.
4. اجرای migration مسیر executor و manager موجود را reuse می‌کند؛ اگر convention فعلی به entry point/overload اختصاصی نیاز داشت، همان overload به مسیر موجود delegate می‌کند و خطای اصلی را مخفی نمی‌کند. `RenameColumnExecutor` مستقل ساخته نمی‌شود.
5. مثال render-only و تست‌های بدون database وجود دارند.
6. dependency direction حفظ است و سندهای ساختار به‌روز هستند.
7. plan پس از تکمیل Definition of Done به `implemented` تغییر می‌کند.
