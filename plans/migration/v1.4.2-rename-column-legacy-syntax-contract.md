# Migration v1.4.2: Version-Aware RENAME COLUMN Compatibility

Status: `implemented`

## Goal

Make the existing rename-only operation work on supported MySQL and MariaDB
versions whose grammar does not provide native `RENAME COLUMN`. The configured
`targetDatabaseVersion` selects the SQL generation path. Runtime server metadata
continues to validate whether the selected SQL can execute; it does not silently
select or rewrite the SQL after generation.

This plan follows `v1.4` and `v2.1`. It does not change the meaning of
`RENAME COLUMN` into a column-definition operation.

## Observed contract and problem

The current public operation contains only:

```text
tableName
name       # current column name
to         # target column name
```

The AST remains rename-only and does not store type, nullability, default,
auto-increment, primary-key, or other column-definition properties. Native
`RENAME COLUMN` can use this information. Legacy `CHANGE COLUMN` also requires
the existing full column definition, which is not present in this AST.

Therefore, setting a target such as `MARIA_DB.Version(10, 4, 28)` cannot by
itself produce a valid legacy statement. The definition must be obtained from
the existing database schema before the DDL is composed.

The intended configuration is explicit about both dialect and target:

```kotlin
DatabaseConfig(
    // connection fields...
    dialect = DialectQuery.MARIA_DB,
    targetDatabaseVersion = MARIA_DB.Version(10, 4, 28),
)
```

## Design decision: obtain the definition from the database

Choose the database-introspection route (option B): preserve the concise
rename-only DSL and obtain the source column's actual definition through the
existing `IQueryExecute` / manager boundary during execution.

Do not add column-definition setters to `renameColumn`. Such setters would
make the operation capable of changing the definition and would violate the
v1.4 identity-only AST contract. Do not hard-code a definition in examples or
library code.

Before implementation, trace the current manager result-set lifecycle and the
actual MySQL/MariaDB `SHOW CREATE TABLE` result shape. Reuse the existing
manager abstraction. If a narrow manager method is required to return structured
table-definition metadata safely, add it at the manager boundary; do not put
connection access or JDBC types into migration API, AST, builder, dialect, or
renderer modules.

## Target strategy and grammar scope

`targetDatabaseVersion` alone selects the generation strategy. Detected server
version must never change that selection. Define the native thresholds in this
single place and refer back to them elsewhere:

| Target product/version | Strategy |
| --- | --- |
| MySQL 8.0.0 or newer | Native `RENAME COLUMN` |
| MariaDB 10.5.3 or newer | Native `RENAME COLUMN` |
| Older target within the repository's supported compatibility range, where `CHANGE COLUMN` is supported | Legacy `CHANGE COLUMN` with resolved source definition |
| Target outside the declared compatibility range, unknown product, or no supported grammar | Fail before DDL |

Do not describe legacy grammar only as “older than native.” Record the
repository compatibility target and verify the lower bound and grammar support
for the legacy path. The repository currently has no declared minimum server
version; keep that as a compatibility finding until the project owner defines
it. Do not infer a library-wide support promise from the local MariaDB 10.4.28
installation.

When `targetDatabaseVersion` is absent, retain the current default native
generation behavior. A configured target example is:

```kotlin
DatabaseConfig(
    // connection fields...
    dialect = DialectQuery.MARIA_DB,
    targetDatabaseVersion = MARIA_DB.Version(10, 4, 28),
)
```

That target selects the legacy preparation path. A newer detected server must
not upgrade it to native syntax; a server that cannot run the selected strategy
must be rejected before introspection or DDL.

## SQL generation and execution contract

For the legacy path, preserve the original definition exactly while replacing
only the source identifier with the target identifier. For example, if the
source is `display_name VARCHAR(120) NOT NULL DEFAULT 'New user'`, generate:

```sql
ALTER TABLE `users` CHANGE COLUMN `display_name` `full_name`
VARCHAR(120) NOT NULL DEFAULT 'New user'
```

The resolver/parser must preserve the original column-definition fragment
byte-for-byte where possible instead of rebuilding it from parsed attributes.
Only the source identifier is replaced with the requested target identifier.
The fragment must retain every property needed to preserve the column's
semantics and stored data, including type modifiers, nullability, default,
character set/collation, comment, generated/invisible attributes, and
auto-increment where present. If the implementation cannot resolve a complete,
unambiguous definition, fail before DDL. Never guess omitted attributes.

The renderer stays independent of manager/connection and remains responsible
for dialect quoting and SQL composition. The executor coordinates the
compatibility preparation step using the target-selected strategy, obtains the
definition through manager, asks the existing dialect/renderer path to produce
the final legacy SQL, and delegates DDL execution through the existing
`IQueryExecute` path.

The implementation must trace the existing renderer interfaces before choosing
the smallest operation-specific representation for native SQL versus legacy
SQL requiring a source definition. A narrow value such as the following is a
candidate only if the current interfaces need it:

```kotlin
sealed interface RenameColumnRenderInput {
    data class Native(val tableName: String, val name: String, val to: String) : RenameColumnRenderInput
    data class Legacy(
        val tableName: String,
        val name: String,
        val to: String,
        val columnDefinition: String,
    ) : RenameColumnRenderInput
}
```

Keep the handoff operation-specific. Do not put the resolved definition in the
public rename AST. Do not add a generic migration operation framework or
capability matrix, and do not add a new production abstraction unless tracing
the actual interfaces shows a narrow one is required.

## Runtime validation

- `DatabaseServerInfo` remains the source of truth for actual server
  product/version and execution capability; it validates the target-selected
  strategy but never selects a different strategy.
- Configured target product must match detected product before introspection or
  DDL.
- Validate that the detected server can execute the target-selected strategy
  before any source-definition lookup. For a native target path, reject a
  detected server that cannot execute native `RENAME COLUMN`; do not switch to
  legacy SQL based on detected version. For a legacy target path, verify the
  detected product/version supports the legacy grammar before introspection.
- Missing server metadata, failed detection, missing table/column, malformed or
  ambiguous definition, and unsupported target all fail before DDL.
- Never execute `CHANGE COLUMN` using a definition supplied from guessed,
  hard-coded, stale, or partial metadata.
- Never fall back from a failed native DDL statement by retrying another syntax.

## Required execution order

1. Validate config, target version, and rename AST.
2. Detect actual `DatabaseServerInfo` through the existing manager boundary.
3. Validate target product equals detected product.
4. Select native or legacy strategy from `targetDatabaseVersion` and the
   thresholds above; detected version does not participate in this choice.
5. Validate detected server supports the selected strategy.
6. Only for legacy strategy, resolve the source column definition.
7. Generate final SQL using the selected dialect and strategy.
8. Execute DDL through the existing manager path.

Required directional cases:

- Target MariaDB 10.4.28, detected MariaDB 10.5.3: remain on legacy strategy;
  resolve the source definition and generate `CHANGE COLUMN`.
- Target MariaDB 10.5.3, detected MariaDB 10.4.28: fail before source-definition
  lookup; do not issue `SHOW CREATE TABLE` and do not fall back to `CHANGE`.
- Target MariaDB 10.4.28, detected MySQL (any version): fail product mismatch
  before source-definition lookup or DDL.

These cases prove the v2.1 boundary: target chooses SQL generation and detected
metadata validates execution.

## Source Column Definition Resolution

The implementation phase must compare available metadata sources and select a
lossless strategy compatible with the existing manager abstraction. If using
`SHOW CREATE TABLE`, its parser must:

- identify the requested table/column using escaped identifier rules;
- distinguish column definitions from table-level keys and constraints;
- handle commas and parentheses inside types/expressions and quoted strings;
- handle escaped quote/backtick characters and multiline formatting;
- preserve the original column-definition fragment byte-for-byte where
  possible, changing only the source identifier;
- reject duplicate, missing, truncated, or unrecognized definitions.

If the current repository offers a structured metadata source that preserves
all needed attributes, prefer it over parsing DDL text. Document which source
was chosen and why before implementation is considered complete.

Identifiers must use the selected dialect's quoting/escaping. Table and column
identifiers are not bind parameters. Values from the extracted definition are
not to be reconstructed by concatenating untrusted user DSL strings.

## Architecture constraints

- API and AST retain only table/source/target identifiers.
- Builder validation and direct-AST renderer validation from v1.4 remain.
- Target version selects generation strategy; detected version validates
  execution.
- Renderer never queries manager, connection, or database.
- Executor uses existing manager abstractions; no new connection path is added.
- JDBC-specific behavior remains behind manager.
- No rewrite/retry based on a DDL failure.
- No changes to `RENAME TABLE`, `DROP COLUMN`, or `MODIFY COLUMN` contracts.

## Tests and acceptance criteria

- Unit tests for target strategy selection: native MySQL, native MariaDB, and
  supported legacy MySQL/MariaDB targets. Keep native grammar thresholds in
  the single strategy table above.
- Unit tests for definition extraction with ordinary, quoted, defaulted,
  charset/collation, generated, and auto-increment columns.
- Negative extraction tests for missing column/table, ambiguous parse, and
  unsupported/unrecognized syntax; assert no DDL is sent.
- Executor fake targets the existing `IQueryExecute` manager boundary and
  verifies metadata lookup occurs before DDL, final SQL preserves the definition,
  callback behavior is preserved, and failures stop before DDL.
- Target MariaDB 10.4.28 with detected MariaDB 10.5.3 selects legacy SQL and
  preserves the source definition; it must not select native SQL from the
  newer detected version.
- Target MariaDB 10.5.3 with detected MariaDB 10.4.28 fails before
  introspection; assert that `SHOW CREATE TABLE` and DDL were not issued.
- Runtime target/detected product mismatch is rejected before introspection or
  DDL.
- Integration test, when an explicitly configured MySQL/MariaDB test database
  is available, verifies the renamed column retains its definition and existing
  values.
- No JDBC assumptions enter migration API/AST/builder/dialect/renderer.
- Examples read dialect and target version from `DatabaseConfig`; they do not
  independently hard-code renderer version or syntax.

## Out of scope

- Changing column definition as part of rename.
- Generic schema-diff/introspection framework.
- Supporting database products beyond MySQL and MariaDB.
- Silent runtime syntax fallback or retry.
- Migration history, rollback, indexes, and constraints.

## Completion record

`RENAME COLUMN` now follows the target-selected native/legacy strategy. The
legacy path reads `SHOW CREATE TABLE` through the existing `IQueryExecute`
boundary, resolves the source definition without rebuilding its attributes,
and asks the selected dialect to render `CHANGE COLUMN`. The executor validates
detected product/capability before introspection and DDL. The example config is
set to MariaDB 10.4.28 to exercise the legacy path.

The scoped Gradle tasks `:data_base:migration:executor:test`,
`:data_base:migration:example:test`, and `:data_base:core:test` passed. No live
database integration test was run. The repository still has no declared
minimum supported server version; this remains a compatibility finding and was
not replaced with an invented library-wide target.
