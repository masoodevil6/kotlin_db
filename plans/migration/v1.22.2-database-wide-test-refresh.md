# Migration v1.22.2: تازه‌سازی کامل پایگاه دادهٔ تست

## وضعیت

**Implemented؛ اجرای واقعی MySQL تأیید نشده است.**

## هدف

قرارداد `migration.test.db.refresh` را در هر دو تست یکپارچه‌سازی `MigrationSystemIntegrationTest` و `MigrationSchemaIntegrationTest` یکسان کنیم. با `refresh=true` تمام جدول‌های پایگاه دادهٔ انتخاب‌شده پیش از شروع Migrationها حذف می‌شوند. با `refresh=false` هیچ objectای حذف نمی‌شود و برخورد با جدول‌های موردنیاز تست پیش از اجرای `MigrationMigrator` متوقف می‌شود.

بعد از پایان موفق یا ناموفق تست، هیچ cleanup پایگاه داده انجام نمی‌شود تا وضعیت ایجادشده برای بررسی برنامه‌نویس بماند.

## شواهد مخزن

* هر دو تست در `data_base/migration/src/test/kotlin/gog/my_project/data_base/migration/integration/` قرار دارند و propertyهای `migration.test.db.*` را می‌خوانند.
* `data_base/migration/build.gradle.kts` propertyهای domain، port، name، username، password و refresh را به JVM تست منتقل می‌کند؛ این فایل در این نسخه تغییر نمی‌کند.
* تست‌ها با `DatabaseMetaData.getTables` می‌توانند جدول‌های catalog انتخاب‌شده را فهرست کنند.
* `MigrationExecutor` overloadهای موجود برای `DropForeignKey` و `DropTable` دارد. Builder مربوط به `DropTable` از `ifExists()` پشتیبانی می‌کند و renderer SQL را از API موجود تولید می‌کند.
* هر دو تست در `finally` فقط config قبلی را restore و connectionهای خود را می‌بندند؛ این رفتار حفظ می‌شود.
* refresh قبلی فقط fixtureهای متعلق به هر تست را حذف می‌کرد؛ قرارداد جدید صریحاً database-wide است و sentinel دیگر با آن سازگار نیست.

## تصمیم‌ها

1. Database هدف فقط همان catalog متصل‌شده از `DatabaseConfig.dbName` است. خود database حذف یا بازسازی نمی‌شود.
2. در `refresh=true`، تست ابتدا snapshot نام جدول‌ها و Foreign Keyهای موجود در همان catalog را از JDBC metadata می‌گیرد.
3. برای پشتیبانی از dependencyهای FK و چرخه‌های احتمالی، constraintهای FK کشف‌شده با `getImportedKeys` و API موجود `DropForeignKey` حذف می‌شوند؛ سپس همهٔ جدول‌های snapshot‌شده با `DropTable { ifExists() }` و `MigrationExecutor` حذف می‌شوند.
4. `Success(false)` از `DropTable ... ifExists()` مجاز است؛ `Failure` یا نتیجهٔ تهی، refresh را fail می‌کند.
5. پس از refresh، `DatabaseMetaData.getTables` باید صفر جدول در catalog هدف گزارش کند. در غیر این صورت تست fail می‌شود و `MigrationMigrator` شروع نمی‌شود.
6. `refresh=false` هیچ عملیات حذف یا تغییر schema اجرا نمی‌کند. اگر جدول موردنیاز تست یا `system_migration` وجود داشته باشد، collision پیش از Migrator تشخیص داده می‌شود و snapshot جدول‌ها باید بدون تغییر بماند.
7. sentinel و تمام منطق ساخت/بررسی آن از هر دو تست حذف می‌شود.
8. بعد از migrationها، چه در موفقیت چه در failure، cleanup جدول انجام نمی‌شود. فقط connection بسته و `DefaultDatabaseConfig.config` restore می‌شود.
9. منطق refresh به‌صورت helper محلی در هر تست می‌ماند؛ abstraction مشترک یا production code اضافه نمی‌شود.

## جریان اجرایی

```text
load properties
→ install target DatabaseConfig
→ open inspection connection to selected catalog
→ if refresh=true:
     snapshot tables + foreign keys
     drop discovered FK constraints through MigrationExecutor
     drop snapshot tables through DropTable + MigrationExecutor
     verify table count == 0
→ if refresh=false:
     inspect only; on owned-table/system_migration collision, assert no mutation and stop before Migrator
→ run the existing test Migration lifecycle
→ preserve resulting database state
→ restore config and close inspection connection
```

### Runtime MySQL

اجرای integration با `refresh=true` به‌طور برگشت‌ناپذیر تمام جدول‌های catalog انتخاب‌شده را حذف می‌کند. این Plan کد را برای چنین اجرایی آماده می‌کند؛ اجرای واقعی فقط با database اختصاصی و مجوز صریح کاربر انجام می‌شود.

سناریوهای لازم:

* `refresh=true`: جدول‌های اولیه حذف شوند، پس از refresh تعدادشان صفر باشد، Migrationها اجرا شوند و schema/history پس از پایان باقی بمانند.
* وجود FK: constraintهای FK از metadata پیدا و پیش از حذف جدول‌ها از مسیر `DropForeignKey` حذف شوند.
* `refresh=false` با collision: MigrationMigrator شروع نشود و فهرست جدول‌ها قبل/بعد یکسان باشد.
* failure میانهٔ MigrationSystemIntegrationTest: جدول‌ها و history موفق تا نقطهٔ failure باقی بمانند.
* refresh failure یا باقی ماندن جدول: MigrationMigrator شروع نشود.

## معیار پذیرش

* هر دو تست قرارداد یکسان database-wide برای refresh داشته باشند.
* هیچ sentinel یا refresh محدود به fixture در این دو تست نماند.
* تمام حذف‌ها از APIهای موجود `DropForeignKey`/`DropTable` و `MigrationExecutor` انجام شوند.
* `refresh=false` هیچ objectای را تغییر ندهد.
* `refresh=true` پیش از Migrator، خالی بودن catalog از table را assert کند.
* هیچ database cleanup پس از تست انجام نشود.
* production code، Gradle، Help و سایر فایل‌های خارج از scope تغییر نکنند.
* Runtime MySQL تا اجرای مجاز روی database اختصاصی `Unverified` گزارش شود.
