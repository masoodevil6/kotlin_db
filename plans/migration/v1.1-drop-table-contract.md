# Migration v1.1: DROP TABLE Contract

وضعیت: `in-progress`

## Scope اجرایی

این plan از Contract تا تست و اجرای واقعی operation `DROP TABLE` را پوشش می‌دهد. operation باید مستقل از `CREATE TABLE` طراحی شود، اما از pipeline و conventionهای تثبیت‌شده‌ی آن استفاده کند.

## Dependencies

- Contract و baseline تأییدشده‌ی `v1.0`.
- `data_base:core` برای `BuiltQuery` و تنظیمات dialect.
- `data_base:migration:api` برای قرارداد operation.
- `data_base:migration:ast` برای `DropTableAst` مستقل.
- `data_base:migration:builder` برای DSL `dropTable`.
- `data_base:migration:dialect` برای registry/capability قرارداد.
- `data_base:migration:renderer` برای MySQL.
- `data_base:migration:executor` برای اتصال operation به اجرای DDL.
- `data_base:migration:example` برای end-to-end demonstration.

## تصمیم‌های تثبیت‌شده

1. `ifExists` اجباری نیست.
2. مقدار پیش‌فرض `ifExists` برابر `false` است.
3. `ifExists` property واقعی AST است، نه رفتار implicit renderer یا executor.
4. بدون `ifExists()` خروجی دقیقاً `DROP TABLE \`users\`` است.
5. با `ifExists()` خروجی دقیقاً `DROP TABLE IF EXISTS \`users\`` است.
6. فقط MySQL در این نسخه پشتیبانی می‌شود.
7. executor عمومی جدید پیش از داشتن دو implementation کامل ساخته نمی‌شود؛ overload محدود یا adapter موقت قابل قبول است.

## فازهای implementation

- DSL `dropTable { ... }` را اضافه کن.

خروجی: تست‌های builder و validation بدون renderer و database.

### فاز 3: Dialect و renderer

- node مربوط به DropTable در registry ثبت شود.

خروجی: renderer مستقل با دو golden output.

### فاز 4: Executor

### فاز 5: Example و integration

## Contract

```text
DropTable
├── Input
│   └── tableName
├── Options
│   └── ifExists
├── AST
│   ├── tableName
│   └── ifExists
├── Validation
│   └── tableName != blank
├── Rendering
│   └── DROP TABLE ...
└── Execution
    └── execute generated SQL
```

## Input

```text
tableName: String
```

قرارداد input:

- مقدار باید ارائه شود.
- مقدار نباید خالی یا فقط whitespace باشد.
- مقدار باید پیش از ذخیره در AST trim شود.
- مقدار identifier است و نباید به‌عنوان SQL خام پذیرفته شود.

نمونه‌ی معتبر:

```kotlin
dropTable {
    tableName("users")
}
```

## Options

```text
ifExists: Boolean = false
```

`ifExists` یک property واقعی و صریح در AST است؛ renderer یا executor نباید آن را implicit اضافه کنند.

بدون option:

```kotlin
dropTable {
    tableName("users")
}
```

```sql
DROP TABLE `users`
```

با option:

```kotlin
dropTable {
    tableName("users")
    ifExists()
}
```

```sql
DROP TABLE IF EXISTS `users`
```

## AST Contract

```text
DropTableAst
├── tableName: String
└── ifExists: Boolean = false
```

invariantهای AST:

- `tableName` پس از validation باید non-blank باشد.
- `ifExists` همیشه مقدار مشخص `true` یا `false` دارد.
- مقدار پیش‌فرض `ifExists` برابر `false` است.
- AST مربوط به `DROP TABLE` مستقل از AST مربوط به `CREATE TABLE` است.

## Builder/API Contract

API مفهومی:

```kotlin
dropTable {
    tableName("users")
    ifExists()
}
```

Builder فقط DSL را به AST تبدیل می‌کند و نباید SQL تولید کند یا اتصال دیتابیس بسازد.

رفتارها:

1. `tableName` را دریافت و trim کند.
2. `ifExists()` مقدار AST را به `true` تغییر دهد.
3. مقدار پیش‌فرض `ifExists` را تغییر ندهد.
4. SQL خام را از ورودی identifier قبول نکند.

## Validation Contract

حداقل validation نسخه‌ی اول:

```text
tableName != blank
```

خطای پیشنهادی:

```text
DropTable validation failed: tableName must not be blank
```

موارد زیر در این نسخه خارج از validation هستند:

- وجود واقعی جدول.
- foreign key dependency.
- permission کاربر.
- reserved بودن نام در همه‌ی dialectها.

این موارد یا به دیتابیس واگذار می‌شوند یا در Contractهای آینده‌ی dialect-specific تعریف خواهند شد.

## Rendering Contract

renderer MySQL باید identifier جدول را با quoting مناسب تولید کند:

```text
ifExists = false → DROP TABLE `users`
ifExists = true  → DROP TABLE IF EXISTS `users`
```

قواعد:

- renderer فقط AST را تفسیر می‌کند.
- renderer نباید `ifExists` را تغییر دهد.
- نام جدول باید با سیاست quoting و escaping dialect تولید شود.
- نام جدول parameter مربوط به `PreparedStatement` نیست.
- render باید بدون اتصال دیتابیس قابل تست باشد.

## Execution Contract

```text
DropTableAst
    → validate
    → render
    → BuiltQuery
    → execute generated SQL
```

رفتار اجرای موفق:

```text
ExecuteResult.Success(true)
```

رفتار اجرای ناموفق:

```text
ExecuteResult.Failure(originalError)
```

executor نباید خطای اجرای `DROP TABLE` بدون `IF EXISTS` را مخفی کند یا خودش `IF EXISTS` اضافه کند.

برای نسخه‌ی اول، overload جدا برای `IMigrationRenderDropTableApi` قابل قبول است. abstraction عمومی executor به plan نسخه‌ی `v1.2` منتقل می‌شود تا قبل از مشاهده‌ی حداقل دو operation واقعی، refactor زودهنگام انجام نشود.

## Test Contract

### AST و Builder

- نام جدول معتبر در AST ذخیره شود.
- whitespace ابتدا و انتهای نام trim شود.
- نام خالی و فقط whitespace رد شود.
- مقدار پیش‌فرض `ifExists` برابر `false` باشد.
- فراخوانی `ifExists()` مقدار را `true` کند.

### Renderer

```text
dropTable { tableName("users") }
→ DROP TABLE `users`
```

```text
dropTable { tableName("users"); ifExists() }
→ DROP TABLE IF EXISTS `users`
```

همچنین quoting identifier و خطای validation باید تست شوند.

### Executor

- SQL صحیح ارسال شود.
- callback موفقیت فراخوانی شود.
- callback خطا فراخوانی شود.
- exception اصلی حفظ شود.
- executor مقدار `ifExists` را تغییر ندهد.

### Integration اختیاری

با configuration صریح MySQL:

1. جدول آزمایشی ایجاد شود.
2. `DROP TABLE` اجرا شود.
3. نبودن جدول بررسی شود.
4. `DROP TABLE IF EXISTS` روی جدول حذف‌شده اجرا شود.
5. اجرای بدون `IF EXISTS` روی جدول حذف‌شده باید خطای دیتابیس بدهد.

## معیار پذیرش

1. Contract بالا در API، AST، builder، renderer و executor قابل ردیابی باشد.
2. هر دو SQL مرجع دقیقاً تولید شوند.
3. `ifExists` فقط از طریق DSL و AST کنترل شود.
4. validation بدون دیتابیس قابل اجرا باشد.
5. اجرای موفق و خطای واقعی دیتابیس به مصرف‌کننده برسد.
6. تست‌های unit بدون MySQL اجرا شوند.

## ریسک‌ها و پاسخ‌ها

| ریسک | پاسخ برنامه |
|---|---|
| اشتباه‌گرفتن identifier با parameter | table name مستقیماً به‌عنوان SQL خام پذیرفته نمی‌شود؛ dialect مسئول quoting است. |
| اضافه‌شدن implicit `IF EXISTS` | فقط AST flag تعیین‌کننده‌ی rendering است و برای هر دو حالت exact test داریم. |
| coupling با AST create-table | AST، API و renderer مستقل برای DropTable ساخته می‌شوند. |
| مخفی‌شدن خطای JDBC | original cause در `ExecuteResult.Failure` حفظ می‌شود. |
| وابستگی تست به MySQL محلی | unit testها بدون DB هستند و integration opt-in است. |
| حذف جدول اشتباه در integration | نام جدول test-specific، cleanup و configuration صریح الزامی است. |
