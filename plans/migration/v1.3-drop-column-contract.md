# Migration v1.3: DROP COLUMN Contract

وضعیت: `implemented`

## هدف

تعریف و پیاده‌سازی operation مستقل `DROP COLUMN` در `data_base:migration` با همان مسیر معماری موجود: API، AST، builder، dialect renderer، executor، مثال نسخه‌بندی‌شده و تست. خروجی MySQL باید با `ALTER TABLE ... DROP COLUMN ...` ساخته شود و اجرای DDL از مسیر executor فعلی و `data_base:manager` بگذرد.

## پیش‌شرط و وابستگی

- قراردادهای عملیاتی `CREATE TABLE` و `DROP TABLE` در `v1.0` و `v1.1` مبنای naming، render و مثال هستند.
- قبل از شروع اجرا، وضعیت و تغییرهای پذیرفته‌شده‌ی `v1.2` بررسی شود. این operation به abstraction جدید وابسته نیست؛ اگر `v1.2` قرارداد pipeline را تغییر داده باشد، implementation باید با قرارداد نهایی آن هماهنگ شود.
- از API فعلی executor برای operationهای migration پیروی شود. اگر مسیر اجرای عمومی در حین تکمیل `v1.2` تغییر کرد، فقط overload و adapter لازم برای `DROP COLUMN` اضافه شود؛ بازطراحی کلی executor خارج از scope است.

## محدوده

در این نسخه:

- حذف یک ستون از یک جدول در هر operation.
- پشتیبانی renderer برای MySQL.
- option اختیاری `ifExists` با default برابر `false`؛ در حالت `true` نبودن جدول یا ستون در execution به‌عنوان no-op موفق گزارش شود.
- Builder ورودی DSL را پیش از ساخت AST اعتبارسنجی می‌کند. Renderer نیز AST را به‌صورت دفاعی، پیش از quote کردن identifierها یا ترکیب SQL، اعتبارسنجی می‌کند.
- اجرای operation از `IMigrationExecutor` با manager مشترک دیتابیس.
- مثال render-only و تست واحد بدون نیاز به اتصال دیتابیس.
- integration test واقعی فقط در صورت وجود محیط MySQL پیکربندی‌شده و با نام جدول آزمایشی اختصاصی.

خارج از محدوده:

- حذف چند ستون در یک statement.
- `CASCADE` یا رفتار وابسته به foreign keyها و constraintها.
- حذف index، constraint یا خود جدول.
- پشتیبانی dialectهای غیر از MySQL.
- rollback خودکار، migration history یا migration runner.
- افزودن syntax `DROP COLUMN IF EXISTS` به SQL MySQL؛ grammar رسمی MySQL این syntax را ندارد. رفتار option در لایه executor و با تشخیص error codeهای مشخص missing-table/missing-column پیاده‌سازی می‌شود.

## Contract

```text
DropColumn
├── Input
│   ├── tableName: String
│   └── name: String
├── Options
│   └── ifExists: Boolean = false
├── AST
│   ├── tableName: String
│   ├── name: String
│   └── ifExists: Boolean
├── Validation
│   ├── tableName is non-blank
│   └── name is non-blank
├── Rendering
│   └── ALTER TABLE <quoted-table> DROP COLUMN <quoted-column>
└── Execution
    ├── ifExists=false → propagate missing-target error
    └── ifExists=true → treat only missing table/column as successful no-op
```

نمونه DSL مفهومی:

```kotlin
dropColumn {
    tableName("users")
    name("display_name")
}
```

SQL مرجع MySQL:

```sql
ALTER TABLE `users` DROP COLUMN `display_name`
```

DSL option:

```kotlin
dropColumn {
    tableName("users")
    name("display_name")
    ifExists()
}
```

## ورودی، AST و builder

- API operation در namespace مستقل `drop_column` تعریف شود و از `IMigrationApi` پیروی کند.
- AST مستقل مانند `IMigrationDropColumnAst` و `MigrationDropColumnAst` داشته باشد؛ ASTهای `DROP TABLE` یا `ADD COLUMN` برای این operation استفاده نشوند.
- AST دو identifier جدول و ستون را نگه دارد؛ identifierها پارامتر bind‌شدنی SQL نیستند.
- AST مقدار `ifExists: Boolean` را با default برابر `false` نگه دارد.
- builder ورودی‌های DSL را trim کند، همانند convention موجود `addColumn` و `dropTable`، و مقدار trim‌شده را در AST ذخیره کند؛ renderer مسئول trim کردن AST نیست.
- builder فقط DSL را به AST تبدیل کند و SQL نسازد یا اتصال دیتابیس ایجاد نکند.
- API هم‌راستا با `ADD COLUMN` و `DROP TABLE`: `tableName(table: String)`، `name(name: String)` و option صریح `ifExists()`.

## اعتبارسنجی و خطاها

اعتبارسنجی در دو مرز انجام شود:

**Builder validation**

- ورودی نام جدول و نام ستون را trim کند و مقدارهای trim‌شده را در AST قرار دهد.
- ورودی خالی یا whitespace-only را زودهنگام رد کند تا DSL نامعتبر به AST معتبرنما تبدیل نشود.

برای نمونه، این DSL:

```kotlin
dropColumn {
    tableName("  users  ")
    name("  email  ")
}
```

باید ASTای با `tableName = "users"` و `name = "email"` بسازد؛ trim شدن در builder انجام می‌شود، نه هنگام rendering.

**Renderer validation**

- پیش از هرگونه quote کردن identifier یا ترکیب SQL، به‌صورت دفاعی AST ناقص یا malformed را رد کند؛ از جمله نام جدول یا ستون تهی/blank.
- renderer این بررسی را حتی اگر builder ورودی را قبلاً اعتبارسنجی کرده باشد انجام دهد، چون AST می‌تواند مستقل ساخته یا تغییر داده شود.

پس از validation و پیش از ساخت SQL:

- identifierها باید توسط renderer و با quoting سازگار با MySQL تولید شوند؛ backtick داخل identifier باید escape شود.
- خطاهای builder و renderer باید روشن باشند و operation و فیلد مربوط را مشخص کنند.
- وجود واقعی جدول یا ستون در schema در زمان render بررسی نمی‌شود؛ این بررسی فقط در دیتابیس ممکن است و خطای اصلی دیتابیس باید در مسیر execution حفظ شود.

نمونه پیام خطا:

```text
DROP COLUMN requires a non-blank table name
DROP COLUMN requires a non-blank column name
```

## Rendering و dialect

- قرارداد capability مستقل `drop_column` در dialect تعریف شود.
- MySQL renderer باید شکل ثابت زیر را تولید کند:

```sql
ALTER TABLE `users` DROP COLUMN `display_name`
```

- renderer به اتصال دیتابیس، executor یا query AST وابسته نشود.
- capability در registry دیالکت ثبت شود و برای AST ناشناخته، رفتار عمومی registry تغییر نکند.
- MySQL renderer برای `ifExists=true` همان SQL معتبر MySQL را render می‌کند؛ تفاوت رفتاری فقط در execution اعمال می‌شود، چون MySQL syntax `DROP COLUMN IF EXISTS` را پشتیبانی نمی‌کند.

## Execution

- overload لازم برای API جدید به `IMigrationExecutor` و پیاده‌سازی آن افزوده شود.
- اجرای SQL از dialect انتخاب‌شده بر اساس تنظیمات مشترک `DefaultDatabaseConfig` و از `IQueryExecute` ماژول `data_base:manager` عبور کند.
- callbackهای query info و نتیجه مطابق قرارداد overloadهای فعلی حفظ شوند.
- با `ifExists=false`، خطای دیتابیس به‌صورت failure واقعی همراه با cause اصلی گزارش شود.
- با `ifExists=true` executor پیش از DDL با query پارامتری در `INFORMATION_SCHEMA.COLUMNS` وجود جدول و ستون را در schema جاری بررسی کند؛ اگر هدف وجود نداشت `Success(true)` بدهد و `ALTER TABLE` را اجرا نکند.
- اگر هدف در preflight موجود بود، DDL اجرا شود؛ خطاهای MySQL `1091` و `1146` در این مرحله نیز به‌عنوان fallback برای race بین بررسی و حذف به `Success(true)` تبدیل شوند. سایر خطاها حفظ شوند.
- شناسایی خطا در executor و پشت مرز execution بماند؛ API، AST، builder، dialect و renderer به JDBC وابسته نشوند.
- ساختن API، AST، render یا unit test نباید config اتصال یا دیتابیس واقعی لازم داشته باشد.
- fake/mock تست executor باید روی abstraction واقعی و موجود در مرز executor/manager قرار بگیرد.
- برای تست `DROP COLUMN` abstraction production جدیدی صرفاً با هدف آسان‌تر شدن تست ساخته نشود.

## قیدهای معماری و استقلال پلتفرم

- AST و builder از execution مستقل باقی بمانند.
- dialect و renderer به اتصال دیتابیس، executor یا manager وابسته نشوند.
- executor migration ساخته‌شده را مصرف کند و اجرای آن را از طریق abstractionهای manager موجود واگذار کند.
- `DROP COLUMN` نباید dependency معکوس در جهت وابستگی فعلی ماژول‌ها ایجاد کند؛ به‌ویژه renderer نباید به executor/manager و AST نباید به renderer وابسته شود، و builder نباید executor را بشناسد.
- API، AST، builder، dialect و renderer نباید فرض یا وابستگی JDBC-specific وارد کنند. جزئیات JDBC و دیتابیس در پشت مرز execution/manager موجود باقی بمانند تا لایه‌های بالاتر مستقل از پلتفرم و قابل استفاده برای Android بمانند.

## مثال و تست

مثال نسخه‌بندی‌شده در `data_base:migration:example` با convention جاری قرار گیرد:

```text
v1/migrations/drop_column/A1ExampleDropColumnV1.kt
```

مثال باید migration را به شکل مستقل بسازد و render کند. اجرای واقعی فقط با فعال‌سازی صریح مسیر execution و config میزبان انجام شود. چون حذف ستون مخرب است، مثال پیش‌فرض فقط render شود.

تست‌های لازم:

- SQL مرجع با تطبیق دقیق.
- trim شدن نام جدول و ستون.
- رد شدن نام جدول خالی یا whitespace-only.
- رد شدن نام ستون خالی یا whitespace-only.
- escape شدن backtick در هر identifier.
- اطمینان از اینکه AST مقادیر trim‌شده را نگه می‌دارد.
- default شدن `ifExists` به false و ذخیره شدن گزینه در AST.
- ثابت ماندن SQL معتبر MySQL در render با هر دو حالت option.
- تست executor با fake/mock برای ارسال SQL، callback موفقیت و انتقال خطا؛ بدون دیتابیس.
- تست suppression برای خطاهای MySQL `1091` و `1146` فقط وقتی `ifExists=true` است؛ سایر خطاها و حالت false باید failure بمانند.
- تست integration اختیاری فقط در MySQL پیکربندی‌شده؛ باید حذف ستون را روی schema اختصاصی ایجادشده برای تست انجام دهد و cleanup داشته باشد.

## مراحل اجرا

### مرحله 1: تثبیت traceability

- ابتدا ساختار package و مسیرهای واقعی `DROP TABLE` و `ADD COLUMN` را از API تا renderer و executor بررسی و mirror کن.
- صرفاً برای هم‌شکل شدن با مسیرهای پیشنهادی این plan، hierarchy یا package جدید نساز؛ نام و محل فایل‌ها را با convention واقعی کد هماهنگ کن.
- قراردادهای `v1.1` و pipeline مشترک پذیرفته‌شده از `v1.2` را کنار implementation واقعی بررسی کن.
- ثبت کن کدام بخش‌ها الگو هستند و کدام semantics باید اختصاصی `DROP COLUMN` بمانند.

### مرحله 2: API و AST

- interfaceهای API و AST مستقل بساز.
- invariant دو identifier را مشخص و تست کن.
- از افزودن optionهایی که قراردادشان روشن نیست خودداری کن.

### مرحله 3: builder و renderer

- DSL `dropColumn { ... }` را اضافه کن.
- validation و quoting را پیاده کن.
- capability مربوط را در MySQL registry ثبت کن و خروجی مرجع را با تست دقیق تثبیت کن.

### مرحله 4: executor

- overload operation را به executor موجود وصل کن.
- با fake/mock روی abstraction واقعی موجود، ارسال SQL، callbackها و حفظ خطای اصلی را تست کن.
- صرفاً برای تست این operation، abstraction جدیدی به production code اضافه نکن.
- در این مرحله مسئولیت اتصال همچنان متعلق به `data_base:manager` است.

### مرحله 5: مثال و مستندات

- مثال V1 را در پوشه‌ی جداگانه‌ی `drop_column` اضافه کن.
- manager مثال را با همان الگوی نسخه‌بندی موجود به‌روزرسانی کن.
- ساختار و دستور اجرای render/test را مستند کن.
- integration test را فقط در محیط MySQL آماده و با schema آزمایشی ایزوله اجرا کن.

## ریسک‌ها و تصمیم‌ها

| ریسک | تصمیم اجرایی |
|---|---|
| حذف ستون داده‌های آن را از بین می‌برد | مثال پیش‌فرض render-only است؛ execution باید صریح باشد. |
| identifier پارامتر bind شدنی نیست | identifierها نباید بدون quoting و escaping مخصوص dialect در SQL قرار بگیرند؛ آن‌ها SQL bind parameter نیستند. برای MySQL، مثلاً ``user`data`` باید به شکل `` `user``data` `` quote شود. |
| foreign key یا index وابسته وجود دارد | در این نسخه cascade یا حذف خودکار وابستگی‌ها وعده داده نمی‌شود؛ خطای دیتابیس حفظ می‌شود. |
| MySQL syntax مستقیم `DROP COLUMN IF EXISTS` ندارد | renderer SQL معتبر ثابت تولید می‌کند؛ executor در حالت `ifExists=true` ابتدا وجود هدف را با `INFORMATION_SCHEMA.COLUMNS` بررسی می‌کند، در نبود هدف DDL را اجرا نمی‌کند و error codeهای missing-target را فقط به‌عنوان fallback رقابت زمانی مهار می‌کند. |
| تکرار منطق quoting در capabilityها | در مرحله traceability بررسی شود؛ abstraction مشترک فقط در صورت وجود الگوی واقعی و سازگار با `v1.2` استخراج شود. |

## معیار پذیرش

1. API، AST، builder، renderer و executor برای `DROP COLUMN` قابل ردیابی و مستقل از AST عملیات دیگر هستند؛ `ifExists` هم در AST default صریح `false` دارد.
2. ورودی ناقص یا blank پیش از تولید SQL رد می‌شود.
3. SQL MySQL با تطبیق دقیق و escaping identifier تست شده است.
4. مسیر execution از executor و manager مشترک استفاده می‌کند؛ `ifExists` فقط missing-table/column MySQL را مهار می‌کند و بقیه خطاها را حفظ می‌کند.
5. مثال نسخه‌ای بدون اتصال، SQL را render می‌کند و به‌صورت پیش‌فرض DDL را اجرا نمی‌کند.
6. unit testها بدون دیتابیس اجرا می‌شوند و تست executor از fake استفاده می‌کند.
7. تست‌های regression عملیات قبلی بدون تغییر رفتار عبور می‌کنند.
8. مستندات ساختار و dependency direction به‌روزرسانی شده‌اند.
9. وضعیت این plan تنها بعد از تکمیل Definition of Done به `implemented` تغییر می‌کند.
