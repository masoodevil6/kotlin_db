# Migration v1.17.3: Execution Boundary و هم‌راستاسازی مسیرهای Query/Migration

## وضعیت

`Ready for Traceability` — این Plan فقط برای بررسی repository و ثبت شواهد است. در این مرحله هیچ implementation یا فایل source/build/test تغییر نمی‌کند.

## زمینه

v1.17 سیستم داخلی Migration State را معرفی کرد. در v1.17.2 مسیر ساخت SELECT و INSERT به Query Builder/AST/Renderer متصل شد و نتیجه از `IQueryExecute` تزریق‌شده اجرا می‌شود؛ bootstrap نیز از `MigrationExecutor` عبور می‌کند. اکنون لازم است مرز اجرای واقعی Query و Migration در سطح `data_base:manager`, `data_base:query` و `data_base:migration` از روی کد و dependencyهای repository روشن شود.

این Plan از روی نام کلاس‌ها دربارهٔ execution architecture نتیجه‌گیری نمی‌کند. مسیر واقعی ساخت `BuiltQuery`، اجرای SQL، دریافت Connection، binding پارامترها و مدیریت lifecycle منابع باید از source code و dependencyهای Gradle استخراج شود.

## 1. هدف

با Traceability repository به این پرسش پاسخ داده شود:

> آیا Query و Migration از یک execution boundary مشترک عبور می‌کنند، یا هرکدام مسیر execution مستقل دارند؟ مالک واقعی هر responsibility کدام module و component است؟

Trace باید این دو مسیر را از ابتدا تا JDBC دنبال کند:

```text
Query Builder
    ↓
Query AST / Renderer
    ↓
BuiltQuery
    ↓
Query Executor
    ↓
IQueryExecute
    ↓
QueryExecute
    ↓
DatabaseConnection
```

```text
Migration Builder
    ↓
Migration AST / Renderer
    ↓
BuiltQuery
    ↓
Migration Executor
    ↓
?
    ↓
IQueryExecute / QueryExecute / DatabaseConnection
```

هدف، انتخاب معماری یا اعمال تغییر نیست. ابتدا Evidence ثبت و سپس Interpretation، Candidate Matrix، Required Decisions و Final Contract همین Traceability تکمیل می‌شوند.

## 2. Scope

### داخل Scope

* بررسی source code و dependency graph مربوط به `data_base:manager`, `data_base:query` و `data_base:migration`.
* trace کردن `IQueryExecute`, `QueryExecute`, `DatabaseConnection`, `IDatabaseConnection`, `MigrationExecutor`, `IMigrationExecutor` و هر execution/manager component دیگری که Migration استفاده می‌کند.
* بررسی جریان config، `BuiltQuery`، parameter binding، JDBC error propagation و resource lifecycle.
* تکمیل جدول ownership و Candidate Architecture Matrix بر اساس Evidence.
* بررسی اثر نتیجه بر مسیر فعلی `SystemMigrationStateStore` در v1.17.2، بدون تغییر implementation آن.
* در صورت نیاز اجرای compile یا تست‌های موجود، صرفاً برای تأیید شواهد.

### خارج از Scope

* هرگونه تغییر implementation، source, build, test یا plan implementation.
* Migration Runner، rollback، locking، checksum، migration discovery و transaction redesign.
* SQLite، ORM، یا redesign کامل Query/Migration subsystem.
* تغییر semantic operationهای موجود.
* commit، push یا هر تغییر remote.

## 3. پرسش‌های Traceability

### 3.1 Execution Boundary

از source code مشخص شود:

* کدام component Connection می‌سازد و `DatabaseConnection` و `IDatabaseConnection` چه نقشی دارند.
* کدام component `BuiltQuery` را به JDBC statement می‌رساند.
* آیا `IQueryExecute.execute(...)` orchestration مشترک execution را انجام می‌دهد؛ از جمله ساخت Connection، آماده‌سازی query/پارامترها و تحویل کنترل به callback.
* parameter binding، JDBC error handling و resource lifecycle دقیقاً در کدام method/module انجام می‌شوند.
* Query و Migration در کدام نقطه به این مسئولیت‌ها متصل می‌شوند.
* آیا Migration مسیر اجرای SQL دیگری، Connection مجزا، `PreparedStatement` مجزا یا parameter binder مجزا دارد.

### 3.2 BuiltQuery Boundary

مشخص شود:

* آیا `AST → Renderer → BuiltQuery → Execution` convention مشترک subsystemهاست یا Query و Migration تفاوت دارند.
* کدام executor `BuiltQuery` را می‌سازد و کدام component فقط آن را اجرا می‌کند.
* usageهای مستقیم `BuiltQuery("SELECT VERSION()", ...)` و نمونه‌های مشابه در source کجا هستند و چه لایه‌ای را دور می‌زنند.
* raw SQL + `BuiltQuery` یک mechanism داخلی پشتیبانی‌شده است یا usage محدود/تاریخی؛ شواهد و محدودیت‌های هر برداشت ثبت شود.
* carrier بودن `BuiltQuery` را از مسئولیت SQL generation جدا نگه دارید.

این دو مسیر جداگانه مقایسه شوند:

```text
Builder / AST / Renderer → BuiltQuery → Execution
```

```text
Raw SQL → BuiltQuery → Execution
```

### 3.3 Configuration Boundary

`DatabaseConfig`, `DefaultDatabaseConfig` و مصرف‌کنندگانشان trace شوند:

* Connection config را از کجا دریافت می‌کند؟
* Query و Migration dialect را از کجا انتخاب می‌کنند؟
* Query execution چه configای مصرف می‌کند؟
* Migration execution چه configای مصرف می‌کند؟
* آیا `DefaultDatabaseConfig.config` source of truth فعلی است؟
* آیا مسیر configuration دیگری وجود دارد؟
* آیا Query و Migration در نهایت از config یکسان استفاده می‌کنند؟

هیچ configuration abstraction جدیدی در این Plan طراحی یا پیاده‌سازی نشود.

### 3.4 Query Execution

برای `data_base:query` مسیر واقعی زیر تا JDBC بررسی شود:

```text
Query Builder
→ Query Renderer
→ BuiltQuery
→ IQueryExecute
→ QueryExecute
→ DatabaseConnection
```

برای هرکدام از `executeSelect`, `executeUpdate`, `executeInsert`, `executeDelete` ثبت شود:

* caller و dispatch path.
* semantic خروجی و نحوهٔ گزارش موفقیت/خطا.
* پارامترها چگونه به placeholderهای JDBC وصل می‌شوند.
* `ResultSet`, `PreparedStatement`, generated keys و Connection چه زمانی باز و بسته می‌شوند.
* تفاوت کاربردی `executeUpdate` با `executeInsert` و operationهای مصرف‌کنندهٔ هرکدام.

تفاوت دو متد از روی implementation و call sites مشخص شود، نه نام متدها. به‌طور خاص بررسی شود آیا `executeInsert` generated key برمی‌گرداند و `executeUpdate` affected-row count؛ سپس بررسی شود کدام خروجی واقعاً برای ثبت یک ردیف Migration لازم است. در Evidence این معنا فقط پس از مشاهدهٔ source ثبت شود؛ انتخاب State Store در Required Decisions انجام شود.

### 3.5 Migration Execution

برای `data_base:migration` مشخص شود:

* dependencyهای واقعی `MigrationExecutor` و `IMigrationExecutor` چیست.
* DDL چگونه از Migration AST و renderer به `BuiltQuery` تبدیل می‌شود.
* DDL از کدام API برای اجرا عبور می‌کند؛ `IQueryExecute.executeTable()` یا مسیر دیگر.
* آیا Migration برای اجرا Connection یا PreparedStatement جدیدی می‌سازد.
* parameter binding و JDBC error handling در کدام component انجام می‌شود.
* آیا lifecycle منابع یا execution behavior با Query تفاوتی دارد.

### 3.6 Dependency Graph

Dependencyهای Gradle واقعی استخراج و این روابط تأیید یا رد شوند:

```text
migration:executor
    ↓
manager:execute
    ↓
manager:connection
```

```text
query:executor
    ↓
manager:execute
    ↓
manager:connection
```

همچنین ثبت شود:

* آیا dependency مشترک واقعاً وجود دارد یا migration مسیر جایگزین دارد.
* چرخه‌های احتمالی یا نبود آن‌ها.
* dependencyهای تکراری یا غیرضروری، با شواهد.
* ownership هر لایه و جهت dependency.

### 3.7 System Migration State v1.17.2

بدون تغییر implementation، اثر execution trace بر این تصمیم‌ها بررسی شود:

* execution path مناسب برای SELECT history.
* انتخاب `executeUpdate` در برابر `executeInsert` برای ثبت history.
* آیا bootstrap باید همچنان از `MigrationExecutor` عبور کند.
* آیا `SystemMigrationStateStore` باید `IQueryExecute` را مستقیماً دریافت کند.
* آیا dependency فعلی Store به `MigrationExecutor` با ownership موجود سازگار است.
* آیا Store مسئولیتی را دوباره اجرا یا پیاده‌سازی می‌کند که owner دیگری دارد.

هیچ تغییر v1.17.2 در این مرحله اعمال نشود؛ نتیجه صرفاً به‌عنوان implication یا finding مستند شود.

## 4. Evidence Discipline

گزارش Traceability باید این ترتیب و تفکیک را حفظ کند:

```text
Evidence
    ↓
Interpretation
    ↓
Candidate Matrix
    ↓
Required Decisions
    ↓
Final Contract
```

* در Evidence فقط واقعیت قابل مشاهده در source، Gradle dependency یا نتیجهٔ verification ثبت شود.
* Evidence شامل پیشنهاد، انتخاب یا قضاوت معماری نباشد؛ مگر اینکه متن یک قرارداد موجود عیناً گزارش شود.
* Interpretation پیامد Evidence را توضیح دهد.
* انتخاب Candidate یا recommendation فقط در Candidate Matrix و Final Contract بیاید.
* فرض را به‌جای Evidence ثبت نکنید؛ مورد نامشخص صریحاً Unverified بماند.

## 6. Candidate Architecture Matrix

هیچ Candidateای از پیش انتخاب‌شده نیست. Traceability حداقل این سه گزینه را با repository evidence مقایسه کند:

### A. Shared execution boundary

```text
Query ───────┐
             ↓
        IQueryExecute
             ↓
       QueryExecute
             ↓
     DatabaseConnection
             ↑
             │
Migration ───┘
```

### B. Separate Query/Migration execution paths

```text
Query → QueryExecute → Connection

Migration → MigrationExecute → Connection
```

### C. Shared low-level mechanism, semantic APIs remain separate

```text
Query
  ↓
Query execution API
  ↓
shared low-level mechanism

Migration
  ↓
Migration execution API
  ↓
shared low-level mechanism
```

Candidate C صرفاً برای مقایسه است. این Plan نباید به دلیل تمیزی نظری، Candidate C را بر مسیرهای مشاهده‌شده در repository ترجیح دهد یا آن را به‌عنوان target architecture فرض کند. هدف کشف و ارزیابی معماری واقعی است، نه طراحی مجدد آن.

| معیار | A: Shared boundary | B: Separate paths | C: Shared mechanism / APIs جدا |
|---|---|---|---|
| مسئولیت‌ها و ownership | بررسی شود | بررسی شود | بررسی شود |
| Dependency direction و coupling | بررسی شود | بررسی شود | بررسی شود |
| Reuse در برابر duplication | بررسی شود | بررسی شود | بررسی شود |
| Extensibility و testability | بررسی شود | بررسی شود | بررسی شود |
| Dialect/config consistency | بررسی شود | بررسی شود | بررسی شود |
| Parameter handling و resource lifecycle | بررسی شود | بررسی شود | بررسی شود |
| سازگاری با architecture فعلی | بررسی شود | بررسی شود | بررسی شود |

## 7. Required Decisions

Traceability باید به هر پرسش پاسخ مستند دهد:

1. Execution boundary canonical فعلی کتابخانه چیست؟
2. آیا Query و Migration execution boundary مشترک دارند؟
3. اگر boundary مشترک نیست، تفاوت معنایی واقعی چیست؟
4. owner واقعی Connection creation کدام component است؟
5. owner واقعی parameter binding کدام component است؟
6. owner واقعی اجرای `BuiltQuery` کدام component است؟
7. آیا `IQueryExecute` در scope فعلی execution boundary قابل قبول است، و چه semanticهایی را پوشش می‌دهد؟
8. آیا `MigrationExecutor → IQueryExecute.executeTable()` با ownership و dependency direction فعلی سازگار است؟
9. مسیر مناسب State Store برای SELECT و INSERT چیست؟
10. آیا architecture change لازم است، یا فقط وضعیت فعلی و اصلاح محدود v1.17.2 کفایت می‌کند؟
11. آیا dependency جدید لازم است؟ اگر هست، کدام dependency و چرا؟
12. اگر هیچ architecture changeای لازم نیست، دلیل مبتنی بر source و dependency چیست؟
13. نقش واقعی `IQueryExecute` در برابر `QueryExecute` چیست: facade/interface عملیات‌ها، orchestration/connection acquisition، یا هر دو؟ مسئولیت‌های مشترک دقیقاً در کدام متد قرار دارند؟
14. برای v1.17.2 دقیقاً چه چیزی باید تغییر کند و چه چیزی باید بدون تغییر بماند؟ پاسخ باید به Evidence و Decisionهای قبلی ارجاع دهد.

هر Decision به Evidenceهای مربوط و تأثیرش بر Final Contract ارجاع دهد.

## 8. Verification Strategy

این مرحله implementation ندارد. فقط برای تأیید Evidence، در صورت نیاز اجرا شود:

* compile ماژول‌های مربوط.
* تست‌های موجود `data_base:query` که مسیرهای select/update/insert/delete را واقعاً پوشش دهند.
* تست‌های موجود `data_base:migration` و `data_base:manager` که dispatch و خطای JDBC را نشان دهند.
* تست واقعی database فقط اگر test environment از قبل و به‌طور صریح تنظیم شده باشد؛ هیچ credential یا config محلی حدس زده نشود.

تست جدید اضافه نشود. نتیجهٔ هر command، از جمله skip یا محدودیت محیط، ثبت شود. اجرای تست فقط evidence موجود را بررسی می‌کند و مجوز تغییر implementation نیست.

## 10. Definition of Done — Traceability

Traceability این Plan زمانی کامل است که:

* execution graph واقعی Query و Migration تا Connection ثبت شده باشد.
* role و usageهای `IQueryExecute`, `QueryExecute`, `DatabaseConnection` و `IDatabaseConnection` از source تعیین شده باشد.
* call graph واقعی Query و Migration جداگانه، تا محل Connection acquisition و JDBC operation، با pathهای source ثبت شده باشد.
* مشخص شده باشد `IQueryExecute.execute(...)` چه orchestration مشترکی دارد و چه مسئولیتی در `QueryExecute` باقی می‌ماند؛ صرف نام‌گذاری interface/class مبنای این نتیجه نباشد.
* تمام مسیرهای JDBC resource lifecycle، parameter binding، generated keys و error propagation بررسی شده باشد.
* جریان configuration برای Connection، Query dialect و Migration dialect ثبت شده باشد.
* نقش `BuiltQuery` و تفاوت raw SQL با render شده به‌طور evidence-based گزارش شده باشد.
* dependency graph و ownership table تکمیل شده باشند.
* Candidate Matrix و Required Decisions بر اساس Evidence کامل باشند.
* اثر بر `SystemMigrationStateStore` v1.17.2 روشن شده باشد، بدون تغییر آن.
* verificationهای موجودی که اجرا شدند و محدودیت‌های محیطی گزارش شده باشند.
* هیچ source, build, test یا implementation plan در این مرحله تغییر نکرده باشد.
* Final Contract وضعیت مرحلهٔ بعد را مشخص کند؛ این Plan به‌خودی‌خود مجوز implementation نیست.

در جمع‌بندی Final Contract، یک پاسخ کوتاه و صریح با این قالب درج شود:

```text

```

این پاسخ باید فقط از Evidence و Required Decisions نتیجه شده باشد و دامنه‌اش به v1.17.2 محدود بماند.
