# Migration v1.19: قرارداد هویت، ثبت صریح و ترتیب Migration

**وضعیت: Identity Contract — Implementation Ready | Persistence Compatibility — Deferred**
Identity/Registration contract برای implementation آماده است. برابری persistence روی databaseهای هدف اثبات نشده و جداگانه Deferred می‌ماند؛ این وضعیت تضمین سازگاری برای محصول یا collation خاصی نیست.

## ۱. هدف و دامنه

این نسخه قرارداد هویت Migration را با **Annotation روی خود declaration** بررسی می‌کند و registration را از identity جدا نگه می‌دارد. Migrationهای انتخاب‌شده به‌صورت صریح در configuration ثبت می‌شوند تا مجموعه، ترتیب و Groupها مشخص باشند؛ registration مقدار ID را دستی تعریف نمی‌کند.

### مدل هدف برای Traceability

```kotlin
@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.RUNTIME)
annotation class MigrationId(val value: String)

object migrationTags {
    const val create_users = "create_users"
    const val add_users_email = "add_users_email"
}

@MigrationId(migrationTags.create_users)
class CreateUsers : Migration {
    // up()/down()
}

migrationConfig {
    migration<CreateUsers>()

    migrationGroup("users") {
        migration<AddUsersEmail>()
    }
}
```

این مدل، قرارداد مصوب Identity/Registration است؛ grammar نهایی تصویب شده و persistence equality همچنان Deferred است. هیچ identity دستی مانند `migration<CreateUsers>(MigrationId.of(...))` در registration وارد نشود.

### داخل Scope

- مالکیت و representation هویت Migration.
- کاربرد `@MigrationId` و `migrationTags`.
- runtime extraction و تبدیل annotation value به domain value.
- explicit registration برای تعیین مجموعه، ترتیب و Groupها.
- ضرورت و مرز `KClass` به‌عنوان registration metadata.
- validation هویت، duplicateها، ordering و snapshot.
- سازگاری قرارداد با State Store فعلی.

### خارج از Scope

- Runner، pending/applied selection، اجرای Migration و state lifecycle.
- instantiation policy، constructor، no-arg requirement، DI، provider یا factory.
- filesystem/JAR scanning و automatic discovery.
- transaction، rollback، locking، checksum و execution policy برای Group.
- تغییر API/source/test/build/schema در مرحلهٔ Traceability.

## ۳. تفسیر (Interpretation)

1. قرارداد اصلی identity در v1.19، بر اساس درخواست صریح کاربر، **declaration-owned** است: ID روی Migration declaration قرار می‌گیرد. انتقال آن به آرگومان registration تغییر معماری جداگانه‌ای است و evidence لازم برای جایگزین کردن قرارداد اولیه ارائه نشده؛ بنابراین این انتقال architectural drift تلقی می‌شود.
2. `@MigrationId` metadata هویت را به class declaration وصل می‌کند. تغییر class name/package/filename مقدار ID را عوض نمی‌کند؛ تغییر مقدار annotation پس از apply شدن Migration یک breaking identity change است.
3. `migrationTags` محل تعریف compile-time Stringهای قابل استفاده در annotation است. این object registry runtime نیست و identity را از declaration به registration منتقل نمی‌کند.
4. Kotlin annotation argument نمی‌تواند `MigrationId.of(...)` یا value class را بپذیرد؛ annotation باید String/نوع مجاز compile-time را بگیرد. پس runtime هنگام خواندن annotation، raw String را به domain value تبدیل و validate می‌کند.
5. نام `MigrationId` هم برای annotation و هم برای value class در یک package تعارض declaration دارد. اگر typed runtime wrapper حفظ شود، نام‌گذاری/package باید جدا شود؛ candidate مناسب `MigrationIdentity` است. انتخاب نام نهایی هنوز تصمیم API است.
6. explicit registration و identity دو مسئولیت‌اند: annotation هویت را تعیین می‌کند؛ `migration<T>()` membership و جایگاه type را در ordered configuration تعیین می‌کند. `migration<T>(id)` این دو مسئولیت را دوباره در registration مخلوط می‌کند و حذف شود.
7. `KClass` یا class reference در صورت استفاده برای حفظ نوع‌های ثبت‌شده، registration metadata است؛ بخشی از identity نیست و ابزار instantiate کردن محسوب نمی‌شود.
8. `MigrationConfiguration` باید ordered registration tree را نگه دارد و برای هر عضو، type ثبت‌شده و identity استخراج‌شده از annotation را به هم associate کند؛ هیچ Migration instance نگه نمی‌دارد یا نمی‌سازد.
9. دریافت metadata از class annotation به‌تنهایی Migration constructor، `up()` یا `down()` را اجرا نمی‌کند. بنابراین Android startup concern مربوط به ساخت instance از identity extraction جداست؛ target Android هنوز تعریف نشده و compatibility اثبات‌شده ادعا نمی‌شود.
10. registration class/type برای v1.19 از شواهد DSL و هدف ترتیب/Group پشتیبانی می‌شود؛ این evidence صرفاً KClass را برای association type در configuration توجیه می‌کند، نه برای Runner یا instantiation.
11. `MigrationId` runtime value type می‌تواند validation و مرز type-safe با State Store بدهد؛ چون نام annotation اشغال است، type domain باید نام/package متفاوت داشته باشد یا Traceability تصمیم بگیرد wrapper لازم نیست.
12. Domain ASCII پیشنهادی و unique-index equality هنوز مستقل از annotation unresolved هستند. انتخاب annotation به‌خودی‌خود persistence collation را حل نمی‌کند.

## ۶. Contract پیشنهادی برای Traceability نهایی

### ۶.۱ Annotation و Tag Constants

```kotlin
@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.RUNTIME)
annotation class MigrationId(val value: String)

object migrationTags {
    const val create_users = "create_users"
    const val add_users_email = "add_users_email"
}

@MigrationId(migrationTags.create_users)
class CreateUsers : Migration
```

`migrationTags` باید فقط compile-time constant نگه دارد. annotation argument مقدار String را زمان compile وارد metadata می‌کند؛ آن را runtime registry یا lookup قابل تغییر فرض نکن. `MigrationId.of(...)` در annotation syntax قابل استفاده نیست.

### ۶.۲ Explicit registration و Configuration

```kotlin
migrationConfig {
    migration<CreateUsers>()

    migrationGroup("users") {
        migration<AddUsersEmail>()
    }
}
```

Registration annotation را از type metadata می‌خواند، identity را به declaration نسبت می‌دهد، و type و identity را در یک ordered registration entry همراه می‌کند. هیچ ID دستی در registration تکرار نمی‌شود.

مدل مفهومی:

```kotlin
data class RegisteredMigration(
    val id: MigrationIdentity,
    val migrationClass: KClass<out Migration>,
)

sealed interface MigrationRegistration
data class SingleMigration(val migration: RegisteredMigration) : MigrationRegistration
data class MigrationGroup(
    val name: String,
    val migrations: List<RegisteredMigration>,
) : MigrationRegistration

class MigrationConfiguration(val registrations: List<MigrationRegistration>)
```

`MigrationIdentity` نام candidate برای runtime wrapper است، نه نام قطعی. `MigrationConfiguration` metadata-only و snapshot است: فقط ordered registration tree، identity value، class/type metadata و Group label را نگه می‌دارد؛ Migration instance نمی‌سازد/نگه نمی‌دارد، constructor را invoke نمی‌کند، `up()`/`down()` یا SQL/executor/connection را اجرا نمی‌کند.

### ۶.۳ Annotation extraction و Validation

- Annotation مفقود: registration fail-fast با خطای مشخص class فاقد MigrationId.
- ID خالی/blank یا grammar نامعتبر: هنگام خواندن/تبدیل به runtime domain value رد شود؛ هیچ trim/lowercase/normalization/rewrite انجام نشود.
- ID تکراری در کل ordered registration tree: fail-fast با نمایش مقدار و declarationهای متعارض.
- type ثبت‌شده باید `Migration` باشد؛ validation نوعی در signature generic و در صورت نیاز runtime boundary پوشش داده شود.
- annotation extraction از metadata class انجام شود؛ ساخت instance شرط خواندن ID نیست.
- حداکثر یک MigrationId برای هر class؛ repeatable annotation وارد contract نشود.

### ۶.۴ Runtime Identity Type

`@MigrationId` باید String compile-time دریافت کند. اگر runtime type-safe wrapper حفظ شود:

```kotlin
@JvmInline
value class MigrationIdentity private constructor(val value: String) {
    companion object {
        fun fromAnnotationValue(value: String): MigrationIdentity
    }
}
```

این فقط candidate است. Traceability باید نام نهایی، ضرورت wrapper، package و ABI آن را تعیین کند. `MigrationIdentity.value` عین annotation value است و در مرز State Store به `String` دقیق تبدیل می‌شود. اگر wrapper حذف شود، validation و exact String contract باید جایگزین آن صریحاً تعیین شوند.

## ۷. KClass، Reflection و Lifecycle

- **KClass: Adopt فقط برای type registration metadata**, مشروط به حفظ DSL صریح `migration<T>()` که در درخواست Group/ordering تصویب شده است. این تصمیم ownership هویت را تغییر نمی‌دهد.
- `KClass`/class reference مشخص می‌کند کدام declaration در configuration ثبت شده؛ annotation مشخص می‌کند آن declaration چه identity پایدار دارد.
- `KClass` ابزار instantiation نیست. Constructor پارامتردار، no-arg requirement، DI، provider/factory و Runner خارج scope می‌مانند.
- برای runtime annotation، JVM class metadata/Java annotation API قابل بررسی است؛ استفاده از `KClass.annotations` یا افزودن `kotlin-reflect` بدون نیاز اثبات‌شده لازم فرض نشود.
- ثبت class literal و خواندن annotation نباید Migration instance بسازد. تست implementation آینده باید constructor counter را صفر بار نشان دهد.
- Android lifecycle از identity جداست: annotation extraction روی declaration پیش از instance construction ممکن است؛ هیچ تعارض identity مشخصی با Android از evidence فعلی دیده نشده، اما Android compatibility target نامشخص است.

## ۸. Ordering، Group و Snapshot

1. ترتیب top-level entryها و اعضای Group برابر ترتیب declaration است.
2. Group یک ordered subtree/label است؛ transaction یا execution semantics ندارد.
3. duplicate MigrationId در کل درخت رد شود؛ duplicate Group name مجاز باشد.
4. MigrationConfiguration ساختار را flatten نکند و ID/type association را در هر registration entry حفظ کند.
5. Configuration نباید Migration instanceها را snapshot یا instantiate کند؛ فقط metadata immutable/ordered را نگه دارد.
6. sort بر اساس ID، class، package یا filename انجام نشود.
7. empty config/group policy در Traceability نهایی مستند شود؛ مگر evidence خلافش را نشان دهد، حفظ شود.

## ۹. State Store و Persistence

- State Store فعلی فقط `String` می‌گیرد؛ runtime identity value از annotation به همان مقدار String تبدیل می‌شود.
- Group name، class name، package و filename به State Store داده نمی‌شوند.
- تغییر annotation value پس از apply شدن Migration، breaking identity change است؛ ردیف قبلی بی‌صدا rewrite نشود.
- schema فعلی `VARCHAR(255) UNIQUE` collation صریح ندارد و compatibility target رسمی MySQL/MariaDB پیدا نشده است.
- grammar candidateها همچنان باید مقایسه شوند؛ equality persistence فقط برای IDهای معتبر و متفاوت از alphabet نهایی بررسی شود. Whitespace، case و Unicode خارج از domain احتمالی تنها در صورت ارتباط مستقیم با آن alphabet تحلیل شوند.
- **Persistence equality remains Unresolved.** هیچ collation، version floor یا schema change از روی محیط محلی حدس زده نشود.

## ۱۲. Compatibility و Migration Notes

1. Annotation identity، class/package/filename را منبع هویت نمی‌کند.
2. registration ID دستی از DSL حذف می‌شود؛ registration فقط migration declaration/type را انتخاب و مرتب می‌کند.
3. اگر annotation در هیچ نسخهٔ منتشرشده‌ای مصرف نشده، compatibility data migration لازم نیست؛ انتشار prerelease بیرونی باید جداگانه بررسی شود.
4. تغییر مقدار annotation پس از persist شدن breaking change است.
5. نام annotation و runtime domain wrapper نمی‌توانند در یک package یک declaration name داشته باشند؛ نام/package wrapper تصمیم باز است.
6. `migrationTags` constant holder است، نه registry ثانویه؛ tag مورد استفاده در annotation مرجع declaration-level است.
7. constructor/instantiation strategy تصمیم این نسخه نیست؛ no-arg constraint اضافه نشود.

## ۱۳. Required Traceability Gates

### ۱۳.۱ Identity contract و evidence

- سابقهٔ درخواست اصلی annotation-based identity و درخواست‌های بعدی explicit registration جدا ثبت شوند.
- صریحاً نتیجه گرفته شود که registration type انتخاب می‌کند؛ declaration annotation مالک ID است.
- هر proposal قبلی `migration<T>(MigrationId)` به‌عنوان architectural drift supersede شود، مگر evidence تازهٔ user-approved خلاف آن بیاید.

### ۱۳.۲ `migrationTags` و syntax

- بررسی شود exact syntax با `object migrationTags { const val ... }` از نظر compile-time annotation argument معتبر است.
- annotation پارامتر `String` بگیرد؛ value class/factory call در annotation قرار نگیرد.
- مشخص شود ثابت‌ها source مرکزی tagها هستند، اما registry/runtime lookup نیستند و مقدارشان در metadata compile می‌شود.
- اگر syntax دقیقاً قابل استفاده نیست، محدودیت فنی و نزدیک‌ترین syntax مستند شود؛ بدون evidence syntax عوض نشود.

### ۱۳.۳ Runtime wrapper و annotation extraction

- تصمیم شود آیا runtime `MigrationIdentity` value class لازم است یا همان String اعتبارسنجی‌شده کافی است.
- اگر wrapper انتخاب شود، نام/package جدا از annotation `MigrationId` باشد و exact value حفظ شود.
- ثابت شود runtime annotation را می‌توان از class metadata خواند بدون ساخت Migration instance.
- `kotlin-reflect` فقط با evidence نیاز اضافه شود؛ مسیر JVM reflection موجود بررسی شود.

### ۱۳.۴ Registration / KClass

- explicit registration برای membership/order/group از هویت annotation تفکیک شود.
- حفظ generic `migration<T>()` در درخواست DSL، evidence برای type association در registration است؛ KClass صرفاً آن type metadata را حفظ می‌کند.
- KClass به identity owner، instantiation mechanism یا no-arg contract تبدیل نشود.
- اگر registration identity تنها کافی دانسته شد، باید دقیقاً توضیح داده شود DSL چگونه declaration type و ordering را حفظ می‌کند؛ generic syntax بدون semantic اثر مجاز نیست.

### ۱۳.۵ Domain و persistence equality

- دو grammar پیشنهادی قبلی و trailing/repeated underscore policy با تصمیم project-level نهایی شوند یا Unresolved بمانند.
- product/version compatibility target بدون evidence تعیین نشود.
- برابری unique index برای تمام IDهای معتبر و متفاوت از alphabet تصویب‌شده تحت collation target اثبات شود؛ در غیر این صورت persistence gate باز بماند.

### ۱۳.۶ Kotlin/JVM و Android

- Kotlin 2.2.0، JVM toolchain 24 و عدم pin صریح bytecode target ثبت شوند.
- Java consumer evidence: none found in repository؛ Java ABI gate صرفاً فرضی ایجاد نشود.
- Android compatibility target: unresolved / not currently defined؛ Android به‌تنهایی دلیل تغییر identity model نیست.
- compile proof برای annotation syntax، const value و runtime class-metadata access در implementation stage لازم است؛ در Traceability build/source تغییر نکند.

### ۱۳.۷ Status

KClass/annotation semantics و grammar تعیین تکلیف شده‌اند و Identity/Registration برای implementation آماده است. Persistence equality به دلیل نبود compatibility target در repository جداگانه Deferred می‌ماند؛ این تعویق مانع implementation قرارداد Identity نیست، اما مانع ادعای compatibility persistence یا verification آن برای databaseهای هدف است.

## ۱۴. Final Decisions

این جدول فقط سه gate باقی‌مانده را می‌بندد. شواهد Kotlin از مستندات رسمی زبان گرفته شده؛ برای persistence، نبود compatibility target رسمی در repository مانع نتیجه‌گیری قطعی است.

| # | تصمیم | وضعیت | نتیجه و مبنا |
|---|---|---|---|
| 1 | مالک `MigrationId` | **Adopt** | Declaration مالک هویت است. `@MigrationId(...)` روی کلاس قرار می‌گیرد؛ registration مقدار هویت را تعیین نمی‌کند. |
| 2 | نقش `migrationTags` | **Adopt** | فقط محل compile-time `String` constantهاست، نه registry یا منبع runtime جداگانه. Kotlin اجازه می‌دهد `const val` عضو `object` باشد و آن را در annotation argument به‌کار ببریم؛ پس `@MigrationId(migrationTags.create_users)` با قرارداد annotation سازگار است. citeturn0search0turn0search1 |
| 3 | معنای registration | **Adopt** | `migration<T>()` declaration را برای membership و ترتیب انتخاب می‌کند؛ `migration<T>(MigrationId)` وجود ندارد. ترتیب top-level و داخل Group حفظ می‌شود و Group فقط ساختار configuration است. |
| 4 | Grammar شناسه | **Adopt** | Grammar برابر `^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$` با حداکثر طول 255 نویسه است. این انتخاب lowercase ASCII را به invariant domain تبدیل می‌کند و underscore انتهایی/متوالی را رد می‌کند. مبنا: grammar مستند `snake_case` و سقف 255 در قرارداد v1.18، همراه با tagهای پیشنهادی `create_users` و `add_users_email`؛ این تصمیم قرارداد جدید v1.19 است و صرفاً convention کد محسوب نمی‌شود. هیچ trim، case conversion یا normalization انجام نمی‌شود. |
| 5 | برابری در persistence | **Deferred** | Collision در alphabet معتبر ممکن است: مستند MySQL فهرست می‌کند که `utf8mb4_la_0900_ai_ci` collation مربوط به Classical Latin است و مستند Unicode می‌گوید Classical Latin accent-insensitive collationها `I/J` و `U/V` را برابر می‌سنجند. چون `_ci` نیز case-insensitive است، lowercaseهای `i/j` و `u/v` هم می‌توانند برابر شوند؛ مثلاً `id_users` و `jd_users`. این شاهد امکان collision را در MySQL ثابت می‌کند، نه اینکه آن collation target پروژه باشد. Case-insensitivity به‌تنهایی برای alphabet lowercase collision نمی‌سازد؛ trailing-space تفاوت PAD/NO PAD این domain را شامل نمی‌شود؛ Unicode/accent خارج از domain است. citeturn0search0turn0search1turn1search2 |
| 6 | Wrapper زمان اجرا | **Adopt** | از `MigrationIdentity` به‌عنوان value class زمان اجرا استفاده شود، با نامی جدا از annotation `MigrationId`. این نوع، ID اعتبارسنجی‌شده را از `String`های عادی و Group label متمایز می‌کند؛ مقدار داخلی عین annotation value است و در مرز State Store بدون تغییر به `String` تبدیل می‌شود. annotation همچنان compile-time `String` می‌گیرد؛ تبدیل و validation پس از خواندن metadata انجام می‌شود. |
| 7 | مرز `KClass` | **Adopt — registration metadata فقط** | DSL نوعی `migration<T>()` ثبت declaration مشخص را بیان می‌کند؛ configuration باید association هر registration با type انتخاب‌شده را حفظ کند. بنابراین `KClass<out Migration>` در registration snapshot می‌ماند، ولی نه identity است، نه instantiation policy و نه Migration instance. این association از DSL و ordered registration contract می‌آید، نه از فرض نیاز Runner. No-arg، constructor، DI و resolution خارج از scope هستند. Java consumer در repository پیدا نشده؛ Android compatibility target تعریف نشده و blocker جداگانه‌ای ایجاد نمی‌کند. |
| 8 | استخراج annotation | **Adopt** | Annotation با مقدار `String` و `RUNTIME` retention از metadata کلاس خوانده می‌شود؛ خواندن metadata مستلزم ساخت Migration instance نیست. `const val`های String مجازند، ولی `MigrationId.of(...)` یا value class نمی‌تواند annotation argument باشد. از Java class metadata / `Class.getAnnotation(...)` استفاده شود؛ `kotlin-reflect` بدون نیاز اثبات‌شده اضافه نشود. مستندات Kotlin نوع‌های مجاز annotation و دسترسی runtime برای retention را مشخص می‌کنند. citeturn0search1turn0search12 |

### Final distinction

`MigrationId` = هویت پایدار و opaque از نظر semantics، با grammar عمومی مشخص‌شده؛ `KClass` = metadata نوع declaration ثبت‌شده؛ `Group name` = برچسب ساختاری configuration. `migrationTags` فقط ثابت‌های کامپایل‌تایم را نگه می‌دارد. این مفاهیم یکی نیستند.

### Persistence Gate — Final Decision

1. **Persistence equality result:** دو MigrationId متفاوت که هر دو عضو grammar قطعی‌اند ممکن است تحت برخی MySQL collations برابر تلقی شوند؛ نمونهٔ رسمی Classical Latin بالا یک collision درون alphabet دارد. دربارهٔ collation واقعی ستون در deploymentهای پروژه نمی‌توان نتیجهٔ قطعی داد. `VARCHAR(255) UNIQUE` یکتایی را بر اساس equality همان collation اعمال می‌کند. در MariaDB نیز collation قواعد مقایسه را تعیین می‌کند و رشتهٔ بدون collation صریح، مقدار را از سطوح بالاتر به ارث می‌برد. citeturn2search1turn2search0turn2search3
2. **Compatibility target:** `Compatibility target: not defined by repository`. Plan v2.1 تعیین compatibility target کلی را خارج از scope ثبت می‌کند؛ JDBC driver dependency و مثال‌های اتصال، minimum server version یا collation تضمین‌شده تعریف نمی‌کنند. پس version floor یا collation انتخاب نمی‌شود.
3. **Persistence gate:** برای implementation بخش Identity/Registration **Deferred** است، نه blocker؛ زیرا آن قرارداد بدون تغییر State Store/schema قابل پیاده‌سازی است. این تصمیم به معنی تضمین رفتار unique persistence نیست. هر ادعای سازگاری یا verification دیتابیسی تا تعیین product/version target و collation مؤثر مسدود می‌ماند.
4. **Overall v1.19:** **Identity Contract: Implementation Ready; Persistence Compatibility: Deferred** — implementation قرارداد Identity/Registration آماده است و ادعای سازگاری persistence تا تعیین target معلق می‌ماند.
