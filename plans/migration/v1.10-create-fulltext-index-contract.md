# Migration v1.10: CREATE FULLTEXT INDEX Contract Analysis

وضعیت: `implemented`

## پیش‌زمینه و هدف

عملیات v1.6 تا v1.9 خانوادهٔ پایهٔ Index را پوشش می‌دهند: `CREATE INDEX` تک‌ستونی، `DROP INDEX`، `CREATE UNIQUE INDEX` تک‌ستونی و `CREATE MULTI-COLUMN INDEX` غیر unique. گام بعدی، operation مستقل `CREATE FULLTEXT INDEX` است.

برای drop کردن هر یک از این indexها operation جدید لازم نیست. `DROP INDEX` موجود در v1.7 با دریافت نام جدول و index می‌تواند index معمولی، unique، multi-column یا FULLTEXT را حذف کند؛ semantics نوع index هنگام drop در این operation نقشی ندارد. بنابراین `DROP MULTI-COLUMN INDEX` یا `DROP FULLTEXT INDEX` در roadmap ساخته نمی‌شود.

Traceability قرارداد انجام و یافته‌های کد و مستندات در ادامه ثبت شده‌اند. این مرحله implementation انجام نمی‌دهد؛ پیاده‌سازی پس از تأیید contract نهایی شروع می‌شود.

## انتخاب operation و استقلال از نسخه‌های قبلی

operation مستقل نهایی:

```kotlin
createFullTextIndex {
    tableName("posts")
    name("ft_posts_content")
    columns("title", "content")
}
```

SQL مفهومی MySQL:

```sql
CREATE FULLTEXT INDEX `ft_posts_content`
ON `posts` (`title`, `content`)
```

نام DSL مطابق convention موجود `createFullTextIndex` است.

- `createIndex` v1.6، `createUniqueIndex` v1.8 و `createMultiColumnIndex` v1.9 بدون تغییر می‌مانند.
- FULLTEXT با boolean/flag به operationهای قبلی اضافه نمی‌شود؛ AST و API خودش را دارد.
- `dropIndex` v1.7 برای حذف FULLTEXT نیز استفاده می‌شود و تغییر نمی‌کند.
- اگر traceability نشان دهد AST/renderer مشترک باعث نشت semantics یا validation بین operationها می‌شود، reuse انجام نشود. reuse فقط با حفظ قرارداد FULLTEXT مجاز است.

## Contract نهایی پس از Traceability

- MySQL تنها dialect پشتیبانی‌شده در این operation است.
- یک FULLTEXT index نام‌گذاری‌شده روی یک جدول موجود.
- ورودی ستون‌ها به‌صورت فهرست مرتب دریافت می‌شود؛ ترتیب ورودی بدون sort یا reorder حفظ می‌شود.
- حداقل ستون ۱ است؛ grammar رسمی MySQL یک یا چند `key_part` را می‌پذیرد. این operation با `columns(...)` یک ستون یا بیشتر می‌گیرد و حداقل دو ستون v1.9 به آن تعمیم نمی‌یابد.
- سقف مصنوعی library برای تعداد ستون‌ها وجود ندارد؛ محدودیت واقعی server/storage engine مسئولیت دیتابیس است.
- index و table name صریح و اجباری‌اند؛ auto-generated name خارج از scope است.
- duplicate-column policy مطابق الگوی واقعی v1.9 تعیین می‌شود: Builder پس از trim مقایسهٔ case-insensitive انجام می‌دهد و duplicate را رد می‌کند؛ Renderer همین invariant را دفاعی روی AST بررسی می‌کند. این library contract است، نه ادعای الزام MySQL. spelling/casing معتبر در AST حفظ می‌شود.
- FULLTEXT همیشه semantics مخصوص خود را دارد؛ `UNIQUE`, `SPATIAL`, `PRIMARY KEY` یا حالت ترکیبی وارد AST/API نشود.
- تنظیم parser/tokenizer/stopword، minimum token length، زبان، ranking/search و queryهای `MATCH ... AGAINST` بیرون از scope هستند. یکسان‌بودن character set و collation ستون‌های یک FULLTEXT index، اگر در دیتابیس نقض شود، محدودیت schema و مسئولیت MySQL است؛ این قاعده مجوز introspection یا validation کتابخانه نیست.

## نتایج Traceability و قیود معماری

Traceability به نتایج زیر رسید:

1. مسیر v1.6 تا v1.9 ردیابی شد؛ جزییات مسیر و فایل‌ها در بخش «شواهد Traceability کد repository» آمده است.
2. grammar و محدودیت‌های MySQL 8.4 در بخش «نتیجهٔ Traceability مستندات MySQL» ثبت شدند؛ schema/engine restrictions اعتبارسنجی library نیستند.
3. جست‌وجوی repository انجام شد: compatibility target عمومی یا minimum supported MySQL اعلام نشده است؛ این مورد finding پروژه است. نسخه‌های موجود در تست‌ها و شرط‌های v1.4 فقط برای سناریوهای همان operation هستند، نه target عمومی. نسخهٔ محلی توسعه‌دهنده معیار minimum support نیست.
4. نوع ستون، engine، charset/collation و partitioning database-level هستند. Builder/Renderer schema واقعی را نمی‌دانند؛ این operation introspection یا validation مبتنی بر schema ندارد.
5. duplicate policy، trim، blank validation، identifier escaping و validation AST مستقیم مطابق قرارداد v1.9 تثبیت شدند.
6. مسیر executor موجود `MigrationExecutor` → `IQueryExecute.executeTable` است و reuse می‌شود؛ executor/manager/connection یا abstraction تولیدی جدید ساخته نمی‌شود.
7. dependency direction حفظ می‌شود: AST/Builder مستقل از execution؛ renderer مستقل از manager، connection، introspection و JDBC؛ executor متکی به manager موجود.
8. v1.2 هنوز `planned` است، اما FULLTEXT به abstraction مورد بررسی آن وابسته نیست؛ ترتیب شماره نسخه‌ها blocker محسوب نمی‌شود.


## نتیجهٔ Traceability مستندات MySQL

مستندات رسمی MySQL 8.4، بخش‌های [`CREATE INDEX Statement`](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) و [`FULLTEXT Restrictions`](https://dev.mysql.com/doc/refman/8.4/en/fulltext-restrictions.html)، با contract تطبیق داده شدند:

- grammar مربوط به `CREATE INDEX` حالت `FULLTEXT` و فهرست یک یا چند `key_part` را پشتیبانی می‌کند؛ بنابراین حداقل ستون یک است و ستون‌ها در DSL به شکل ordered list می‌آیند.
- FULLTEXT روی ستون‌های `CHAR`، `VARCHAR` و `TEXT` و در storage engineهای `InnoDB` و `MyISAM` پشتیبانی می‌شود. تشخیص نوع ستون و engine به schema introspection نیاز دارد؛ library در این operation introspection نمی‌کند و این محدودیت‌ها را validate نمی‌کند.
- ستون‌های یک FULLTEXT index باید character set و collation یکسان داشته باشند. این شرط schema-level است و بدون introspection به validation Builder/Renderer تبدیل نمی‌شود.
- Full-text search روی partitioned tables پشتیبانی نمی‌شود؛ تشخیص partitioning نیز schema-level است و به MySQL واگذار می‌شود.
- syntax رسمی گزینهٔ اختیاری `WITH PARSER parser_name` دارد؛ این parser option و تنظیمات search خارج از scope v1.10 باقی می‌مانند.
- prefix length برای FULLTEXT پشتیبانی نمی‌شود؛ FULLTEXT کل column را index می‌کند، پس API این option را نمی‌پذیرد.
- نوع ستون، engine، charset/collation و partitioning محدودیت‌های وابسته به schema/engine هستند. Builder/Renderer فقط identifierها را می‌شناسند؛ خطای این موارد باید از MySQL به caller برسد و این operation preflight/introspection اضافه نمی‌کند.
- جست‌وجوی repository برای minimum supported MySQL version و compatibility target عمومی نتیجه‌ای نداشت. ارجاع‌های MySQL 8.0/MariaDB 10.5.3 در rename-column فقط syntax target همان operation هستند؛ این‌ها baseline کلی repository نیستند.



## API/AST و Builder Contract

شکل نهایی DSL و AST:

```text
createFullTextIndex {
    tableName(table)
    name(index)
    columns(column1, column2, ...)
}

CreateFullTextIndexAst
├── tableName: String?
├── indexName: String?
└── columnNames: List<String>?
```

`columnNames: List<String>?` مدل مناسب reference به ستون‌های موجود است. حداقل یک ستون پذیرفته می‌شود. هر فراخوانی `columns(...)` کل فهرست قبلی را جایگزین می‌کند و ترتیب آرگومان‌های آخرین فراخوانی حفظ می‌شود، همانند v1.9.

Builder ورودی‌ها را trim می‌کند و casing و محتوای identifier را حفظ می‌کند. Builder و Renderer هر دو duplicate ستون‌ها را پس از trim و با مقایسهٔ case-insensitive رد می‌کنند؛ این سیاست library invariant است. Renderer AST ناقص/نامعتبر را پیش از quote یا ساخت SQL دفاعی بررسی می‌کند.

## Renderer Contract

SQL مفهومی:

```sql
CREATE FULLTEXT INDEX <quoted-index-name>
ON <quoted-table-name> (<quoted-column-1>, <quoted-column-2>, ...)
```

- کلمهٔ `FULLTEXT` از semantics خود operation می‌آید و flag دلخواه کاربر نیست.
- نام index، جدول و هر نام ستون با quote/escape dialect موجود وارد SQL شوند؛ identifierها bind parameter نیستند.
- ترتیب ستون‌ها، در صورت تأیید contract، عیناً حفظ شود.
- Renderer به سرور یا manager وصل نمی‌شود و metadata دیتابیس را نمی‌خواند.
- compatibility target عمومی MySQL در repository اعلام نشده است؛ از این operation minimum supported version کلی library استنتاج نمی‌شود.

## Executor، مثال و تست

- entry point/overload فقط در executor موجود و مطابق convention repository افزوده شود؛ اجرای SQL از مسیر فعلی `IQueryExecute.executeTable` انجام شود.
- fake باید abstraction واقعی `IQueryExecute` را هدف بگیرد؛ abstraction تولیدی تازه برای تست ایجاد نشود.
- مثال versioned و render-only به‌صورت پیش‌فرض باشد؛ اجرای DDL فقط با opt-in روشن انجام شود.
- unit test بدون دیتابیس، SQL دقیق و quoting/escaping، ترتیب ستون‌ها، trim/casing، validation نهایی، Builder و Renderer روی AST مستقیم را بپوشاند.
- executor fake ارسال SQL به `executeTable`، callback موفقیت و انتقال failure/cause را بسنجد؛ هرگونه select/preflight/introspection ناخواسته باید fail شود.
- regressionهای v1.6 تا v1.9 اجرا شوند و فایل‌های محلی کاربر در `Main.kt` حفظ شوند.
- integration test روی MySQL اختصاصی و قابل reset اختیاری است، نه پیش‌نیاز test عادی. اگر نوشته شد، ایجاد index و metadata نوع FULLTEXT/ستون‌های ثبت‌شده را بررسی کند.

## خارج از scope

- `DROP FULLTEXT INDEX` مستقل؛ `DROP INDEX` v1.7 کافی است.
- تغییر operationهای v1.6 تا v1.9.
- SPATIAL index، ترکیب FULLTEXT با UNIQUE یا SPATIAL و dialectهای دیگر.
- parser/tokenizer/stopword configuration، search DSL، `MATCH ... AGAINST`، ranking و query execution.
- prefix length (برای FULLTEXT پشتیبانی نمی‌شود)، expression/functional index، index options، algorithm/lock و auto-generated names.
- introspection، preflight، `IF NOT EXISTS`، rollback، migration history یا runner.
- abstraction عمومی Index صرفاً برای کاهش تکرار، مگر آنکه traceability الگوی موجود و reuse معنایی امن را اثبات کند.

## Roadmap خانوادهٔ Index

```text
Index v1
├── v1.6 CREATE INDEX (single-column, non-unique) ✅
└── v1.7 DROP INDEX (any supported index by name) ✅
        ↓
Index v2
├── v1.8 CREATE UNIQUE INDEX (single-column) ✅
└── v1.9 CREATE MULTI-COLUMN INDEX (non-unique) ✅
        ↓
Index v3
├── v1.10 CREATE FULLTEXT INDEX (separate operation) ✅
├── future: CREATE SPATIAL INDEX
└── future: dialect-specific index options
```

`DROP INDEX` برای indexهای ساخته‌شده در مراحل بعد نیز استفاده می‌شود؛ operation حذف جداگانه بر اساس نوع index برنامه‌ریزی نشده است.
