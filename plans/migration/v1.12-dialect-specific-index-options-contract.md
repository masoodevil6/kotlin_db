# Migration v1.12: Dialect-specific Index Options Contract Analysis

وضعیت: `Implemented`

## پیش‌زمینه و هدف

پس از تکمیل v1.11 `CREATE SPATIAL INDEX`، مرحلهٔ بعد در roadmap خانوادهٔ Index بررسی امکان پشتیبانی از optionهای وابسته به dialect است.

این عنوان فعلاً یک دستهٔ کلی از قابلیت‌هاست، نه یک operation یا contract مشخص. قبل از طراحی API یا implementation باید با شواهد repository و مستندات رسمی تعیین شود:

- منظور دقیق از «index option» چیست و کدام گزینه‌ها واقعاً مورد نیازند.
- option به کدام operationهای موجود تعلق می‌گیرد.
- تفاوت grammar میان MySQL و MariaDB چیست.
- آیا مدل‌سازی option نیازمند API/AST جدید یا تغییر operationهای موجود است.
- سازگاری option با dialect version چگونه باید تعیین شود.

این plan فقط Contract Analysis و Traceability است. implementation در scope نیست و تا بسته‌شدن Traceability ممنوع است.

ترتیب کلی:

```text
v1.11 CREATE SPATIAL INDEX
        ↓
Implementation + Tests + Regression  ✅
        ↓
v1.12 Contract Analysis
        ↓
Traceability
        ↓
Final Contract
        ↓
Implementation Ready
        ↓
Implementation
```

## اصل راهنما

- عنوان v1.12 مجوز اضافه‌کردن optionهای حدسی یا یک bag عمومی از تنظیمات نیست.
- هیچ API مانند `options(Map<String, Any>)`، SQL خام، stringly-typed option، یا abstraction عمومی Index صرفاً برای پیش‌بینی آینده طراحی نشود.
- هر گزینه باید با syntax رسمی dialect هدف، نسخه‌های مستندشده، معنا، operationهای قابل‌اعمال، validation و آزمون مستقل توجیه شود.
- تغییر semantics نسخه‌های v1.6 تا v1.11 ممنوع است، مگر آنکه Traceability یک نیاز واقعی و ناسازگاری اجتناب‌ناپذیر را ثابت کند؛ در آن صورت scope جداگانه و تصمیم صریح لازم است.
- `DROP INDEX` در v1.7 همچنان برای حذف index بر اساس نام استفاده می‌شود؛ v1.12 عملیات drop جدیدی تعریف نمی‌کند مگر Traceability نیاز مستقل و evidenceدار نشان دهد.

## دسته‌بندی candidateها برای Traceability

این دسته‌بندی برای تعیین مرزهای grammar است، نه تأیید پشتیبانی یا طراحی API. هیچ candidate در این بخش هنوز وارد قرارداد یا DSL نمی‌شود.

- **Index-definition options:** مواردی که grammar آن‌ها را به تعریف index متصل می‌کند؛ candidateها شامل `USING BTREE/HASH`, `COMMENT`, visibility در MySQL (`VISIBLE`/`INVISIBLE`) و معادل یا syntax MariaDB (`IGNORED`) هستند. `WITH PARSER` فقط برای FULLTEXT بررسی شود. گزینه‌های خاص MariaDB مانند `CLUSTERING`, `DISTANCE` و `M` نیز فقط در صورت ارتباط با use case واقعی بررسی شوند.
- **Key-part definition:** مواردی که به هر index column تعلق دارند، نه به index به‌عنوان کل؛ از جمله prefix length و `ASC`/`DESC`. در MySQL grammar، prefix بخشی از `index_col_name` است (`col_name(length)`), نه `index_option`. اگر بررسی شوند، باید به‌عنوان احتمالاً قرارداد جداگانهٔ column/key-part مدل شوند؛ به `IndexOptions` نچسبند.
- **DDL execution clauses:** `ALGORITHM` و `LOCK` باید جدا از index-definition options بررسی شوند. منابع MySQL و MariaDB آن‌ها را به DDL مربوط به ایجاد/تغییر index وصل می‌کنند و DROP INDEX نیز ممکن است execution clauseهای مربوط را داشته باشد. Traceability باید مشخص کند آیا آن‌ها در scope خانوادهٔ Index هستند یا به مرحله‌ای جدا برای DDL execution options تعلق دارند.
- **Operation-specific syntax:** `WITH PARSER`، قواعد `USING` برای FULLTEXT/SPATIAL و تفاوت engineها operation-specific هستند. syntax مشترک ظاهری، semantics مشترک را ثابت نمی‌کند.

candidateهای مورد بررسی و شواهد اولیه‌ای که باید با منابع رسمی نسخهٔ هدف بازبینی شوند:

| Candidate | MySQL (initial evidence) | MariaDB (initial evidence) | Traceability focus |
|---|---|---|---|
| `USING BTREE/HASH` | candidate اولیه: موجود؛ engine و نوع index محدودیت دارند؛ برای FULLTEXT مجاز نیست و SPATIAL قیود خودش را دارد | candidate اولیه: `BTREE`, `HASH`, `RTREE` در grammar/engineهای مشخص | هر assertion با grammar رسمی هر dialect/version تأیید شود؛ engine و operation applicability؛ use case لازم |
| `WITH PARSER` | candidate اولیه: فقط FULLTEXT | candidate اولیه: FULLTEXT/parserهای MariaDB | syntax و plugin registration هر محصول جدا بررسی شود |
| `COMMENT` | candidate اولیه: index comment | candidate اولیه: پشتیبانی دارد | size limit، persistence و version semantics تأیید شود |
| Visibility | candidate اولیه: `VISIBLE` / `INVISIBLE` | candidate اولیه: `IGNORED` با syntax متفاوت و semantics نزدیک | abstraction معنایی مشترک فرض نشود؛ version، optimizer behavior و operation applicability بررسی شود |
| `IGNORED` | candidate اولیه: وجود ندارد | candidate اولیه: MariaDB-specific؛ reportedly از 10.6 به بعد | نسخه و semantics در مستندات رسمی تأیید شود؛ فقط با use case وارد contract شود |
| `CLUSTERING`, `DISTANCE`, `M` | candidate اولیه: در grammar بررسی‌شده پیدا نشده‌اند | candidateهای MariaDB-specific | grammar رسمی تعیین کند کدام operation/engine/type و semantics |
| `KEY_BLOCK_SIZE` | candidate اولیه: محدودیت engine و semantics storage دارد | candidate اولیه: گزینه و semantics جدا دارد | احتمال defer؛ property عمومی index فرض نشود |
| Prefix length | candidate اولیه: بخشی از key-part grammar، مثل `column(20)` | candidate اولیه: key-part grammar با محدودیت‌های خودش | index-level option نیست؛ قرارداد key-part جدا بررسی شود |
| `ALGORITHM`, `LOCK` | candidate اولیه: DDL execution clauses برای عملیات index/table؛ syntax و concurrency semantics مختص عملگر | candidate اولیه: DDL execution clauses با grammar و محدودیت نسخهٔ خود | از definition options جدا؛ تصمیم دربارهٔ scope مستقل |

این ماتریس فقط نقطهٔ شروع است. هر cell باید در Traceability با منبع رسمی MySQL یا MariaDB برای نسخه‌های بررسی‌شده تأیید یا اصلاح شود؛ نبود evidence نباید به‌صورت پشتیبانی فرض شود.

هیچ‌یک از موارد بالا خودکار وارد API نمی‌شوند. Traceability باید گزینه‌ها را به‌صورت جدول evidence ثبت و برای هر مورد یکی از تصمیم‌های `adopt`, `defer`, `reject` را مستند کند.

## تفکیک grammar مورد انتظار

```text
Index definition
├── USING / COMMENT / visibility family
├── WITH PARSER (FULLTEXT-specific)
└── dialect-specific definition attributes

Key-part definition
├── column name
├── prefix length?
└── direction (ASC/DESC)?

DDL execution clauses
├── ALGORITHM
└── LOCK
```

این دیاگرام فقط طبقه‌بندی برای Traceability است؛ هیچ API، AST مشترک یا `IndexOptions` type را پیشنهاد یا مجاز نمی‌کند.

## پرسش‌های الزامی Traceability

1. **Repository use cases:** آیا کد، مستندات، مثال‌ها یا برنامهٔ مصرف‌کننده نیاز مشخصی برای index option ثبت کرده‌اند؟ نیاز کلی «پشتیبانی از optionها» کافی نیست؛ use case باید option، operation و dialect هدف را مشخص کند. اگر use caseی پیدا نشد، این finding را ثبت کنید و option صرفاً برای کامل‌بودن SQL اضافه نشود.
2. **نسخه‌ها و وضعیت:** تأیید کنید v1.11 implementation شده و تست‌های آن به‌همراه regressionهای v1.6 تا v1.10 موفق بوده‌اند. این plan نباید پیش از آن به implementation برود.
3. **Operation surface:** برای هر گزینه تعیین کنید آیا روی `CREATE INDEX`, `CREATE UNIQUE INDEX`, `CREATE MULTI-COLUMN INDEX`, `CREATE FULLTEXT INDEX` یا `CREATE SPATIAL INDEX` قابل اعمال است. گزینه‌ای که فقط به یک grammar تعلق دارد نباید به APIهای دیگر نشت کند.
4. **Grammar category:** هر مورد را مشخصاً در یکی از این دسته‌ها قرار دهید: index-definition option، key-part definition، یا DDL execution clause. Prefix length و `ASC`/`DESC` را به‌عنوان index-level option طبقه‌بندی نکنید مگر grammar رسمی آن را تأیید کند.
5. **MySQL grammar/evidence:** syntax رسمی، محدودیت‌ها، engineها و نسخهٔ ورود/تغییر هر candidate را از مستندات رسمی MySQL بررسی کنید. `USING` برای indexهای عادی را به FULLTEXT/SPATIAL تعمیم ندهید؛ grammar index definition را با DDL execution clauses یا رفتار runtime خلط نکنید.
6. **MariaDB evidence:** syntax، semantics، نسخه و engineها را جداگانه از مستندات رسمی MariaDB بررسی کنید. `IGNORED` را معادل API-level `INVISIBLE` فرض نکنید؛ ارث‌بری `MariaDbDialect` از `MySqlDialect` به‌تنهایی پشتیبانی یکسان را ثابت نمی‌کند.
7. **Dialect/version policy:** مشخص کنید option در زمان SQL generation چگونه به dialect و target version متصل می‌شود. renderer به connection یا server introspection دسترسی نداشته باشد. اختلاف target و detected server نباید موجب rewrite خاموش شود؛ policy موجود v2.1 را بررسی کنید، ولی scope v1.12 را بی‌دلیل به capability framework عمومی گسترش ندهید.
8. **API/AST:** بررسی کنید آیا گزینهٔ تایپ‌شده و operation-specific کافی است یا operation جدید لازم است. `options(Map)`، `Any`, SQL fragment خام و propertyهای مبهم مثل Boolean flag بدون semantics ممنوع‌اند.
9. **Validation boundary:** Builder ورودی DSL را بررسی کند؛ renderer پیش از quoting/SQL composition، AST را دفاعی اعتبارسنجی کند. وجود ستون، نوع ستون، engine/table eligibility، collation/SRID و metadata schema با introspection این plan اضافه نشوند.
10. **Dependency direction:** AST و Builder مستقل از execution بمانند؛ dialect/renderer مستقل از manager و اتصال DB باشند؛ executor مسیر موجود `MigrationExecutor → IQueryExecute.executeTable` را به کار ببرد.
11. **v1.2 dependency:** قرارداد v1.2 را بررسی کنید، اما صرفاً تقدم شمارهٔ نسخه را dependency تلقی نکنید. اگر option feature به abstraction مشترک واقعی وابسته نیست، این استقلال را ثبت کنید.
12. **Compatibility target:** compatibility target عمومی repository و حداقل grammar/engine لازم برای هر option دو موضوع جدا هستند. نسخهٔ نصب‌شدهٔ توسعه‌دهنده minimum support محسوب نمی‌شود. اگر compatibility target repository اعلام نشده، آن را finding نگه دارید.
13. **Regression/API compatibility:** تغییر پیشنهادی نباید AST/DSL یا SQL نسخه‌های v1.6 تا v1.11 را بی‌دلیل تغییر دهد. اگر نمی‌توان این را حفظ کرد، این مورد باید به‌عنوان تصمیم breaking change مجزا ثبت شود.

## خروجی Traceability

Traceability باید در همین plan ثبت شود و فقط شامل evidence و تصمیم‌های لازم باشد:

```text
Traceability Result
├── Repository Use Cases
├── v1.11 Completion Check
├── Candidate Options Matrix
├── Grammar Category Classification
├── MySQL Evidence
├── MariaDB Evidence
├── Dialect and Version Policy
├── Operation Applicability
├── API/AST Decision
├── Builder/Renderer Validation Decision
├── Executor/Reusability Evidence
├── Compatibility Target
├── v1.2 Dependency Check
└── Final Contract Decision
```

برای هر گزینه حداقل این فیلدها ثبت شوند:

| Field | Required evidence |
|---|---|
| Option | نام دقیق و semantics رسمی |
| Applicable operations | operationهایی که grammar اجازه می‌دهد |
| Dialects | MySQL/MariaDB و هر تفاوت مستند |
| Version/engine constraints | حداقل‌های مستند، جدا از target کلی repository |
| Repository use case | محل نیاز واقعی یا «یافت نشد» |
| Decision | adopt / defer / reject همراه دلیل |
| Contract impact | API/AST/renderer/executor/test تغییر لازم |

اگر شواهد با فرض اولیه تعارض داشتند، candidate یا scope اصلاح شود؛ implementation برای وادار کردن repository به پیروی از plan مجاز نیست.

## موارد خارج از scope

- implementation یا تغییر source قبل از تکمیل Traceability و نهایی‌شدن contract.
- افزودن همهٔ optionهای موجود در MySQL یا MariaDB به‌صورت یکجا.
- API عمومی مبتنی بر map، `Any`، SQL خام یا رشته‌های آزاد.
- query/search DSL، execution tuning عمومی یا مدیریت engine.
- introspection، preflight، migration history، runner و rollback.
- تغییر semantic نسخه‌های v1.6 تا v1.11 بدون تصمیم مستقل و evidence.
- abstraction عمومی Index صرفاً برای تجمیع optionها.
- ادعای compatibility بر اساس نصب محلی توسعه‌دهنده.

## Traceability Result — 2026-09-29

### Repository Evidence

- ساخت indexها با API، AST، Builder و rendererهای مستقل انجام شده است: CREATE INDEX در v1.6، CREATE UNIQUE INDEX در v1.8، CREATE MULTI-COLUMN INDEX در v1.9، CREATE FULLTEXT INDEX در v1.10 و CREATE SPATIAL INDEX در v1.11. abstraction عمومی IndexOptions وجود ندارد.
- MySqlDialect هر AST را جداگانه در registry ثبت می‌کند. MariaDbDialect از MySqlDialect ارث می‌برد و محصول را MariaDB اعلام می‌کند؛ inheritance به‌تنهایی اثبات یکسانی همهٔ grammarها نیست.
- renderer فعلی v1.6 identifierها را quote/escape می‌کند و SQL تک‌ستونی پایه را تولید می‌کند. Builder مقادیر را trim می‌کند. MigrationExecutor از مسیر مشترک executeOut و IQueryExecute.executeTable استفاده می‌کند.
- در source، test و example نیاز مصرف‌کننده‌ای برای هیچ‌یک از candidateها پیدا نشد. اشاره در planها یا تست‌هایی که نبود option را assert می‌کنند، use case مصرف‌کننده حساب نشد.
- targetDatabaseVersion در config و DialectSelector موجود است؛ فعلاً تصمیم syntax آن برای RENAME COLUMN به کار می‌رود. option جدید نباید بر مبنای metadata اتصال rewrite شود.
- v1.2 دربارهٔ اشتراک احتمالی CREATE/DROP TABLE است و dependency واقعی با این option پیدا نشد؛ v1.12 از آن مستقل است.

| OR REPLACE و IF NOT EXISTS | رفتار statement و idempotency را تغییر می‌دهند؛ option تعریف index نیستند. | یافت نشد. | reject از v1.12؛ semantics v1.6 تا v1.11 تغییر نمی‌کند. |

### Grammar Categories

- Index definition: USING، COMMENT، visibility، KEY_BLOCK_SIZE و engine attributes.
- FULLTEXT-specific: WITH PARSER.
- Key-part: prefix length، ASC/DESC و expression key part.
- DDL execution: ALGORITHM، LOCK، WAIT/NOWAIT.
- Statement behavior: IF NOT EXISTS و OR REPLACE.
- Separate operation family: VECTOR و attributeهای ویژهٔ آن.

### MySQL and MariaDB Evidence

- MySQL 8.0 CREATE INDEX grammar گزینهٔ index_type را پس از key-part هم می‌پذیرد؛ مستندات جایگاه پیش از ON را deprecated می‌دانند. مثال رسمی برای MEMORY: CREATE INDEX id_index ON lookup (id) USING BTREE. محدودیت engineها نیز صریح است: InnoDB و MyISAM از BTREE و MEMORY از HASH/BTREE استفاده می‌کند. FULLTEXT از index_type استفاده نمی‌کند.
- مستند رسمی MySQL برای MEMORY جزییات کاربرد BTREE/HASH را توضیح می‌دهد.
- MariaDB CREATE INDEX grammar عبارت USING {BTREE | HASH | RTREE} و همچنین گزینه‌های دیگر جدول بالا را فهرست می‌کند. مستند Silent Column Changes هشدار می‌دهد engine ممکن است برای نوع غیرمجاز، نوع دیگری را به‌کار بگیرد؛ library این fallback را انجام یا پنهان نمی‌کند.
- compatibility target کلی repository در build/docs پیدا نشد. این finding ثبت می‌شود، اما چون contract محدود است و ادعای حداقل نسخهٔ جدیدی ندارد، مانع تعیین scope نیست. نسخهٔ محلی توسعه‌دهنده مبنای compatibility نیست.

### Final Contract Decision — v1.12

v1.12 فقط روش index را برای operation معمولی و تک‌ستونی v1.6 پشتیبانی می‌کند:

    createIndex {
        tableName("lookup")
        name("idx_lookup_code")
        column("code")
        using(IndexMethod.HASH) // اختیاری؛ BTREE یا HASH
    }

- API از enum تایپ‌شدهٔ IndexMethod با مقادیر BTREE و HASH استفاده می‌کند؛ رشتهٔ آزاد، Any یا SQL خام پذیرفته نیست.
- AST مربوط به CREATE INDEX یک مقدار اختیاری indexMethod نگه می‌دارد. مقدار غایب، SQL دقیق فعلی را حفظ می‌کند.
- وقتی تعیین شده باشد، renderer این شکل را می‌سازد: CREATE INDEX <name> ON <table> (<column>) USING <BTREE|HASH>.
- Builder identifierها را مطابق v1.6 trim می‌کند و spelling/casing را تغییر نمی‌دهد. Renderer AST ناقص را پیش از quote و composition رد می‌کند؛ method فقط از enum ثابت می‌آید.
- از registry و MySqlDialect موجود استفاده می‌شود. MariaDbDialect inheritance فعلی را حفظ می‌کند؛ خروجی syntax مشترک است، اما library تضمین نمی‌کند storage engine واقعاً همان پیاده‌سازی فیزیکی را به‌کار بگیرد.
- هیچ engine introspection، preflight، metadata lookup یا fallback/rewrite اضافه نمی‌شود. محدودیت engine را خود database اعمال می‌کند.
- در این contract، using فقط برای createIndex تک‌ستونی v1.6 است؛ به UNIQUE، MULTI-COLUMN، FULLTEXT یا SPATIAL تعمیم داده نمی‌شود.
- targetDatabaseVersion جایگاه SQL را تغییر نمی‌دهد؛ policy عمومی capability برای این گزینه ساخته نمی‌شود. حداقل نسخهٔ پشتیبانی‌شدهٔ کل repository اعلام نشده و از این سند هم عددی حدس زده نمی‌شود.
- executor همان مسیر MigrationExecutor → IQueryExecute.executeTable را دارد؛ executeSelect استفاده نمی‌شود.
- این Traceability هیچ source codeی را تغییر نمی‌دهد. در implementation باید regressionهای v1.6 تا v1.11 حفظ شوند و SQL بدون using(...) عیناً مانند قبل بماند.

تست‌های implementation:
1. SQL دقیق پیش‌فرض، بدون تغییر نسبت به v1.6.
2. SQL دقیق برای BTREE و HASH.
3. Builder مقدار enum را حفظ کند و ترتیب فراخوانی DSL بر SQL اثر نگذارد.
4. trim و حفظ casing/spelling identifierها.
5. Renderer AST ناقص را reject کند.
6. executor موفقیت/خطا را از executeTable عبور دهد و executeSelect را صدا نزند.
7. regression همهٔ operationهای v1.6 تا v1.11.
