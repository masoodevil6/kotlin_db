# Migration v1.22: تست یکپارچه‌سازی برای شِمای رابطه‌ای واقع‌گرایانه

## وضعیت

**آمادهٔ پیاده‌سازی**

قرارداد مخزن برای شِما و مرز تست زیر مشخص است. راستی‌آزمایی زمان اجرا به تنظیمات پایگاه دادهٔ MySQL خارجی موجود نیاز دارد؛ هنگام تهیهٔ این پلن، دسترسی به آن فرض نشده است.

## هدف

یک تست یکپارچه‌سازی دوم به `data_base:migration` اضافه شود که با Migration API موجود، شِمای رابطه‌ای کوچک و واقع‌گرایانه‌ای بسازد و سپس جدول‌ها، ستون‌ها، کلیدهای اصلی، محدودیت‌های یکتا، ایندکس‌ها و کلیدهای خارجی حاصل را از طریق JDBC metadata بررسی کند.

این تست ساخت شِما را می‌آزماید. تست موجود `MigrationSystemIntegrationTest` همچنان مسئول چرخهٔ عمر Runner، ترتیب، batchها، history، اجرای مجدد، شکست/ادامه، تعداد operationها، رفتار refresh و collision guard است. در v1.22 این تست نباید شکسته، جایگزین یا بازطراحی شود.

پس از موفقیت یا شکست، وضعیت پایگاه داده برای بررسی برنامه‌نویس باقی می‌ماند. گزینهٔ `migration.test.db.refresh=true` فقط پیش از تست آماده‌سازی می‌کند و جدول‌های صریحاً متعلق به تست جدید و `system_migration` را حذف می‌کند؛ پس از تست cleanup جدولی انجام نمی‌شود.

## شواهد مخزن

### ساختار تست و مسیر اجرا

* فایل `data_base/migration/src/test/kotlin/gog/my_project/data_base/migration/integration/MigrationSystemIntegrationTest.kt` تست یکپارچه‌سازی MySQL در ماژول والد است. این تست system propertyهای `migration.test.db.*` را می‌خواند، یک `DefaultDatabaseConfig.config` مخصوص تست نصب می‌کند، Migrationها را از طریق `MigrationMigrator` اجرا می‌کند و برای بررسی از `DriverManager` و JDBC metadata استفاده می‌کند.
* فایل `data_base/migration/build.gradle.kts` همین حالا `migration.test.db.domain`, `port`, `name`, `username`, `password` و `refresh` را به JVM تست منتقل می‌کند و از JVM toolchain 24 استفاده می‌کند. برای تست دیگری با همین propertyها نیازی به تغییر Gradle نیست.
* فایل `data_base/migration/executor/src/main/kotlin/manager/MigrationMigrator.kt` کلاس‌های Migration ثبت‌شده را نمونه‌سازی می‌کند، تعریف `up()` هرکدام را اجرا می‌کند، برای هر Migration دقیقاً یک operation لازم می‌داند، operation را به `MigrationExecutor` می‌فرستد و شناسه‌های موفق را در `system_migration` ثبت می‌کند.
* `MigrationMigrator` batch بعدی را با `Math.addExact(state.currentBatch ?: 0, 1)` محاسبه می‌کند و همان batch را به Migrationهای pending همان invocation می‌دهد. `SystemMigrationReader` در history خالی `currentBatch = null` برمی‌گرداند و `SystemMigrationRecorder` شناسه و batch دقیق هر Migration موفق را ثبت می‌کند.
* تست موجود در `data_base/migration/src/test/.../MigrationSystemIntegrationTest.kt` وضعیت پایگاه داده را حفظ می‌کند؛ `finally` آن تنظیم قبلی `DefaultDatabaseConfig.config` را برمی‌گرداند و connection بازرسی را می‌بندد. جدول‌های fixture یا `system_migration` را حذف نمی‌کند.

### پشتیبانی فعلی operationها و شِما

* `data_base/migration/api/src/main/kotlin/interfaces/create_table/definition/IMigrationCreateTablePrimaryKeyApi.kt` متد `columns(vararg ...)` را عرضه می‌کند و `.../IMigrationCreateTableUniqueApi.kt` امکان تعریف unique چندستونی با نام مشخص را دارد.
* `data_base/migration/api/src/main/kotlin/interfaces/create_table/definition/IMigrationCreateTableIndexApi.kt` و `.../IMigrationCreateTableForeignKeyApi.kt` تعریف چندستونی را پشتیبانی می‌کنند. Builder کلید خارجی ستون‌های محلی و مرجع را به‌صورت positional جفت می‌کند، برابر بودن طول فهرست‌ها را اعتبارسنجی می‌کند و actionهای حذف/به‌روزرسانی را می‌پذیرد.
* فایل `data_base/migration/ast/src/main/kotlin/interfaces/create_table/definition/MigrationCreateTableDefinitions.kt` شامل `PrimaryKeyDefinitionAst`, `UniqueDefinitionAst`, `IndexDefinitionAst`, `FullTextIndexDefinitionAst` و `ForeignKeyDefinitionAst` است؛ ASTها ترتیب فهرست ستون‌ها را حفظ می‌کنند.
* `data_base/migration/builder/src/main/kotlin/ast/create_table/definition/MigrationCreateTableDefinitionBuilders.kt` این definitionها را می‌سازد. بنابراین `createTable` می‌تواند ستون‌ها، محدودیت‌ها و ایندکس‌های یک جدول را داخل یک operation معنایی `CreateTable` نگه دارد.
* در همین Builder، `onDelete` و `onUpdate` برای FK به‌طور پیش‌فرض `null` هستند و فقط فراخوانی setter مقدارشان را تعیین می‌کند؛ `MySqlMigrationCreateTableDefinitionCapability.renderForeignKey` نیز clauseهای `ON DELETE` و `ON UPDATE` را فقط برای مقدار non-null تولید می‌کند. بنابراین اگر setter فراخوانی نشود، SQL هر دو clause را ندارد.
* برای معنای پایگاه‌داده‌ای حذف این clauseها، مستند رسمی MySQL، بخش `FOREIGN KEY Constraints` از Reference Manual، نبود `ON DELETE`/`ON UPDATE` را معادل action پیش‌فرض `NO ACTION` می‌داند و تصریح می‌کند که در InnoDB این رفتار معادل `RESTRICT` است. این شاهد فقط معنای default را مستند می‌کند؛ نسخهٔ سازگار یا storage engine پروژه را تعیین نمی‌کند.
* `data_base/migration/renderer/src/main/kotlin/nodes/create_table/definition/MySqlMigrationCreateTableDefinitionCapability.kt` این definitionها را render می‌کند؛ از جمله کلید اصلی ترکیبی مرتب، unique، ایندکس عادی، fulltext و کلید خارجی ترکیبی.
* تست `data_base/migration/executor/src/test/kotlin/manager/MigrationExecutorCreateTableDefinitionsTest.kt` SQL مربوط به کلید اصلی ترکیبی، ایندکس BTREE و FK ترکیبی را داخل یک operation ساخت جدول بررسی می‌کند و یک unique definition را نیز پوشش می‌دهد.
* قراردادها، builderها، rendererها و overloadهای executor برای operationهای مستقل `CREATE INDEX`, `DROP INDEX`, `CREATE UNIQUE INDEX`, `CREATE MULTI-COLUMN INDEX`, `CREATE FULLTEXT INDEX`, `CREATE SPATIAL INDEX`, `CREATE FOREIGN KEY` و `DROP FOREIGN KEY` نیز موجودند. v1.22 از definitionهای درون `CREATE TABLE` برای شِمای رابطه‌ای استفاده می‌کند و نیازی نیست قراردادهای مستقل DROP/index را دوباره بیازماید.
* مسیر `data_base/migration/params/src/main/kotlin/data_types/` شامل `IntType`, `VarcharType`, `TextType`, `DecimalType`, `DateTimeType` و typeهای معمولی/زمانی دیگر است. در این مدل type هندسی/spatial وجود ندارد.
* `data_base/migration/example/src/test/kotlin/v1/migrations/foreign_key/ForeignKeyV1Test.kt` render کردن FK ترکیبی و ترتیب جفت‌های ستون‌های محلی/مرجع را بررسی می‌کند. `.../temporal_data_types/TemporalDataTypesV1Test.kt` نیز render کردن typeهای زمانی را پوشش می‌دهد.
* نمونهٔ `data_base/migration/example/src/main/kotlin/v1/migrations/composite/CreateCustomersMigrationV1.kt` نشان می‌دهد تعریف Migration می‌تواند بیش از یک operation داشته باشد؛ اما قرارداد Runner در v1.20 برای هر Migration اجرایی دقیقاً یک operation در `up()` می‌خواهد. fixtureهای v1.22 برای هر Migration فقط یک operation `createTable` خواهند داشت.

### مالکیت نام جدول‌های موجود

fixture فعلی v1.21 نام‌هایی مانند `migration_test_users`, `migration_test_posts`, `migration_test_failure_users` و `migration_test_existing_table` و نیز `system_migration` را مالک است. استفادهٔ دوباره از این نام‌ها محدودهٔ collision/refresh دو تست را هم‌پوشان می‌کند. بنابراین v1.22 از پیشوند مجزای مبتنی بر نقش `migration_schema_*` استفاده می‌کند؛ شمارهٔ پلن یا نسخه بخشی از هویت شیء پایگاه داده نیست.

### Dialect و سازگاری

تنظیم تست یکپارچه‌سازی، JDBC URL مربوط به MySQL را بررسی و `DialectQuery.MY_SQL` را انتخاب می‌کند. مخزن حداقل نسخهٔ رسمی MySQL را مشخص نکرده است. بنابراین قرارداد زمان اجرای v1.22 همان «سرور MySQL خارجی تنظیم‌شده برای این تست» است؛ این پلن version floor تعیین نمی‌کند و ادعای راستی‌آزمایی زمان اجرا روی MariaDB ندارد.

## مرز تست یکپارچه‌سازی موجود

`MigrationSystemIntegrationTest` در v1.22 بدون تغییر می‌ماند. تست جدید یک کلاس جداگانه در همان package تست یکپارچه‌سازی ماژول والد خواهد بود و fixture Migrationها، ثابت‌های tag هویت، فهرست objectهای تحت مالکیت، collision guard، assertionهای metadata و helperهای کوچک محلی خودش را دارد.

از propertyهای موجود تست و مسیر اجرای production استفاده شود:

```text
system propertyهای migration.test.db.*
        ↓
DatabaseConfig / DefaultDatabaseConfig.config
        ↓
MigrationConfiguration
        ↓
MigrationMigrator
        ↓
MigrationExecutor
        ↓
IQueryExecute / DatabaseConnection
        ↓
پایگاه دادهٔ MySQL پیکربندی‌شده
```

استفاده از `DriverManager` فقط برای connection و بازرسی تست و ایجاد sentinel نامرتبط مجاز است. خود Migrationهای شِما باید از طریق `MigrationMigrator` و pipeline اجرای موجود اجرا شوند.

## شِمای دامنهٔ پیشنهادی

از شِمای فروشگاهی چندمستاجری کوچک استفاده شود. ارجاع ترکیبی tenant/user برای FK ترکیبی کاربرد واقعی دارد و رابطه‌ای صرفاً آزمایشی برای تمرین syntax اضافه نمی‌کند.

```text
categories
tenants
users
products
addresses
orders
order_items
```

تمام نام جدول‌ها از namespace ثابت تست استفاده می‌کنند:

```text
migration_schema_categories
migration_schema_tenants
migration_schema_users
migration_schema_products
migration_schema_addresses
migration_schema_orders
migration_schema_order_items
migration_schema_unrelated   # sentinel؛ خارج از مالکیت refresh
```

نام‌ها نقش object را بیان می‌کنند و به کلاس JUnit یا نسخهٔ Migration وابسته نیستند. پیشوند `migration_schema_*` عمداً از fixtureهای `migration_test_*` در v1.21 جداست.

## ترتیب Migrationها

هفت کلاس عمومی Migration بدون آرگومان، به ترتیب وابستگی صریح ثبت شوند. هر کلاس از یک شیء `migrationTags` محلی در تست استفاده می‌کند که شامل `const val String`ها است و در `@MigrationId(...)` به کار می‌رود؛ این کار با قواعد هویت v1.19 هماهنگ است. شناسه به‌صورت literal مستقیم در annotation نوشته نشود. پیکربندی تا زمانی که `MigrationMigrator` موجود اجرا نشود، فقط metadata است.

ترتیب پیشنهادی:

1. `CreateSchemaCategories`
2. `CreateSchemaTenants`
3. `CreateSchemaUsers` (ارجاع به tenants)
4. `CreateSchemaProducts` (ارجاع به categories)
5. `CreateSchemaAddresses` (ارجاع به users)
6. `CreateSchemaOrders` (ارجاع ترکیبی به users)
7. `CreateSchemaOrderItems` (ارجاع به orders و products)

`up()` هر کلاس دقیقاً یک entry در `MigrationDefinition` برمی‌گرداند که یک API از نوع `createTable { ... }` دارد. محدودیت‌ها و ایندکس‌ها داخل همان تعریف `createTable` قرار می‌گیرند. چند ساخت جدول را در یک Migration definition ترکیب نکنید و قاعدهٔ دقیقاً یک operation در v1.20 را تغییر ندهید.

برای این تست، registration تخت و مرتب استفاده شود. هیچ معنای تراکنش یا اجرای جدیدی به Group اضافه نمی‌شود؛ تست v1.21 پوشش متمرکز ترتیب Group را حفظ می‌کند.

## قرارداد شِما

موارد زیر قرارداد هدف شِما هستند. نام دقیق ستون‌ها و typeها باید از typeها و builder callهای موجود در مخزن استفاده کند؛ برای انطباق با این پلن، data type یا قابلیت production جدیدی اضافه نکنید.

* `migration_schema_categories`: ستون `id` از نوع integer و auto-increment با کلید اصلی؛ ستون `name` غیرخالی و یکتا.
* `migration_schema_tenants`: ستون `id` از نوع integer و auto-increment با کلید اصلی؛ ستون `name` غیرخالی و یکتا.
* `migration_schema_users`: ستون `id` از نوع integer و auto-increment با کلید اصلی؛ ستون‌های `tenant_id`, `email`, `name`؛ کلید خارجی `tenant_id → tenants.id`؛ unique ترکیبی `(tenant_id, email)`؛ unique نام‌دار `(tenant_id, id)` برای فراهم کردن کلید مرجع معتبر جهت ارجاع tenant-scoped به کاربر.
* `migration_schema_products`: ستون `id` از نوع integer و auto-increment با کلید اصلی؛ ستون‌های `category_id`, `sku`, `description`, `price`؛ FK از `category_id` به `categories.id`؛ `sku` یکتا؛ ایندکس عادی روی `category_id`؛ fulltext روی `description`.
* `migration_schema_addresses`: ستون `id` از نوع integer و auto-increment با کلید اصلی؛ ستون‌های `user_id`, `address_type`, `address_line`؛ FK از `user_id` به `users.id`؛ unique ترکیبی `(user_id, address_type)`.
* `migration_schema_orders`: ستون `id` از نوع integer و auto-increment با کلید اصلی؛ ستون‌های `tenant_id`, `user_id`, `order_number`, `created_at`, `total`؛ FK ترکیبی `(tenant_id, user_id) → users(tenant_id, id)`؛ unique ترکیبی `(tenant_id, order_number)`؛ ایندکس BTREE ترکیبی مرتب `(tenant_id, created_at)`.
* `migration_schema_order_items`: ستون‌های `order_id`, `product_id`, `quantity`, `unit_price`؛ کلید اصلی ترکیبی مرتب `(order_id, product_id)`؛ FK تک‌ستونی از `order_id` به `orders.id` و از `product_id` به `products.id`.

این شِما صرفاً ساختاری است. دادهٔ نمونهٔ کسب‌وکار، رفتار ORM، trigger، timestamp خودکار یا queryهای برنامه‌ای در scope نیست.

## قرارداد محدودیت‌ها

* کلیدهای اصلی تک‌ستونی جدول‌های categories، tenants، users، products، addresses و orders را assert کنید.
* کلید اصلی ترکیبی `order_items` را دقیقاً با ترتیب `KEY_SEQ` بررسی کنید: ابتدا `order_id` و سپس `product_id`.
* وجود هر unique key نام‌دار، یکتا بودن آن و ترتیب دقیق ستون‌هایش را بررسی کنید. نمونهٔ تک‌ستونی و ترکیبی هر دو پوشش داده شوند.
* FK ترکیبی orders به users را در `getImportedKeys` با دو ردیف جفت‌شدهٔ درست و مرتب‌شده بر اساس `KEY_SEQ` بررسی کنید.
* FKهای users به tenants، products به categories، addresses به users و order_items به orders/products را با جفت ستون و جدول مورد انتظار assert کنید.
* برای هر شش FK، در DSL هیچ `onDelete(...)` یا `onUpdate(...)` فراخوانی نشود؛ این دقیقاً رفتار فعلی Builder است و SQL هر FK باید هر دو clause را حذف کند. مستندات MySQL مقدار پیش‌فرض هنگام نبود clause را `NO ACTION` تعریف می‌کند؛ در InnoDB این رفتار معادل `RESTRICT` است. تست action دیگری مانند `CASCADE`، `SET NULL` یا `SET DEFAULT` اضافه نکند. در metadata، `DELETE_RULE` و `UPDATE_RULE` باید نمایش JDBC متناظر با همین default را داشته باشند؛ اگر Connector/J مقدار `NO_ACTION` یا `RESTRICT` گزارش کند، فقط این دو نمایش معادل پذیرفته شوند و مقدار واقعی ثبت شود. نوع storage engine از روی repository فرض نشود.
* صحت constraint را فقط از موفقیت `CREATE TABLE` نتیجه‌گیری نکنید؛ metadata را بررسی کنید.

جدول تصمیم FKهای این شِما:

| FK | ON DELETE در DSL/SQL | ON UPDATE در DSL/SQL | معنای پیش‌فرض MySQL |
|---|---|---|---|
| `users.tenant_id → tenants.id` | تعریف‌نشده؛ clause تولید نمی‌شود | تعریف‌نشده؛ clause تولید نمی‌شود | `NO ACTION` |
| `products.category_id → categories.id` | تعریف‌نشده؛ clause تولید نمی‌شود | تعریف‌نشده؛ clause تولید نمی‌شود | `NO ACTION` |
| `addresses.user_id → users.id` | تعریف‌نشده؛ clause تولید نمی‌شود | تعریف‌نشده؛ clause تولید نمی‌شود | `NO ACTION` |
| `orders(tenant_id, user_id) → users(tenant_id, id)` | تعریف‌نشده؛ clause تولید نمی‌شود | تعریف‌نشده؛ clause تولید نمی‌شود | `NO ACTION` |
| `order_items.order_id → orders.id` | تعریف‌نشده؛ clause تولید نمی‌شود | تعریف‌نشده؛ clause تولید نمی‌شود | `NO ACTION` |
| `order_items.product_id → products.id` | تعریف‌نشده؛ clause تولید نمی‌شود | تعریف‌نشده؛ clause تولید نمی‌شود | `NO ACTION` |

## قرارداد ایندکس‌ها

* وجود ایندکس عادی دسته‌بندی روی products را assert کنید.
* ایندکس BTREE ترکیبی orders را با ترتیب `(tenant_id, created_at)` بررسی کنید.
* نام fulltext و ستون `description` ایندکس‌شده را از JDBC metadata بررسی کنید. اگر metadata مربوط به Connector/J پیکربندی‌شده تمایز قابل اتکایی بین نوع fulltext و ایندکس عادی نشان نمی‌دهد، این محدودیت را ثبت کنید و فقط وجود نام و ستون ایندکس را assert کنید؛ SQL خام یا تغییر production اضافه نکنید.
* ایندکس‌های unique را با فیلد `NON_UNIQUE` در JDBC metadata جدا از ایندکس‌های غیر یکتا بررسی کنید.
* کلید نزولی، prefix length، ایندکس spatial، engine option یا توسعهٔ مختص dialect اضافه نشود.

## قرارداد کلید خارجی

FKها فقط به‌صورت inline در `createTable` تعریف می‌شوند و جدول مرجع باید در Migration ثبت‌شدهٔ قبلی ساخته شده باشد. ترتیب انتخاب‌شده این وابستگی را رعایت می‌کند. ترتیب ستون‌های محلی و مرجع FK ترکیبی باید positional و یکسان باشد.

schema qualification، تغییر constraint پس از ساخت جدول، مدیریت خودکار supporting index یا introspection پایگاه داده در Builder/Renderer اضافه نمی‌شود. سازگاری واقعی engine/schema را MySQL اعمال می‌کند و تست metadata حاصل را بررسی می‌کند.

## محدودهٔ Spatial و FullText

* FULLTEXT در این پلن گنجانده شده، چون تعریف fulltext داخل create-table و MySQL renderer وجود دارد و `products.description` از `TextType` پشتیبانی‌شده استفاده می‌کند.
* SPATIAL به مرحلهٔ بعد موکول می‌شود. با اینکه `CREATE SPATIAL INDEX` پیاده‌سازی شده، مدل نوع ستون Migration فاقد type هندسی/spatial است؛ بنابراین این پلن بدون افزودن type خارج از scope یا استفاده از SQL خام نمی‌تواند ستون spatial معتبر بسازد.
* در v1.22 parser مربوط به FULLTEXT، type spatial یا operation جدید پیاده‌سازی نمی‌شود.

## قرارداد Refresh پایگاه داده

از گزینهٔ موجود `migration.test.db.refresh` و `DatabaseConfig.dbName` استفاده کنید؛ test property جدید یا تغییری در `DatabaseConfig` اضافه نکنید.

```text
نصب DefaultDatabaseConfig.config مخصوص تست
        ↓
اگر sentinel وجود ندارد: ایجاد آن با JDBC/DriverManager
اگر sentinel موجود است: حفظ آن بدون ادعای مالکیت
        ↓
اگر refresh=true:
    DropTable برای ownedSchemaTables
    DropTable جداگانه برای sharedMigrationState.system_migration
        ↓
collision guard:
    ownedSchemaTables
    sharedMigrationState.system_migration
        ↓
اجرای MigrationConfiguration شِما
```

مدل مالکیت:

```text
ownedSchemaTables
├── migration_schema_categories
├── migration_schema_tenants
├── migration_schema_users
├── migration_schema_products
├── migration_schema_addresses
├── migration_schema_orders
└── migration_schema_order_items

sharedMigrationState
└── system_migration
```

* `system_migration` جدول مشترک زیرساختی است و عضو `ownedSchemaTables` نیست؛ با این حال در refresh و collision guard به‌صورت مستقل و صریح بررسی می‌شود.
* Refresh یک بار در شروع تست، پیش از collision check و Migrator انجام می‌شود.
* محدودهٔ refresh دقیقاً `ownedSchemaTables` به‌علاوهٔ `sharedMigrationState.system_migration` است.
* sentinel با نام `migration_schema_unrelated` در صورت نبودن با JDBC/DriverManager ایجاد می‌شود. اگر از قبل موجود باشد، تست مالکیت آن را ادعا نمی‌کند؛ در هر دو حالت sentinel خارج از محدودهٔ refresh و collision guard است، پس از refresh و در پایان تست باید باقی بماند و در `finally` حذف نمی‌شود.
* برای refresh از `DropTable` موجود با `ifExists()` و مسیر `MigrationExecutor` استفاده کنید؛ SQL خام، `TRUNCATE`، حذف/ساخت database یا `MigrationMigrator` برای refresh مجاز نیست.
* در حالت `refresh=false`، وجود هر جدول از `ownedSchemaTables` یا وجود مستقل `system_migration` باید پیش از حذف هر object یا شروع Migration باعث شکست collision شود. هیچ‌کدام نباید در اثر collision حذف یا تغییر کنند.
* شکست refresh یعنی شکست setup تست؛ Migrator نباید اجرا شود و fallback به database دیگر وجود ندارد.
* چون جدول history یعنی `system_migration` مشترک است، از قرارداد فعلی database اختصاصی/قابل‌دورریختن تست استفاده شود. تست‌های یکپارچه‌سازی v1.21 و v1.22 نباید همزمان روی یک database اجرا شوند. معماری اجرای موازی جدیدی اضافه نمی‌شود.
* پس از تست هیچ cleanup پایگاه داده‌ای انجام نمی‌شود؛ چه تست موفق شود چه شکست بخورد. `finally` فقط مجاز است `DefaultDatabaseConfig.config` قبلی را restore کند و connection/resourceهای JDBC تست را ببندد.

## مالکیت پایگاه دادهٔ تست

`ownedSchemaTables` یک فهرست صریح و محلی تست است که فقط هفت جدول `migration_schema_*` را شامل می‌شود. `system_migration` در فهرست جداگانهٔ `sharedMigrationState` قرار دارد و برای refresh و collision guard صریحاً لحاظ می‌شود. این دو فهرست برای موارد زیر استفاده می‌شوند:

* محدودهٔ refresh هنگام شروع؛
* تشخیص collision پیش از اجرای Migration.

هیچ‌یک برای cleanup هنگام teardown استفاده نمی‌شوند. sentinel عمداً بیرون از هر دو فهرست است و باید باقی بماند. جدول‌های namespace مربوط به v1.21 یعنی `migration_test_*` را به هیچ‌یک از این فهرست‌ها اضافه نکنید.

## قرارداد بررسی شِما

از `DatabaseMetaData` مربوط به JDBC connection تست استفاده کنید. هر `ResultSet` مربوط به metadata را در همان محدودهٔ محلی `use` ببندید و پیش از بازگشت helper، داده‌ها را به مقادیر عادی Kotlin تبدیل کنید.

موارد زیر بررسی شوند:

1. وجود هر هفت جدول مورد انتظار در catalog انتخاب‌شده.
2. وجود ستون‌های مهم با JDBC data type، nullability و metadata مربوط به auto-increment مورد انتظار.
3. تطبیق نام/ستون کلید اصلی و ترتیب `KEY_SEQ`.
4. وجود unique keyها و ایندکس‌های عادی/fulltext نام‌دار با ترتیب ستون و metadata یکتایی مورد انتظار.
5. تطبیق metadata کلیدهای خارجی واردشده با جدول مبدأ، ستون‌های مبدأ، جدول مرجع، ستون‌های مرجع، `KEY_SEQ` و ruleهای تعریف‌شده.
6. وجود sentinel نامرتبط قبل و بعد از refresh آغاز تست.
7. خواندن `system_migration` پس از اجرای موفق و تطبیق دقیق هر هفت ID، ترتیب ثبت‌شده و batch مورد انتظار.
8. باقی ماندن schema و history مربوط به Migrationهای ثبت‌شده پس از اتمام تست برای بررسی برنامه‌نویس.

برای این assertionها، tagهای test-local دقیقاً این مقادیر را دارند و در annotation از طریق `migrationTags` استفاده می‌شوند: `schema_create_categories`, `schema_create_tenants`, `schema_create_users`, `schema_create_products`, `schema_create_addresses`, `schema_create_orders`, `schema_create_order_items`. history موفق باید همین هفت ID را با همین ترتیب داشته باشد. در مسیر موفق `refresh=true`, baseline تست شامل نبودن `system_migration` است؛ Reader در نتیجه history خالی و `currentBatch = null` می‌بیند، پس طبق محاسبهٔ فعلی Migrator هر هفت Migration این invocation باید در batch `1` ثبت شوند. این انتظار از semantics فعلی Migrator/State Store می‌آید و قاعدهٔ عمومی تازه‌ای برای شماره‌گذاری batch تعریف نمی‌کند. در مسیر `refresh=false`، collision guard با object یا history از قبل موجود باید تست را متوقف کند و انتظار ثبت history جدید ندارد.

مقادیر JDBC metadata ممکن است در شکل نمایش (برای نمونه املای type name) متفاوت باشند. assertionها باید از JDBC type constantها و فقط metadata پایداری استفاده کنند که driver MySQL انتخاب‌شده مستند کرده است. اگر فیلدی قابل اتکا نیست، همان محدودیت را دقیق ثبت کنید؛ از جایگزین کردن metadata با قابلیت production یا تضعیف پنهانی assertionهای نامرتبط خودداری کنید.

## شواهد و گزارش تست

JUnit assertionها و Gradle test report موجود کافی هستند. چارچوب عمومی گزارش شِما نسازید و Help را از domain tableها آگاه نکنید.

اگر لازم است تست جدید مستقیماً از Help قابل انتخاب باشد، فقط metadata اعلانی تست را در `help.json` موجود ماژول اضافه کنید؛ از Gradle test filter و همان bindingهای `migration.test.db.*` استفاده شود. منطق مختص شِما به Help server، runner یا UI اضافه نکنید. اینکه Help تست یکپارچه‌سازی دوم را نمایش دهد، انتخابی وابسته به گردش‌کار برنامه‌نویس است و برای اجرای مستقیم Gradle مانع محسوب نمی‌شود.

## سناریوهای شکست

گزارش شکست اصلی تست باید assertion ناموفق شِما را مشخص کند و جدول‌ها/history ساخته‌شده تا آن نقطه را حفظ کند. فقط برای تکرار پوشش failure/resume در v1.21 یک Migration عمداً ناموفق اضافه نکنید.

رد constraint به‌دلیل تنظیمات محلی ناسازگار MySQL، شکست integration محسوب می‌شود و باید خطای MySQL حفظ شود. preflight شِما، retry، skip بی‌صدا یا ادامهٔ اجرای sequence ناقص ممنوع است.

## برنامهٔ تست

### بررسی build و compile

* source تست ماژول والد `data_base:migration` را با JDK/toolchain مخزن compile کنید.
* اگر تغییر implementation به declarationهای fixture یا helperها مربوط شد، تست‌های focused موجود برای create-table definition، composite FK و typeهای زمانی را اجرا کنید. تست‌های نامرتبط را تغییر ندهید.

### تست یکپارچه‌سازی واقعی MySQL

تست جدید را با propertyهای Gradle موجود و database اختصاصیِ صریحاً پیکربندی‌شده اجرا کنید. سناریوهای لازم:

* `refresh=true`: فقط هفت جدول تحت مالکیت و `system_migration` پیش از Migration حذف شوند؛ sentinel نامرتبط باقی بماند.
* `refresh=false`: جدول تحت مالکیت یا `system_migration` از قبل موجود باشد، collision failure طبق الگوی فعلی رخ دهد؛ Migration شروع نشود و object قبلی دست‌نخورده بماند.
* در اجرای موفق از baseline تمیز، هر هفت Migration تک‌operation از مسیر Definition → Registration → `MigrationMigrator` → `MigrationExecutor` → `CREATE TABLE` به MySQL برسند؛ metadata شِما با قرارداد تطبیق داشته باشد و history شامل هفت ID دقیق و مرتب، همگی با batch `1` باشد.
* ترتیب ستون‌های composite PK، composite unique، composite index و FKهای تک/ترکیبی در metadata حفظ و بررسی شود.
* action هر شش FK همان default فعلی باشد: هیچ clause `ON DELETE` یا `ON UPDATE` در SQL تولید نشود و metadata JDBC مقدار متناظر با default MySQL (`NO ACTION`، با نمایش معادل `RESTRICT` در صورت گزارش driver) را نشان دهد.
* شِمای نهایی موفق، sentinel و history هفت‌ردیفی Migration پس از بازگشت تست باقی بمانند؛ هر هفت ردیف همان batch `1` را داشته باشند.
* اگر Migration در میانه شکست خورد، جدول‌ها/history ایجادشده تا همان نقطه باقی بمانند؛ `finally` همچنان config را restore و connectionها را ببندد.
* اجرای بعدی با `refresh=true` فقط objectهای تحت مالکیت این تست و `system_migration` را به baseline تمیز برگرداند و sentinel نامرتبط را حفظ کند.

اگر propertyهای معتبر DB یا MySQL در دسترس نیستند، وضعیت اجرای runtime را `Blocked/Unverified` گزارش کنید؛ موفقیت compile را به‌جای اجرای واقعی تست جا نزنید.
