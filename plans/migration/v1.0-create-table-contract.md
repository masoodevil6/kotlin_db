# Migration v1.0: CREATE TABLE Contract

وضعیت: `planned`

## Scope اجرایی

این plan baseline عملیات موجود `CREATE TABLE` را تثبیت می‌کند؛ هدف آن افزودن operation جدید نیست. هر موردی که در این سند به‌عنوان Contract تعریف شده، باید یا در کد موجود قابل ردیابی باشد یا به‌عنوان gap صریح در implementation ثبت شود.

## Dependencies

- `data_base:core` برای مدل‌های پایه و `BuiltQuery`.
- `data_base:migration:params` برای data typeهای column.
- `data_base:migration:api` برای قراردادهای عمومی.
- `data_base:migration:ast` برای AST.
- `data_base:migration:builder` برای DSL.
- `data_base:migration:dialect` برای contractهای renderer.
- `data_base:migration:renderer` برای MySQL.
- `data_base:migration:executor` و `data_base:manager:execute` برای اجرای DDL.

## فازهای implementation

### فاز 1: ممیزی Contract و AST

- هر field ورودی و constraint به node متناظر AST map شود.
- invariantهای جدول و column مشخص شوند.
- مشخص شود validation در builder انجام می‌شود یا renderer؛ validation باید پیش از تولید SQL قطعی باشد.

خروجی: جدول traceability بین Contract، AST و کد واقعی.

### فاز 2: validation مستقل

- validation جدول، column، type و constraintها استخراج یا تکمیل شود.
- خطاها مسیر node و علت را نگه دارند.
- validation بدون JDBC قابل اجرا باشد.

خروجی: تست‌های منفی برای هر invariant.

### فاز 3: تثبیت renderer MySQL

- SQL مرجع برای typeها و constraintها تثبیت شود.
- quoting identifier و literalهای پیش‌فرض تست شوند.
- ترتیب deterministic ستون‌ها و constraintها حفظ شود.

خروجی: golden/expected SQL test برای مثال مرجع و edge caseها.

### فاز 4: تثبیت executor

- `CREATE TABLE` از مسیر executor به `IQueryExecute.executeTable` برسد.
- success و failure callback هر دو تست شوند.
- exception اصلی JDBC حفظ شود.

خروجی: unit test با fake executor و integration test اختیاری.

| لایه | module | ناحیه‌ی تغییر |
|---|---|---|
| API | `data_base:migration:api` | `interfaces/create_table` |
| AST | `data_base:migration:ast` | `interfaces` و `schema/create_table` |
| Builder | `data_base:migration:builder` | `ast/create_table` و entry point DSL |
| Dialect | `data_base:migration:dialect` | context، registry و capability contract |

نام دقیق interfaceها بعد از traceability تعیین می‌شود و از این سند به‌تنهایی الزام نمی‌گیرد.

## Contract

```text
CreateTable
├── Input
│   ├── table
│   └── columns
├── Options
│   └── column constraints
├── AST
│   ├── table
│   └── columns
├── Validation
│   ├── table name is not blank
│   ├── at least one column
│   ├── unique column names
│   ├── every column has a name and type
│   └── constraints are compatible
├── Rendering
│   └── CREATE TABLE ...
└── Execution
    └── execute generated SQL
```

## Input

نسخه‌ی فعلی باید حداقل ساخت یک جدول با یک یا چند column را پشتیبانی کند. typeهای پایه عبارت‌اند از:

- `Int`
- `Boolean`
- `Decimal`
- `Text`
- `Varchar`
- `Json`

constraintهای فعلی:

- `NULL` / `NOT NULL`
- `DEFAULT`
- `AUTO_INCREMENT`
- `PRIMARY KEY`

## Validation

پیش از render باید موارد زیر بررسی شوند:

- نام جدول non-blank باشد.
- جدول حداقل یک column داشته باشد.
- نام هر column non-blank باشد.
- نام columnها تکراری نباشد.
- type هر column معتبر باشد.
- `AUTO_INCREMENT` فقط روی type عددی مجاز باشد.
- ترکیب constraintهای column معتبر باشد.

خطا باید مسیر node و علت را مشخص کند؛ برای مثال:

```text
CreateTable validation failed: table.users.columns[1].name must not be blank
```

## Rendering

renderer مستقل از اتصال دیتابیس است و برای MySQL باید SQL معتبر با quoting identifier تولید کند.

نمونه‌ی مرجع:

```sql
CREATE TABLE `users` (
  `id` INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `name` VARCHAR(120) NOT NULL
)
```

## Execution

executor SQL تولیدشده را اجرا می‌کند و نتیجه یا خطای واقعی دیتابیس را گزارش می‌دهد. renderer و تست‌های AST/validation نباید به اتصال دیتابیس وابسته باشند.

## معیار پذیرش

1. DSL معتبر AST کامل بسازد.
2. ورودی نامعتبر پیش از اجرا رد شود.
3. SQL مرجع MySQL با تست تثبیت شود.
4. نتیجه‌ی موفق و exception اصلی در execution قابل مشاهده باشد.
5. تست‌های unit مستقل از دیتابیس اجرا شوند.

## ریسک‌ها و تصمیم‌ها

- پشتیبانی فعلی فقط MySQL است؛ dialect جدید در این plan ساخته نمی‌شود.
- transaction و rollback عمومی خارج از scope است، چون رفتار DDL بین موتورهای مختلف یکسان نیست.
- integration test نباید به credential محلی hard-code وابسته باشد.
- اگر validation فعلی ناقص باشد، قبل از شروع `DROP TABLE` باید gapهای blocker رفع شوند.
