## 6. Refresh Semantics

با repository evidence تأیید شود refresh فقط این موارد را پاک می‌کند:

```text
ownedFixtureTables
system_migration
```

و مسیر آن همان API موجود باشد:

```kotlin
dropTable {
    tableName(...)
    ifExists()
}
```

از `MigrationExecutor` موجود استفاده شود؛ refresh نباید به `DROP DATABASE`, `CREATE DATABASE`, `TRUNCATE`, raw SQL، `MigrationMigrator` یا Migration operation جدید متکی باشد.

اگر DropTable یا executor موجود نتواند دقیقاً همین scope را پوشش دهد، implementation متوقف شود و capability gap با evidence مشخص گزارش شود.

### Semantics نتیجهٔ `DropTable`

Evidence source:

* `data_base/migration/builder/src/main/kotlin/ast/drop_table/MigrationDropTableBuilder.kt`: `ifExists()` فقط `ast.ifExists = true` می‌کند.
* `data_base/migration/renderer/src/main/kotlin/nodes/drop_table/MySqlMigrationDropTableCapability.kt`: با flag، SQL به‌شکل `DROP TABLE IF EXISTS <quoted-name>` ساخته می‌شود.
* `data_base/migration/executor/src/main/kotlin/manager/MigrationExecutor.kt`: overload مربوط به `IMigrationDropTableApi`، `executeTable` را صدا می‌زند و نتیجه را مستقیم forward می‌کند.
* `data_base/manager/execute/src/main/kotlin/manager/QueryExecute.kt`: در نبود خطا، `Statement.execute()` را اجرا می‌کند و `ExecuteResult.Success(true)` می‌دهد. مقدار Boolean بازگشتی `Statement.execute()` عمداً برای DDL نادیده گرفته می‌شود؛ source comment می‌گوید `false` برای DDL طبیعی است چون ResultSet تولید نمی‌شود.
* `data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt`: `executeTable` نتیجهٔ `ExecuteResult<Boolean>` دارد؛ callback عمومی خودش برای DropTable existence را تفکیک نمی‌کند.
* مستندات رسمی `MySQL Reference Manual — DROP TABLE Statement` و `MariaDB Server Documentation — DROP TABLE` می‌گویند `IF EXISTS` برای table ناموجود SQL error نمی‌دهد؛ این فقط grammar behavior را توضیح می‌دهد و compatibility floor جدیدی تعیین نمی‌کند.

**Interpretation:** در مسیر concrete فعلی، `Success(true)` یعنی اجرای DDL بدون خطای SQL؛ به‌تنهایی ثابت نمی‌کند object قبلاً وجود داشته است. اگر object ناموجود باشد، `IF EXISTS` اجازهٔ اجرای بدون SQL error را می‌دهد و `QueryExecute` باز هم `Success(true)` تولید می‌کند. مسیر concrete فعلی `Success(false)` تولید نمی‌کند و source معنایی مانند «object وجود نداشت» برای آن تعریف نکرده است.

**Decision:** شرط `Success(true)` برای `MigrationExecutor()` پیش‌فرض حفظ می‌شود، اما در Contract به‌صراحت بیان می‌شود که این مقدار existence را گزارش نمی‌کند. `Success(false)` در مسیر concrete فعلی قابل انتظار نیست و نباید بدون evidence به «object نبود ولی موفق بود» تعبیر شود. اگر implementation result دیگری دریافت کرد، آن را نتیجهٔ تعریف‌نشده/غیرمنتظره ثبت کند؛ `ExecuteResult.Failure` خطای واقعی execution است. `ifExists()` همچنان missing table را در SQL مجاز می‌کند.

## 8. Collision Guard

دو حالت مستقل بررسی شوند:

### `refreshDatabase=false`

* database باید clean باشد.
* اگر owned object موجود باشد، collision guard failure می‌دهد.
* guard پیش از تغییر مالکیت یا هر DropTable اجرا می‌شود؛ object باید باقی بماند.

### `refreshDatabase=true`

* ابتدا فقط owned fixtureها و `system_migration` حذف می‌شوند.
* بعد collision guard اجرا می‌شود.
* collision باقی‌مانده پس از refresh باعث failure می‌شود.
* object نامرتبط خارج از `ownedFixtureTables + system_migration` باید باقی بماند.

Collision نه Skip است و نه با assumption پنهان می‌شود. اگر repository فعلی این رفتار را ثابت نمی‌کند، اختلاف دقیق ثبت شود.

## 9. Failure Behavior و منابع

* config قبلی حتی در شکست setup restore می‌شود.

* اگر cleanup با failure اصلی همزمان شود، cleanup failure با suppression فعلی حفظ می‌شود.

اگر این رفتارها از control flow فعلی قابل پیاده‌سازی/test نیستند، بدون افزودن abstraction جدید، مورد به‌عنوان mismatch گزارش شود.

## 13. Test Plan Review

سناریوهای زیر فقط از نظر قابلیت اثبات و انطباق با تست فعلی review شوند:

### A. Refresh خاموش

* database clean، lifecycle کامل اجرا شود.
* seeded owned object → collision → failure؛ همان object بعد از failure همچنان موجود باشد.

### B. Refresh روشن

پیش از refresh، owned fixture tables، `system_migration` و history وجود داشته باشند. پس از refresh:

* fixture tables حذف شده باشند.
* `system_migration` و history قبلی حذف شده باشند.
* Migrator جدول state را دوباره bootstrap کند.

### C. Object نامرتبط

یک object خارج از `ownedFixtureTables` پیش از refresh موجود باشد و پس از refresh باقی بماند. این سناریو اثبات می‌کند refresh کل database را پاک نمی‌کند.

### D. Refresh failure

اگر test infrastructure معتبر برای permission denial وجود دارد، ثابت شود refresh fail می‌شود و Migrator شروع نمی‌شود. اگر چنین infrastructureای موجود نیست، این سناریو `Unverified` بماند.

Failure باید پیش از lifecycle باشد؛ history یا fixture جدیدی از Migrationها نباید ایجاد شود. fallback، retry و database جایگزین وجود ندارد.

## 15. Plan Corrections

هر تناقض یا assumption بدون پشتوانه با مسیر فایل ثبت شود. برای هرکدام:

```text
Evidence
Interpretation
Decision
```

به‌طور ویژه قابلیت دفاع از موارد زیر بررسی شود:

```text
migration.test.db.refresh
default = false
strict true/false parsing
refresh = ownedFixtureTables + system_migration
refresh via DropTable + MigrationExecutor
config installed before refresh
collision guard after refresh
```

### نتیجهٔ Final Contract Review

**Evidence:** `QueryExecute.executeTable` در صورت نبود SQL error، صرف‌نظر از Boolean مقدار برگشتی `Statement.execute()`, `Success(true)` می‌دهد. Renderer، `IF EXISTS` را در SQL قرار می‌دهد. Integration Test فعلی collision guard را قبل از `ownsTestObjects = true` اجرا می‌کند؛ cleanup فقط پس از ownership موفق، با فهرست صریح owned names انجام می‌شود. `MigrationExecutor` از `DefaultDatabaseConfig.config` به‌واسطهٔ `IQueryExecute`/`DatabaseConnection` استفاده می‌کند. Gradle test properties فعلی refresh key را هنوز forward نمی‌کنند.

**Interpretation:** برای نتیجهٔ concrete فعلی، نبود table زیر `IF EXISTS` به `Success(false)` نگاشت نمی‌شود؛ این مسیر `Success(true)` دارد. حالت `refresh=false` هیچ deletion قبل از guard ندارد. در `refresh=true`، اگر فراخوانی refresh پیش از guard و پیش از Migrator به‌صورت ترتیبی انجام شود، refresh failure جلوی Migrator را می‌گیرد. Scope ثابت DropTableها object نامرتبط را لمس نمی‌کند. Test config change موردنیاز در build.gradle صرفاً در محدودهٔ مجاز است.

**Decision / Contract Correction:**

1. `Success(true)` عبارت از successful DDL execution است، نه اثبات اینکه جدول واقعاً وجود داشته یا حذف شده است.
2. `Success(false)` از concrete `QueryExecute` تولید نمی‌شود و source برایش معنی «جدول نبود» تعریف نکرده است؛ معنای تازه‌ای به آن نسبت داده نشود. برای executor پیش‌فرض، `Success(true)` نتیجهٔ مورد انتظار و `Failure` خطای execution است.
3. test matrix باید صریحاً ثابت کند: `refresh=false + collision → failure + object remains`; `refresh=true → owned objects removed → guard → lifecycle`; object نامرتبط باقی می‌ماند; refresh failure پیش از Migrator خاتمه می‌یابد.
4. در implementation، تنها build edit مجاز افزودن refresh property به test property forwarding است؛ production APIs و semantics بدون تغییر می‌مانند.

اگر contract با source ناسازگار بود، فقط correction همین Plan ارائه شود و implementation انجام نشود.
