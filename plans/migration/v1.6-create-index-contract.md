# Migration v1.6: CREATE INDEX Contract

وضعیت: `implemented`

## پیش‌شرط و هدف

آخرین operationهای ثبت‌شده در مسیر اصلی migration تا این مرحله شامل `v1.5 MODIFY COLUMN` است. این plan نوبت بعدی را به اولین operation از خانوادهٔ Index اختصاص می‌دهد: `CREATE INDEX`.

هدف، افزودن operation مستقل برای ساخت یک index عادی روی یک ستون در جدول موجود است. این operation باید از pipeline موجود API → AST → Builder → Dialect/Renderer → Executor عبور کند و اجرای DDL را به `data_base:manager` موجود بسپارد.

## مبنا و traceability

- پیش از implementation، قراردادهای `CREATE TABLE`، `ADD COLUMN`، `DROP COLUMN` و `MODIFY COLUMN v1.5` از API تا renderer/executor بررسی شوند؛ این‌ها فقط الگوی pipeline هستند و AST/API آنها reuse نشود.
- traceability باید naming convention واقعی APIها، شکل ASTها، الگوی Builder، capability registration در dialect و مسیر `executeTable` در executor موجود را ثبت کند.
- مسیر واقعی اجرای migration و قرارداد executor/manager بررسی شود؛ برای CREATE INDEX abstraction اجرایی جدید نسازید.
- ساختار package و naming از operationهای موجود repository پیروی کند. صرفاً برای تطبیق با مسیر پیشنهادی این plan hierarchy موازی نسازید.
- API مفهومی برای consistency با DSL فعلی به شکل کوتاه `tableName(...)`, `name(...)`, `column(...)` باشد؛ AST برای وضوح از propertyهای `tableName`, `indexName`, `columnName` استفاده کند. traceability این انتخاب را با convention واقعی repository تطبیق و نتیجه را ثبت کند.
- وجود syntax و محدودیت‌های CREATE INDEX در MySQL و compatibility target اعلام‌شدهٔ repository بررسی شود. تا این مرحله repository compatibility target کلی MySQL اعلام نکرده است؛ traceability این را به‌عنوان finding تأیید/ثبت کند و CREATE INDEX را فقط بر اساس baseline grammar مستندشده ارزیابی کند، نه نسخهٔ نصب‌شدهٔ توسعه‌دهنده یا نسخهٔ حدسی.
- identifier quoting/escaping و serialization نام جدول، index و ستون از convention واقعی MySQL renderer پیروی کند؛ traceability مشخص کند renderer موجود برای همهٔ این identifierها یک quote mechanism مشترک دارد یا نه.
- اگر plan مشترک `v1.2` هنوز `planned` است، وابستگی واقعی CREATE INDEX به آن بررسی شود؛ فقط در صورت وابستگی، contract باید قبل از implementation تعیین تکلیف شود.

### یافته‌های traceability و تصمیم‌های implementation

- API مطابق operationهای موجود در package `interfaces/create_index` قرار گرفت و DSL کوتاه `tableName()`, `name()`, `column()` را دارد؛ `name()` نام index است.
- AST مستقل در `interfaces/create_index` و `schema/create_index` سه property nullable و روشن `tableName`, `indexName`, `columnName` دارد تا renderer بتواند AST ناقص مستقیم را رد کند.
- Builder مطابق الگوی operationهای دیگر، مقادیر را trim می‌کند، casing/محتوا را نگه می‌دارد و در `build()` سه مقدار خالی/تعیین‌نشده را رد می‌کند.
- `MySqlDialect.registerRenders()` capability را بر اساس AST interface در renderer registry موجود ثبت می‌کند؛ capability از `IAstRenderer` فعلی پیروی می‌کند و identifierها را با backtick و doubling backtick داخلی quote می‌کند.
- executor موجود یک overload محدود دارد که از `executeOut` و سپس `IQueryExecute.executeTable` عبور می‌کند. fake تست همان `IQueryExecute` موجود است؛ executor یا manager production جدیدی ساخته نشده.
- plan مشترک `v1.2` هنوز `planned` است، اما مسیر `executeOut`/renderer موجود dependency به abstraction پیشنهادی آن ایجاد نمی‌کند؛ v1.6 از آن مستقل است.
- جست‌وجوی repository compatibility target کلی برای MySQL پیدا نکرد؛ این finding ثبت می‌شود و نسخهٔ محلی به‌عنوان حداقل پشتیبانی فرض نشده است.
- grammar پایه با MySQL 8.0 Reference Manual، بخش 15.1.15 (`CREATE INDEX Statement`) تطبیق داده شد: `CREATE INDEX index_name ON tbl_name (key_part,...)`. این تطبیق syntax را تأیید می‌کند و minimum supported server version برای کل repository اعلام نمی‌کند.

ترتیب کار پیش از implementation:

```text
CREATE INDEX contract
    → traceability کدهای موجود
    → ثبت naming / AST / Builder / renderer / executor conventions
    → تأیید MySQL grammar و ثبت compatibility finding
    → API → AST → Builder → dialect capability → renderer
    → executor → tests → example → docs → regression
```

## محدوده

در v1.6:

- ایجاد یک index عادی (non-unique) روی یک ستون موجود.
- MySQL dialect و renderer موجود.
- DSL مفهومی:

```kotlin
createIndex {
    tableName("users")
    name("idx_users_email")
    column("email")
}
```

`name()` در DSL نام index را می‌گیرد؛ AST آن را با نام صریح `indexName` نگه می‌دارد. `column()` فقط یک نام ستون می‌گیرد.

- SQL مفهومی:

```sql
CREATE INDEX `idx_users_email`
ON `users` (`email`)
```

- operation API، AST و Builder مستقل داشته باشد؛ AST فقط ورودی‌های همین operation را حمل کند.
- مثال نسخه‌بندی‌شده با render-only پیش‌فرض و اجرای صریح از executor/manager موجود.
- unit testهای بدون دیتابیس برای validation، SQL و مسیر executor با fake در abstraction موجود.

خارج از محدودهٔ v1.6:

- `DROP INDEX`.
- `UNIQUE INDEX` یا constraint مربوط به UNIQUE.
- index چندستونی، prefix length و ترتیب/جهت index columnها.
- `FULLTEXT`، `SPATIAL` و گزینه‌های اختصاصی dialect.
- `IF NOT EXISTS`، deduplication یا preflight خودکار schema.
- introspection برای بررسی وجود جدول، ستون یا index پیش از اجرا.
- rollback، migration history و runner.
- dialectهای غیر از MySQL.

هر مورد خارج از محدوده نیازمند plan/contract جداگانه یا اصلاح صریح همین plan پیش از implementation است.

## Contract و invariantها

یک `CreateIndex` معتبر شامل این ورودی‌هاست:

```text
CreateIndex
├── tableName: non-blank identifier
├── indexName: non-blank identifier
└── columnName: non-blank identifier
```

- هر operation دقیقاً یک index عادی برای دقیقاً یک ستون می‌سازد.
- index باید نام صریح داشته باشد؛ نام خودکار از table/column تولید نشود.
- نام‌ها در Builder trim می‌شوند و پس از trim، مقدار identifier بدون تغییر معنایی در AST نگهداری می‌شود. Builder فقط whitespace پیرامونی را حذف می‌کند و casing یا محتوای identifier را تغییر نمی‌دهد.
- `tableName`، `indexName` و `columnName` سه identifier مستقل‌اند؛ هیچ رابطهٔ معنایی یا نام‌گذاری مانند `idx_<table>_<column>` از روی آن‌ها infer نشود و library هیچ نامی را تولید یا اصلاح نکند.
- نام خالی یا whitespace-only در Builder رد شود.
- Renderer پیش از quote کردن identifierها یا compose کردن SQL، AST ناقص/نامعتبر را دفاعی رد کند.
- Identifierها bind parameter نیستند و باید با quoting و escaping dialect وارد SQL شوند؛ convention موجود renderer مرجع است.
- مقدار identifier نباید به‌عنوان SQL خام، expression یا fragment قابل اجرا پذیرفته شود.
- operation مسئول بررسی وجود table/column یا index نیست و metadata دیتابیس را introspect نمی‌کند؛ خطاهای واقعی execution از manager حفظ شوند.
- `CREATE INDEX` در این نسخه non-unique است. هیچ flag یا حالت مبهمی برای UNIQUE در AST/API وجود نداشته باشد.
- renderer، API، AST و Builder به connection، executor یا JDBC وابسته نباشند.
- executor operation را به مسیر execution موجود و `IQueryExecute.executeTable` تحویل دهد؛ dependency direction فعلی حفظ شود.

## API، AST و Builder

- API مستقل در package متناظر با convention repository تعریف شود؛ DSL مفهومی `createIndex { tableName(...); name(...); column(...) }` است. در traceability تفاوت احتمالی convention ثبت شود، اما DSL پیشنهادی `indexName()`/`columnName()` را وارد نکند مگر convention واقعی repository الزام کند.
- AST مستقل سه identifier trimmed را در propertyهای روشن `tableName`, `indexName`, `columnName` نگه دارد؛ casing و محتوای باقی‌مانده پس از trim عین ورودی است. stateهای UNIQUE، چندستونی یا dialect option در AST نباشند.
- Builder فقط مسئول ساخت AST و رد ورودی‌های خالی است؛ SQL تولید یا اجرا نکند.
- ترتیب فراخوانی setterها نباید در SQL تفاوت ایجاد کند؛ AST معنایی است.
- تا وقتی traceability duplication واقعی و یکسان را ثابت نکرده، abstraction مشترک index/table/column ساخته نشود.

## Dialect و Renderer

- قابلیت `CREATE INDEX` در قرارداد dialect موجود ثبت و در MySQL dialect registry اضافه شود.
- SQL با grammar زیر تولید شود:

```sql
CREATE INDEX <quoted-index-name>
ON <quoted-table-name> (<quoted-column-name>)
```

- ترتیب و فاصله‌گذاری SQL بر اساس convention renderer فعلی باشد.
- identifier quoting/escaping باید برای نام‌های معمولی، underscore، reserved wordها و identifier دارای backtick در هر سه جایگاه table/index/column مطابق convention موجود آزموده شود. اگر renderer موجود همه را یکسان quote نمی‌کند، تفاوت در traceability ثبت شود و mechanism جدید خارج از convention اختراع نشود.
- Renderer فقط AST را مصرف کند؛ اتصال، server introspection و executor را نشناسد.
- هیچ `UNIQUE`، `FULLTEXT`، `SPATIAL`، prefix length یا گزینه‌ای خارج از contract به SQL اضافه نشود.

## Executor و خطا

- فقط در صورت نیاز convention فعلی، entry point/overload برای API جدید به executor موجود اضافه شود.
- اجرا از `IQueryExecute.executeTable` موجود عبور کند.
- خطاهای duplicate index name، missing table/column، permission و محدودیت‌های MySQL با cause اصلی حفظ شوند؛ خطای احتمالی به no-op یا success تبدیل نشود.
- fake/mock تست باید abstraction واقعی موجود (`IQueryExecute`) را هدف بگیرد؛ abstraction production جدید فقط برای تست ساخته نشود.

## مثال و تست

- مثال در ساختار نسخه‌بندی‌شدهٔ واقعی example module قرار گیرد و DDL را به‌طور پیش‌فرض فقط render کند؛ اجرای واقعی فقط با opt-in مشخص انجام شود.
- تست‌های بدون دیتابیس موارد زیر را پوشش دهند:
  - AST مستقل و trim شدن سه identifier.
  - رد جدول، نام index یا نام ستون خالی در Builder.
  - validation دفاعی renderer برای AST مستقیم/بدساخت.
  - SQL دقیق `CREATE INDEX ... ON ... (...)`.
  - escaping نام عادی، underscore، reserved word و backtick برای index name، table name و column name بر اساس quote convention جاری؛ نمونهٔ مفهومی:

    ```sql
    CREATE INDEX `order` ON `users` (`select`)
    ```

  - حفظ case و محتوای identifier پس از trim؛ برای مثال `User_Name` نباید به `user_name` تبدیل شود.
  - عدم تولید `UNIQUE` و SQL optionهای خارج scope.
  - یکسان بودن SQL برای ترتیب‌های مختلف فراخوانی DSL با ورودی‌های یکسان.
  - executor: ارسال BuiltQuery به `IQueryExecute.executeTable`، callback موفقیت و حفظ همان failure/cause.
- integration test فقط در MySQL اختصاصی و با index آزمایشی قابل cleanup اجرا شود؛ مثال عادی نباید خودکار آن را اجرا کند.
- regression test operationهای پیشین در اجرای نهایی اجرا شود.

## مستندات مورد انتظار

- structure docs مربوط به API، AST، Builder، dialect، renderer، executor و example به‌روز شوند.
- DSL، SQL تولیدشده، non-unique بودن، تک‌ستونی بودن و موارد خارج scope مستند شوند.

- تصمیم‌های traceability که با این contract فرق دارند، پیش از implementation در همین plan ثبت شوند.

## نقشهٔ راه خانوادهٔ Index

این roadmap اطلاع‌رسانی است و scope همین v1.6 را گسترش نمی‌دهد:

```text
Index v1 roadmap
├── v1.6: CREATE INDEX (single-column, non-unique)
└── next operation: DROP INDEX (separate plan/version)
        ↓
Index v2 (future plan)
├── UNIQUE INDEX
└── Multi-column index
        ↓
Index v3 (future plan)
├── FULLTEXT
├── SPATIAL
└── Dialect-specific options
```

ترتیب کلی پس از operationهای پایه:

```text
CREATE TABLE → DROP TABLE → RENAME TABLE
    → ADD COLUMN → DROP COLUMN → RENAME COLUMN → MODIFY COLUMN
    → INDEX OPERATIONS → CONSTRAINT OPERATIONS → FOREIGN KEY
    → MIGRATION HISTORY / RUNNER
```

هر گام بعدی plan و traceability مستقل دارد؛ این roadmap تعهد implementation برای نسخه‌های بعدی نیست.

`DROP INDEX` در scope این v1.6 نیست؛ عنوان Index v1 در roadmap خانواده است و این plan فقط operation `CREATE INDEX` را تعریف می‌کند.
