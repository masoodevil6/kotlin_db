# Migration v1.17.4: SystemMigrationStateStore Responsibility Refactor

## وضعیت

`Ready for Review` — این سند plan اجرای یک refactor ساختاری است. پیاده‌سازی پس از تأیید این plan انجام می‌شود.

## 1. هدف

مسئولیت‌های داخلی `SystemMigrationStateStore` بر اساس concern دامنه‌ای جدا شوند تا Store به facade/coordinator تبدیل شود. این مرحله هیچ قابلیت جدیدی به Migration subsystem اضافه نمی‌کند و رفتار persistence فعلی را تغییر نمی‌دهد.

## 2. Evidence

### E1 — فایل و API فعلی

پیاده‌سازی فعلی در:

`data_base/migration/executor/src/main/kotlin/internal/system_migration/SystemMigrationStateStore.kt`

کلاس internal `SystemMigrationStateStore` constructor فعلی `IQueryExecute` تزریق‌شده و `MigrationExecutor` را می‌گیرد. Callerهای فعلی، شامل unit و integration test، فقط با همین Store کار می‌کنند.

### E2 — مسئولیت‌های جمع‌شده در Store

فایل فعلی این کارها را انجام می‌دهد:

* تعریف schema جدول `system_migration` در `systemMigrationTable()`.
* orchestration متد `initialize()`: ساخت جدول با `MigrationExecutor` و سپس خواندن state.
* ساخت SELECT AST و اجرای آن از طریق `IQueryExecute.executeSelect()`.
* خواندن و بستن `ResultSet`، اعتبارسنجی rowها و ساخت `AppliedMigration` و `SystemMigrationState` در `readHistory()`.
* ساخت INSERT AST، اعتبارسنجی ورودی و ثبت از طریق `IQueryExecute.executeUpdate()`.
* تبدیل Query API/AST به `BuiltQuery` با dialect و renderer فعلی در `toBuiltQuery()`.

### E3 — مرزهای اجرای موجود

DDL bootstrap از `MigrationExecutor` عبور می‌کند. خواندن و ثبت state از `IQueryExecute` تزریق‌شده عبور می‌کنند. `QueryBuilderExecutor` در این مسیر نیست و این refactor آن را وارد نخواهد کرد.

### E4 — محل helper تبدیل به BuiltQuery

جست‌وجوی repository نشان داد `toBuiltQuery()` helper مشترکی در اختیار Store ندارد. الگوی render و ساخت `BuiltQuery` در executorهای Query و Migration نیز در همان executorها پیاده شده است؛ extraction عمومی در این plan انجام نمی‌شود.

### E5 — تست‌های موجود

* `data_base/migration/executor/src/test/kotlin/internal/system_migration/SystemMigrationStateStoreTest.kt` routing، SQL/پارامترها، validation، history و failure handling را با fake manager بررسی می‌کند.
* `data_base/migration/executor/src/test/kotlin/internal/system_migration/SystemMigrationStateStoreIntegrationTest.kt` integration opt-in برای MySQL دارد.
* تست‌های موجود، رفتار facade و persistence را پوشش می‌دهند؛ تغییر ساختار نباید قرارداد یا API Store را به callerها تحمیل کند.

## 3. Interpretation

Store هم‌زمان schema، query construction، row mapping و persistence policy را در خود نگه می‌دارد. این مسئولیت‌ها با یکدیگر مرتبط‌اند، اما concern یکسانی نیستند: schema تعریف جدول است؛ Reader history را به domain state تبدیل می‌کند؛ Recorder نوشتن state را انجام می‌دهد؛ Store ترتیب initialize/read و delegation عمومی را هماهنگ می‌کند.

Bootstrap فعلی فقط یک delegation به `MigrationExecutor` و سپس read است. شواهد فعلی منطق کافی برای یک component مستقل bootstrap نشان نمی‌دهند.

`toBuiltQuery()` وابستگی به dialect/config و تبدیل Query API به carrier اجرایی را در یک تابع کوتاه جمع کرده است. جست‌وجوی repository helper آماده‌ای برای reuse نشان نداد؛ اضافه‌کردن class/interface جدید برای این چند خط، abstraction مستقل و غیرضروری خواهد بود.

## 4. Decision و ساختار هدف

```text
internal/system_migration/
├── SystemMigrationStateStore.kt
├── SystemMigrationTable.kt
├── SystemMigrationReader.kt
├── SystemMigrationRecorder.kt
└── SystemMigrationQuerySupport.kt   // فقط top-level internal helper، بدون type/API جدید
```

### 4.1 `SystemMigrationTable`

* تعریف schema فعلی جدول را نگه می‌دارد و یک CREATE TABLE builder برای bootstrap فراهم می‌کند.
* شامل اجرای SQL، خواندن state یا policy مربوط به Recorder نمی‌شود.
* مشخصات schema تغییر نمی‌کند: `id` افزایشی و primary key، `migration VARCHAR(255) NOT NULL` با unique constraint و `batch INT NOT NULL`، به‌علاوه `IF NOT EXISTS`.

### 4.2 `SystemMigrationReader`

* مسئول SELECT history، تحویل `BuiltQuery` به `IQueryExecute.executeSelect()`، خواندن و بستن `ResultSet`، validation و ساخت domain state است.
* ترتیب `id ASC`، الزام مثبت و صعودی بودن id، migration identity غیرخالی و یکتا، و مثبت بودن batch حفظ می‌شوند.
* خواندن همهٔ history و محاسبهٔ `currentBatch` به‌صورت فعلی باقی می‌ماند.

### 4.3 `SystemMigrationRecorder`

* مسئول اعتبارسنجی migration identity و batch، ساخت INSERT، اجرای آن با `executeUpdate()` و کنترل affected-row count است.
* شرط ثبت یک ردیف و propagation خطای manager حفظ می‌شوند؛ `executeInsert()` وارد مسیر نمی‌شود.

### 4.4 `SystemMigrationStateStore`

* facade/coordinator داخلی باقی می‌ماند و API فعلی `initialize`, `read`, `recordSuccessfulMigration` را تا حد امکان حفظ می‌کند.
* `initialize()` ایجاد جدول با `MigrationExecutor` را هماهنگ می‌کند و پس از موفقیت به Reader delegate می‌کند.
* `read()` و `recordSuccessfulMigration()` به Reader و Recorder delegate می‌کنند.
* Callerها مستقیماً با Table، Reader یا Recorder کار نمی‌کنند.
* جهت dependency یک‌طرفه است؛ هیچ component جدیدی به Store وابسته نمی‌شود.

### 4.5 Bootstrapper

`SystemMigrationBootstrapper` ساخته نمی‌شود. orchestration فعلی کوتاه است و به‌تنهایی منطق مستقل قابل‌توجهی ندارد؛ نگه‌داشتن آن در facade از ایجاد یک wrapper کم‌ارزش جلوگیری می‌کند.

Bootstrap همچنان فقط CREATE TABLE IF NOT EXISTS را از طریق MigrationExecutor هماهنگ می‌کند و پس از موفقیت، خواندن state را به SystemMigrationReader واگذار می‌کند.

### 4.6 تصمیم `toBuiltQuery()`

* Query architecture و executorهای عمومی تغییر نمی‌کنند.
* conversion فعلی به یک top-level `internal` helper در همان package داخلی منتقل می‌شود تا Reader و Recorder یک implementation داشته باشند.
* helper فقط انتخاب Query dialect، render کردن AST و ساخت `BuiltQuery` را انجام می‌دهد؛ execution در Reader/Recorder از manager تزریق‌شده می‌گذرد.
* class/interface، API عمومی یا execution abstraction جدید ساخته نمی‌شود. اگر امضای عمومی فعلی Query API مانع استخراج این تابع شود، همان منطق کوتاه با کمترین duplication در Reader و Recorder نگه داشته می‌شود و دلیل در Implementation Result ثبت خواهد شد.

## 5. Dependency direction

```text
SystemMigrationStateStore
    ├── SystemMigrationTable
    ├── SystemMigrationReader ──→ IQueryExecute
    ├── SystemMigrationRecorder ─→ IQueryExecute
    └── MigrationExecutor ───────→ existing execution boundary

SystemMigrationReader / SystemMigrationRecorder
    └── SystemMigrationQuerySupport (file-level helper; if applicable)

SystemMigrationTable
    └── existing Migration CREATE TABLE builder / params
```

هیچ مسیر مستقیمی از Store یا اجزای جدید به JDBC ایجاد نمی‌شود. هیچ وابستگی معکوسی به Store ایجاد نمی‌شود.

## 6. Scope و رفتارهای ثابت

این نسخه فقط structural refactor است. موارد زیر نباید تغییر کنند:

* schema جدول، نام‌ها، نوع‌ها، constraints و `IF NOT EXISTS`.
* ترتیب و validation history، duplicate identity و محاسبهٔ current batch.
* validation ورودی Recorder و شرط affected-row برابر یک.
* استفاده از `IQueryExecute` تزریق‌شده برای SELECT و UPDATE.
* عبور bootstrap از `MigrationExecutor`.
* callbackها، failure propagation و مدیریت/بستن `ResultSet`.
* نبود pre-read برای duplicate هنگام ثبت.

خارج از scope: Migration Contract، discovery/provider/runner، rollback، locking، checksum، config migrationها، transaction redesign، تغییر Query یا manager architecture و تغییر behavior دیتابیس.

## 7. تست‌ها و Verification پس از تأیید

تست جدید صرفاً برای بازآرایی اضافه نشود مگر اینکه جداسازی componentها یک gap مستقیم در پوشش فعلی ایجاد کند؛ ابتدا تست‌های موجود حفظ و اجرا شوند.

* `:data_base:migration:executor:test` — unitها و integration opt-in Store.
* `:data_base:migration:example:test` — regression نمونه‌های Migration.
* در صورت تغییر ناخواسته در dependencyهای manager/query، taskهای متناظر آن ماژول‌ها اجرا شوند؛ این refactor به‌خودی‌خود نباید source آن ماژول‌ها را تغییر دهد.
* integration واقعی فقط با متغیرهای اتصال موجود و database اختصاصی اجرا شود. نبود environment معتبر به‌صورت `Blocked/Unverified` گزارش می‌شود؛ موفقیت فرض نمی‌شود.
* پس از اجرای refactor، diff و `git diff --check` بررسی شوند.

## 8. Acceptance Criteria

* Store facade است و API موردنیاز callerهای فعلی حفظ شده است.
* schema فقط در `SystemMigrationTable` تعریف شده است.
* history query، ResultSet lifecycle، validation و mapping در Reader قرار دارند.
* validation نوشتن، INSERT و affected-row handling در Recorder قرار دارند.
* Bootstrapper مستقل ساخته نشده و bootstrap از `MigrationExecutor` می‌گذرد.
* `toBuiltQuery()` طبق بند 4.6 منتقل شده یا fallback کم‌تکرار آن با دلیل ثبت شده است.
* dependency direction و execution boundary موجود حفظ شده‌اند.
* هیچ تغییر رفتاری در state persistence رخ نداده و تست‌های مرتبط نتیجهٔ روشن دارند.
* این نسخه هیچ Migration Runner یا lifecycle feature دیگری اضافه نکرده است.
