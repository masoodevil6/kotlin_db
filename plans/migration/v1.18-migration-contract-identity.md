# Migration v1.18: Migration Definition, Operation Handoff & Identity

## 1. وضعیت

**Implemented — تست‌های ماژول‌های مرتبط موفق‌اند؛ real-DB integration به‌علت نبود تنظیمات opt-in رد شد و task کامل `example:build` در packaging با duplicate entry متوقف شد.**

این نسخه Contract را بر پایهٔ شواهد repository می‌بندد. Scope فقط تعریف Migration، جمع‌آوری صریح operationها و handoff یک operation به executor موجود است. Runner و lifecycle کامل در این نسخه پیاده‌سازی نمی‌شوند.

## 2. هدف

امکان تعریف یک Migration مصرف‌کننده‌محور با چند operation در هر جهت:

```kotlin
class CreateUsers : Migration {
    override fun up() = migration {
        createTable {
            // تعریف جدول
        }

        createIndex {
            // تعریف index
        }
    }

    override fun down() = migration {
        dropTable {
            // تعریف حذف جدول
        }
    }
}
```

`up()` و `down()` فقط definition برمی‌گردانند. ساخت definition نباید SQL اجرا کند یا به executor، connection، `IQueryExecute`، JDBC، execution context، global state، thread-local یا collector پنهان دسترسی داشته باشد. لایهٔ بالاتر definition را می‌خواند و operationها را از مسیر `IMigrationExecutor` موجود اجرا می‌کند.

در repository فعلی نام operation تک‌ستونی `createIndex` است؛ نمونهٔ `addIndex` در درخواست به‌عنوان مثال مفهومی در نظر گرفته می‌شود و alias تازه‌ای به این Contract اضافه نمی‌کند.

## 4. Interpretation

1. Operation factoryها API concrete و typed برمی‌گردانند؛ object concrete هنگام قرار گرفتن در collection از بین نمی‌رود، هرچند static type آن در collection مشترک به `IMigrationApi<*>` تبدیل می‌شود.
2. از آنجا که APIهای operation interfaceهای مجزا هستند، executor می‌تواند با `when` و type checkهای `is` API concrete را smart-cast کند و overload متناظر را صدا بزند؛ این مسیر unchecked wildcard cast یا 15 wrapper نیاز ندارد.
3. این dispatch runtime-checked است، نه sealed/compile-time exhaustive. چون API base discriminator ندارد و open است، adapter باید برای API ناشناخته خطای صریح بدهد و تست باید mapping تمام operationهای پشتیبانی‌شده را پوشش دهد.
4. رندر/اجرای عمومی با `executeOut` برای همهٔ اعضا صحیح نیست: overloadهای operation موجود رفتارهای معنایی و capability-specific دارند.
5. handoff باید از type check صریح به overload متناظر executor برسد و هیچ API ناشناخته‌ای را با fallback عمومی render نکند.
6. `migration { ... }` باید صرفاً operationهای موجود را به ترتیب ثبت کند. خود block هیچ side effect اجرایی ندارد.
7. دسترسی به `SystemMigrationStateStore` و filename identity بیرون از قرارداد `Migration` باقی می‌ماند.

## 6. Decision

1. `Migration` در ماژول public API تعریف می‌شود و دقیقاً دو متد دارد:

   ```kotlin
   interface Migration {
       fun up(): MigrationDefinition
       fun down(): MigrationDefinition
   }
   ```

2. `MigrationDefinition` یک snapshot مرتب و قابل‌خواندن از `List<IMigrationApi<*>>` ارائه می‌کند؛ concrete API object همان نوع واقعی operation را حفظ می‌کند.
3. wrapperهای 15گانه ایجاد نمی‌شوند. adapter در executor با checked `when` و `is` concrete API را smart-cast می‌کند و overload typed متناظر را فراخوانی می‌کند. برای API ناشناخته، adapter خطای صریح می‌دهد؛ generic `executeOut` fallback نیست.
4. `MigrationDefinition.operations` ترتیب declaration در DSL را دقیقاً حفظ می‌کند. operation تکراری حذف یا ادغام نمی‌شود.
5. `migration { ... }` در ماژول Builder یک `MigrationDefinition` می‌سازد. Receiver برای هر standalone operation تابع هم‌نام factory موجود دارد و به همان factory delegate می‌کند؛ Builder موجود دوباره پیاده‌سازی نمی‌شود.
6. DSL v1.18 شامل operationهای standalone متناظر با overloadهای فعلی executor است: `createTable`, `dropTable`, `renameTable`, `addColumn`, `dropColumn`, `renameColumn`, `modifyColumn`, `createIndex`, `dropIndex`, `createUniqueIndex`, `createMultiColumnIndex`, `createFullTextIndex`, `createSpatialIndex`, `createForeignKey`, `dropForeignKey`. Definitionهای درون `createTable` همچنان جزئی از همان operation جدول هستند.
7. یک adapter public در ماژول executor، یک `IMigrationApi<*>` از definition را با checked type dispatch به overload typed متناظر `IMigrationExecutor.execute(...)` می‌فرستد. Adapter فقط یک operation را dispatch می‌کند؛ اجرای لیست به‌ترتیب، تصمیم‌گیری و continuation پس از callback متعلق به لایهٔ بالاتر است.
8. هیچ dispatcherای نباید همهٔ operationها را با `executeOut` عمومی اجرا کند؛ مسیر overload موجود حفظ می‌شود تا `ifExists`, compatibility و سایر رفتارهای operation-specific از دست نروند.
9. Migration و Definition هیچ dependencyای به `IMigrationExecutor`, `IQueryExecute`, JDBC، connection، database config یا execution context ندارند.
10. Definition همان Builder-created API referenceها را نگه می‌دارد؛ قرارداد v1.18 از deep-copy کردن تمام ASTهای فعلی که mutable هستند تعهد نمی‌دهد. پس از ساخت Definition، consumer نباید API/AST داخلی operationها را mutate کند.
11. `MigrationDefinition` خالی مجاز است؛ اعتبارسنجی اینکه Migration دارای operation هست یا نه به این Contract اضافه نمی‌شود.
12. Example درخواست از `addIndex` استفاده کرده است، ولی repository operation را `createIndex` نام‌گذاری کرده است؛ v1.18 از `createIndex` استفاده می‌کند و alias جدید تعریف نمی‌کند.

## 7. Public Contract

نمونهٔ قراردادی:

```kotlin
class CreateUsers : Migration {
    override fun up(): MigrationDefinition = migration {
        createTable {
            tableName("users")
            // columns and table definitions
        }
        createIndex {
            tableName("users")
            name("idx_users_email")
            column("email")
        }
    }

    override fun down(): MigrationDefinition = migration {
        dropTable {
            tableName("users")
        }
    }
}
```

Contract typeها:

```text
Migration
├── up(): MigrationDefinition
└── down(): MigrationDefinition

MigrationDefinition
└── operations: List<IMigrationApi<*>>  // ordered, read-only view; runtime operation type retained
```

Adapter dispatch shape (conceptual; use repository package/style):

```kotlin
when (operation) {
    is IMigrationRenderCreateTableApi -> execute(operation, ...)
    is IMigrationDropTableApi -> execute(operation, ...)
    // every current standalone executor API has a typed branch
    else -> error("Unsupported migration operation API: ${operation::class.qualifiedName}")
}
```

`when` branches use Kotlin smart casts; unchecked `as` casts are prohibited.

## 8. Definition DSL and Collection Semantics

نمونهٔ DSL:

```kotlin
val definition = migration {
    createTable { /* ... */ }
    addColumn { /* ... */ }
    createIndex { /* ... */ }
}
```

قواعد:

* هر receiver method، factory موجود operation را فراخوانی می‌کند و API برگشتی را مستقیم به definition اضافه می‌کند.
* هر فراخوانی یک عضو جدید اضافه می‌کند؛ فراخوانی بعدی فهرست قبلی را replace نمی‌کند.
* ترتیب اعضا همان ترتیب فراخوانی DSL است.
* تکرار همان operation مجاز است و حذف/ادغام خودکار ندارد.
* DSL receiver خودش SQL تولید یا اجرا نمی‌کند.
* definition فهرست را به‌صورت read-only و snapshot از ترتیب اعضا expose می‌کند؛ به operation APIهای mutable داخل آن deep-copy نسبت داده نمی‌شود.

## 9. Operation Handoff

زنجیرهٔ قراردادی:

```text
Migration.up()/down()
        ↓
MigrationDefinition.operations (ordered API objects; concrete runtime type retained)
        ↓
higher-level consumer selects direction and iteration policy
        ↓
executor adapter: IMigrationExecutor.execute(IMigrationApi<*>, ...)
        ↓
checked `is` dispatch / Kotlin smart cast
        ↓
matching existing typed IMigrationExecutor.execute(operationApi, ...)
        ↓
existing MigrationExecutor behavior
        ↓
IQueryExecute / manager boundary
```

Adapter API دقیق را با checked runtime type dispatch به overload موجود می‌دهد. از wildcard cast استفاده نمی‌کند. Adapter حق ندارد config، connection یا dialect را مستقلاً بخواند یا SQL را دوباره render کند؛ برای نوع ناشناخته خطای صریح می‌دهد.

این plan اجرای یک Definition به‌صورت batch، ترتیب‌بندی asynchronous، stop/continue policy، جمع‌آوری callbackها، انتخاب migrationها یا ثبت state را طراحی نمی‌کند. Consumer بالاتر `operations` را می‌خواند و هر عضو را از adapter موجود عبور می‌دهد؛ سیاست sequencing بخشی از Runner/lifecycle آینده است.

## 10. Dependency Direction

```text
migration:api
  ├── Migration
  ├── MigrationDefinition
  └── MigrationDefinition.operations: List<IMigrationApi<*>>
          ↑
migration:builder
  └── migration { ... } DSL; delegates to current operation factories
          ↑
migration:executor
  └── checked type dispatcher → current IMigrationExecutor overloads
          ↑
consumer / future higher-level execution
```

* `migration:api` از همان API پایهٔ operation استفاده می‌کند؛ به executor یا manager وابسته نمی‌شود.
* `migration:builder` به API وابسته می‌ماند و DSL را با factoryهای فعلی می‌سازد.
* `migration:executor` به API و Builder موجود وابسته است و تنها لایهٔ جدید handoff را به overloadهای execution وصل می‌کند.
* dependency معکوس از API/Builder به executor، manager یا JDBC ممنوع است.
* قبل از افزودن dependency در Gradle، dependencyهای فعلی `api`, `builder`, `executor`, `example` را بررسی کن؛ اگر همین dependencyها کافی‌اند، build file را تغییر نده.

## 11. Identity و Filename Convention

تصمیمات نسخهٔ قبلی حفظ می‌شوند:

```text
Migration ID = filename basename - final ".kt" suffix
YYYY_MM_DD_HHMMSS_description.kt
```

* timestamp چهارده رقم در قالب ثابت `YYYY_MM_DD_HHMMSS` است؛ تفسیر آن UTC است و timezone suffix ندارد.
* description غیرخالی و lowercase ASCII `snake_case` است: `[a-z0-9]+(?:_[a-z0-9]+)*`.
* طول ID از 255 کاراکتر بیشتر نمی‌شود؛ با prefix هجده‌کاراکتری، description حداکثر 237 کاراکتر است.
* ترتیب IDها lexicographical ascending است؛ description برای timestamp برابر tie-break می‌کند.
* class name، package، numeric row id و شمارهٔ ترتیبی جای identity را نمی‌گیرند.
* این convention از example filenames موجود (`A1Example...V1.kt`) استخراج نشده و آن exampleها migration files نیستند.
* v1.18 identity را به‌عنوان Contract حفظ می‌کند، ولی parser، filename scanning، discovery، provider، registration و validation اجرایی را پیاده‌سازی نمی‌کند.

## 12. System Migration State Compatibility

* `SystemMigrationStateStore` همچنان string opaque دریافت می‌کند.
* در آینده لایهٔ registration/runner، filename-derived Migration ID را پس از اجرای موفق `up()` به Store می‌دهد.
* migration class یا definition خودش filename را استخراج نمی‌کند.
* numeric `system_migration.id` کلید داخلی ردیف باقی می‌ماند و Migration ID نیست.
* duplicate identity پیش از اجرا و ثبت نهایی در database خارج از این Contract است.

## 13. Scope

### داخل Scope

* public `Migration` interface با `up/down(): MigrationDefinition`.
* ordered definition روی API objectهای typed موجود و adapter checked-type برای dispatch به standalone overloadهای executor.
* `migration { ... }` با delegate به factoryهای فعلی.
* adapter تک-operation برای handoff به overloadهای موجود `IMigrationExecutor`.
* تست و مثال compile-time/runtime محدود برای definition و dispatch.
* حفظ filename identity contract در همین سند.

### خارج از Scope

* Migration Runner، discovery/provider، filename scanning و registration.
* System migration state management یا تغییر `SystemMigrationStateStore`.
* batch execution API، transaction/rollback، locking، retries، checksum و lifecycle کامل.
* automatic rollback، reverse ordering یا auto-generation برای `down()`.
* اتصال، JDBC، execution context، global state، thread-local یا hidden collector.
* تغییر semantics، API، AST، renderer یا SQL operationهای v1.0–v1.17.4.
* alias `addIndex`, generic `IndexOptions` یا abstraction جدید برای خود schema operations.

## 15. Test Strategy and Acceptance Criteria

### Tests

* API compile test/fixture: یک کلاس `Migration` هر دو جهت را با `migration {}` برمی‌گرداند.
* Builder test: definition خالی، یک operation، و چند operation معتبر ساخته می‌شود و ساخت آن execution را trigger نمی‌کند.
* Ordering test: ترتیب سه operation در `operations` با ترتیب DSL برابر است.
* Repetition test: operationهای تکراری حفظ می‌شوند و deduplicate نمی‌شوند.
* Runtime API type test: خروجی هر factory در definition concrete API type مورد انتظار را حفظ می‌کند.
* Executor adapter test: type branchهای پشتیبانی‌شده به overload دقیق executor می‌رسند؛ حداقل یک مورد دارای رفتار اختصاصی (`dropColumn(ifExists)` یا `renameColumn`) ثابت کند dispatcher از `executeOut` عمومی عبور نمی‌کند.
* Unsupported API test: API ناشناخته‌ای که مستقیم به Definition داده شده باشد، پیش از render/execution با خطای صریح رد می‌شود.
* Error test: exception/`ExecuteResult` رفتار همان overload موجود را حفظ می‌کند؛ adapter خطا را swallow یا تبدیل نمی‌کند.
* Example test/compile check: composite example بدون DB و بدون opt-in اجرا، definition را می‌سازد و محتوایش قابل مشاهده است.
* Regression: تست‌های موجود migration API/builder/executor/example اجرا شوند؛ هیچ SQL خروجی یا semantics قبلی تغییر نکند.
