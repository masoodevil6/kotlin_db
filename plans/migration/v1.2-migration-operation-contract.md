# Migration v1.2: Common Operation Contract

وضعیت: `planned`

## پیش‌شرط

این plan فقط بعد از کامل‌شدن `v1.0` و `v1.1` اجرا می‌شود. هدف آن استخراج abstraction از دو implementation واقعی است، نه ساختن interfaceهای پیشگیرانه بر اساس حدس.

## Scope اجرایی

- مقایسه‌ی pipeline واقعی `CREATE TABLE` و `DROP TABLE`.
- شناسایی duplication واقعی در validation، rendering، query building و execution.
- تعریف کمترین قرارداد مشترک لازم.
- حفظ semantics و AST مستقل هر operation.

## روش تصمیم‌گیری

برای هر abstraction پیشنهادی این پرسش‌ها پاسخ داده شود:

1. آیا رفتار در هر دو operation واقعاً یکسان است؟
2. آیا abstraction وابستگی operation-specific ایجاد می‌کند؟
3. آیا حذف آن duplication، خوانایی یا تست‌پذیری را بهتر می‌کند؟
4. آیا operation سوم مانند `ALTER TABLE` نیز از آن استفاده خواهد کرد؟
5. آیا abstraction جدید migration را به query AST یا SQL خام وابسته می‌کند؟

اگر پاسخ‌ها روشن نباشند، abstraction به نسخه‌ی بعد منتقل شود.

## خروجی‌های مورد انتظار

- جدول مقایسه‌ی Contractهای `CREATE TABLE` و `DROP TABLE`.
- فهرست duplicationهای واقعی با مسیر فایل.
- تصمیم برای هر abstraction: `adopt`, `defer` یا `reject`.
- migration plan برای تغییرات کم‌ریسک.
- تست regression برای حفظ رفتار هر دو operation.

## فازهای implementation

### فاز 1: مقایسه و traceability

pipeline هر دو operation از API تا executor مستند شود.

### فاز 2: استخراج حداقل abstraction

فقط قراردادهایی که هر دو operation واقعاً به آن نیاز دارند استخراج شوند؛ مثلاً render context یا اجرای BuiltQuery، نه column API یا `ifExists`.

### فاز 3: migration تدریجی

یک operation در هر مرحله به abstraction جدید منتقل شود و بعد از هر مرحله regression test اجرا شود.

### فاز 4: اعتبارسنجی با operation سوم

بررسی شود abstraction برای `ALTER TABLE` قابل استفاده است، بدون اینکه Contract آن operation را از قبل تحریف کند.

## مواردی که نباید مشترک شوند

- AST و API اختصاصی `CREATE TABLE` و `DROP TABLE`.
- optionهای operation-specific مانند `ifExists`.
- validation اختصاصی column و table definition.
- renderer capabilityهایی که grammar متفاوت دارند.

## Contract مفهومی مشترک

هر operation باید این بخش‌ها را داشته باشد:

```text
MigrationOperation
├── Purpose
├── Input
├── Options
├── AST
├── Invariants
├── Validation
├── Rendering
├── Execution
├── Result
├── Errors
└── Tests
```

## مرز abstraction

این نسخه نباید APIهای operationها را بدون نیاز ادغام کند. abstraction مشترک باید فقط مسئول قرارداد مشترک pipeline باشد:

```text
operation AST
    → validation
    → dialect renderer
    → BuiltQuery
    → executor
```

جزئیات اختصاصی مانند columnهای `CREATE TABLE` یا flag `ifExists` مربوط به AST همان operation باقی می‌مانند.

## کاندیداهای abstraction

پس از مقایسه‌ی implementation واقعی `CREATE TABLE` و `DROP TABLE` بررسی شود که آیا نیاز به این موارد وجود دارد:

- قرارداد مشترک render migration.
- قرارداد مشترک validation.
- executor عمومی برای operationهای DDL.
- result و error مشترک.
- registry عمومی برای nodeهای dialect.

اسم interface در این مرحله از قبل تثبیت نمی‌شود؛ ابتدا رفتار مشترک باید از implementation استخراج شود.

## خارج از محدوده

- migration runner
- migration history
- rollback عمومی
- transaction policy کامل
- اجرای چند operation در یک migration
- abstraction پیش از داشتن شواهد کافی از دو operation

## معیار پذیرش

1. Contractهای `CREATE TABLE` و `DROP TABLE` بدون از دست‌دادن semantics مستقل باقی بمانند.
2. duplication واقعی در pipeline شناسایی و مستند شود.
3. abstraction جدید با کمترین coupling اضافه شود.
4. تست‌های قبلی هر دو operation بدون تغییر رفتاری عبور کنند.
5. اضافه‌کردن operation سوم، مانند `ALTER TABLE`، از Contract مشترک قابل استفاده باشد.

## ریسک‌ها و تصمیم‌ها

- refactor فقط برای کم‌کردن تعداد interfaceها انجام نمی‌شود.
- اگر abstraction باعث generic شدن بیش از حد Contract شود، رد می‌شود.
- compatibility با API عمومی موجود باید حفظ شود یا breaking change صریحاً ثبت شود.
- تغییرات این plan نباید رفتار SQL دو operation قبلی را تغییر دهد.
