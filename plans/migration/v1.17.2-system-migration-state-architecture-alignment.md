# Migration v1.17.2: هم‌راستاسازی System Migration State با معماری Query/Migration

## وضعیت

`Verification Pending` — implementation و regressionهای محلی کامل‌اند؛ real database integration به‌دلیل نبود تنظیمات اتصال اجرا نشده و DoD هنوز کامل نیست.

## زمینه

v1.17 برای System Migration State قرارداد History-based بست و implementation اولیه‌ای به آن افزود. در بازبینی آن implementation، Store مستقیماً `BuiltQuery` را با SQL رشته‌ای می‌سازد و برای INSERT نیز `BuiltQuery` و `SqlParameter` را دستی کنار هم قرار می‌دهد. Bootstrap از CREATE TABLE DSL و `MigrationExecutor` موجود عبور می‌کند.

این پلن، بازبینی و اصلاح محدود همان implementation است. هدف تغییر مدل History، طراحی Runner یا بازطراحی Query/Migration نیست؛ هدف مشخص‌کردن این است که مسیرهای مستقیم SQL واقعاً لازم‌اند یا از Builder، AST، Renderer و Executor موجود می‌توان استفاده کرد.

## 1. هدف

به این پرسش با Traceability واقعی پاسخ داده شود:

> آیا System Migration State می‌تواند Queryهای خود را از Query Builder/AST/Renderer و execution path موجود بسازد، و Bootstrap را از Migration infrastructure موجود عبور دهد، بدون اینکه abstraction موازی یا escape hatch غیرضروری ایجاد کند؟

اگر قابلیت معنایی لازم از قبل وجود دارد، همان مسیر بررسی و استفاده شود. اگر بخشی کم است، ابتدا مشخص شود کوچک‌ترین توسعهٔ سازگار در کدام ماژول است. SQL خام یا Builder جدید هیچ‌کدام از پیش برنده فرض نشوند.

## 3. اصول تصمیم‌گیری

```text
قابلیت معنایی موجود و سازگار
        → reuse

قابلیت لازم موجود نیست
        → کمینه‌ترین extension در ماژول مسئول، پس از اثبات نیاز

هیچ semantic fit در معماری موجود وجود ندارد
        → بررسی یک mechanism داخلی محدود با دلیل ثبت‌شده
```

* Internal بودن State به‌تنهایی دلیل کافی برای SQL خام نیست.
* حذف SQL خام به‌تنهایی دلیل کافی برای افزودن abstraction یا تغییر Query Builder نیست.
* `BuiltQuery` خروجی پایین‌دستی execution محسوب می‌شود؛ باید جداگانه مشخص شود ساخت مستقیم آن مورد پشتیبانی معماری است یا bypass لایهٔ AST/Renderer.
* `IQueryExecute` مرز اجرای manager است و به‌خودی‌خود جایگزین Query Builder یا Renderer نیست.
* v1.17 قرارداد History کامل دارد؛ بهینه‌سازی Current Batch نباید migration identityهای لازم برای State/Runner آینده را ناخواسته حذف کند.

## 5. Traceability Work Plan

### 5.1 قابلیت‌های Query Builder

برای SELECT مورد نیاز v1.17 بررسی شود:

```sql
SELECT id, migration, batch
FROM system_migration
ORDER BY id ASC
```

مواردی که باید با API و Renderer واقعی verify شوند:

* انتخاب دقیق ستون‌ها و FROM/table.
* `ORDER BY id ASC` و حفظ ترتیب history.
* quoting identifierها در Dialect فعلی.
* قابلیت render `MAX(batch)` جداگانه بررسی شود؛ وجود این grammar به‌تنهایی به معنی مناسب‌بودن آن برای State contract نیست. `MAX(batch)` ممکن است فقط `currentBatch` را بدهد و history کامل و identityهای migration را بازنگرداند.
* پارامتر/alias semantics و نحوه مصرف `ResultSet` در callback موجود.

برای INSERT نیز بررسی شود آیا Builder موجود می‌تواند این قرارداد را بسازد:

```sql
INSERT INTO system_migration (migration, batch)
VALUES (?, ?)
```

باید binding نوع‌های `String` و `Int`, ترتیب پارامترها، SQL نهایی و مسیر `executeInsert` یا `executeUpdate` در API فعلی دقیقاً trace شوند. متدهای `IQueryRenderInsertApi` در حال حاضر `addValue` را نشان می‌دهد؛ مشخص شود برای ساخت یک ردیف با چند ستون، builder چند بار و با چه semanticsی فراخوانی می‌شود.

### 5.2 جایگاه `BuiltQuery`

در Traceability مشخص شود:

* `BuiltQuery` فقط carrier خروجی Builder است یا قرارداد رسمی raw-SQL نیز محسوب می‌شود؟
* آیا ساخت مستقیم آن در moduleهای داخلی نمونه/precedent معتبر دارد؟
* آیا SELECT/INSERT رشته‌ای از Dialect/Renderer فعلی عبور می‌کنند یا quoting را در Store ثابت می‌کنند؟
* آیا استفادهٔ مستقیم فقط abstraction تولید SQL را bypass می‌کند یا execution/parameter binding را نیز؟

تصمیم باید تفاوت این دو مرز را روشن کند:

```text
Raw SQL string → BuiltQuery → existing manager
```

و:

```text
Query Builder → AST → Dialect Renderer → BuiltQuery → existing manager
```

### 5.3 مسیر Bootstrap و `MigrationExecutor`

گزینه‌ها را با dependency direction و ownership واقعی مقایسه کن:

**گزینه A — مسیر فعلی:**

```text
SystemMigrationStateStore
    → MigrationExecutor
    → existing CREATE TABLE renderer
    → IQueryExecute.executeTable
```

**گزینه B — Builder و execution path پایین‌تر:**

```text
SystemMigrationStateStore
    → existing CREATE TABLE builder/renderer
    → IQueryExecute.executeTable
```

مشخص شود آیا گزینه B واقعاً dependency را حذف می‌کند یا فقط rendering/delegation را دوباره پیاده می‌کند. Executor جدید نساز.

### 5.4 Current State و History

v1.17 contract هم history و identityهای ثبت‌شده را می‌خواهد و هم `currentBatch` را از max batch استخراج می‌کند.

Traceability بررسی کند:

* آیا public/internal State result باید کل `history` را برگرداند یا فقط دادهٔ لازم برای consumer فعلی را؟
* آیا Query Builder می‌تواند همهٔ history را با ordering لازم بسازد؟
* آیا `MAX(batch)` به‌تنهایی contract را نقض می‌کند، چون identityها و state history را حذف می‌کند؟
* آیا full history، order by و max batch را در یک query واحد می‌توان به‌صورت قابل انتقال render کرد، یا محاسبهٔ max در Kotlin برای وضوح contract مناسب‌تر است؟

Contract v1.17 را بی‌دلیل عوض نکن؛ اگر نتیجه نشان داد نیاز واقعی مبهم است، اختلاف را به Decision ثبت کن.

### 5.5 Validation و Duplicate Identity

هر validation با contract mapping بررسی شود:

| Validation فعلی | پرسش Traceability |
|---|---|
| `id > previousId` | آیا ID افزایشی پس از `ORDER BY id` یک invariant قراردادی است یا تکرار تضمین query/DB؟ آیا corruption واقعی را تشخیص می‌دهد؟ |
| identity nonblank | contract v1.17 آن را الزام می‌کند؟ در read و record هر دو کجا باید اعمال شود؟ |
| batch positive | contract v1.17 آن را الزام می‌کند؟ DB constraint لازم است یا Store check کافی است؟ |
| duplicate rows در history | unique constraint با collation واقعی چه semanticsای دارد؟ validation داخلی چه value اضافه می‌کند؟ |
| pre-read پیش از INSERT | آیا unique constraint روی `migration` کفایت می‌کند؟ آیا pre-read فقط round trip اضافه می‌کند؟ race باقی‌مانده چیست؟ |

فرض concurrency همچنان single-runner است. برای حل race، lock یا transaction جدید نساز. رفتار duplicate اگر pre-read حذف شد باید به‌صورت مشخص از DB failure به caller منتقل شود.

### 5.6 Dependency و ماژول‌بندی

dependencyهای `migration:executor` و `query:executor` را trace کن:

* آیا استفاده از Query Builder به dependency مستقیم migration executor → Query builder/API/renderer نیاز دارد؟
* آیا چرخهٔ dependency ایجاد می‌شود؟
* آیا Query executor یا renderer به Migration dependency دارد؟
* آیا reuse `QueryBuilderExecutor` از مرز مسئولیت آن درست است، یا Store باید Builder/Renderer را render و `IQueryExecute` موجود را صدا بزند؟
* dependency فعلی executor به migration builder برای bootstrap بعد از انتقال باقی می‌ماند یا حذف می‌شود؟

dependency فقط برای یک قابلیت semantic اثبات‌شده اضافه یا حذف شود؛ module restructuring در scope نیست.

## 6. Candidate Matrix

حداقل این گزینه‌ها بررسی شوند:

| Candidate | شرح | مواردی که باید سنجیده شود |
|---|---|---|
| A. Query Builder کامل | SELECT و INSERT از Query Builder/AST/Dialect/Renderer و Executor موجود | پوشش واقعی grammar؛ dialect correctness؛ dependency و parameter binding |
| B. Builder برای SELECT، insert پارامتری محدود | query خواندن از builder؛ INSERT از مسیر موجود با پارامترهای bindشده | آیا insert builder کامل/سازگار است؟ اگر نه، کوچک‌ترین دلیل برای raw insert چیست؟ |
| C. SQL رشته‌ای + `BuiltQuery` | مسیر فعلی با manager موجود | آیا Raw SQL قرارداد رسمی و مستند است؟ MySQL quoting ثابت چه اثری روی dialect boundary دارد؟ |
| D. mechanism داخلی محدود جدید | فقط اگر هیچ Builder/executor موجود semantic را پوشش ندهد | کوچک‌ترین abstraction لازم چیست و چرا extension در moduleهای موجود مناسب نیست؟ |

برای هر candidate: مزایا، معایب، dialect boundary، testability، dependency direction، duplication، parameter safety و میزان انطباق با v1.17 contract ثبت شود. قبل از Traceability هیچ‌یک انتخاب نهایی فرض نشود.

## 7. Required Decisions

Traceability باید هر تصمیم زیر را مستند کند:

1. مسیر نهایی SELECT history.
2. مسیر نهایی INSERT history و `executeUpdate` در برابر `executeInsert`.
3. آیا `BuiltQuery` مستقیم در هر query باقی می‌ماند؛ برای هر مورد دلیل مشخص.
4. آیا Query Builder موجود تمام grammar لازم را دارد؛ اگر نه، کمینهٔ capability مفقود.
5. آیا DDL Bootstrap همچنان از `MigrationExecutor` عبور می‌کند.
6. State result history کامل دارد یا contract نیازمند اصلاح است.
7. validationهای `id`, identity و batch که باقی می‌مانند.
8. duplicate handling: pre-read در Store، یا unique constraint و DB error propagation؛ race و round-trip هر دو ثبت شوند.
9. dependencyهای لازم و نبود dependency cycle.
10. test plan واقعی شامل integration DB و regression.

هر تصمیم باید به Repository Evidence و contract clause مربوط در v1.17 لینک شود.

## 8. Test Strategy

### Unit Tests

* Contractهای State/validation که پس از Traceability باقی می‌مانند تست شوند.
* SQL/parameter order فقط در لایهٔ واقعی Query Builder/Renderer تست شود، اگر همان مسیر انتخاب شد.
* تست fake manager باید routing درست به `executeSelect`, `executeUpdate` یا `executeInsert` را ثابت کند.
* تست جدید صرفاً برای افزایش تعداد تست ساخته نشود؛ تست‌هایی که فقط implementation جزئی و حذف‌شده را تثبیت می‌کنند، اصلاح شوند.

### Integration Tests

با database واقعی روی test database اختصاصی، bootstrap، re-bootstrap، empty history، ثبت history، چند migration/batch، duplicate behavior و failure بررسی شوند. Integration test opt-in باشد، دادهٔ موجود را حذف نکند و جدول را فقط اگر خودش ساخته است پاک کند.

### Regression

* `data_base:migration:executor` و `data_base:migration:example`.
* اگر Query Builder/Renderer تغییر کرد، تست‌های `data_base:query` مربوط نیز اجرا شوند.
* هیچ test/example قبلی بدون دلیل حذف نشود.

| T3 | Aggregate API وجود دارد، اما `MySqlQueryColumnCapability` مقدار method را به‌شکل `($columnMethod)` پیشوند می‌کند و سپس column را می‌افزاید؛ برای `max()` حاصل `MAX(batch)` نیست. افزون بر آن، aggregate به‌تنهایی history و identityها را برنمی‌گرداند. بنابراین برای State از MAX استفاده نمی‌شود. |

| T6 | `BuiltQuery` یک carrier پایین‌دستی شامل query و `SqlParameter` است و named placeholderها را به `?` تبدیل می‌کند. در production کد، Query/Migration executorها پس از render آن را می‌سازند؛ `IQueryExecute.getDatabaseServerInfo` و preflightهای موجود `MigrationExecutor` نیز نمونه‌های مستقیم SQL + `BuiltQuery` دارند. پس ساخت مستقیم carrier به‌تنهایی ممنوع/ناممکن نیست، اما SQL مستقیم در Store لایهٔ AST/Renderer و dialect selection را دور می‌زند. |

### 14.2 Interpretation

* Query Builder grammar لازم برای full-history SELECT و parameterized INSERT را دارد؛ در مسیر این Store از Query Executor سطح بالا استفاده نمی‌شود، چون آن executor manager تزریق‌شده را نادیده می‌گیرد.
* مسیر انتخابی `Query Builder → AST → Query Dialect Renderer → BuiltQuery → injected IQueryExecute` است. `BuiltQuery` مستقیم فقط carrier خروجی این مسیر است؛ SQL رشته‌ای مستقیم در Store حذف می‌شود.
* SQL renderer فعلی quote identifiers نمی‌کند. چون identifierهای این Store ثابت، داخلی و نام‌های سادهٔ schema هستند، این limitation نیازمند توسعهٔ عمومی Query renderer نیست. هیچ identifier ورودی مصرف‌کننده از این مسیر عبور نمی‌کند. Test باید SQL واقعی renderشده و execution روی database را پوشش دهد.
* `MAX(batch)` نه برای full-history کافی است و نه renderer فعلی آن را به grammar درست تبدیل می‌کند؛ max در Kotlin حفظ می‌شود.
* INSERT با دو فراخوانی `addValue` ساخته می‌شود و از `executeUpdate` استفاده می‌کند تا affected-row count بررسی شود. خطای unique constraint بدون ترجمهٔ dialect-specific از manager به caller می‌رسد.
* پیش‌خواندن history پیش از هر درج حذف می‌شود: unique constraint قاعدهٔ واقعی collation را اعمال می‌کند، round trip اضافی حذف می‌شود و از pre-checkای که race را نمی‌بندد اجتناب می‌شود. validation duplicate دقیق در خود full-history read باقی می‌ماند تا دادهٔ تکراری موجود به‌عنوان state خراب گزارش شود.
* Bootstrap همچنان از `MigrationExecutor` عبور می‌کند. Query dependencies به migration executor افزوده می‌شوند؛ dependency cycle وجود ندارد. Migration builder/params برای bootstrap باقی می‌مانند.

### 14.3 Candidate Matrix نهایی

| Candidate | نتیجه | دلیل |
|---|---|---|
| A. Query Builder کامل، سپس manager تزریق‌شده | **انتخاب شد، بدون QueryBuilderExecutor** | SELECT و INSERT قابل ساخت‌اند؛ AST/renderer حفظ می‌شود و carrier نهایی از همان `IQueryExecute` تزریق‌شده عبور می‌کند. QueryBuilderExecutor manager تازه می‌سازد، پس برای Store مناسب نیست. |
| B. Builder برای SELECT و raw INSERT | رد شد | INSERT Builder موجود قادر به دو ستون و bound params است؛ raw INSERT مزیت معنایی ندارد. |
| C. raw SQL + BuiltQuery | رد شد برای queryهای State | یک precedent پایین‌دستی وجود دارد، اما SQL ثابت در Store dialect renderer را دور می‌زند و query builder موجود کافی است. |
| D. mechanism داخلی جدید | رد شد | Builder، AST، renderer و manager موجود برای semantics لازم کافی‌اند؛ abstraction جدیدی توجیه ندارد. |

### 14.4 Required Decisions نهایی

1. **SELECT history:** `QueryRenderSelectBuilder` با ستون‌های `id`, `migration`, `batch`، table ثابت `system_migration` و `ORDER BY id ASC`; تمام ردیف‌ها در ResultSet خوانده می‌شوند.
2. **INSERT history:** `QueryRenderInsertBuilder`; دو `addValue` به‌ترتیب `migration`, `batch`; رندر با query dialect جاری؛ اجرای `BuiltQuery` از طریق `IQueryExecute.executeUpdate` و assert یک ردیف متاثر.
3. **BuiltQuery:** در هر دو مسیر فقط پس از AST و renderer ساخته می‌شود؛ SQL دست‌ساز در Store باقی نمی‌ماند.
4. **Query capability:** grammarهای SELECT/ORDER BY/INSERT لازم موجودند. MAX renderer defect ثبت شد اما چون قرارداد full-history است، خارج از اصلاح این نسخه و بدون تغییر Query subsystem می‌ماند.
5. **Bootstrap:** `MigrationExecutor` و `executeTable` حفظ می‌شوند.
6. **State:** کل history و ترتیب id حفظ می‌شود؛ `currentBatch` بیشینهٔ batch در Kotlin است.
7. **Validation:** `id > previousId`, identity غیرخالی، batch مثبت و duplicate identity داخل history باقی می‌مانند. ورودی record پیش از query برای identity خالی و batch غیرمثبت رد می‌شود.
8. **Duplicate write:** SELECT pre-read حذف می‌شود؛ unique index منبع نهایی duplicate/collation است؛ database failure عیناً propagate می‌شود. این کار race را با locking حل نمی‌کند و runner همچنان تک‌اجرا فرض شده است.
9. **Dependencies:** افزودن query `api`, `ast`, `builder`, `dialect`, `renderer` به migration executor؛ `query:executor` استفاده نمی‌شود. هیچ cycle وجود ندارد.
10. **Tests:** unit tests مسیر render‌شده، ترتیب و پارامترهای bind‌شده، عدم استفاده از `executeInsert`, failure propagation، duplicate DB error و validation را پوشش می‌دهند؛ real DB integration الزامی و opt-in است. چون Query subsystem source تغییر نمی‌کند، regressionهای مستقل Query شرط اجرا نیستند.

Traceability پیش از تغییر source تکمیل شد و وضعیت موقت `Implementation Ready` برای اجرای اصلاح حداقلی ثبت شد.
