# Migration v1.9: CREATE MULTI-COLUMN INDEX Contract

وضعیت: `implemented`

## پیش‌شرط و هدف

`v1.6 CREATE INDEX`، `v1.7 DROP INDEX` و `v1.8 CREATE UNIQUE INDEX` پیاده‌سازی شده‌اند. مرحلهٔ بعدی roadmap خانوادهٔ Index، operation مستقل `CREATE MULTI-COLUMN INDEX` است.

هدف، ساخت یک index عادی و نام‌گذاری‌شده روی دو یا چند ستون موجود در یک جدول است. ترتیب ستون‌ها بخشی از معنای index است و باید بدون تغییر از DSL به AST و سپس SQL منتقل شود.

## تصمیم operation و استقلال از نسخه‌های قبلی

API جدید مستقل باشد:

```kotlin
createMultiColumnIndex {
    tableName("users")
    name("idx_users_name_email")
    columns("last_name", "first_name", "email")
}
```

SQL مفهومی:

```sql
CREATE INDEX `idx_users_name_email`
ON `users` (`last_name`, `first_name`, `email`)
```

- `createIndex` در v1.6 دقیقاً تک‌ستونی می‌ماند.
- `createUniqueIndex` در v1.8 دقیقاً تک‌ستونی و unique می‌ماند.
- `dropIndex` در v1.7 بدون تغییر می‌ماند.
- به APIهای قبلی `columns(...)` یا `unique(...)` اضافه نشود.
- Multi-column Unique Index خارج از scope است و در صورت نیاز contract/version مستقل می‌خواهد.

پیش از implementation، کد واقعی عملیات CREATE INDEX و مسیر manager/executor دوباره بررسی شود؛ ساختار پیشنهادی این plan نباید repository را مجبور به ساخت hierarchy جدید کند.

- API و AST مستقل، package operation-specific و هماهنگ با convention واقعی repository داشته باشند.
- trace شود که Builderهای v1.6/v1.8 مقادیر را چگونه trim، validate و در AST نگهداری می‌کنند؛ casing و محتوای identifierها نباید دستکاری شود.
- registration capability جدید در renderer registry موجود `MySqlDialect` انجام شود؛ از identifier quoting/escaping واقعی MySQL renderer استفاده شود.
- executor موجود و `IQueryExecute.executeTable` reuse شوند. production abstraction یا executor جدید صرفاً برای این operation ساخته نشود.
- fake تست در مرز موجود `IQueryExecute` قرار گیرد.
- dependency direction حفظ شود: AST/Builder از execution مستقل بمانند؛ dialect/renderer به manager، connection، introspection یا JDBC وابسته نشوند.
- وضعیت plan مشترک v1.2 و dependency واقعی آن بررسی شود؛ ترتیب عدد نسخه‌ها به‌تنهایی dependency نیست.
- compatibility target کلی MySQL در repository بررسی شود. اگر تعیین نشده، همین را به‌عنوان finding ثبت کنید؛ نسخهٔ محیط محلی مبنای ادعای سازگاری نباشد.
- grammar با MySQL Reference Manual، بخش `CREATE INDEX Statement` تطبیق داده شود. MySQL 8.0 grammar چند `key_part` در `ON tbl_name (key_part,...)` دارد و Multiple-Column Index توضیح می‌دهد که ترتیب ستون‌ها در استفاده از index اهمیت دارد. مستند InnoDB در MySQL 8.0 حداکثر ۱۶ key part را ذکر می‌کند؛ این محدودیت سرور/storage engine است و نباید به سقف مصنوعی در API تبدیل شود.
- MySQL 8.0 Reference Manual، بخش `Identifier Case Sensitivity` می‌گوید نام columnها در MySQL case-insensitive هستند؛ همین رفتار مبنای duplicate guard است، درحالی‌که casing ورودی در AST حفظ می‌شود.

## محدوده

در v1.9:

- MySQL تنها dialect پشتیبانی‌شده.
- index عادی (non-unique) روی یک جدول و **حداقل دو ستون**.
- تعداد ورودی‌های DSL سقف مصنوعی در library نداشته باشد؛ MySQL و storage engine محدودیت واقعی تعداد/طول key part و type را اعمال می‌کنند و خطای آن‌ها به caller می‌رسد.
- نام جدول و نام index اجباری و صریح‌اند.
- نام ستون‌ها به‌صورت ordered collection دریافت می‌شوند؛ ترتیب آرگومان‌های آخرین فراخوانی `columns(...)` حفظ می‌شود.
- API مفهومی:

```text
createMultiColumnIndex {
    tableName(table)
    name(index)
    columns(column1, column2, ...)
}
```

- هر فراخوانی `columns(...)` فهرست ستون‌های قبلی را به‌طور کامل جایگزین می‌کند. ترتیب `columnNames` دقیقاً ترتیب آرگومان‌های آخرین فراخوانی `columns(...)` است؛ آرگومان‌های فراخوانی‌های قبلی باقی نمی‌مانند.
- API، AST، Builder، MySQL capability/renderer و مثال operation-specific باشند.
- execution فقط از executor و `IQueryExecute.executeTable` موجود عبور کند.
- مثال versioned render-only باشد؛ اجرای DDL تنها با opt-in صریح فعال شود.

خارج از محدوده:

- تغییر API، AST یا renderer نسخه‌های v1.6/v1.7/v1.8.
- `UNIQUE`, `FULLTEXT`, `SPATIAL`, `PRIMARY KEY` و UNIQUE constraint.
- auto-generated index name، `IF NOT EXISTS` یا introspection/preflight.
- prefix length، expression/functional index، ترتیب ASC/DESC، visibility و هر index/dialect option.
- سایر dialectها، rollback، migration history و runner.

## Contract مربوط به DSL، AST و validation

AST مستقل و معنایی:

```text
CreateMultiColumnIndexAst
├── tableName: String?
├── indexName: String?
└── columnNames: List<String>?
```

Invariants:

- `tableName` و `indexName` پس از trim غیرخالی‌اند.
- هر مقدار ستون پس از trim غیرخالی است؛ فهرست خالی، تک‌ستونی و مقدار blank رد می‌شوند.
- Builder فقط whitespace پیرامونی را حذف می‌کند؛ casing و بقیهٔ محتوای identifierها را تغییر نمی‌دهد.
- هر فراخوانی `columns(...)` کل فهرست قبلی را جایگزین می‌کند؛ ترتیب `columnNames` دقیقاً ترتیب آرگومان‌های آخرین فراخوانی `columns(...)` است و AST آن را بدون sort یا reorder نگه می‌دارد.
- **Duplicate policy:** Builder تکرار نام ستون را پس از trim با مقایسهٔ case-insensitive رد می‌کند؛ برای نمونه `columns("email", " EMAIL ")` رد می‌شود. این مقایسه فقط برای validation است: spelling اصلی مقادیر معتبر در AST حفظ می‌شود؛ برای نمونه `columns("Email", "UserName")` در AST دقیقاً `["Email", "UserName"]` نگه می‌دارد. هیچ lower-case/normalization روی مقدار ذخیره‌شده انجام نمی‌شود.
- Renderer همان validation را دفاعی روی AST مستقیم نیز انجام می‌دهد، پیش از quote کردن identifierها یا ساخت SQL.
- AST/API حالت unique ندارند؛ این operation همیشه index عادی می‌سازد.
- هیچ identifier به bind parameter تبدیل نشود؛ همه با quoting/escaping MySQL وارد SQL می‌شوند و raw SQL fragment پذیرفته نیست.

## قرارداد Renderer

SQL دقیق:

```sql
CREATE INDEX <quoted-index-name>
ON <quoted-table-name> (<quoted-column-1>, <quoted-column-2>, ...)
```

- index name، table name و تک‌تک column nameها با convention فعلی MySQL renderer quote و escape شوند.
- فقط فهرست trim‌شدهٔ معتبر render شود؛ ستون‌ها با `, ` جدا شوند.
- renderer ترتیب را تغییر ندهد، ستون اضافه/حذف نکند و `UNIQUE` اضافه نکند.
- `IF NOT EXISTS`، `ALTER TABLE` جایگزین، prefix، expression و هیچ option خارج scope تولید نشود.
- Renderer فقط AST/config لازم برای rendering را بخواند؛ به manager، connection، executor یا JDBC دسترسی نداشته باشد و metadata نخواند.
- وجود جدول/ستون، محدودیت‌های engine، سقف تعداد key part، طول index key و سایر legalityهای DB در MySQL اعتبارسنجی شوند؛ renderer آن‌ها را introspect یا پیش‌بینی نکند.

## Executor و خطا

- فقط entry point/overload لازم در `IMigrationExecutor` موجود اضافه شود؛ `MigrationExecutor` مسیر `executeOut` را طی کند.
- SQL از `IQueryExecute.executeTable` موجود اجرا شود.
- success و failure manager با cause اصلی به callback برسد؛ duplicate index/table/column، محدودیت engine و permission failure به success/no-op تبدیل نشوند.
- هیچ `SHOW INDEX`، metadata lookup یا query جانبی برای preflight اجرا نشود.
- fake تست باید ثابت کند هیچ `executeSelect`/preflightی رخ نمی‌دهد.

## مثال و تست

Unit testهای بدون DB حداقل این موارد را پوشش دهند:

- ساخت AST مستقل با فقط table، index name و ordered column list.
- دو ستون حداقل معتبر؛ صفر/یک ستون و مقدار خالی/blank رد شوند.
- تعداد بیش از دو ستون بدون سقف مصنوعی library پذیرفته شود؛ تست عدد خاصی را به‌عنوان maximum library تعریف نکند.
- trim پیرامونی و حفظ casing برای table/index/هر ستون در AST و SQL.
- duplicate column پس از trim و case-insensitive بودن رد شود؛ مقدارهای AST در موارد معتبر casing اصلی را حفظ کنند.
- `columns("email", " EMAIL ")` به‌علت duplicate رد شود، اما `columns("Email", "UserName")` پذیرفته شود و AST دقیقاً `["Email", "UserName"]` را نگه دارد.
- AST ناقص یا دارای blank/duplicate columns که مستقیماً به renderer داده شده، قبل از SQL generation رد شود.
- تست ترتیب: `columns("last_name", "first_name", "email")` دقیقاً همین توالی را در SQL داشته باشد؛ فهرست معکوس SQL متفاوت تولید کند.
- تست replacement: پس از `columns("last_name", "first_name")`، فراخوانی `columns("email", "age")` فقط `email, age` را نگه دارد؛ SQL هم دقیقاً همین ترتیب را داشته باشد.
- SQL دقیق non-unique `CREATE INDEX ... ON ... (...)` و عدم وجود `UNIQUE`, `IF NOT EXISTS`, `ALTER TABLE` و bind parameters.
- reserved word و backtick داخلی در index/table و هر جای فهرست ستون quote/escape شوند.
- ترتیب setterهای `tableName`, `name` و `columns` در صورت یکسان بودن مقادیر نهایی SQL را تغییر ندهد؛ برای چند فراخوانی `columns(...)` فقط آخرین فهرست ملاک است و ترتیب داخل همان فهرست مؤثر باقی می‌ماند.
- executor fake ارسال BuiltQuery از `IQueryExecute.executeTable`، success callback و حفظ exception/cause را بررسی کند؛ select/preflight غیرمنتظره fail شود.
- regressionهای example/executor برای v1.6، v1.7 و v1.8 حفظ و اجرا شوند.

Integration test اختیاری و خارج از prerequisite اجرای معمول تست‌هاست؛ اگر اضافه شد، فقط روی MySQL اختصاصی و قابل reset اجرا شود و از metadata دیتابیس ثابت کند ترتیب ستون‌های index ساخته‌شده همان ترتیب declaration است. مثال عادی render-only بماند و DDL را خودکار اجرا نکند.
