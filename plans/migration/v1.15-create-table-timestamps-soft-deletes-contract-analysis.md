# Migration v1.15: تحلیل قرارداد `timestamps` و `softDeletes` در `CREATE TABLE`

## وضعیت

`Implemented`

---

## 1. هدف

بررسی و تعیین قرارداد API/AST/Builder/Renderer برای shorthandهای رایج در `CREATE TABLE`:

```kotlin
timestamps()
softDeletes()
```

هدف، ارزیابی پشتیبانی از الگوهای قراردادی متداول و آشنا برای کاربران Laravel است، بدون وابستگی به Laravel و بدون افزودن abstraction غیرضروری.

این مرحله فقط **Traceability و Contract Analysis** است و شامل implementation نیست. قرارداد نهایی با dependency بسته‌شدهٔ v1.16 در بخش 14 ثبت شده است.

---

## 2. Scope

### داخل Scope

Traceability باید موارد زیر را بررسی و درباره‌شان تصمیم مستند ارائه کند:

* معنای schemaای `timestamps()` و `softDeletes()` در `CREATE TABLE`
* نام و تعداد ستون‌هایی که هر shorthand تعریف می‌کند
* نوع دادهٔ هر ستون و پشتیبانی آن در data typeهای فعلی migration
* nullability و رفتار default هر ستون
* ترتیب ستون‌های حاصل نسبت به ستون‌های دستی و سایر اجزای `CREATE TABLE`
* استفادهٔ همزمان از `timestamps()` و `softDeletes()`
* رفتار در صورت تعریف دستی ستونی با همان نام
* رفتار در صورت فراخوانی تکراری هر shorthand
* جایگاه و قرارداد فراخوانی shorthandها در DSL فعلی
* نمایش در AST، از جمله اینکه shorthand هنگام ساخت AST به تعریف ستون‌های فعلی گسترش یابد یا به‌صورت node جداگانه نگهداری شود
* مسئولیت Builder، AST و Renderer و مرزهای validation
* سازگاری با مدل و رفتار فعلی `CREATE TABLE`
* تفاوت‌های مرتبط dialectها و compatibility target اعلام‌شدهٔ repository
* نیازهای تست، regression، example و مستندات برای مرحلهٔ implementation بعدی

### خارج از Scope

موارد زیر بخشی از این قابلیت نیستند و نباید در قرارداد v1.15 وارد شوند:

* مقداردهی خودکار `created_at` هنگام `INSERT`
* به‌روزرسانی خودکار `updated_at` هنگام `UPDATE`
* رفتار soft delete هنگام `DELETE`
* Query Builder soft-delete behavior یا global scope
* restore و بازیابی رکوردهای soft-deleted
* model lifecycle hooks یا ORM behavior
* مدیریت timezone یا تبدیل timezone
* trigger یا هر رفتار خودکار سمت database برای تغییر مقدارها
* migration history، version tracking یا migration runner
* تغییر معنای operationهای مستقل قبلی برای شبیه‌سازی رفتار ORM

در این نسخه shorthandها، در صورت تأیید Traceability، فقط تعریف ستون در schema هستند.

## 3. اصول Traceability

1. کد و قرارداد واقعی repository مرجع تصمیم‌گیری دربارهٔ الگوی API، AST، Builder، Renderer، validation و ترتیب SQL است.
2. مثال‌های Laravel فقط می‌توانند مرجع آشنایی اصطلاحات باشند؛ Laravel dependency یا مرجع تعیین رفتار dialect دیتابیس نیست.
3. نوع داده، nullability و default را از روی نام‌هایی مانند `timestamps` یا `softDeletes` حدس نزن. هر تصمیم باید به convention فعلی repository، نیاز قراردادی پروژه یا منبع رسمی dialect متصل باشد.
4. نسخهٔ نصب‌شدهٔ دیتابیس توسعه‌دهنده، به‌تنهایی compatibility target رسمی repository را تعیین نمی‌کند. اگر target در repository مشخص نیست، آن را به‌عنوان finding ثبت کن.
5. در این مرحله source code، tests، examples و مستندات موجود را تغییر نده؛ فقط همین plan را با شواهد و نتیجهٔ Traceability به‌روز کن.
6. abstraction مشترک یا عمومی برای timestamp، soft delete یا column shorthand صرفاً برای استفادهٔ احتمالی آینده پیشنهاد یا ایجاد نکن.

## 4. Repository Traceability

منابع repository زیر را بررسی و مسیرها و شواهد واقعی را در نتیجه ثبت کن:

### 4.1 `CREATE TABLE`

* API و DSL فعلی ساخت جدول
* AST ساخت جدول و تعریف ستون
* Builder و ترتیب جمع‌آوری ستون‌ها و table-level definitionها
* validation فعلی برای نام‌ها، تکرار تعریف‌ها و ورودی ناقص
* rendererهای dialect و ترتیب قطعات SQL
* مکانیزم ثبت capabilityها و rendererها
* exampleهای versioned و convention اجرای render-only در برابر اجرای صریح

### 4.2 Column Definition

* data typeهای قابل استفاده در migration `CREATE TABLE`
* مدل فعلی nullability
* تفاوت omitted default، `DEFAULT NULL` و مقدار default، در صورت پشتیبانی
* ترتیب ثابت rendering برای type، nullability، default، auto increment و سایر attributeهای موجود
* امکان ساخت چند column definition در یک `CREATE TABLE` بدون افزودن semantics جدید به columnهای مستقل

### 4.3 Compatibility و Dialect

* dialectهای واقعاً موجود و registration آن‌ها
* رابطهٔ inheritance و رفتار فعلی `MySqlDialect` و `MariaDbDialect`
* target سازگاری اعلام‌شدهٔ پروژه، اگر وجود دارد
* اینکه shorthandها باید برای کدام dialectها قابل استفاده باشند یا آیا فعلاً محدود به dialect مشخصی هستند

هیچ dialectی را صرفاً به علت شباهت syntax یا inheritance به‌طور ضمنی پشتیبانی‌شده اعلام نکن.

## 5. پرسش‌های قراردادی که باید پاسخ داده شوند

### 5.1 معنای هر shorthand

برای هر shorthand دقیقاً مشخص کن چه column definitionهایی تولید می‌شوند. موارد زیر باید صریحاً تعیین شوند و تا پایان Traceability فرض‌شده نیستند:

* `timestamps()` شامل کدام نام‌های ستون است و ترتیب آن‌ها چیست؟
* `softDeletes()` چه نامی برای ستون تولید می‌کند؟
* آیا هر shorthand دقیقاً یک یا چند column definition معمولی را به `CREATE TABLE` اضافه می‌کند؟
* آیا shorthandها صرفاً sugar برای columnهای موجودند یا semantic جداگانه‌ای دارند؟

Candidateهای نام‌گذاری مانند `created_at`, `updated_at` و `deleted_at` را فقط پس از ثبت مبنا نهایی کن.

### 5.2 نوع داده، nullability و default

برای هر ستون، contract باید جداگانه مشخص کند:

* data type دقیق و نگاشت آن به typeهای فعلی migration
* nullable یا not-null بودن
* default state دقیق: بدون default clause، `DEFAULT NULL` یا مقدار مشخص
* اینکه shorthand timestamp با data type موجود repository قابل نمایش است یا type جدیدی لازم می‌شود
* اینکه نوع یا default انتخابی database-specific است یا می‌تواند در قرارداد فعلی dialectها مشترک باشد

از تعیین خودکار `CURRENT_TIMESTAMP`، `ON UPDATE CURRENT_TIMESTAMP`، نوع `TIMESTAMP`/`DATETIME` یا default دیگری بدون evidence و تصمیم قراردادی خودداری کن.

### 5.3 تعامل با تعریف دستی

رفتار این حالت‌ها را مشخص کن:

* کاربر قبل یا بعد از `timestamps()` یکی از ستون‌های متناظر را دستی تعریف کند.
* کاربر پیش یا پس از `softDeletes()` ستون متناظر را دستی تعریف کند.
* فقط بخشی از ستون‌هایی که یک shorthand می‌افزاید دستی تعریف شده باشند.
* نام یکسان با تفاوت در casing یا whitespace ارائه شود.

برای هر حالت یکی از رفتارهای صریح را انتخاب و مستند کن، مانند رد ورودی تکراری در Builder، رد AST ناقص/متناقض در Renderer، یا رفتار دیگری که با invariantهای فعلی repository سازگار باشد. تعریف خاموش، جایگزینی بی‌خبر یا حذف بی‌خبر column دستی را مفروض نگیر.

### 5.4 فراخوانی تکراری و ترتیب

رفتار فراخوانی بیش از یک‌بار هر shorthand باید مشخص شود. همچنین مشخص کن:

* آیا shorthand‌ها فقط در بدنهٔ `createTable` قابل فراخوانی‌اند؟
* آیا ترتیب فراخوانی shorthandها و `addColumn` ترتیب ستون‌های SQL را تعیین می‌کند؟
* آیا هر shorthand فقط یک بار مجاز است؟
* اگر Builder برای setterها یا collectionها convention مشخصی دارد، shorthand جدید چگونه با آن سازگار می‌شود؟

SQL نهایی نباید به‌طور ناخواسته به ترتیب فراخوانی attributeهای یک column وابسته شود؛ ولی ترتیب تعریف خود columnها باید طبق convention واقعی `CREATE TABLE` تعیین شود.

### 5.5 API، AST و Builder

Candidate API برای تحلیل:

```kotlin
createTable("users") {
    timestamps()
    softDeletes()
}
```

این فقط candidate است. Traceability باید تعیین کند:

* آیا این محل با DSL فعلی سازگار است؟
* آیا shorthandها در Builder به columnهای موجود expand می‌شوند؟
* اگر AST مستقل لازم است، چه invariantی را حفظ می‌کند که expansion در Builder نتواند؟
* چگونه AST مستقیم و ناقص به شکل defensive اعتبارسنجی می‌شود؟
* چگونه ترتیب و تشخیص collision در Builder و Renderer حفظ می‌شود؟

AST باید فقط اطلاعات لازم برای تولید schema را نگه دارد. هیچ state مربوط به lifecycle مدل، clock، timezone، insert/update/delete، restore یا trigger به AST وارد نشود.

### 5.6 Renderer و SQL

* از مسیر فعلی renderer و convention رندر column definition استفاده شود، اگر semantics را حفظ می‌کند.
* renderer باید ورودی malformed یا state نامعتبر را مطابق مرز validation فعلی به‌صورت defensive رد کند.
* shorthandها نباید باعث introspection، اتصال به دیتابیس یا `executeSelect` شوند.
* خروجی هر shorthand و ترکیب آن‌ها باید با SQL دقیق و ترتیب مشخص در contract نهایی ثبت شود.
* renderer نباید مقدار timestamp را در زمان اجرا تولید یا به‌روزرسانی کند؛ scope این مرحله فقط DDL ساخت جدول است.

* محصول و dialect مورد بررسی

## 7. Candidate Contract — هنوز نهایی نیست

نمونهٔ زیر فقط برای ملموس‌کردن سؤال‌های Traceability است و contract نهایی محسوب نمی‌شود:

```kotlin
createTable("users") {
    addColumn {
        name("id")
        dataType(IntType())
        autoIncrement()
        primary()
    }

    timestamps()
    softDeletes()
}
```

Traceability باید پیش از تغییر وضعیت plan، برای هر shorthand این خروجی‌ها را تعیین کند:

```text
timestamps()
└── ستون‌ها و attributeهای دقیق: [Traceability تعیین کند]

softDeletes()
└── ستون و attributeهای دقیق: [Traceability تعیین کند]
```

هیچ SQL قطعی برای نمونهٔ بالا در این plan ادعا نمی‌شود تا type، nullability، default، naming و ordering بررسی و بسته شوند.

* SQL دقیق `timestamps()` و `softDeletes()` به‌صورت جداگانه
* SQL دقیق استفادهٔ همزمان
* ترتیب ستون‌ها
* type، nullability و default هر ستون
* رفتار collision با column دستی
* رفتار فراخوانی تکراری shorthandها
* trim/casing نام‌های دستی در تعامل با collision detection
* validation ورودی‌های ناقص و AST مستقیم، در صورت وجود AST مستقل
* regression برای `CREATE TABLE` و columnها/constraintهای موجود
* example versioned مطابق convention جاری و render-only بودن پیش‌فرض؛ اجرای واقعی DDL فقط با opt-in صریح

Integration test دیتابیس، اگر لازم تشخیص داده شود، نباید prerequisite اجرای عادی unit testها شود.

## 9. محدودیت‌های معماری

* هیچ رفتار ORM یا lifecycle به `CREATE TABLE` اضافه نشود.
* shorthandها در صورت پذیرش، باید در نهایت به schema column definitionهای قابل‌فهم تبدیل شوند.
* جهت dependency فعلی حفظ شود: API/AST/Builder به executor یا manager وابسته نشوند؛ renderer به اتصال یا manager دسترسی نداشته باشد؛ executor از مسیر manager موجود استفاده کند.
* abstraction عمومی برای `TimestampColumns`, `SoftDeleteColumn`, `TemporalColumn`, `ColumnPreset` یا مشابه آن صرفاً برای این دو shorthand ایجاد نشود، مگر Traceability وجود یک الگوی واقعی و بالفعل repository را اثبات کند.
* operationهای `CREATE TABLE` و migrationهای مستقل قبلی از نظر semantics تغییر نکنند.
* این plan خود را بر ساختار واقعی repository منطبق می‌کند؛ برای تطبیق با سند package hierarchy تازه نساز.

### Repository Evidence

* `IMigrationRenderCreateTableApi` در `data_base/migration/api/.../create_table/render_migration_create_table/` فقط `table`, `addColumn`, table-level definitions و `ifNotExists` را عرضه می‌کند؛ shorthand زمانی وجود ندارد.
* `IMigrationRenderCreateTableAst` در `data_base/migration/ast/.../create_table/render_migration_create_table/` فهرست مرتب `columns` و `definitions` را نگه می‌دارد. Column shorthand مستقلی در AST لازم نیست اگر در Builder به column ASTهای عادی expand شود.
* `IMigrationColumnAst` فقط name، `MigrationColumnDataType?`، default همراه `hasColumnDefault`، nullable، auto increment و primary را نگه می‌دارد.
* پس از implementation v1.16، sealed `MigrationColumnDataType` شامل `DateType`, `TimeType`, `DateTimeType`, `TimestampType` نیز هست؛ shorthand این contract از `DateTimeType()` استفاده می‌کند.
* `MigrationColumnBuilder` نام را trim می‌کند و nullable/default/type state را روی column AST می‌گذارد. Default omission از `default(null)` با `hasColumnDefault` جدا است.
* `MySqlMigrationColumnCapability` همواره `NULL` یا `NOT NULL` را صریح render می‌کند و mapping نوع‌های v1.16 را دارد. `MySqlMigrationRenderCreateTableCapability` در وضعیت فعلی نام columnها را با مقایسهٔ case-sensitive duplicate می‌سنجد.
* `MySqlMigrationModifyColumnCapability` mapping مستقل typeها را دارد؛ v1.16 هر چهار temporal type را در آن و در shared column renderer پوشش می‌دهد. `ADD COLUMN` از shared column renderer استفاده می‌کند.
* `MigrationRenderCreateTableBuilder` columnها را به ترتیب فراخوانی به فهرست اضافه می‌کند. Renderer تمام columnها را با همان ترتیب پیش از table-level definitions می‌نویسد.
* `MySqlDialect` registry فعلی را برای CREATE TABLE و column rendering دارد. `MariaDbDialect` از آن ارث می‌برد و در حال حاضر همان ثبت rendererها را به‌کار می‌برد.
* exampleهای `A1ExampleCreateTableV1` و `A1ExampleCreateTableConstraintsV1` در `data_base/migration/example/src/main/kotlin/v1/migrations/create_table...` برای columnها از `addColumn` استفاده می‌کنند. Manager، exampleها را versioned ثبت می‌کند و الگوی فعلی اجرای example render-first است؛ opt-in اجرا از مسیر manager کنترل می‌شود.
* `MigrationExecutor` برای CREATE TABLE از مسیر `IQueryExecute.executeTable` استفاده می‌کند؛ shorthand به مسیر executor یا `executeSelect` نیاز ندارد.
* قرارداد rendererهای مستقل نیز SQL/AST را از execution جدا نگه می‌دارد؛ shorthandها در Builder/AST باید فقط schema definition بسازند.

### Database and Framework Evidence

* Laravel 12.x Schema Builder API فقط contextual evidence است: `timestamps()` و `softDeletes()` متداول‌اند و nullable timestamp definitions را نشان می‌دهد. Laravel مبنای انتخاب temporal type این قرارداد نیست.
* v1.16 تصمیم گرفته است `DATETIME` و `TIMESTAMP` typeهای مستقل باشند. MySQL 8.4 Reference Manual می‌گوید TIMESTAMP از session time zone به UTC تبدیل و هنگام خواندن تبدیل معکوس می‌شود؛ DATETIME این تبدیل را ندارد. MySQL TIMESTAMP range را تا 2038 مستند می‌کند، در حالی DATETIME range گسترده‌تری دارد.
* MySQL و MariaDB برای `TIMESTAMP` در بعضی نسخه‌ها یا configurationها رفتارهای implicit default/automatic update دارند. چون contract به هیچ server/session behavior وابسته نیست، shorthand از DATETIME استفاده می‌کند و default clause یا `ON UPDATE` تولید نمی‌کند.
* MariaDB Oracle mode، DATE دارای time portion را synonym برای DATETIME می‌گیرد؛ v1.15 مستقیماً DATETIME تولید می‌کند و SQL mode را model نمی‌کند.
* رفتار فعلی repository: `MySqlMigrationRenderCreateTableCapability` نام ستون‌های duplicate را با مقایسهٔ case-sensitive تشخیص می‌دهد؛ Builder فعلی نیز duplicate columnها را پیش از render رد نمی‌کند.
* MySQL 8.4 و MariaDB مستند می‌کنند که column identifierها از نظر lookup case-insensitive هستند. برای جلوگیری از SQLای که دو نام ظاهراً متفاوت اما غیرقابل تمایز می‌سازد، v1.15 duplicate نام column را پس از trim و با مقایسهٔ case-insensitive رد می‌کند؛ این tightening عمومی CREATE TABLE صریحاً در contract ثبت می‌شود.
* جست‌وجوی build، source، documentation و planهای قبلی compatibility target/minimum supported version عمومی برای MySQL یا MariaDB پیدا نکرد. target version موجود در config برای انتخاب syntax برخی operationهاست و baseline عمومی پروژه محسوب نمی‌شود.

### نتیجهٔ تصمیم‌ها

* `timestamps()` به‌ترتیب `created_at`, سپس `updated_at` اضافه می‌کند.
* `softDeletes()` ستون `deleted_at` را اضافه می‌کند.
* type هر سه ستون `DateTimeType()` است؛ precision در API shorthand وجود ندارد و SQL type به صورت `DATETIME` render می‌شود (precision پیش‌فرض SQL برابر صفر است).
* هر سه ستون nullable و بدون default clause هستند: `created_at DATETIME NULL`, `updated_at DATETIME NULL`, `deleted_at DATETIME NULL`.
* انتخاب DATETIME از اختلاف معنایی واقعی با TIMESTAMP می‌آید: shorthand schema-only است، timezone/session management ندارد، نمی‌خواهد runtime instant را به UTC تبدیل کند و range تاریخی TIMESTAMP MySQL را تحمیل نمی‌کند. این choice ادعای timezone handling برای application ایجاد نمی‌کند.
* هیچ `CURRENT_TIMESTAMP`, `ON UPDATE CURRENT_TIMESTAMP`, trigger یا مقدار runtime تولید نمی‌شود. `updated_at` فقط یک nullable column است؛ update behavior خارج از migration contract می‌ماند.
* API بدون آرگومان است؛ precision و نام سفارشی columnها scope نیستند.
* shorthandها در Builder به column ASTهای معمولی expand می‌شوند؛ AST node مستقل یا shorthand metadata لازم نیست.
* duplicate detection برای تمام columnهای یک CREATE TABLE پس از trim به‌صورت case-insensitive انجام می‌شود. این تغییر با رفتار فعلی case-sensitive متفاوت است و به‌عنوان compatibility tightening صریحاً پذیرفته شده؛ casing/spelling اصلی حفظ می‌شود.
* collision دستی با نام shorthand در هر casing رد می‌شود. فراخوانی تکراری shorthand نیز به‌دلیل تولید نام تکراری رد می‌شود.
* ستون‌های ساخته‌شده در محل فراخوانی shorthand به ترتیب ثبت‌شده درج می‌شوند؛ ترتیب داخلی `timestamps()` ثابت و `created_at` سپس `updated_at` است.
* Builder و Renderer هر دو duplicateهای case-insensitive را رد می‌کنند؛ Renderer این invariant را برای AST مستقیم نیز اعمال می‌کند.
* رفتار SQL در MySQL و MariaDB از registration مشترک فعلی استفاده می‌کند؛ هر دو dialect، mapping `DATETIME` از v1.16 را دارند. Compatibility target عمومی repository همچنان نامشخص است و minimum کلی ادعا نمی‌شود.

## 13. قرارداد shorthand و تصمیم باز دربارهٔ Temporal Data Types

### 13.1 DSL

```kotlin
createTable {
    table { tableName("users") }

    addColumn {
        name("id")
        dataType(IntType())
        notNull()
        autoIncrement()
        primaryKey()
    }

    timestamps()
    softDeletes()
}
```

`timestamps()` و `softDeletes()` بدون آرگومان هستند. نام قابل تنظیم، precision قابل تنظیم و aliasهایی مثل `nullableTimestamps()` در v1.15 اضافه نمی‌شوند.

### 13.2 Expansion و semantics

```text
timestamps()
├── created_at DATETIME NULL
└── updated_at DATETIME NULL

softDeletes()
└── deleted_at DATETIME NULL
```

هر سه column nullable هستند و default clause ندارند. SQL fragmentهایشان به‌ترتیب `\`created_at\` DATETIME NULL`, `\`updated_at\` DATETIME NULL` و `\`deleted_at\` DATETIME NULL` است. ترتیب نام‌ها با ترتیب DSL و column list فعلی حفظ می‌شود؛ در نمونهٔ بالا `id`, `created_at`, `updated_at`, `deleted_at` است.

### 13.3 مرز Temporal Data Types

* v1.16 چهار temporal type عمومی را افزوده و در CREATE/ADD/MODIFY پشتیبانی می‌کند؛ v1.15 از `DateTimeType()` استفاده می‌کند.
* precision و default behavior از shorthand حذف‌اند: precision `DATETIME` omitted و معادل FSP صفر است؛ default clause اصلاً تولید نمی‌شود.
* نوع timestamp-type انتخاب نمی‌شود: `TIMESTAMP` در MySQL/MariaDB session-zone conversion و range/version اختلاف دارد؛ shorthandهای schema-only برای این semantics پیکربندی یا ضمانتی ندارند.

### 13.4 Validation و برخوردها

* رفتار فعلی repository case-sensitive است. پیشنهاد v1.15، duplicate detection case-insensitive برای تمام columnهای یک `CREATE TABLE` است؛ این validation tightening مستقل از وجود shorthand است و باید به‌صورت تغییر قراردادی صریح ثبت شود.
* این policy از identifier storage/rendering جداست: ورودی پس از trim با casing/spelling خودش نگه داشته و render می‌شود؛ مقایسهٔ case-insensitive فقط برای validation است.
* بر این اساس collision دستی با `created_at`, `updated_at`, یا `deleted_at` در هر casing رد می‌شود.
* فراخوانی دوبارهٔ هر shorthand همان column names را تولید می‌کند و به‌عنوان duplicate رد می‌شود.
* Builder در نقطهٔ ورود shorthand و در addColumnهای بعدی نام‌های trim‌شده را با تمامی نام‌های موجود مقایسه می‌کند؛ case-insensitive collision رد می‌شود.
* Renderer duplicate check را برای AST کامل و مستقیم نیز case-insensitive انجام می‌دهد؛ این رفتار عمومی CREATE TABLE tightening است و نه metadata ویژهٔ shorthand.
* هیچ schema introspection یا preflight اجرا نمی‌شود.

### 13.5 رفتار خارج از قرارداد

این shorthandها فقط column definition می‌سازند. هیچ منطق INSERT/UPDATE/DELETE، ORM, query scope, restore, trigger, timezone conversion یا مقداردهی خودکار اضافه نمی‌شود. دیتابیس همچنان مسئول اعتبارسنجی SQL و محدودیت‌های server/storage است.

### 13.6 Dialect و compatibility

* مسیر فعلی MySQL renderer و registry حفظ می‌شود.
* MariaDB از registration مشترک فعلی و SQL یکسان `DATETIME NULL` استفاده می‌کند؛ این انتخاب به معنی پشتیبانی از modeهای اختصاصی یا timezone behavior یکسان نیست.
* compatibility target عمومی MySQL/MariaDB در repository یافت نشد و همچنان finding است؛ حداقل نسخهٔ کلی اعلام نمی‌شود.
* نسخهٔ نصب‌شدهٔ local معیار compatibility نیست.

### 13.7 نیازهای implementation بعدی

* API مستقل shorthandها به `IMigrationRenderCreateTableApi` و Builder اضافه شود.
* AST table-level جدید نساز؛ shorthandها را به column ASTهای معمولی expand کن.
* قبل از implementation v1.15، contract مستقل Temporal Data Types تعیین کند آیا type عمومی لازم است؛ در صورت تصویب، mappingهای CREATE/ADD/MODIFY همگی پوشش داده شوند.

1. آیا temporal data types قابلیت عمومی Migration باشند؟

## 14. Final Contract پس از v1.16 Traceability

### تصمیم نهایی type

از `DateTimeType()` برای هر سه column استفاده شود. دلایل: DATETIME برخلاف TIMESTAMP مقدار را با session time zone به UTC تبدیل نمی‌کند، range مستند MySQL آن بسیار گسترده‌تر است، و از implicit TIMESTAMP default/auto-update rules دور می‌ماند. کتابخانه timezone را مدیریت نمی‌کند؛ معنای wall-clock DATETIME را هم به UTC instant تبدیل یا تفسیر نمی‌کند. این انتخاب برای schema-only shorthand است، نه تضمین semantics runtime بین برنامه‌ها.

v1.16 API نوع‌های `DateTimeType(precision: Int? = null)` را دارد؛ shorthand precision argument یا تنظیم runtime ندارد و `DateTimeType()` به SQL `DATETIME` render می‌شود.

### SQL و semantics دقیق

```sql
CREATE TABLE `users` (
  ...,
  `created_at` DATETIME NULL,
  `updated_at` DATETIME NULL,
  `deleted_at` DATETIME NULL
)
```

`timestamps()` دقیقاً دو ordinary column به ترتیب created_at سپس updated_at اضافه می‌کند. `softDeletes()` دقیقاً deleted_at را اضافه می‌کند. هر سه NULL صریح دارند، `hasColumnDefault = false` دارند و SQL default/automatic attribute ندارند.

`updated_at` هیچ `ON UPDATE CURRENT_TIMESTAMP` نمی‌گیرد و هیچ insertion/update به‌طور خودکار زمان را مقداردهی نمی‌کند. `deleted_at` هیچ delete/query/restore semantics ندارد. این‌ها صرفاً schema columns هستند.

### API، Builder، AST و ordering

افزوده‌های API صرفاً `timestamps()` و `softDeletes()` روی `IMigrationRenderCreateTableApi` هستند و بدون آرگومان‌اند. `MigrationRenderCreateTableBuilder` هر shorthand را با همان مسیر افزودن columnهای عادی به ترتیب همان نقطهٔ DSL expand می‌کند. AST فقط `IMigrationColumnAst` عادی دارد؛ AST shorthand یا metadata origin تازه‌ای ساخته نمی‌شود. Column list همچنان قبل از table-level definitions render می‌شود.

فراخوانی `timestamps(); softDeletes()` ترتیب generated columns را created_at, updated_at, deleted_at می‌کند. اگر ترتیب فراخوانی عوض شود، blockها به همان ترتیب فراخوانی در فهرست columnها قرار می‌گیرند؛ ترتیب داخلی timestamps ثابت است. ستون دستی پیش یا پس از shorthand نیز طبق ترتیب addColumn فعلی می‌ماند.

### Collision و repeated-call policy

- تمام column nameها پس از trim، case-insensitive یکتا هستند؛ spelling/casing اصلی در AST و SQL دست‌نخورده می‌ماند.
- تعریف دستی CREATED_AT/created_at، UPDATED_AT/updated_at یا DELETED_AT/deleted_at با shorthand متناظر در هر ترتیب DSL رد می‌شود.
- نام‌های blank در Builder رد می‌شوند. collision در Builder زودهنگام و در Renderer برای AST مستقیم بررسی می‌شود.
- فراخوانی دوم timestamps() یا softDeletes() رد می‌شود، چون duplicate generated names می‌سازد. استفادهٔ همزمان یک‌بار از هرکدام معتبر است.
- این duplicate rule نسبت به repository قبلی case-sensitive یک compatibility tightening عمومی برای CREATE TABLE است؛ مستندات رسمی MySQL و MariaDB می‌گویند column identifiers case-insensitive هستند. casing ذخیره/رندر نمی‌شود و فقط مقایسه برای validation case-insensitive است.

### Dialect، compatibility و server boundaries

MySqlDialect و MariaDbDialect از registration فعلی استفاده می‌کنند و SQL syntax برای DATETIME NULL مشترک است. Compatibility target کلی repository اعلام نشده و minimum version از نسخهٔ محلی استنتاج نمی‌شود. هیچ SQL mode، timezone config، `CURRENT_TIMESTAMP`, `ON UPDATE`, trigger، introspection یا execution path جدید اضافه نمی‌شود. Runtime value validity/range و semantics session همچنان مسئولیت سرور/application است.

### Implementation test/example checklist

- SQL دقیق سه ستون، هر shorthand جداگانه و هر دو با هم
- ordering با addColumnهای قبل و بعد و ترتیب فراخوانی shorthandها
- DateTimeType() AST و type/nullable/default stateهای دقیق
- manual collision در هر دو ترتیب، casing متفاوت، whitespace و blank
- repeated calls به هر shorthand و حالت استفادهٔ همزمان
- Builder collision و defensive renderer duplicate check برای AST مستقیم
- regression قرارداد قبلی CREATE TABLE و table-level definitions
- example versioned، render-only پیش‌فرض و DDL واقعی فقط با opt-in
- هیچ تستی updated_at auto-update، soft-delete lifecycle، timezone conversion یا database value behavior را claim نکند
