# Migration v2.1: Database Dialect Configuration Contract

وضعیت: `implemented` — config مشترک، metadata سرور در مرز manager، dialectهای MySQL/MariaDB و رد capability ناسازگار پیاده‌سازی شده‌اند.

## هدف

انتخاب dialect و نسخهٔ هدف را در پیکربندی اتصال تعریف کنیم و مرز روشنی میان تولید SQL و اجرای آن داشته باشیم. خطای `RENAME COLUMN` روی MariaDB 10.4.28 نشان داد که `DialectQuery.MY_SQL` به‌تنهایی محصول و نسخهٔ واقعی سرور را مشخص نمی‌کند.

اصل طراحی: target product/version فقط برای SQL generation است؛ `DatabaseServerInfo` تشخیص‌داده‌شده از اتصال واقعی، تنها مرجع capability اجرای DDL است. اگر target، MariaDB 10.4 باشد ولی سرور واقعی MySQL 5.7، SQL تولیدشده اجرا نمی‌شود و با خطای صریح رد می‌شود؛ executor حق ندارد آن را به `CHANGE COLUMN` بازنویسی کند.

## Traceability وضع موجود

- `data_base:core`: `DatabaseConfig` اطلاعات اتصال را نگه می‌دارد و `DatabaseConfigBuilder` آن را می‌سازد.
- `DefaultDatabaseConfig`: config اتصال و dialect را در دو property جدا نگه می‌داشت؛ اکنون dialect داخل `DatabaseConfig` است و property قدیمی فقط facade deprecated روی همان config است.
- `data_base:query:executor` و `data_base:migration:executor` renderer را از `DefaultDatabaseConfig.config.dialect` مشترک انتخاب می‌کنند.
- `DialectQuery` شامل `MY_SQL` و `MARIA_DB` مستقل است؛ هر دو renderer فعلاً grammarهای موجود MySQL را reuse می‌کنند.
- `IQueryExecute.getDatabaseServerInfo` اطلاعات product/version را از اتصال manager می‌خواند و به شکل type-safe برمی‌گرداند؛ migration executor آن را مصرف می‌کند و خودش metadata SQL را query/parse نمی‌کند.

## مدل پیکربندی و metadata سرور

سه مفهوم مستقل‌اند:

1. **Dialect**: قواعد SQL مورد استفاده برای render؛ مستقل از target database که SQL برای آن ساخته می‌شود.
2. **Target database (اختیاری)**: محصول و نسخه‌ای که SQL برای آن تولید می‌شود؛ این مقدار از dialect مستقل است.
3. **Detected `DatabaseServerInfo`**: محصول و نسخهٔ واقعی اتصال، تنها مرجع قابلیت اجرای DDL.

MySQL و MariaDB باید به‌صورت صریح از هم قابل تشخیص باشند؛ grammar و capability آن‌ها یکسان فرض نمی‌شود. برای وضعیت فعلی repository، MySQL و MariaDB دو dialect مستقل باشند: `DialectQuery.MY_SQL` و `DialectQuery.MARIA_DB`. مدل family + flavor در scope این نسخه نیست. Target database محصول و نسخه را در خود نگه می‌دارد، اما از dialect مستقل است؛ از نام dialect یا JDBC URL/driver به‌صورت ضمنی حدس زده نمی‌شود.

Version به product تعلق داشته باشد تا نسخهٔ یک محصول با محصول دیگر اشتباه نشود؛ این product ownership به معنی یکی بودن target با dialect نیست. به‌جای version بی‌هویت مثل `MARIA_DB.Version(10, 4, 28)`، مدل مفهومی باید نسخهٔ type-safe محصول‌دار بسازد؛ برای نمونه:

```kotlin
val mysqlVersion = MYSQL.Version(8, 0, 36)
val mariaVersion = MARIA_DB.Version(10, 4, 28)
```

در صورت نیاز، مقایسه با حداقل نسخه‌های مهم capability به شکل ثابت‌های معنایی انجام شود، نه تعریف نام/کلاس جدا برای هر release:

```kotlin
if (version >= MYSQL.V8_0) {
    // capability is available
}
```

`DatabaseServerInfo` همچنان metadata واقعی manager را به‌شکل product + version ارائه می‌کند؛ اما نوع/مقدار version باید product-aware باشد. پیاده‌سازی می‌تواند sealed hierarchy یا representation سازگار با Kotlin فعلی را برگزیند، مشروط بر آنکه نسخه‌های MySQL و MariaDB بدون تبدیل صریح جابه‌جا نشوند و مقایسه عددی باشد.

`DatabaseServerInfo` از اتصال واقعی به دست می‌آید. `DatabaseConfig` بدون اتصال قابل ساختن می‌ماند و metadata واقعی داخل آن ذخیره نمی‌شود.

## قرارداد پیکربندی

- `dialect` و `targetDatabaseVersion` فیلدهای مستقل در config مشترک `data_base:core` باشند. Dialect قواعد render SQL را تعیین می‌کند؛ target می‌گوید SQL برای کدام محصول و نسخه تولید می‌شود.
- `targetDatabaseVersion` اختیاری و product-aware است. product از نوع version مشخص می‌شود و wrapper جداگانهٔ `DatabaseServerTarget` نیاز نیست؛ target version از dialect مستقل می‌ماند.
- `DatabaseConfigBuilder` API متناظر را مطابق naming repository فراهم کند.
- defaults فعلی حفظ شوند تا مصرف‌کنندگان قدیمی رفتارشان را از دست ندهند.
- `DefaultDatabaseConfig.dialect` منبع موازی و متناقض باقی نماند؛ انتقال call siteها و compatibility/deprecation API قدیمی مستند شود.
- اطلاعات حساس اتصال در log و diagnostic چاپ نشوند.

DSL مفهومی زیر جدایی dialect و نسخهٔ هدف را نشان می‌دهد. نام نهایی API تابع convention repository است:

```kotlin
DatabaseConfigBuilder()
    .domain("jdbc:mariadb://127.0.0.1")
    .port(3306)
    .name("app")
    .username("app")
    .password("...")
    .dialect(DialectQuery.MARIA_DB)
    .targetDatabaseVersion(MARIA_DB.Version(10, 4, 28))
    .build()
```

## تفکیک SQL generation از execution

- Renderer فقط config/context لازم برای generation را مصرف می‌کند و SQL را بر اساس dialect و target صریح می‌سازد.
- نبود target با نسخهٔ فرضی یا نسخهٔ توسعه‌دهنده پر نشود؛ رفتار پیش‌فرض backward-compatible و مستند باشد.
- Renderer حق ندارد برای تشخیص version یا capability به manager، connection یا database وصل شود.
- manager موجود تنها مرز خواندن product/version واقعی اتصال است و نتیجه را به شکل `DatabaseServerInfo(product, version)` ارائه می‌دهد؛ query و parsing metadata در migration executor تکرار نشود.
- مرز مسئولیت capability در execution policy مشخص باشد و بر اساس dialect/target و detected info تصمیم بگیرد. در v2.1 فقط این boundary تعریف شود؛ abstraction عمومی مانند `DatabaseCapabilities` یا capability matrix ساخته نشود تا operationهای بعدی نیاز مشترک واقعی نشان دهند.
- executor فقط SQL سازگار با capability واقعی را اجرا کند. اگر capability لازم وجود ندارد، executor با خطای صریح متوقف شود؛ rewrite خودکار SQL به syntax دیگری، از جمله تبدیل `RENAME COLUMN` به `CHANGE COLUMN`، ممنوع است. این رد اجرا همان compatibility fallback محسوب نمی‌شود و نباید به‌صورت پنهان رخ دهد.

## مراحل کار

### مرحله 1: بررسی compatibility

همهٔ ساخت‌های `DatabaseConfig`، استفاده‌های `DatabaseConfigBuilder` و call siteهای `DefaultDatabaseConfig.dialect` در core/query/migration/example فهرست شوند. قرارداد source/binary compatibility پروژه نیز بررسی شود.

### مرحله 2: بستن design decisions

پیش از implementation این تصمیم‌ها ثبت شوند:

1. نام‌گذاری نهایی عضوهای `DialectQuery` مستقل MySQL و MariaDB؛ تصمیم معماری این plan دو dialect مستقل است و family + flavor خارج از scope است.
2. API نهایی dialect مستقل، target database version مستقل و defaultها.
3. محل تعریف versionهای product-aware و `DatabaseServerInfo`; نسخهٔ product-aware مستقیماً target است و wrapper جدا تعریف نمی‌شود.
4. manager abstraction خواندن metadata واقعی و lifecycle/cache آن.
5. محل تصمیم capability در execution policy و خطای دقیق mismatch؛ فقط مرز مسئولیت تعریف شود و abstraction عمومی capability فعلاً ساخته نشود.
6. رفتار SQL generation وقتی target تنظیم نشده است.
7. رفتار mismatchها:
   - target product با detected product متفاوت است: پیش از DDL خطای صریح.
   - detected product ناشناخته یا metadata در دسترس نیست: پیش از DDL وابسته به capability خطا.
   - detection شکست می‌خورد: خطا؛ هیچ DDL وابسته به capability ارسال نشود.
   - فقط version متفاوت است: policy تعیین کند؛ برای نمونه MySQL 8.0 target در برابر MySQL 8.0.36 detected ممکن است سازگار باشد، اما target MySQL 8.0 در برابر MySQL 5.7 باید با توجه به capability رد شود.
7. مسیر سازگاری و deprecation برای `DefaultDatabaseConfig.dialect`.

### مرحله 3: core config و model

نسخه‌های product-aware و `DatabaseServerInfo` با validation و مقایسهٔ عددی تعریف شوند؛ یک type عمومی بی‌هویت فقط در صورت حفظ type-safety مجاز است. config فقط تنظیم کاربر را نگه دارد؛ JDBC dependency به core اضافه نشود.

### مرحله 4: manager metadata boundary

manager موجود API ساخت‌یافته‌ای برای خواندن `DatabaseServerInfo` از اتصال فراهم کند. محصول ناشناخته، نسخهٔ parse‌ناشدنی و خطای metadata رفتار صریح داشته باشند.

### مرحله 5: انتقال config در query و migration

selectorهای هر دو مسیر از config مشترک استفاده کنند. منبع global قدیمی حذف یا compatibility facade با precedence روشن شود؛ config موازی ساخته نشود و رفتار عملیات فعلی تغییر ناخواسته نکند.

### مرحله 6: capability policy و RENAME COLUMN

execution policy محل تصمیم capability است و target version و server info تشخیص‌داده‌شده را مصرف می‌کند؛ interface عمومی capability در این نسخه ساخته نمی‌شود. `RENAME COLUMN` در generation از target پیروی کند و در execution با detected server سنجیده شود. در صورت capability ناکافی یا product ناسازگار، executor پیش از DDL خطای صریح بدهد و SQL را به `CHANGE COLUMN` یا syntax دیگری rewrite نکند.

### مرحله 7: مستندات و migration guide

ساختار core/manager/query/migration/example، mapping config قدیم به جدید، defaults، mismatch behavior و نمونه‌های MySQL/MariaDB به‌روز شوند.

## تست‌های مورد انتظار

- نسخهٔ product-aware با validation و مقایسهٔ عددی؛ جابه‌جایی نسخهٔ MySQL/MariaDB بدون تبدیل صریح و اجزای نامعتبر رد شوند؛ برای هر release نام مستقل تعریف نشود.
- metadata MySQL و MariaDB به `DatabaseServerInfo` درست تبدیل شود؛ محصول/نسخهٔ ناشناخته حدس زده نشود.
- ساخت config قدیمی و Builder جدید با defaults سازگار باشد و config بدون connection ساخته شود.
- query و migration یک منبع config داشته باشند.
- target version و detected `DatabaseServerInfo` مستقل بمانند.
- execution policy برای product mismatch، version mismatch، target غایب، server ناشناخته و خطای detection آزموده شود.
- target MariaDB 10.4 در برابر detected MySQL 5.7 پیش از DDL با خطا رد شود؛ SQL به `CHANGE COLUMN` تبدیل نشود.
- target MySQL 8.0 در برابر detected MySQL 8.0.36 می‌تواند طبق policy سازگار باشد؛ target MySQL 8.0 در برابر MySQL 5.7 به‌دلیل capability ناکافی رد شود.
- mismatch یا capability ناکافی خطای صریح بدهد و executor SQL را rewrite نکند.
- regressionهای query/migration و compatibility API قدیمی حفظ شوند.
- core/config/model/renderer بدون database و JDBC تست‌پذیر بمانند؛ fake در مرز manager موجود باشد. در v2.1 abstraction عمومی capability اضافه نشود مگر operationهای موجود نیاز مشترک واقعی را ثابت کنند.

## خارج از scope

- افزودن SQLite/Android renderer یا driver.
- حدس محصول از JDBC URL یا classpath driver.
- migration runner، version history یا rollback.
- تعیین compatibility target کلی repository.
- بازطراحی connection pool فراتر از نیاز metadata boundary.


## معیار پذیرش

- MySQL و MariaDB در مدل صریحاً قابل تمایز باشند.
- versionها product-aware، type-safe و عددی مقایسه‌پذیر باشند؛ `DatabaseServerInfo(product, version)` ساخت‌یافته و مستقل از JDBC باشد.
- `DatabaseConfig` dialect و target version مستقل را نگه دارد، نه metadata واقعی اتصال.
- manager موجود تنها منبع detected server info باشد و migration executor خودش version را query/parse نکند.
- execution policy محل تصمیم بر اساس target version و server info واقعی مشخص باشد؛ abstraction capability عمومی تا زمان نیاز اثبات‌شده ساخته نشود.
- target version فقط بر SQL generation اثر بگذارد؛ detected info تنها مرجع قابلیت اجرای واقعی باشد.
- product mismatch خطای صریح بدهد؛ server ناشناخته یا detection failure پیش از DDL وابسته به capability متوقف شود.
- version mismatch طبق policy ارزیابی شود؛ نابرابری عددی به‌تنهایی الزاماً mismatch اجرایی نیست.
- در capability ناکافی، executor خطا بدهد و SQL را rewrite نکند؛ fallback خاموش وجود نداشته باشد.
- renderer به manager/connection وابسته نباشد؛ SQL generation و execution دو مرحلهٔ مستقل بمانند.
- query و migration از config مشترک استفاده کنند و defaults/compatibility API مستند باشند.
- dependency direction و platform independence حفظ شوند.

## نتیجهٔ implementation

پیاده‌سازی v2.1 تکمیل شد. `targetDatabaseVersion` فقط پیش‌شرط تولید SQL بومی برای `RENAME COLUMN` است؛ قابلیت اجرای واقعی با `DatabaseServerInfo` تشخیص‌داده‌شده سنجیده می‌شود. سرور قدیمی یا product mismatch پیش از DDL با خطا متوقف می‌شود و هیچ `SHOW CREATE TABLE`، `CHANGE COLUMN` یا rewrite خودکاری انجام نمی‌شود. تست‌های core، manager execute (بدون test source)، query executor (بدون test source)، migration executor و migration example با JDK 24 موفق شدند.

## وابستگی و گام بعدی

این پلن تغییر cross-module در core، manager، query و migration است. پلن `v1.5 MODIFY COLUMN` پیش از implementation باید با این قرارداد هم‌راستا شود و منبع dialect/version موازی نسازد. پس از اجرای v2.1، operationهای بعدی از config و capability policy مشترک استفاده می‌کنند.
