# Migration v1.8: CREATE UNIQUE INDEX Contract

وضعیت: `implemented`

## پیش‌شرط و هدف

`v1.6 CREATE INDEX` و `v1.7 DROP INDEX` پیاده‌سازی شده‌اند. مرحلهٔ بعد خانوادهٔ Index، افزودن operation مستقل `CREATE UNIQUE INDEX` تک‌ستونی است.

هدف، ساخت یک unique index نام‌گذاری‌شده روی یک ستون از جدول موجود است. operation باید از pipeline واقعی API → AST → Builder → Dialect/Renderer → `MigrationExecutor` عبور کند و اجرا را به `IQueryExecute.executeTable` موجود بسپارد.

## انتخاب operation در Index v2

دو مسیر آینده برای Index v2 مطرح بودند: `UNIQUE INDEX` و `Multi-column INDEX`. برای v1.8، `CREATE UNIQUE INDEX` تک‌ستونی انتخاب شد چون مدل تک‌ستونی v1.6 را حفظ می‌کند و تغییر معنایی آن به unique بودن محدود است. Multi-column قرارداد جداگانه می‌خواهد و در این plan پیاده نمی‌شود.

`CREATE INDEX v1.6` و `DROP INDEX v1.7` دست‌نخورده می‌مانند. API و AST این operation مستقل‌اند؛ به `createIndex` flag یا حالت `unique` اضافه نشود.

## مبنا و traceability از v1.6 و v1.7

Traceability واقعی v1.6/v1.7 پیش از implementation انجام شد و این یافته‌ها مبنای operation جدید بودند:

- API و AST مستقل در package operation-specific مطابق ساختار موجود قرار گیرند؛ package موازی صرفاً برای تطبیق با این plan ساخته نشود.
- convention Builder برای trim پیرامونی، حفظ casing/content، validation مقادیر blank و نگهداری identifierها در AST دنبال شود.
- capability مستقل در dialect و registration در `MySqlDialect.registerRenders()` به روش فعلی انجام شود.
- quoting/escaping شناسه‌ها از renderer واقعی MySQL پیروی کند: backtick پیرامونی و دوبرابرکردن backtick داخلی.
- entry point لازم در `IMigrationExecutor` موجود افزوده شود و `MigrationExecutor` از `executeOut` و `IQueryExecute.executeTable` استفاده کند؛ executor یا production abstraction جدید ساخته نشود.
- fake تست همان `IQueryExecute` موجود را هدف بگیرد.
- API، AST، Builder، dialect capability، MySQL renderer، executor overload و registry با conventionهای واقعی v1.6/v1.7 پیاده‌سازی شدند؛ `CREATE INDEX` و `DROP INDEX` تغییر نکردند.
- مثال `A1ExampleCreateUniqueIndexV1` و opt-in خاموش `statusRunCreateUniqueIndex` در manager مثال اضافه شدند. فایل محلی `Main.kt` تغییر داده نشد.
- `A1ExampleCreateUniqueIndexV1Test` و `MigrationExecutorCreateUniqueIndexTest` اضافه شدند. `:data_base:migration:example:test` و `:data_base:migration:executor:test` با JDK 24 موفق شدند؛ این دو task regressionهای v1.6/v1.7 را نیز اجرا کردند.
- MySQL compatibility target کلی repository همچنان اعلام نشده است؛ این finding حفظ شد و نسخهٔ توسعه‌دهنده مبنا قرار نگرفت.
- plan مشترک v1.2 اگر همچنان planned است، وابستگی واقعی v1.8 به آن بررسی شود؛ صرف ترتیب شماره‌ها dependency محسوب نمی‌شود.
- compatibility target کلی MySQL repository بررسی شود. اگر همچنان اعلام نشده است، به‌عنوان finding ثبت شود و از نسخهٔ نصب‌شدهٔ توسعه‌دهنده baseline حدس زده نشود.
- grammar مستند MySQL برای CREATE INDEX و semantics unique بررسی شود. MySQL Reference Manual برای این grammar شکل `CREATE [UNIQUE | FULLTEXT | SPATIAL] INDEX ... ON ...` را ثبت می‌کند؛ این مدرک syntax است و به‌تنهایی minimum supported version repository را تعیین نمی‌کند.

## محدوده

در v1.8:

- ایجاد یک unique index روی دقیقاً یک ستون موجود.
- MySQL تنها dialect پشتیبانی‌شده.
- DSL مفهومی مستقل:

```kotlin
createUniqueIndex {
    tableName("users")
    name("uq_users_email")
    column("email")
}
```

- SQL مفهومی:

```sql
CREATE UNIQUE INDEX `uq_users_email`
ON `users` (`email`)
```

- API، AST، Builder، dialect capability و renderer مستقل از `CREATE INDEX` عادی.
- overload فقط در executor موجود، مطابق convention واقعی و از مسیر manager موجود.
- مثال نسخه‌بندی‌شده با render-only پیش‌فرض؛ اجرای دیتابیس فقط با opt-in روشن.
- unit test بدون دیتابیس برای validation/SQL و executor fake برای مرز واقعی `IQueryExecute`.

خارج از محدوده:

- تغییر `createIndex` یا AST/renderer مربوط به v1.6؛ افزودن `unique` Boolean یا mode به آن.
- index چندستونی، functional index، prefix length یا expression.
- `FULLTEXT`, `SPATIAL`, index options، algorithm و lock options.
- `IF NOT EXISTS`، تولید خودکار نام، introspection، preflight duplicate scan یا تغییر/حذف index موجود.
- API جدا برای UNIQUE constraint یا PRIMARY KEY.
- dialect غیر از MySQL، migration history، runner و rollback.

## قرارداد API، AST و Builder

API مفهومی:

```text
createUniqueIndex {
    tableName(table)
    name(index)
    column(column)
}
```

AST مستقل:

```text
CreateUniqueIndexAst
├── tableName: String?
├── indexName: String?
└── columnName: String?
```

Invariants:

- هر سه ورودی identifier اجباری و پس از trim غیرخالی‌اند.
- Builder فقط whitespace پیرامونی را حذف می‌کند؛ casing و محتوای باقیمانده را تغییر نمی‌دهد.
- AST فقط ورودی همین operation را نگه می‌دارد؛ unique بودن از نوع operation معلوم است و flag جداگانه ندارد.
- Renderer AST ناقص یا blank را دفاعی و پیش از quoting/SQL composition رد می‌کند.
- `PRIMARY KEY` به‌عنوان operation مستقل ایجاد نمی‌شود. مقدار `name("PRIMARY")` از دید library صرفاً یک `indexName` است؛ Builder و Renderer آن را special-case نمی‌کنند و مانند identifierهای دیگر quote می‌کنند. اگر MySQL این نام را نپذیرد، همان خطای MySQL به caller می‌رسد.
- identifierها bind parameter نیستند؛ باید با quote/escape dialect وارد SQL شوند. raw SQL fragment پذیرفته نیست.
- ترتیب فراخوانی setterها نباید AST معنایی یا SQL را تغییر دهد.

## قرارداد Renderer

MySQL renderer دقیقاً این فرم را تولید کند:

```sql
CREATE UNIQUE INDEX <quoted-index-name>
ON <quoted-table-name> (<quoted-column-name>)
```

- هر سه identifier با convention موجود quote و escape شوند.
- فقط یک column در پرانتز render شود.
- SQL شامل `UNIQUE` دقیقاً یک‌بار، بلافاصله پس از `CREATE` باشد.
- SQL شامل `IF NOT EXISTS`، `ALTER TABLE` جایگزین یا هیچ index option خارج scope نباشد.
- renderer به connection، manager، executor یا JDBC وابسته نباشد و برای بررسی duplicate value به دیتابیس متصل نشود.
- وجود جدول/ستون، duplicate data، محدودیت طول/type و سازگاری engine به MySQL واگذار شود؛ renderer ادعای اعتبار schema نمی‌کند.

## Executor و خطا

- entry point/overload در `IMigrationExecutor` فقط در صورت نیاز convention موجود اضافه شود.
- اجرای SQL از `executeOut` و `IQueryExecute.executeTable` موجود عبور کند.
- success و failure manager بدون تبدیل خطای duplicate key به success/no-op به callback برسد و cause اصلی حفظ شود.
- هیچ query برای metadata یا جست‌وجوی duplicate value پیش از DDL اجرا نشود.

## مثال و تست

تست‌های بدون database:

- AST مستقل با سه identifier مربوط به همین operation.
- trim پیرامونی و حفظ casing/content در AST و SQL؛ برای نمونه `Users`, `Uq_User_Email`, `Email` همان casing را پس از trim حفظ کنند.
- رد table/index/column نامشخص یا blank در Builder و AST ناقص مستقیم در Renderer.
- SQL دقیق `CREATE UNIQUE INDEX ... ON ... (...)`، با reserved word و backtick داخلی در هر موقعیت identifier.
- assert شود خروجی `UNIQUE` دارد و `IF NOT EXISTS`, `ALTER TABLE` یا bind parameter برای identifierها اضافه نمی‌کند.
- ترتیب متفاوت setterها SQL یکسان تولید کند.
- executor fake ارسال همان BuiltQuery از `IQueryExecute.executeTable`، callback موفق و حفظ failure/cause را بررسی کند؛ fake نباید روی manager/executor خیالی ساخته شود.
- تست صریح `name("PRIMARY")` ثابت کند SQL این است؛ این نام در Builder/Renderer special-case نمی‌شود و پذیرش یا رد آن هنگام اجرا به MySQL واگذار می‌شود:

  ```sql
  CREATE UNIQUE INDEX `PRIMARY` ON `users` (`email`)
  ```

- تست‌های `CREATE INDEX v1.6` و `DROP INDEX v1.7` به‌عنوان regression حفظ و اجرا شوند.

Integration test دیتابیس اختیاری است و فقط روی MySQL اختصاصی/قابل reset اجرا شود؛ اگر نوشته شد، ایجاد unique index روی دادهٔ بدون تکرار و رد insert تکراری را بررسی کند. اجرای عادی example نباید DDL را خودکار اجرا کند.

## Roadmap خانوادهٔ Index

این roadmap خارج از scope v1.8 باقی می‌ماند:

```text
Index v1
├── v1.6 CREATE INDEX (single-column, non-unique) ✅
└── v1.7 DROP INDEX ✅
        ↓
Index v2
├── v1.8 CREATE UNIQUE INDEX (single-column) ← this plan
└── future plan: Multi-column index operation
        ↓
Index v3 (future)
├── FULLTEXT
├── SPATIAL

```
