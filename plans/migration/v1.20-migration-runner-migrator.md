# Migration v1.20: Migration Runner / Migrator

## Status

**Implementation Ready** — قرارداد Runner/Migrator مشخص شده است.

**Deferred compatibility:** سازگاری برابری IDهای v1.19 با collation دیتابیس همچنان `Deferred` است. این مورد ادعای compatibility برای هیچ نسخهٔ MySQL/MariaDB ایجاد نمی‌کند و در v1.20 schema یا version floor تغییر نمی‌کند.

این سند حاصل Traceability کد فعلی، تصمیم‌های قراردادی v1.20 و برنامهٔ implementation است. هیچ source، test، build، example یا schema در مرحلهٔ تهیهٔ این Plan تغییر نکرده است.

## Objective

اولین orchestration واقعی Migration را با کمترین لایهٔ لازم اضافه کند:

```text
MigrationConfiguration
    → registrationهای مرتب
    → SystemMigrationStateStore
    → فیلتر Migrationهای pending با ID
    → اجرای ترتیبی هر Migration
    → MigrationDefinition
    → MigrationExecutor موجود
    → ثبت موفقیت و batch
```

Runner فقط `up()` را اجرا می‌کند. هر شکست، ادامهٔ همان اجرای `migrate` را متوقف می‌کند. Transaction، rollback خودکار، locking و discovery به این مرحله وارد نمی‌شوند.

## Existing Migration Lifecycle

در حال حاضر registration، Migration را instantiate نمی‌کند. نمونه‌های قدیمی‌تر در `example` اغلب operation Builder را مستقیماً به Executor تحویل می‌دهند و lifecycle ثبت/اجرا/record را ندارند. `MigrationExecutor` خود Migration یا MigrationDefinition را مدیریت نمی‌کند؛ اجرای یک operation API را بر عهده دارد.

**Interpretation:** v1.20 نخستین orchestrator است و باید مسئولیت pending selection، instantiation، اجرای `up()`، dispatch Definition و state recording را به‌صورت ترتیبی جمع کند.

## v1.17 State Store Traceability

### Applied history

- Bootstrap و read در مسیر `SystemMigrationStateStore.initialize(...)` انجام می‌شود.
- Reader همهٔ ردیف‌ها را به `AppliedMigration(id, migration, batch)` تبدیل می‌کند و history را بر اساس row `id` می‌خواند.
- منبع تشخیص applied بودن فقط مقدار دقیق migration ID در history است؛ class name، filename، package و group name در State Store وجود ندارند.
- ترتیب execution از configuration می‌آید، نه ترتیب ردیف‌های history. Runner ابتدا history را به مجموعهٔ IDهای applied تبدیل می‌کند و سپس registrationها را در ترتیب configuration فیلتر می‌کند.
- IDهای ثبت‌شده در Configuration از قبل validate و در کل registration tree یکتا شده‌اند. v1.20 رفتار duplicate تازه‌ای تعریف نمی‌کند.

### State operations

- `initialize` جدول را ایجاد می‌کند و سپس history را می‌خواند.
- `read` history موجود را بدون ساخت batch جدید می‌خواند.
- `recordSuccessfulMigration` یک ID و batch از caller می‌گیرد.
- Reader بیشترین batch را می‌خواند، ولی batch بعدی را تولید نمی‌کند.
- State Store قرارداد drift برای تغییر MigrationId ندارد. تغییر annotation به ID جدید برای Runner مانند Migration جدید و pending دیده می‌شود؛ ردیف ID قبلی باقی می‌ماند.

**Decision:** از همین Store و schema استفاده شود. هیچ table، column یا history model جدیدی اضافه نشود.

## v1.18 Definition / Executor Traceability

`MigrationDefinition` حامل مرتب چند API operation است؛ `MigrationDefinitionBuilder` می‌تواند صفر، یک یا چند مورد بسازد و `MigrationExecutorDispatch` هر مورد را جداگانه به overload موجود می‌فرستد. `MigrationExecutor` SQL را render می‌کند و از `IQueryExecute.executeTable` اجرا می‌کند.

### یک Migration و یک Operation

درخواست v1.20 invariant جدیدی تعیین می‌کند: **Definitionای که از `Migration.up()` برای اجرای این Runner دریافت می‌شود باید دقیقاً یک semantic Migration Operation داشته باشد.** این با قابلیت عمومی v1.18 که Definition را برای handoff چندعملیاتی طراحی کرده، یکسان نیست. Evidence فعلی نشان می‌دهد Builder و API این شرط را enforce نمی‌کنند و نمونهٔ composite آن را نقض می‌کند.

این Plan invariant جدید را فقط در مرز Runner اعمال می‌کند:

- Definition خالی: پیش از هر dispatch یا state recording رد شود.
- Definition با دقیقاً یک operation: به overload typed متناظر dispatch شود.
- Definition با بیش از یک operation: پیش از هر dispatch رد شود.
- `MigrationDefinition` و Builder عمومی v1.18 بدون تغییر باقی بمانند.

این تصمیم **محدودیت جدید قرارداد اجرای v1.20** است و از رفتار فعلی v1.18 استنتاج نشده است. Migration composite موجود تا وقتی به چند Migration تک‌عملیاتی تقسیم نشده باشد از طریق Runner جدید قابل‌اجرا نخواهد بود. «یک Operation» به معنی یک SQL statement نیست؛ یک operation می‌تواند در Executor به بیش از یک query/statement نیاز داشته باشد.

## v1.19 Identity / Registration Traceability

قرارداد v1.19 حفظ می‌شود:

- `@MigrationId(...)` مالک persistent identity است.
- `migrationTags` فقط holder ثابت‌های compile-time است.
- `migration<T>()` membership و order را مشخص می‌کند؛ ID دستی نمی‌گیرد.
- `KClass<out Migration>` registration metadata است و هیچ instantiation policy را تعریف نکرده است.
- Group نام structural است، Migration identity نیست و در v1.20 transaction/batch boundary نمی‌شود.
- Configuration snapshot مرتب و بدون instance است.
- ID عین مقدار معتبر annotation است و State Store همان String را دریافت می‌کند.

`Persistence Compatibility` v1.19 همچنان Deferred است. این Plan تضمینی دربارهٔ case/accent equality در unique index دیتابیس اضافه نمی‌کند.

## Registration and Ordering Contract

1. registration order در سطح Configuration ترتیب اجرای Migrationهای pending است.
2. Groupها در همان نقطهٔ خود در ترتیب top-level traverse می‌شوند؛ اعضای هر Group نیز به ترتیب ثبت traverse می‌شوند.
3. traversal برای اجرا می‌تواند یک فهرست ترتیبی موقت بسازد، ولی خود Configuration و Group structure را mutate یا بازنویسی نمی‌کند.
4. Groupهای فعلی تو در تو نیستند؛ و v1.20 nesting جدیدی اضافه نمی‌کند.
5. applied migrations با `MigrationIdentity.value` دقیق فیلتر می‌شوند. sort بر اساس ID، class، package، filename یا State Store row id انجام نمی‌شود.
6. اگر registration قبلی جابه‌جا شده ولی ID آن applied است، صرفاً skip می‌شود؛ ترتیب اصلی اجرای تاریخی یا identity drift تشخیص داده نمی‌شود.

## Migration Unit Contract

برای هر entry pending:

```text
KClass metadata
  → ساخت یک Migration تازه با no-arg constructor عمومی
  → فراخوانی up() دقیقاً یک بار
  → بررسی تعداد operationها (باید ۱ باشد)
  → اجرای همان operation
  → ثبت MigrationId دقیق با batch اجرا
```

- یک instance برای هر Migration pending در هر invocation ساخته می‌شود؛ instance cache نمی‌شود.
- `down()` در v1.20 فراخوانی یا validate نمی‌شود.
- Constructor پارامتردار، injection، DI، provider و factory پشتیبانی نمی‌شوند.
- failure در construction یا `up()` قبل از اجرای operation است و State ثبت نمی‌شود.
- خطای operation یا ثبت State اجرای pendingهای بعدی را متوقف می‌کند.

## Batch Semantics

یک `migrate()` invocation که حداقل یک Migration pending دارد یک batch number مشترک خواهد داشت.

```text
nextBatch = (state.currentBatch ?: 0) + 1
```

- Batch فقط history grouping است؛ transaction یا rollback boundary نیست.
- برای Configuration خالی، Runner بدون bootstrap و بدون batch موفقیت no-op می‌دهد.
- برای configuration غیرخالی که همهٔ IDها applied هستند، Runner history را می‌خواند ولی batch جدید نمی‌سازد.
- Batch فقط پس از read موفق و تشخیص pending نیاز دارد؛ overflow عددی پیش از اجرای اولین Migration خطا می‌دهد.
- Batch برای تمام Migrationهای موفق همان invocation ثابت است؛ ثبت هر مورد پس از operation موفق انجام می‌شود.
- Store خودش Batch را تولید نمی‌کند؛ calculation در Runner است.
- هیچ row جداگانه‌ای برای batch خالی ثبت نمی‌شود.

### Concurrency

خواندن `currentBatch` و درج State اتمیک یا قفل‌شده نیست. دو Runner همزمان ممکن است یک State قدیمی بخوانند، Migration تکراری اجرا کنند یا درج یکی از آن‌ها با unique identity شکست بخورد. چون Locking خارج از scope است، **اجرای همزمان یا چند process روی یک migration history پشتیبانی‌شده نیست**. اجرای دوم ممکن است پس از انجام بخشی از DDL شکست بخورد؛ automatic repair وجود ندارد.

## Failure Semantics

- Bootstrap/state read failure: هیچ Migrationای instantiate یا اجرا نمی‌شود.
- Instantiation یا `up()` failure: همان Migration ثبت نمی‌شود؛ execution متوقف می‌شود.
- Definition با صفر/چند operation: قبل از dispatch و record خطای مشخص؛ execution متوقف می‌شود.
- Executor failure: همان identity ثبت نمی‌شود؛ Migrationهای بعدی اجرا نمی‌شوند.
- State-record failure پس از DDL موفق: اجرای بعدی متوقف می‌شود؛ migration در history نیست و invocation بعد ممکن است همان DDL را دوباره اجرا کند. این وضعیت خودکار repair نمی‌شود.
- موفقیت‌های قبلی همان batch باقی می‌مانند؛ rollback انجام نمی‌شود.
- اجرای بعدی history را دوباره می‌خواند، IDهای ثبت‌شده را skip می‌کند و از اولین pending در ترتیب Configuration ادامه می‌دهد.
- retry خودکار در همان invocation، fallback، silent skip یا schema repair وجود ندارد.

## Transaction Decision

Repository evidence:

- `IQueryExecute` transaction/begin/commit/rollback API ارائه نمی‌دهد.
- اجرای `IQueryExecute.execute(...)` از `DatabaseConnection().build()` connection می‌گیرد و آن را با `use` می‌بندد؛ اجرای DDL و INSERT تاریخچه در فراخوانی‌های جداگانه می‌تواند connection جدا بگیرد.
- هیچ Migration/batch/group transaction در migration layer فعلی وجود ندارد.

مستندات رسمی MySQL 8.4 توضیح می‌دهد که DDLهای مرتبط از جمله `CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX` و `DROP TABLE` implicit commit دارند؛ مستندات MariaDB نیز DDL را در فهرست implicit commit می‌آورد. MySQL همچنین Atomic DDL را صریحاً از transactional DDL متمایز می‌کند. این اسناد وجود atomicity محلی برای بعضی statementها را با rollback چند statement در یک Migration یکی نمی‌دانند.

**Contract:** v1.20 هیچ transaction API یا تضمین atomic rollback ندارد؛ نه در سطح Migration، Group و نه Batch. هر operation با مسیر execution موجود اجرا می‌شود. compatibility/version floor جدیدی از این اسناد استنتاج نمی‌شود.

منابع رسمی بررسی‌شده: *MySQL 8.4 Reference Manual*, «Statements That Cause an Implicit Commit» و «Atomic Data Definition Statement Support»؛ *MariaDB Server Documentation*, «SQL Statements Causing an Implicit Commit» و «START TRANSACTION — DDL Statements» (بررسی‌شده در ۳۰ سپتامبر ۲۰۲۶).

## Group Semantics

- Group فقط ساختار registration است.
- اعضای Group در محل خود و به ترتیب registration اجرا می‌شوند.
- Group transaction، rollback، batch، identity یا selection boundary نیست.
- شکست یک member همان سیاست توقف عمومی را اعمال می‌کند؛ اعضای بعدی و registrationهای بعد از Group اجرا نمی‌شوند.
- انتخاب Group در API v1.20 وجود ندارد.

## Migration Instantiation

### مقایسهٔ گزینه‌ها

| گزینه | سازگاری با v1.19 | هزینه/محدودیت | نتیجه |
|---|---|---|---|
| `KClass.java.getDeclaredConstructor().newInstance()` | از KClass ثبت‌شده استفاده می‌کند و Registration را تغییر نمی‌دهد | public no-arg constructor لازم است؛ dependency injection ندارد | **Adopt** |
| factory در registration | constructorهای پارامتردار را می‌پذیرد | API و snapshot v1.19 را تغییر می‌دهد و factory/closure جدید وارد می‌کند | Deferred؛ بدون نیاز فعلی evidence ندارد |
| DI/provider/ServiceLoader | امکان lifecycle سفارشی | infrastructure و dependency تازه، در repository موجود نیست | Out of Scope |
| `kotlin-reflect` `createInstance()` | DSL راحت | dependency جدید و الزام no-arg همچنان باقی می‌ماند | رد؛ Java reflection کافی است |

**Contract:** Runner از Java reflection استاندارد روی `KClass.java` استفاده می‌کند؛ Migration class باید concrete، قابل دسترسی و دارای public no-arg constructor باشد. Constructor برای هر migration pending یک بار و فقط هنگام اجرا فراخوانی می‌شود. خطای construction با cause اصلی به‌عنوان failure گزارش می‌شود.

این یک نیاز اجرایی جدید v1.20 است؛ v1.19 عمداً آن را تعیین نکرده بود. کلاس‌های ثبت‌شده با constructor وابستگی‌دار تا زمانی که factory/provider contract جداگانه تصویب شود پشتیبانی نمی‌شوند. هیچ Android minSdk یا Android compatibility guarantee تعریف نمی‌شود؛ Java reflection استفاده‌شده JVM-oriented است و target Android در repository وجود ندارد.

## Runner / Migrator Responsibility

نام پیشنهادی `MigrationMigrator` است؛ در repository Runner/Migrator/Manager مربوط به lifecycle وجود ندارد. آن را در ماژول `data_base:migration:executor` و کنار `MigrationExecutor` قرار بده، نه در API/Builder.

```kotlin
class MigrationMigrator(
    private val configuration: MigrationConfiguration,
    private val executor: IMigrationExecutor = MigrationExecutor(),
) {
    fun migrate(block: (ExecuteResult<Unit>) -> Unit)
}
```

این API callback-based است چون State Store، `IMigrationExecutor` و `IQueryExecute` فعلی callback/`ExecuteResult` استفاده می‌کنند. `migrate` blocking API جدید، generic manager یا return value همگام نمی‌سازد. خطای هر مرحله یک `ExecuteResult.Failure` به caller می‌دهد؛ موفقیت نهایی `ExecuteResult.Success(Unit)` است.

Runner مسئول است:

1. no-op برای Configuration خالی؛
2. bootstrap/read یک‌بارهٔ State Store؛
3. ساخت set از identityهای applied و محاسبهٔ pending بر اساس ترتیب Configuration؛
4. نساختن batch تا وقتی pending وجود دارد؛ سپس تخصیص یک batch؛
5. ساختن Migration، فراخوانی `up()` و اعتبارسنجی یک operation؛
6. dispatch ترتیبی با extension فعلی `IMigrationExecutor.execute(operation, ...)`؛
7. ثبت identity دقیق پس از موفقیت؛
8. تکمیل callback یک بار با موفقیت یا اولین failure.

Runner SQL نمی‌سازد، renderer/dialect را صدا نمی‌زند، Store schema را مدیریت نمی‌کند و `executeOut` fallback نمی‌زند.

## State Store Responsibility

- همان `SystemMigrationStateStore` فعلی برای bootstrap، read و record reuse شود.
- State به MigrationIdentity دقیق/String تبدیل شود؛ Group/class/filename به Store ارسال نشود.
- Store مالک batch allocation نیست.
- برای reuse همان executor تزریق‌شده، در صورت نیاز signature داخلی Store از concrete `MigrationExecutor` به interface موجود `IMigrationExecutor` تغییر کند؛ abstraction تازه ساخته نشود.
- schema، unique index، charset/collation و validationهای v1.17 بدون تغییر می‌مانند.

## Executor Responsibility

- Executor مسئول render و اجرای operation API typed است.
- Runner با dispatch extension موجود هر operation را به overload متناظر می‌رساند.
- ۱۵ operation فعلی در dispatcher باید regression شوند؛ operation ناشناخته failure صریح می‌دهد.
- `MigrationExecutor.executeOut` generic fallback برای Runner نیست.
- مسیر پایین‌دستی همان `MigrationExecutor → IQueryExecute.executeTable → DatabaseConnection/JDBC` می‌ماند.

## Exception Contract

- `ExecuteResult.Failure` دریافتی از Store/Executor بدون swallow شدن به caller می‌رسد.
- synchronous exception از instantiate، `up()` یا validation/render/dispatch باید به یک failure برای همان invocation تبدیل شود؛ exception hierarchy جدید لازم نیست.
- failure در record نیز failure کل invocation است، حتی اگر DDL پیش از آن موفق بوده باشد.
- State پیش از اجرای موفق operation درج نمی‌شود.
- هیچ migration بعد از اولین failure آغاز نمی‌شود.
- callback completion برای یک invocation دقیقاً یک بار انجام می‌شود؛ خطای callback خود caller جزو failure داخلی Runner محسوب نمی‌شود.

## Execution Flow

```text
migrate(callback)
  ├─ configuration خالی؟ → Success(Unit)، بدون DB/batch
  └─ StateStore.initialize()
       ├─ failure → callback(Failure)، توقف
       └─ history
            ├─ pending خالی؟ → Success(Unit)، بدون batch جدید
            └─ nextBatch = maxBatch + 1
                 └─ برای هر pending به ترتیب config:
                      instantiate
                      up()
                      require operations.size == 1
                      executor.execute(operation)
                      require ExecuteResult.Success(true)
                      stateStore.recordSuccessfulMigration(id.value, batch)
                      پس از record موفق برو به بعدی
```

`SystemMigrationStateStore.initialize()` خودش bootstrap و read را انجام می‌دهد؛ Runner دوباره `read()` موازی یا جداگانه فراخوانی نمی‌کند.

## State Recording Contract

```text
construct → up → check exactly one operation → execute
         → successful result → record exact MigrationId and shared batch
```

هر نتیجه‌ای غیر از DDL `Success(true)` موفقیت تلقی نمی‌شود. ثبت State باید affected row برابر ۱ باشد؛ Recorder این invariant را در Store فعلی enforce می‌کند. اگر DDL موفق ولی record ناموفق شود، migration pending باقی می‌ماند و اجرای مجدد می‌تواند DDL را تکرار کند.

## Down / Rollback Scope

- `migrate()` فقط `up()` را اجرا می‌کند.
- `down()` در v1.20 نه اجرا می‌شود و نه Migrationها خودکار rollback می‌شوند.
- API rollback جداگانه، selection و ترتیب reverse برای rollback به نسخهٔ آتی موکول است.

## Concurrency

- Locking، mutex، database lock و distributed coordination اضافه نمی‌شود.
- اجرای موازی `migrate()` روی یک DB خارج از contract پشتیبانی‌شده است.
- چون pending check و state insert atomic نیستند، race می‌تواند DDL تکراری یا unique-insert failure بسازد.
- این failure به‌صورت عادی به caller می‌رسد؛ auto repair/retry نداریم.

## API Design

API پیشنهادی:

```kotlin
val migrator = MigrationMigrator(configuration, migrationExecutor)
migrator.migrate { result ->
    // ExecuteResult.Success(Unit) یا ExecuteResult.Failure
}
```

- `MigrationMigrator` نام lifecycle orchestrator است؛ `MigrationExecutor` فقط operation executor می‌ماند.
- از نام عمومی `MigrationManager` استفاده نمی‌شود چون مسئولیت دقیق آن مبهم است.
- نتیجه از نوع موجود `ExecuteResult<Unit>` است؛ API نتیجه/مدل report جدیدی لازم ندارد.
- `MigrationConfiguration` از ماژول API استفاده می‌شود؛ `migrationConfig` یا registration جدیدی ساخته نمی‌شود.

## AST / Definition Impact

- AST dialect و operationهای قبلی تغییر نمی‌کنند.
- `MigrationDefinition` به‌عنوان ordered collection باقی می‌ماند.
- قید v1.20 فقط در Runner روی `up()` اجراشده enforce می‌شود: دقیقاً یک entry.
- Builder عمومی برای استفاده‌های v1.18 چند-operation باقی می‌ماند؛ چنین Definitionای برای Runner v1.20 نامعتبر است.
- Definition `down()` فراخوانی/بررسی نمی‌شود.

## Builder Impact

- `migrationConfig`, `migration<T>()`, Group، annotation parsing و duplicate validation بدون تغییر reuse می‌شوند.
- Builder مسئول instantiate یا enforce operation count نیست.
- API registration دستی برای ID و `MigrationDefinition` جدید لازم نیست.

## Renderer Impact

- هیچ تغییر renderer/dialect یا SQL لازم نیست.
- SQL فقط در `MigrationExecutor` موجود render می‌شود.

## Executor Impact

- `MigrationExecutorDispatch` extension برای dispatch تک operation reuse می‌شود.
- تمام overloadهای typed فعلی حفظ می‌شوند.
- تغییر احتمالی فقط برای دسترسی Runner به `IMigrationExecutor` و reuse همانی است که State Store bootstrap می‌کند؛ `executeOut` عمومی نشده و fallback نمی‌شود.

## State Store Impact

- Store و جدول `system_migration` reuse می‌شوند.
- Store API جدید برای pending selection یا batch allocation لازم نیست.
- تنها refactor مجازِ احتمالی، پذیرفتن `IMigrationExecutor` به‌جای concrete `MigrationExecutor` در constructor داخلی است تا instance تزریق‌شده برای Bootstrap و operationهای Migration مشترک باشد.
- batch بعدی در Runner از `currentBatch` محاسبه می‌شود.

## Dialect Impact

- MySQL و MariaDB از dialect selector/executor فعلی استفاده می‌کنند؛ Runner محصول یا dialect را تشخیص نمی‌دهد.

- هیچ dialect جدیدی اضافه نمی‌شود.

## MySQL Evidence

مستندات رسمی MySQL 8.4 می‌گوید DDLهای فهرست‌شده از جمله `CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX` و `DROP TABLE` implicit commit دارند. مستند Atomic DDL نیز می‌گوید atomic DDL همان transactional DDL نیست و DDL transaction جاری را implicit پایان می‌دهد. این evidence پشتیبان عدم ارائهٔ transaction گروهی در Runner است؛ minimum version رسمی repository را تعیین نمی‌کند.

## MariaDB Evidence

مستند رسمی MariaDB، DDLهایی مانند `CREATE`, `ALTER`, `DROP`, `CREATE INDEX` و `DROP INDEX` را در زمرهٔ statements ایجادکنندهٔ implicit commit قرار می‌دهد. این evidence نیز هیچ تضمین rollback چند-operation یا compatibility floor برای repository ایجاد نمی‌کند.

## Compatibility Impact

- قرارداد Registration و Identity v1.19 تغییر نمی‌کند.
- State Store v1.17/v1.17.4 و schema آن تغییر نمی‌کند.

- Migrationهایی با Definition صفر/چندعضوی از طریق Runner رد می‌شوند؛ composite migration باید به چند Migration با IDهای مجزا split شود.
- migration ID rename همچنان برای Runner یک ID تازه ایجاد می‌کند و تشخیص drift انجام نمی‌شود.
- duplicate ID همچنان در configuration به exact equality رد می‌شود؛ برابری persistence برای deploymentهای مختلف Deferred است.
- هیچ compatibility target، version floor یا collation جدیدی تعریف نمی‌شود.

- اگر بعداً DI/parameterized constructors یا Android lifecycle لازم شد، factory/provider contract مستقل نیاز دارد؛ v1.20 آن را پیشاپیش اضافه نمی‌کند.

## Candidate Architecture

| Candidate | سازگاری با repository | Abstraction/dependency | ارزیابی |
|---|---|---|---|
| `MigrationMigrator` در `migration:executor` با `IMigrationExecutor` و Store داخلی | executor و Store همین ماژول‌اند؛ config API موجود است | Runner جدید تنها orchestrator لازم؛ همان manager injection | **Adopt** |

| factory/DI بر Registration | v1.19 configuration metadata-only است | تغییر Registration/identity package/API | Defer |

Dependency direction:

```text
migration:executor / MigrationMigrator
    ├─ MigrationConfiguration / Migration API
    ├─ SystemMigrationStateStore
    ├─ IMigrationExecutor

         → DatabaseConnection / JDBC
```

`migration:api`, `builder`, AST, renderer و dialect به Runner/execution وابسته نمی‌شوند.

## Final Contract

| موضوع | قرارداد v1.20 |
|---|---|
| API | `MigrationMigrator(configuration, executor).migrate(callback)`؛ callback از نوع `ExecuteResult<Unit>` |
| Ordering | ترتیب registration منبع ترتیب اجراست؛ Group در همان محل و با ترتیب اعضای خود traverse می‌شود. |
| Applied detection | فقط MigrationId دقیق در State Store |
| Pending | registrationهای configuration که ID آن‌ها در history نیست، به ترتیب config |
| Empty configuration | no-op موفق؛ بدون DB/bootstrap/batch |
| All applied | no-op موفق؛ بدون batch جدید |
| Batch | برای pendingهای یک invocation یک batch؛ `currentBatch + 1` و در history خالی ۱ |
| Operation count | `up()` باید دقیقاً یک semantic Migration API داشته باشد؛ zero/multiple قبل از dispatch رد می‌شوند. |
| Instantiation | `KClass.java` و public no-arg constructor؛ instance تازه فقط برای pendingها |
| Execution | `up()` و سپس operation-specific overload موجود از طریق `IMigrationExecutor` |
| State record | فقط بعد از `ExecuteResult.Success(true)`؛ exact `MigrationId.value` و batch جاری |
| Failure | اولین failure به caller می‌رسد، Migration شکست‌خورده record نمی‌شود، بعدی اجرا نمی‌شود |
| Transaction | وجود ندارد؛ Batch/Group/ Migration مرز transaction نیستند |
| `down()` | اجرا نمی‌شود؛ rollback automatic نیست |
| Retry/repair | وجود ندارد |
| Locking | وجود ندارد؛ concurrent run پشتیبانی‌شده نیست |
| Discovery | explicit config موجود؛ filesystem/JAR/classpath scan وجود ندارد |

## Implementation Steps

1. در `migration:executor` کلاس `MigrationMigrator` و API callback نهایی را طبق این Plan اضافه کن.
2. Configuration را به ترتیب top-level و Group به یک traversal ترتیبی غیرمخرب تبدیل کن.
3. برای config غیرخالی از `SystemMigrationStateStore.initialize()` استفاده کن؛ failure را بدون execution تحویل caller بده.
4. pending list را با exact MigrationId و بدون sort بساز؛ اگر خالی است با موفقیت تمام کن.
5. batch را با overflow-safe محاسبهٔ `currentBatch + 1` بساز.
6. برای هر pending Migration، class را با Java reflection instantiate کن؛ خطا را با cause حفظ‌شده به failure تبدیل کن.
7. `up()` را یک‌بار بگیر؛ operation count را قبل از dispatch validate کن.
8. operation را از extension dispatch فعلی به overload متناظر Executor بفرست.
9. فقط پس از `Success(true)`، همان ID و batch را با Store ثبت کن؛ سپس به مورد بعدی برو.
10. تمام failureها را terminal کن: callback یک بار، بدون اجرای Migration بعدی.
11. اگر Store برای هم‌استفاده‌شدن از executor تزریق‌شده concrete type می‌خواهد، فقط امضای داخلی‌اش را به `IMigrationExecutor` تغییر بده؛ abstraction تازه نساز.
12. Build/testهای ماژول‌های درگیر و regressionها را اجرا کن؛ integration واقعی را فقط با DB environment معتبر اجرا کن.

## Test Plan

### Configuration / ordering

- خالی: no-op موفق و بدون query/bootstrap/batch.
- یک Migration، چند Migration، Group، و ترکیب Group/ungrouped: order دقیقاً registration order باشد.
- تمام applied: هیچ instantiation، execution، record یا batch تازه رخ ندهد.
- بعضی applied: فقط pendingها و با ترتیب configuration اجرا شوند.
- تغییر order موارد applied، identityها را عوض نکند و runner sorting تازه‌ای نکند.
- duplicate ID همچنان در Configuration رد شود.

### Instantiation / `up()`

- concrete public class با public no-arg constructor فقط هنگام pending بودن instantiate شود.
- applied class instantiate نشود.
- constructor invocation دقیقاً یک بار برای migration pending باشد.
- constructor failure، abstract class، inaccessible class/constructor و فقدان no-arg constructor با failure صریح تمام شوند.
- `up()` یک بار صدا شود؛ exception باعث عدم اجرای operation و عدم record شود.
- `down()` هیچ‌وقت صدا نشود.

### Operation invariant

- zero operation: fail قبل از Executor و State Recorder.
- exactly one: فقط یک overload متناظر dispatch شود.
- more than one: fail پیش از اجرای حتی operation اول؛ migration ثبت نشود.
- یک operation که خود Executor برایش چند مرحلهٔ SQL لازم دارد همچنان یک semantic unit محسوب شود.

### Execution / State

- یک و چند Migration موفق: execution به ترتیب، هر ID با batch مشترک record شود.
- State record فقط پس از executor success فراخوانی شود.
- executor `Success(false)`، failure، exception و record failure همگی توقف ایجاد کنند.
- failure در اول/میانه: موارد بعد از آن اجرا نشوند؛ موارد موفق قبلی ثبت باقی بمانند.
- execution بعدی، موفق‌های قبلی را skip و از اولین ID ثبت‌نشده ادامه دهد.
- state read/bootstrap failure: هیچ Migration اجرا نشود.
- batch خالی `1`، batch بعدی `max + 1`؛ overflow پیش از execution fail شود.
- test تأیید کند State Store String همان `MigrationIdentity.value` است.

### Group / failure / batch

- group members در جایگاه Group و به ترتیب خود اجرا شوند.
- failure داخل Group اعضای بعدی و بیرون Group را متوقف کند.
- Group batch/transaction boundary ایجاد نکند.
- batch فقط وقتی pending هست مصرف شود؛ all-applied invocation batch جدید ندارد.

### Exception / dispatcher

- تمام ۱۵ operation overload موجود dispatcher regression شوند.
- `IMigrationApi` ناشناخته به failure صریح برسد؛ `executeOut` fallback نشود.
- exceptionهای synchronous constructor/`up()`/render/dispatch به callback failure برسند.
- failureهای asynchronous-style `ExecuteResult` از Executor/Store حفظ شوند.
- callback terminal در هر مسیر دقیقاً یک بار انجام شود.

### Regression / Integration

- regression v1.17 و v1.17.4 State Store؛ schema و reader/recorder behavior.
- regression v1.18 Definition ordering، empty/multiple operation carrier و typed dispatch؛ API عمومی آن تغییر نکند.
- regression v1.19 identity validation, registration/group ordering, immutable snapshot, no instantiation at registration.
- integration با MySQL disposable: bootstrap → pending اجرا → record → اجرای دوم بدون duplicate؛ در نبود environment معتبر `Blocked/Unverified` گزارش شود.
- database collation/persistence compatibility همچنان Deferred است و این تست‌ها آن را اثبات نمی‌کنند.

## Deferred / Out of Scope

- `down()` execution و automatic rollback
- Transaction در Migration, Group یا Batch
- batch rollback
- locking/concurrency coordination
- checksum, drift detection و automatic repair
- automatic discovery، filesystem/JAR/classpath scan
- DI, provider/factory و constructor injection
- Migration dependency graph و parallel execution
- CLI/remote registry
- schema introspection و database preflight
- retry/fallback/silent skip
- database version floor، collation یا State Store schema update
- Android minSdk/shrinker compatibility guarantee
- تغییر Query/Manager/Connection transaction architecture

## Unresolved Decisions

برای v1.20 تصمیم معماری مسدودکننده باقی نمانده است. فرض‌های اجرایی جدیدی که در همین Plan صریحاً تصویب شده‌اند عبارت‌اند از:

1. no-arg public constructor و Java reflection برای instantiation؛
2. یک semantic operation دقیقاً برای `up()`؛
3. `currentBatch + 1` به‌عنوان batch بعدی، فقط در صورت وجود pending؛
4. callback `ExecuteResult<Unit>` با نام `MigrationMigrator`؛
5. عدم پشتیبانی اجرای concurrent.

این تصمیم‌ها implementation contract v1.20 هستند؛ هنوز در source پیاده نشده‌اند. `Persistence Compatibility` v1.19 و compatibility نسخه‌های DB همچنان Deferred هستند و هیچ تضمین تازه‌ای از این Plan حاصل نمی‌شود.
