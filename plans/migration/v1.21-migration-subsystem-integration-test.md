# Migration v1.21: Migration Subsystem Integration Test

## Status

**Implemented / DB Integration Unverified** — Integration Test و test-only dependencies اضافه شده‌اند و unit/regression tasks موفق بوده‌اند. خود تست end-to-end به‌دلیل نبود envهای DB به صورت `Skipped` گزارش شده؛ رفتار واقعی MySQL هنوز verify نشده است.

این Plan فقط برنامهٔ افزودن Integration Test در سطح `data_base:migration` است. در این مرحله هیچ source، test، build، API یا documentation تغییر نکرده است.

## Objective

یک Integration Test واقعی در ماژول `data_base:migration` اضافه شود که مسیر عمومی Migration را تا دیتابیس واقعی و State Store بررسی کند:

```text
Migration declaration / @MigrationId
        ↓
migrationTags constants
        ↓
migrationConfig / MigrationConfiguration
        ↓
MigrationMigrator
        ↓
Migration.up() / MigrationDefinition
        ↓
exactly-one-operation check
        ↓
MigrationExecutor
        ↓
Renderer / configured dialect
        ↓
real MySQL database
        ↓
system_migration history
```

این تست باید رفتار قابل مشاهده برای مصرف‌کنندهٔ کتابخانه را تأیید کند. آن را به تست واحد بزرگ یا suite دیگری از mock و fake تبدیل نکن.

### Interpretation

1. `data_base:migration` یک module مستقل است، نه parent taskای که خودکار testهای submoduleها را در یک classpath جمع کند. اجرای `:data_base:migration:test` امروز integration بین submoduleها را انجام نمی‌دهد.
2. تست واحد API/Builder/Executor هر مرز را جداگانه می‌آزماید. v1.21 شکاف سیستم‌سطحی را پر می‌کند: آیا config واقعی از fixtureهای Migration به Migrator و Executor موجود می‌رسد، DDL واقعی در DB اثر می‌گذارد و همان ID ثبت می‌شود؟
3. Code Vision، `val result = migrator.migrate()` را صرفاً به‌عنوان نمای مفهومی پیشنهاد می‌دهد. قرارداد repository callback-based است؛ v1.21 باید `migrate { result = it }` را از طریق helper کوچک test-local capture کند و API محصول را برای تست synchronous تغییر ندهد.
4. تنها `migrationTags` موجود در example در ماژول `example` است. وابسته‌کردن module سطح Migration به example، test boundary و dependency direction را معکوس می‌کند. بنابراین fixtureهای v1.21 یک `migrationTags` کوچک و test-local خواهند داشت.
5. تست State Store/Migrator موجود در executor همچنان برای integration مرز داخلی خودش معتبر است. تست جدید جایگزین یا جابه‌جایی آن نیست؛ مالکیت تست جدید public subsystem در `data_base:migration` خواهد بود.
6. وجود `MariaDbDialect` به‌تنهایی infrastructure Integration Test برای MariaDB را ثابت نمی‌کند. قرارداد DB موجود در executor صریحاً MySQL URL/connector/env pattern دارد؛ compatibility floor رسمی MySQL/MariaDB همچنان تعریف نشده است.
7. Lifecycleهای وابسته باید داخل یک test method ترتیبی و صریح اجرا شوند؛ ترتیب اجرای JUnit منبع state نیست. v1.21 یک lifecycle end-to-end برای success، rerun، failure/resume و operation-count failure تعریف می‌کند.

## Gradle Module Boundary

module هدف دقیقاً `:data_base:migration` است؛ این نام به معنی دسترسی خودکار به submoduleها نیست.

| Gradle module | نقش در test subsystem |
|---|---|
| `:data_base:migration` | مالک Integration Test v1.21 |
| `:data_base:migration:api` | `Migration`, `MigrationId`, `MigrationConfiguration`, `MigrationDefinition` |
| `:data_base:migration:builder` | `migration {}` و `migrationConfig {}` |
| `:data_base:migration:params` | data typeهای fixture مانند `IntType` و `VarcharType` |
| `:data_base:migration:executor` | `MigrationMigrator` و `MigrationExecutor` |
| `:data_base:manager:execute` و dependencyهای runtime آن | `ExecuteResult`, execution boundary و JDBC manager |
| `:data_base:migration:ast`, `dialect`, `renderer` | از مسیر dependencyهای واقعی Executor وارد runtime می‌شوند؛ test نباید renderer را مستقیم صدا بزند |
| `:data_base:migration:example` | به تست subsystem dependency داده نشود؛ fixtureها از example کپی یا import نشوند |

Test-only dependencyهای لازم در `data_base/migration/build.gradle.kts` باید بر اساس compile واقعی انتخاب شوند و حداقل این moduleهای مستقیماً مصرف‌شده را پوشش دهند:

```kotlin
testImplementation(project(":data_base:core"))
testImplementation(project(":data_base:manager:execute"))
testImplementation(project(":data_base:migration:api"))
testImplementation(project(":data_base:migration:builder"))
testImplementation(project(":data_base:migration:params"))
testImplementation(project(":data_base:migration:executor"))
```

MySQL connector dependency جدید اضافه نشود؛ connector از dependency runtime موجود `manager:connection` تأمین می‌شود. اگر compile proof یک dependency مستقیم دیگر را لازم نشان داد، فقط همان dependency با دامنهٔ `testImplementation` اضافه و دلیل ثبت شود. هیچ dependency تولیدی جدید به `data_base:migration` اضافه نشود.

## Integration Test Boundary

Test جدید در:

```text
data_base/migration/src/test/kotlin/
```

قرار می‌گیرد، چون مالکیت آن کل زنجیرهٔ زیر است:

```text
public Migration API + registration
    → Migrator
    → operation dispatch
    → real executor / renderer / dialect
    → database state + migration history
```

مرزبندی مسئولیت:

```text
migration:api       → identity / configuration / definition unit correctness
migration:builder   → DSL and registration correctness
migration:executor → typed dispatch / State Store / Migrator boundary tests
migration           → cross-module, public subsystem behavior against a real DB
```

تست جدید نباید `MigrationMigratorTest` fakeها را تکرار کند، API/AST داخلی را assert کند، یا تست واحد submodule را به این module منتقل کند.

## Database Strategy

- همان متغیرهای محیطی و JDBC/MySQL mechanism موجود استفاده شود:

```text
KOTLIN_DB_MIGRATION_TEST_HOST
KOTLIN_DB_MIGRATION_TEST_DATABASE
KOTLIN_DB_MIGRATION_TEST_USERNAME
KOTLIN_DB_MIGRATION_TEST_PASSWORD
KOTLIN_DB_MIGRATION_TEST_PORT   (اختیاری؛ default مطابق تست موجود)
```

رفتار دقیق precedent موجود: `HOST`, `DATABASE`, و `USERNAME` باید nonblank باشند؛ `PASSWORD` می‌تواند unset/خالی باشد؛ `PORT` با `toIntOrNull() ?: 3306` خوانده می‌شود، بنابراین unset یا non-numeric به 3306 می‌رسد. این فقط همان behavior موجود را دنبال می‌کند و compatibility floor جدیدی تعریف نمی‌کند.

- `DatabaseConfig` و `DefaultDatabaseConfig.config` برای تنظیم dialect/connection مطابق precedent تست‌های executor استفاده شوند.
- DDL تحت آزمون فقط از `MigrationMigrator` → `MigrationExecutor` → renderer/dialect → manager اجرا شود.
- mock database، fake JDBC، fake Executor یا SQL executor سفارشی ساخته نشود.
- `DriverManager`/JDBC مستقیم فقط برای safety check دیتابیس اختصاصی، مشاهدهٔ schema/history، ایجاد blocker کنترل‌شده برای failure case و cleanup test-owned objectها مجاز است؛ این مسیر جای اجرای Migration API را نمی‌گیرد.
- فقط test-side assertions با `DatabaseMetaData` و `SELECT` ساده از `system_migration` استفاده شوند. Query جدید `INFORMATION_SCHEMA`، preflight تولیدی یا abstraction introspection اضافه نشود.

## Test Isolation

1. Integration Test یک database اختصاصی، disposable و در اختیار انحصاری همین test run می‌خواهد؛ از DB تنظیمات local application یا credential حدسی استفاده نکند.
2. پیش از هر DDL، با `DatabaseMetaData` بررسی شود که `system_migration` و تمام نام‌های fixture v1.21 از قبل وجود ندارند. اگر هرکدام وجود دارند، از دست‌زدن به آن‌ها خودداری و کل lifecycle را با assumption skip کند.
3. دیتابیس را global پاک نکند و cleanup پیش از اجرا انجام ندهد.
4. تست خودش `system_migration` را قبل از Migrator نمی‌سازد. پس از clean-DB guard، اولین فراخوانی `MigrationMigrator` باید `StateStore.initialize()` را اجرا کند و جدول را از مسیر bootstrap موجود ایجاد کند.
5. فقط objectهایی را که همین lifecycle پس از guard ساخته یا برای blocker ساخته، در `finally` حذف کند؛ اگر `system_migration` را Migrator ایجاد کرده، همان‌جا cleanup شود. Config قبلی `DefaultDatabaseConfig` و connection نیز در همهٔ مسیرها restore/close شوند.
6. migration IDها ثابت و test-local هستند؛ history table خالی و test-owned تضمین می‌کند تکرار تست از وضعیت تمیز شروع شود. ID را با UUID یا class/file name عوض نکن.
7. اگر connection/config با env معتبر fail شود، تست fail شود؛ آن را به skip تبدیل نکن. Skip فقط برای نبودن env یا collision با objectهای قبلی مجاز است.

## Test Fixture Design

تمام Migrationهای تست فقط در فایل/پکیج test باشند؛ وارد `src/main`, public API یا `example` نشوند. یک فایل fixture کوچک در پکیج integration کافی است؛ `fixtures/` module یا framework جدید نساز. Fixtureها public no-arg constructor دارند چون Migrator واقعی v1.20 از همان قرارداد فعلی instantiate استفاده می‌کند؛ این امر قرارداد identity/registration تازه‌ای تعریف نمی‌کند.

از آنجا که `migrationTags` فعلی داخل `data_base:migration:example` تعریف شده و target module نباید به example وابسته شود، در فایل test یک holder کوچک محلی تعریف شود:

```kotlin
private object migrationTags {
    const val create_test_users = "create_test_users"
    const val add_test_users_email = "add_test_users_email"
    const val create_test_posts = "create_test_posts"
    const val failure_create_users = "failure_create_users"
    const val failure_add_email = "failure_add_email"
    const val broken_migration = "broken_migration"
    const val migration_after_failure = "migration_after_failure"
    const val empty_operation = "empty_operation"
    const val multiple_operations = "multiple_operations"
    const val after_empty_operation = "after_empty_operation"
    const val after_multiple_operations = "after_multiple_operations"
}

@MigrationId(migrationTags.create_test_users)
class CreateTestUsers : Migration { /* ... */ }
```

قواعد Identity fixture:

- **هیچ** `@MigrationId("literal")` مستقیم در fixtureهای v1.21 نوشته نشود.
- تمام annotationها از `migrationTags.<tag>` استفاده کنند؛ مقدارها `const val String` compile-time و مطابق grammar v1.19 باشند.
- از `MigrationIdentity` دستی در `migrationConfig`، ID registration دستی، shorthand تازه یا reflection test-only برای تعیین ID استفاده نشود.
- registration فقط `migration<T>()` و برای ساختار Group از `migrationGroup(...)` استفاده کند.
- assertionهای State Store همان `migrationTags` value را مقایسه کنند؛ ID در annotation، config و history نباید به صورت چند literal موازی تعریف شود.
- `migrationTags` فقط منبع ثابت‌های compile-time است، نه registry، discovery table یا identity source جدا از annotation.

Traceability مورد انتظار fixture:

```text
migrationTags const
    → @MigrationId(migrationTags.some_id)
    → migration<T>() reads annotation
    → MigrationIdentity / MigrationConfiguration
    → MigrationMigrator
    → SystemMigrationStateStore persists exact tag String
```

مقدار هویت به case/grammar/identity semantics v1.19 وفادار بماند؛ هیچ trim/lowercase/normalization انجام نشود.

Fixtureهای موفق کوچک باشند:

- `CreateTestUsers`: یک جدول test-prefixed با `id` و `name` بسازد.
- `AddTestUsersEmail`: ستون `email` را به همان جدول اضافه کند.
- `CreateTestPosts`: جدول test-prefixed دیگری بسازد.
- `FailureCreateUsers` و `FailureAddEmail`: جدول دوم برای تست failure/resume بسازند.
- `BrokenMigration`: یک `CREATE TABLE` برای نام blocker از قبل موجود تعریف کند تا DDL واقعی fail شود.
- `MigrationAfterFailure`: روی جدول blocker ستونی اضافه کند تا عدم اجرای آن هنگام شکست و وابستگی اجرای بعدی observable شود.
- `EmptyOperationMigration`: `up()` با Definition خالی برگرداند.
- `MultipleOperationsMigration`: `up()` دو Create Table با نام‌های test-only متفاوت تعریف کند تا هر اجرای زودهنگام observable باشد.
- دو Migration بعدی کوچک با IDهای `after_empty_operation` و `after_multiple_operations` به‌ترتیب effect test-owned مجزا ایجاد کنند؛ پس از invalid operation-count نباید اجرا یا ثبت شوند.

تمام table/column nameها test-prefixed و ثابت باشند؛ قبل از اجرا collision check شوند و در cleanup حذف شوند. `down()` در هیچ سناریوی v1.21 اجرا نمی‌شود.

## Identity / migrationTags Contract

Integration Test دقیقاً contract v1.19/v1.20 را از مسیر عمومی exercise می‌کند:

```kotlin
val configuration = migrationConfig {
    migration<CreateTestUsers>()
    migrationGroup("test_users") {
        migration<AddTestUsersEmail>()
    }
    migration<CreateTestPosts>()
}

val migrator = MigrationMigrator(configuration = configuration)
```

- Identity از annotation روی declaration می‌آید.
- `migrationTags` فقط compile-time tag holder است.
- `migration<T>()` membership و order را ثبت می‌کند.
- Group ترتیب structural configuration را نشان می‌دهد؛ transaction معنا نمی‌دهد.
- KClass/annotation metadata به سازوکار test instantiation یا ID دستی تبدیل نمی‌شود.
- ترتیب fixtureها طوری انتخاب شود که ID lexical order با registration order یکسان نباشد.

## Scenario 1: Successful Migration

این Scenario و Scenarioهای state-dependent بعدی در همان test method اصلی و با ترتیب صریح اجرا می‌شوند. به ترتیب اجرای چند `@Test` تکیه نمی‌شود.

ترتیب کامل lifecycle همان test method:

```text
env/config + exclusive database guard
→ successful migrations
→ rerun same configuration
→ create owned blocker
→ failure sequence
→ repeat failure sequence to verify resume
→ zero-operation rejection and later-migration guard
→ multi-operation rejection and later-migration guard
→ finally cleanup owned objects / restore config / close JDBC
```

Configuration به ترتیب `CreateTestUsers`، Group شامل `AddTestUsersEmail` و سپس `CreateTestPosts` ثبت شود. ترتیب این IDها عمداً با alphabetical order متفاوت است.

Test نتیجه را از callback واقعی capture کند؛ production API جدید `migrate(): ExecuteResult` تعریف نشود:

```kotlin
val result = migrateAndCapture(migrator) // helper خصوصی کوچک برای API callback فعلی
```

Assertions روی database واقعی:

- Migrator نتیجهٔ success بدهد.
- جدول users، ستون‌های تعریف‌شده و `email` موجود باشند.
- جدول posts موجود باشد.
- ردیف‌های `system_migration` به ترتیب اجرای مورد انتظار، دقیقاً IDهای `migrationTags` را داشته باشند.
- تمام سه migration موفق در batch یکسان ثبت شده باشند.

استفاده از ordering dependency (`AddTestUsersEmail` بدون جدول users نباید موفق شود) همراه با ID order متفاوت، اجرای registration order را در برابر sort شدن IDها قابل مشاهده می‌کند.

## Scenario 2: Re-run

بلافاصله پس از موفقیت Scenario 1، همان Configuration و همان `MigrationMigrator` در همان test method دوباره اجرا شود.

Assertions:

- اجرای دوم success بدهد.
- schema تغییری نکند و migrationها دوباره اجرا نشوند. DDLهای fixture عمداً `IF NOT EXISTS` یا duplicate-tolerant نباشند؛ اجرای مجدد operationها باید failure می‌داد.
- history همان سه tag را دقیقاً یک بار داشته باشد.
- batchها تغییر نکنند و batch جدیدی ساخته نشود.

## Scenario 3: Failure and Resume

پس از Scenario 2، در همان lifecycle اصلی یک blocker table test-owned با JDBC test setup بساز و failure configuration را با دو migration موفق، سپس Migration شکست‌خورده و یک Migration بعدی ثبت کن. این blocker فقط پس از clean-DB guard و برای ایجاد failure قطعی ساخته می‌شود؛ DDLهای خود Migration همچنان از API/Migrator/Executor واقعی می‌گذرند. ثبت‌های اول به صورت top-level و Group تعریف شوند تا ordering ساختاری قابل مشاهده باشد؛ Group هیچ transaction semantics ندارد.

```text
FailureCreateUsers               → success
FailureAddEmail                  → success (inside Group)
BrokenMigration                  → CREATE TABLE برای blocker موجود → real DB failure
MigrationAfterFailure            → must not execute
```

Assertions اجرای اول:

- callback یک failure واقعی DDL برگرداند و context خطا نام blocker را نشان دهد.
- schema و record دو Migration موفق باقی بمانند.
- هر دو ID موفق با batch دوم ثبت شوند.
- `broken_migration` و `migration_after_failure` در history نباشند.
- اثر قابل مشاهدهٔ `MigrationAfterFailure` ایجاد نشده باشد.
- نبود transaction/rollback مطابق v1.20 حفظ شود؛ Plan هیچ rollback یا repair خودکاری اضافه نمی‌کند.

اجرای دوباره در حالی که blocker باقی است و در همان test method:

- دو Migration موفق skip شوند؛ duplicate error آن‌ها رخ ندهد.
- Migration شکست‌خورده دوباره pending باشد و همان blocker failure را ایجاد کند.
- history تغییر نکند و Migration بعدی هنوز اجرا/ثبت نشود.

این scenario رفتار resume را تا اولین Migration هنوز ثبت‌نشده مشاهده می‌کند. برای عبور از Migration شکست‌خورده، test رفتار DB را خودکار repair نمی‌کند؛ تغییر schema یا retry خودکار خارج از قرارداد است.

## Scenario 4: Registration Ordering

Scenario 1 علاوه بر success، ordering contract را می‌سنجد:

```text
migration<CreateTestUsers>()
migrationGroup("test_users") { migration<AddTestUsersEmail>() }
migration<CreateTestPosts>()
```

اولویت ordering از Configuration است، نه MigrationId، class name، package یا filename. وابستگی Add Column به جدول users و ترتیب persisted history این رفتار را اثبات می‌کنند. تست به private execution log یا internal collection assertion وابسته نشود.

## Scenario 5: Exactly-One-Operation

این دو بررسی پس از lifecycle اصلی، با ID و نام table مجزا و در همان test method اجرا می‌شوند؛ به JUnit ordering یا state تست دیگری وابسته نیستند.

دو Configuration مستقل با fixtureهای test-local اجرا شوند؛ هرکدام بعد از invalid Migration یک later-effect Migration با ID/table مستقل دارند:

```text
empty_operation      → up() returns MigrationDefinition with 0 entries
after_empty_operation → must not run
multiple_operations  → up() returns MigrationDefinition with 2 entries
after_multiple_operations → must not run
```

Assertions برای هر دو:

- Migrator failure بدهد.
- هیچ DDL مربوط به operationهای تعریف‌شده اجرا نشود؛ در multi case هر دو fixture table غایب باشند.
- ID مربوطه در `system_migration` ثبت نشود.
- ID و effect مربوط به later Migration ثبت/ایجاد نشود.
- Migrationهای بعدی Configuration شروع نشوند.
- invariant بر اساس تعداد `IMigrationApi` در Definition است، نه تعداد SQL statement یک renderer.

Integration Test با DB واقعی نبود DDL، نبود history record و اجرا نشدن effect مربوط به Migration بعدی را مشاهده می‌کند. «هیچ executor dispatch رخ نداد» به‌تنهایی observable از مسیر واقعی و بدون instrument کردن Executor نیست؛ آن جزء دقیقاً با source و unit regression موجود `MigrationMigratorTest` پوشش داده می‌شود. Integration Test برای شمردن dispatch fake یا wrapper تزریقی نمی‌سازد.

این Integration Test، رفتار خارجی را assert می‌کند. جزئیات `operations` list، AST یا internal helper فقط در unit test submoduleها می‌مانند.

## Risks

- اگر `data_base:migration` dependencyهای test-only را نداشته باشد، top-level `test` نمی‌تواند public classes submoduleها را کامپایل کند؛ Gradle dependency لازم است، ولی production graph نباید تغییر کند.
- API Migrator callback-based است؛ helper test باید فقط callback فعلی را capture کند و به sync behavior موجود متکی باشد. API return-valued یا async wrapper جدید وارد scope نیست.

- `BrokenMigration` باید failure deterministic و محدود به test-prefixed object داشته باشد؛ پیام خطا فقط به‌اندازه‌ای assert شود که مشخص کند blocker مورد انتظار باعث failure بوده است، نه متن vendor-specific کامل.
