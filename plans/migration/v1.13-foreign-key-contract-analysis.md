## پرسش‌های Traceability

### Repository و نیاز واقعی

- آیا source, examples, docs, tests یا TODOها نیاز واقعی Foreign Key را نشان می‌دهند؟
- CREATE TABLE فعلی چه constraintهایی را مدل می‌کند؟ آیا table-level constraint node یا FK model وجود دارد؟
- آیا FK هنگام CREATE TABLE تعریف می‌شود یا operation تغییر schema جداگانه لازم است؟
- API، AST، Builder، dialect registry، renderer، executor و example فعلی چه conventionی دارند؟
- آیا abstraction موجود از query یا manager قابل استفاده است، یا migration باید از pipeline خودش عبور کند؟
- آیا v1.2 dependency واقعی است؟ تقدم شمارهٔ نسخه dependency نیست.

### Lifecycle و عملیات

برای هر مورد تصمیم adopt/defer/reject ثبت شود:

- افزودن Foreign Key به جدول موجود.
- تعریف FK داخل CREATE TABLE.
- حذف Foreign Key موجود.
- تغییر action یا rename constraint.
- آیا create به تنهایی migration عملی و قابل تکمیل است یا drop/recreate هم لازم است؟
- آیا DROP FOREIGN KEY باید operation مستقل و هم‌زمان باشد یا contract بعدی؟

SQL و نیاز واقعی هر کدام جدا ثبت شوند. وجود CREATE به‌تنهایی دلیل قطعی برای ساخت یا حذف هم‌زمان نیست.

### Single و composite

شواهد باید مشخص کنند contract اولیه:

- یک جفت local/reference column می‌گیرد یا دو فهرست ordered برای composite.
- حداقل تعداد ستون و برابر بودن طول دو فهرست چگونه validate می‌شود.
- ترتیب جفت‌شدن ستون‌ها و duplicate policy چیست.
- setter تکراری چه رفتاری دارد.
- آیا referenced composite key با همان ترتیب لازم است.

Multi-column index را reuse نکنید؛ FK دو فهرست positionally paired دارد و semantics خودش را دارد.

### Identifier و reference model

بررسی شود:

- نام FK الزامی، اختیاری یا تولیدشده است؛ collision scope چیست.
- schema/database برای جدول مبدأ و مقصد پشتیبانی می‌شود یا نه.
- self-reference و cross-schema reference چه قواعدی دارند.
- API تک‌ستونی یا composite چگونه table/columnهای مقصد را بیان می‌کند.
- trimming، حفظ casing، quoting و escaping از convention repository پیروی می‌کند یا نیاز متفاوت دارد.
- آیا مدل فعلی identifier می‌تواند schema qualification را بدون SQL خام بیان کند.

بدون evidence از schema introspection برای حدس نام constraint یا وجود جدول/ستون استفاده نشود.

### ON DELETE و ON UPDATE

هرکدام جداگانه بررسی شوند:

- معنای action تنظیم‌نشده و تفاوتش با action صریح پیش‌فرض.
- پشتیبانی CASCADE، RESTRICT، NO ACTION، SET NULL و SET DEFAULT در هر محصول.
- آیا انتخاب action باید enum تایپ‌شده باشد.
- آیا قاعده‌ای به nullability یا engine وابسته است و کدام لایه مسئول آن است.
- آیا syntax یا اثر action بین MySQL و MariaDB یا نسخه‌ها فرق دارد.

DEFAULT و omitted clause یکسان فرض نشوند. SQL action مجاز را validate کند؛ engine و schema محدودیت واقعی را اعمال کنند مگر repository evidence الزام دیگری ثابت کند.

### MySQL و MariaDB

مستندات رسمی و نسخه‌های مشخص‌شده جداگانه بررسی شوند:

- syntax افزودن با ALTER TABLE در برابر تعریف در CREATE TABLE؛
- syntax حذف FK و اینکه DROP INDEX برای آن کافی است یا نه؛
- نام‌گذاری constraint و scope نام؛
- single/composite FK و matching با referenced key؛
- referential actionها و omitted/default behavior؛
- engine، type/sign، collation، index، schema و partitioning constraints؛
- self-reference و cross-schema؛
- version boundary و تفاوت واقعی محصول‌ها.

از ارث‌بری MariaDbDialect از MySqlDialect برابری syntax نتیجه‌گیری نشود. grammar رسمی، registration واقعی و behavior هر محصول جدا ثبت شوند.

### Version و execution policy

- compatibility target repository از build/docs/release policy استخراج شود. اگر اعلام نشده، finding باشد؛ نسخهٔ local developer minimum support نیست.
- minimum syntax/product version هر feature از منابع رسمی ثبت شود و با target کلی یکی فرض نشود.
- v2.1 را بررسی کنید: targetDatabaseVersion مربوط به generation است، detected DatabaseServerInfo به execution policy.
- مشخص شود FK واقعاً version-aware generation یا capability detection لازم دارد یا خیر.
- renderer به manager، connection یا introspection وابسته نشود.
- executor از MigrationExecutor و IQueryExecute path موجود استفاده کند؛ executeSelect یا metadata query فقط با evidence نیازمند آن اضافه شود.
- mismatch باعث rewrite خاموش SQL نشود.

### Architecture و validation

- API/AST از execution مستقل بمانند.
- Builder فقط DSL input را validate کند؛ renderer پیش از quoting/composition AST مستقیم را دفاعی بررسی کند.
- وجود schema/table/column/index، engine و eligibility بدون evidence و contract صریح introspect نشود.
- executor خطای database/manager را حفظ کند.
- dependency direction معکوس نشود و JDBC به API/AST/Builder/renderer راه پیدا نکند.
- abstraction عمومی Constraint، ForeignKeyOptions یا AlterTable فقط در صورت وجود contract مشترک واقعی مطرح شود.
- بررسی شود آیا v1.2 واقعاً لازم است یا این feature مستقل از آن است.

### Tests و compatibility

Final Contract باید test plan قابل اجرا داشته باشد:

- required fields، trim و AST ناقص.
- single/composite، paired order، duplicate و repeated setters.
- schema qualification و identifier quote/escape.
- ماتریس ON DELETE/UPDATE و omitted clause.
- SQL دقیق MySQL و MariaDB.
- executor success/failure روی IQueryExecute واقعی و اثبات عدم استفاده از executeSelect، مگر شواهد خلاف آن.
- metadata/capability fake فقط روی manager abstraction موجود، اگر واقعاً لازم است.
- integration test اختیاری در DB اختصاصی و جدا از unit test.
- regression v1.0 تا v1.12 و SQL پیش‌فرض unchanged.
- source/binary compatibility اثر API و AST عمومی.

## Candidate API Surface

نمونه‌ها فقط برای ارزیابی‌اند، نه API قطعی:

        tableName("orders")
        name("fk_orders_user")
        column("user_id")
        referencesTable("users")
        referencesColumn("id")
        onDelete(ForeignKeyAction.CASCADE)
        onUpdate(ForeignKeyAction.RESTRICT)

        tableName("order_items")

Traceability باید مشخص کند این‌ها یک operation، contract جدا، API مربوط به CREATE TABLE یا candidate نامناسب‌اند. آن‌ها را مستقیم به implementation منتقل نکنید.

## Traceability Result — 2026-09-29

### Repository Evidence

- جست‌وجوی source، tests، examples و module docs مورد FK API/AST/Builder/renderer/executor پیدا نکرد. موارد موجود در roadmapها صریحاً Foreign Key را برای مرحلهٔ بعدی Migration ذکر می‌کنند. Repository use case اجرایی یافت نشد؛ این به‌تنهایی مانع نیست، چون FK یک قابلیت بنیادی DDL است و roadmap خود کتابخانه آن را پوشش‌نداده ثبت کرده است.
- API فعلی CREATE TABLE فقط table، فهرست columnها و ifNotExists دارد. Column AST نوع، default، nullability، autoIncrement و primary Boolean دارد؛ table-level constraint list یا FK node ندارد.
- CREATE TABLE renderer فقط columnها را render می‌کند و بیش از یک column-level primary key را رد می‌کند؛ composite primary key و table constraints در این برش وجود ندارند. Example نیز سه column عادی و یک column-level primary key می‌سازد.
- Operations مستقل مانند ADD COLUMN و CREATE/DROP INDEX از API → AST → Builder → dialect capability/renderer عبور می‌کنند. MigrationExecutor SQL را از executeOut و renderer می‌گیرد و از مسیر IQueryExecute.executeTable می‌فرستد.
- MySqlDialect هر AST را در registry جداگانه ثبت می‌کند. MariaDbDialect از MySqlDialect ارث می‌برد، اما grammar و behavior محصول باید از مستندات خودش تعیین شود.
- IQueryExecute.executeTable مرز موجود DDL است. metadata access در executor صرفاً برای policy مربوط به RENAME COLUMN و syntax قدیمی آن دیده شد؛ path عمومی ADD/DROP DDL introspection ندارد.
- DatabaseConfig targetDatabaseVersion و IQueryExecute.getDatabaseServerInfo را دارد. v2.1 target را برای generation و detected info را برای execution policy از هم جدا کرده است. Syntax اصلی ADD/DROP FK در این candidateها product-specific rewrite نمی‌خواهد؛ engine/schema eligibility را database تعیین می‌کند.
- v1.2 در وضعیت planned دربارهٔ اشتراک CREATE/DROP TABLE است. هیچ dependency فنی با operation مستقل FK پیدا نشد؛ صرف تقدم شماره dependency نیست.
- compatibility target کلی پروژه در build/docs/release metadata پیدا نشد. این finding می‌ماند؛ حداقل نسخه از سرور نصب‌شدهٔ توسعه‌دهنده حدس زده نمی‌شود.

### MySQL Evidence

بر اساس MySQL 8.4 Reference Manual، بخش FOREIGN KEY Constraints:

- Syntax برای CREATE TABLE و ALTER TABLE هردو وجود دارد. افزودن به جدول موجود با ALTER TABLE ... ADD [CONSTRAINT symbol] FOREIGN KEY (col_name, ...) REFERENCES tbl_name (col_name, ...) انجام می‌شود.
- composite FK بومی grammar است و ترتیب ستون‌ها در هر دو لیست حفظ می‌شود.
- حذف مستقل با ALTER TABLE ... DROP FOREIGN KEY fk_symbol انجام می‌شود؛ index drop operation جایگزین حذف constraint نیست.
- constraint symbol اختیاری است و در صورت حذف، server نام می‌سازد. symbol صریح باید در database unique باشد. برای DROP بدون introspection، نام صریح deterministic لازم است.
- ON DELETE و ON UPDATE شامل RESTRICT، CASCADE، SET NULL، NO ACTION و SET DEFAULT هستند. برای InnoDB، omitted clause معادل NO ACTION است و NO ACTION معادل RESTRICT است. SET DEFAULT توسط parser شناخته می‌شود ولی InnoDB و NDB آن را reject می‌کنند.
- FK child و parent باید engine یکسان داشته باشند؛ column types باید compatible باشند و برای INTEGER/DECIMAL size/sign یکسان باشد؛ string character set/collation باید یکسان باشد.
- index لازم است؛ InnoDB می‌تواند index child را خودکار بسازد. referenced key باید index مناسب با ترتیب متناظر داشته باشد؛ reference به non-unique key در MySQL جدید deprecated و با flag کنترل می‌شود. MySQL 8.4 پیشنهاد می‌کند از referenced primary/unique key استفاده شود.
- InnoDB user-partitioned tables را برای FK پشتیبانی نمی‌کند. SET NULL با local NOT NULL سازگار نیست.
- engine و database schema eligibility در Builder/Renderer قابل اثبات نیست و به server سپرده می‌شود.

### MariaDB Evidence

بر اساس مستندات رسمی MariaDB، Foreign Keys و ALTER TABLE:

- FK هنگام CREATE TABLE یا با ALTER TABLE به جدول موجود اضافه می‌شود. برای مرحلهٔ مستقل، ADD FOREIGN KEY و DROP FOREIGN KEY صریحاً مستند شده‌اند.
- syntax مقدار یک column یا column list را می‌پذیرد و برای composite FK دو لیست ordered لازم است.
- ON DELETE/UPDATE مقادیر RESTRICT، NO ACTION، CASCADE، SET NULL و SET DEFAULT را در grammar/شرح دارد؛ در InnoDB، SET DEFAULT پشتیبانی نمی‌شود. MariaDB ALTER TABLE مستند می‌کند SET DEFAULT فقط برای engine قدیمی PBXT است که disabled/unsupported در مسیر معمول است.
- action تنظیم‌نشده در MariaDB برابر RESTRICT است. NO ACTION معادل RESTRICT است. SET NULL در عمل به nullable بودن local columns نیاز دارد.
- FK در MariaDB فقط روی storage engine پشتیبان و طبق مستندات فعلی فقط InnoDB قابل اتکا است؛ temporary و partitioned tables و views محدودیت دارند. parent/child باید engine یکسان داشته باشند و referenced columns indexed باشند.
- constraint name اختیاری است و server می‌تواند نام بسازد. مستند رسمی فعلی namespace نام‌ها را database-wide توصیف می‌کند، با تغییر MariaDB 12.1 به uniqueness per table. constraint name اجباری در API از وابستگی به naming خودکار جلوگیری می‌کند، ولی collision و scope واقعی همچنان به server واگذار می‌شود.
- مستند رسمی برای ADD/Drop مثال schema-qualified در database جاری دارد. Repository identifier renderer فعلی schema.table را به‌عنوان دو شناسه quote نمی‌کند؛ schema qualification در اولین برش defer می‌شود.

| Composite FK | هر دو محصول ordered column lists را پشتیبانی می‌کنند. | adopt | حداقل یک local و یک referenced column؛ تعداد دو لیست برابر؛ ترتیب positionally paired؛ duplicate داخل هر لیست رد شود. |
| Constraint name اختیاری یا auto-generated | هر دو server می‌توانند نام بسازند، اما DROP نام constraint را می‌خواهد و بدون introspection نام خودکار قابل اتکا نیست. | reject | name اجباری برای add و drop؛ duplicate/name namespace collision را server گزارش می‌کند، Builder metadata نمی‌خواند. |
| ON DELETE و ON UPDATE | هر دو محصول از actionهای مشترک CASCADE، RESTRICT، NO ACTION و SET NULL پشتیبانی می‌کنند. omitted behavior محصول/engine است. | adopt | هر دو action اختیاری و مستقل؛ absence یعنی clause تولید نشود؛ action با enum تایپ‌شده باشد. |
| NO ACTION و RESTRICT | در InnoDB و MariaDB semantics یکسان دارند؛ syntax هر دو محصولی است. MySQL NDB می‌تواند NO ACTION را deferred معنا کند. | adopt به‌عنوان دو SQL token مستقل | enum هر دو را نگه می‌دارد؛ library رفتار تراکنشی/engine را شبیه‌سازی نمی‌کند. |
| SET DEFAULT | MySQL parser می‌پذیرد ولی InnoDB/NDB reject می‌کنند؛ MariaDB تنها legacy PBXT را ذکر می‌کند. | reject از قرارداد مشترک اولیه | feature برای engineهای هدف قابل اتکا نیست. |
| FK supporting index | محصولات ممکن است index child را خودکار بسازند؛ referenced side باید index مناسب داشته باشد. v1.7 index API موجود است. | defer مدیریت index به database/user | FK DSL index name/options نمی‌گیرد؛ introspection یا مدیریت خودکار index توسط library انجام نمی‌شود. خطا و side effect server به caller واگذار می‌شود. |
| Schema-qualified table names | SQL product grammar می‌تواند database qualifier داشته باشد؛ renderer فعلی identifier رشته‌ای را یکپارچه quote می‌کند. | defer | اولین contract فقط table identifier بدون schema qualifier می‌گیرد؛ قابلیت schema نیازمند model و tests مجزاست. |
| MATCH clause، SET DEFAULT، deferrable، IF EXISTS، cascading drops | تفاوت product/engine یا خارج از نیاز حداقلی‌اند. | reject/defer | MATCH به دلیل بی‌اثر بودن در MariaDB و product semantics رد می‌شود؛ SET DEFAULT/IF EXISTS/cascade خارج scope؛ deferrable خارج از MySQL/MariaDB contract. |
| DDL preflight/introspection | manager می‌تواند metadata بخواند، اما create/drop SQL مستقل و خطاهای schema database خودش تشخیص می‌دهد. | reject از scope اولیه | executor فقط executeTable؛ هیچ executeSelect یا SHOW CREATE/INFORMATION_SCHEMA برای تکمیل operationها اضافه نشود. |

### Final Contract Decision

v1.13 شامل دو operation مستقل برای تغییر جدول موجود است: ADD FOREIGN KEY و DROP FOREIGN KEY. این scope یک cycle عملی و قابل استفاده می‌دهد و با syntax مستقیم MySQL/MariaDB منطبق است. Inline definition در CREATE TABLE deferred می‌ماند.

Candidate DSL نهایی:

    createForeignKey {
        tableName("orders")
        name("fk_orders_user")
        columns("tenant_id", "user_id")
        referencesTable("users")
        referencesColumns("tenant_id", "id")
        onDelete(ForeignKeyAction.CASCADE)
        onUpdate(ForeignKeyAction.RESTRICT)
    }

    dropForeignKey {
        tableName("orders")
        name("fk_orders_user")
    }

قرارداد دقیق:

- createForeignKey AST: tableName، constraintName، ordered columnNames، referencedTableName، ordered referencedColumnNames، onDelete? و onUpdate?.
- dropForeignKey AST: tableName و constraintName.
- DSL ورودی column/columns و referenceها به‌شکل listهای paired است؛ single-column با list تک‌عضوی استفاده می‌شود.
- هر دو list حداقل یک شناسه دارند، تعدادشان برابر است، ترتیب‌شان معنای positional دارد و duplicate درون هر list پس از trim/case-insensitive comparison رد می‌شود. spelling اصلی پس از trim حفظ می‌شود.
- نام constraint اجباری است؛ Builder/Renderer نام خودکار یا collision check نمی‌سازند. SQL database namespace فعلی را enforce می‌کند.
- reference فقط به table بدون schema qualifier در این برش محدود است. schema field مستقل یا تفسیر dot در identifier ساخته نمی‌شود.
- onDelete و onUpdate مستقل و optional هستند. enum: CASCADE، RESTRICT، NO_ACTION، SET_NULL. اگر مشخص نشده باشد clause حذف می‌شود؛ هیچ default action در SQL تزریق نمی‌شود. SET_DEFAULT پشتیبانی نمی‌شود.
- SQL canonical add:
  ALTER TABLE <quoted-table>
  ADD CONSTRAINT <quoted-name>
  FOREIGN KEY (<quoted-local-columns>)
  REFERENCES <quoted-reference-table> (<quoted-reference-columns>)
  [ON DELETE action]
  [ON UPDATE action]
- SQL canonical drop:
  ALTER TABLE <quoted-table> DROP FOREIGN KEY <quoted-name>
- identifiers با quoting/escaping dialect فعلی render می‌شوند. SQL خام و SQL string options پذیرفته نمی‌شوند.
- Builder ورودی ناقص، خالی، unequal cardinality و duplicateهای درون هر فهرست را رد می‌کند. Renderer همان invariants را روی AST مستقیم قبل از quoting/composition دوباره بررسی می‌کند.
- database مسئول وجود جدول/ستون، matching data type/sign/collation، indexها، engine eligibility، referenced key suitability، nullability/action compatibility، constraint collision و data consistency است. هیچ introspection یا preflight انجام نمی‌شود.
- action omitted به SQL clause تبدیل نمی‌شود؛ behavior حاصل از engine است. contract نمی‌گوید سرورهای مختلف action omitted یا NO_ACTION را با یکسانی تراکنشی اجرا می‌کنند.
- MySQL و MariaDB rendererهای موجود syntax مشترک دارند؛ MariaDbDialect inheritance و registry فعلی حفظ می‌شود. targetDatabaseVersion برای generation این syntax استفاده نمی‌شود و detected version به‌تنهایی سبب rewrite یا fallback نمی‌شود.
- هر دو operation از MigrationExecutor entrypoint موجود در سبک repository، executeOut و IQueryExecute.executeTable استفاده می‌کنند؛ SELECT/manager metadata لازم نیست.
- AST/API/Builder/renderer به manager یا JDBC وابسته نیستند. ForeignKey عمومی options object یا AlterTable abstraction ساخته نمی‌شود.
- CREATE TABLE، CREATE INDEX، DROP INDEX، FK supporting index management، schema qualification، generated names، IF EXISTS، MATCH و migration rollback خارج scope هستند.
- v1.2 dependency نیست. نبود compatibility target کلی repository به‌عنوان finding باقی می‌ماند؛ این تصمیم حداقل version جدیدی ادعا نمی‌کند.
- test plan: AST/Builder validation، single و composite order، unequal lengths/duplicates، identifiers با reserved names و escaping، omitted و هر چهار action، exact SQL برای هر دو dialect، direct incomplete AST، executor success/failure از executeTable، عدم executeSelect، و regression v1.0 تا v1.12. Integration test دیتابیس اختصاصی اختیاری است.
- source/binary impact: APIهای مستقل جدید اضافه می‌شوند؛ API و AST عملیات قبلی تغییر نمی‌کنند. Compatibility عمومی migration interfaceها سیاست اعلام‌شده ندارد و این محدودیت به‌عنوان finding ثبت می‌شود.
