# Migration v1.7: DROP INDEX Contract

وضعیت: `implemented`

## پیش‌شرط و هدف

`v1.6 CREATE INDEX` پیاده‌سازی شده است. مرحلهٔ بعدی خانوادهٔ Index در مسیر migration، operation مستقل `DROP INDEX` است.

هدف، حذف یک index موجود از یک جدول با نام صریح آن است. operation باید از pipeline واقعی API → AST → Builder → Dialect/Renderer → Executor عبور کند و اجرای DDL را به `data_base:manager` موجود بسپارد.

## مبنا و traceability از v1.6

این قرارداد بر implementation واقعی `CREATE INDEX` بنا می‌شود:

- API موجود در `interfaces/create_index/IMigrationCreateIndexApi.kt` DSL کوتاه `tableName(...)`, `name(...)`, `column(...)` دارد؛ برای `DROP INDEX` همان naming ergonomics به‌کار رود: `tableName(...)`, `name(...)`.
- AST موجود سه identifier mutable/nullable مستقل دارد و Builder در `build()` ورودی‌های خالی را رد می‌کند. AST جدید operation-specific بماند و فقط `tableName` و `indexName` را نگه دارد.
- `MigrationCreateIndexBuilder` فقط whitespace پیرامونی را trim می‌کند و casing و بقیهٔ محتوا را دست‌نخورده نگه می‌دارد. Builder جدید همین convention را دنبال کند.
- `MySqlDialect.registerRenders()` capabilityها را با AST interface در `RendererRegistry` ثبت می‌کند. `DROP INDEX` نیز capability و AST مستقل خود را در همین registry داشته باشد.
- `MigrationExecutor` operationها را از `executeOut` و سپس `IQueryExecute.executeTable` موجود عبور می‌دهد. overload جدید فقط مطابق convention فعلی در همین executor اضافه شود؛ executor یا abstraction production دیگری ساخته نشود.
- renderer `CREATE INDEX` backtick quoting و escaping را با دوبرابرکردن backtick داخلی انجام می‌دهد. Renderer جدید از همین convention استفاده کند.
- پیاده‌سازی v1.7 در مسیرهای متناظر انجام شد: `api/interfaces/drop_index`, `ast/interfaces/drop_index` و `ast/schema/drop_index`, `builder/ast/drop_index` و `builder/dropIndex.kt`, `dialect/nodes/drop_index`, `renderer/nodes/drop_index` و registry در `MySqlDialect`.
- ورودی `IMigrationDropIndexApi` به `IMigrationExecutor` و overload موجود `MigrationExecutor` افزوده شد؛ اجرا از `executeOut` و `IQueryExecute.executeTable` عبور می‌کند.
- تست renderer/example در `A1ExampleDropIndexV1Test` و تست مرز executor در `MigrationExecutorDropIndexTest` ثبت شد؛ هر دو task یعنی `:data_base:migration:example:test` و `:data_base:migration:executor:test` با JDK 24 موفق شدند.
- مثال نسخه‌بندی‌شده در `v1/migrations/drop_index/A1ExampleDropIndexV1.kt` و گزینهٔ خاموش `statusRunDropIndex` به manager مثال افزوده شد.
- plan مشترک `v1.2` همچنان `planned` است؛ v1.7 به abstraction آن وابسته نیست و از execution/rendering موجود استفاده می‌کند.
- compatibility target کلی MySQL در repository اعلام نشده است. این finding حفظ شود و حداقل نسخه از محیط نصب‌شدهٔ توسعه‌دهنده حدس زده نشود.
- syntax پایه با MySQL Reference Manual، بخش `DROP INDEX Statement` تطبیق داده شود: `DROP INDEX index_name ON tbl_name`. syntax این statement به‌تنهایی minimum supported version کلی repository را تعیین نمی‌کند.

## محدوده

در v1.7:

- حذف یک index با نام صریح از یک جدول مشخص.
- MySQL dialect تنها dialect پشتیبانی‌شده است.
- DSL مفهومی:

```kotlin
dropIndex {
    tableName("users")
    name("idx_users_email")
}
```

- SQL مفهومی:

```sql
DROP INDEX `idx_users_email` ON `users`
```

- API و AST مستقل، Builder مختص operation و MySQL renderer مستقل.
- executor موجود و `IQueryExecute.executeTable`.
- مثال نسخه‌بندی‌شده با render-only پیش‌فرض و اجرای صریح/opt-in.
- unit testهای بدون دیتابیس و executor fake در مرز موجود.

خارج از محدودهٔ v1.7:

- `IF EXISTS` یا تبدیل خطای missing index/table به موفقیت.
- preflight، schema introspection، خواندن `SHOW INDEX` یا بررسی وجود جدول/index.
- rename، rebuild یا تغییر definition/options خود index.
- API مستقل برای مدیریت lifecycle مربوط به primary key؛ با این حال `name("PRIMARY")` در همین `DROP INDEX` طبق semantics MySQL حذف primary-key index را درخواست می‌کند.
- دست‌کاری جداگانهٔ UNIQUE constraint، foreign key یا indexهای پشتیبان constraintها. این operation index type را تشخیص نمی‌دهد؛ اگر نام به یک index ثانویهٔ موجود (از جمله unique index) اشاره کند، semantics خود MySQL اعمال می‌شود و خطا/اثر همان سرور به caller می‌رسد.
- index چندستونی به‌عنوان یک عملیات چند-نامی یا هر option جدید dialect.
- rollback، migration history و runner.
- dialectهای غیر از MySQL.

## Contract و invariantها

یک `DropIndex` معتبر شامل این ورودی‌هاست:

```text
DropIndex
├── tableName: non-blank identifier
└── indexName: non-blank identifier (including the special MySQL name PRIMARY)
```

- هر operation فقط یک index نام‌گذاری‌شده را در یک جدول هدف می‌گیرد.
- نام index اجباری است؛ نام از table یا conventionهایی مانند `idx_<table>_<column>` تولید یا اصلاح نمی‌شود.
- `tableName` و `indexName` دو identifier مستقل‌اند؛ هیچ رابطهٔ معنایی بین آن‌ها infer نمی‌شود.
- Builder فقط whitespace پیرامونی را حذف کند؛ casing و محتوای باقی‌ماندهٔ identifier را تغییر ندهد.
- مقدار خالی/whitespace-only برای هر دو فیلد در Builder رد شود.
- `PRIMARY` رد یا بازنویسی نشود؛ به‌عنوان نام ویژهٔ MySQL برای primary-key index، با quoting identifier عادی به سرور فرستاده شود. API جداگانه‌ای برای primary-key operation ساخته نمی‌شود.
- Renderer پیش از quote و SQL composition، AST ناقص یا نامعتبر را رد کند.
- Identifierها bind parameter نیستند و باید با convention فعلی MySQL quote/escape شوند؛ raw SQL fragment پذیرفته نشود.
- operation وجود جدول یا index را بررسی نمی‌کند و metadata دیتابیس را نمی‌خواند.
- برای index غایب، table غایب، permission failure، index موردنیاز foreign key یا هر محدودیت سرور، خطای اصلی manager/database حفظ می‌شود؛ fallback، no-op یا success جعلی وجود ندارد.
- API، AST، Builder، dialect و renderer مستقل از connection، executor و JDBC هستند.
- executor operation را به مسیر execution موجود و `IQueryExecute.executeTable` می‌سپارد.

## API، AST و Builder

- API در package مطابق convention repository و با DSL مفهومی `dropIndex { tableName(...); name(...) }` تعریف شود.
- AST مستقل فقط `tableName` و `indexName` را نگه دارد؛ column، type، uniqueness، `ifExists` و dialect option نداشته باشد.
- Builder مقادیر را trim کند، identifierهای خالی را رد کند و مقدار trimmed را بدون تغییر دیگر در AST ذخیره کند؛ `PRIMARY` نیز به‌عنوان index name پذیرفته شود.
- Renderer validation دفاعی داشته باشد تا AST ساخته‌شدهٔ مستقیم نیز قبل از SQL رد شود.
- هیچ abstraction مشترکی با `CreateIndex` صرفاً برای کاهش چند خط کد اضافه نشود؛ reuse تنها اگر الگوی repository واقعاً آن را ایجاب کند و semantics مستقل operation حفظ شود.

## Dialect و Renderer

- capability جدید `DROP INDEX` در قرارداد dialect تعریف و برای AST آن در registry موجود `MySqlDialect` ثبت شود.
- SQL دقیق:

```sql
DROP INDEX <quoted-index-name> ON <quoted-table-name>
```

- quoting و escaping برای هر دو identifier از همان convention `CREATE INDEX` پیروی کند، از جمله reserved wordها و backtick داخلی.
- هیچ `IF EXISTS`، `UNIQUE`, `ALTER TABLE` جایگزین، `ALGORITHM`, `LOCK` یا option دیگری در v1.7 تولید نشود.
- Renderer فقط AST را مصرف کند و connection، manager، introspection یا executor را نشناسد.

## Executor و خطا

- entry point/overload مورد نیاز به `IMigrationExecutor` موجود افزوده شود.
- `MigrationExecutor` SQL رندرشده را از مسیر `executeOut` و `IQueryExecute.executeTable` اجرا کند.
- خطای manager بدون wrapper/suppression غیرضروری و با cause اصلی به callback برسد.
- fake تست همان interface واقعی `IQueryExecute` را هدف بگیرد؛ abstraction production برای testability ساخته نشود.

## مثال و تست

- مثال در ساختار نسخه‌بندی‌شدهٔ واقعی example module قرار گیرد؛ اجرای DDL فقط با opt-in مشخص فعال شود.
- تست‌های بدون database موارد زیر را پوشش دهند:
  - AST مستقل با فقط table/index name.
  - trim پیرامونی، حفظ casing/محتوا و رد identifier خالی.
  - case preservation صریح: `tableName("  Users  ")` و `name("  Idx_User_Email  ")` در AST به‌ترتیب دقیقاً `Users` و `Idx_User_Email` بمانند و SQL برابر `DROP INDEX `Idx_User_Email` ON `Users`` شود.
  - `PRIMARY` یک `indexName` عادی در DSL و AST است؛ Builder آن را special-case نمی‌کند و Renderer آن را مانند identifierهای دیگر quote می‌کند. SQL دقیق باید `DROP INDEX ``PRIMARY`` ON ``users``` باشد.
  - SQL دقیق `DROP INDEX ... ON ...`.
  - quoting/escaping هر دو identifier برای نام عادی، underscore، reserved word و backtick داخلی.
  - نبود `IF EXISTS` و نبود query/preflight introspection در مسیر executor.
  - executor: ارسال BuiltQuery از طریق `IQueryExecute.executeTable`، callback موفقیت و حفظ failure/cause اصلی.
- integration test فقط روی MySQL اختصاصی و index آزمایشی قابل cleanup؛ اجرای مثال عادی نباید DDL را خودکار اجرا کند.
- regression test operationهای پیشین، از جمله `CREATE INDEX v1.6`، در اجرای نهایی اجرا شود.

## نقشهٔ راه خانوادهٔ Index

این roadmap اطلاع‌رسانی است و scope v1.7 را گسترش نمی‌دهد:

```text
Index v1
├── v1.6: CREATE INDEX (single-column, non-unique)
└── v1.7: DROP INDEX (one named index)
        ↓
Index v2 (future plan)
├── UNIQUE INDEX operations
└── Multi-column index operations
        ↓
Index v3 (future plan)
├── FULLTEXT
├── SPATIAL
└── Dialect-specific options
```

هر operation بعدی plan و traceability مستقل دارد. عملیات مستقل مدیریت constraint/primary-key، foreign key، migration history و runner در scope این plan نیستند. بااین‌حال، مطابق MySQL، `DROP INDEX` با نام `PRIMARY` خود primary-key index را حذف می‌کند؛ این رفتار از همان operation و DSL عمومی index name حاصل می‌شود.
