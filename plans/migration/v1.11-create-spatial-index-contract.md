# Migration v1.11: CREATE SPATIAL INDEX Contract Analysis

وضعیت: `implemented`

## پیش‌زمینه و هدف

عملیات `CREATE INDEX` از v1.6 تا v1.10 پیاده‌سازی شده‌اند؛ `CREATE FULLTEXT INDEX` در v1.10 operation مستقل خود را دارد. مرحلهٔ بعد خانوادهٔ Index، تحلیل قرارداد مستقل `CREATE SPATIAL INDEX` است.

Traceability و implementation انجام شده‌اند. SPATIAL به‌صورت operation مستقل اضافه شد. نام ستون و metadata schema در DSL/AST وارد نمی‌شوند و بررسی دیتابیسی برای تشخیص آن‌ها انجام نمی‌شود.

v1.10 در workspace پیاده‌سازی شده است. این plan وضعیت commit ایجاد نمی‌کند و به commit جدید نیاز عملیاتی نمی‌دهد.

## قرارداد نهایی operation و استقلال از نسخه‌های پیشین

شکل DSL نهایی:

```kotlin
createSpatialIndex {
    tableName("places")
    name("spx_places_geom")
    column("geom")
}
```

SQL مفهومی MySQL:

```sql
CREATE SPATIAL INDEX `spx_places_geom`
ON `places` (`geom`)
```

- `CREATE SPATIAL INDEX` operation مستقل با API و AST مستقل باشد؛ به `createIndex`, `createUniqueIndex`, `createMultiColumnIndex` یا `createFullTextIndex` flag اضافه نشود.
- این operation در v1.11 دقیقاً یک column identifier می‌گیرد: `column(...)`. مستند MySQL spatial index تک‌ستونی را تصریح می‌کند؛ مستند MariaDB نحو تک‌ستونی را تأیید می‌کند اما قاعدهٔ چند spatial-column را صریحاً بیان نمی‌کند. قرارداد کتابخانه تک‌ستونی می‌ماند و دربارهٔ پشتیبانی چندستونی MariaDB ادعایی ندارد.
- `DROP INDEX` v1.7 برای حذف index ساخته‌شده کافی است؛ `DROP SPATIAL INDEX` operation جداگانه تعریف نمی‌شود.
- `UNIQUE`, `PRIMARY KEY`, `FULLTEXT`, `WITH PARSER`, prefix length و گزینه‌های index به این operation اضافه نمی‌شوند.
- operation مستقل، AST را فقط با table/index/column identifierها مدل می‌کند؛ definition ستون، نوع geometry، nullability، SRID، storage engine و metadata جدول بخشی از AST نیستند.

## یافته‌های مستندات رسمی MySQL

این یافته‌ها بر اساس نسخه‌های مستندشده ثبت شده‌اند. چون compatibility target کلی repository اعلام نشده، از آن‌ها حداقل نسخهٔ عمومی library نتیجه‌گیری نمی‌شود:

- MySQL 8.4 مستند می‌کند که `CREATE SPATIAL INDEX name ON table (geometry_column)` برای `InnoDB` و `MyISAM` پشتیبانی می‌شود و ستون indexشده باید `NOT NULL` و دارای SRID مشخص باشد. MySQL 8.0 الزام `NOT NULL` را ذکر می‌کند؛ شرط SRID-restricted بودن همچنین برای استفادهٔ optimizer لازم است.
- MySQL 8.0 `CREATE INDEX Statement` محدودیت را صریح‌تر می‌کند: SPATIAL index تنها برای یک spatial column است؛ ستون باید `NOT NULL` باشد؛ prefix length ممنوع است؛ SPATIAL با `PRIMARY KEY` یا `UNIQUE` ترکیب نمی‌شود.
- spatial index از نوع R-tree است. داشتن index با قابل‌استفاده‌بودن آن توسط optimizer یکسان نیست. مستند 8.4 شرط SRID را برای ساخت و استفادهٔ optimizer بیان می‌کند؛ مستند 8.0 شرط SRID-restricted را برای optimizer توضیح می‌دهد. چون compatibility target repository مشخص نیست، library این اختلاف نسخه‌ای را با introspection یا rewrite حل نمی‌کند.
- geometry typeهای پایه شامل `GEOMETRY`, `POINT`, `LINESTRING`, `POLYGON` و نوع‌های collection هستند. Library از نام column نمی‌تواند نوع واقعی آن را تعیین کند.
- از MySQL 8.0.12 به بعد، index روی spatial column باید SPATIAL باشد؛ این نکته به‌تنهایی minimum version کلی یا syntax floor operation را تعیین نمی‌کند.
- برای حذف spatial index، MySQL همان `DROP INDEX index_name ON table_name` را نیز مستند می‌کند؛ operation v1.7 قابل reuse است.

## محدودهٔ نهایی

- operation از registry مشترک `MySqlDialect` و `MariaDbDialect` قابل دسترسی خواهد بود. این reuse با مستند رسمی MariaDB برای syntax و پشتیبانی engineهای MariaDB تأیید شده است؛ matrix engine در دو محصول متفاوت است و نباید یکسان فرض شود.
- یک index با نام صریح روی یک جدول و یک spatial column موجود.
- table name، index name و column name صریح و اجباری‌اند؛ auto-generated name خارج از scope است.
- Renderer فقط SQL تولید می‌کند؛ connection، manager، introspection یا schema metadata نمی‌شناسد.
- `NOT NULL`، spatial type، SRID، engine/table eligibility و محتوای geometry محدودیت schema/database هستند. چون API فقط نام ستون موجود را می‌گیرد و introspection خارج scope است، Builder/Renderer آن‌ها را validate نمی‌کنند؛ خطای manager/database به caller می‌رسد. MySQL 8.4 مستندات برای ساخت index، `NOT NULL` و SRID مشخص را ذکر می‌کنند؛ مستند MySQL 8.0 الزام `NOT NULL` را تصریح و SRID-restricted بودن را برای استفادهٔ optimizer لازم می‌داند. مستند جاری MariaDB `NOT NULL` را ذکر می‌کند و شرط SRID مشابه را تصریح نمی‌کند؛ تفاوت در سطح database باقی می‌ماند.
- duplicate-column policy موضوعیت ندارد اگر قرارداد نهایی یک ستون داشته باشد. duplicate index/table names بین operationها یا وجود index از پیش ساخته‌شده در این operation بررسی نمی‌شوند.
- SQL identifierها را با quoting/escaping renderer MySQL موجود تولید می‌کند؛ identifier bind parameter نیست.
- compatibility target عمومی repository پیدا نشد و به‌عنوان finding باقی است. نسخهٔ نصب‌شدهٔ توسعه‌دهنده مبنا نیست؛ این operation ادعای minimum version عمومی نمی‌کند.

## Traceability Result

Traceability بر اساس کد موجود repository و مستندات رسمی انجام شد. موارد زیر نتیجهٔ evidence است، نه فرض برگرفته از شباهت FULLTEXT:

1. **Repository Evidence:** مسیر v1.10 شامل API، AST، Builder، capability مستقل، registration در `MySqlDialect` و executor overload است. این ساختار اجازه می‌دهد SPATIAL با operation مستقل به pipeline موجود افزوده شود؛ hierarchy موازی یا abstraction تولیدی تازه لازم نیست.
2. **MySQL Evidence:** MySQL 8.0، Spatial Indexes را فقط برای InnoDB/MyISAM، روی یک spatial column، با `NOT NULL` و بدون prefix یا UNIQUE/PRIMARY KEY مجاز می‌داند. MySQL 8.4 مستند می‌کند: `CREATE SPATIAL INDEX name ON table (column)`، `NOT NULL` و SRID مشخص برای ساخت. SRID-restricted بودن همچنین شرط استفادهٔ optimizer است؛ ساخت index و استفادهٔ optimizer دو موضوع جدا هستند.
3. **MariaDB Evidence:** مستند رسمی جاری MariaDB مثال `CREATE SPATIAL INDEX ... ON ... (g)` را تأیید می‌کند و SPATIAL index را در MyISAM، Aria و InnoDB پشتیبانی می‌کند؛ ستون باید `NOT NULL` باشد. پشتیبانی geometry column در engineهای بیشتری از spatial index است. مستند جاری MariaDB قاعدهٔ چندستونی یا شرط SRID مشابه MySQL 8.4 را صریحاً تعیین نمی‌کند؛ این plan چنین ادعایی ندارد.
4. **Compatibility Target:** بررسی source، docs و build/repository metadata، نبود compatibility target عمومی یا minimum supported MySQL/MariaDB را نشان می‌دهد. نسخهٔ نصب‌شدهٔ توسعه‌دهنده baseline نیست و حداقل نسخهٔ کلی از grammar نسخه‌های مستندشده استنتاج نمی‌شود.
5. **Single-column Decision:** قطعی: API این operation دقیقاً یک `column(...)` می‌گیرد. تک‌ستونی بودن محدودیت MySQL است؛ در MariaDB این محدودیت دامنهٔ قرارداد کتابخانه است و دربارهٔ multi-column spatial index آن ادعایی نمی‌شود.
6. **Builder/Renderer Validation Decision:** Builder شناسه‌ها را طبق convention موجود trim و blank را reject می‌کند؛ casing و spelling را نگه می‌دارد. Renderer AST ناقص را دفاعی پیش از quoting رد می‌کند. نوع geometry، nullability، SRID و engine introspect یا validate نمی‌شوند.
7. **Executor/Reusability Evidence:** `MariaDbDialect` از `MySqlDialect` ارث می‌برد و registry جدا ندارد. مستند رسمی MariaDB نحو operation را پشتیبانی می‌کند؛ registration مشترک موجود برای همین grammar پذیرفتنی است، با توجه به تفاوت engine matrix. executor موجود از `executeOut` به `IQueryExecute.executeTable` می‌رسد و preflight لازم نیست. `DROP INDEX` v1.7 برای حذف کافی است.
8. **v1.2 Dependency Check:** v1.2 همچنان `planned` است و abstraction CREATE TABLE/DROP TABLE را بررسی می‌کند. v1.11 به آن abstraction وابسته نیست؛ شماره نسخه blocker نیست.
9. **Final Contract Decision:** candidate تأیید شد با این قیدها: API تک‌ستونی؛ engine و SRID/schema eligibility مسئولیت database؛ بدون ادعای compatibility target عمومی یا multi-column MariaDB. وضعیت به `Implementation Ready` تغییر یافت.

## API/AST و Builder نهایی

قرارداد نهایی:

```text
createSpatialIndex {
    tableName(table)
    name(index)
    column(column)
}

CreateSpatialIndexAst
├── tableName: String?
├── indexName: String?
└── columnName: String?
```

AST مستقل می‌ماند و هیچ state مربوط به column definition، SRID یا engine نمی‌گیرد. `NOT NULL`، geometry type و SRID ویژگی schema/table هستند و از introspection به AST منتقل نمی‌شوند. Builder طبق convention واقعی repository whitespace پیرامونی را trim می‌کند، spelling/casing را تغییر نمی‌دهد و مقدار blank را رد می‌کند. چون قرارداد یک‌ستونی است، validation فهرست/duplicate لازم نیست. Renderer AST ناقص مستقیم را پیش از quoting دفاعی رد می‌کند.

`column(...)` تنها API این نسخه است؛ `columns(...)` اضافه نمی‌شود. AST فقط table/index/column identifierها را نگه می‌دارد و metadata تعریف ستون/جدول نمی‌گیرد.

## Contract نهایی Renderer و Executor

SQL پیشنهادی:

```sql
CREATE SPATIAL INDEX <quoted-index-name>
ON <quoted-table-name> (<quoted-spatial-column>)
```

- `SPATIAL` معنای ثابت operation است، نه flag ورودی.
- renderer identifierها را با quote/escape MySQL تولید می‌کند؛ prefix، `UNIQUE`, `USING`, algorithm، lock یا parser option اضافه نمی‌کند.
- executor entry point در صورت نیاز فقط به `MigrationExecutor` موجود اضافه شود؛ SQL از `executeOut` به `IQueryExecute.executeTable` می‌رود.
- preflight، introspection یا validation schema انجام نشود. executor خطای manager/MySQL را حفظ می‌کند.
- برای SQL این operation target version در generation لازم نیست؛ executor حق rewrite خاموش SQL بر اساس version یا engine را ندارد.

## Example و Test Plan

- مثال versioned در `data_base/migration/example` بیاید و render-only پیش‌فرض باشد؛ اجرای DDL فقط با opt-in صریح انجام شود.
- مثال از یک column geometry مانند `geom` استفاده کند. شرط جدول نمونه، نوع geometry، `NOT NULL`, SRID و engine در توضیح مثال ذکر شود؛ این اطلاعات به API index منتقل نشوند.
- unit test بدون DB خروجی دقیق `CREATE SPATIAL INDEX`, quote/escape، نام‌های trim‌شده، single-column contract، blank input و Renderer روی AST ناقص مستقیم را پوشش دهد.
- executor fake همان `IQueryExecute` مرز واقعی را هدف بگیرد، `executeTable`، success/failure و عدم اجرای `executeSelect` را بررسی کند.
- regressionهای v1.6 تا v1.10 اجرا شوند؛ Main.kt تنظیمات محلی کاربر را حفظ کند.
- integration test دیتابیس اختیاری است؛ اگر نوشته شد، روی MySQL یا MariaDB اختصاصی و قابل reset، با جدول geometry سازگار با همان engine/version، ایجاد واقعی و metadata index را تأیید کند.

## خارج از scope

- اجرای تغییرات source/example خارج از Traceability این پلن است و پس از تأیید implementation آغاز می‌شود.
- تغییر API یا semantics نسخه‌های v1.6 تا v1.10.
- `DROP SPATIAL INDEX` مجزا؛ `DROP INDEX` v1.7 کافی است.
- spatial query/search DSL، GIS functionها، SRID management و تعریف/تغییر column geometry.
- `UNIQUE`, `PRIMARY KEY`, prefix length، expression/functional index، چند spatial column، index options، algorithm/lock و dialectهایی غیر از MySQL/MariaDB موجود.
- introspection، preflight، `IF NOT EXISTS`، auto-generated names، rollback، migration history و runner.
- abstraction عمومی Index فقط برای کم‌کردن duplication؛ reuse فقط اگر ساختار واقعی repository و یکسانی semantics آن را اثبات کند.

## Implementation Record

1. syntax و محدودیت‌های MySQL/MariaDB بر مبنای مستندات رسمی ثبت شدند؛ تفاوت engine و SRID محفوظ است.
2. نبود compatibility target عمومی repository به‌عنوان finding ثبت شد و minimum version حدسی تعیین نشد.
3. DSL/AST تک‌ستونی و مستقل از سایر index operationها قطعی است.
4. inheritance مربوط به `MariaDbDialect` و reuse مسیرهای واقعی renderer/executor بررسی شده‌اند.
5. محدودیت‌های schema به validation یا introspection کتابخانه تبدیل نمی‌شوند؛ v1.2 dependency نیست.
6. API، AST، Builder، renderer، executor overload، مثال versioned و تست‌ها اضافه شدند؛ `Main.kt` و تنظیمات محلی دست‌نخورده ماندند.
7. تست‌های `:data_base:migration:example:test` و `:data_base:migration:executor:test` با موفقیت اجرا شدند. regression نسخه‌های v1.6 تا v1.10 داخل همین taskها موفق بود.
8. اجرای تست ابتدا با Java 20 به‌دلیل نیاز build به JVM 24 شروع نشد؛ با Java 24 نصب‌شده و Gradle home موقت دوباره اجرا شد. Kotlin daemon به‌خاطر AccessDenied در مسیر temp محلی در دسترس نبود، اما Gradle به compiler fallback رفت و build با موفقیت تمام شد.
9. integration test دیتابیس اجرا نشد؛ طبق قرارداد اختیاری است. هیچ مورد غیرمنتظرهٔ رفتاری در implementation پیدا نشد.
