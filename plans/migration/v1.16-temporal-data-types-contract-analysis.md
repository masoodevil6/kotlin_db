# Migration v1.16: تحلیل قرارداد Temporal Data Types

## وضعیت

`Implementation Ready`

---

## 1. هدف

قرارداد عمومی typeهای زمانی را در Migration subsystem بررسی کن تا مشخص شود کدام temporal data typeها باید در مدل type مشترک migration پشتیبانی شوند و چگونه در API، AST، Builder و rendererهای dialect نمایش داده شوند.

این قابلیت دربارهٔ **نوع عمومی یک column** است:

```text
Temporal Data Type
    ↓
column definition در CREATE TABLE / ADD COLUMN / MODIFY COLUMN
```

این قابلیت shorthand یا رفتار lifecycle نیست. به‌طور مشخص، v1.16 قرارداد `timestamps()` یا `softDeletes()` را طراحی یا پیاده‌سازی نمی‌کند. این دو در plan مستقل v1.15 باقی می‌مانند و پس از بسته‌شدن temporal type contract دوباره نهایی خواهند شد.

این مرحله فقط Traceability و Contract Analysis است. تا زمانی که Traceability کامل و contract تأیید نشده، source، tests، examples و مستندات ساختاری ماژول را تغییر نده.

## 2. مرز مفهومی

```text
MigrationColumnDataType
├── DATE
├── TIME
├── DATETIME
├── TIMESTAMP
└── YEAR

Column Default / Expression
├── literal default موجود
├── DEFAULT CURRENT_TIMESTAMP     ← expression/default feature جداگانه
└── ON UPDATE CURRENT_TIMESTAMP  ← column attribute/DDL feature جداگانه

Convenience DSL
├── timestamps()                 ← v1.15؛ فعلاً pending
└── softDeletes()                ← v1.15؛ فعلاً pending
```

فهرست بالا candidate برای بررسی است و پذیرش همهٔ موارد را از پیش اعلام نمی‌کند. type و default expression نباید در یک کلاس یا state واحد ادغام شوند. پشتیبانی از یک temporal type به‌خودی‌خود به معنای پشتیبانی از current-time expression، automatic initialization/update، timezone management یا behavior ORM نیست.

هویت معنایی type در AST از SQL spelling هر dialect جداست:

```text
Temporal type identity in AST
        ↓
Dialect-specific type rendering
        ↓
SQL type spelling / storage representation
```

در نتیجه، پذیرفتن `TIMESTAMP` به این معنی نیست که هر dialect آینده باید SQL token `TIMESTAMP` را تولید کند؛ mapping آیندهٔ SQLite نیز از این plan نتیجه‌گیری نمی‌شود.

## 3. Scope

### داخل Scope

Traceability باید این موارد را با شواهد repository و مستندات رسمی بررسی کند:

* candidate typeها: `DATE`, `TIME`, `DATETIME`, `TIMESTAMP`, `YEAR`
* subset لازم برای scope فعلی پروژه و دلیل adopt/defer/reject هر نوع
* data class/type representation و invariantهای پارامترها
* fractional-second precision برای typeهایی که آن را می‌پذیرند
* SQL rendering مجزا برای MySQL و MariaDB و واقعیت registration/inheritance فعلی
* propagation typeهای پذیرفته‌شده در `CREATE TABLE`, `ADD COLUMN`, `MODIFY COLUMN`
* validation در Builder و Renderer و پوشش ASTهایی که مستقیماً ساخته می‌شوند
* سازگاری با literal default model فعلی
* مرز temporal type با SQL expressionهای default و column attributes خودکار
* version/engine/SQL-mode constraints مستندشده و compatibility target اعلام‌شدهٔ repository
* آزمون‌ها و exampleهای لازم برای implementation بعدی
* اینکه در آینده چه چیزی برای SQLite portability نیازمند dialect-specific mapping است؛ SQLite implementation وارد scope نمی‌شود.

### خارج از Scope

* `timestamps()` و `softDeletes()` یا هر shorthand دیگری
* ایجاد یا تغییر API/AST/Builder/Renderer مربوط به shorthandهای v1.15
* `DEFAULT CURRENT_TIMESTAMP`, `CURRENT_DATE`, `NOW()` یا SQL expression default عمومی
* `ON UPDATE CURRENT_TIMESTAMP` یا هر automatic initialization/update clause
* مقداردهی timestamp در INSERT/UPDATE
* soft-delete query behavior، ORM، global scope، restore یا lifecycle hooks
* timezone conversion در برنامه، session configuration یا مدیریت zone identifier
* generated columns، triggerها، server functions یا introspection
* پیاده‌سازی dialect SQLite یا ادعای portability میان MySQL/MariaDB/SQLite
* تغییر سیاست duplicate column validation؛ این موضوع از temporal typeها مستقل است.

## 4. وضعیت فعلی repository برای Traceability

این بخش نقطهٔ شروع است؛ در مرحلهٔ Traceability مسیر و وضعیت نهایی را دوباره با source فعلی تطبیق بده:

* مدل type در `data_base/migration/params/src/main/kotlin/data_types/MigrationColumnDataType.kt` یک `sealed class` است.
* typeهای فعلی در همان package عبارت‌اند از `BooleanType`, `DecimalType`, `IntType`, `JsonType`, `TextType`, `VarcharType`; temporal type موجود نیست.
* APIهای `CREATE TABLE` و `ADD COLUMN`، `MigrationColumnDataType` می‌گیرند؛ AST ستون create-table نوع nullable دارد و AST `MODIFY COLUMN` نوع اجباری دارد.
* renderer ستون در `MySqlMigrationColumnCapability` type را به SQL تبدیل می‌کند و برای `ADD COLUMN` نیز reuse می‌شود.
* `MODIFY COLUMN` renderer مستقل خود را دارد و type mapping جداگانه دارد. تغییر sealed type باید تمام `when`های exhaustive و rendererهای مصرف‌کننده را پوشش دهد.
* `CREATE TABLE` default validation type-specific است؛ defaultهای فعلی literal/null هستند و renderer، raw string را SQL expression تلقی نمی‌کند.
* `MySqlDialect` ثبت فعلی rendererها را انجام می‌دهد و `MariaDbDialect` از آن ارث می‌برد. inheritance به‌تنهایی یکسانی semantics یا compatibility همهٔ temporal typeها را اثبات نمی‌کند.
* compatibility target عمومی MySQL/MariaDB تاکنون در repository اعلام نشده است؛ این مورد را دوباره بررسی کن و در صورت نبود، به‌عنوان finding نگه دار.

در Traceability مسیرهای دقیق API, AST, Builder, type model, renderer, registry, tests, docs و Gradle modules را ثبت کن. ساختار repository را به‌خاطر تطبیق با این plan تغییر نده.

### 5.2 مستندات رسمی

برای هر candidate پذیرفته‌شده یا ردشده، MySQL و MariaDB را جداگانه بررسی کن. از نسخهٔ محلی توسعه‌دهنده minimum support استنتاج نکن.

موضوعات لازم برای بررسی:

* syntax دقیق type و fractional precision
* range، storage/interpretation و محدودیت‌های مستند
* timezone conversion یا نبود آن، اگر برای semantics type مهم است
* default behavior و implicit behavior، به‌خصوص برای TIMESTAMP
* تفاوت‌های version-dependent، SQL mode و engine
* آیا تفاوت محصول با یک type semantic مشترک قابل پوشش است یا renderer/product-specific branch لازم است
* semantic equivalence هر type میان MySQL و MariaDB، جدا از یکسان بودن spelling
* تفاوت SQL modeها، از جمله رفتار `DATE` در MariaDB Oracle mode، بدون افزودن SQL mode configuration به library

منابع اولیهٔ مورد انتظار: MySQL Reference Manual در بخش Date and Time Data Types, Type Syntax, Default Values, Automatic Initialization and Updating؛ MariaDB Server Documentation در Date and Time Data Types, TIMESTAMP, defaults, precision؛ و در صورت بحث دربارهٔ portability، مستندات رسمی SQLite.

### 5.4 شواهد رسمی مشخص برای بررسی و ثبت

موارد زیر در مستندات رسمی اولیه مشاهده شده‌اند؛ Traceability باید محدودهٔ نسخه، اثرشان بر قرارداد و اینکه آیا برای subset نهایی relevant هستند را ثبت کند:

* **MySQL `TIME`:** Reference Manual بخش `The TIME Type` می‌گوید SQL `TIME` برای time-of-day و نیز elapsed time/interval به‌کار می‌رود؛ مقدار می‌تواند منفی یا بزرگ‌تر از 24 ساعت باشد. بنابراین API کتابخانه نباید بدون تصمیم مستقل آن را به `TimeOfDay` یا `Duration` domain type تقسیم کند. اگر پذیرفته شود، نماینده‌اش صرفاً SQL temporal type است.
* **MySQL `TIMESTAMP` و `DATETIME`:** Reference Manual بخش‌های `The DATE, DATETIME, and TIMESTAMP Types` و `Indexed Lookups from TIMESTAMP Columns` تفاوت session timezone conversion و UTC storage برای TIMESTAMP را در برابر DATETIME شرح می‌دهد؛ typeها همچنین range یکسان ندارند. این دو type در AST/API از نظر semantic متمایزند حتی اگر syntax شبیه باشد.
* **MariaDB `TIMESTAMP`:** Server Documentation بخش `TIMESTAMP` conversion بین session time zone و UTC را توضیح می‌دهد و می‌گوید zone identifier همراه مقدار ذخیره نمی‌شود. همان مستند رفتار implicit مربوط به first TIMESTAMP و `explicit_defaults_for_timestamp` را نیز شرح می‌دهد.
* **Implicit TIMESTAMP behavior:** بعضی configuration/versionهای MySQL/MariaDB برای TIMESTAMP رفتار ضمنی default/auto-update دارند. کتابخانه بدون introspection یا خواندن session/server configuration نمی‌تواند آن رفتار runtime را normalize کند. Final Contract باید صریحاً بگوید کتابخانه type syntax را render می‌کند و دربارهٔ implicit server behavior تضمین سازگاری نمی‌دهد، مگر شواهد و تصمیم جداگانه‌ای چیز دیگری الزام کنند.
* **Type در برابر column attributes:** `TIMESTAMP` فقط نوع SQL است. `NULL`/`NOT NULL`، explicit `DEFAULT`, و `ON UPDATE` stateهای جدا در قرارداد column هستند. Traceability باید روشن کند renderer هرکدام را از column contract مستقل می‌گیرد و `TimestampType` به‌تنهایی nullability/default/automatic attribute تولید نمی‌کند. این distinction برای `TIMESTAMP NULL` مهم است، چون اعلام صریح NULL می‌تواند رفتارهای implicit بعضی server configurationها را تغییر دهد.
* **Fractional precision:** مستند رسمی MySQL 8.4 و MariaDB، برای TIME/DATETIME/TIMESTAMP precision کسری ثانیه را بررسی می‌کند؛ candidate دامنهٔ `0..6` است. Traceability باید برای هر type، نسخهٔ grammar و رفتار omitted precision در برابر precision صریح صفر را جداگانه ثبت کند.
* **MariaDB Oracle mode:** MariaDB DATETIME Documentation و SQL_MODE=ORACLE Compatibility documentation می‌گویند `DATE` همراه time portion در Oracle mode synonym برای `DATETIME` است. Library فعلی SQL mode را model نمی‌کند؛ بررسی کن contract canonical `DATE` syntax را تولید کند و mode-specific semantic را به server بسپارد، نه اینکه SQL mode abstraction بسازد.
* **TIME value coercion:** MySQL مستند می‌کند که clipping/normalization مقدار نامعتبر یا خارج از range می‌تواند به SQL mode وابسته باشد؛ Traceability تعیین کند type declaration و precision مسئولیت library است، اما range/value coercion و enforcement متعلق به server/SQL mode می‌ماند. این قاعده validation مقدارهای runtime را به Builder یا Renderer اضافه نمی‌کند.
* **SQLite:** SQLite `Datatypes` documentation می‌گوید storage class مستقل date/time ندارد و date/time را می‌توان به‌صورت TEXT, REAL یا INTEGER ذخیره کرد. این فقط Architecture Finding برای dialect احتمالی آینده است: AST temporal identity با SQL spelling/storage representation dialect یکی نیست؛ mapping SQLite خارج از scope می‌ماند.

این موارد دلیل adoption همهٔ candidateها نیستند. قرارداد نهایی می‌تواند subset انتخاب کند و باقی را defer/reject کند.

SQLite evidence باید فقط برای مستندسازی design constraint آینده باشد. از آن API عمومی یا mapping قطعی استخراج نکن.

### 5.3 Framework و convention بیرونی

برای تعیین نیاز واقعی پروژه، Laravel یا ORM دیگری را به‌عنوان مرجع الزامی استفاده نکن. اگر برای مقایسه نام type یا use case بیرونی بررسی می‌شود، آن را فقط contextual evidence ثبت کن؛ contract این library را رفتار framework تعیین نمی‌کند.

## 6. Required Decisions

برای هر سؤال نتیجهٔ `Adopt`, `Defer`, `Reject` یا `Unresolved` همراه دلیل ثبت کن.

### 6.1 فهرست typeها

* آیا `DATE` لازم است؟
* آیا SQL type `TIME` لازم است؟ اگر بله، آن را به‌عنوان database temporal type واحد model کن؛ خود library آن را به time-of-day و duration تقسیم نکند.
* آیا `DATETIME` لازم است؟
* آیا `TIMESTAMP` لازم است؟
* آیا `YEAR` ارزش type مستقل دارد؟
* آیا scope کوچک‌تر از کل فهرست کافی است؟ برای هر نوع خارج از subset دلیل و مسیر آینده را ذکر کن.

هم‌نامی type در MySQL/MariaDB به‌تنهایی دلیل کافی برای یکسان فرض‌کردن معنا نیست.

### 6.2 Type model و parameterization

* typeها class/object ساده باشند یا type parameter لازم داشته باشند؟
* `TimestampType()` بدون پارامتر باشد یا precision بگیرد؟
* اگر precision قابل‌تنظیم است، domain دقیق آن چیست و برای کدام typeها اعمال می‌شود؟
* آیا precision omitted و precision صفر دو state متفاوت‌اند یا یک SQL واحد تولید می‌کنند؟
* type model مستقل از dialect باقی می‌ماند؟ اگر semantics دو محصول واقعاً متفاوت است، تفاوت کجا model می‌شود؟
* public class naming در package فعلی چه conventionی دارد؟
* هویت type در AST و spelling خروجی dialect چگونه مستقل می‌مانند؟ از نام class به‌تنهایی SQL token یا storage format SQLite استنتاج نکن.

Validation precision باید پیش از SQL composition در Builder و defensive در Renderer تعریف شود. مقدارهای خارج از grammar مستندشده نباید از builder یا AST مستقیم عبور کنند.

Precision را بررسی کن، اما abstraction مشترکی مثل `TemporalType(precision)` را صرفاً به‌خاطر داشتن constructorهای مشابه نساز. اگر precision برای چند type پذیرفته شد، تصمیم بگیر آیا هر concrete type پارامتر خودش را دارد؛ invariant مشترک فقط وقتی مجاز است که evidence یک semantic مشترک واقعی را ثابت کند.

### 6.3 Operation coverage

برای هر type تصمیم بگیر آیا هم‌زمان در این operationها قابل استفاده است:

```text
CREATE TABLE column
ADD COLUMN
MODIFY COLUMN
```

Contract عمومی type نباید typeای معرفی کند که یکی از operationهای استاندارد کتابخانه آن را بی‌دلیل نمی‌تواند render کند. اگر پشتیبانی operationها مرحله‌ای است، API surface و محدودیت مصرف صریح باشد و این عدم تقارن به‌عنوان تصمیم versioned ثبت شود.

`RENAME COLUMN` type را مصرف نمی‌کند. `DROP COLUMN` نیز type mapping ندارد.

### 6.4 Defaults و expressions

* مشخص کن literal default فعلی برای هر type چه stateهایی را می‌پذیرد یا رد می‌کند.
* `CURRENT_TIMESTAMP`, `CURRENT_DATE`, `NOW()` و expressionهای مشابه را با `String` خام یا literal default اشتباه نگیر.
* تصمیم بگیر expression default خارج از v1.16 و نیازمند feature contract جداست یا شواهد واقعی دامنه، آن را بخشی از scope type model می‌کند. در صورت نیاز واقعی، expression را داخل data type encode نکن؛ قرارداد API/AST/escaping/renderer جداگانه لازم دارد.
* `ON UPDATE CURRENT_TIMESTAMP` یک column attribute/DDL behavior مجزاست، نه type. مگر evidence ضرورت را ثابت کند، defer شود.

### 6.5 Dialect، server version و compatibility

* MySQL و MariaDB grammar/semantics جداگانه ثبت شوند.
* registry/inheritance واقعی بررسی شود؛ inheritance مجوز claim یکسانی type semantics نیست.
* MariaDB native `DATE` را از mode-specific Oracle `DATE` semantic جدا نگه دار. این تفاوت به معنی APIای مانند `DateType(SqlMode.ORACLE)` نیست؛ v1.16 SQL mode را model یا پیکربندی نمی‌کند.
* config target version موجود را با detected version execution قاطی نکن؛ v1.16 دربارهٔ type syntax generation است و نباید خودبه‌خود config یا execution path را تغییر دهد.
* compatibility target کلی repository و minimum grammar version typeهای منتخب دو finding جدا هستند.
* اگر compatibility target repository اعلام نشده، مقدار نساز؛ finding ثبت کن و روشن کن که آیا مانع نهایی‌کردن scope/contract هست.
* MariaDB Oracle mode و هر SQL mode/version-specific meaning را به‌عنوان server semantic ثبت کن. Library در v1.16 SQL mode را پیکربندی نمی‌کند؛ syntax canonical type را render می‌کند و رفتار mode-specific را کنترل یا rewrite نمی‌کند.
* SQLite future portability را با MySQL native type names یکی فرض نکن. dialect آینده می‌تواند mapping جدا داشته باشد؛ این plan mapping را طراحی نمی‌کند.

### 6.6 Nullability و timezone

Temporal typeها nullability را تعیین نمی‌کنند؛ nullability از column definition فعلی می‌آید.

Type contract باید semantics ذاتی نوع را از موارد زیر جدا و مستند کند:

* تفاوت semantic میان `TIMESTAMP` و `DATETIME`: session-zone/UTC conversion بخشی از رفتار database برای TIMESTAMP است، حتی اگر library timezone را مدیریت نکند.
* نگهداری یا عدم نگهداری zone identifier؛ در شواهد فعلی MySQL/MariaDB این موضوع با timestamp value یکی نیست و باید جدا ثبت شود.
* type range
* precision
* implicit TIMESTAMP default/auto-update behavior وابسته به server version/configuration

Final Contract باید صریح کند که `TimestampType` با `DateTimeType` یکی نیست. کتابخانه timezone را تبدیل، ذخیره، مدیریت یا server/session configuration را تشخیص نمی‌دهد؛ بااین‌حال semantics ذاتی TIMESTAMP در database باقی می‌ماند. اگر library فقط SQL token را render می‌کند، تضمین نمی‌دهد که serverهای مختلف با configurationهای متفاوت runtime behavior یکسانی داشته باشند.

قرارداد نهایی باید این stateها را جدا نگه دارد:

```text
TimestampType
    └── فقط type identity و در صورت تصویب، precision/type syntax

Column definition
    ├── nullability
    ├── explicit default state
    └── automatic update attribute (فعلاً خارج از scope مگر contract جدا)

Database server
    ├── implicit TIMESTAMP rules
    ├── SQL mode behavior
    ├── timezone/session conversion
    └── inserted-value range/coercion enforcement
```

پس عبارت «کتابخانه فقط SQL type را render می‌کند» نباید به‌عنوان تضمین یکسان‌بودن runtime semantics تفسیر شود. اگر در آینده operationی مانند v1.15 `TIMESTAMP NULL` تولید کند، nullability باید از column contract بیاید و مستقل از type renderer باشد.

## 7. Candidate Decision Matrix

جدول زیر با شواهد Traceability تکمیل شده است؛ تصمیم هر candidate در ستون آخر آمده است.

| Candidate | MySQL semantics | MariaDB semantics | Semantic equivalence | Repository impact | Decision |
|---|---|---|---|---|---|
| `DATE` | grammar/range/default/version بررسی شود | grammar/range/default/Oracle-mode/version بررسی شود | syntax مشابه را معادل معنایی فرض نکن | `MigrationColumnDataType` و سه renderer | Adopt; native DATE syntax |

## 8. Architecture Constraints

* `MigrationColumnDataType` عمومی و مستقل از connection, manager, executor و database runtime بماند.
* API/AST/Builder به renderer یا executor وابسته نشوند.
* dialect و renderer از manager و connection مستقل بمانند.
* executor از مسیر فعلی `MigrationExecutor → IQueryExecute.executeTable` برای DDL استفاده کند؛ data type نباید execution path جدید بخواهد.
* از `String`, `Any`, raw SQL یا map عمومی برای نمایش type/default expression استفاده نکن.
* برای هر temporal type، class/type model فقط وقتی اضافه شود که Traceability نیاز و semantics آن را تأیید کند.
* abstraction عمومی `TemporalType`, `DateTimeLike`, `TimestampPreset` یا converter مشترک صرفاً برای کم‌کردن چند branch ایجاد نکن.
* operationهای v1.0 تا v1.15 از نظر semantics دست‌نخورده بمانند. هر تغییر لازم در عملیات قبلی باید additive، دقیقاً justified و regression-covered باشد.
* به‌دلیل sealed type مشترک، افزودن type باید compile/render coverage کامل برای تمام مصرف‌کننده‌های فعلی داشته باشد.
* هیچ shorthand یا validation تغییر duplicate columnها را در v1.16 وارد نکن.

## 9. Test و Example Requirements برای implementation بعدی

Traceability فقط requirements را ثبت می‌کند؛ تست یا example نساز.

پس از نهایی‌شدن contract، implementation باید تست‌هایی متناسب با subset پذیرفته‌شده داشته باشد:

* type SQL exact برای هر dialect پشتیبانی‌شده
* constructor/Builder validation برای parameterها و precision
* Renderer defensive validation برای type AST و precision نامعتبر
* coverage یکسان یا محدودیت مستند برای CREATE TABLE / ADD COLUMN / MODIFY COLUMN
* nullability مستقل از type
* عدم تغییر رفتار default omission و `DEFAULT NULL`
* رد یا defer شدن expression defaultهایی که در contract پذیرفته نشده‌اند
* regression برای typeها و SQLهای فعلی
* تست dialect registration و عدم claim ناخواسته از inheritance
* tests بدون دیتابیس برای grammar/rendering؛ integration اختیاری و فقط در صورت نیاز قراردادی
* example versioned، render-only به‌صورت پیش‌فرض؛ اجرای واقعی DDL فقط با opt-in صریح

هیچ تستی نباید ادعا کند library، server range، timezone setting، SQL mode یا runtime conversion را کنترل می‌کند، مگر آن behavior جداگانه وارد contract شده باشد.

### 14.3 Final Type/Precision Contract

- Subset عمومی این مرحله: DateType بدون پارامتر؛ TimeType(precision: Int?)؛ DateTimeType(precision: Int?)؛ TimestampType(precision: Int?). این‌ها type identityهای مستقل‌اند و superclass عمومی TemporalType ساخته نمی‌شود.
- برای TIME, DATETIME و TIMESTAMP، precision اختیاری و در بازه 0..6 است. مقدار خارج از بازه در Builder و defensive Renderer، پیش از SQL composition رد شود.
- precision برابر null syntax بدون پرانتز می‌دهد؛ precision برابر صفر syntax صریح TYPE(0) می‌دهد. هر دو در دیتابیس precision صفر دارند.
- SQL spelling: DATE، TIME[(fsp)]، DATETIME[(fsp)] و TIMESTAMP[(fsp)]. DATE precision نمی‌گیرد.
- هر type پذیرفته‌شده باید هم‌زمان در CREATE TABLE، ADD COLUMN و MODIFY COLUMN قابل render باشد.
- Type فقط type syntax را تعیین می‌کند. Nullability، explicit default و ON UPDATE مستقل می‌مانند. TimestampType به‌تنهایی NULL/NOT NULL/DEFAULT/ON UPDATE تولید نمی‌کند.
- Default compatibility این contract فقط literal String و null است؛ String به‌صورت SQL literal quote/escape می‌شود و expression تلقی نمی‌شود. مقدار temporal توسط Builder/Renderer parse یا range-check نمی‌شود. CREATE TABLE validation و MODIFY COLUMN باید این مرز را یکسان رعایت کنند.
- API/config برای SQL mode، Oracle mode، timezone/session، implicit server defaults یا server introspection اضافه نمی‌شود. Dialect syntax canonical را render می‌کند و mode-specific behavior را rewrite نمی‌کند.
- compatibility target عمومی همچنان finding است، اما blocker این subset نیست. به‌کارگیری precision صریح ممکن است به grammar/version متناسب سرور نیاز داشته باشد؛ هیچ minimum version عمومی از آن ادعا نمی‌شود.

### 14.4 مرز مسئولیت Server

| کتابخانه | Database/server |
|---|---|
| هویت type، precision declaration، SQL type syntax، operation coverage، nullability و literal-default state؛ validation محدوده precision | SQL mode، range و پذیرش مقدار، TIME clipping/coercion، zero/invalid date، session timezone conversion، implicit TIMESTAMP default/auto-update، MariaDB Oracle-mode DATE |

پس تولید یکسان SQL تضمین نمی‌کند که سرورهای مختلف یا sessionهای متفاوت مقادیر یکسان بپذیرند یا runtime semantics یکسان داشته باشند.

### 14.5 Dependency، Tests و وضعیت نهایی

v1.15 باید پس از این مرحله typeهای تصویب‌شده را مصرف کند و shorthand contract خود را جداگانه ببندد؛ v1.16 درباره expansion یا duplicate-column policy تصمیم نمی‌گیرد. برای implementation بعدی، تست mapping دقیق چهار type، FSP مرزهای 0 و 6 و مقادیر نامعتبر، omitted در برابر explicit zero، validation AST، استقلال nullability/default، coverage سه operation، ثبت dialect و regression typeهای قبلی لازم است. Example باید versioned و render-only باشد و DDL واقعی فقط با opt-in اجرا شود. Traceability تست اجرا نکرد.

**Final Contract Decision: Implementation Ready.** Evidence و subset، precision، dialect mapping و server boundary تعیین شدند. Compatibility target نامشخص و اختلاف server runtime behavior ثبت‌شده‌اند، اما مانع implementation syntax contract نیستند. v1.15 همچنان pending برای بازبینی مستقل است.
