# Migration v1.21.2: پیکربندی و مرزهای Integration Test

## Status

`Final Review Complete / Implementation Blocked by External Test Infrastructure`

Traceability کد و abstractionهای لازم انجام شده است. تصمیم‌های داخل repository مشخص‌اند؛ تنها blocker اجرای implementation، تأمین مقصد اختصاصی و disposable MySQL و روش معتبرِ غیرمبتنی بر ENV برای ارائهٔ configuration تست است. هیچ نام دیتابیس یا credentialای حدس زده نمی‌شود.

Integration Test سطح `data_base:migration` باید بدون `System.getenv()` مسیر واقعی Migration subsystem و تا حد ممکن Query subsystem را end-to-end exercise کند. fixtureهای schema باید از Migration DSL، خواندن history از Query Builder موجود، و ساخت `system_migration` از State Store انجام شود.

هم‌زمان این سند تصمیم می‌گیرد آیا `dbTestName` یا `dbTestReset` به `DatabaseConfig` تعلق دارند. این Plan هیچ implementationای انجام نمی‌دهد.

## 3. Interpretation

1. `DatabaseConfig` مقصد connection است؛ reset یک test lifecycle/setup operation است و با connection configuration یکی نیست.
2. تست می‌تواند یک config صریح و test-scoped بسازد و آن را در `DefaultDatabaseConfig.config` قرار دهد. library نباید خودش `dbName` را به مقصد دیگری تبدیل کند.
3. مقدار `kotlin_db` در example، مقصد اختصاصی integration test را اثبات نمی‌کند؛ استفاده یا reset آن مجاز نیست مگر project/test infrastructure آن را صریحاً dedicated اعلام کند.
4. Migration DSL برای create fixture و Query Builder برای history SELECT capability واقعی دارند؛ raw SQL در این دو semantic موردنیاز، دورزدن abstractionهای موجود است.
5. `system_migration` internal است: Migrator/State Store ایجادش می‌کند و تست آن را مشاهده می‌کند.
6. `assumeTrue` collision را در کد فعلی به skip تبدیل می‌کند. در Integration Testی که باید واقعاً subsystem را اجرا کند، این می‌تواند database اشتباه/آلوده را به `BUILD SUCCESSFUL` ولی `SKIPPED` تبدیل کند؛ پس collision روی target اختصاصی باید failure آشکار باشد.
7. test database باید clean باشد. چون reset در `DatabaseConfig` جایی ندارد و reset semantics تصویب نمی‌شود، provisioning/clean state مسئولیت External Test Infrastructure است.

## 4. Configuration Decisions

### `dbTestName`

**Decision: Reject as a `DatabaseConfig` property.** یک config یک `dbName` به‌عنوان مقصد connection دارد. Integration Test خودش test-scoped `DatabaseConfig` می‌سازد که `dbName` آن مقصد dedicated تست باشد. `dbTestName` دوم، consumer عمومی ندارد و به‌طور implicit نباید `DatabaseConnection.build()` را تغییر دهد.

Public API decision از test target decision مستقل است:

```text
Public API: DatabaseConfig فاقد dbTestName می‌ماند.
Test infrastructure: باید مقصد dedicated/disposable و راه غیر-ENV ارائهٔ config را مشخص کند.
```

وجود target و delivery mechanism فعلاً **External Test Infrastructure Dependency / Unresolved** است. نه `kotlin_db_test` و نه `kotlin_db` به‌عنوان target تست فرض نمی‌شوند.

### `dbTestReset`

**Decision: Reject as a `DatabaseConfig` property.** Reset lifecycle/setup policy است، نه connection config. اگر در آینده reset لازم شود، آن را test-specific mechanism یا external provisioning انجام می‌دهد و برایش قرارداد مستقل لازم است؛ v1.21.2 `DROP DATABASE`, `TRUNCATE` یا reset flag اضافه نمی‌کند.

بدون reset، infrastructure باید test database خالی/قابل‌استفاده فراهم کند. اگر reset کل database در آینده مطرح شد، باید جداگانه connection به server بدون DB منتخب، DROP/CREATE privilege، رفتار DB غایب، `system_migration`, fixture state و ownership را تعیین کرد.

## 6. Migration Fixture Strategy

### Failure scenario نهایی

Fixture semantic باید با خود Migration ساخته شود؛ blocker با SQL خام pre-seed نشود:

```text
Migration A (ID: create_test_blocker)
  → CREATE TABLE blocker
  → Success
  → history recorded in initial successful configuration, batch 1

Migration B (ID: duplicate_test_blocker)
  → CREATE TABLE blocker again
  → real MySQL duplicate-table failure
  → no history record for B

Migration C (ID: after_test_blocker_failure)
  → CREATE TABLE after_failure
  → must not execute
```

شرایط:

* A و B IDهای متفاوت و annotationهای `migrationTags` معتبر دارند.
* A ابتدا در successful configuration ثبت و اجرا می‌شود؛ سپس همان A همراه B و C در failure configuration ثبت می‌شود. A به دلیل history applied است؛ B pending می‌ماند.
* Failure واقعی B پیش از state recording رخ می‌دهد؛ C اجرا/ثبت نمی‌شود.
* invocation بعدی A را اجرا نمی‌کند، B را دوباره pending می‌بیند و دوباره fail می‌شود؛ C همچنان اجرا نمی‌شود.
* طبق v1.20 batch invocation اول موفق `1` است؛ failure configuration batch `2` دارد و successهای پیش از B در همان batch ثبت می‌شوند. retry بعدی batch محاسبه‌شدهٔ `3` خواهد داشت، اما چون B پیش از recording شکست می‌خورد، ردیف جدیدی در batch 3 درج نمی‌شود.
* هیچ prerequisite fixture با raw SQL ساخته نمی‌شود.

این طراحی با state/filter/order/record sequence در `MigrationMigrator` سازگار است و جای raw `CREATE TABLE blocker` را می‌گیرد.

## 7. Query Builder History Verification

History query باید به شکل semantic با Query Builder ساخته شود:

```text
SELECT id, migration, batch
FROM system_migration
ORDER BY id ASC
```

مسیر مورد انتظار:

```text
QueryRenderSelectBuilder
  → Query AST
  → QueryBuilderExecutor / DialectSelector
  → dialect renderer
  → BuiltQuery
  → QueryExecute.executeSelect
  → DatabaseConnection
  → MySQL
```

ResultSet در callback به rowهای test value تبدیل شود؛ ResultSet از callback/resource lifecycle بیرون برده نشود. `DatabaseMetaData.getTables/getColumns` برای schema inspection همچنان مجاز است.

ماژول `data_base:migration` در حال حاضر test dependency برای Query Builder ندارد. Implementation plan باید حداقل `testImplementation`های لازم برای API/Builder/Executor Query را بر اساس import/compile proof اضافه کند؛ dependency production یا abstraction جدید اضافه نشود. Raw SQL history fallback فقط اگر compile proof یک capability gap واقعی نشان دهد مجاز است؛ gap باید دقیق گزارش و از اضافه‌کردن abstraction برای حذف یک SQL string خودداری شود.

```text
Test does NOT create system_migration.

```

History query observation است، نه migration execution. fixtureها یا setup دستی حق ساخت این جدول را ندارند.

## 9. Collision Guard و Initial State

### Initial state

بدون reset:

```text
dedicated test database exists and is reachable
system_migration absent
all v1.21 fixture tables absent
```

در این state State Store history خالی را bootstrap می‌کند و batchهای `1` و `2` deterministic هستند. `system_migration` یا هر fixture table از قبل موجود یعنی target پاک/درست نیست.

### Collision result

**Decision: Failure, not Skip.** Guard باید قبل از هر Migration DDL و قبل از State Store bootstrap، `system_migration` و تمام fixture names را بررسی کند. وجود هر collision در dedicated target، test setup failure با پیام شامل objectهای متعارض است. از `assumeTrue` برای collision استفاده نشود؛ assumption باعث پنهان‌شدن database آلوده یا config اشتباه در گزارش build می‌شود.

نبود MySQL، connection/config failure و target نامعتبر نیز failure هستند، نه skip. v1.21.2 نباید skip مکانیزم تازه‌ای اضافه کند.

### Reset order

در v1.21.2 reset وجود ندارد (`dbTestReset` property رد شده است)، پس ترتیب فقط config → collision guard → fixtures → test است. اگر test-specific reset در آینده جداگانه تصویب شود، resetی که collisionها را پاک می‌کند باید پیش از collision guard اجرا شود؛ اما reset semantics خارج از این Contract است و هیچ reset در این Plan اجرا نمی‌شود.

## 10. Ownership و Cleanup

`ownsTestObjects` فقط بعد از clean collision guard و پیش از lifecycle true می‌شود. database parent متعلق به تست فرض نمی‌شود و test آن را drop/recreate نمی‌کند.

Fixture creation و teardown:

```text
Fixture creation → Migration DSL + MigrationMigrator
Fixture verification → Query Builder / JDBC Metadata
Fixture cleanup → test-only cleanup through existing DropTable API + MigrationExecutor directly
```

Repository `DropTable` API با `ifExists()` و executor overload دارد؛ بنابراین cleanup tableها را می‌توان با DropTable builder به `MigrationExecutor` موجود فرستاد، بدون `MigrationMigrator` و بدون ثبت history. این cleanup lifecycle تست است، نه migration جدید. `system_migration` نیز فقط پس از آنکه همین test با clean initial state و Migrator آن را ساخته، در teardown حذف می‌شود.

اگر cleanup شکست بخورد، شکست باید قابل مشاهده و به‌عنوان test failure گزارش شود؛ best-effort خاموش ممنوع است. اگر شکست اصلی تست هم وجود داشت، گزارش باید هر دو علت را حفظ کند. هیچ database-level cleanup انجام نمی‌شود.

## 11. Existing Test Assertions

این سناریوها حفظ می‌شوند و با configuration/test access جدید بازنویسی معنایی نمی‌شوند:

* successful migrations، Group و registration ordering؛
* rerun و already-applied behavior؛
* failure/resume، ثبت‌نشدن B ناموفق و اجرا‌نشدن C؛
* empty operation و multiple operations؛
* `system_migration` history؛
* batch 1/2 (و retry attempt batch 3 بدون recording)؛
* safety guard و cleanup.

مصرف Query Builder برای history و Migration DSL برای fixtureها باید همین assertions را از مسیرهای واقعی repository اجرا کند.

## 12. Raw SQL Policy

```text
Raw SQL is not prohibited globally.

Raw SQL is allowed only when:
1. the required semantic capability does not exist in repository abstractions, and
2. adding that capability is outside v1.21.2 scope, and
3. the raw SQL is necessary for environment control or verification.
```

اگر abstraction موجود معنای operation را پوشش می‌دهد، تست همان abstraction را مصرف می‌کند. در این Plan:

* raw DDL برای fixture creation رد است.
* raw history SELECT رد است، چون Query Builder capability موجود است.
* direct JDBC metadata برای `getTables/getColumns` Adopt است.
* cleanup از DropTable API و executor مستقیم استفاده می‌کند؛ Migrator برای teardown اجرا نمی‌شود.
* SQL خام جدید برای ساخت `system_migration` ممنوع است.

## 16. Implementation Scope پس از رفع External Dependency

تغییرهای مجاز بعد از تأمین configuration معتبر:

1. فقط Integration Test v1.21 در `data_base/migration/src/test/...` تغییر کند.
2. ENV خواندن و skip مبتنی بر نبود ENV حذف شود.
3. config صریح test-scoped از منبع مورد تأیید test infrastructure ساخته، قبلی ذخیره، در `DefaultDatabaseConfig.config` نصب و در `finally` restore شود.
4. raw blocker با Migration A/B/C جایگزین شود.
5. history query با Query Builder و `QueryBuilderExecutor` اجرا و ResultSet در callback map شود.
6. test-only dependencyهای لازم برای query API/builder/executor به‌صورت `testImplementation` اضافه شوند؛ dependency production اضافه نشود.
7. cleanup با DropTable API و `MigrationExecutor` مستقیم انجام شود؛ `system_migration` همچنان فقط توسط State Store ساخته شود.
8. production code، public API، schema، migration behavior و تست‌های opt-in مستقل `migration:executor` تغییر نکنند.

اگر compile proof برخلاف source evidence capability gap نشان داد، تنها همان gap گزارش شود و raw SQL فقط طبق policy بالا مجاز است؛ abstraction جدید برای test ساخته نشود.

## 19. Deferred / Out of Scope

* `dbTestName`, `dbTestReset` یا هر test-only field در public `DatabaseConfig`
* تعریف reset عمومی یا DROP/CREATE DATABASE
* test target/config source جدید بدون قرارداد و evidence بیرونی
* production configuration/connection/executor/query/migration architecture
* تغییر StateStore یا ساخت دستی `system_migration`
* تغییر integration testهای مستقل `migration:executor`
* raw SQL abstraction جدید، migration runner feature جدید، DI یا framework پاک‌سازی
