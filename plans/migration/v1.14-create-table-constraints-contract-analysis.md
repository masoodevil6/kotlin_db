# Migration v1.14: تحلیل قرارداد Constraints، Indexها و Spatial Data Types در CREATE TABLE

## وضعیت

`Implemented (scoped contract)`

---

# 1. هدف

یک تحلیل کامل **Traceability و Contract Analysis** برای قابلیت مهاجرت بعدی انجام بده.

هدف این است که مشخص شود کوچک‌ترین و صحیح‌ترین قرارداد قابل‌پیاده‌سازی برای گسترش `CREATE TABLE` چیست تا بتواند علاوه بر تعریف ستون‌ها، موارد زیر را نیز در ساخت جدول پشتیبانی کند:

* Primary Key
* Composite Primary Key
* UNIQUE
* Index
* Multi-Column Index
* FULLTEXT Index
* SPATIAL Index
* Foreign Key
* در صورت توجیه فنی، CHECK Constraint
* Data Typeهای مکانی مانند `POINT`

این مرحله **فقط تحلیل و طراحی قرارداد است**.

### در مرحله Traceability مجاز نیستی:

* کد source را تغییر بدهی
* تست ایجاد یا تغییر بدهی
* مستندات را تغییر بدهی
* ساختار repository را تغییر بدهی
* abstraction جدید را صرفاً برای پیاده‌سازی آینده اضافه کنی

تا زمانی که دستور جداگانه‌ای برای Implementation داده نشده، هیچ implementation انجام نده.

---

# 2. هدف معماری

در حال حاضر `CREATE TABLE` عمدتاً ساختاری شبیه این دارد:

```text
CREATE TABLE
└── Columns
```

هدف بررسی این است که آیا باید به مدلی شبیه این تبدیل شود:

```text
CREATE TABLE
├── Column Definitions
├── Primary Key
├── Unique Constraints
├── Normal Indexes
├── FullText Indexes
├── Spatial Indexes
├── Foreign Keys
└── Check Constraints
```

اما این ساختار **صرفاً یک مدل پیشنهادی اولیه است**.

در Traceability باید مشخص کنی آیا این مدل صحیح است یا ساختار دیگری از نظر معماری مناسب‌تر است.

---

# 3. اصل مهم معماری

فرض نکن که operationهای مستقل فعلی را باید مستقیماً داخل `CREATE TABLE` reuse کنیم.

در repository قبلاً operationهای مستقلی برای موارد زیر وجود دارند:

```text
CREATE INDEX
DROP INDEX
CREATE UNIQUE INDEX
CREATE MULTI-COLUMN INDEX
CREATE FULLTEXT INDEX
CREATE SPATIAL INDEX
CREATE INDEX USING BTREE/HASH
CREATE FOREIGN KEY
DROP FOREIGN KEY
```

این operationها را بررسی کن و مشخص کن:

* چه بخش‌هایی قابلیت reuse دارند
* چه بخش‌هایی باید مستقل باقی بمانند
* آیا AST مشترک منطقی است
* آیا Builder مشترک منطقی است
* آیا فقط renderer/helper قابل reuse است
* آیا CREATE TABLE به definitionهای مستقل خودش نیاز دارد

از ایجاد abstraction صرفاً برای جلوگیری از تکرار چند خط کد خودداری کن.

# 6. Primary Key

بررسی کن که `CREATE TABLE` باید چه نوع Primary Keyهایی را پشتیبانی کند.

حداقل موارد زیر را بررسی کن:

### Single-column Primary Key

وضعیت فعلی:

```kotlin
addColumn {
    name("id")
    dataType(IntType())
    primaryKey()
}
```

بررسی کن که این API چگونه باید حفظ شود.

### Composite Primary Key

بررسی کن آیا نیاز است:

```kotlin
primaryKey {
    columns("tenant_id", "user_id")
}
```

پشتیبانی شود.

بررسی کن:

* grammar در MySQL
* grammar در MariaDB
* تفاوت Primary Key سطح ستون و سطح جدول
* نیاز به AST جدید
* backward compatibility
* ترتیب ستون‌ها

`primaryKey()` فعلی را بدون دلیل حذف یا تغییر نده.

# 7. UNIQUE Constraint

بررسی کن که `CREATE TABLE` باید UNIQUE constraint داشته باشد یا خیر.

برای مثال:

```kotlin
unique {
    name("uq_users_email")
    columns("email")
}
```

و:

```kotlin
unique {
    name("uq_users_name_email")
    columns("name", "email")
}
```

مشخص کن:

* تفاوت UNIQUE constraint با UNIQUE INDEX چیست
* آیا هر دو باید در domain model وجود داشته باشند
* آیا UNIQUE باید single و multi-column باشد
* آیا name اجباری است
* آیا unnamed UNIQUE قابل قبول است
* grammar در MySQL
* grammar در MariaDB
* ارتباط آن با `CREATE UNIQUE INDEX`
* آیا می‌توان از AST مشترک استفاده کرد یا خیر

UNIQUE constraint و UNIQUE INDEX را بدون evidence یکی فرض نکن.

# 8. Normal INDEX

مثال:

```kotlin

    name("idx_users_email")
    columns("email")
}
```

و:

```kotlin
index {
    name("idx_users_name_email")
    columns("last_name", "first_name")
}
```

بررسی کن:

* single-column
* multi-column
* ترتیب columnها
* نام index
* identifier escaping
* آیا `USING BTREE/HASH` نسخه v1.12 باید اینجا هم قابل استفاده باشد
* آیا method برای همه indexها معتبر است
* آیا AST موجود `CreateIndex` قابل reuse است
* آیا CREATE TABLE باید definition مستقل داشته باشد

از این موارد استفاده نکن:

```text
Map<String, Any>
String options
Raw SQL
Generic IndexOptions
```

مگر اینکه evidence بسیار مشخصی وجود داشته باشد.

اگر قابلیت‌هایی مثل `WITH PARSER` باید جداگانه بررسی شوند، آن‌ها را به contract مستقل منتقل کن.

# 11. FOREIGN KEY


بررسی کن که همین مفهوم در `CREATE TABLE` چگونه باید نمایش داده شود.

باید موارد زیر بررسی شوند:

* single-column
* composite
* positional pairing
* constraint name
* referenced table
* referenced columns
* ON DELETE
* ON UPDATE
* MySQL grammar
* MariaDB grammar
* تفاوت احتمالی inline FK با `ALTER TABLE ADD FOREIGN KEY`

v1.13 را بدون evidence تغییر نده.

```text
├── indexes
```

```text

├── columns

    ├── Index
    ├── FullTextIndex
```

این دو رویکرد را از نظر:

# 15. DSL پیشنهادی

DSL زیر فقط یک candidate است و نباید بدون Traceability به عنوان قرارداد نهایی پذیرفته شود:

```kotlin
createTable {
    table {
        tableName("orders")
    }

    addColumn {
        name("id")
        dataType(IntType())
        notNull()
        autoIncrement()
        primaryKey()
    }

    addColumn {
        name("user_id")
        dataType(IntType())
        notNull()
    }

    foreignKey {
        name("fk_orders_user")
        columns("user_id")
        referencesTable("users")
        referencesColumns("id")
        onDelete(ForeignKeyAction.CASCADE)
    }

    unique {
        name("uq_orders_code")
        columns("code")
    }

    index {
        name("idx_orders_user")
        columns("user_id")
    }

    fullTextIndex {
        name("ft_orders_description")
        columns("description")
    }

    spatialIndex {
        name("spx_places_location")
        column("location")
    }
}
```

بررسی کن آیا این DSL با architecture فعلی سازگار است.

# 17. SQL Ordering

مشخص کن اجزای `CREATE TABLE` با چه ترتیب deterministicای render شوند.

برای مثال ممکن است چیزی شبیه این باشد:

```sql
CREATE TABLE `orders` (
    `id` INT NOT NULL AUTO_INCREMENT,

    `user_id` INT NOT NULL,

    PRIMARY KEY (`id`),

    UNIQUE KEY `uq_orders_code` (`code`),

    INDEX `idx_orders_user` (`user_id`),

    FULLTEXT INDEX `ft_orders_description` (`description`),

    SPATIAL INDEX `spx_places_location` (`location`),

    CONSTRAINT `fk_orders_user`
        FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`)
)
```

این ordering فقط مثال است.

بررسی کن:

* آیا grammar ترتیب خاصی دارد
* آیا ordering روی semantics تأثیر دارد
* آیا declaration order باید حفظ شود
* آیا collectionهای مستقل بهتر هستند
* آیا renderer باید ordering ثابت داشته باشد

در Final Contract ترتیب دقیق را مشخص کن.

# 24. Final Contract

در انتهای Traceability یک Final Contract دقیق ارائه کن.

Final Contract باید مشخص کند:

* دقیقاً چه featureهایی در v1.14 هستند

* DSL نهایی
* AST نهایی
* Builder validation
* Renderer validation
* SQL grammar
* SQL ordering
* Dialect behavior
* Version behavior
* Executor behavior
* compatibility impact
* test plan
* deferred features

Final Contract باید به اندازه‌ای دقیق باشد که developer دیگری بتواند implementation را انجام دهد بدون اینکه مجبور شود تصمیم معماری جدید بگیرد.

اگر چیزی هنوز مشخص نیست، بنویس:

```text

```

و دقیقاً توضیح بده چه evidenceای برای تصمیم‌گیری لازم است.

# نتیجه Traceability و Contract Analysis

## Status

`Implemented (scoped contract)` — تحلیل انجام شد. این وضعیت فقط به قرارداد محدودشدهٔ انتهای سند مربوط است؛ CHECK و SPATIAL type/SRID در این نسخه پیاده‌سازی نمی‌شوند.

## Objective

هدف این بررسی تعیین کوچک‌ترین قرارداد قابل‌پیاده‌سازی برای گسترش `CREATE TABLE` بود، با حفظ API و SQL قدیمی و بدون تغییر operationهای v1.6 تا v1.13.

## Repository Evidence

- مسیر واقعی ماژول‌ها به API، AST، Builder، params، dialect/renderer، executor، example و tests تفکیک شده است.
- `CREATE TABLE` فعلی فقط AST جدول، فهرست مرتب ستون‌ها و `ifNotExists` را نگه می‌دارد؛ هیچ table-level definition برای constraint یا index ندارد.
- `MigrationColumnDataType` یک sealed class مشترک است. افزودن spatial data type به آن، علاوه بر CREATE TABLE، rendererهای ADD COLUMN و MODIFY COLUMN را نیز درگیر می‌کند.
- API فعلی `addColumn { ... }` به AST ستون اضافه می‌کند. Builder مقدارها را عمدتاً مستقیم نگه می‌دارد؛ validation اصلی در MySQL renderer است.
- renderer فعلی table/column identifierها را quote و backtick را دوبرابر می‌کند؛ validation شامل نام جدول/ستون، وجود حداقل یک ستون، نام تکراری، یک PK ستونی، نوع داده، default و قواعد AUTO_INCREMENT است.
- SQL فعلی تمام ستون‌ها را به ترتیب ثبت‌شده render می‌کند و PK ستونی را در definition خود ستون می‌آورد.
- مسیر عادی executor، SQL ساخته‌شده را از مسیر `IQueryExecute.executeTable` اجرا می‌کند.
- `DialectSelector` هر دو `MySqlDialect` و `MariaDbDialect` را ثبت می‌کند؛ `MariaDbDialect` از grammar/registration مشترک MySQL ارث می‌برد. v1.14 نباید با این inheritance ادعای پشتیبانی database-specific اضافه کند.
- config می‌تواند `targetDatabaseVersion` داشته باشد و selector آن را دریافت می‌کند؛ با این حال `executeOut` عمومی `MigrationExecutor` در مسیر عادی selector را فقط با dialect فراخوانی می‌کند. پس target-version policy عمومی هنوز در مسیر معمول CREATE TABLE اعمال/انتقال داده نشده است.
- compatibility target/minimum version عمومی MySQL یا MariaDB در repository اعلام نشده است.
- operationهای v1.6 تا v1.13 موجودند؛ AST مستقل operationها شامل table-level CREATE TABLE definitions نیست. reuse مستقیم ASTهای آن‌ها برای statement داخل CREATE TABLE مناسب نیست، اما قراردادهای معنایی‌شان می‌تواند مرجع باشد.
- در ماژول‌های بررسی‌شده، expression AST برای CHECK و spatial column type/SRID modifier پیدا نشد.

## Existing CREATE TABLE Architecture

```text
CreateTable API
  ├── table { ... }
  ├── addColumn { ... }  → ordered columns
  └── ifNotExists()
       ↓
MigrationRenderCreateTableAst
  ├── migrationTableAst
  ├── columns: MutableList<IMigrationColumnAst>
  └── ifNotExists
       ↓
MySqlMigrationRenderCreateTableCapability
  ├── validate table/columns
  ├── render columns through registry
  └── CREATE TABLE ... (columns in insertion order)
       ↓
MigrationExecutor → IQueryExecute.executeTable
```

خط مبنا برای سازگاری: اگر هیچ table-level definition جدیدی داده نشود، SQL تولیدشده باید دقیقاً همان SQL قبلی باشد.

## Existing Migration Operation Traceability

|---|---|
| v1.6 CREATE INDEX و v1.12 `using(BTREE/HASH)` | قرارداد تک‌ستونی index مرجع syntax است؛ AST/API اجرایی آن مستقیم reuse نمی‌شود. |
| v1.7 DROP INDEX | برای تعریف در CREATE TABLE کاربرد مستقیم ندارد؛ drop جدا باقی می‌ماند. |

| v1.9 CREATE MULTI-COLUMN INDEX | ترتیب ستون‌ها و duplicate policy مرجع است؛ AST operation مستقیم reuse نمی‌شود. |

هیچ abstraction عمومی Index یا Constraint فقط به دلیل شباهت fieldها استخراج نمی‌شود. تنها یک ordered table-definition collection توجیه دارد، چون CREATE TABLE باید column و table-level definitionهای ناهمگون را به‌صورت typed نگه دارد.

## Primary Key Analysis

MySQL و MariaDB table-level `PRIMARY KEY (col, ...)` را می‌پذیرند. MySQL فقط یک PK برای جدول می‌پذیرد، آن را unique و NOT NULL می‌داند، و صریحاً می‌گوید attribute ستونی `PRIMARY KEY` برای کلید چندستونی کافی نیست؛ برای composite باید table-level clause باشد. MariaDB نیز PK را constraint سطح جدول می‌داند.

قرارداد: حفظ `primaryKey()` فعلی برای single-column و افزودن table-level `primaryKey { columns(...) }` برای ۱..N ستون. هر دو شکل در یک CREATE TABLE قابل ترکیب نیستند؛ بیش از یک PK رد می‌شود. تمام ستون‌های عضو باید NOT NULL باشند؛ Builder/renderer ساختار declaration را validate می‌کند و دیتابیس نیز legality نهایی را اعمال می‌کند. ترتیب ستون‌های composite حفظ می‌شود.

## UNIQUE Analysis

هر دو سرور table-level `UNIQUE (...)` با یک یا چند key part دارند. در MySQL، UNIQUE index/constraint برای ستون nullable اجازهٔ چند مقدار NULL می‌دهد. از دید database، unique constraint با unique index به هم پیوند دارند؛ API این پروژه همچنان می‌تواند syntax/semantic را در CREATE TABLE به‌عنوان table-level UNIQUE بیان کند.

قرارداد: `unique { name(...); columns(...) }`، نام صریح اجباری، حداقل یک و حداکثر نامحدود از دید API، ترتیب حفظ‌شده؛ duplicate نام ستون‌ها طبق policy case-insensitive خانوادهٔ index رد می‌شود ولی spelling اولیه ذخیره می‌ماند. Builder محتوای داده یا تکراری‌بودن رکوردهای موجود را بررسی نمی‌کند. نام‌گذاری صریح یک قرارداد کتابخانه برای قابلیت ردیابی است، نه الزام grammar هر دو سرور.

## INDEX Analysis

MySQL و MariaDB هر دو index table-level تک‌ستونی و چندستونی دارند. v1.12 فقط syntax اختیاری `USING BTREE/HASH` را برای CREATE INDEX معمولی تعریف کرده است؛ پشتیبانی واقعی method وابسته به engine/server است.

قرارداد: `index { name(...); columns(...); using(...) }` با نام اجباری، حداقل یک ستون، ترتیب مهم، و method اختیاری از enum موجود BTREE/HASH. اگر method omitted باشد هیچ clause جدیدی render نشود. API ادعای سازگاری engine یا موفقیت اجرایی نمی‌کند.

## FULLTEXT Analysis

MySQL grammar از FULLTEXT table-level definition با یک یا چند key part پشتیبانی می‌کند؛ در MySQL 8.4 engine و data type محدودیت دارند (InnoDB/MyISAM و CHAR/VARCHAR/TEXT). MariaDB engineهای پشتیبانی‌شدهٔ متفاوتی دارد و محدودیت‌های schema خودش را اعمال می‌کند. این قواعد، اعتبارسنجی اسمی identifierها نیستند و بدون schema introspection نباید در Builder ادعا شوند.

قرارداد: `fullTextIndex { name(...); columns(...) }`، حداقل یک ستون، ترتیب حفظ‌شده، نام صریح برای deterministic DDL. Parser/search options وارد scope نمی‌شوند. نوع واقعی ستون/engine/partitioning/charset و eligibility به database واگذار می‌شود.

## SPATIAL Analysis

syntax table-level وجود دارد؛ محدودیت‌های engine و ستون‌ها بین محصولات/نسخه‌ها متفاوت است. در MySQL 8.4 برای ساخت SPATIAL index ستون باید NOT NULL باشد؛ SRID-restricted بودن ستون شرط استفادهٔ optimizer از index است و با شرط ساخت یکی گرفته نمی‌شود. MariaDB از spatial index در engineهای مشخصی پشتیبانی می‌کند و semantics نوع geometry/SRID آن با MySQL یکسان فرض نمی‌شود.

تصمیم: SPATIAL index و spatial data types در v1.14 defer شوند. دلیل: type hierarchy فعلی مشترک با ADD/MODIFY COLUMN است و spatial/SRID rendering به policy محصول/نسخه و syntax مخصوص هر dialect نیاز دارد؛ generic `PointType` بدون این تصمیم‌ها contract کاملی نیست. v1.14 نباید `MariaDbDialect` را به‌طور ضمنی با MySQL SPATIAL semantics توسعه دهد.

## FOREIGN KEY Analysis

MySQL grammar table-level FK و composite referencing columns را پشتیبانی می‌کند؛ syntax رسمی شامل `CONSTRAINT symbol`, `FOREIGN KEY (...) REFERENCES ... (...)`, و actionهای ON DELETE/ON UPDATE است. v1.13 همین semanticها را برای عملیات مستقل بسته است.

قرارداد: در CREATE TABLE یک table-level FK با نام اجباری، دو لیست positional و هم‌اندازه، actionهای موجود v1.13، و همان trim/duplicate policy اضافه شود. AST داخل CREATE TABLE مستقل باشد ولی مدل semantic v1.13 (لیست‌ها و ForeignKeyActionها) را mirror کند؛ AST اجرایی v1.13 که برای ALTER TABLE تولید شده مستقیم نگهداری نشود. ساخت supporting index یا بررسی وجود جدول/ستون reference شده انجام نمی‌شود؛ این محدودیت‌ها مسئولیت DB هستند.

## CHECK Analysis

MySQL 8.0 فقط از 8.0.16 به بعد CHECK constraint را می‌پذیرد/اجرا می‌کند؛ syntax expression می‌خواهد و `[NOT] ENFORCED` هم دارد. MariaDB CHECK را از 10.2.1 پشتیبانی می‌کند و API آن expression می‌خواهد. compatibility target عمومی repository موجود نیست.

تصمیم: CHECK در v1.14 رد/defer شود. رشتهٔ SQL خام یا `Map<String, Any>` به‌عنوان expression مجاز نیست و پروژه expression AST ندارد. اجرای CHECK بدون مدل expression امن و معنایی نیست و version floor نیز اعلام نشده. برای بازگشت به این قابلیت ابتدا باید expression model و version policy مستقل تعریف شوند.

## Spatial Data Types Analysis

MySQL geometry family شامل GEOMETRY و subtypeهاست و SRID attribute بر اعتبارسنجی داده و استفاده optimizer اثر دارد. MariaDB نیز geometry types دارد اما SRID declaration/semantics آن متفاوت است. نوع spatial صرفاً یک SQL token ساده نیست؛ افزودنش به sealed `MigrationColumnDataType` اثر API آنی روی CREATE, ADD و MODIFY COLUMN دارد.

تصمیم: هیچ `PointType` یا family جدیدی در v1.14 اضافه نشود. این کار به قرارداد جداگانهٔ spatial types با product/version-aware syntax و پوشش CREATE/ADD/MODIFY نیاز دارد. در v1.14 SPATIAL index هم defer شده است تا type ناقص و index غیرقابل‌استفاده به‌عنوان feature کامل عرضه نشود.

## DSL Analysis

سطح DSL زیر افزوده می‌شود و APIهای موجود تغییر نمی‌کنند:

```kotlin
createTable {
    table { name("orders") }
    addColumn { name("tenant_id"); dataType(IntType()); notNull() }
    addColumn { name("user_id"); dataType(IntType()); notNull() }
    primaryKey { columns("tenant_id", "user_id") }
    unique { name("uq_orders_pair"); columns("tenant_id", "user_id") }
    index { name("idx_orders_pair"); columns("tenant_id", "user_id"); using(IndexMethod.BTREE) }
    fullTextIndex { name("ft_orders_text"); columns("description") }
    foreignKey {
        name("fk_orders_user")
        columns("tenant_id", "user_id")
        referencesTable("users")
        referencesColumns("tenant_id", "id")
        onDelete(ForeignKeyAction.CASCADE)
    }
}
```

نام نهایی متدها باید با naming فعلی API و packageهای موجود هم‌تراز شود؛ semantics بالا contract است. `columns(...)` برای هر definition فهرست ordered است؛ آخرین فراخوانی جای فهرست قبلی را می‌گیرد، حداقل تعداد رعایت می‌شود و ترتیب arguments حفظ می‌شود.

## AST Analysis

`IMigrationRenderCreateTableAst`، در کنار `migrationTableAst`, `columns`, `ifNotExists`، یک collection مرتب و typed برای table-level definitions خواهد داشت. این collection فقط definitionهای v1.14 را می‌پذیرد و به `Any`, map یا raw SQL متکی نیست.

- `PrimaryKeyDefinitionAst`: columnNames.
- `UniqueDefinitionAst`: indexName + columnNames.
- `IndexDefinitionAst`: indexName + columnNames + optional `IndexMethod`.
- `FullTextIndexDefinitionAst`: indexName + columnNames.
- `ForeignKeyDefinitionAst`: constraintName + columnNames + referencesTable + referencesColumnNames + optional delete/update actions.
- `IMigrationColumnAst` و `primaryKey()` فعلی دست‌نخورده‌اند.
- v1.6–v1.13 ASTها به این ASTها تبدیل یا تغییر داده نمی‌شوند.

## SQL Ordering

برای backward compatibility، renderer ابتدا column definitions را دقیقاً با ترتیب فعلی می‌نویسد. سپس table-level definitions را با ترتیب افزوده‌شدنشان در DSL می‌نویسد. این ترتیب ثابت است незалеж از grouping نوع definitionها. Column-level single PK قبلی همچنان در column SQL خود render می‌شود.

اگر هیچ table-level definitionی ثبت نشده باشد، SQL CREATE TABLE باید byte-for-byte با خروجی کنونی یکسان بماند (با لحاظ همان formatter فعلی). Renderer constraintهای PK/UNIQUE/index را بازمرتب نمی‌کند، حتی اگر سرور در metadata ترتیب داخلی دیگری نشان دهد.

## Builder Validation

- identifierها trim می‌شوند؛ blank رد می‌شود؛ casing/spelling پس از trim حفظ می‌شود.
- collectionهای columns باید به حداقل مقرر برسند؛ source و reference lists در FK باید هم‌اندازه باشند.
- تکرار ستون در هر یک از لیست‌ها با policy case-insensitive رد می‌شود؛ مقایسهٔ validation باعث تغییر spelling ذخیره‌شده نمی‌شود.
- حداقل/حداکثر ساختاری AST (یک PK، عدم ترکیب PK ستونی و table-level، non-empty columns) در renderer هم به‌صورت defensive بررسی می‌شود.
- Builder نوع واقعی/وجود ستون‌ها، داده‌های duplicate، engine، schema، collation، FK target/index و eligibility spatial را introspect نمی‌کند.

## Renderer Contract

Renderer پیش از quoting/composition AST را validate می‌کند؛ identifierها با helper فعلی MySQL quote و escape می‌شوند. Renderer تنها SQL grammar را render می‌کند؛ نه introspection/preflight، نه تبدیل syntax بر اساس اتصال، نه تضمین engine eligibility.

## Dialect Contract

در این scope rendererهای MySQL/MariaDB رفتار مشترک فقط برای PK, UNIQUE, normal index, FULLTEXT و FK table-level claim می‌کنند. registration فعلی حفظ می‌شود. به دلیل inheritance موجود، هیچ قابلیت MySQL-only spatial/check یا feature version-sensitive از مسیر MariaDbDialect claim نمی‌شود. compatibility target عمومی همچنان تعیین‌نشده است؛ renderer در این version policy تازه‌ای اضافه نمی‌کند.

## Executor Contract

همان `MigrationExecutor` و `IQueryExecute.executeTable` برای اجرای CREATE TABLE استفاده می‌شوند. executor/manager introspection یا executeSelect جدید اضافه نمی‌کند. rendering و execution همان مسیر فعلی را طی می‌کنند.

## MySQL Evidence

مستند رسمی MySQL 8.4 برای CREATE TABLE grammar موارد column، index، FULLTEXT/SPATIAL، PK، UNIQUE، FK و CHECK را در create_definition می‌آورد. برای PK می‌گوید فقط یک PK در هر جدول است، composite آن باید table-level باشد و ستون‌هایش NOT NULL هستند. UNIQUE و چند key part در grammar هستند. FULLTEXT فقط برای InnoDB/MyISAM و CHAR/VARCHAR/TEXT ذکر شده است. SPATIAL محدودیت NOT NULL و engine دارد. FK syntax شامل دو لیست ستونی و referential actions است. CHECK expression دارد و نسخه‌های MySQL پیش از 8.0.16 نباید به‌عنوان enforcement compatibility فرض شوند.

- MySQL 8.4 CHECK Constraints: https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html
- MySQL 8.4 Creating Spatial Indexes: https://dev.mysql.com/doc/refman/8.4/en/creating-spatial-indexes.html

- MySQL 8.0 Spatial Data Types/SRID: https://dev.mysql.com/doc/refman/8.0/en/spatial-type-overview.html

## MariaDB Evidence

مستند جاری MariaDB CREATE TABLE می‌گوید هر definition یا column می‌سازد یا index/constraint روی یک یا چند ستون. grammar مستقل CONSTRAINT شامل PRIMARY KEY, FOREIGN KEY, UNIQUE و CHECK در table level است. MariaDB FK shortcut به شکل inline column `REFERENCES` تفاوت نسخه‌ای دارد و در نسخه‌های قدیمی‌تر بی‌اثر است؛ بنابراین قرارداد از آن shortcut استفاده نمی‌کند. MariaDB CHECK از نسخهٔ 10.2.1 پشتیبانی شده است. Spatial index در engineها و با semantics مخصوص MariaDB تعریف می‌شود؛ این برای reuse خودکار MySQL renderer کافی نیست.

| CHECK | Defer | expression AST و compatibility policy وجود ندارد |
| Spatial data types/SRID | Defer | cross-operation type system و dialect/version impact |
| Generic IndexOptions / Constraint framework | Reject | abstraction بی‌نیاز و خلاف scope فعلی |
| raw SQL / map | Reject | type safety/validation را دور می‌زند |

## Final Contract

v1.14 یک افزونهٔ additive به `CREATE TABLE` است که table-level Primary Key، UNIQUE، normal INDEX (single/multi + optional existing BTREE/HASH), FULLTEXT INDEX و FOREIGN KEY را می‌پذیرد.

- تمام column definitions قدیمی و ترتیبشان حفظ می‌شوند.
- تمام table-level definitions در یک typed ordered list ذخیره و پس از columns به ترتیب DSL render می‌شوند.
- primary key ستونی فعلی حفظ می‌شود؛ table-level PK برای composite (و فهرست غیرخالی) می‌آید؛ دو شکل یا چند PK هم‌زمان رد می‌شوند.
- نام UNIQUE/index/FULLTEXT/FK در contract کتابخانه اجباری است.
- key-part order حفظ می‌شود؛ duplicate column validation case-insensitive است، spelling ذخیره‌شده تغییر نمی‌کند.
- FK دقیقاً همان field/action contract v1.13 را دارد اما AST آن متناسب CREATE TABLE است.
- فقط MySQL/MariaDB SQL grammar مشترک این operationها در scope است؛ هیچ minimum server version عمومی claim نمی‌شود.
- CHECK، SPATIAL و spatial type/SRID در این نسخه نیستند.

## Compatibility Impact

- APIهای فعلی و single-column `primaryKey()` تغییر نمی‌کنند.
- callهایی که table-level definition جدید ندارند، SQL قبلی را بدون تغییر حفظ می‌کنند.
- `MigrationColumnDataType` و rendererهای CREATE/ADD/MODIFY برای spatial typeها تغییر نمی‌کنند.
- v1.6–v1.13 operation semantics دست‌نخورده می‌مانند.
- compatibility floor محصول همچنان یک finding برای repository است، نه مقدار قابل حدس از local DB.

## v1.2 Dependency

بررسی plan v1.2 و source وابستگی لازم برای این قرارداد را نشان نداد. target version config موجود است اما compatibility target عمومی نه؛ این قرارداد syntax-version fallback نمی‌سازد. پس v1.2 مانع این scope نیست. مسیر معمول CREATE TABLE با target version متصل نیست؛ اگر در آینده feature خاص version-dependent وارد شود، این finding باید جداگانه حل شود.

## Test Plan

تست‌های پیاده‌سازی شامل regression SQL قبلی؛ single/composite PK و حالت‌های نامعتبر؛ auto-increment همراه table-level PK؛ UNIQUE؛ INDEX تک/چندستونی و BTREE/HASH؛ FULLTEXT؛ FK composite/action؛ ordering؛ trim/casing؛ blank/duplicate؛ AST ناقص؛ quoting/escaping؛ و مسیر executor success/failure بدون `executeSelect` هستند. اجرای کامل `:data_base:migration:example:test` و `:data_base:migration:executor:test` با موفقیت تمام شد: به‌ترتیب 104 و 32 تست، بدون failure/error/skip. این دو suite regression مثال‌های v1.6 تا v1.13 را نیز پوشش می‌دهند.

## Deferred / Out of Scope

- CHECK و SQL expression AST.
- SPATIAL index، geometry types و SRID modifiers.
- inline column `REFERENCES` sugar.
- table options, engine selection, parser, prefix length, key direction, visibility/ignored, generated names, IF NOT EXISTS برای index definitions.
- introspection/preflight، FK supporting index management، database eligibility validation.
- abstraction عمومی index/constraint/options یا raw SQL escape hatch.

## Unresolved Decisions

هیچ unresolved design decisionی برای scope نهایی بالا باقی نمانده است. دو finding بیرون scope باقی‌اند و مانع implementation این قرارداد نیستند:

1. repository هنوز compatibility target عمومی MySQL/MariaDB را اعلام نکرده است.
2. integration test واقعی دیتابیس اجرا نشد؛ unit و executor contract بدون اتصال دیتابیس پوشش داده شده‌اند.
