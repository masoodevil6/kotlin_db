# Migration v1.17: قرارداد وضعیت سیستمی و Bootstrap

## وضعیت

`Implementation Ready` — implementation code is present; real-database integration verification is pending.

## هدف

در این نسخه، سازوکار **System Migration State** بررسی و طراحی شود.

این بخش باید **قبل از اجرای هر Migration مربوط به Schema/Application** اجرا شود و وظیفه آن آماده‌سازی و خواندن وضعیت داخلی Migration Engine باشد.

هدف این نسخه این است که مشخص شود `kotlin_db` چگونه:

1. وجود جدول سیستمی Migration را بررسی می‌کند.
2. در صورت نبودن، جدول سیستمی را ایجاد می‌کند.
3. وضعیت فعلی Migration را از آن می‌خواند.
4. این وضعیت را در اختیار Migration Runner آینده قرار می‌دهد.
5. پس از اجرای موفق Migration، امکان ثبت/به‌روزرسانی وضعیت را فراهم می‌کند.

در این مرحله **کدنویسی انجام نشود**، مگر اینکه شواهد Repository نشان دهد بخشی از این قرارداد از قبل پیاده‌سازی شده و فقط نیاز به تکمیل دارد.

# 1. مسئله

قبل از اینکه Migration Engine بتواند Migrationهای واقعی را اجرا کند، باید بداند Database در چه وضعیت Migration قرار دارد.

جریان مفهومی مورد انتظار:

```text
Migration Runner
      │
      ▼
System Migration State
      │
      ├── آیا جدول System Migration وجود دارد؟
      │       │
      │       ├── خیر → ساخت جدول
      │       │
      │       └── بله
      │
      ├── خواندن وضعیت فعلی
      │
      ▼
تشخیص Migrationهای مورد نیاز
      │
      ▼
اجرای Migrationها
      │
      ▼
ثبت وضعیت جدید
```

ساختار دقیق جدول و نحوه نمایش State در این مرحله **از پیش تعیین نشده است**.

# 4. Bootstrap جدول سیستمی

مشخص شود سیستم چگونه متوجه می‌شود جدول System Migration وجود دارد یا خیر.

بررسی شود که آیا:

```sql
CREATE TABLE IF NOT EXISTS ...
```

کافی است یا نیاز به بررسی جداگانه وجود دارد.

همچنین بررسی شود:

* آیا Syntax به Dialect وابسته است؟
* ساخت جدول متعلق به Migration Engine است یا Migration subsystem؟
* آیا از Rendererهای فعلی می‌توان استفاده کرد؟
* در صورت خطا هنگام ساخت جدول چه اتفاقی می‌افتد؟
* آیا Bootstrap باید چندبار بدون ایجاد مشکل قابل اجرا باشد؟

Bootstrap باید **Idempotent** باشد.

یعنی اجرای مجدد آن نباید باعث ایجاد وضعیت خراب یا Duplicate Table شود.

# 5. تعریف وضعیت فعلی Migration

دقیقاً مشخص شود منظور از:

> Current Migration State

چیست.

بررسی شود که آیا State فعلی نشان‌دهنده یکی از موارد زیر است:

* Current Batch
* آخرین Migration Version
* آخرین Migration Identity
* تعداد Migrationهای اجراشده
* ترکیبی از چند مورد
* مدل دیگری

نباید فرض شود:

```text
batch == migration version
```

این دو مفهوم باید صریحاً از یکدیگر تفکیک شوند.

# 6. تفاوت Batch و Migration Version

به‌طور مشخص بررسی شود:

```text
Batch
```

چه مفهومی دارد و:

```text
Migration Version / Ordering
```

چه مفهومی دارد.

مثلاً ممکن است:

```text
Migration 1 → Batch 1
Migration 2 → Batch 1
Migration 3 → Batch 2
Migration 4 → Batch 2
```

در این حالت:

```text
Current Batch = 2
```

اما:

```text
Latest Migration = 4
```

این دو مقدار یک چیز نیستند.

طرح نهایی باید مشخص کند Migration Runner آینده به کدام یک یا هر دو نیاز خواهد داشت.

# 7. وضعیت اولیه Database

رفتار زمانی که Database برای اولین بار ساخته می‌شود مشخص شود.

مثلاً:

```text
Database
   │
   ├── System Migration Table وجود ندارد
   │
   ▼
ساخت جدول
   │
   ▼
Initial State
```

باید مشخص شود:

* Initial State چیست؟
* آیا مقدار `0` دارد؟
* آیا State تهی دارد؟
* آیا نبودن Record به معنی Initial State است؟
* آیا اولین Migration باید State خاصی داشته باشد؟

مقداری مانند `0` بدون دلیل قراردادی تعیین نشود.

# 9. عملیات خواندن State

عملیات دقیق مورد نیاز برای خواندن State مشخص شود.

اگر مثلاً پیشنهاد شود:

```sql
SELECT MAX(batch)
FROM system_migration;
```

باید توضیح داده شود که چرا این Query دقیقاً State مورد نظر را نمایش می‌دهد.

اگر State واقعی بر اساس Migration Version باشد، Query مناسب آن طراحی شود.

نباید صرفاً چون یک SELECT لازم است، `executeSelect()` عمومی به Executor اضافه شود.

# 10. به‌روزرسانی State

مشخص شود پس از اجرای موفق Migration، System Migration State چگونه به‌روزرسانی می‌شود.

در این نسخه لازم نیست Migration Runner کامل طراحی شود.

فقط Contract مورد نیاز State subsystem مشخص شود.

جریان مفهومی:

```text
Migration
   │
   ▼
Execution
   │
   ├── Failure → State نباید موفقیت را ثبت کند
   │
   └── Success
          │
          ▼
    Update Migration State
```

دقیقاً مشخص شود چه چیزی ثبت می‌شود:

* Migration
* Batch
* Version
* Timestamp
* یا ترکیبی از این موارد.

# 13. مرز Dialect

بررسی شود System Migration Table چگونه با معماری فعلی Dialectها هماهنگ می‌شود.

مشخص شود:

* آیا ساخت System Table از Renderer فعلی Migration استفاده می‌کند؟
* آیا نیاز به Renderer داخلی اختصاصی وجود دارد؟
* آیا Syntax ساخت System Table با Migrationهای عادی تفاوت دارد؟
* آیا MySQL و MariaDB می‌توانند Contract یکسان داشته باشند؟
* آیا طراحی باید از همین حالا برای SQLite قابل استفاده باشد؟

SQLite در این نسخه پیاده‌سازی نشود.

اما Contract نباید بدون دلیل طوری طراحی شود که پشتیبانی آینده از SQLite دشوار یا غیرممکن شود.

# 16. Concurrency

بررسی شود آیا اجرای همزمان Migration Runner در محدوده این نسخه است یا خیر.

مثلاً:

```text
Process A
   ↓
read state

Process B
   ↓
read state

Process A
   ↓
execute migration

Process B
   ↓
execute same migration
```

نباید بدون Requirement واقعی Locking یا Distributed Lock طراحی شود.

فقط مشخص شود:

* آیا Concurrency فعلاً در Scope است؟
* آیا معماری فعلی Single Runner فرض می‌کند؟
* آیا Contract باید فقط امکان اضافه شدن Locking در آینده را محدود نکند؟

اگر خارج از Scope است، صریحاً ثبت شود.

---

# 17. Transaction Boundary

Transaction کامل Migration Runner در این نسخه طراحی نشود.

فقط مرز State subsystem بررسی شود.

به‌خصوص بررسی شود آیا در آینده باید:

```text
Migration Execution
+
State Update
```

در یک Transaction قرار بگیرند یا خیر.

این موضوع را با قابلیت‌های واقعی Database و Dialect بررسی کنید.

اگر تصمیم نهایی وابسته به Migration Runner آینده است، به‌عنوان Unresolved Decision ثبت شود.

# 18. Traceability Result: Evidence / Interpretation / Decision

مطابق روش برنامه‌ریزی فعلی Repository، سه لایه کاملاً جدا باشند.

### 18.1 Repository Evidence

| ID | Evidence from current repository |
|---|---|
| R1 | `data_base/migration/executor/src/main/kotlin/interfaces/IMigrationExecutor.kt` exposes DDL-operation overloads; it has no System Migration State or Runner API. |
| R2 | `data_base/migration/executor/src/main/kotlin/manager/MigrationExecutor.kt` renders migration operations and delegates DDL through `IQueryExecute.executeTable`. |
| R3 | `data_base/manager/execute/src/main/kotlin/interfaces/IQueryExecute.kt` already exposes `executeSelect(BuiltQuery)`, `executeUpdate(BuiltQuery)`, and `executeTable(BuiltQuery)`. |
| R4 | `data_base/manager/execute/src/main/kotlin/manager/QueryExecute.kt` uses prepared statements and binds parameters. `executeSelect` yields a `ResultSet` in its callback while statement resources are managed by the manager; callers must consume/close rows inside that callback. |
| R5 | `data_base/core/src/main/kotlin/query/reader/BuiltQuery.kt` converts named `:name` parameters to `?`, retaining values in `SqlParameter`. |
| R6 | CREATE TABLE AST/API and the registered MySQL renderer support `ifNotExists`; see `data_base/migration/ast/src/main/kotlin/schema/create_table/render_query_create_table/MigrationRenderCreateTableAst.kt` and `data_base/migration/renderer/src/main/kotlin/dialects/MySqlDialect.kt`. |
| R7 | `data_base/migration/renderer/src/main/kotlin/dialects/MariaDbDialect.kt` inherits `MySqlDialect` and currently shares its registered migration grammar. This records current code behavior, not a compatibility guarantee for every server version. |
| R8 | `data_base/core/src/main/kotlin/data_base/DatabaseConfig.kt` contains dialect and target version configuration; no migration-state configuration is present. Connection work is behind manager modules. |
| R9 | Repository search under `data_base/migration`, `data_base/manager`, and `data_base/core` found no implemented `MigrationRunner`, `SystemMigrationState`, `schema_migrations`, `batch_current`, or internal history persistence; matches are confined to plans. |
| R10 | `data_base/migration/example/src/main/kotlin/v1/migrations/IExampleV1.kt` and `managers/IManagerExample.kt` organize versioned public DSL render/execute examples; they do not expose System State. |
| R11 | Current manager execution does not provide a shared connection/transaction abstraction for the DDL operation and a subsequent state insert. |
| R12 | No official minimum MySQL/MariaDB compatibility target was found in `DatabaseConfig` or the migration executor. |

### 18.2 Official Database Documentation Evidence

| ID | Evidence |
|---|---|
| DB1 | MySQL documents that `CREATE TABLE IF NOT EXISTS` suppresses the already-exists error but does not verify that an existing table has the requested structure. |
| DB2 | MariaDB documents that `CREATE TABLE IF NOT EXISTS` creates only when the same-named table is absent; if present it emits a warning. |
| DB3 | SQLite documents that with `IF NOT EXISTS`, an existing same-named table or view makes `CREATE TABLE` a no-op without an error. |
| DB4 | MySQL lists non-temporary `CREATE TABLE` and DDL among statements that implicitly commit; this does not support promising an atomic, rollbackable DDL-plus-history transaction. |

Official sources reviewed:

* MySQL 8.4 `CREATE TABLE`: https://dev.mysql.com/doc/refman/8.4/en/create-table.html
* MariaDB `CREATE TABLE`: https://mariadb.com/docs/server/server-usage/tables/create-table
* SQLite `CREATE TABLE`: https://www.sqlite.org/lang_createtable.html
* MySQL 8.4 implicit commit: https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html

### 18.3 Interpretation

* R1–R5 show the State Store can use the existing manager read/write methods and parameter binding; no new public `executeSelect` or MigrationExecutor overload is evidenced.
* R4 means the Store must consume the ResultSet inside the callback rather than retain it after callback return.
* R6–R7 provide an existing bootstrap route through CREATE TABLE and the dialect registry. Integration tests still need to confirm behavior against each supported server.
* DB1–DB3 show `IF NOT EXISTS` gives idempotent creation only; it does not validate an existing state table's schema. The contract must not claim schema verification.
* R11 and DB4 mean atomicity between a migration's DDL and history insert cannot be promised with the current execution boundary. The crash window must be explicit and transaction/recovery design belongs to a future Runner decision.
* R9–R10 confirm System State is currently internal engine infrastructure; public examples demonstrate consumer DSL, not engine internals.
* No declared compatibility target was found, so this traceability cannot invent a minimum server version.

### 18.4 Scope Result

This result defines only the internal state subsystem. Pending-migration discovery, execution ordering, retry, rollback, locking, and concurrency orchestration remain future Runner responsibilities. The Runner is not designed or changed here.

# 20. Candidate Designs

حداقل سه مدل زیر با یکدیگر مقایسه شوند:

### Candidate A — History only

History-based:

```text
system_migration
├── id
├── migration
├── batch
└── executed_at
```

### Candidate B — Explicit current state only

Explicit State:

```text
system_migration
├── batch_current
└── ...
```

### Candidate C — History plus duplicated explicit state

History + Explicit State:

```text
migration history
+
current state
```

| معیار | A: History | B: Explicit state | C: History + state |
|---|---|---|---|
| سادگی | یک جدول و یک رکورد به‌ازای هر migration موفق | ساده ظاهری؛ برای identity/history ناکافی | ضعیف‌تر؛ دو منبع باید sync شوند |
| قابلیت توسعه | خوب؛ history منبع دادهٔ آینده است | ضعیف برای pending/rollback | بالا با هزینهٔ synchronization |
| تناسب با Runner | مناسب؛ identity اجراشده خوانده می‌شود | برای چند migration در یک batch کافی نیست | مناسب اما دارای state تکراری |
| History | کامل | ندارد مگر دوباره اضافه شود | کامل |
| Current State | از history استخراج می‌شود | خلاصهٔ مستقیم | از دو محل نگهداری می‌شود |
| خطر تناقض | کم؛ یک منبع حقیقت | خطر از دست‌دادن هویت/تاریخچه | بیشترین؛ دو مقدار قابل واگرایی |
| Rollback آینده | هویت‌های اجراشده موجودند؛ semantics rollback جداست | دادهٔ کافی ندارد | history موجود، با نگهداری دشوارتر |
| SQLite آینده | schema ساده و قابل نگاشت؛ نیازمند integration بعدی | قابل نگاشت | قابل نگاشت ولی دارای پیچیدگی اضافه |
| Query / synchronization | یک history read؛ current batch از همان رکوردها | کم، اما state ناکافی | read و update دو منبع |
| پیچیدگی | کم | متوسط در lifecycle واقعی | زیاد |

**انتخاب: Candidate A.** `executed_at` در قرارداد حداقلی لازم نیست: ordering ثبت را `id` می‌دهد و timestamp برای state فعلی لازم نیست، ضمن اینکه clock/timezone semantics اضافه می‌کند. اگر audit time به requirement واقعی تبدیل شد، باید جداگانه تصویب شود.

هیچ Candidate صرفاً به دلیل شباهت به Laravel برنده اعلام نشود.

## 22.2 Schema and State

```text
system_migration
├── id        INT NOT NULL AUTO_INCREMENT PRIMARY KEY
├── migration VARCHAR(255) NOT NULL UNIQUE
└── batch     INT NOT NULL
```

یک جدول و یک منبع حقیقت داریم. `currentBatch` مقدار استخراج‌شده از history است، نه ستون/ردیف جدا. برای history خالی `null` است.

## 22.3 Bootstrap / Read / Record

1. از CREATE TABLE DSL موجود با `tableName("system_migration")`، سه ستون فوق و `ifNotExists()` استفاده می‌شود.
2. پس از bootstrap موفق، State Store با `executeSelect` ردیف‌ها را به ترتیب `id ASC` می‌خواند و ResultSet را داخل callback مصرف و می‌بندد.
3. migration identityها دقیقاً به‌عنوان رشته‌های opaque بازگردانده می‌شوند؛ batch مثبت validate می‌شود؛ `currentBatch` بیشینه batch موجود یا null است.
4. پس از DDL موفق، `executeUpdate` یک `INSERT` پارامتری برای identity و batch می‌زند. مقدار batch را Runner آینده می‌دهد؛ State Store آن را تخصیص نمی‌دهد.
5. اگر جدول هم‌نام ساختار اشتباه داشته باشد، `IF NOT EXISTS` آن را اصلاح/تأیید نمی‌کند؛ SELECT/INSERT واقعی error را propagate می‌کند.

## 22.4 Public Surface and Deferred Boundaries

هیچ API/AST/Builder عمومی migration تغییر نمی‌کند. State Store یک component داخلی با dependency به `IQueryExecute` است. کشف، انتخاب، ترتیب یا اجرای pending migration، lock، retry، rollback و recovery از مسئولیت Store خارج‌اند. قرارداد حاضر Runner را طراحی/تغییر نمی‌دهد.

از آنجا که manager فعلی shared connection/transaction ارائه نمی‌کند و MySQL برای DDL implicit commit دارد، DDL و history insert atomic فرض نمی‌شوند؛ crash gap آشکارا باقی می‌ماند.

این بخش باید دقیقاً مشخص کند:

```text
System Migration State
├── Table
├── Identity
├── State
├── Bootstrap
├── Read
├── Update
└── Error behavior
```

Contract نهایی نباید شامل قابلیت‌هایی باشد که در Decisionها بررسی نشده‌اند.

# 26. Test Strategy — Traceability Decision

با توجه به داخلی بودن System Migration State در repository فعلی، اولویت تست‌ها اثبات رفتار subsystem است، نه نمایش آن از مسیر Example عمومی. قرارداد تست:

### Unit Tests — Required

منطق State، تفسیر History خالی/موجود، identity و batch، validation دادهٔ خراب و error mapping بدون نیاز به اتصال واقعی پوشش داده شوند.

### Integration Tests با Database واقعی — Required, opt-in

Bootstrap جدول، idempotency، read و update state با database واقعی بررسی شوند. اگر این تست‌ها به environment اختصاصی نیاز دارند، از unit testهای عادی جدا و opt-in باشند.

### Renderer Tests — Conditional

فقط در صورت معرفی Renderer یا SQL داخلی جدید، SQL و رفتار dialect آن به‌صورت unit test بررسی شود.

### Executor / Database Regression — Conditional

در صورت استفاده یا تغییر مسیر executor/manager، delegation موفق، propagation خطا و عدم ثبت موفقیت پس از execution failure تست شود. تغییرنکردن مسیرهای موجود نیز در regression suite پوشش داده شود.

حداقل سناریوهای رفتاری:

### Bootstrap

```text
System Table absent
→ create successfully
```

### Idempotency

```text
System Table exists
→ bootstrap does not recreate/fail
```

### Empty State

```text
Table exists
+
no records
→ expected initial state
```

### Existing State

```text
records exist
→ current state correctly resolved
```

### Invalid State

```text
malformed state
→ expected error behavior
```

### State Record

```text
successful migration
→ state updated
```

### DDL Failure

```text

→ state must not falsely indicate success
```

تست‌های Dialect و SQL Rendering نیز فقط در صورت وجود Renderer/SQL جدید لازم‌اند.

# 27. Example Strategy

## Repository Evidence دربارهٔ Exampleهای فعلی

* `IExampleV1` نمونه‌های versioned را از طریق API عمومی migration می‌سازد و قابلیت `render()` و `execute()` دارد.
* `IManagerExample` فهرست نمونه‌ها و flagهای `statusRun...` را بر اساس operationهای قابل استفاده مدیریت می‌کند و اجرای واقعی را با `MigrationExecutor` انجام می‌دهد.
* `IMigrationExecutor` entry pointهای operationهای schema را عرضه می‌کند؛ API عمومی برای System Migration State در آن دیده نمی‌شود.
* System Migration State در این پلن زیرساخت داخلی Engine برای Bootstrap، read و ثبت وضعیت است؛ در حال حاضر API/DSL عمومی مصرف‌کننده برای آن در قرارداد تعریف نشده است.

## Interpretation و Decision نهایی

Exampleهای فعلی برای نمایش API/DSL قابل استفادهٔ مصرف‌کنندگان کتابخانه هستند. ساختن Example عمومی برای جزئیات داخلی State بدون API مصرف‌کننده، آن را به‌اشتباه بخشی از سطح عمومی کتابخانه جلوه می‌دهد و به Definition of Done ارزشی اضافه نمی‌کند.

بنابراین Example عمومی برای v1.17 لازم نیست و از DoD حذف می‌شود. Contract نهایی API/DSL عمومی مصرف‌کننده معرفی نمی‌کند؛ نبود Example عمومی به‌دلیل internal بودن state engine ثبت شد و رفتار با unit/integration test پوشش داده می‌شود. اگر در آینده API عمومی مصرف‌کننده تعریف شد، Example آن API جداگانه ارزیابی می‌شود.

System Migration State نباید به Migration Runner کامل تبدیل شود. اگر برای تحلیل integration lifecycle مثال داخلی/fixture لازم باشد، آن را به‌عنوان test fixture بشمارید، نه Example عمومی versioned.

# 33. پاسخ نهایی به پرسش معماری

کوچک‌ترین mechanism مبتنی بر Repository فعلی یک **History-based internal State Store** است: جدول `system_migration` با CREATE TABLE موجود و `ifNotExists()` bootstrap می‌شود؛ State Store از `IQueryExecute.executeSelect` ردیف‌ها را داخل callback می‌خواند؛ پس از موفقیت DDL، identity و batch را با INSERT پارامتری از `executeUpdate` ثبت می‌کند. Current batch برابر بیشترین batch ثبت‌شده است و history خالی `null` دارد.

این راه‌حل API عمومی migration، AST/Builder/Renderer تازه، overload جدید executor، یا Example عمومی نمی‌خواهد. اجرای pending migrations را انجام نمی‌دهد و DDL به‌همراه درج history را atomic فرض نمی‌کند. Recovery از crash gap و transaction policy را Runner آینده تعیین می‌کند.
