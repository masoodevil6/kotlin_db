## Evidence Review

### Repository Evidence — source جاری

- `IModelBase` در Core خالی است؛ `IModel` در `models:eloquent` آن را extend می‌کند؛ `BaseModel` نیز خالی است.
- `Users` و `UserPhones` کلاس‌های قابل ساخت با propertyهای نمونه‌اند. در `Users`، property برابر `userAge: String?` است و annotation آن `QBColumn(name="age", alias="u_user_age")` می‌گوید. property به نام `age` وجود ندارد.
- `QBTable` روی class و `QBColumn` روی property است. نام و alias رشته‌اند؛ QBColumn فیلد `primaryKey` نیز دارد.
- Query API جاری string-based است: جدول با `table(String, String)` و ستون با `tableColumn(String, String)` مشخص می‌شود. Model overloadها و readerهای reflection در API/Builder کامنت‌اند.
- AST موجود رشته‌های table، table alias، column qualifier، column و SELECT alias را نگه می‌دارد. SELECT alias در node سطح بالاتر `QueryColumnsAst.ColumnAlias` است.
- Renderer جاری AST رشته‌ای را مصرف می‌کند؛ Executor قرارداد Model/annotation ندارد.
- Gradle جاری `query:builder → models:eloquent` و `query:builder → core/query:api/query:ast/kotlin-reflect` دارد. `models:eloquent → core` است. importهای Model در `CteInfoUser.kt` به‌تنهایی مصرف فعال Model-aware را ثابت نمی‌کنند.
- در source و exampleهای جاری، call سایت Model reference پیدا نشد. مثال‌های جاری مسیر رشته‌ای دارند. شواهد مصرف‌کنندهٔ خارجی در repository موجود نیست.

### Historical Evidence — revisionها و رفتار دقیق

- در revision `7b85b76`، API فعال جدول `table(KClass<T>)` داشت؛ `QueryToolsTable` نتیجهٔ `findAnnotation<QBTable>()` را به شکل خود annotation نگه می‌داشت.
- در همان revision، API فعال ستون `column(KClass<T>, KProperty1<T,R>)` داشت؛ `QueryToolsColumnsBase`، QBTable را از KClass و QBColumn را از property reference می‌خواند و هر دو annotation را نگه می‌داشت.
- dialect قدیمی `QBTable.name` را برای FROM، `QBTable.alias` را برای table alias و qualifier ستون، و `QBColumn.name` را برای شناسهٔ ستون SQL مصرف می‌کرد. مسیر مورد بررسی `QBColumn.alias` را در SELECT AST منتقل نمی‌کرد؛ alias SELECT از API/مسیر جداگانه می‌آمد. مسیر مذکور `primaryKey` را query-rendering برای ستون مصرف نمی‌کرد.
- در revision `58716ab` (v33)، public API فعال `table(KClass)` و `column(KClass, KProperty1)` بود. مثال‌های فعال A1–A5 از `table(Users::class)` و جفت‌های `column(Users::class, Users::userAge)` استفاده می‌کردند؛ نمونهٔ A1 همچنین UserPhones را در join و predicate با جفت KClass/property ارجاع می‌داد. بنابراین سابقه محدود به SELECT ساده نیست.
- v33 Builder مقدارهای annotation را مستقیم به AST می‌نوشت: جدول از QBTable.name/alias، ستون از QBTable.name/alias و QBColumn.name. QBColumn.alias به column-base AST نوشته نمی‌شد. نبود annotation به `null` منجر می‌شد؛ validation یا خطای دامنه‌ای مشخص در آن reader دیده نشد. این implementation فعال تاریخی بود، اما شواهد موجود در این بررسی صحت کامل همهٔ queryها/حالات metadata را ثابت نمی‌کند.
- در revision `b2c5d55` (v35)، transition به string API آغاز شده بود؛ public API رشته‌ای شد/فعال ماند، درحالی‌که بخشی از reader/interfaceهای داخلی هنوز generic بودند. v37/`59ce507` ساختار فعلی را وارد و Model overload/reader را کامنت کرد. Source history به‌تنهایی دلیل این تغییر را مشخص نمی‌کند؛ commit message/ساختار diff نشانگر گذار معماری است، نه مدرک قطعی اینکه علت bug، refactor، ساده‌سازی یا حذف عمدی feature بوده است.
- History نمونهٔ `Users::class` و `Users::userAge` را ثابت می‌کند. `Users.age` به‌عنوان Kotlin static property API در history اثبات نشد. call منفرد `column(Users::userAge)` در بخش کامنت‌شدهٔ A1، implementation فعال نیست و baseline محسوب نمی‌شود.

### Architecture Fit

- ماژول Core مالک IModelBase و annotationهاست و Models فقط به Core وابسته است.
- Query API در حال حاضر به Core و AST وابسته است. Bound عمومی `IModelBase` در API می‌تواند Modelهای `models:eloquent` را بشناسد بی‌آنکه API به interface اختصاصی `IModel` یا ماژول concrete آن وابسته شود.
- Reflection و نوشتن AST در architecture موجود در Builder رخ می‌دهد؛ Renderer و Executor مصرف‌کنندهٔ AST/string هستند.
- بنابراین نزدیک‌ترین مسیر به history و architecture، ورودی‌های typed در API، resolution در Builder، و lowering به AST فعلی است. وابستگی Builder به ماژول concrete Models لازم نیست تا `Users::class` به‌عنوان generic T پذیرفته شود؛ این نتیجه بر پایهٔ module/interface فعلی است، ولی dependency edge موجود را در این کار تغییر نمی‌دهد.

## Historical API Baseline Decision

### Repository Evidence → Historical Evidence → Architecture Fit → Decision

- **Repository Evidence:** API فعلی string-based است و overloadهای Model کامنت‌اند.
- **Historical Evidence:** KClass/property-pair API در v26/v33 فعال بوده و examples آن را برای table، select، join و predicate به کار برده‌اند. Readerها annotationها را resolve می‌کردند، اما رفتار QBColumn.alias ناقص/جدا از column reader بود و validation خطای metadata را ثابت نمی‌کرد.
- **Architecture Fit:** `KClass<T : IModelBase>` و `KProperty1<T,R>` با IModelBase در Core قابل بیان‌اند. Builder می‌تواند metadata را به رشته تبدیل و AST موجود را پر کند؛ Renderer و Executor به Model احتیاج ندارند.
- **Decision:** `Adapt Historical API` به‌عنوان v1.3 baseline. جدول با `table(Users::class)` و ستون با زوج صریح `column(Users::class, Users::userAge)` در DSL فعلی/هم‌خانواده resolve شود. API تاریخی را عیناً کپی نکنید: alias SELECT باید در جایگاه AST جاری نوشته شود و خطاهای metadata باید طبق قرارداد روشن باشند. `addColumn(Users::userAge)` بدون table class برای v1.3 Adopt نمی‌شود، چون baseline فعال، جفت table/property را به کار برده و association آن را صریح می‌کند.

دلیل کنارگذاشتن API تاریخی به‌عنوان قرارداد بدون تغییر، نقص evidence درباره alias و validation، و تفاوت معماری جاری است. دلیل Reject کامل نیز وجود سابقهٔ فعال قابل استفاده و سازگاری generic آن با AST جاری است. پس adaptation کم‌تغییرترین تصمیم مستند به evidence است.

## Decision 1: Model Reference Shape

| گزینه | Kotlin / Model فعلی | History و architecture | تصمیم |
|---|---|---|---|
| A: `table(Users::class)` و paired property reference | با class فعلی و instance property reference سازگار است؛ class قابل ساخت و reference به property از نوع Users است. برای UserPhones نیز همان الگو قابل استفاده است. | همان شکل در API/examples فعال v26/v33 و در bound Core فعلی قابل بیان است؛ بدون Model object/descriptor تازه. | **Adopt as adapted historical API**. |
| B: `table(Users)` و `addColumn(Users.age)` | با class فعلی به‌تنهایی سازگار نیست: `Users` value نیست و `age` property تعریف نشده. نیازمند object/companion/propertyهای تازه یا تغییر مدل است. | history فعال چنین قرارداد دقیقی را ثابت نمی‌کند؛ تغییر شکل مدل بیش از گزینه A است. | **Reject for v1.3** به‌عنوان API هدف؛ نه به‌معنای رد هر API static آینده. |
| C: `table(Users.table)` و `addColumn(Users.age)` | نیازمند member/descriptor جدیدی به نام table و property/reference مستقل است. | history فعلی چنین descriptorای را ندارد و AST برای lowered strings کافی است. | **Reject for v1.3**؛ abstraction اضافه بدون نیاز اثبات‌شده. |
| D: wrapper/reference دیگر | از نظر فنی قابل طراحی است، اما source/history ضرورت آن را نشان نمی‌دهد. | هزینه و API جدید بیشتری نسبت به historical KClass/property-pair دارد. | **Defer**؛ فقط با requirement تازه بازبینی شود. |

**Exact v1.3 call shape:**

```kotlin
table {
    table(Users::class)
}

addColumn {
    column(Users::class, Users::userAge)
    alias("age") // optional explicit SELECT alias
}
```

`column(KClass, KProperty1)` روی receiver بیرونی `IQueryColumnsApi` قرار می‌گیرد؛ همان receiver `alias(String)` را دارد. شکل `addColumn { column { column(...) } }` انتخاب نمی‌شود، چون default SELECT alias و override آن باید در همان outer column API resolve شوند و AST جاری alias را در outer `QueryColumnsAst` نگه می‌دارد. این adaptation signature را صریح می‌کند و base AST جدید لازم ندارد.

**Compatibility / readability / joins:** این گزینه کلاس‌های `Users` و `UserPhones` را حفظ می‌کند و history برای join/predicate نیز paired reference داشته است. مسیر string API حفظ می‌شود. Join و predicate خارج از scope v1.3 هستند. source compatibility با مصرف‌کنندگان بیرونی قابل اثبات نیست؛ policy بیرونی در repository وجود ندارد.

## Decision 2: Property → Database Column

### Repository Evidence → Historical Evidence → Architecture Fit → Decision

- **Repository Evidence:** `Users.userAge` دارای `QBColumn.name="age"` است؛ name annotation در مثال جاری از Kotlin property name متفاوت است.
- **Historical Evidence:** `KProperty1` برای یافتن QBColumn استفاده شده و builder تاریخی `QBColumn.name` را به شناسهٔ column در AST می‌نوشت. SQL dialect قدیمی همان annotation name را رندر می‌کرد.
- **Architecture Fit:** KProperty1 identity را به property مشخص می‌کند؛ QBColumn metadata نام DB را فراهم می‌کند. AST نام resolved را به صورت string می‌پذیرد.
- **Decision:** برای propertyای که `QBColumn` دارد، `QBColumn.name` canonical database identifier است. **Fallback به Kotlin property name مجاز نیست**؛ evidence آن را تعریف نمی‌کند و ممکن است SQL identifier نادرست بسازد.

نبود annotation و `name=""` در source تاریخی به شکل nullable عبور می‌کرد، اما آن رفتار معیار v1.3 نیست.

**Decision:** نبود `QBTable`، خالی‌بودن `QBTable.name`، نبود `QBColumn` یا خالی‌بودن `QBColumn.name` باعث `IllegalArgumentException` در resolution می‌شود. این با convention فعال Core یعنی `require` برای ورودی نامعتبر هم‌خوان است. پیام خطا باید annotation و class/property مربوط را مشخص کند؛ متن دقیق پیام جزئیات implementation است. هیچ fallback به Kotlin property name انجام نمی‌شود. Alias خالی تابع قاعدهٔ جداگانهٔ بخش Alias است.

## Decision 3: Annotation Resolution

### Resolution ownership

**Repository Evidence:** historical `QueryTableBuilder`/`QueryToolsTable` و `QueryColumnsBaseBuilder`/`QueryToolsColumnsBase` reflection و `findAnnotation` را در Builder/Query Builder انجام می‌دادند. API generic reflection typeها را می‌گرفت؛ Core محل annotation و markerهاست. AST/Renderer/Executor فقط دادهٔ حل‌شده را مصرف می‌کنند.

**Interpretation:** انتقال resolution به Query API، Models، Renderer یا Executor الگوی تاریخی/جاری لازم ندارد. Models وابسته‌کردن به Query را ایجاب نمی‌کند؛ API می‌تواند generic و Builder می‌تواند resolver باشد.

**Decision:** resolution در **Query Builder layer** انجام شود، هنگام materialize کردن API input به AST. Query API فقط typeهای reference را می‌پذیرد و نباید reflection resolution انجام دهد؛ AST نباید reflection بکند؛ Renderer و Executor نباید annotation Model را بشناسند.

### Exact mapping

```text
Users::class
  → QBTable روی class
  → tableName = QBTable.name
  → modelDefaultTableAlias = QBTable.alias

Users::userAge paired with Users::class
  → QBColumn روی property
  → databaseColumn = QBColumn.name
  → modelDefaultSelectAlias = QBColumn.alias
```

Table/property pair باید متعلق به یک Model type باشد. API تاریخی generic type pairing این رابطه را در compile-time محدود می‌کرد؛ v1.3 نباید property reference مدل دیگری را با table class نامرتبط قبول کند. نبود annotation یا name خالی طبق بخش قبل `IllegalArgumentException` می‌دهد. `primaryKey` به این lowering وارد نمی‌شود.

## Decision 4: Alias Contract

### SELECT alias

**Repository Evidence:** QueryColumnsAst فعلی alias خروجی را در outer column node نگه می‌دارد. API alias صریح نیز همان node را تنظیم می‌کند. Reader تاریخی QBColumn.alias را در column-base AST نمی‌نوشت؛ بنابراین precedent قدیمی precedence را تعیین نمی‌کند.

**Architecture Fit:** یک resolved SELECT alias string را outer alias node می‌تواند حمل کند؛ resolution precedence قبل از AST write قابل انجام است.

**Owner-provided contract clarification:** explicit query alias بر QBColumn.alias مقدم است؛ QBColumn.alias default SELECT alias است.

**Decision:** `Explicit Query Alias → QBColumn.alias → No Alias` را برای SELECT Adopt کن. اگر `alias(...)` فراخوانی نشود، مقدار پیش‌فرض از `QBColumn.alias` می‌آید؛ مقدار default خالی یعنی alias تولید نشود. `alias("")` صریحاً alias را پاک می‌کند و باید `ColumnAlias = null` در AST بگذارد؛ رشتهٔ صریح غیرخالی بر default مقدم است. پس omitted و explicit none از هم متمایزند.

### Table alias

**Repository Evidence:** `QBTable.alias` در dialect تاریخی alias جدول و qualifier ستون بود. API string جاری `table(String, String)` alias را صریح می‌گیرد؛ historical model table overload QBTable.alias را می‌خواند. explicit-over-default table precedence در implementation بررسی‌شده ثابت نشده. `QueryRenderSelectBuilder` فعلی select و table را با child builderهای جداگانه و بدون context مشترک می‌سازد؛ پس alias سفارشی table به‌صورت خودکار به column qualifierهای typed نمی‌رسد.

**Owner-provided contract clarification:** QBTable.alias پیش‌فرض SQL table alias است.

**Decision:** typed overload دقیقاً `table(model: KClass<T>, alias: String? = null)` است. حذف آرگومان یا `alias == null` یعنی استفاده از `QBTable.alias`؛ alias صریح غیرخالی بر default مقدم است؛ `alias == ""` صریحاً alias پیش‌فرض را پاک می‌کند. اگر metadata alias پیش‌فرض `""` باشد نیز table بدون alias است. چون renderer فعلی sentinel خالی را بررسی می‌کند، Builder در حالت بدون alias باید `tableAlias = ""` به AST جدول بدهد، نه null. **همان alias مؤثر باید qualifier ستون‌های typed همان Model نیز باشد.** از آنجا که root builder فعلی context مشترک ندارد و ترتیب DSL می‌تواند select را پیش از table بسازد، v1.3 به state/association موقت در سطح همان QueryRenderSelectBuilder برای ثبت Model class و alias مؤثر و اعمال آن به typed column AST نیاز دارد؛ این state داخلی است، node جدید AST یا public abstraction نیست. API رشته‌ای فعلی بدون تغییر می‌ماند.

## Decision 5: Dependency Direction

### Repository Evidence → Historical Evidence → Architecture Fit → Decision

- **Repository Evidence:** `query:builder → models:eloquent` در Gradle فعلی وجود دارد ولی public API فعال رشته‌ای است. `models:eloquent → core` است.
- **Historical Evidence:** Model-aware API به marker model در Core متکی بود؛ generic methods `KClass<T>`/`KProperty1<T,R>` داشتند. مثال‌ها concrete Models را در ماژول consumer/example می‌شناختند. این history وجود edge concrete Builder→eloquent را ضروری نمی‌کند.
- **Architecture Fit:** Query API می‌تواند T را به `IModelBase` در Core محدود کند. Builder به Core و kotlin-reflect دسترسی دارد. Consumer که typed syntax می‌نویسد هر دو artifact را برای call-site می‌آورد؛ Query Builder string API به Model artifact وابسته نمی‌شود.
- **Exact generic-bound location and signatures:** bound در سطح method و در interface صاحب همان API قرار می‌گیرد؛ interface کلی generic نمی‌شود.

```kotlin
// IQueryTableApi
fun <T : IModelBase> table(model: KClass<T>, alias: String? = null): IQueryTableApi

// IQueryColumnsApi
fun <T : IModelBase, R> column(
    table: KClass<T>,
    property: KProperty1<T, R>
): IQueryColumnsApi
```

- **Decision:** **Adopt optional typed integration without concrete `query:builder → models:eloquent` coupling as target architecture.** Typed signature generic و marker-bound به Core باشد؛ resolution در Builder؛ Models به Query وابسته نشوند؛ Query Builder بدون Models همچنان string-based usable بماند. این تصمیم دربارهٔ معماری هدف است، نه مجوز تغییر Gradle در این مرحله. edge موجود در implementation phase جداگانه فقط پس از compile/dependency verification بررسی/حذف شود.

این انتخاب هم جهت وابستگی `Model → Query Builder` را در سطح call-site/consumer ممکن می‌گذارد، هم وابستگی اجباری Query Builder به ماژول concrete Models را ایجاد نمی‌کند. هیچ evidenceی وجود ندارد که خود classهای `Users` باید به Query import داشته باشند.

### Scope of typed call sites

Historical evidence در select، table، join و predicates/model conditions referenceهای typed دارد. اما v1.3 plan scope را روی table و select-column گذاشته است؛ بزرگ‌کردن scope به خاطر history لازم نیست.

**Decision:** v1.3 = `table + select columns` فقط. Join/predicate/where/order/group/typed SQL expressions به نسخهٔ بعدی موکول شوند؛ history آن‌ها را candidate می‌کند، نه نیاز scope فعلی.

## Historical API Reconstruction

| مرحلهٔ تاریخی | رفتار مشاهده‌شده | ارزیابی |
|---|---|---|
| API | `table(KClass<T>)`; `column(KClass<T>, KProperty1<T,R>)` | type association صریح؛ منطبق با instance propertyهای Model جاری. |
| Table reader | `findAnnotation<QBTable>()`; نام و alias annotation به holder/AST | metadata resolution در Builder family. |
| Column reader | table annotation از KClass؛ column annotation از KProperty1 | property به table با generic T جفت می‌شود. |
| AST | table/name/alias/column به رشته/nullable field | ساختار مفهومی با AST رشته‌ای فعلی سازگار است. |
| Dialect | QBTable.name در FROM؛ QBTable.alias در FROM و qualifier؛ QBColumn.name برای SQL column | SQL مصرف‌کننده metadataهای حل‌شده بوده است. |
| SELECT alias | reader قدیمی QBColumn.alias را در base column نمی‌نوشت | gap واقعی؛ کپی مستقیم، owner alias contract را پیاده نمی‌کند. |
| PK/errors | reader path بررسی‌شده primaryKey را مصرف یا خطای missing annotation تعریف نمی‌کرد | قابلیت کامل یا ایمنی همهٔ حالت‌ها اثبات نشده. |
| Transition | v35 string API transition؛ v37 ماژول‌بندی/AST فعلی و کامنت‌کردن مدل overloadها | علت دقیق transition از source/history بررسی‌شده قابل تعیین نیست؛ intentional removal contract ثابت نشده. |

جمع‌بندی: API تاریخی یک **historically active usable path** برای metadataهای معتبر و مثال‌های موجود بوده، نه صرفاً sketch. اما API کامل/robust برای alias default و invalid metadata ثابت نشده است؛ baseline باید **Adapt** شود، نه blind copy و نه ادعای حذف عمدی.

## API Surface

| سطح | شواهد | تصمیم v1.3 |
|---|---|---|
| `table` | history فعال و API جاری string table | typed `table(Users::class)` داخل scope. |
| `addColumn` / `column` | `addColumn` یک lambda از IQueryColumnsApi می‌گیرد؛ outer `QueryColumnsAst` alias را نگه می‌دارد | overload typed روی IQueryColumnsApi قرار می‌گیرد تا property resolution و alias precedence در یک scope باشند. |
| `tableColumn` | فعال string API، AST qualifier+column | همچنان low-level/manual path و compatibility path بماند. |
| `join`, `where/condition` | تاریخچه typed usage دارد، جاری string/current plan محدود | out of scope برای v1.3. |
| `orderBy`, `groupBy` | ASTهایشان base string column مصرف می‌کنند؛ typed current API evidence ندارد | out of scope برای v1.3. |

## AST Decision

**Repository Evidence:** موجودی AST می‌تواند `tableName`, table alias، column qualifier، database column name و SELECT alias نهایی را به شکل رشته‌ای نگه دارد. Renderer این داده را مصرف می‌کند.

**Decision:** `Resolved Identifier AST: Sufficient` برای `Model Reference → resolved strings → existing Query AST`. Model-specific AST، typed/provenance AST یا nodeهای Model/Table/Column تازه اضافه نشوند. این حکم برای scope resolved table/select identifiers است و تضمینی برای typed predicates یا SQL type system نیست.

## Type Safety Boundary

**Decision:** KClass/property reference در حد identity/type Kotlin استفاده شود؛ KProperty1 generic R فقط `String?`, `Int` و مانند آن را به‌عنوان نوع Kotlin reference حمل می‌کند. SQL VARCHAR/INT، nullable بودن DB، operator validity، cast یا SQL expression type از آن inference نشود. Type-safe SQL system برای این scope **Defer** است.

## Backward Compatibility

- String APIهای `table(String, String)` و `tableColumn(String, String)` مسیرهای مستقل فعلی هستند و باید باقی بمانند.
- Typed API overload اضافه/هم‌خانواده است؛ callهای string موجود نباید به Model type نیازمند شوند.
- Model classها و `Users()`/`UserPhones()` در حد contract جاری تغییر شکل نمی‌دهند.
- API تاریخی از دید source repository حذف شده و comment است. Adopt کردن آن دوباره source capability تازه‌ای ایجاد می‌کند، نه تضمین binary compatibility.
- repository compatibility policy یا external consumer corpus ندارد؛ binary compatibility بیرونی **not specified in repository** است.
- Concrete Builder→Models Gradle edge فعلی، هدف architectural direction را تعیین نمی‌کند. تغییر edge در implementation task نیازمند compile/dependency verification است؛ در traceability هیچ dependency و build تغییر نکرد.

## Final Implementation Contract

### Model API

```kotlin
table {
    table(Users::class)
}

addColumn {
    column(Users::class, Users::userAge)
    // optional explicit override: alias("age")
}
```

همین الگو برای `UserPhones` قابل استفاده است. جدول typed داخل receiver جاری `IQueryTableApi` و ستون typed روی receiver بیرونی `IQueryColumnsApi` قرار دارد. `Users.age` و تبدیل Model به object/companion در v1.3 contract نیستند. Call مستقیم `addColumn(Users::userAge)` نیز baseline نیست؛ association با class صریح باقی می‌ماند.

### Resolution and lowering

```text
IQueryTableApi.table<T : IModelBase>(KClass<T>, alias?) → QBTable → name + selected table alias
IQueryColumnsApi.column<T : IModelBase, R>(KClass<T>, KProperty1<T,R>) → QBColumn → DB name + default SELECT alias
resolved strings → existing table/column AST fields
```

- generic bound در methodهای `IQueryTableApi` و `IQueryColumnsApi` است، نه در سطح interface؛ R نیز generic همان method ستون است.
- Query Builder layer (نه Renderer/Executor/AST) مسئول reflection resolution است.
- table/property pair باید type-compatible باشد.
- QBColumn.name canonical DB identifier است؛ هیچ fallback به Kotlin property name نیست.
- QBTable.alias default table qualifier/SQL alias است؛ null/omitted آرگومان از default استفاده می‌کند، مقدار غیرخالی explicit آن را override و `""` آن را پاک می‌کند. برای no-alias، AST جدول `tableAlias = ""` می‌گیرد چون renderer فعلی sentinel خالی را بررسی می‌کند.
- qualifier ستون typed باید alias مؤثر table را بگیرد، شامل override یا clear صریح. چون select/table child builderهای فعلی مستقل‌اند و chain معمولاً select را زودتر می‌سازد، orchestration در `QueryRenderSelectBuilder` باید association موقت typed-column↔Model و alias را نگه دارد/به‌روز کند. این نیاز از رفتار فعلی source استنتاج شده؛ implementation نباید qualifier را بی‌قیدوشرط از QBTable.alias بردارد وقتی table alias override شده است.
- SELECT alias: عدم فراخوانی alias از QBColumn.alias استفاده می‌کند؛ alias غیرخالی explicit مقدم است؛ `alias("")` آن را پاک و به `ColumnAlias = null` تبدیل می‌کند.
- `primaryKey` در typed reference lowering مصرف نمی‌شود.
- Kotlin property R فقط Kotlin reference type است؛ هیچ SQL type/nullability/operator inference ندارد.

### Dependency graph target

```text
models:eloquent → core
query:api / query:builder → core + query AST
consumer with typed calls → models:eloquent + query API/Builder
```

Query API generic bound را به IModelBase/Core محدود کند؛ Builder resolver نباید برای typed generic API به `models:eloquent` وابستگی اجباری داشته باشد. Query Builder و string API باید در نبود Models قابل مصرف بمانند. Renderer و Executor Model-unaware بمانند. Graph بالا target architecture است و در این traceability پیاده/آزمایش نشده است.

### Preserved surface

String `table(String, String)` و `tableColumn(String, String)` و Model declarations فعلی در این scope حفظ می‌شوند. typed references در v1.3 فقط table و SELECT columns هستند؛ join/predicates/order/group defer می‌شوند.

## Closure Notes

هیچ تصمیم معماری یا قراردادی در scope v1.3 برای implementation باز نمانده است. نوع خطای metadata و semantics aliasها تعیین شده‌اند؛ متن دقیق پیام `IllegalArgumentException` جزئیات implementation است و باید class/property نامعتبر را مشخص کند. Compatibility بیرونی در repository قابل سنجش نیست و binary compatibility تضمین نمی‌شود؛ string API داخلی حفظ می‌شود. این محدودیت، تصمیم باز درون scope نیست و تضمین سازگاری خارجی ادعا نمی‌شود.
