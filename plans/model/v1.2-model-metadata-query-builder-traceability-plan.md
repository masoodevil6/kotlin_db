# مدل نسخهٔ ۱.۲: ردیابی فرادادهٔ مدل تا زبان سازندهٔ پرس‌وجو

## وضعیت

`Ready for Traceability`

## هدف

این برنامه مرحلهٔ بعدی بررسی زیرسامانهٔ مدل را تعریف می‌کند: پیوند فرادادهٔ کنونی مدل با سازندهٔ پرس‌وجو را ردیابی می‌کند و مرزها و قراردادهای قابل اتکا برای یکپارچه‌سازی احتمالی و زبان آیندهٔ پرس‌وجو را مشخص می‌کند.

این مرحله شامل ردیابی مخزن، تحلیل معماری و وابستگی‌ها، بررسی قراردادها، تصمیم‌گیری و برنامه‌ریزی برای پیاده‌سازی است. در این مرحله هیچ پیاده‌سازی‌ای انجام نمی‌شود.

## زمینهٔ مخزن

مخزن در این برنامه:

```text
D:\projects\kotlin\query_builder\master\my_project
```

نام پروژه طبق درخواست: `kotlin_db`.

ساختارهای مورد انتظار صرفاً مبنای اولیه برای بررسی هستند و باید با کد واقعی مقایسه شوند:

```text
Query DSL → Builder → AST → Renderer → BuiltQuery → Executor

IModelBase ← IModel ← BaseModel ← Users / UserPhones
QBTable
QBColumn
```

برنامهٔ ردیابی نسخهٔ ۱.۱ و گزارش آن را به‌عنوان سابقه و شواهد اولیه بخوان؛ یافته‌ها را دوباره با کد منبع فعلی تطبیق بده و فرض‌های گزارش پیشین را بدون بررسی مجدد قطعی ندان.

## دامنه

- قرارداد مدل و annotationهای موجود را ردیابی کن؛
- مسیرهای اجرایی، توضیحی، نمونه‌ای و بدون مصرف در سازندهٔ پرس‌وجو را ردیابی کن؛
- مرز وابستگی میان یکپارچه‌سازی مدل و سازندهٔ پرس‌وجو را مشخص کن؛
- گزینه‌های معماری برای تبدیل فراداده به AST و زبان آیندهٔ پرس‌وجو را ارزیابی کن؛
- ارائهٔ جدول تصمیم‌گیری، قرارداد نهایی، تأثیر بر سازگاری و برنامهٔ آزمون پیشنهادی؛
- فهرست‌کردن دقیق تصمیم‌های unresolved و شواهد لازم برای حل آن‌ها.

## محدودیت‌ها

در این مرحله:

- کد منبع، آزمون‌ها، مستندات و رابط برنامه‌نویسی موجود را تغییر نده؛
- بازآرایی یا آزمایش زمان اجرا انجام نده؛
- سازندهٔ پرس‌وجو، AST، annotationها یا مدل‌های فعلی را تغییر نده؛
- واسط مدل، لایهٔ نماد، گرهٔ AST یا انتزاع تازه ایجاد نکن؛
- رابط برنامه‌نویسی عمومی مدل یا نگاشت عمومی فراداده مانند `Map<String, Any>` طراحی یا ایجاد نکن؛
- SQL خام، ORM، مخزن/CRUD، نگاشت ResultSet یا یکپارچه‌سازی با Migration اضافه نکن؛
- وابستگی اجباری از سازندهٔ پرس‌وجو به مدل ایجاد نکن؛
- درون‌نگری پایگاه داده یا بررسی مقدماتی انجام نده.

خروجی این مرحله سندی برای تحلیل و تصمیم‌گیری است؛ پیاده‌سازی فقط با درخواست جداگانه انجام خواهد شد.

## قواعد شواهد

برای هر تصمیم مهم، این موارد را جدا نگه دار:

```text
شواهد مخزن
        ↓
برداشت
        ↓
تصمیم
```

رفتار اجرایی کد را از کدهای توضیحی، نمونه‌ها، قرارداد پیشنهادی و گفته‌های صاحب مخزن جدا کن. اگر نکته‌ای فقط از درخواست یا توضیح کاربر آمده است، آن را با برچسب `Owner-provided contract clarification` ثبت کن و آن را شواهد مخزن جا نزن. در نبود شواهد، `Unresolved` بنویس.

## قرارداد فعلی مدل

در کد منبع فعلی بررسی کن:

### `IModelBase`

- محل تعریف و وراثت؛
- مصرف‌کنندههای فعال در برابر توضیح‌شده؛
- نشانگر بودن و وجود یا نبود رفتار زمان اجرا.

### `IModel`

- آنچه به `IModelBase` اضافه می‌کند؛
- مصرف‌کنندههای واقعی؛
- شواهد توجیه وجود انتزاع مستقل.

### `BaseModel`

- رفتار و زمان اجرا قرارداد؛
- رابطه با مدل‌های موجود؛
- اینکه آیا فقط کلاس پایهٔ خالی است.

### مدل‌ها

حداقل `Users` و `UserPhones` را بررسی کن. برای هرکدام فرادادهٔ جدول و ستون، نام‌های مستعار، پرچم کلید اصلی، ویژگی‌های Kotlin، سازنده، تغییرپذیری و تهی‌پذیری را ثبت کن و میان قرارداد اثبات‌شده و شکل نمونه تمایز بگذار.

## ردیابی `QBTable`

تعریف واقعی annotation و همهٔ کاربردها را بیاب. همهٔ خوانشگرها، خوانشگرهای توضیح‌شده، مقصدهای AST و مقصدهای رندرکننده قابل ردیابی را بررسی کن.

قراردادهای مورد بررسی:

```text
QBTable.name  = نام جدول
QBTable.alias = نام مستعار پیش‌فرض جدول در SQL
```

این موارد را با شواهد تطبیق بده. برای نقل‌قول‌گذاری شناسه، نام یا نام مستعار خالی، تعیین schema، حساسیت به بزرگی و کوچکی حروف و شناسه‌های رزروشده در نبود شواهد، صریحاً `Unresolved` ثبت کن.

## ردیابی `QBColumn`

همهٔ اعلان‌ها، کاربردها و مصرف‌کنندگان `QBColumn` را بررسی کن. قراردادهای مورد بررسی:

```text
QBColumn.name       = نام ستون پایگاه داده
QBColumn.alias      = نام مستعار پیش‌فرض در SELECT
QBColumn.primaryKey = فرادادهٔ کلید اصلی
```

شواهد را از برداشت جدا کن و نام مستعار ستون را با نام مستعار جدول یا نام مستعار اختصاصی پرس‌وجو یکی نگیر.

## معنای نام مستعار

مسیر واقعی نام مستعار جدول و نام مستعار ستون در SELECT را در رابط برنامه‌نویسی، سازنده، AST و رندرکننده بررسی کن؛ از جمله الگوهای موجود در مخزن:

```kotlin
addColumn {
    column {
        tableColumn("uu", "id")
    }
    alias("user_id")
}

.table {
    table("user_users", "uu")
}
```

ارزیابی کن که آیا قرارداد زیر توسط معماری موجود پشتیبانی می‌شود:

```text
QBColumn.alias = نام مستعار پیش‌فرض در SELECT
نام مستعار صریح پرس‌وجو = اولویت دارد
```

`Adopt` فقط زمانی مجاز است که مسیر فعلی AST/سازنده/رندرکننده این تقدم را پشتیبانی کند یا شواهد روشنی برای حداقل تبدیل به AST لازم وجود داشته باشد. در غیر این صورت `Unresolved` یا `Defer` را با دلیل ثبت کن.

## ردیابی سازندهٔ پرس‌وجو

ماژول‌های متناظر با موارد زیر را بررسی کن:

```text
query/api
query/ast
query/builder
query/dialect
query/renderer
query/executor
```

جست‌وجو و طبقه‌بندی ارجاع‌های زیر را انجام بده:

```text
IModelBase

QBTable
QBColumn

```

وضعیت هر ارجاع را از میان `Active`, `Commented`, `Dead`, `Example-only`, `Unused` تعیین کن و با ذکر فایل و مصرف‌کننده پشتیبانی کن.

## رابط برنامه‌نویسی فعلی سازندهٔ پرس‌وجو

نمونهٔ دستی زیر را با پیاده‌سازی واقعی تطبیق بده:

```kotlin
QueryRenderSelectBuilder()
    .select {
        addColumn {
            column {
                tableColumn("uu", "id")
            }
            alias("user_id")
        }
    }
    .table {
        table("user_users", "uu")
    }
```

ردیابی کن که جدول، ستون، نام مستعار و شرط چگونه وارد AST می‌شوند؛ رندرکننده کدام گره‌ها و فیلدهای AST را می‌خواند و اجراکننده چه داده‌ای دریافت می‌کند. مرز محتمل ورود فرادادهٔ مدل را فقط از این زنجیره استخراج کن.

## DSL آیندهٔ شبیه SQL

وجود نحو یا انتزاع‌های مشابه در مخزن را بررسی کن. نحوهای زیر فقط مثال هدف احتمالی‌اند و قرارداد نهایی محسوب نمی‌شوند:

```kotlin
select(Users.id, Users.name).from(Users)
select(Users.id as userId, Users.name).from(Users)
where(Users.name like "Meh%")
```

مشخص کن معماری کنونی چه قابلیت‌هایی را دارد، کدام گره‌های AST موجود قابل استفاده‌اند و آیا مدل باید فراداده فراهم کند، نماد نوع‌دار بسازد یا از مسیر تبدیل یا یک واسط استفاده کند. انتزاع آینده را بدون شواهد یا نیاز اثبات‌شده نپذیر.

## مرز مدل → سازندهٔ پرس‌وجو

حداقل دو گزینه را با هم مقایسه کن:

```text
مدل → تبدیل فراداده/نماد → AST فعلی سازندهٔ پرس‌وجو → رندرکننده
مدل → واسط/مترجم → سازندهٔ پرس‌وجوی موجود → AST → رندرکننده
```

در صورت لزوم گزینه سوم را فقط با شواهد معرفی کن. مقایسه بر اساس درستی معناشناختی، ایمنی نوع، وابستگی متقابل، سادگی رابط برنامه‌نویسی، سازگاری AST و رندرکننده، DSL آیندهٔ شبیه SQL، گسترش‌پذیری، آزمون‌پذیری، استقلال از Migration و تعداد انتزاع‌ها باشد.

اصل معماری مورد بررسی:

```text
یکپارچه‌سازی مدل → سازندهٔ پرس‌وجو    قابل قبول
سازندهٔ پرس‌وجو → مدل                نباید وابستگی اجباری شود
```

سازندهٔ پرس‌وجو باید همچنان بدون مدل قابل استفاده بماند.

## مرز AST

گزینهٔ ساخت AST اختصاصی مدل مانند `ModelTableAst`, `ModelColumnAst`, `ModelAliasAst` را با تبدیل به AST به AST فعلی مقایسه کن. در صورت کافی بودن AST موجود، عین عبارت زیر را ثبت کن:

```text
No new Model-specific AST node required
```

اگر کافی نیست، معنای ازدست‌رفته، دلیل ناکافی بودن AST و حداقل نیاز را صرفاً به‌عنوان تصمیم طراحی گزارش کن؛ هیچ گره‌ای نساز.

## تحلیل لایهٔ نماد

نیاز احتمالی به `Table Symbol`, `Column Symbol`, `Select Expression`, `Aliased Expression` و `Predicate` را جداگانه با قالب زیر ارزیابی کن:

```text
Evidence
Need
Alternative
تصمیم
```

بررسی کن `Users`, `Users.id`, و `Users.name` به اطلاعات نوع نیاز دارند یا نه و آیا نماد باید مستقیماً به AST برسد یا تبدیل شود. صرف امکان توسعه در آینده، دلیل کافی برای ایجاد لایه نیست.

## ردیابی کلید اصلی

`QBColumn.primaryKey` را در سازندهٔ پرس‌وجو، Migration، مدل، نگاشت نتیجه، اعتبارسنجی، بازتاب و کدهای توضیحی ردیابی کن. مشخص کن در v1.2 کاربردی برای سازندهٔ پرس‌وجو دارد یا باید فراداده‌ای جدا از زبان پرس‌وجو بماند. کلید اصلی مرکب را فقط در صورت شواهد موجود گزارش کن.

## ردیابی بازتاب

برای همهٔ کاربردهای بازتاب مرتبط با مدل، به‌ویژه `findAnnotation<QBTable>()` و `findAnnotation<QBColumn>()`، محل و وضعیت فعال یا توضیح‌شده، مقدار استخراج‌شده، مقصد آن، وجود حافظهٔ نهان و قرارداد را ثبت کن. اگر خوانشگر فعالی وجود ندارد، خوانشگر تازه نساز و فقط گزینه‌های معماری را تحلیل کن.

## ایمنی نوع

بررسی کن نوع Kotlin ویژگی‌ها در مدل موجود چگونه می‌تواند در عبارت‌های پرس‌وجو حفظ شود؛ از جمله امکان تمایز `Column<Int>` از `Column<String>`. نگاشت نوع Kotlin به نوع پایگاه داده را خودکار فرض نکن. نوع‌های Kotlin فعلی و نوع پایگاه داده را جداگانه ثبت کن.

## تهی‌پذیری

`String?` و `Int` را از نظر معنای ویژگی در Kotlin بررسی کن. مشخص کن آیا تهی‌پذیری صرفاً در سطح Kotlin معلوم است، به فرادادهٔ پایگاه داده متصل شده، عبارت نوع را تحت تأثیر می‌گذارد یا unresolved است. بدون شواهد نگاشت تعریف نکن.

## مرز مدل → Migration

وجود یا نبود وابستگی فعلی میان فرادادهٔ مدل و Migration را بررسی کن. اگر شاهدی نیست، عیناً ثبت کن:

```text
Model → Migration dependency: None found
v1.2 Migration dependency: none
```

مدل v1.2 نباید یکپارچه‌سازی با سازندهٔ پرس‌وجو را به Migration وابسته کند.

## مرز ResultSet → مدل

بررسی کن آیا مدل برای نگاشت خروجی پرس‌وجو طراحی یا استفاده شده است. در نبود پیاده‌سازی، عیناً ثبت کن:

```text
ResultSet → Model mapping: Not implemented
```

نگاشت نتیجه وارد دامنهٔ نسخهٔ ۱.۲ نشود، مگر مخزن شواهد مشخصی آن را بخشی از قرارداد موجود ثابت کند.

## مرز تولید SQL

ردیابی کن فراداده احتمالی چگونه می‌تواند به جدول، ستون و نام مستعار موجود در SQL برسد؛ رندرکننده و dialect کدام داده‌ها را دریافت می‌کنند؛ و نقل‌قول‌گذاری شناسه و رندر نام مستعار کجا رخ می‌دهد. مدل نباید رشتهٔ SQL تولید کند؛ تولید SQL باید در مرز رندرکننده/dialect فعلی باقی بماند، مشروط به تأیید کد منبع.

## جهت وابستگی و مرز ماژول

وابستگی واقعی Gradle ماژول‌ها و importها را برای این ماژول‌ها بررسی کن:

```text
:data_base:core
:data_base:query
:data_base:models
:data_base:models:eloquent
```

گزینه‌های جهت وابستگی و محل احتمالی یکپارچه‌سازی در `data_base:models`, `data_base:models:eloquent`, `data_base:query` یا `data_base:query:api` را مقایسه کن. هیچ ماژول جدیدی صرفاً برای زیبایی پیشنهاد نده. وابستگی اجباری سازندهٔ پرس‌وجو به مدل را نپذیر.

## قرارداد نهایی

قرارداد نهایی گزارش باید، با تفکیک شواهد از تصمیم پیشنهادی، این موارد را روشن کند:

- قرارداد فعلی مدل، نشانگرها و annotationها؛
- معنای نام جدول، نام مستعار جدول، نام ستون، نام مستعار پیش‌فرض SELECT و کلید اصلی؛
- مرز و جهت وابستگی برای ورود فراداده به سازندهٔ پرس‌وجو؛
- انتخاب یا رد واسط/نماد layer و AST جدید؛
- مسئولیت مدل، سازندهٔ پرس‌وجو و رندرکننده در تولید SQL، نقل‌قول‌گذاری و رندر نام مستعار؛
- قابلیت‌های لازم و مرز معنایی برای DSL آینده؛
- مرز Kotlin نوع، DB نوع و تهی‌پذیری؛
- سازگاری رابط‌های برنامه‌نویسی و ماژول‌ها؛
- قابلیت‌های به‌تعویق‌افتاده.

هر تصمیم اصلی که شواهد کافی ندارد باید `Unresolved` بماند و شواهد لازم برای حل آن ذکر شود. قرارداد نهایی نباید به بهانهٔ کامل بودن، تصمیم معماری فاقد شواهد را قطعی کند.

## تأثیر بر سازگاری

اثر تصمیم‌های پیشنهادی بر کد منبع، رابط برنامه‌نویسی و گراف وابستگی و مصرف‌کنندگان فعلی را جداگانه گزارش کن. چون در این مرحله تغییری اعمال نمی‌شود، مسیر مهاجرت صرفاً طرح آینده خواهد بود.

## برنامهٔ آزمون

برای گزینه‌هایی که در گزارش تصمیم `Adopt` می‌گیرند، برنامهٔ آزمون تدوین کن؛ آزمون اجرا یا ویرایش نکن. دست‌کم این موارد را پوشش بده:

- کشف فرادادهٔ مدل و `QBTable`/`QBColumn`؛
- نام مستعار جدول و نام مستعار پیش‌فرض SELECT؛
- اولویت نام مستعار صریح پرس‌وجو؛
- تبدیل به AST از مدل به سازندهٔ پرس‌وجو و AST؛
- رندر SQL، گریزدهی شناسه‌ها و شناسه‌های رزروشده؛
- فراداده خالی و نامعتبر؛
- معنای نوع و تهی‌پذیری، فقط اگر قرارداد آن‌ها Adopt شده باشد؛
- آزمون بازگشت استفاده از سازندهٔ پرس‌وجو بدون مدل؛
- آزمون بازگشت کلاس‌های فعلی `Users` و `UserPhones`.

برای موارد حل‌نشده یا به‌تعویق‌افتاده تست را به‌عنوان شرط اجرای آینده برچسب بزن، نه تعهد پیاده‌سازی فعلی.

## موارد به‌تعویق‌افتاده و خارج از دامنه

همهٔ قابلیت‌های بخش «موارد خارج از هدف» و هر انتزاع بدون شواهد یا تصمیم قطعی را فهرست کن. نگاشت ResultSet و یکپارچه‌سازی با Migration مستقل باقی بمانند مگر شواهد مخزن خلاف آن را ثابت کند.

## آمادگی برای پیاده‌سازی

در انتها فقط یکی از وضعیت‌های زیر را انتخاب کن:

```text
Status: Implementation Ready
```

یا:

```text
Status: Ready for Traceability
```

`آمادهٔ پیاده‌سازی` فقط وقتی مجاز است که تصمیم‌های معماری اصلی برای مدل→سازندهٔ پرس‌وجو مرز، تقدم نام مستعار، AST/نماد/واسط، جهت وابستگی و دامنهٔ نوع و تهی‌پذیری با شواهد کافی بسته شده باشند. در غیر این صورت `Ready for Traceability` و فهرست دقیق تصمیم‌های حل‌نشده را ثبت کن.
