# Plan 1.4: Model-backed Column References و تکمیل استفاده از Model در Query DSL

## Status

**Ready for Traceability**

این سند Plan بررسی و تصمیم‌گیری است، نه مجوز implementation. پیش از implementation باید Traceability روی source جاری اجرا شود و موارد unresolved این سند با evidence بسته شوند. Model v1.3 baseline است و در این مرحله نباید بازطراحی یا تغییر کند.

## Objective

تمام نقاط Query DSL را که String در آن‌ها واقعاً هویت جدول یا ستون را نمایش می‌دهد پیدا و بررسی کن. برای هر نقطه مشخص کن Model-backed reference مناسب است یا باید String، value/parameter، CTE reference یا raw expression باقی بماند.

خروجی اجرای این Plan باید Traceability و قرارداد قابل پیاده‌سازی باشد؛ در اجرای آن source، test، Gradle، documentation، Model v1.3، API یا AST تغییر نمی‌کند.

## Model v1.3 Baseline

قرارداد موجود v1.3:

```kotlin
table(UserModelV2::class)
column(UserModelV2::class, UserModelV2::id)
```

در source جاری:

- `IQueryTableApi` متد typed `table(KClass<T>, alias: String? = null)` را دارد.
- `IQueryColumnsApi` متد typed `column(KClass<T>, KProperty1<T, R>)` را دارد.
- Builderهای typed با `QBTable` و `QBColumn` مقدار table name، column name و default alias را resolve می‌کنند.
- `ModelTableAliasContext` فعلی میان typed SELECT column و typed root table alias هماهنگی برقرار می‌کند.
- `data_base/query/builder` در production به `core`, `query:ast`, `query:api` وابسته است و dependency concrete به `models:eloquent` ندارد.
- تست `TypedModelReferenceTest` و گزارش v1.3 Implementation Verification baseline رفتار موجودند؛ آن‌ها را بازنویسی یا refactor نکن.

Plan 1.4 قابلیت v1.3 را فرض می‌گیرد و فقط نقاط اتصال جدید را تحلیل می‌کند. هر نوع Kotlin property در این مرحله صرفاً reference type است؛ از آن SQL type، nullability در SQL یا operator compatibility استنتاج نکن.

## Repository Evidence

Traceability باید evidence جاری را دوباره از فایل‌ها بخواند، نه اینکه یافته‌های گزارش v1.3 را بدون verify کپی کند. حداقل این موارد را بررسی کن:

- Models مثال در `data_base/query/example/src/main/kotlin/v2/queries/models/` و نمونه‌های `v2/queries/select`, `insert`, `update`, `delete`.
- metadata در `data_base/core/.../AnnotationModelTable.kt`, `AnnotationModelColumn.kt` و marker `IModelBase`.
- typed پیاده‌سازی v1.3 در `QueryTableBuilder`, `QueryColumnsBuilder`, `ModelTableAliasContext`, و `QueryRenderSelectBuilder`.
- API و Builderهای `IQueryColumnsBaseApi`, `QueryColumnsBaseBuilder`, `IQueryConditionsApi`, `QueryConditionsBuilder`, `IQueryJoinsItemApi`, `QueryJoinsItemBuilder`.
- API، Builder و ASTهای Insert، Update، Delete، CTE و Query Select.
- rendererهای select column/condition/join، insert/update/delete و table/CTE.
- Gradle `implementation`, `api`, `testImplementation`, importها، و runtime dependency graph هر ماژولی که تصمیم‌ها به آن وابسته‌اند.
- همه‌ی overloadها و call siteهای `tableColumn`, `column`, `table`, `cteColumn`, `tableAttribute`, `addValue`, `sideSelector`, `sideValue`, `addTarget`.
- تست‌های فعلی Query Builder و مثال‌های v1/v2؛ active code را از comment، example-only، dead و unused code جدا کن.

برای هر تصمیم مهم این زنجیره را ثبت کن:

```text
Repository Evidence
        ↓
Interpretation
        ↓
Decision
```

تفسیری که فقط از owner clarification می‌آید باید صریحاً با `Owner-provided contract clarification` برچسب بخورد.

## Existing Model-backed APIs

موارد زیر در v1.3 **Already Supported** محسوب می‌شوند و باید فقط به‌عنوان baseline verify شوند:

| محل | API جاری | بررسی در v1.4 |
|---|---|---|
| Root table | `table(KClass, alias?)` | default/explicit/clear alias و compatibility را دوباره از source تأیید کن. |
| SELECT projection | `column(KClass, KProperty1)` | QBColumn name/default SELECT alias و root-table qualifier را بررسی کن. |

JOIN table باید جداگانه trace شود: API عمومی join از `IQueryTableApi` استفاده می‌کند، اما اتصال alias آن به typed columns ممکن است با root query context متفاوت باشد.

## Column Reference Traceability

برای هر مسیر دنبال این زنجیره باش:

```text
Existing DSL
    ↓
Public API
    ↓
Builder
    ↓
AST
    ↓
Renderer
    ↓
Executor
    ↓
Tests / Examples
    ↓
Model v1.3 capability
    ↓
Decision
```

اگر لایه‌ای موجود نیست، نبودش را ثبت کن. مشخص کن Model reference در کدام Builder resolve می‌شود و آیا AST فعلی می‌تواند با همان فیلدهای string/alias ادامه دهد. Renderer یا Executor را به Model-aware reflection و annotation lookup وابسته نکن، مگر evidence آن را ضروری ثابت کند.

**اصل تصمیم‌گیری:** وجود call siteای مثل `tableColumn("uu", "id")` به‌تنهایی اثبات نمی‌کند که overload جدیدی مانند `tableColumn(Model::class, Model::id, "uu")` لازم است. پیش از پیشنهاد API جدید، بررسی کن آیا `IQueryColumnsBaseApi` و AST فعلی همان semantics را با resolution/lowering موجود پوشش می‌دهند. اگر می‌دهند، ترجیح با استفاده از مسیر موجود است؛ overload یا abstraction تازه فقط با evidence از کمبود واقعی توجیه می‌شود. این اصل برای selector، operand ستونی در JOIN/WHERE و سایر مسیرهای مشترک Builder اعمال شود.

این اصل به معنی فرض‌کردن کفایت API فعلی نیست: مسیر public API → Builder → AST → Renderer را برای هر محل جدا trace کن و evidence کفایت یا نابسندگی را ثبت کن.

## SELECT Traceability

SELECT projection typed در v1.3 موجود است. باقی candidateها:

- projectionهای `tableColumn(alias, name)` که به‌جای typed overload باقی مانده‌اند.
- `tableAttribute(String)` که ممکن است raw expression باشد و نباید صرفاً با دیدن `uu.name` Model column تلقی شود.
- alias صریح projection نسبت به `QBColumn.alias`.

مشخص کن چه projectionهایی هنوز schema identity خام دارند و آیا typed SELECT overload موجود آن‌ها را پوشش می‌دهد. Expression را به این دسته وارد نکن.

## JOIN Traceability

در `IQueryJoinsItemApi`، جدول join با block مبتنی بر `IQueryTableApi` ساخته می‌شود و ON condition با `IQueryConditionsGroupsApi`/`IQueryConditionsApi` ساخته می‌شود. نمونه‌ی v2 از دو `tableColumn(alias, name)` در دو طرف ON استفاده می‌کند.

هر دو طرف شرط ON را جدا تحلیل کن:

- selector سمت چپ ممکن است ستون Model اول باشد.
- operand سمت راست ممکن است ستون Model دوم باشد، نه مقدار پارامتر.
- alias مؤثر هر table باید مشخص و از Model identity جدا باشد.
- نتیجه‌ی typed ON باید با AST فعلی `conditionSideLeft` و `conditionSideRight: Any?` سازگار باشد.

کاندیدای API صرفاً برای بررسی می‌تواند در خانواده‌ی زیر باشد؛ تا بررسی threading و alias، signature را قطعی نکن:

```kotlin
tableColumn(Model::class, Model::property, effectiveTableAlias)
```

بررسی کن آیا `QueryJoinsItemBuilder` و child builderها context مشترک دریافت می‌کنند یا نه، و آیا joinهای متعدد یا self-join با mapping صرفاً `KClass → alias` ابهام ایجاد می‌کنند.

## WHERE Traceability

`IQueryConditionsApi.sideSelector` یک block از `IQueryColumnsBaseApi` می‌گیرد و `sideValue` دو شکل جدا دارد: block ستونی و `(paramName, paramValue)`. Builder فعلی block ستونی را به `IQueryColumnsBaseAst` می‌سازد؛ overload value مقدار را به `SqlParameter` تبدیل می‌کند.

تصمیم مورد انتظار را با evidence تعیین کن:

- selector ستون می‌تواند candidate Model-backed باشد.
- `sideValue(paramName, value)` و `sideValueCollection` مقدار/پارامتر می‌مانند؛ Model جایگزین مقدار runtime نیست.
- `sideValue { tableColumn(...) }` یک column operand است و جدا از parameter overload بررسی می‌شود.
- برای `IN`, `LIKE`, `IS NULL`, equality و سایر operatorها بررسی کن آیا یک column reference lowering مشترک کفایت می‌کند یا قرارداد خاصی لازم است.
- نمونه‌ی عمداً invalid یعنی `IS 1` را حذف یا اصلاح نکن. اگر validation مربوطه موجود است فقط trace کن؛ اگر contract تازه می‌خواهد، جدا و با وضعیت unresolved ثبت کن.

اصل:

```text
Model Column != Query Parameter
```

## UPDATE Traceability

دو موضوع مستقل‌اند:

1. SET target جاری: `IQueryColumnUpdateApi.column(columnName, value)` و overload دارای `columnAlias`.
2. WHERE selector جاری: `sideSelector { tableColumn(alias, name) }`.

بررسی کن typed target چگونه `QBColumn.name` را به `IQueryColumnUpdateAst.columnName` می‌رساند و `columnTag`/parameter tag جاری را حفظ می‌کند. مقدار SET همچنان runtime value/parameter می‌ماند. alias جدول، alias پارامتر و column identity را یکی نکن.

Candidateهایی مانند `column(Model::class, Model::property, value)` یا `column(Model::property, value)` را فقط پس از بررسی generic bound، metadata resolution، AST و overload collision ارزیابی کن.

## INSERT Traceability

INSERT table در v1.3 از typed `IQueryTableApi.table(KClass, alias?)` استفاده می‌کند، اما target column از `IQueryColumnInsertApi.column(columnName, value)` می‌آید.

بررسی کن:

- `QBColumn.name` می‌تواند مقدار `IQueryColumnInsertAst.columnName` را تعیین کند یا خیر.
- `columnTag` و `SqlParameter` نام و مقدار را چگونه به هم وصل می‌کنند.
- آیا property `R` می‌تواند به‌صورت Kotlin-side فقط نوع reference را constrain کند، بدون اینکه SQL typing ادعا شود.
- API فعلی String بدون تغییر می‌تواند باقی بماند یا خیر.

Candidateهای `column(Model::class, property, value)` و `column(property, value)` را مقایسه کن؛ هیچ‌کدام را صرفاً به‌خاطر کوتاه‌تر بودن Adopt نکن. مدل فقط هویت schema/column را تعیین می‌کند و value همچنان parameter است.

## DELETE Traceability

DELETE table typed از v1.3 در دسترس است. Selector شرط WHERE ممکن است Model-backed شود؛ `addTarget(String)` در API جاری target/alias رشته‌ای می‌گیرد.

مشخص کن:

- Model در table target وارد می‌شود یا در column selector هم لازم است.
- آیا `addTarget("uu")` alias است و جدا از column identity می‌ماند.
- renderer و AST برای delete table/target/where چه فیلدهایی دارند.
- آیا alias مدل/explicit table alias باید در target یا شرط propagation جداگانه اعمال شود.

`addTarget` را به Model property تبدیل نکن مگر evidence معنای schema column برای آن ثابت کند.

## CTE Traceability

`cteColumn(cteAlias, selectName)` و `cte(name, alias)` نماینده‌ی CTE source و CTE output column هستند. آن‌ها به‌طور پیش‌فرض معادل physical table/property نیستند.

بررسی کن:

- CTE AST، source name، alias و output column identity چگونه نگهداری می‌شوند.
- مدل‌های `ICte`/annotationهای احتمالی فعال‌اند یا فقط comment/unused.
- آیا CTE دارای schema/metadata مستقل و قابل اتکا است.
- آیا Query CTE outputها را از SELECT AST/aliasها می‌سازد یا metadata دیگری دارد.

تا وقتی evidence نشان نداده Model metadata برای همان CTE output معتبر است، قرارداد را جدا نگه دار و CTE را **Defer** کن. `UserModel::id` به‌تنهایی اثبات نمی‌کند CTE خروجی هم‌نام/هم‌نوع دارد.

## Expression / Table Attribute Traceability

`tableAttribute(String)` را جدا از identifier یک ستون بررسی کن. تعیین کن آیا AST مستقل Expression در repository وجود دارد، آیا renderer متن خام را مستقیماً مصرف می‌کند و مثال فعلی example-only است یا API فعال.

صرف دیده‌شدن `uu.name` یا `uu.family` در متن expression دلیل Model-backed شدن expression نیست. اگر Expression AST/contract موجود evidence ندارد، تصمیم **Defer** است؛ در این Plan Expression system جدید یا generic expression/operand layer پیشنهاد یا ایجاد نکن.

## Alias Analysis

معانی زیر جدا بمانند:

```text
Model identity
Table identity (`QBTable.name`)
Column identity (`QBColumn.name`)
Effective table alias
CTE identity and alias
Runtime parameter identity
```

Model metadata می‌تواند default table alias (`QBTable.alias`) و default SELECT alias (`QBColumn.alias`) داشته باشد؛ aliasهای query scope به‌طور خودکار از property reference استنتاج نمی‌شوند. Alias را به metadata Model جدید منتقل نکن مگر repository evidence صریح وجود داشته باشد.

Traceability باید این حالات را از هم جدا کند:

- alias پیش‌فرض مدل، alias صریح query، و clear alias.
- SELECT projection و qualifier column.
- root table، join table و table alias صریح.
- یک Model class که در یک query بیش از یک بار آمده (self-join).
- CTE alias، که با table alias یکی نیست.

v1.3 `ModelTableAliasContext` را برای SELECT و root table دارد؛ این evidence به‌تنهایی ثابت نمی‌کند همان strategy برای WHERE، JOIN، UPDATE و DELETE کافی است. mapping تنها بر اساس `KClass` ممکن است در self-join چند alias مؤثر داشته باشد؛ این حالت را صریحاً تحلیل کن. در صورت unresolved بودن، آن را پیش از implementation با evidence موردنیاز ثبت کن.

## Type Safety Analysis

بررسی کن property reference در v1.3 table class و property generic type را حفظ می‌کند و metadata reflection چه چیزهایی قابل استخراج می‌دهد:

```text
table name, table default alias, column name, column default SELECT alias,
Kotlin property type, Kotlin nullability
```

فقط table/column identity و alias metadata را وارد قرارداد کن مگر scope صریحاً type feature دیگری را مجاز کند. Kotlin type/nullability را به DB type، SQL nullability، operator compatibility، coercion یا ResultSet mapping تعمیم نده. Cross-table references هویت هر طرف را حفظ کنند؛ از سازگاری SQL نوع دو طرف نتیجه نگیر.

## Model vs Query Parameter Boundary

این boundary باید در قرارداد نهایی و مثال‌ها صریح باشد:

```text
Model property → schema / column identity
sideValue(name, value), sideValueCollection(...), addParam(value)
                 → runtime value / query parameter
```

این یک **invariant** است، نه صرفاً پیشنهاد طراحی: `Model Property` هویت schema/column را می‌دهد و `sideValue(...)`, `sideValueCollection(...)`, `addParam(...)` و مقدار INSERT/UPDATE داده‌ی زمان اجرا را. هیچ نتیجه‌ای در Traceability نباید این دو نقش را با هم ادغام کند.

Model property هیچ‌گاه جای `sideValue`, `addParam` یا value مربوط به INSERT/UPDATE را نگیرد. `sideValue { column reference }` operand ستونی است، نه parameter؛ APIها و AST branchهای فعلی را trace کن تا این تفاوت روشن بماند.

## Candidate Feature Matrix

برای هر سطر تصمیم دقیقاً یکی از `Adopt`, `Defer`, `Reject`, `Already Supported`, `Unresolved` باشد. هر سطر Evidence، Interpretation، Decision و Reason داشته باشد.

`Already Supported` فقط زمانی مجاز است که همان semantics و public contract در source جاری v1.3 با evidence قابل بررسی در سطح compile-time و use-site اثبات شود. صرف معرفی قابلیت به‌عنوان baseline در این Plan، وجود implementation، یا دیدن مثال مشابه کافی نیست؛ مسیر `API → Builder → AST → Renderer` را برای همان رفتار trace کن و شواهدش را ثبت کن.

برای SELECT و TABLE تصمیم اولیه‌ی این Plan فقط **candidate: Already Supported — verify** است، نه تصمیم نهایی. اجرای Traceability باید آن را بر اساس source جاری تأیید کند یا به `Unresolved`/تصمیم مناسب دیگری تغییر دهد.

| TABLE | `table(...)` | table identity | ... | Already Supported — verify v1.3 semantics and public contract | ... | ... |

| WHERE column operand | `sideValue { ... }` | right-side column | ... | Unresolved pending trace | ... | ... |

## API Contract

Traceability خروجی باید برای هر feature Adopt شده method owner/interface، argumentها، generic bound، نحوه‌ی اعلام alias و رفتار property نامعتبر را تعیین کند. محل امضای API را به‌طور دقیق مشخص کن: `IQueryColumnsBaseApi` برای column operandهای عمومی، `IQueryColumnUpdateApi` برای SET و `IQueryColumnInsertApi` برای INSERT، یا جایگزین دارای evidence.

امضای خامی را که source موجود پشتیبانی نمی‌کند به‌عنوان قرارداد قطعی وانمود نکن. اگر انتخاب بین KClass+KProperty، KProperty تنها، یا wrapper قابل حل نیست، API را `Unresolved` بگذار و بنویس برای بستن آن کدام compile-time/use-site evidence یا owner contract لازم است. APIهای String جاری حذف یا تغییر نمی‌کنند.

## AST Contract

برای هر Adopt شده نشان بده property به کدام field موجود تبدیل می‌شود، برای نمونه:

```text
QBColumn.name → existing column string field
effective query alias → existing tableAlias/columnAlias field
runtime value → existing parameter/tag fields
```

AST فعلی `IQueryColumnsBaseAst`، condition sideهای آن، `IQueryColumnUpdateAst`، `IQueryColumnInsertAst` و Delete/Join AST را ارزیابی کن. Model-specific AST، generic operand AST یا expression AST فقط وقتی قابل قبول است که use case و کمبود فیلدهای فعلی با evidence اثبات شود؛ در غیر این صورت Defer/Reject.

## Builder Contract

مشخص کن هر metadata lookup در کدام Builder انجام می‌شود و چگونه به AST موجود lowering می‌شود. Alias context باید در root SELECT و JOIN/WHERE child builderها، و نیز update/delete context بررسی شود. قرارداد باید ترتیب ساخت بخش‌های query را پوشش دهد و برای Model تکراری در چند alias تعیین تکلیف کند.

Renderer و Executor نباید reflection یا annotation lookup انجام دهند مگر evidence معماری خلاف آن را ثابت کند. هیچ implementation در اجرای Plan انجام نمی‌شود.

## Renderer Contract

هر renderer فقط از AST و render context جاری چه می‌خواند؟ بررسی کن آیا column qualifier/نام، CTE qualifier، UPDATE target و INSERT target در AST فعلی قابل نمایش‌اند. اگر lowering به stringها کفایت کند، renderer بدون تغییر/Model-unaware می‌ماند. اگر موردی نیازمند renderer change است، آن را موردبه‌مورد و با فیلد/نیاز دقیق مستند کن؛ تغییر نده.

## Backward Compatibility

- APIهای String/block از جمله `tableColumn`, `table`, `column`, `cteColumn`, `tableAttribute`, update/insert `column`, و `addTarget` را حذف یا تغییر نده.
- API typed جدید کنار API قبلی قرار می‌گیرد مگر شواهد compatibility خلاف آن را ثابت کند.
- overload ambiguity، JVM erasure، source/binary compatibility و generic boundها را بررسی کن.
- `Users`, `UserPhones`, مدل‌های نمونه‌ی v2، annotationها و v1.3 APIها در این مرحله تغییر نمی‌کنند.
- v1 exampleها را صرفاً برای زیبایی بازنویسی نکن. تغییر example در implementation آینده، demonstration contract مجزا است.

## Test / Example Impact

فقط test plan آینده را بنویس؛ test اضافه یا اجرا نکن. برای Adopt شده‌ها برنامه حداقل این موارد را دربرگیرد:

- resolve کردن table/column metadata و عدم fallback به Kotlin property name.
- root/join/default/explicit alias، ترتیب ساخت بخش‌ها و duplicate Model/self-join.
- WHERE selector، column-to-column ON operands، parameter/value و collection separation.
- LIKE و IS NULL؛ invalid `IS 1` مثال را نگه دار و validation behavior را فقط طبق contract مستقل تست کن.
- UPDATE target/WHERE و INSERT target/value tags.
- DELETE table/WHERE/target alias.
- CTE و expression همان تصمیم Defer/Reject را حفظ کنند؛ مگر traceability تصمیم متفاوتی با evidence بگیرد.
- AST lowering و renderer SQL؛ String API regression.
- Query Builder بدون dependency اجباری به concrete model module.

برای feature Deferred/Unresolved تست را به شرط بسته‌شدن تصمیم موکول کن؛ آن را تعهد implementation تلقی نکن.

## Adopted Features

فقط فهرست candidateهایی که evidence برای semantics، API ownership، alias، AST lowering، dependency و compatibility کافی فراهم کرده است. برای هر مورد یک خط Evidence → Interpretation → Decision بنویس. خالی ماندن این بخش مجاز است.

## Deferred Features

حداقل CTE-backed Model metadata و `tableAttribute`/expression را تا وجود evidence مستقل Defer کن. همچنین Kotlin-to-SQL type mapping، SQL nullability، operator type checking و ResultSet mapping خارج از این Plan هستند.

## Rejected Features

هر موردی را Reject کن که صرفاً برای کوتاه‌سازی یا آینده‌نگری abstraction می‌سازد، Model property را به parameter value تبدیل می‌کند، یا identityهای Model/table/column/alias/CTE را مخلوط می‌کند. هر Reject نیازمند evidence و دلیل است؛ در غیر این صورت Unresolved بماند.

## Unresolved Decisions

برای هر مورد unresolved این قالب را کامل کن:

```text
Decision:
Current repository evidence:
Why unresolved:
Evidence or owner contract required:
Affected API / module / compatibility:
```

به‌طور خاص بررسی کن آیا شواهد برای بستن موارد زیر کافی‌اند:

1. **مالکیت API برای typed column operand:** signature و محل API عمومی؛ با اثبات اینکه API فعلی کفایت دارد یا overload جدید لازم است.
2. **Propagation واقعی alias در child builderها:** WHERE/JOIN و UPDATE/DELETE، شامل ترتیب ساخت و alias صریح.
3. **Self-join:** تمایز دو reference از یک Model با aliasهای متفاوت.
4. **Signature دقیق UPDATE:** فقط در صورت اثبات نیاز typed target، همراه سازگاری parameter tag.
5. **Signature دقیق INSERT:** فقط در صورت اثبات نیاز typed target، همراه سازگاری parameter/tag.
6. **Cross-table column operands:** هر دو سمت condition و ON و lowering آن‌ها به AST موجود.
7. **مرز CTE و expression:** اعتبار یا عدم اعتبار Model metadata برای CTE output و expression/tableAttribute.
8. **Dependency direction:** مالکیت integration و جهت وابستگی بر اساس Gradle/import evidence، بدون فرض dependency اجباری Query Builder به ماژول concrete Model.

`IS`/null و مثال عمداً نامعتبر `IS 1` را در WHERE Traceability بررسی کن؛ این‌ها محور معماری جداگانه‌ای به فهرست هشت‌گانه اضافه نمی‌کنند، مگر source نشان دهد تصمیم مستقل و مسدودکننده‌ای لازم است.

Unresolved را با حدس پر نکن.

## Implementation Boundary

اجرای Plan 1.4 فقط traceability/reporting است. ممنوع:

- تغییر source/test/Gradle/documentation/model/API یا v1.3.
- ساخت Adapter، Symbol Layer، generic Model/Column/Expression/Operand abstraction یا AST node.
- implementation، refactor، build/runtime experiment، DB introspection یا migration.
- حذف یا اصلاح مثال invalid موجود.
- نتیجه‌گیری درباره SQL type، SQL nullability، operator compatibility یا mapping از Kotlin property type.

خروجی اجرای Plan باید فقط report مورد توافق مرحله‌ی traceability باشد؛ این Plan هنگام نوشته‌شدن، source را تغییر نمی‌دهد.

## Implementation Readiness

**Ready for Traceability** — هدف مرحله‌ی بعد جمع‌آوری evidence و بستن تصمیم‌های این Plan است، نه implementation. وضعیت را پس از اجرای Traceability فقط در صورت evidence کامل برای API shape، alias semantics/context، AST lowering، integration ownership/dependency direction، type/nullability scope و backward compatibility به `Implementation Ready` ارتقا بده.
