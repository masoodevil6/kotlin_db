# Model v1.3: Typed Model References in Query Builder

## وضعیت

`Ready for Traceability`

## هدف

این برنامه بررسی می‌کند آیا و چگونه می‌توان ارجاع type-safe به Model و propertyهای آن را به Query Builder موجود اضافه کرد؛ به‌گونه‌ای که candidateهایی مانند `table(Users)` و `addColumn(Users.age)` در صورت پشتیبانی معماری فعلی قابل ارزیابی باشند و در نهایت به AST و Renderer موجود برسند.

دامنه فقط **Traceability و Contract Analysis** است. در این مرحله تصمیم نهایی API یا implementation از پیش تعیین نشده است. به‌خصوص، هدف ساخت SQL-like DSL کامل یا تبدیل Model به ORM نیست.

## دامنه

### Modelها و metadata

source فعلی این موارد را بازبینی کن:

```text
IModelBase
IModel
BaseModel
Users
UserPhones
QBTable
QBColumn
```

برای `Users` و `UserPhones` این موارد را ثبت کن:

- class/object/companion ساختار فعلی و constructor؛
- propertyها، Kotlin type، nullability و mutability؛
- `QBTable.name` و `QBTable.alias`؛
- برای هر `QBColumn`: نام Kotlin property، `QBColumn.name`, `alias`, `primaryKey`؛
- اینکه metadata یا API فعلی property را به‌صورت static/class-level reference عرضه می‌کند یا نه.

### Query Builder و AST

تمام API، implementation و ASTهای مرتبط با این مفاهیم را از source ردیابی کن:

```text
table
tableColumn
column
addColumn
alias
```

دامنهٔ جست‌وجو شامل SELECT، table/join، CTE و هر کاربرد مرتبط در INSERT/UPDATE/DELETE است؛ فقط جاهایی را تحلیل کن که از نظر ورودی Model Reference یا مقصد lowering ارتباط مستقیم دارند. برای هر مسیر مشخص کن:

- API عمومی و overloadهای موجود؛
- Builder فعال در برابر کد کامنت‌شده؛
- AST node و field دقیق مقصد؛
- Rendererای که field را مصرف می‌کند؛
- آیا qualifier/table association در AST باقی می‌ماند؛
- آیا property/type/provenance در AST حفظ می‌شود یا فقط identifierهای رشته‌ای باقی می‌مانند.

## 1. Table Reference

قابلیت candidate زیر را بررسی کن:

```kotlin
table(Users)
```

مشخص کن:

- `Users` در API موجود class، object، companion یا نوع دیگری است؛
- چه referenceی از مدل باید به Builder برسد و چه امضایی می‌تواند آن را بپذیرد؛
- چگونه و در کدام لایه `QBTable.name` به table identifier فعلی تبدیل می‌شود؛
- `QBTable.alias` آیا default table alias محسوب می‌شود؛
- alias صریح table API چگونه بر default تقدم می‌گیرد؛
- metadata غایب، خالی یا نامعتبر چه وضعیت قراردادی دارد؛
- آیا resolution قبل از ورود به AST موجود ممکن است.

`table(Users)` را syntax قطعی فرض نکن؛ اگر شکل فعلی Kotlin آن را ممکن نمی‌کند، شکل‌های نزدیک را فقط به‌عنوان candidate تحلیل کن و limitation را ثبت کن.

## 2. Column Reference

قابلیت candidate زیر را بررسی کن:

```kotlin
addColumn(Users.age)
```

مقایسه کن با API رشته‌ای فعلی:

```kotlin
addColumn {
    column {
        tableColumn("uu", "age")
    }
    alias("user_age")
}
```

برای column reference مشخص کن:

- `Users.age` چه شیء/نوعی می‌تواند باشد و آیا syntax از class/object فعلی قابل دسترس است؛
- `QBColumn.name` چگونه و کجا resolve می‌شود؛
- ارتباط ستون با Model/table/alias چگونه حفظ یا حل می‌شود؛
- آیا type generic صرفاً نوع Kotlin property را حمل می‌کند یا semantics دیگری دارد؛
- آیا Kotlin type در این مرحله صرفاً compile-time reference است؛
- آیا reference را می‌توان به مسیر primitive و موجود `tableColumn(tableAlias, columnName)` lowering کرد؛
- اضافه‌کردن alias block یا پارامتر چگونه با API فعلی `addColumn` سازگار می‌شود؛
- خطاهای metadata/property ناشناخته کجا و با چه قراردادی رخ می‌دهند.

هیچ Kotlin→SQL type mapping، operator system یا typed predicate contract تعریف نکن.

## 3. گزینه‌های شکل Kotlin API

حداقل این گزینه‌ها را بررسی و با evidence مقایسه کن؛ گزینه‌ای را از پیش انتخاب نکن:

```kotlin
class Users : BaseModel() { /* instance properties */ }
```

در برابر:

```kotlin
class Users : BaseModel() {
    companion object { /* candidate references */ }
}
```

و:

```kotlin
object Users { /* candidate model/reference */ }
```

و:

```kotlin
separate typed Model/Column Reference
```

در صورت ارتباط، `KClass`, `KProperty1`, property referenceهای Kotlin، instance property، companion و wrapper/reflection-based candidateها را نیز مقایسه کن.

برای هر گزینه بررسی کن:

- آیا دقیقاً syntax `Users.age` یا `table(Users)` را می‌دهد؛
- چطور `QBTable`/`QBColumn` به آن وصل می‌شوند؛
- نوع Kotlin property کجا و چگونه باقی می‌ماند؛
- annotation target/retention و reflection behavior چه اثری دارد؛
- boilerplate و abstraction جدید چقدر است؛
- تست‌پذیری و compiler/type inference؛
- سازگاری با class/constructor/propertyهای فعلی `Users` و `UserPhones`؛
- source/binary compatibility برای Modelها و Query API؛
- نیاز به dependency مستقیم بین moduleها.

فقط به دلیل شباهت syntax به SQL یا future extensibility گزینه‌ای را Adopt نکن.

## 4. Alias Precedence

قراردادهای زیر را به‌عنوان owner-provided clarification ثبت و با source فعلی مقایسه کن:

```text
QBTable.name       = table name
QBTable.alias      = default SQL table alias
QBColumn.name      = database column name
QBColumn.alias     = default SELECT alias
```

برای SELECT alias، contract مورد بررسی:

```text
Explicit Query Alias
        ↓
Model Default Alias
        ↓
No Alias
```

نمونهٔ candidate:

```kotlin
addColumn(Users.age) {
    alias("age")
}
```

با evidence نشان بده:

- explicit alias API فعلی کدام field AST را تنظیم می‌کند؛
- Model default alias در کدام layer می‌تواند resolve شود؛
- alias winner پیش از AST تعیین می‌شود یا نیاز به AST representation دیگری دارد؛
- مقدار absent/empty صریح چه تفاوتی با alias حذف‌شده دارد؛
- table alias نیز نیازمند precedence مشابه است یا نه.

تصریح کن آیا precedence فعلی executable evidence دارد یا صرفاً candidate contract است. Renderer را Model-aware فرض نکن.

## 5. AST Boundary

اصل بررسی:

```text
برای Model Reference، AST جدید نساز مگر evidence آن را ضروری کند.
```

بررسی کن آیا resolution قبل از AST می‌تواند به ورودی‌های فعلی Builder تبدیل شود:

```text
Users.age
   ↓
Model Reference Resolution
   ↓
existing tableColumn(tableAlias, columnName)
   ↓
existing Query AST
   ↓
existing Renderer
```

با source دقیقاً مشخص کن آیا AST فعلی برای table/column/final alias کافی است. `Model-specific AST`, provenance یا type node را صرفاً برای توسعه‌پذیری پیشنهاد نکن. اگر نگهداری اطلاعات خاصی ضروری است، ضرورت را با use case و fieldهای موجود اثبات کن؛ در غیر این صورت `Defer`.

## 6. Dependency Direction و Integration Ownership

dependency graph فعلی را دوباره از `settings.gradle.kts` و `build.gradle.kts`ها استخراج کن؛ یافته‌های report قبلی را فرض نکن.

مقایسه کن:

```text
Query Builder → Model
Model → Query Builder
Model → optional Query Integration / Adapter → Query Builder
Model Reference → Translation Layer → Existing Query Builder/AST
```

برای هر مورد بررسی کن:

- dependency مستقیم/transitive و جهت واقعی import؛
- آیا Builder بدون module Model همچنان قابل استفاده می‌ماند؛
- آیا Model مستقل از Query Builder می‌ماند؛
- ownership API و lifecycle تغییرها؛
- سازگاری با edge فعلی `query:builder → models:eloquent` و علت compile آن در گزارش قبلی؛
- اثر بر مصرف‌کنندگان داخلی و محدودیت شواهد consumerهای بیرونی؛
- آیا adapter جدا یا module جدید واقعاً لازم است.

هدف‌گذاری «Model → Query Builder» را به‌عنوان اصل پیشنهادی مالک ثبت کن، نه fact مخزن. dependency Query Builder به Model را intentional اعلام نکن مگر candidate انتخاب‌شده و evidence آن را توجیه کند.

## 7. Lowering، Renderer و Executor

مسیر پیشنهادی را تا source واقعی trace کن:

```text
Typed Model/Column Reference
    ↓
Resolution
    ↓
Existing Builder API
    ↓
Existing AST
    ↓
Renderer
```

ثبت کن:

- در کدام layer table/column string و alias نهایی تولید می‌شوند؛
- Renderer چه AST fieldsی می‌خواند و آیا Model را لازم دارد؛
- Executor از چه interface/result استفاده می‌کند و آیا به Model Reference نیاز دارد؛
- اجرای query در نبود Model module ممکن است یا نه.

این مرحله ResultSet→Model mapping را بررسی معماری فراتر نده و اضافه نکن.

## 8. Backward Compatibility

برای Query Builder فعلی و Modelهای موجود جداگانه بررسی کن:

- API رشته‌ای `table(...)`, `tableColumn(...)`, `column(...)`, `alias(...)` باید در traceability به‌عنوان مسیر فعلی ثبت شود؛
- اضافه‌کردن API typed آیا overload ambiguity، source/binary break یا signature conflict دارد؛
- تغییر class به object یا افزودن companion/property reference چه migrationی برای مصرف‌کننده می‌خواهد؛
- annotationهای فعلی و `Users`/`UserPhones` باید بدون تغییر باقی بمانند؛
- dependency graph و artifact exposure downstream چه اثری دارد.

هیچ compatibility edit یا migration اعمال نکن.

## قرارداد نهایی

گزارش باید برای هر مورد، با تفکیک fact و پیشنهاد، contract قابل implementation ارائه کند:

### Table Reference

چگونه یک Model به table name و default/explicit alias تبدیل می‌شود؛ یا چرا هنوز unresolved است.

### Column Reference

چگونه property reference، `QBColumn.name`، ارتباط آن با جدول و Kotlin type (صرفاً در حد مجاز scope) مشخص می‌شوند؛ یا چرا unresolved هستند.

### Resolution و Alias

کجا metadata resolve می‌شود و چگونه اولویت `Explicit → Model default → None` اعمال می‌شود؛ بدون نسبت‌دادن رفتار اجرایی به source فاقد آن.

### AST و Renderer

آیا referenceهای حل‌شده به AST موجود می‌رسند؛ آیا node تازه لازم است؛ و آیا Renderer/Executor باید مستقل از Model بمانند.

### Module/Dependency

module مالک typed API و جهت dependency. روشن کن آیا dependency فعلی Query Builder به `models:eloquent` باقی می‌ماند یا integration بالادستی/اختیاری است؛ هر تصمیم بدون evidence `Unresolved` بماند.

### Compatibility

مسیر استفادهٔ رشته‌ای موجود، تغییرات احتمالی Model/Kotlin API و migration احتمالی مصرف‌کننده‌ها را ثبت کن.

## برنامهٔ آزمون پیشنهادی

فقط برای candidateهایی که گزارش `Adopt` می‌کند، test plan بنویس؛ test اضافه یا اجرا نکن. برنامه حداقل این موارد را پوشش دهد:

- resolve کردن `Users` و `UserPhones` به table reference؛
- resolve کردن propertyهای واقعی نمونه به `QBColumn.name`؛
- حفظ qualifier/table association؛
- type parameter/reference behavior بدون تعمیم به DB type؛
- alias پیش‌فرض، alias صریح، precedence و alias حذف‌شده/خالی؛
- lowering به همان AST فعلی و render خروجی؛
- عدم نیاز به Model-specific AST، مگر تصمیم خلاف آن با evidence باشد؛
- regression برای مسیر رشته‌ای قدیمی و query بدون Model؛
- source compatibility گزینهٔ منتخب با Modelهای موجود؛
- dependency/build tests فقط به‌عنوان برنامهٔ آینده، نه در این traceability.

برای تصمیم‌های unresolved یا deferred، آزمون را شرط آینده بنویس، نه تعهد فعلی.
