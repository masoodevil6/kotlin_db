# Model v1.3: Typed Model References in Query Builder

## Status

`Status: Ready for Traceability`

## Objective

این گزارش بررسی می‌کند Modelهای فعلی چگونه می‌توانند به referenceهای table/column قابل‌استفاده در Query Builder تبدیل شوند، بدون اینکه از پیش تغییر Model یا AST را مفروض بگیریم. محورهای اصلی، امکان Kotlin APIهایی مانند `table(Users)` و `addColumn(Users.age)`، روش resolve کردن annotationها، alias precedence، lowering به AST موجود، dependency direction و سازگاری هستند.

هیچ source، Gradle، test یا plan تغییر نکرد. Build، test، database و runtime experiment در این مرحله اجرا نشد.

## Evidence Discipline

گزارش‌های v1.1 و v1.2 شامل traceability اصلی، dependency boundary و dependency-resolution experiment دوباره خوانده شدند. یافته‌های مهم آن‌ها با source و Gradle فعلی تطبیق داده شدند. گزارش dependency-resolution پیشین ثبت می‌کند که حذف موقت importهای بلااستفاده همراه با Gradle edge، Builder و downstreamهای داخلی آزموده‌شده را assemble کرده بود؛ در source فعلی هنوز importها و edge وجود دارند. آزمایش قبلی تکرار نشد، چون v1.3 صرفاً traceability است.

`QBTable`/`QBColumn` و معانی alias در بخش‌های مربوط از هم تفکیک شده‌اند: annotationها و APIها شواهد مخزن‌اند؛ معانی مالک به‌صورت `Owner-provided contract clarification` برچسب خورده‌اند. کد کامنت‌شده implementation فعال محسوب نشده است.

**پاسخ به سؤال Model instance یا schema/table definition:** repository یک **class مبتنی بر instance** نشان می‌دهد: class دارای constructor و propertyهای `val` معمولی است که مقدار اولیه دارند. annotation جدول روی class declaration قرار گرفته، اما هیچ contract فعال آن را به‌عنوان object سراسری schema تعریف نمی‌کند. بنابراین شواهد نمی‌گویند «Model فقط instance است» به‌عنوان قرارداد محصول؛ آنچه قطعی است شکل Kotlin فعلی class/instance-based است و static schema reference ارائه نشده.

به‌خصوص در source فعلی propertyای به نام `age` وجود ندارد. property Kotlin برابر `userAge` است و database name ثبت‌شده در `QBColumn.name` برابر `age` است. این دو نام را نباید یکی فرض کرد.

## Current Query Builder and AST Paths

### API و Builder فعال

- `IQueryTableApi.table(String, String)` ورودی table name و alias می‌گیرد؛ overload مربوط به `KClass<T>` داخل comment است.
- `IQueryColumnsBaseApi.tableColumn(String, String)` qualifier و column name می‌گیرد؛ overload مربوط به `KClass<T>`/`KProperty1<T,R>` کامنت است.
- `IQuerySelectApi.addColumn` در وضعیت فعلی فقط lambda از نوع `IQueryColumnsApi.() -> Unit` می‌گیرد.
- `IQueryColumnsApi.column` یک lambda برای ساخت base column می‌گیرد؛ `alias(String)` alias خروجی را ثبت می‌کند.
- `QueryTableBuilder`, `QueryColumnsBaseBuilder`, `QueryColumnsBuilder`, `QuerySelectBuilder` همین رشته‌ها/closureها را به AST می‌نویسند.
- `QueryRenderSelectBuilder`، table/select/join/where را به AST مربوط وصل می‌کند. table block در INSERT/UPDATE/DELETE و join هم از API جدول استفاده می‌کند.
- `QueryOptionGroupBuilder` و `QueryOptionOrderBuilder` نیز base column AST می‌سازند؛ قرارداد typed reference برای آن‌ها در API موجود نیست.

### مسیر AST و Renderer

```text
table(name, alias)
    → QueryTableAst.table / tableAlias

tableColumn(tableAlias, columnName)
    → QueryColumnsBaseAst.tableAlias / column

alias(alias)
    → QueryColumnsAst.ColumnAlias
```

Rendererهای MySQL از همین fieldها SQL متنی می‌سازند. `QueryTableAst` table و table alias، `QueryColumnsBaseAst` qualifier/column، و `QueryColumnsAst` column base و alias نهایی را نگه می‌دارند. AST فعلی provenance اینکه مقدار از Model آمده یا explicit بوده، Kotlin property identity و Kotlin type را نگه نمی‌دارد.

### Reflection / comment

امضاهای Model-based در `IQueryTableApi` و `IQueryColumnsBaseApi` و بدنه‌های متناظر `findAnnotation` در `QueryTableBuilder`/`QueryColumnsBaseBuilder` کامنت هستند. Reader اجرایی برای `QBTable` یا `QBColumn` پیدا نشد. وجود importهای `KClass`, `KProperty1`, `findAnnotation` و `kotlin-reflect` به‌تنهایی integration فعال را ثابت نمی‌کند.

## Table Reference Analysis

**Repository Evidence:** `Users` یک class declaration با constructor است؛ API فعال `table(String, String)` می‌خواهد. `QBTable.name` و `alias` در دو مدل مقدار دارند. Reader فعال Model وجود ندارد؛ code پیشنهادی `KClass`/`findAnnotation` کامنت است. AST موجود دو string nullable برای table و alias دارد.

**Kotlin language evidence (غیرمخزنی):** class literal برای گرفتن reference به class به شکل `Users::class` است؛ companion object اعضایی دارد که با نام class قابل دسترسی‌اند. object declaration یک singleton value است و از نظر شکل با class فعلی فرق دارد. بنابراین `table(Users)` به‌عنوان expression با declaration فعلی ممکن نیست مگر `Users` به object/companion-based value تغییر کند؛ candidate نزدیک با class فعلی `table(Users::class)` است. citeturn0search0turn0search2

**Interpretation:** اگر API یک `KClass<out IModelBase>` یا type-safe معادل بگیرد، می‌تواند class metadata را در لایهٔ integration resolve کند و نام table را به Builder رشته‌ای بدهد. اما این امضا به‌تنهایی table default alias را انتخاب نمی‌کند؛ همچنین source فعلی کلاس را به‌عنوان schema object تعریف نکرده است. تبدیل `Users` به `object` رفتار construction/type را عوض می‌کند. افزودن companion با descriptor نیز قرارداد و propertyهای تازه‌ای می‌سازد.

**Decision:** شکل دقیق `table(Users)` در declarations فعلی `Reject` است. امکان API نزدیک مثل `table(Users::class)` یا companion/reference descriptor `Unresolved` می‌ماند تا owner قرارداد Model-as-schema و alias table را روشن کند. پس از resolve، AST موجود برای table name و alias حل‌شده کفایت ساختاری دارد.

## Column Reference Analysis

**Repository Evidence:** در `Users` property فعال `userAge: String?` وجود دارد، نه `age`; annotation آن `name="age"` و `alias="u_user_age"` را ثبت می‌کند. API فعال `addColumn { column { tableColumn(alias, name) }; alias(...) }` است. API مستقیم `addColumn(ModelColumnReference)` وجود ندارد. Reader کامنت‌شدهٔ قدیمی هم `KClass<T>` و `KProperty1<T,R>` می‌گرفت و به AST base نظر داشت.

**Kotlin language evidence (غیرمخزنی):** برای ارجاع first-class به member property کلاس، Kotlin از callable/property reference مانند `Users::userAge` استفاده می‌کند؛ reference این member property receiver از نوع `Users` دارد و با property access value یکی نیست. `KProperty1` می‌تواند نوع generic مقدار property را حمل کند، ولی خود این موضوع SQL معنا نمی‌سازد. citeturn0search1

**Interpretation:** `Users.age` عیناً نه با اسم property فعلی سازگار است و نه syntax عادی دسترسی به instance member است. شکل class-property-reference نزدیک `Users::userAge` است، ولی برای resolve کردن `QBTable` و حفظ table association ممکن است نیاز به class/model reference جدا یا descriptor بسته‌بندی‌شده داشته باشد. Generic `R` می‌تواند در compile-time نوع Kotlin property (برای `userAge`، `String?`) را حمل کند؛ اما از آن هیچ نتیجه‌ای دربارهٔ SQL type، SQL nullability semantics یا operator compatibility به دست نمی‌آید.

**Decision:** reference typed در لایهٔ Kotlin ممکن است به شکل candidate بررسی شود، ولی `addColumn(Users.age)` با Model و API فعلی پشتیبانی نمی‌شود. نگاشت به `QBColumn.name`، ارتباط table/property و overload shape هنوز `Unresolved` است. اگر pairای از Model class و `KProperty1` قبل از AST به qualifier/column string تبدیل شود، AST موجود می‌تواند آن را نمایش دهد.

### مرز type safety

در v1.3 می‌توان نوع Kotlin را صرفاً metadata/reference type یا generic compile-time parameter تحلیل کرد. `String?`/`Int`، `QBColumn` یا `KProperty1<Users,R>` هیچ‌کدام به‌تنهایی SQL type، SQL `NULL` contract، predicate compatibility یا operator overload را تعیین نمی‌کنند. این مرز `Separate Contract` است و بیرون از v1.3 typing behavior می‌ماند.

## Alias Precedence

**Owner-provided contract clarification:**

```text
QBTable.name       = table name
QBTable.alias      = default SQL table alias
QBColumn.name      = database column name
QBColumn.alias     = default SELECT alias

Explicit Query Alias
        ↓
Model Default Alias
        ↓
No Alias
```

**Repository Evidence:** API رشته‌ای جدول، alias را به‌صورت پارامتر اجباری می‌گیرد و Builder آن را در `QueryTableAst.tableAlias` می‌نویسد. برای SELECT، alias صریح در `QueryColumnsAst.ColumnAlias` قرار می‌گیرد و Renderer آن را می‌خواند. alias مدل به این fieldها منتقل نمی‌شود. Reader کامنت‌شدهٔ `QBColumn` alias را به fieldی در column-base نسبت می‌دهد که با محل alias خروجی فعال یکی نیست.

**Interpretation:** AST فعلی می‌تواند alias نهایی حل‌شده را نگه دارد؛ precedence باید پیش از ثبت آن در AST (یا در API/Builder layer) resolve شود. Renderer نیازی ندارد Model را بشناسد. برای table alias، source فعال هیچ default/fallback resolution ندارد؛ آیا explicit table alias بر `QBTable.alias` تقدم دارد باید از clarification جداگانه یا تأیید صریح owner بیاید.

**Decision:** alias string صریح در مسیر دستی فعال است؛ owner precedence برای Model reference قرارداد موردنظر است، نه رفتار اجرایی فعلی. زمان/مالک resolver و semantics empty/absent explicit alias `Unresolved` است. Table alias precedence نیز `Unresolved` است.

## AST Boundary

**Evidence:** `QueryTableAst` دو field لازم table/tableAlias دارد؛ `QueryColumnsBaseAst` qualifier و column را دارد؛ `QueryColumnsAst` column base و final `ColumnAlias` را نگه می‌دارد. Query Builder ورودی دستی را به این fieldها می‌نویسد و Renderer آن‌ها را مصرف می‌کند.

**Interpretation:** پس از آنکه Model reference بیرون از AST به `(table name, resolved table alias, column name, resolved SELECT alias)` تبدیل شد، AST فعلی برای شکل SQL فعلی کافی است. AST فعلی generic Kotlin type، property identity و origin/provenance را حفظ نمی‌کند؛ برای string lowering ساده این‌ها لازم نیستند. اگر type/provenance پس از lowering لازم شمرده شود باید use case مشخص ارائه شود.

**Decision:** `Adopt` برای استفاده از AST موجود برای identifierها و aliasهای از پیش resolveشده؛ `Defer` برای Model-specific AST یا حفظ type/provenance تا وقتی ضرورت مستند شود. این نتیجه، امکان typed Query API را به‌تنهایی اثبات نمی‌کند.

## Dependency Direction and Integration Ownership

### Gradle و source فعلی

گراف مرتبط فعلی از build files:

```text
models:eloquent → core
query:api → core, query:ast
query:builder → core, query:ast, query:api, models:eloquent, kotlin-reflect
query:dialect → core, query:ast, query:api, query:builder
query:renderer → core, query:api, query:ast, query:dialect
query:executor → tools, core, query:ast, query:builder, query:api,
                query:dialect, query:renderer, manager:execute
query:example → tools, core, models:eloquent, manager:execute,
                query:api, query:builder, query:renderer, query:executor
```

`models:eloquent` هیچ dependency به Query module ندارد؛ Query Builder edge مستقیم به `models:eloquent` دارد. source importهای فعلی `CteInfoUser.kt` علت compile-level ثبت‌شده در گزارش قبلی‌اند. همان گزارش نتیجه می‌دهد پس از حذف importهای unused، Builder و downstreamهای داخلی بررسی‌شده بدون edge assemble شدند. این edge، نیاز runtime metadata را ثابت نمی‌کند.

### Candidate ownership

| مسیر | Evidence / تفسیر | Decision |
|---|---|---|
| Query Builder مستقیم Model concrete را بشناسد | edge فعلی وجود دارد اما generic Model API فعال نیست. generic reference مبتنی بر `IModelBase`/property reference از Core می‌تواند concrete `models:eloquent` را از API پایه جدا کند. | `Defer` |
| Model مستقیماً Query Builder را فراخوانی کند | Model فعلی مستقل از Query است؛ edge تازه‌ای برعکس جهت فعلی می‌سازد. مالکیت API و نیاز فراخوانی از مدل ثابت نشده. | `Defer` |
| Integration optional در consumer/layer بالاتر | می‌تواند هر دو module را مصرف کند، metadata را resolve کند و Query Builder پایه را رشته‌ای و مستقل نگه دارد؛ module موجود/ضرورت reuse ثابت نشده. | `Defer` |
| Model→AST مستقیم | AST representation است و Model فعلی به آن وصل نیست؛ API/ownership و direct coupling لازم بودنش ثابت نشده. | `Reject` به‌عنوان فرض پیش‌فرض؛ بازبینی فقط با evidence use case |

**پاسخ مرزی:** جهت پیشنهادی مالک `Model → Query Builder` است، اما repository این جهت را پیاده یا الزام نکرده است. اگر API generically در Query module فقط Core contracts و Kotlin references را بپذیرد، مصرف‌کنندهٔ Models می‌تواند Query API را صدا بزند بی‌آنکه Query Builder به `models:eloquent` وابسته باشد. اینکه API در Builder، integration optional یا caller قرار بگیرد `Unresolved` است. Query Builder بدون Model در مسیر string-based موجود قابل استفاده است؛ این گزاره با Gradle independence فعلی یکسان نیست.

## Lowering, Renderer, and Executor

مسیر فعال source:

```text
QueryRenderSelectBuilder
  → QueryTableBuilder / QuerySelectBuilder / QueryColumnsBuilder
  → QueryTableAst / QuerySelectAst / QueryColumnsAst / QueryColumnsBaseAst
  → Renderer registry and MySQL capabilities
  → SQL string
  → Executor builds BuiltQuery(query, params)
```

Reference resolver احتمالی باید class/property identity و annotation را به stringهای فعلی ترجمه کند، سپس Builder/AST موجود را پر کند. Renderer فقط AST و dialect data را مصرف می‌کند؛ Executor Query API/AST و `BuiltQuery` را اجرا می‌کند و Model type نمی‌گیرد. در این source path نیاز به Model-aware Renderer/Executor دیده نمی‌شود.

Migration module API/AST مستقل دارد و reportهای v1.2 اتصال Model metadata را ثابت نکرده‌اند؛ v1.3 integration با Migration را خارج از دامنه نگه می‌دارد.

## Backward Compatibility

- API رشته‌ای فعلی `table(String,String)`, `tableColumn(String,String)`, `addColumn(lambda)` و `alias(String)` مسیر فعال است؛ reference typed نباید در traceability باعث حذف آن تلقی شود.
- افزودن overloadهای class/property ممکن است اضافه‌شدن API public باشد؛ ambiguity و source/binary impact بدون امضای انتخاب‌شده قابل تعیین نیست.
- تغییر classهای `Users`/`UserPhones` به object، constructor و نوع Model را تغییر می‌دهد و با سازگاری موجود قابل فرض نیست.
- افزودن companion یا separate reference می‌تواند class فعلی را حفظ کند، ولی public Model API تازه‌ای می‌سازد و به migration/contract نیاز دارد.
- owner alias semantics، قرارداد اجرایی فعلی نیست؛ فعال‌سازی آن می‌تواند SQL خروجی مثال‌ها/مصرف‌کنندگان را تغییر دهد.
- Gradle edge فعلی Query Builder→Model هنوز در build file هست؛ report قبلی internal assemblies را پس از حذف موقت importها/edge موفق ثبت کرده است، اما external consumer evidence unavailable است.

**Decision:** سازگاری مسیر string API را باید حفظ کرد؛ سازگاری دقیق API typed تا انتخاب shape `Unresolved` است.

## Non-Goals

- ResultSet→Model mapping، ORM، `find`, `save`, update/delete CRUD، Repository؛
- relations، lazy/eager loading، composite relationships؛
- full SQL-like `select/from/where` DSL یا raw SQL؛
- Kotlin→SQL type mapping، SQL nullability semantics، operator/predicate compatibility؛
- Model-specific AST به‌عنوان پیش‌فرض؛
- Migration integration؛
- پیاده‌سازی annotation reader، Adapter، Symbol Layer یا dependency change؛
- تغییر source، test یا plan، build، runtime experiment یا database access.

## Final Contract

### Table Reference

Repository contract فعلی: `Users` یک class Model با `QBTable` metadata است، نه schema descriptor value فعال. `table(Users)` با declarations فعلی expression معتبر API نیست. `Users::class` یا companion/reference descriptor فقط candidate است. `QBTable.name`/alias در source فعال به AST منتقل نمی‌شوند؛ پس روش resolution هنوز قرارداد اجرایی نیست.

### Column Reference

Repository contract فعلی: Kotlin property `userAge` به database column name `age` و default alias `u_user_age` metadata دارد. `Users.age` property موجود نیست. Kotlin member reference candidate نزدیک `Users::userAge` است، اما association با table و lowering به AST فعال وجود ندارد.

### Resolution و Alias

مالک خواسته است explicit SELECT alias بر Model default مقدم باشد، سپس نبود alias بدون alias render شود. این owner-provided contract است؛ active code فقط explicit string را ثبت می‌کند. Resolver metadata باید قبل از ثبت AST winner را انتخاب کند. مالک module و empty/absent rules، به‌خصوص برای table alias، unresolved است.

### Type safety

Kotlin property type می‌تواند در حد compile-time/reference metadata باقی بماند. در v1.3 از `String?` یا `Int` هیچ SQL type، SQL nullability، DB schema یا operator compatibility استنتاج نمی‌شود.

### AST و Renderer

برای table/column/aliasهای resolveشده AST فعلی کافی است. Model-specific AST node یا Model awareness در Renderer/Executor لازم اثبات نشده و پیش‌فرض پذیرفته‌شده نیست.

### Module و dependency

Model فعلی به Query وابسته نیست. Query Builder فعلاً به `models:eloquent` dependency دارد؛ source importهای فعلی علت compile، و گزارش resolution قبلی نشان داد حذف موقت importها همراه edge حذف‌شده درون repository قابل assemble بوده است. اینکه typed API generic در Query API/Builder باشد یا optional upper integration module باید با contract مالک و external compatibility تعیین شود. Model→Query جهت پیشنهادی است، نه current fact.

### Compatibility

String API موجود باید به‌عنوان مسیر جاری باقی بماند. `Users`/`UserPhones` را نمی‌توان بی‌تصمیم به object تبدیل کرد. overload یا companion API تا زمان انتخاب shape و بررسی downstream source/ABI آمادهٔ تصویب نیست.

## Proposed Test Plan

هیچ test تغییر یا اجرا نشد. در صورت انتخاب API typed، برنامهٔ آینده باید شامل این موارد باشد:

1. resolve `Users::class`/reference منتخب به `QBTable.name` و table alias؛
2. resolve reference واقعی `Users.userAge` به `QBColumn.name="age"`، نه فرض `Users.age`؛
3. اثبات ارتباط class/property و جلوگیری از پذیرش property متعلق به Model دیگر؛
4. alias پیش‌فرض SELECT، explicit override، no alias و empty/absent contract؛
5. lowering به AST موجود و SQL rendering برای SELECT و table/joinهای مربوط؛
6. regression مسیر string API و Query Builder بدون Model؛
7. type reference/generic test صرفاً برای اثبات compile-time property association، بدون SQL type/nullability/operator assertion؛
8. module dependency/build tests برای گزینهٔ مالکیت منتخب؛
9. source/API compatibility برای Modelهای فعلی و consumerهای مشخص‌شده.

مواردی که policy آن‌ها unresolved است شرط تست آینده‌اند، نه قرارداد implementation پذیرفته‌شده.

## Deferred / Out of Scope

- انتخاب قطعی `class`, `companion`, `object` یا wrapper/reference؛
- direct syntax `Users.age` تا وقتی property و API reference قرارداد ندارند؛
- annotation reader و error policy برای metadata ناقص؛
- `QBColumn.primaryKey` مصرف در Query Builder؛
- alias resolver implementation و table alias override policy؛
- generic typed expressions، SQL type/nullability mapping و operators؛
- Adapter/Translation/Symbol layer جدید بدون evidence reuse؛
- تغییر Gradle dependency یا public Query API؛
- Model-specific AST, ResultSet mapping, Migration, ORM/CRUD/relations و full DSL.

## Unresolved Decisions

### 1. آیا Model یک instance model است یا schema/table definition؟

**تصمیم:** source فقط class-based instance property structure را ثابت می‌کند؛ contract محصول را نه.

**چرا unresolved است:** `Users` یک class با `val`های instance و annotation class-level است؛ object/companion descriptor یا rule معنایی جدا ندارد.

**شواهد لازم:** owner باید تعیین کند آیا Model class خودِ table schema محسوب می‌شود یا instance؛ آیا instance construction برای reference لازم است؛ و آیا static descriptor افزوده می‌شود.

**قرارداد متأثر:** `table(Users)`, column reference API و سازگاری Model.

### 2. شکل Kotlin API برای table و column reference

**تصمیم:** direct `table(Users)` و `Users.age` با source declarations فعلی کار نمی‌کنند؛ شکل جایگزین منتخب نیست.

**چرا unresolved است:** class literal، `KClass`/`KProperty1`, companion یا wrapper هرکدام API و compatibility متفاوتی می‌سازند؛ `age` هم نام property موجود نیست (`userAge`).

**شواهد لازم:** owner contract برای spelling موردنیاز، قبول `Users::class`/`Users::userAge` یا الزام static syntax، و سیاست اختلاف property name/database name.

**قرارداد متأثر:** public Query API, Model schema API, type reference.

### 3. Resolution contract

**تصمیم:** `QBTable`/`QBColumn` resolution فعال نیست.

**چرا unresolved است:** خوانشگرها فقط comment هستند؛ missing, empty, conflicting annotationها و property-to-table association سیاست ندارند.

**شواهد لازم:** lookup strategy، failure/validation behavior، تعیین نام مرجع source vs annotation، و محل module resolver.

**قرارداد متأثر:** API reference و lowering.

### 4. Alias precedence و محل resolver

**تصمیم:** SELECT precedence به‌عنوان clarification مالک ثبت است، اما implementation layer و empty/absent behavior unresolved است؛ table precedence هم روشن نیست.

**چرا unresolved است:** Builder فعلی فقط مقدار صریح را می‌گیرد و Reader default وجود ندارد.

**شواهد لازم:** confirmation table alias override rule، explicit empty vs omitted semantics، و انتخاب owner layer برای resolve قبل از AST.

**قرارداد متأثر:** SQL output، AST fieldهای alias.

### 5. Sufficiency AST برای نوع reference

**تصمیم:** برای lowering stringهای حل‌شده کافی است؛ حفظ type/provenance در آن لازم دانسته نشده است.

**چرا بخشی unresolved است:** نیاز future consumer به نگهداری property/type پس از lowering مشخص نیست.

**شواهد لازم:** use case‌ای که نشان دهد اطلاعات reference پس از ساخت AST باید در AST باقی بماند.

**قرارداد متأثر:** AST representation و type-safety scope.

### 6. Integration ownership / dependency direction

**تصمیم:** Model فعلی مستقل از Query است؛ مسیر typed API module انتخاب نشده.

**چرا unresolved است:** dependency فعلی Builder→eloquent بابت importهای باقی‌مانده است؛ آزمایش قبلی حذف ترکیبی داخلی را گذرانده، اما consumer بیرونی و انتخاب مالک API در دسترس نیست.

**شواهد لازم:** تأیید owner برای جهت Model→Query integration، فهرست consumerهای بیرونی و Gradle artifact/runtime expectations.

**قرارداد متأثر:** Gradle graph، Builder independence و source/API compatibility.

### 7. Backward compatibility

**تصمیم:** string API فعلی را باید حفظ کرد؛ اثر API typed unresolved است.

**چرا unresolved است:** هیچ overload یا Model Reference shape انتخاب نشده تا ambiguity/ABI بررسی شود.

**شواهد لازم:** امضای دقیق candidate منتخب و فهرست/قرارداد مصرف‌کنندگان داخلی و خارجی.

**قرارداد متأثر:** source/binary compatibility و مهاجرت Model.

## Implementation Readiness

`Status: Ready for Traceability`

شش موضوع لازم برای readiness یکجا بسته نشده‌اند: شکل Kotlin API، resolution واقعی، مالک resolver alias، مالکیت integration/dependency، و compatibility هنوز unresolved هستند. AST برای lowering رشته‌ای حل‌شده کافی دانسته شد، اما typed/provenance semantics آن قرارداد جدا می‌خواهد. `Users` در source فعلی class با instance properties است، و `Users.age` نه syntax/reference موجود و نه نام property فعلی است. بنابراین implementation-ready اعلام نمی‌شود.
