# Model v1.1: Traceability و تثبیت قرارداد فعلی Table Model

## Status

`Ready for Traceability`

## Objective

هدف این مرحله بررسی کامل infrastructure فعلی Model در repository و مشخص کردن کوچک‌ترین قرارداد قابل‌اتکای آن است.

در repository در حال حاضر infrastructure زیر وجود دارد:

```text
IModelBase
    ↓
IModel
    ↓
BaseModel
    ↓
User Models

@QBTable
@QBColumn
```

نمونه فعلی:

```kotlin
@QBTable(
    name = "user_users",
    alias = "uu"
)
class Users : BaseModel() {

    @QBColumn(
        name = "id",
        alias = "u_user_id",
        primaryKey = true
    )
    val userId: Int = 0

    @QBColumn(
        name = "name",
        alias = "u_user_name"
    )
    val userName: String? = null
}
```

هدف این plan این نیست که Model جدیدی طراحی شود.

هدف این است که مشخص شود infrastructure فعلی دقیقاً چه semantic و مصرفی دارد و آیا می‌تواند baseline رسمی Table Model در `kotlin_db` باشد.

## Repository path note

درخواست به `data_base:model` اشاره می‌کند، اما `settings.gradle.kts` در حال حاضر ماژول‌های `:data_base:models` و `:data_base:models:eloquent` را ثبت کرده است و `:data_base:model` وجود ندارد.

Traceability باید همین ماژول‌های واقعی و قراردادهای مرتبط در `data_base:core` را بررسی کند.

این plan مجوز تغییر نام، جابه‌جایی یا بازطراحی ماژول‌ها نیست.

# 7. QBTable

تعریف فعلی:

```kotlin
@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.RUNTIME)
annotation class QBTable(
    val name: String = "",
    val alias: String = "",
)
```

برای `QBTable` دقیقاً مشخص کن:

### name

* آیا نام واقعی database table است؟
* آیا در SQL rendering استفاده می‌شود؟
* آیا identifier quoting روی آن انجام می‌شود؟
* آیا blank مجاز است؟
* آیا validation دارد؟
* آیا name می‌تواند schema-qualified باشد؟
* آیا name case-sensitive است یا فقط به renderer سپرده می‌شود؟

### alias

مشخص کن alias دقیقاً چیست.

مثلاً:

```kotlin
@QBTable(
    name = "user_users",
    alias = "uu"
)
```

آیا semantic آن این است:

```sql
FROM `user_users` AS `uu`
```

یا معنای دیگری دارد؟

تمام usageها را بررسی کن.

### Runtime

مشخص کن چه کدی annotation را با reflection می‌خواند.

اگر هیچ runtime consumerای وجود ندارد، صریحاً ثبت کن:

```text
Runtime consumer: None found
```

# 8. QBColumn

تعریف فعلی:

```kotlin
@Target(AnnotationTarget.PROPERTY)
@Retention(AnnotationRetention.RUNTIME)
annotation class QBColumn(
    val name: String = "",
    val alias: String = "",
    val primaryKey: Boolean = false
)
```

برای هر field مشخص کن:

### name

بررسی کن آیا نام database column است.

### alias

semantic دقیق آن را پیدا کن.

مثلاً:

```kotlin
@QBColumn(
    name = "id",
    alias = "u_user_id"
)
val userId: Int
```

بررسی کن آیا alias برای:

```sql
SELECT `id` AS `u_user_id`
```

است یا کاربرد دیگری دارد.

### primaryKey

بررسی کن:

* کجا مصرف می‌شود
* آیا فقط metadata است
* آیا Query Builder از آن استفاده می‌کند
* آیا Migration از آن استفاده می‌کند
* آیا runtime behavior ایجاد می‌کند
* آیا فقط single-column primary key را مدل می‌کند

در این مرحله composite primary key اضافه نکن.


مشخص کن:

* آیا no-arg constructor لازم است
* آیا reflection instantiation وجود دارد
* آیا propertyها mutable هستند
* آیا immutable Model فعلی supported است
* آیا default value برای mapping لازم است

در این مرحله constructor model را تغییر نده.

# 15. Reflection Contract

به دلیل اینکه:

```kotlin
@Retention(AnnotationRetention.RUNTIME)
```

است، بررسی کن runtime reflection واقعاً استفاده می‌شود یا نه.

مشخص کن:

* annotation discovery کجا انجام می‌شود
* class metadata چگونه خوانده می‌شود
* property metadata چگونه خوانده می‌شود
* performance concern فعلی وجود دارد یا نه
* caching وجود دارد یا نه

اگر reflection فقط به دلیل design اولیه annotationهاست ولی consumer واقعی ندارد، همین را ثبت کن.

# 23. Critical Rule

در این مرحله هیچ کدی تغییر نکند.

این plan فقط باید به این سؤال پاسخ دهد:

> «با توجه به چیزی که همین الان در repository داریم، Model دقیقاً چیست و کوچک‌ترین Contract رسمی آن چیست؟»

هیچ API جدیدی صرفاً برای زیباتر شدن طراحی پیشنهاد نده.

هیچ abstraction جدیدی صرفاً برای generalization ایجاد نکن.

هیچ ORM طراحی نکن.

هیچ feature آینده را بدون evidence وارد Contract نکن.

اصل تصمیم‌گیری:

```text
Repository Evidence
        ↓
Current Semantics
        ↓
Minimal Contract
        ↓
Future Features Deferred
```
