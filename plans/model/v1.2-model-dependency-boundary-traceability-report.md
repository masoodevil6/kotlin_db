# Model v1.2: Dependency / Integration Boundary Traceability

## Status

`Status: Ready for Traceability`

بررسی source و Gradle تکمیل شد. dependency فعلی `query:builder → models:eloquent` از نظر معماری/runtime مصرف فعال metadata را ثابت نمی‌کند؛ اما دو import فعال در source تولیدی `CteInfoUser.kt` به کلاس‌های Model دارد و در نتیجه حذف edge بدون اصلاح source، بر اساس وضعیت فعلی compile-safe تلقی نمی‌شود. دلیل تاریخی افزودن dependency، سازگاری مصرف‌کنندگان بیرونی و مالکیت integration با شواهد repository به‌تنهایی تعیین نمی‌شوند.

## Objective

این گزارش بررسی می‌کند dependency مستقیم `:data_base:query:builder → :data_base:models:eloquent` چه شواهد source-level دارد، مسیرهای مستقل Query Builder و Model چه وضعی دارند، و integration آینده در کدام مرز می‌تواند قرار گیرد. این گزارش فقط traceability است؛ هیچ source، Gradle، test یا documentation دیگری تغییر نکرده و build/test/runtime/database اجرا نشده است.

## Reverse Dependency Analysis

بر اساس project dependencyهای Gradle یافت‌شده:

| هدف | وابسته‌های مستقیم قابل مشاهده | طبقه‌بندی |
|---|---|---|
| `:data_base:query:builder` | `:data_base:query:dialect`, `:data_base:query:executor`, `:data_base:query:example`, `:data_base:migration` (فقط `testImplementation`), `:data_base:migration:executor` (`implementation`) | edgeهای production در dialect/executor/example/migration executor؛ یک edge آزمایشی در migration. |
| `:data_base:models:eloquent` | `:data_base:query:builder`, `:data_base:query:example` | edge production در Builder و example. در Builder، source importها توضیح compile-time می‌دهند؛ در example dependency مستقل اعلام شده است. |

زنجیرهٔ `query:builder → models:eloquent → core` چرخه ایجاد نمی‌کند: `models:eloquent` به Query وابسته نیست و فقط به Core وصل است. حذف edge مستقیم Builder→Model، پس از رسیدگی به importهای فعال، یک یال و مسیر دسترسی غیرضروری به Model را از graph حذف می‌کند؛ اما اینکه این ساده‌سازی هدف نهایی باشد، از graph به‌تنهایی نتیجه نمی‌شود.

`query:dialect` به Builder وابسته است و `query:builder` به dialect وابسته نیست؛ جهت این دو یال چرخه نمی‌سازد. source dependency و Gradle dependency جدا هستند: importهای Model در Builder source-level هستند، در حالی که نمونه‌های `models:eloquent` از Builder استفاده نمی‌کنند.

## Query Builder Independence

مسیر دستی فعال از source چنین است:

```text
String DSL
    ↓
QueryRenderSelectBuilder / QueryTableBuilder / QueryColumnsBaseBuilder
    ↓
Query AST
    ↓
Dialect Renderer
    ↓
BuiltQuery(query, params)
    ↓
Executor / DB execute interface
```

`table(String, String)`, `tableColumn(String, String)`, `cte(String, String)` و `alias(String)` رشته‌ها را در AST می‌گذارند. Renderer از AST SQL می‌سازد؛ `executeOut` query را render می‌کند و `BuiltQuery` را به callback می‌دهد. API اجرای SELECT `ExecuteResult<ResultSet>` را تحویل callback می‌دهد. این مسیر از نظر semantic به Model احتیاج ندارد و در source هیچ Model metadataیی نمی‌خواند.

اما گزارهٔ `Query Builder can work without Model` با گزارهٔ `query:builder has no Gradle dependency on Model` یکی نیست. فعلاً اولی برای queryهای رشته‌ای پشتیبانی می‌شود؛ دومی نادرست است: edge Gradle موجود است و importهای Model در source تولیدی compile resolution را لازم می‌کنند. استقلال module/build فقط پس از حذف یا جابه‌جایی آن referenceها و edge قابل تحقق است؛ این مرحله چنین تغییری نداده است.

## Model Independence

`models:eloquent` برای تعریف `IModel`, `BaseModel`, `Users`, `UserPhones`, `QBTable`, و `QBColumn` به Query Builder وابسته نیست. `IModelBase`, `QBTable`, و `QBColumn` در `core` هستند؛ `models:eloquent` به `core` وابسته است و source آن‌ها را مصرف می‌کند. در Gradle فایل‌های `models:eloquent` هیچ project dependency به Query API/Builder/AST/Renderer/Executor ندارند.

این evidence با جهت احتمالی آیندهٔ `Model → Query integration → Query Builder` سازگار است؛ اما به‌تنهایی تصمیم نمی‌دهد که integration باید ماژول جدا، API در Model یا facade بالادستی باشد.

## Alias Integration Boundary

**Owner-provided contract clarification:** `QBTable.name` نام جدول، `QBTable.alias` alias پیش‌فرض جدول، `QBColumn.name` نام ستون DB، و `QBColumn.alias` alias پیش‌فرض SELECT است؛ alias صریح query بر default تقدم دارد.

Source فعال رشته‌های صریح alias جدول/SELECT را می‌پذیرد و AST می‌تواند مقدار resolveشده را نگه دارد. default Model در مسیر فعال خوانده نمی‌شود و resolver precedence وجود ندارد. بر همین evidence:

| گزینهٔ مالکیت | برداشت از dependency boundary |
|---|---|
| Model metadata reader | اگر در Query Builder قرار گیرد، جهت dependency را Query→Model می‌کند؛ با استقلال Build مطلوب تعارض دارد. در وضعیت فعلی reader فقط comment است. |
| Model adapter / integration | می‌تواند metadata را قبل از Builder به ورودی‌های عادی Builder ترجمه کند؛ نیاز به abstraction و module مالک از repository ثابت نیست. |
| Symbol layer | می‌تواند precedence و property identity نگه دارد، ولی برای query سادهٔ resolveشده لازم نیست و use case typed DSL اثبات نشده است. |
| Query Builder | می‌تواند explicit/default را resolve کند، اما اگر مستقیماً annotation بخواند Model dependency می‌گیرد؛ در AST فعلی فقط alias نهایی ذخیره می‌شود. |
| Renderer | AST را render می‌کند و از Model اطلاعی ندارد. انتقال metadata interpretation به Renderer coupling ناموجه ایجاد می‌کند؛ source نیازی به آن نشان نمی‌دهد. |

`explicit query alias > model default alias` به‌عنوان owner clarification روشن است، ولی محل implementation آن هنوز unresolved است. مدل انتخابی نباید Renderer یا Executor را به Model وابسته کند. این نتیجه تصمیم جدید implementation نیست.

## AST Boundary

برای جدول/alias جدول، qualifier/column و یک alias نهایی SELECT، AST موجود fieldهای string/null پذیر دارد. در صورت resolve شدن metadata پیش از ورود به AST، انتقال به همین nodeها از نظر شکل داده کافی است و `No new Model-specific AST node required` همچنان برای query ساده برقرار است.

`Model → Query Builder API` یعنی Model-side یا integration-side API ورودی‌های موجود Builder را فراخوانی/بسازد؛ `Model → Query AST` یعنی Model مستقیماً به module داخلی/عمومی AST وابسته شود. دومی ownership سطح پایین‌تری را به Model می‌دهد و coupling مستقیم به representation می‌آورد. Source هیچ نیاز فعلی برای Model→AST نشان نمی‌دهد. اینکه در DSL آینده Adapter به API وصل شود یا lowering مجاز به AST باشد، بر اساس repository فعلی unresolved می‌ماند.

## Future SQL-like DSL Boundary

Syntaxهای `select(Users.id, Users.name).from(Users)` فقط candidate هستند و API نهایی طراحی نمی‌شود. چنین DSLای به property identity، نماد typed و resolve metadata نیاز احتمالی دارد؛ این نیاز در AST فعلی که identifierها را string می‌کند وجود ندارد. اگر ساخته شود، از منظر graph محل مناسب integration یک لایهٔ بالاتر از Query Builder است که Model/metadata را به Builder یا AST موجود ترجمه کند؛ این پیشنهاد با جهت موردنظر Model→Query سازگار است، اما انتخاب بین facade، adapter یا symbol module بدون قرارداد use case/مالکیت قطعی نیست.

برای DSL آینده، Query Builder پایه باید queryهای string-based و بدون Model را همچنان پشتیبانی کند. Renderer/Executor محل خواندن Model نیستند. نیاز به abstraction تازه یا typed layer جداگانه `Defer` می‌شود.

## Compatibility Analysis

- در source عمومی فعال Query API/Builder که بررسی شد، امضای `IModel`, `Users` یا `UserPhones` پیدا نشد؛ Model-based overloadها کامنت هستند. Model classes به public Builder API متصل نیستند.
- `CteInfoUser.kt` دو import فعال دارد. حذف Gradle edge بدون حذف/جابجایی این imports احتمالاً compile resolution را می‌شکند؛ چون build اجرا نشده، این نتیجه بر قواعد compile/source inspection متکی است، نه نتیجهٔ تجربی build.
- حذف edge می‌تواند runtime dependency graph و Gradle resolution مصرف‌کنندگان downstream را عوض کند. از آنجا که dependency `implementation` است، در سطح declaration یک API publicِ Model از Builder مشاهده نشد؛ اما downstreamها ممکن است عملاً به حضور transitive artifact تکیه کرده باشند. این repository آن‌ها را نشان نمی‌دهد.
- **External consumer evidence: unavailable.** مصرف‌کنندگان داخل repository قابل فهرست‌اند؛ مصرف‌کنندگان خارج از آن و توافق binary compatibility در دسترس نیستند.
- دلیل تاریخی افزودن dependency، generated class، annotation processor یا runtime Model loading از source/build files قابل اثبات نشد. هیچ processor configuration مربوطی پیدا نشد؛ reflection فعال موجود در Query dialect مربوط به registry renderer است، نه Model.
- نتیجه: از repository به‌تنهایی evidence کافی برای حذف بی‌خطر edge بدون source change یا اعلام عدم تأثیر downstream وجود ندارد. تغییر compatibility انجام نشد.

## Final Boundary Contract

### Query Builder

Query Builder فعلی table، qualifier، column، alias، CTE و query را از API رشته‌ای می‌گیرد و AST می‌سازد. برای queryهای پایه نباید به runtime Model metadata نیاز داشته باشد. در حال حاضر Gradle edge به Model باقی است و دلیل compile source آن دو import در CTE است.

### Model

Model فعلی metadata annotation و propertyها را تعریف می‌کند و فقط به Core وابسته است. Query Builder، Renderer، Executor و Migration را نمی‌شناسد. رفتار فعال برای ترجمه یا persistence از annotationها اثبات نشده است.

### Integration Layer

وجود integration اختیاری در لایهٔ بالاتر با dependency direction مستقل سازگار است. اینکه این لایه adapter، facade یا translation/symbol module باشد، unresolved است و باید پس از مشخص‌شدن use case، API ownership، consumerها و compatibility انتخاب شود.

### AST

AST موجود برای identifiers و aliasهایی که پیشاپیش resolve شده‌اند کافی است. Model-specific AST node لازم شناخته نشد. Model→AST مستقیم نیز ضرورت ندارد.

### Renderer

Renderer باید AST/dialect را render کند؛ Model metadata را نمی‌شناسد. در source فعال evidenceای برای چنین dependency یا نیازی نیست.

### Executor

Executor query API/AST و `BuiltQuery` را اجرا می‌کند و `ResultSet` را به callback می‌دهد. Model یا Model mapping را نمی‌شناسد؛ این مرز نباید برای اجرای query پایه به Model وابسته شود.

### Migration

در مسیر migration، reference تولیدی به Model metadata در این بررسی پیدا نشد. Builder فقط در migration executor به صورت production و در migration root به صورت test dependency دیده می‌شود. این شواهد integration Model/Migration را ثابت نمی‌کنند.

### پاسخ صریح دربارهٔ `query:builder → models:eloquent`

**Decision: Unresolved.** این edge را نباید بر اساس شواهد حاضر «جزء ضروری معماری نهایی» دانست: مصرف metadata در runtime ثابت نیست و source Builder queryهای رشته‌ای را اجرا می‌کند. اما evidence کافی برای حذف/جابجایی بی‌خطر همین حالا هم نداریم: دو import فعال Model در `CteInfoUser.kt` برای compilation نیاز به resolution دارند، و سازگاری مصرف‌کنندگان بیرونی قابل مشاهده نیست. پیشنهاد معماری صرفاً این است که پس از روشن‌شدن importها و downstream contract، Builder پایه Model-independent بماند و integration آینده در لایهٔ اختیاری بالادست قرار بگیرد.

## Unresolved Decisions

1. **تاریخچه و intent edge:** maintainer باید مشخص کند چرا `implementation(models:eloquent)` افزوده شده و آیا importهای `Users`/`UserPhones` بقایای ناخواسته‌اند یا contract عمدی.
2. **حذف یا جابه‌جایی edge:** لازم است مصرف‌کنندگان downstream و Gradle publication/variantهای واقعی، وابستگی احتمالی به artifact عبوری و سازگاری source/binary بررسی شوند. در این traceability، build حذف‌شده آزمایش نشده است.
3. **مالکیت integration آینده:** use case و API نهایی لازم است تا B/C/D از روی نیاز واقعی انتخاب شوند؛ source فعلی بین آن‌ها تصمیم نمی‌دهد.
4. **alias precedence:** قرارداد مالک روشن است، اما تصمیم اینکه adapter/API کجا default و explicit را resolve کند و برای مقدار absent/empty چه کند هنوز لازم است.
5. **DSL type/nullability:** اگر DSL typed خواسته شود، قرارداد جداگانهٔ property identity، type/nullability و operator لازم است؛ source فعلی آن را حمل نمی‌کند.
6. **commented APIs:** برای تعیین اینکه prototype قبلی بوده یا experiment کنارگذاشته‌شده، history/maintainer evidence لازم است؛ هیچ‌یک برای contract فعال کافی نیست.

## Implementation Readiness

`Status: Ready for Traceability`

مرز semantic استقلال Query Builder از Model و استقلال Model از Query Builder قابل مشاهده است، اما استقلال build فعلی برقرار نیست. تصمیم نگه‌داری/حذف edge به دلیل importهای فعال و فقدان شواهد downstream بسته نمی‌شود. محل integration آینده و مالکیت resolver alias نیز هنوز انتخاب نشده‌اند؛ پس این بررسی مجوز implementation یا تغییر Gradle نیست.
