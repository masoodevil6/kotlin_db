# مدل نسخهٔ ۱.۲: ردیابی فرادادهٔ مدل تا DSL سازندهٔ پرس‌وجو

## وضعیت

`Status: Ready for Traceability`

ردیابی source کامل شد. قراردادهای نام و alias از سوی مالک مشخص شده‌اند، اما کد فعال آن‌ها را از metadata مدل نمی‌خواند و تقدم alias را اعمال نمی‌کند. علاوه بر این، جهت dependency گراف Gradle با مرز مستقل از Model هم‌راستا نیست: `query:builder` به `models:eloquent` وابستگی build دارد. تصمیم‌های حل‌نشده و شواهد لازم در انتهای گزارش آمده‌اند.

## هدف

این گزارش رابطهٔ موجود میان `QBTable`/`QBColumn` و Query Builder را از روی source بررسی می‌کند. هدف، تفکیک قراردادهای اعلام‌شده از رفتار اجرایی، ردیابی عبور داده از Builder و AST تا Renderer و Executor، و مشخص‌کردن مرزهایی است که پیش از implementation آینده نیاز به تصمیم دارند.

هیچ source، test یا فایل دیگری در این مرحله تغییر نکرد. build، test، database introspection و runtime experiment اجرا نشد.

## معماری کنونی مدل

```text
data_base:core
├── IModelBase                 (interface خالی)
├── QBTable                    (annotation زمان اجرا برای class)
└── QBColumn                   (annotation زمان اجرا برای property)
           ↑
data_base:models:eloquent
├── IModel : IModelBase        (interface خالی)
├── BaseModel : IModel         (abstract class خالی)
└── Users / UserPhones         (دو class دارای annotation)
```

`IModelBase` و `IModel` هیچ عضو یا رفتار زمان اجرایی ندارند. در source بررسی‌شده، `IModel` تنها subtype مستقیم `IModelBase` و `BaseModel` تنها پیاده‌ساز آن است. دلیل طراحی این تفکیک در repository مستند نشده است. `BaseModel` پایهٔ ارث‌بری فعلی دو نمونه است؛ abstract بودن آن نیز رفتار اجرایی اضافه نمی‌کند.

| مدل | `QBTable` | ویژگی‌ها و `QBColumn` | سازنده/تغییرپذیری |
|---|---|---|---|
| `Users` | `name="user_users"`, `alias="uu"` | `userId: Int` → `id`, alias `u_user_id`, PK=true؛ `userName: String?` → `name`, `u_user_name`؛ `userFamily: String?` → `family`, `u_user_family`؛ `userAge: String?` → `age`, `u_user_age` | `class Users()`؛ ویژگی‌ها `val` و دارای default هستند. |
| `UserPhones` | `name="user_phones"`, `alias="up"` | `userPhoneId: Int` → `id`, alias `up_id`, PK=true؛ `userPhone: String?` → `phone`, `up_phone`؛ `userId: Int` → `user_id`, `up_user_id` | `class UserPhones()`؛ ویژگی‌ها `val` و دارای default هستند. |

این‌ها facts مربوط به دو نمونه‌اند، نه الزام عمومی constructor یا mutability برای Model. نام‌های Kotlin property با نام‌های ثبت‌شده در `QBColumn` تفاوت دارند. ویژگی `userAge` از نوع `String?` است؛ معنای پایگاه‌داده‌ای آن از source قابل استنتاج نیست.

## ردیابی QBTable

**شواهد مخزن:** declaration در core شامل `@Target(CLASS)`, `@Retention(RUNTIME)` و دو رشتهٔ `name` و `alias` با default برابر `""` است. دو مدل موجود مقادیر غیرخالی دارند. API فعال Query Builder رشتهٔ جدول و alias را جداگانه می‌پذیرد و Builder آن‌ها را در `QueryTableAst.table` و `tableAlias` می‌گذارد. Renderer فعال جدول را از AST می‌خواند و در حالت مجاز alias را با `As` می‌افزاید. Reader annotation فقط در comment دیده می‌شود.

**برداشت:** شکل داده‌ها و مقصد رشته‌ای با معنای table name و table alias سازگار است؛ مسیر فعال اما ارتباط annotation با این مقصدها را اجرا نمی‌کند. Renderer مسیر بررسی‌شده identifier را quote یا escape نمی‌کند. annotation خالی مجاز است؛ سیاست validation برای آن یافت نشد. schema qualification، casing و reserved identifierها نیز قرارداد مستندی ندارند. رفتار `null` در AST با رشتهٔ خالی annotation یکسان نیست؛ renderer در شرط alias، مقدار را با `""` می‌سنجد، نه با null-check صریح.

**Owner-provided contract clarification:** `QBTable.name = table name` و `QBTable.alias = default SQL table alias`.

**تصمیم:** معنای اعلام‌شده به‌عنوان clarification ثبت می‌شود، اما چون مصرف فعال annotation وجود ندارد، آن را رفتار اثبات‌شدهٔ repository نمی‌دانیم. ارتباط اجرایی، قواعد خالی/نامعتبر، schema، casing و quoting همچنان `Unresolved` هستند.

## ردیابی QBColumn

**شواهد مخزن:** declaration در core شامل `@Target(PROPERTY)`, `@Retention(RUNTIME)`, دو رشتهٔ `name` و `alias` با default خالی، و Boolean `primaryKey` با default `false` است. هر دو نمونهٔ Model برای یک property مقدار `primaryKey=true` دارند. Query API فعال نام ستون/qualifier را رشته‌ای می‌گیرد. alias صریح از API فعال به `QueryColumnsAst.ColumnAlias` می‌رود. annotation reader در `QueryColumnsBaseBuilder` کامنت است و مقصد پیشنهادی‌اش `ast.columnAlias` روی AST پایه است، در حالی که interface و class فعال AST پایه چنین عضوی ندارند؛ alias فعال SELECT روی node بیرونی `QueryColumnsAst` است.

**برداشت:** مقادیر نمونه با نام ستون پایگاه داده و label خروجی سازگارند، ولی مثال‌ها و نام propertyها به‌تنهایی قرارداد اجرایی نیستند. `primaryKey` metadata ذخیره‌شده است؛ هیچ reader یا رفتار Query مصرف‌کننده‌ای ندارد. migration، کلید اصلی را از API و AST مستقل خودش می‌سازد و به Model annotation وصل نیست.

**Owner-provided contract clarification:** `QBColumn.name = database column name`, `QBColumn.alias = default SELECT alias`, `QBColumn.primaryKey = primary-key metadata`.

**تصمیم:** این معانی را به‌عنوان قرارداد پیشنهادی مالک نگه می‌داریم، نه رفتار اثبات‌شده. پشتیبانی اجرایی همهٔ موارد `Unresolved` است. `primaryKey` در v1.2 وارد رفتار Query نمی‌شود و metadata جدا باقی می‌ماند. ساختار فعلی صرفاً flag هر property را دارد و قرارداد composite key را تعیین نمی‌کند.

## معنای نام مستعار

**Owner-provided contract clarification:** alias جدول در metadata، alias پیش‌فرض جدول است؛ `QBColumn.alias` alias پیش‌فرض SELECT است؛ alias صریح query باید alias پیش‌فرض Model را override کند.

**شواهد مخزن:** API فعال `table(table, alias)`، AST جدول را پر می‌کند. برای SELECT، Builder فعال `alias(alias)` را در `QueryColumnsAst.ColumnAlias` ذخیره می‌کند و `MySqlQueryColumnCapability` اگر مقدار non-null باشد، `As <alias>` را render می‌کند. مثال `A7ExampleSelectV1` هر دو را دستی وارد می‌کند: `table("user_users", "uu")`, `tableColumn("uu", "id")`, و `alias("user_id")`. مثال فقط ثابت می‌کند مسیر alias صریح کار می‌کند؛ Model metadata در آن نقشی ندارد.

**برداشت:** AST می‌تواند یک alias نهایی و حل‌شده را نگه دارد، بنابراین برای پیاده‌سازی آینده می‌توان alias صریح یا default را پیش از قرار دادن در `ColumnAlias` انتخاب کرد. اما source فعلی default Model را به آن field نمی‌رساند و resolver یا fallback ندارد. کد comment‌شدهٔ قدیمی alias را روی AST پایه می‌گذارد، نه nodeای که renderer alias SELECT را از آن می‌خواند.

**تصمیم:** طبق قاعدهٔ «اگر source semantics را ثابت نمی‌کند، `Unresolved`»، هم default alias از Model و هم تقدم explicit-over-default در رفتار موجود `Unresolved` هستند. ساختار AST برای نگهداری نتیجهٔ انتخاب‌شده کافی است؛ این امکان معماری، evidence اجرای precedence نیست.

## ردیابی کلید اصلی

**شواهد مخزن:** `QBColumn.primaryKey` در annotation و دو Model وجود دارد؛ خوانشگر فعال یا reference اجرایی آن در Query Builder، Model runtime، validation یا ResultSet mapping پیدا نشد. کد annotation reader هم کامنت است و flag را استخراج نمی‌کند. Migration API/AST نمونه‌هایی برای primary key تک‌ستونی و چندستونی دارد، اما آن‌ها مستقل از Model هستند.

**برداشت:** در وضعیت جاری، این flag فقط مقدار metadata است. هیچ اثر query مانند projection، predicate یا ordering از آن ثابت نیست. نمونه‌های فعلی با علامت‌گذاری یک property در هر مدل سازگارند، ولی composite-key policy کلی را اثبات نمی‌کنند.

**تصمیم:** `QBColumn.primaryKey` را در v1.2 از Query Builder contract جدا نگه دار؛ معنای اجرایی و ارتباط احتمالی آینده‌اش با schema یا persistence نیازمند قرارداد مستقل است. این تصمیم هیچ API یا annotationی را تغییر نمی‌دهد.

## مرز AST کنونی

زنجیرهٔ اجرایی مشاهده‌شده برای SELECT:

```text
QueryRenderSelectBuilder
  ├── select { ... } → QuerySelectAst → QuerySelectBuilder
  │     └── addColumn → QueryColumnsAst
  │           ├── column { tableColumn(alias, name) } → QueryColumnsBaseAst
  │           └── alias(string) → ColumnAlias
  ├── table { table(name, alias) } → QueryTableAst
  └── where { ... } → QueryWhereAst / condition ASTs
```

`QueryTableAst` fieldهای nullable `table`, `tableAlias`, `cte`, `cteAlias` دارد. `QueryColumnsBaseAst` qualifier و column را در `tableAlias` و `column` می‌گذارد؛ `QueryColumnsAst` node پایه، aggregate method اختیاری و `ColumnAlias` را نگه می‌دارد. شرط‌ها با `QueryConditionsBuilder` به ASTهای سمت چپ، operation و سمت راست/پارامتر تبدیل می‌شوند. مقادیر identifier در AST رشته‌اند؛ property reference یا Kotlin type در آن حفظ نمی‌شود.

Builder سطح SELECT هر node را می‌سازد و به root AST می‌چسباند. Rendererهای dialect nodeها را از registry رندر می‌کنند. `MySqlQueryCapability` SELECT، table، joins، where و optionها را ترکیب می‌کند. بنابراین جدول، ستون، alias و predicate در معماری فعلی با string/AST دستی وارد می‌شوند.

**نتیجهٔ مرز:** برای یک query که نام جدول، qualifier، ستون و alias نهایی آن قبلاً resolve شده‌اند، AST فعلی آن مقادیر را نمایش می‌دهد. AST کنونی provenance مقدار (Model default یا explicit)، property identity و اطلاعات نوع را نگه نمی‌دارد.

## ردیابی بازتاب

- Annotationها `RUNTIME` retention دارند، اما retention به معنی وجود reader فعال نیست.
- `findAnnotation<QBTable>()` و `findAnnotation<QBColumn>()` فقط در بدنه‌های کامنت‌شدهٔ `QueryTableBuilder`/`QueryColumnsBaseBuilder` پیدا شدند.
- reader پیشنهادی جدول `name` و `alias` را به `QueryTableAst` می‌فرستاد.
- reader پیشنهادی ستون `name` را به column-base AST و alias را به `ast.columnAlias` همان AST می‌فرستاد؛ در قرارداد فعال AST پایه، این field وجود ندارد. alias SELECT واقعی در `QueryColumnsAst.ColumnAlias` است.
- caching یا metadata cache پیدا نشد. اجرای reflection یا نگرانی performance برای Model metadata از source جاری قابل گزارش نیست.

**تصمیم:** reader نساز و رفتار reader آینده را فعلاً قطعی نکن. لازم است مقصد metadata و شکل property reference پیش از implementation مشخص شود.

هیچ candidateای به‌دلیل extensibility آینده به‌تنهایی `Adopt` نشده است. مدل→Query یک جهت طراحی مجاز از سوی درخواست است؛ implementation موجود چنین مسیری ندارد. برعکس، dependency واقعی Gradle از Query Builder به Model وجود دارد و باید در تصمیم module/dependency حل شود.

## تحلیل زبان آیندهٔ شبیه SQL

نحوهای `select(Users.id, Users.name).from(Users)`, `Users.id as userId`, و `where(Users.name like ...)` در source فعال پیدا نشدند. Query Builder فعلی receiver/lambda-based است و string identifier می‌گیرد. این نحوها فقط future candidate هستند.

AST موجود می‌تواند خروجی ساده و از پیش resolve شده را بپذیرد، ولی پشتیبانی از class/property symbols، selection typed، نام مستعار با provenance یا operator type-safe را نشان نمی‌دهد. این تفاوت‌ها به‌تنهایی اثبات نمی‌کنند که حتماً Symbol Layer یا AST جدید لازم است.

## ایمنی نوع

ویژگی‌های `Users` و `UserPhones` نوع Kotlin مشخص دارند (`Int`, `String?`)، اما Query AST و API شناسه‌ها را با `String?` نگه می‌دارند. مسیر فعلی property type را از Model به AST انتقال نمی‌دهد. Generic بودن بعضی پارامترهای مقدار در condition API پیوندی به نوع یک property مدل ایجاد نمی‌کند.

هیچ Kotlin→DB type inference از source اثبات نمی‌شود. تمایز احتمالی `Column<Int>` و `Column<String>` در DSL آینده نیازمند API/contract type-safe جداگانه است؛ scope و operatorها هنوز تعیین نشده‌اند. **تصمیم: `Unresolved`** برای type semantics در DSL آینده؛ نگاشت به نوع پایگاه داده `Defer`.

## تهی‌پذیری

`String?` و `Int` فعلاً فقط نوع/تهی‌پذیری Kotlin propertyهای نمونه را مشخص می‌کنند. annotation `QBColumn` فیلد nullability ندارد و هیچ reader یا expression typeای nullability را از Model منتقل نمی‌کند. DB nullability از Kotlin nullability قابل استنتاج نیست.

**تصمیم:** معنای Kotlin property موجود روشن است؛ propagation به query expression یا ستون پایگاه داده `Unresolved` است و تا تعیین type contract وارد implementation scope نمی‌شود.

## مرز مدل → Migration

در source production مربوط به Migration reference فعال به `QBTable`, `QBColumn`, `IModelBase` یا `models:eloquent` پیدا نشد. Migration schema را از API/AST خودش می‌سازد. شباهت نام جدول/کلید در مثال‌ها و تست‌های Migration اتصال به Model metadata را ثابت نمی‌کند.


## جهت وابستگی

**جهت source فعال:** Model classes به `core` وابسته‌اند؛ Query API به core و AST وابسته است؛ Builder کد فعالش API/AST رشته‌ای را اجرا می‌کند و class مدل را مصرف نمی‌کند.

**جهت Gradle واقعی:** `query:builder` با `implementation(project(":data_base:models:eloquent"))` به Model وابسته است. بنابراین گزارهٔ «هیچ dependency اجباری Query→Model در build graph وجود ندارد» با Gradle فعلی نادرست است، حتی اگر Model برای اجرای API رشته‌ای از نظر مفهومی لازم نباشد. `query:dialect` نیز به Builder وابسته است و executor آن را می‌گیرد.

**برداشت و تصمیم:** boundary مطلوبِ Query قابل استفاده بدون Model از طریق API رشته‌ای/source-level قابل تصور است، اما استقلال build/module فعلی ثابت نیست. منطق و مصرف‌کنندگان dependency موجود ناشناخته‌اند؛ آن را تغییر ندادیم. حفظ dependency، حذف آن یا جابه‌جایی integration به محل دیگر `Unresolved` است و به بررسی قصد مالک ماژول و compatibility مصرف‌کنندگان نیاز دارد.

## مرز تولید SQL

Builder ورودی‌های lambda را به AST تبدیل می‌کند؛ MySQL dialect capabilityها را برای AST register می‌کند؛ renderer از AST رشتهٔ SQL می‌سازد. در مسیر جدول، table و alias مستقیم درج می‌شوند. در مسیر ستون، qualifier و column مستقیم به هم افزوده می‌شوند و alias SELECT غیر-null با `As` درج می‌شود. این identifierها در capabilityهای بررسی‌شده quote/escape نمی‌شوند.

`tableAttribute(String)` نیز در API فعال وجود دارد و به‌صورت متن render می‌شود؛ این صرفاً توصیف رفتار موجود است، نه پیشنهاد افزودن escape hatch جدید. Query executor با `DialectSelector`، AST را render می‌کند، `BuiltQuery(query, params)` می‌سازد و آن را به execute لایهٔ database می‌سپارد. در SELECT callback نوع `ExecuteResult<ResultSet>` دریافت می‌کند.

**تصمیم:** Model نباید SQL تولید کند؛ مرز فعلی Builder→AST→dialect Renderer مسئول تبدیل به SQL است. سیاست identifier quoting/escaping و validation در مسیر مشاهده‌شده وجود ندارد یا دست‌کم در capabilityهای این traceability دیده نشد؛ مسئولیت و policy نهایی `Unresolved` است.

## قرارداد نهایی

### قرارداد و clarification مالک

مالک این معانی را روشن کرده است: `QBTable.name` نام جدول، `QBTable.alias` نام مستعار پیش‌فرض جدول، `QBColumn.name` نام ستون پایگاه داده، `QBColumn.alias` نام مستعار پیش‌فرض SELECT، و alias صریح query دارای تقدم است. این موارد **Owner-provided contract clarification** هستند و repository evidence محسوب نمی‌شوند.

### آنچه source اکنون اجرا می‌کند

- Model chain فعلی marker-only است؛ `BaseModel` خالی است.
- Annotationها runtime-retained و دارای fieldهای فوق هستند؛ دو Model نمونه آن‌ها را مقداردهی می‌کنند.
- Readerهای `QBTable`/`QBColumn` و overloadهای Model-based کامنت هستند؛ هیچ مسیر فعال از Model metadata به Query AST پیدا نشد.
- API فعال رشته‌های جدول، qualifier، ستون و alias صریح می‌پذیرد.
- AST موجود می‌تواند جدول، alias جدول، ستون qualified و یک alias نهایی SELECT را نگه دارد.
- alias صریح در مسیر دستی render می‌شود؛ default alias و precedence در source فعلی اجرا نمی‌شوند.
- `primaryKey` در Query مصرف نمی‌شود.
- Query به Model در Gradle وابستگی دارد، پس استقلال module/build فعلاً برقرار نیست؛ مصرف اجرایی metadata از آن dependency ثابت نشده است.

برای SQL ساده‌ای که مقادیرش پیشاپیش تعیین شده‌اند، عبارت زیر دربارهٔ AST موجود برقرار است:

```text
No new Model-specific AST node required
```

این نتیجه مجوز ساختن Model Adapter، Symbol Layer یا node جدید نیست و DSL typed آینده را هم تعیین تکلیف نمی‌کند.

### مواردی که قرارداد اجرایی‌شان حل نشده

تا وقتی reader، مقصد درست alias، قواعد مقدار خالی/نامعتبر و ownership ماژولی روشن نشوند، قراردادهای اعلام‌شده را نباید به‌عنوان رفتار موجود معرفی کرد. Kotlin type/nullability به DB type/nullability نگاشت نشده است. Renderer SQL را تولید می‌کند؛ اما policy quoting/escaping برای شناسه‌ها در capabilityهای بررسی‌شده وجود ندارد. Migration و ResultSet mapping خارج از مرز Model→Query این نسخه می‌مانند.

## تأثیر بر سازگاری

هیچ تغییری اعمال نشده، پس compatibility فعلی تغییر نکرده است. فعال‌سازی metadata API ممکن است امضاهای عمومی تازه یا مقصد field متفاوت بخواهد. حذف dependency `query:builder → models:eloquent` نیز می‌تواند resolution گراف Gradle را برای مصرف‌کنندگان فعلی عوض کند؛ پیش از هر تغییر باید usage بیرونی و دلیل dependency مشخص شود.

## برنامهٔ آزمون

آزمون‌ها اجرا یا تغییر داده نشده‌اند. برای implementation آینده، پس از بسته‌شدن تصمیم‌ها:

1. کشف `QBTable` و `QBColumn` روی `Users` و `UserPhones`، از جمله annotation غایب/مقادیر خالی طبق policy نهایی.
2. تبدیل table name و default table alias به `QueryTableAst` و render خروجی.
3. قراردادن `QBColumn.name` در column-base AST و default alias در **node صحیح** `QueryColumnsAst.ColumnAlias`.
4. اثبات precedence: بدون alias صریح از Model default استفاده شود؛ با alias صریح همان مقدار render شود؛ empty explicit alias طبق policy نهایی تست شود.
5. بررسی mapping به AST موجود و SQL رندرشده برای دو Model نمونه.
6. identifier معمولی، schema-qualified، reserved، خالی و نامعتبر پس از تعیین quoting/validation policy؛ source فعلی quoting این مسیر را نشان نمی‌دهد.
7. regression برای APIهای دستی table/column/alias و queryهای بدون Model.
8. آزمون dependency/build consumer بدون Model فقط پس از تصمیم دربارهٔ Gradle edge.
9. type/nullability tests فقط در صورت تصویب قرارداد typed؛ نوع Kotlin را به نوع DB تعمیم نده.

مواردی که policy آن‌ها unresolved است، شرط آزمون آینده‌اند و نه قرارداد implementation پذیرفته‌شده.

## تصمیم‌های حل‌نشده

### ۱. آیا owner-provided metadata semantics رفتار قراردادی اجرایی هستند؟

**تصمیم:** نام جدول، نام مستعار جدول، نام ستون و نام مستعار پیش‌فرض با active source قابل اثبات نیستند.

**دلیل حل‌نشده‌ماندن:** مقادیر نمونه و AST مقصد سازگارند، ولی annotation reader کامنت شده و قرارداد executable/testی وجود ندارد.

**شواهد لازم:** تصمیم تاییدی مالک برای الزام‌های اجرایی و مشخصات empty/null/invalid، همراه با قرارداد property/class discovery.

**قرارداد متأثر:** semantics `QBTable.name/alias`, `QBColumn.name/alias`.

### ۲. تقدم alias صریح بر Model default

**تصمیم:** `Unresolved` در رفتار فعلی.

**دلیل حل‌نشده‌ماندن:** Builder/Renderer alias صریح دستی را پشتیبانی می‌کنند، اما default مدل به AST فعال نمی‌رسد و precedence resolver نداریم.

**شواهد لازم:** قرارداد صریح برای absent/empty explicit alias و تعیین مرحله‌ای که winner را در `ColumnAlias` قرار می‌دهد.

**قرارداد متأثر:** SELECT output alias و backward compatibility برای default خالی annotation.

### ۳. مقصد درست و API خواندن `QBColumn.alias`

**تصمیم:** `Unresolved`.

**دلیل حل‌نشده‌ماندن:** reader کامنت‌شده alias را روی column-base AST می‌گذارد؛ AST فعال alias SELECT را در `QueryColumnsAst.ColumnAlias` نگه می‌دارد. API property-based فعالی وجود ندارد.

**شواهد لازم:** تصمیم دربارهٔ class/property reference و mapping metadata به هر دو node؛ قرارداد مصرف‌کنندهٔ property annotation.

**قرارداد متأثر:** Adapter/translator، reflection، AST lowering و default alias.

### ۴. جهت dependency و محل یکپارچه‌سازی

**تصمیم:** `Unresolved`.

**دلیل حل‌نشده‌ماندن:** Gradle `query:builder` را به `models:eloquent` وابسته می‌کند ولی source مصرف فعال Model ندارد. Model هم Query dependency ندارد؛ ownership این edge توضیح داده نشده.

**شواهد لازم:** علت dependency از maintainer، مصرف‌کنندگان واقعی ماژول و نیازهای build/API آن‌ها؛ سپس تصمیم محل integration که Query Builder را برای API پایه به Model محتاج نکند.

**قرارداد متأثر:** استقلال Query Builder، ABI/source/build compatibility و مرز ماژول.

### ۵. نیاز به Adapter یا Symbol Layer

**تصمیم:** `Unresolved` برای وجود یکپارچه‌سازی reusable؛ `Defer` برای ساخت هر abstraction در این مرحله.

**دلیل حل‌نشده‌ماندن:** API رشته‌ای موجود است و مصرف‌کننده‌های Model متعدد/نیاز به reuse از source ثابت نشده‌اند.

**شواهد لازم:** use caseهای مصرف‌کننده، شکل DSL موردنیاز، نیاز به type safety و module ownership.

**قرارداد متأثر:** API و dependency direction.

### ۶. Type safety و nullability DSL

**تصمیم:** `Unresolved`.

**دلیل حل‌نشده‌ماندن:** AST شناسه‌ها را string می‌کند؛ نوع و nullability Model به DB/query expression وصل نیستند.

**شواهد لازم:** DSL/operator/result contract و تصمیم مجزای Kotlin type→DB type؛ نوع Kotlin به‌تنهایی کافی نیست.

**قرارداد متأثر:** typed column/expression، predicate، و nullability propagation.

### ۷. identifier policy

**تصمیم:** `Unresolved` برای empty/invalid، schema/casing/reserved و quoting/escaping.

**دلیل حل‌نشده‌ماندن:** annotation default خالی است؛ rendererهای بررسی‌شده identifier را مستقیم interpolate می‌کنند و policy validation/quoting نشان نمی‌دهند.

**شواهد لازم:** grammar شناسه و تصمیم dialect-specific دربارهٔ quote/escape/validation، به‌علاوهٔ آزمون‌های متناظر.

**قرارداد متأثر:** امنیت و SQL rendering، metadata اعتبارسنجی‌شده و سازگاری خروجی.

### ۸. semantics اجرایی `primaryKey`

**تصمیم:** `Separate Contract` برای v1.2؛ مصرف آینده `Unresolved`.

**دلیل حل‌نشده‌ماندن:** فقط flag annotation موجود است؛ خوانشگر/مصرف‌کنندهٔ Model ندارد و Migration مستقل عمل می‌کند.

**شواهد لازم:** نیاز مصرف‌کننده‌ای مشخص و قرارداد آن که query behavior را از schema/persistence behavior جدا کند.

**قرارداد متأثر:** metadata کلید اصلی و composite key.
